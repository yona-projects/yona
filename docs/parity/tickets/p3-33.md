# P3-33: hg4j PR 병합이 매번 대상 저장소 전체를 재구성하는 성능 문제 — in-core 병합 커밋 API 필요

## 배경

[[tickets/p3-27|P3-27]]에서 구현한 `PullRequestServiceImpl.hgMerge()`(Mercurial 프로젝트의 실제
PR 병합 확정)는 병합 커밋 하나를 만들기 위해 매번:

1. `Files.createTempDirectory`로 임시 디렉터리 생성
2. `Hg.cloneRepository()`로 **대상 프로젝트 저장소 전체를 임시 디렉터리에 클론**
3. 대상 브랜치로 `update`(전체 작업 디렉터리 체크아웃)
4. 소스 프로젝트에서 `fetch`
5. `merge` → `commit`(진짜 병합 커밋 생성)
6. 임시 클론 → 원본 저장소로 `push`
7. 임시 디렉터리 전체 삭제

를 수행한다. 이 구조가 실제로 얼마나 비용이 큰지 `CloneCommand.call()`을 직접 읽어 확인한
결과, 예상보다 훨씬 심각했다:

- **hg4j의 "로컬 클론"은 실제 Mercurial의 `hg clone`처럼 스토어를 하드링크하지 않는다.**
  `Hg.init()`(빈 저장소)을 만든 뒤 `PullCommand`로 **전체 히스토리를 changegroup 포맷으로
  처음부터 다시 인코딩→디코딩→복원**한다 — 이건 파일 복사가 아니라 저장소 전체 리비전
  개수에 비례하는 CPU 작업이다.
- 이어서 `checkoutLatest()`가 대상 브랜치의 **모든 추적 파일을 작업 디렉터리에 실제로
  써 내려가는 전체 체크아웃**을 수행한다.
- 이 두 단계 모두 **PR이 실제로 바꾼 파일 개수/커밋 개수와 무관하게, 대상 저장소 전체
  크기(히스토리 길이 + 파일 개수/크기)에 비례**한다. PR 하나가 파일 2~3개만 바꿔도, 저장소가
  커밋 수천 개짜리면 병합할 때마다 그 전체 비용을 다시 치른다.
- 동시에 PR 여러 개가 병합되면 이 비용이 동시 클론 개수만큼 곱해진다(디스크 사용량도 함께
  증가).

[[tickets/p3-27|P3-27]]의 다른 세 메서드(`previewMerge`/`attemptMerge`/`updateMerge`)는
`TreeMergeCommand`(작업 디렉터리를 건드리지 않는 순수 계산)를 대상 저장소에 직접 써서 이미
이 문제가 없다 — 문제는 **실제 확정 병합(`merge()`) 하나뿐**이다.

## 왜 해결 가능해 보이는가 (사전 조사, 착수 시 재검증 필요)

`TreeMergeCommand.call()`이 반환하는 `TreeMergeResult`는 이미 병합 결과를
**"디스크에 쓰지 않은 순수 데이터"**로 갖고 있다:

- `getChangedFiles(): Map<String, byte[]>` — 병합 후 추가/덮어써야 할 경로→최종 콘텐츠.
- `getRemovedFiles(): Set<String>` — 삭제해야 할 경로.
- `getChangedModes(): Map<String, Integer>` — 실행권한 등 모드 변경.

그리고 `Revlog`에는 이미 **로컬 콘텐츠로 새 리비전을 추가하는 범용 API**가 있다:

```java
public synchronized byte[] appendRevision(byte[] content, int parent1, int parent2, ...)
```

`CommitCommand`(일반 커밋 경로)도 내부적으로 결국 이 메서드를 호출해서 filelog/manifest/
changelog에 새 리비전을 쓴다 — 다만 그 전에 "무엇이 바뀌었는지"를 **디스크의 실제 파일을
읽고 dirstate와 비교**해서 알아낸다는 점만 다르다. `TreeMergeResult`가 그 "무엇이 바뀌었는지"
정보를 이미 순수 계산으로 갖고 있으므로, 원리적으로는:

1. `TreeMergeResult`의 변경분으로 각 파일의 filelog에 새 리비전을 직접 추가(`appendRevision`)
2. 부모 manifest(들)를 로드해 변경분을 반영한 새 manifest 텍스트를 조립해 manifest revlog에
   추가
3. p1/p2(병합 양쪽 부모)를 가진 changelog 리비전을 조립해 changelog revlog에 추가
4. 대상 bookmark를 새 changeset으로 전진(`BookmarkCommand`, 이미 존재)
5. `repository.lockStore()`/`lockWorkingCopy()`(이미 `CommitCommand`가 쓰는 락)로 전체를
   보호

로 **작업 디렉터리를 한 번도 건드리지 않고** 병합 커밋을 만들 수 있어 보인다. 이러면 클론/
체크아웃/push/삭제가 전부 사라지고, 비용이 "대상 저장소 전체 크기"가 아니라 "이 병합이 실제로
바꾼 파일 개수"에 비례하게 된다(JGit의 inCore 병합과 동등한 성격).

포크 PR(fromProject != toProject)의 경우도, 이미 `previewMerge`/`attemptMerge`가 검증한 대로
`FetchCommand`로 fromProject의 리비전을 toProject 저장소에 직접(작업 디렉터리 없이) 가져올
수 있으므로, 그 부분은 그대로 재사용 가능해 보인다 — 클론이 필요 없어지면 push도 필요 없어져서
(대상 저장소에 직접 쓰므로) [[tickets/p3-27|P3-27]]에서 만든 "포크 브랜치 흔적 정리
(`hgImportBranchWithoutBookmarkLeak`)" 로직도 그대로 재사용 가능해 보인다.

## 범위 (착수 시 설계 문서 승인 후 확정)

상세 설계는 `docs/yona-wiki/plans/p3-33-hg4j-incore-merge-commit.md` 참고. 요약:

1. hg4j에 새 API 신설(가칭 `InCoreMergeCommitCommand` 또는 기존 `CommitCommand`/
   `MergeCommand`에 in-core 모드 추가 — 설계 문서에서 최종 결정) — `TreeMergeResult` +
   두 부모 노드ID + 커밋 메타데이터(author/message/date)를 받아 filelog/manifest/changelog에
   직접 쓰고 새 changeset 노드ID를 반환.
2. yona `PullRequestServiceImpl.hgMerge()`를 이 새 API 사용으로 재작성 — 임시 클론/체크아웃/

4. 실사용 검증(실제 hg 바이너리로 만든 결과 changeset이 정상적으로 읽히는지까지 확인 —
   hg4j로 쓴 리비전을 real `hg`가 깨지지 않고 읽어들이는지는 항상 별도로 검증해야 하는
   이 저장소의 관례).

**설계 문서 대비 달라진 점 / 열린 질문 결론**:

1. **락 범위(열린 질문 1번)**: `lockStore()` 하나만 사용하고 `lockWorkingCopy()`는 잡지 않는다.
   `MergeCommitCommand`는 dirstate/작업 디렉터리를 전혀 읽거나 쓰지 않으므로(순수 revlog 쓰기)
   워킹카피 락이 보호할 대상 자체가 없다 — `CommitCommand`가 wlock을 잡는 이유(dirstate 백업/
   갱신, 작업 디렉터리 파일 스캔)가 이 커맨드에는 해당하지 않음을 코드 감사로 확인.
   `MergeCommitCommandTest.neverTouchesTheWorkingDirectoryOrDirstate`로 회귀 방지.

2. **manifest 텍스트 포맷(열린 질문 2번)**: 실제로 깔끔하게 분리됐다 — `extractManifestNode`/
   `buildChangelogText`를 package-private으로 완화하는 것만으로 충분했고, dirstate 관련 로직과의
   결합 문제는 없었다(설계 문서가 우려했던 "지저분해질 경우 별도 구현" 시나리오는 발생하지 않음).
   다만 **treemanifest 저장소는 이번 범위에서 다루지 않는다** — `CommitCommand`의 treemanifest
   재귀 직렬화(`writeTreeManifestDir`)는 재사용하지 않고 flat manifest 직렬화만 구현했다(아래
   "이번 범위에서 고치지 않은 것" 참고).

3. **copy/rename 추적(열린 질문 3번)**: `TreeMergeResult`는 원래 copy/rename 메타데이터를 담고
   있지 않았다 — 설계 문서 예상대로 hg4j에 신규 구현했다(`getCopiedFiles()`). 3-way로 실제
   블렌드된 파일(양쪽 다 수정)에는 fresh copy 메타데이터를 만들지 않는다(실제 hg도 그 시점에는
   새 copy 레코드를 만들지 않음 — `mergecopies()`의 전체 rename-감지 알고리즘까지는 이번
   범위에서 재현하지 않았다, 아래 한계 참고). "theirs에서 그대로 채택"되는 두 경우만 원본
   메타데이터를 전달한다.

4. **실제 hg 바이너리 호환성(열린 질문 4번)**: 구현 완성 후 실제 `hg` CLI(로컬 설치, 7.2.2)로
   검증 완료 — 아래 "실사용 검증" 참고.

5. **동시성(열린 질문 5번)**: 설계 문서 결론(JGit 낙관적 동시성 + fail-fast 스토어 락) 그대로
   구현. `hgMerge()`가 `TreeMergeCommand` 계산 직후, `MergeCommitCommand.call()` 호출 직전에
   `hg.bookmark().call()[toBookmark]`를 다시 읽어 `leftHex`와 여전히 같은지 확인하고, 다르면
   `PullRequestException`을 즉시 던진다(대기 없음, 재시도는 호출자 몫).
   **구현 중 발견한 실제 버그(설계 문서에 없던 사항)**: 포크 PR 시나리오에서 `hgImportBranch
   WithoutBookmarkLeak`의 `fetch()`가 fromProject에 toBookmark와 "우연히 같은 이름"의 bookmark가
   있으면(흔한 경우 — 둘 다 "master") `BookmarkCommand.mergeFromRemote()`를 통해 그 이름의
   로컬 bookmark까지 fromProject 쪽 위치로 전진시켜버리는 것을 낙관적 동시성 검사가 실제로
   잡아냈다(테스트가 `PullRequestException`으로 실패하며 드러남). 이건 "동시 수정"이 아니라
   fetch 자신의 부수효과이므로, fetch 직후 toBookmark가 leftHex와 다르면 즉시 leftHex로
   되돌리는 보정을 `hgMerge()`에 추가했다(`hgImportBranchWithoutBookmarkLeak` 자체는 손대지
   않음 — attemptMerge/previewMerge는 이 부수효과에 의존하지 않아 영향 없음). 이 버그는 P3-27
   구현에도 이미 존재했으나 임시클론+`hg.commit()`의 활성 bookmark 자동 추종 동작에 의해 우연히
   가려져 있었다 — in-core 재작성과 낙관적 동시성 검사가 처음으로 이 문제를 표면화시켰다.

**실사용 검증(real hg CLI, 로컬 설치 Mercurial 7.2.2)**:
`MergeCommitCommandRealHgInteropTest`가 실제 `hg bookmark`/`hg commit`으로 두 갈래(ours/theirs)를
만든 뒤 hg4j `TreeMergeCommand`+`MergeCommitCommand`로 병합 changeset을 생성하고, 그 결과를 다시
실제 `hg verify`(무결성 오류 없음)/`hg log`(부모가 정확히 ours/theirs)/`hg cat`(병합된 내용
정확)/`hg manifest`(양쪽 파일 모두 나열)/`hg update`(체크아웃 성공)로 왕복 검증했다. 별도
테스트로 실제 `hg copy`가 만든 copy 메타데이터가 in-core 병합을 거쳐도 살아남아 `hg log
--follow`가 원본 커밋까지 따라감을 확인했다.

**이번 범위에서 고치지 않은 것(발견했지만 손대지 않음)**:
- **treemanifest 저장소**: `MergeCommitCommand`는 flat manifest만 지원한다. `CommitCommand`는
  treemanifest를 완전히 지원하므로, treemanifest 저장소에서 PR 병합을 호출하면 이번 구현은
  실패하거나 부정확한 manifest를 만들 수 있다 — 설계 문서의 "비목표"에 명시되진 않았지만
  실제로 다루지 않은 범위. yona가 현재 treemanifest 저장소를 프로비저닝하지 않으므로 실사용
  영향은 없다고 판단했으나, 별도 확인/티켓 필요.
- **exp-copies-sidedata-changeset(사이드데이터 copy tracing)**: `CommitCommand`는 이 실험적
  포맷의 저장소에 `SD_FILES` 사이드데이터를 changelog 리비전에 붙이지만, `MergeCommitCommand`는
  붙이지 않는다(늘 `sidedataContainer=null`). 이 포맷을 쓰는 저장소가 있다면 병합 커밋만
  사이드데이터 copy tracing 정보가 빠질 수 있다 — 정확성에는 영향 없음(파일 자체의 copy
  메타데이터는 정상 기록됨), 최적화 정보 손실만 있음.
- **fileindex-v1 포맷의 fncache 대응 트래킹**: `CommitCommand`는 `isFileIndexV1()` 저장소에서
  `FileIndex` 트라이도 함께 갱신하지만 `MergeCommitCommand`는 이를 갱신하지 않는다(항상 표준
  `fncache`만 갱신) — fileindex-v1 저장소에서 병합 커밋을 만들면 `hg verify`가 불일치를 보고할
  가능성이 있다. yona가 이 실험적 포맷을 쓰는 저장소를 만들지 않으므로 실사용 영향은 없다고
  판단.
- **`mergecopies()` 수준의 완전한 rename 감지**: 이번 구현은 "theirs에서 그대로 채택"되는
  파일의 기존 copy 메타데이터만 전달한다 — 실제 hg의 `mergecopies()`처럼 병합 자체에서 새로운
  rename을 추론(예: 양쪽이 각자 다른 이름으로 같은 파일을 옮긴 경우의 rename-rename 충돌 감지)
  하지는 않는다. 설계 문서 범위(copy 메타데이터 보존)를 넘는 항목으로 판단해 다루지 않았다.
- **`hgImportBranchWithoutBookmarkLeak`의 근본적인 "우연한 동명 bookmark 오염" 가능성**: 위
  5번에서 `hgMerge()`에 국소 보정을 추가했지만, `hgAttemptMerge`/`hgPreviewMerge`가 공유하는
  `hgComputeMerge()`/`hgImportBranchWithoutBookmarkLeak()` 자체는 고치지 않았다 — 현재는 이
  두 함수가 fetch 후 toBookmark의 실제 값에 의존하지 않아 영향이 없지만, 근본 원인(fetch가
  fromBookmark 외의 다른 bookmark까지 건드릴 수 있음)은 여전히 남아 있다. 향후 이 함수들이
  toBookmark 값에 의존하는 방향으로 확장되면 재발할 수 있다 — 별도 개선 필요 여부는 후속 판단.
