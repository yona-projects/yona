# P3-14: yona를 OAuth2 서버(Authorization Server)로 제공 — 제3자 앱의 "Sign in with yona"/위임 API 접근 지원

## 원본 표 정보

- **우선순위 구분**: P3
- **상태(원본 체크박스)**: `[ ]`
- **비고(원문)**: **2026-09-06 사용자 제안, 코드 0줄 — 설계 전.** 목표: 현재 yona는 OAuth2 **클라이언트** 역할만 한다(`config/oauth2/` 패키지의 `CustomOAuth2UserService`/`OAuth2UserInfoFactory`/`OAuth2AccountMergeService`/`YonaOAuth2User` — GitHub/Google 같은 외부 IdP로 로그인하는 소셜 로그인 전용, `SecurityConfig.kt`엔 `.oauth2Login { }`만 있고, `build.gradle.kts`엔 `spring-boot-starter-oauth2-client`만 있을 뿐 `-authorization-server`는 없음 — 코드로 확인). 이번 제안은 반대 방향이다 — **yona 자신이 OAuth2 인가 서버(Provider)가 되어, 제3자 애플리케이션이 "Sign in with yona"로 로그인하거나 사용자 동의 하에 yona API(이슈/PR/저장소)에 위임 접근하도록** 지원하는 것(GitHub의 OAuth Apps와 동등한 개념). **기존 관련 계획과의 관계(중복 설계 주의, 착수 전 반드시 재확인)**: [[tickets/p3-07|P3-07]]이 이미 정확히 같은 라이브러리(`spring-security-oauth2-authorization-server`)로 **MCP 리소스 서버 보호 전용** 인가 서버를 도입하기로 설계해뒀다(`docs/yona-wiki/plans/p3-07-mcp-server.md`, 아직 미구현·`status: planned`) — 이 항목은 그 인가 서버를 MCP 클라이언트(Claude 등록)뿐 아니라 **범용 제3자 OAuth 클라이언트 등록**까지 확장하는 것으로 볼 수 있어, 별개로 새로 만들면 안 되고 **[[tickets/p3-07|P3-07]]의 인가 서버 인프라를 그대로 확장**해서 구현해야 한다(반대로 이 항목을 먼저 만들면 [[tickets/p3-07|P3-07]]이 그 위에 올라타는 구조도 가능 — 착수 순서는 사용자 결정 필요). [[tickets/p3-02|P3-02]]가 이미 만든 Fine-grained 토큰 스코프 체계(`ApiTokenScopeGroup`, 8개 그룹)를 OAuth 스코프 축으로 그대로 재사용할 수 있는지 검토 필요(중복 설계 방지). [[tickets/p3-06|P3-06]](yona가 SAML2/OIDC의 **클라이언트**가 되어 사내 IdP로 로그인)과는 방향이 정반대라 블로커 관계 없음([[tickets/p3-07|P3-07]] 문서가 이미 같은 논리로 [[tickets/p3-06|P3-06]]과의 독립성을 확인해둠). **미결 설계 사항(전부 미착수)**: (1) OAuth 클라이언트 등록 방식 — 정적 사전등록만 할지, GitHub OAuth Apps처럼 사용자가 웹 UI에서 직접 앱을 등록하는 셀프서비스를 지원할지, RFC7591 Dynamic Client Registration([[tickets/p3-07|P3-07]]이 이미 채택 예정)까지 열지, (2) 동의 화면(consent screen) UI 신규 필요, (3) 발급 토큰의 스코프 축을 [[tickets/p3-02|P3-02]]의 `ApiTokenScopeGroup`과 통일할지 별도로 만들지, (4) 사이트 관리자만 앱을 등록할 수 있게 할지 일반 사용자도 자신의 프로젝트 범위로 등록 가능하게 할지. 착수 전 [[tickets/p3-07|P3-07]]과 순서/책임 분담을 먼저 정해야 함.

## 완료 로그

- **2026-09-07 1라운드**: 착수 전 미결 설계 사항 4가지를 코드로 직접 확인해 확정 — (1) 클라이언트
  등록: DCR(RFC7591, MCP 등 자동등록)는 P3-07 그대로 유지, 별도로 사이트 관리자 UI(`/site/oauth-apps`)
  신설(정적 사전등록, 셀프서비스 아님) (2) 동의 화면: P3-07의 `OAuthConsentController`가 이미
  클라이언트 종류 무관하게 범용이라 재사용, 신규 불필요 (3) 스코프 축: P3-07이 이미
  `ApiTokenScopeGroup`/`ApiTokenPermission`으로 통일해둠, 그대로 재사용 (4) 등록 권한: 사이트
  관리자 전용(`OAuthAppsAdminController`의 `checkAdmin`).
  발급 가능한 리소스를 `/mcp` 하나에서 `ProtectedResource`(mcp/api) 레지스트리로 일반화하고,
  `/api/v1/**`에 OAuth2 JWT 인증 + [[tickets/p3-02|P3-02]] 스코프 인가(`OAuthApiScopeAuthorizationFilter`)를
  추가했다. OIDC("Sign in with yona")는 2라운드로 이월. 상세: `docs/yona-wiki/plans/p3-14-oauth2-provider.md`
  완료 로그 참고.
- **2라운드 착수 전 결정사항(2026-09-07 사용자 확정)**: UserInfo는 `profile`+`email` 스코프
  전부 노출(GitHub OAuth App과 동등한 수준). identity 스코프(openid/profile/email)는 전
  클라이언트 자동 포함이 아니라 앱 등록 시 관리자가 개별 선택. 상세: 계획서 완료 로그 참고.
- **2026-09-07 2라운드(OIDC, "Sign in with yona") — 완료**: `AuthorizationServerConfig`에
  `.oidc { }` 한 줄로 discovery(`/.well-known/openid-configuration`)/`/userinfo`/ID 토큰 발급을
  켜고, `scopes_supported`(profile/email 추가)/`claims_supported`(프레임워크가 기본 채워주지
  않는 필드라 직접 지정)를 커스터마이즈했다. identity 스코프(openid/profile/email)는
  `OAuthAppRegistrationService.availableScopes()`에 API 스코프와 같은 화이트리스트 축으로
  추가하고, 사용자 셀프서비스 등록 폼(`edit_oauth_apps_owned_new.html`)에 별도 섹션(체크박스 +
  plain-language 설명)으로 노출했다. 동의 화면(`consent.html`)도 openid/profile/email 세
  스코프에 한해 원문 스코프 문자열 대신 사람이 읽는 설명으로 대체했다(그 외 스코프는 1라운드와
  동일하게 원문 유지 — 기존에 별도 설명 메커니즘이 없었으므로 새로 만들지 않음).
  **클레임 매핑 설계**: ID 토큰의 identity 클레임(`name`/`email`/`email_verified`/`picture`)만
  직접 커스터마이즈하고(`ResourceIndicatorTokenCustomizer`가 `authorizedScopes` 기준으로
  gate), `/userinfo`는 프레임워크 기본 `DefaultOidcUserInfoMapper`를 그대로 사용한다 — 그
  기본 구현이 "ID 토큰에 이미 있는 클레임을 액세스 토큰의 스코프로 다시 필터링"하는 방식이라
  ID 토큰만 스코프 게이팅해서 채워두면 `/userinfo`에도 동일한 게이팅이 자동으로 적용된다(별도
  커스텀 매퍼 불필요, 과잉설계 회피). `sub`는 프레임워크가 이미 `principal.getName()`(=loginId)로
  채워둠.
  **실제로 발견된 버그(2개, 실측 확인 후 즉시 수정)**:
  (1) `OAuth2TokenCustomizer<JwtEncodingContext>` 빈을 새로 하나 더 추가하면 안 된다 —
  Spring이 이 타입 빈을 `ApplicationContext.getBeanProvider(type).getIfUnique()`로 조회해서,
  후보가 2개 이상이면 `@Primary` 없이는 **예외 없이 조용히 null을 반환**한다(즉 "둘 다 적용"이
  아니라 "1라운드의 RFC8707 오디언스 스탬핑까지 포함해 둘 다 무시"). 그래서 ID 토큰 클레임
  매핑을 별도 클래스로 분리하지 않고 기존 `ResourceIndicatorTokenCustomizer` 하나에 합쳤다.
  (2) `OAuthAuthorization`/`JpaOAuth2AuthorizationService`가 1라운드 시점엔 "OIDC 미사용"이라는
  이유로 `oidc_id_token` 컬럼 자체를 뺐었는데, OIDC를 켜자마자 이게 진짜 gap이 됐다 — ID 토큰
  발급 자체는 성공해도 재저장 시 조용히 사라져 `/userinfo` 호출마다 `invalid_token`으로
  실패했다(공식 JdbcOAuth2AuthorizationService와 동일한 4컬럼 구성을 추가해 해결,
  `JpaOAuth2AuthorizationServiceSpec`에 왕복 검증 테스트 추가). (2)는 실제 E2E 통합테스트
  (`OidcSignInIntegrationSpec`)를 작성하는 과정에서 처음 드러났다 — 이런 "발급은 되는데 재조회가
  깨지는" 유형의 버그는 순수 단위 테스트로는 못 잡는다는 방증.
  **스코프-클레임 게이팅 회귀 테스트 결과**: `openid`만 동의한 클라이언트는 ID 토큰/`/userinfo`
  둘 다 `sub` 외 클레임이 전혀 없음을 확인(GREEN) — 단, 이 과정에서 프레임워크 자체의 진짜 동작
  하나를 더 실측 확인했다: **"openid가 유일한 요청 스코프면 동의 화면 자체를 건너뛴다"**
  (`OAuth2AuthorizationCodeRequestAuthenticationProvider.isAuthorizationConsentRequired()`
  공식 소스 주석 "'openid' scope does not require consent" — `requireAuthorizationConsent=true`로
  강제 등록한 클라이언트라도 예외 없이 적용됨). 버그가 아니라 GitHub/Google 등 표준 OIDC IdP와
  동일한 의도된 설계라 코드 변경 없이 테스트 쪽에서 이 분기를 처리했다.
  **테스트**: `OidcSignInIntegrationSpec`(신규 — discovery 문서, confidential 클라이언트로
  authorization_code+client_secret_basic 전체 플로우 완주 후 ID 토큰/서명 검증/`/userinfo` 응답
  검증, 스코프 게이팅 회귀), `OAuthAppRegistrationServiceSpec`(신규 — availableScopes/register의
  identity 스코프 화이트리스트), `JpaOAuth2AuthorizationServiceSpec`에 OidcIdToken 왕복 테스트
  추가. 기존 `McpOAuth2SecurityIntegrationSpec`/`ApiV1OAuth2SecurityIntegrationSpec`/
  `OAuthAppsAdminControllerSpec`/`UserViewControllerSpec` 등 1라운드 회귀 스위트 전부 GREEN 재확인
  (변경 없이 그대로 통과 — OIDC 활성화가 기존 DCR/MCP/API 플로우에 영향 없음).
