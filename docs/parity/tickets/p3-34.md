# P3-34: SVN도 Git/Hg와 동일한 수준의 실제 서버+실제 클라이언트 HTTP interop 테스트 추가

## 배경

Git과 Mercurial은 각각 `GitSmartHttpProtocolIntegrationSpec.kt`/`HgHttpProtocolIntegrationSpec.kt`에서
`@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)`로 실제 임베디드
톰캣을 띄우고, `ProcessBuilder("git"/"hg", ...)`로 **실제 CLI 바이너리**를 실행해 HTTP
clone/push 왕복을 확정적으로 검증한다.

반면 SVN 관련 테스트는 `SvnControllerOptionsIntegrationSpec.kt`/
`DeployKeySvnAuthorizationIntegrationSpec.kt` 둘뿐이고, 둘 다 `MockMvc`(가짜 서블릿 컨테이너,
실제 포트 없음) 기반이며 실제 `svn` CLI 바이너리를 실행하는 코드는 테스트 트리 전체에 한 곳도
없다. `SvnControllerOptionsIntegrationSpec`은 자체 주석에도 "OPTIONS 응답의 Allow 헤더에
PROPFIND가 있으면 DAVServlet까지 도달했다는 뜻"이라고 **간접 추론**만 검증할 뿐, 실제
`svn checkout`/`svn commit`을 돌려 end-to-end로 확정 검증한 적이 없다.

즉 SVN 저장소가 실제 svn 클라이언트로 clone/checkout/commit이 되는지는 이 코드베이스의
자동화된 테스트로는 한 번도 확정 검증된 적이 없다(Git/Hg는 있음).

## 요구사항

Git/Hg 스펙과 동일한 패턴으로 SVN interop 테스트를 신설한다:

1. `@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제 서버를 띄운다.
2. 테스트 환경에 실제 `svn` CLI가 설치돼 있는지 먼저 확인하고(`ProcessBuilder("svn", "--version")`),
   없으면 스킵한다 — Hg 스펙의 기존 관례와 동일.
3. `svn checkout http://127.0.0.1:$port/svn/{owner}/{project}`로 실제 워킹카피를 만들고,
   파일 추가 후 `svn add`/`svn commit`으로 실제 서버에 커밋한다.
4. 커밋이 실제로 반영됐는지 별도 워킹카피로 다시 checkout하거나 `svn log`로 확인한다.
5. 가능하면 DeployKey 인증 경로(`DeployKeySvnAuthorizationIntegrationSpec`가 다루는 시나리오)도
   실제 `svn` 클라이언트로 왕복하는 케이스를 함께 추가해, 그 스펙의 MockMvc 검증을 실제
   end-to-end로 보강한다(기존 MockMvc 스펙은 대체가 아니라 유지 — 더 빠른 하위 계층 검증으로 남김).

## 참고

- 실제 `svn` 바이너리는 로컬/CI 환경에 설치가 전제되어야 한다 — Hg 스펙처럼 미설치 시
  조용히 스킵하는 방어 코드가 필요하다.
- SVN은 WebDAV/DeltaV 기반이라 Git/Hg의 smart HTTP 프로토콜과 요청 흐름이 다르다
  (PROPFIND/REPORT/MKACTIVITY 등) — `DAVServlet`(Apache Jackrabbit 또는 동등 구현)이 실제로
  이 메서드들을 다 처리하는지까지 실제 클라이언트로 검증하는 게 이 티켓의 핵심 가치다.

## 완료 로그

### 조사

`HgHttpProtocolIntegrationSpec`/`GitSmartHttpProtocolIntegrationSpec`을 먼저 읽고 패턴(`@SpringBootTest(webEnvironment = RANDOM_PORT)`, `@DynamicPropertySource`로 base-dir 오버라이드, `ProcessBuilder`로 실제 CLI 실행, 프로젝트/사용자 픽스처 `findAll().find { } ?: save(...)` 관례)을 확인했다. SVN 쪽은 `SvnController`(DAVServlet 위임), `SvnAuthorizationFilter`(RepoAccessPolicy 재사용, DeployKey 분기 포함), `SvnServletRequestWrapper`(서블릿 경로 재작성), `SecurityConfig`(`/svn/**` permitAll + `SvnAuthorizationFilter`를 `BasicAuthenticationFilter` 뒤에 addFilterAfter — 즉 Basic 인증은 표준 Spring Security 경로로 처리됨을 확인)를 읽어, 인증이 Git/Hg와 동일하게 실제 계정 비밀번호 기반 Basic 인증(멤버) 또는 `x-access-deploykey` 고정 사용자명 + raw 토큰(DeployKey) 조합으로 동작함을 확인했다. `SvnRepository.create()`는 trunk/branches/tags 구조를 강제하지 않는 순수 빈 저장소를 만들므로 checkout 대상 URL은 프로젝트 루트로 충분함을 확인.

### 구현

`SvnHttpProtocolIntegrationSpec` 신설(`src/test/kotlin/com/github/yonaprojects/yona/web/`), 3개 시나리오:
1. PUBLIC SVN 프로젝트를 실제 `svn checkout` 바이너리로 checkout(빈 저장소, 인증 불필요).
2. 멤버가 `--username`/`--password`로 실제 `svn checkout` → 파일 작성 → `svn add` → `svn commit` → 별도 디렉터리로 재-checkout해 서버에 실제 반영됐는지 확정 검증(Git/Hg 스펙의 "push 후 별도 clone으로 재검증" 패턴과 동일).
3. `DeployKeySvnAuthorizationIntegrationSpec`(MockMvc, 상태 코드만 확인)이 다루던 시나리오를 실제 `svn` 클라이언트로 보강 — `deployKeyService.create()`로 발급한 raw 토큰을 `--username x-access-deploykey --password <token>`으로 실제 checkout/add/commit/재-checkout까지 왕복.

모든 svn 호출은 `--non-interactive --config-dir <스펙 전용 임시 디렉터리>`로 실행해, 공유 개발 환경의 실제 사용자 `~/.subversion` 설정/인증 캐시를 건드리지 않게 격리했다. `svnAvailable()`로 `svn --version` 존재 확인 후 미설치 시 스킵하는 방어 코드는 Hg 스펙과 동일하게 넣었다(이 환경엔 svn 1.14.5가 실제로 설치돼 있어 스킵되지 않고 전부 실행됨을 확인).

### 버그 발견 및 근본 수정

최초 실행 시 시나리오 2/3(실제 commit)이 전부 `svn: E175002: Unexpected server error 500 '' on '.../committed.txt'`로 실패했다. 서버 로그(`--info`로 재실행해 stdout 캡처)를 추적한 결과:

1. svn 클라이언트가 커밋 준비 단계에서 아직 서버에 없는 신규 파일에 대해 `HEAD /svn/.../committed.txt`를 보낸다 — 이건 DeltaV 프로토콜상 "신규 파일이니 추가하라"는 정상 협상이며, DAVServlet은 `response.sendError(404)`로 응답한다(정상 동작).
2. 그런데 Spring Boot는 서블릿 어디서 호출되든 `sendError()`를 감지하면 컨테이너 표준 에러 페이지 메커니즘(`/error`로 재-dispatch)을 무조건 가로챈다.
3. 이 재-dispatch 시점에 DAVServlet이 이미 응답에 설정해둔 `Content-Type: text/xml`이 그대로 남아있는데, `BasicErrorController`가 이 컨텐츠타입을 그대로 존중해 에러 바디(`LinkedHashMap`)를 text/xml로 직렬화하려 시도한다.
4. 이 앱에는 XML 메시지 컨버터가 등록돼 있지 않아 `HttpMessageNotWritableException: No converter for [class java.util.LinkedHashMap] with preset Content-Type 'text/xml;charset=utf-8'`을 던지고, 결과적으로 정상적인 404 프로토콜 신호가 빈 바디의 500으로 뒤바뀌어 실제 커밋이 깨진다.

근본 원인 수정: `SvnServletResponseWrapper` 신설(`src/main/kotlin/.../web/SvnServletResponseWrapper.kt`) — `SvnController.service()`가 DAVServlet에 넘기는 응답만 감싸 `sendError(sc)`/`sendError(sc, msg)`를 컨테이너 재-dispatch를 트리거하지 않는 `setStatus(sc)`로 치환한다(raw wire 프로토콜 서블릿을 감싸는 통상적인 패턴 — Git/Hg 경로나 컨트롤러의 나머지 sendError 호출은 건드리지 않아 영향 범위를 SVN DAVServlet 응답으로 한정). 컨트롤러 catch 블록의 자체 500 처리(`response.sendError`)는 여전히 원본(비-래핑) `response`를 쓰도록 유지해 기존 `SvnControllerSpec`의 "이미 커밋된 응답엔 sendError 재호출 안 함" 회귀 테스트와 충돌하지 않게 했다.

`SvnServletResponseWrapperSpec` 신설(단위 테스트, `MockHttpServletResponse`로 sendError가 setStatus 경로를 타는지 직접 확인)로 회귀 가드를 추가했다.

### 검증

- `./gradlew compileKotlin compileTestKotlin` 성공.
- 수정 전: `SvnHttpProtocolIntegrationSpec` 3개 중 2개(멤버 커밋, DeployKey 커밋) 실패 — 실제 서버 로그로 `HttpMessageNotWritableException` 스택 확인(가짜 통과가 아님을 스스로 재확인).
- `SvnServletResponseWrapper` 수정 후: `SvnHttpProtocolIntegrationSpec`(3) + `SvnServletResponseWrapperSpec`(2) + `SvnControllerSpec`(8, 기존 "물리 저장소 없음→500"/"이미 커밋됨→sendError 재호출 안 함" 케이스 포함 무회귀) + `SvnControllerOptionsIntegrationSpec`(1) + `SvnServletRequestWrapperSpec`(8) + `SvnAuthorizationFilterSpec`+`SvnAuthorizationFilterExtraSpec` + `DeployKeySvnAuthorizationIntegrationSpec`(4) + `SvnCommitSpec`+`SvnRepositorySpec` 전부 재실행, 전부 GREEN.
- 실사용 검증(가짜 통과 배제): 서버 접근 로그에서 `"SVN/1.14.5 (x86_64-pc-linux-gnu) serf/1.3.10"` User-Agent로 실제 `OPTIONS`/`PROPFIND`/`MKACTIVITY`/`PUT`/`DELETE`/`HEAD` 요청이 실제 임베디드 톰캣 포트로 들어온 것을 확인했고, 이 로그 추적 과정에서 실제로 존재하던 버그(위 500 오류)를 재현·발견·수정까지 완료했다 — mock으로는 재현 불가능한 컨테이너 수준의 상호작용이라 이 테스트가 실제 프로토콜을 왕복하고 있음이 실증됐다.
- 공유 테스트 DB 컨테이너는 중지하지 않았고(H2 프로파일로 검증), 작업 중 공유 저장소에 다른 세션과의 충돌은 없었다(`git status`/`git log` 확인).
