# P3-42: GitHub/Forgejo 수준의 프로젝트 위키 기능 추가

## 배경

yona에는 위키 기능이 전혀 없다. legacy v1.6도 원래부터 위키가 없던 프로젝트라(전수 검색 결과
위키 관련 파일 0건) 이건 "동치성 이식 누락"이 아니라 **완전 신규 기능**이다. 다만
`ResourceType.WIKI_PAGE`/`ApiTokenScopeGroup.WIKI`가 이미 정의만 돼 있고(스코프 축 자리만
파여있음, 실제 컨트롤러/템플릿/도메인 로직은 0줄) 실 기능 연결은 안 돼 있는 상태를 대화 중
발견했다.

사용자가 목표 수준으로 "적어도 Forgejo 수준"을 지정했다. **착수는 보류 — 백로그 등록만
지시받음("위키 작업은 시작하지마 ... 백로그만 추가해줘").**

## 목표 수준 (Forgejo wiki 기준)

Forgejo(Gitea 계열)의 위키는 DB 엔티티 없이 **프로젝트당 별도 bare git 저장소
(`<owner>/<project>.wiki.git`)만으로 전체가 동작**한다 — 페이지 자체가 그 저장소 안의
마크다운 파일이고, 목록/이력은 그 저장소를 스캔/`git log`한 결과다. yona가 이미 갖고 있는
인프라(bare git 저장소 관리 `GitRepository`/`BareCommit`, 온라인 커밋 편집 패턴 — README/
이슈템플릿 편집에 이미 사용 중, 마크다운 렌더링 서비스, 커밋 히스토리/diff 조회)를 거의 그대로
재사용 가능해 보인다(착수 시 재검증 필요).

Forgejo가 실제로 제공하는 기능(이 티켓의 "최소 목표선"):

1. **페이지 CRUD**: 목록(사이드바), 보기(마크다운 렌더링), 새 페이지 만들기, 편집(마크다운
   에디터, raw/preview), 삭제, 이름변경(rename).
2. **특수 페이지**: `_Sidebar`(커스텀 사이드바 내용), `_Footer`(커스텀 푸터), `Home`(위키
   최초 생성 시 기본 페이지).
3. **페이지별 히스토리**: 그 페이지 파일의 `git log`, 리비전 목록 + 리비전 간 diff.
4. **커밋 메시지 커스터마이징**: 저장 시 커밋 메시지를 사용자가 입력 가능(기본값 자동 생성).
5. **git 클론 접근**: 위키 저장소 자체를 `git clone`/`push`로 로컬에서 직접 편집 가능(기존
   Git smart HTTP 서빙 인프라 재사용 가능성 검토).
6. **권한**: 위키 쓰기는 기본적으로 저장소 쓰기 권한과 동일(또는 프로젝트 설정으로 "누구나
   편집 가능" 토글 — Forgejo도 이 옵션 있음, 범위 확정 시 재검토).
7. **페이지 제목에 슬래시 허용 시 하위 경로/중첩 페이지 구조**(Forgejo 지원 여부 착수 전
   재확인 필요).
8. **위키 검색**(최소 페이지 제목 검색).

## 범위 확정 필요 사항 (착수 시 먼저 결정할 것)

- 위키 저장소를 GIT 전용으로 할지(Forgejo와 동일, 프로젝트의 실제 VCS가 SVN/Mercurial이어도
  위키만 항상 git으로), 프로젝트 VCS를 따라갈지 — 기존 README 온라인편집이 이미 GIT
  (`BareCommit`)과 Mercurial(`HgRepository.commitTextFile`)을 분기 처리하고 있어 참고 가능.
- `ApiTokenScopeGroup.WIKI`/`ResourceType.WIKI_PAGE`를 실제로 연결(REST API 스코프 판정).
- MCP 서버(P3-07)/CLI(`yona-cli`)에도 위키 읽기/쓰기 노출할지(이 세션의 표준 원칙 — "모든
  기능은 읽기/쓰기가 반드시 이뤄져야 한다"를 따르면 필요).
- 웹 UI는 GitHub/Forgejo 관례(사이드바 페이지 목록 + 마크다운 에디터)를 그대로 따를 것
  (이 세션의 표준 원칙).
