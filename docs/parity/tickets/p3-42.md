# P3-42: GitHub/Forgejo 수준의 프로젝트 위키 기능 추가

## 배경

yona에는 위키 기능이 전혀 없다. legacy v1.6도 원래부터 위키가 없던 프로젝트라(전수 검색 결과
위키 관련 파일 0건) 이건 "동치성 이식 누락"이 아니라 **완전 신규 기능**이다. 다만
`ResourceType.WIKI_PAGE`/`ApiTokenScopeGroup.WIKI`가 이미 정의만 돼 있고(스코프 축 자리만
파여있음, 실제 컨트롤러/템플릿/도메인 로직은 0줄) 실 기능 연결은 안 돼 있는 상태를 대화 중
발견했다.

사용자가 목표 수준으로 "적어도 Forgejo 수준"을 지정했다. **착수는 보류 — 백로그 등록만
지시받음("위키 작업은 시작하지마 ... 백로그만 추가해줘").**

## 목표 수준 (Forgejo wiki 기준)

Forgejo(Gitea 계열)의 위키는 DB 엔티티 없이 **프로젝트당 별도 bare git 저장소
(`<owner>/<project>.wiki.git`)만으로 전체가 동작**한다 — 페이지 자체가 그 저장소 안의
마크다운 파일이고, 목록/이력은 그 저장소를 스캔/`git log`한 결과다. yona가 이미 갖고 있는
인프라(bare git 저장소 관리 `GitRepository`/`BareCommit`, 온라인 커밋 편집 패턴 — README/
이슈템플릿 편집에 이미 사용 중, 마크다운 렌더링 서비스, 커밋 히스토리/diff 조회)를 거의 그대로
재사용 가능해 보인다(착수 시 재검증 필요).

Forgejo가 실제로 제공하는 기능(이 티켓의 "최소 목표선"):

1. **페이지 CRUD**: 목록(사이드바), 보기(마크다운 렌더링), 새 페이지 만들기, 편집(마크다운
   에디터, raw/preview), 삭제, 이름변경(rename).
2. **특수 페이지**: `_Sidebar`(커스텀 사이드바 내용), `_Footer`(커스텀 푸터), `Home`(위키
   최초 생성 시 기본 페이지).
3. **페이지별 히스토리**: 그 페이지 파일의 `git log`, 리비전 목록 + 리비전 간 diff.
4. **커밋 메시지 커스터마이징**: 저장 시 커밋 메시지를 사용자가 입력 가능(기본값 자동 생성).
5. **git 클론 접근**: 위키 저장소 자체를 `git clone`/`push`로 로컬에서 직접 편집 가능(기존
   Git smart HTTP 서빙 인프라 재사용 가능성 검토).
6. **권한**: 위키 쓰기는 기본적으로 저장소 쓰기 권한과 동일(또는 프로젝트 설정으로 "누구나
   편집 가능" 토글 — Forgejo도 이 옵션 있음, 범위 확정 시 재검토).
7. **페이지 제목에 슬래시 허용 시 하위 경로/중첩 페이지 구조**(Forgejo 지원 여부 착수 전
   재확인 필요).
8. **위키 검색**(최소 페이지 제목 검색).

## 범위 확정 필요 사항 (착수 시 먼저 결정할 것)

- 위키 저장소를 GIT 전용으로 할지(Forgejo와 동일, 프로젝트의 실제 VCS가 SVN/Mercurial이어도
  위키만 항상 git으로), 프로젝트 VCS를 따라갈지 — 기존 README 온라인편집이 이미 GIT
  (`BareCommit`)과 Mercurial(`HgRepository.commitTextFile`)을 분기 처리하고 있어 참고 가능.
- `ApiTokenScopeGroup.WIKI`/`ResourceType.WIKI_PAGE`를 실제로 연결(REST API 스코프 판정).
- MCP 서버(P3-07)/CLI(`yona-cli`)에도 위키 읽기/쓰기 노출할지(이 세션의 표준 원칙 — "모든
  기능은 읽기/쓰기가 반드시 이뤄져야 한다"를 따르면 필요).
- 웹 UI는 GitHub/Forgejo 관례(사이드바 페이지 목록 + 마크다운 에디터)를 그대로 따를 것
  (이 세션의 표준 원칙).

## 완료 로그(2026-09-10)

**전부 완료** — 8개 목표 기능 + yona-cli + MCP 서버 도구까지 예외 없이 구현/검증했다(진행 중 사용자가
"7~8번도 시간 되는 만큼이 아니라 다 해", "yona-cli/MCP도 이번 라운드에 포함해"로 범위를 두 차례
확정 지시). 아래 항목별로 무엇을 구현했고 무엇으로 검증했는지 기록한다.

### 설계 결정(착수 시 확정)

- 위키 저장소는 Forgejo와 동일하게 **DB 엔티티 없이 항상 GIT**(`<owner>/<project>.wiki.git`) —
  프로젝트의 실제 VCS(SVN/Mercurial이어도)와 무관. `domain/vcs/GitRepository`를 그대로 재사용하되
  `projectName` 인자에 `"<project>.wiki"`를 넘겨 생성(코드 수정 없이 재사용 가능했음).
  `domain/vcs/BareCommit`은 `repoNameOverride` 파라미터를 추가해(기본값 null, 기존 호출부 전부
  무변경) 같은 방식으로 위키 저장소를 가리키게 했다.
- 페이지 저장/삭제는 `BareCommit`에 `commitPage(branchName, oldPath, newPath, text, message)` /
  `deletePage(branchName, path, message)`를 신규 추가 — in-core `DirCache`로 HEAD 트리를 복사하며
  oldPath 제거+newPath 추가를 한 커밋에 반영한다(생성/수정/이름변경을 한 오퍼레이션으로 통합).
- 페이지별 diff는 `GitRepository.getPatch(commitId, path)` / `getPatch(revA, revB, path)`
  (신규 오버로드, `getPatchForPath`로 명명 — 기존 2-인자 `getPatch(revA, revB)`와 시그니처가
  겹쳐 이름을 분리했다)로 `PathFilter`를 얹어 그 파일만 스코프된 unified diff를 얻는다.
- 페이지 제목은 슬래시로 하위 경로 표현("Guides/Setup" → `Guides/Setup.md`), `..`/빈 세그먼트는
  거부. `_new`/`_edit`/`_delete`/`_history`/`_search`/`_diff`는 웹 라우팅이 선점하는 예약
  세그먼트라 페이지 제목 첫 세그먼트로 금지(Forgejo/GitHub 위키도 동일한 예약어 관례).
- 특수 페이지(Home/_Sidebar/_Footer)는 별도 자료구조 없이 "그 이름의 일반 페이지"로 취급 —
  `_Sidebar.md`가 있으면 사이드바 목록 대신 렌더링, `_Footer.md`가 있으면 본문 아래 렌더링,
  위키가 비어 있으면 "Home 만들기" CTA를 보여준다(자동 생성 대신 — 조회만으로 부작용 있는
  커밋을 만들지 않기 위해 두 옵션 중 이 쪽을 택함).
- 위키 쓰기 권한 = "프로젝트 멤버"(코드 push와 동일 문턱, `existsByProjectIdAndUserId`) —
  Tag/Branch API가 쓰는 매니저 전용 `Operation.UPDATE`보다 낮은 문턱으로 의도적으로 다르게
  설계(요구사항 6번 "프로젝트 쓰기 권한(멤버)과 동일"). "누구나 편집 가능" 토글은 이번
  라운드에서 명시적으로 제외(과제 지침에 명시된 대로 이번 라운드 범위 밖, 백로그로 남김).

### 1. 페이지 CRUD

- `domain/wiki/WikiService.kt`(인터페이스) + `WikiServiceImpl.kt` — listPages/getPage/savePage
  (생성+수정+이름변경 통합)/deletePage. `web/WikiViewController.kt`(세션 기반 웹 UI,
  `/{owner}/{project}/wiki`, `_new`, `_edit/{*title}`, `_delete/{*title}`) +
  `web/WikiRestApiController.kt`(`/api/v1/projects/{owner}/{project}/wiki/pages` GET/POST/PUT/DELETE).
  템플릿: `templates/wiki/view.html`(사이드바+렌더링된 본문+New/Edit/History/Delete 버튼),
  `templates/wiki/edit.html`(기존 `site/layout :: markdownEditor` 프래그먼트 재사용 — 새 CSS/JS
  컴포넌트 도입 없음).
- 검증: `WikiServiceImplSpec`(실제 파일시스템 bare 저장소, CRUD 각 케이스),
  `WikiRestApiControllerIntegrationSpec`(실제 DB+실제 bare 저장소, MockMvc end-to-end —
  생성→목록/조회→수정→삭제 전체 사이클, 409 중복 생성). 실사용: 아래 "실사용 검증" 절 참고.

### 2. 특수 페이지(Home/_Sidebar/_Footer)

- `WikiViewController.addCommonAttributes()`가 매 요청마다 `_Sidebar`/`_Footer` 페이지 존재
  여부를 확인해 커스텀 렌더링. 위키가 비었으면 view.html이 "Create the Home page" CTA를 보여줌.
- 검증: `WikiServiceImplSpec`("_Sidebar, _Footer, Home도 일반 페이지처럼 저장/조회된다").
  실사용: 실제 서버에서 `_Sidebar` 생성 후 `/admin/wikitest/wiki`(Home) 응답 HTML에
  `wiki-custom-sidebar` div로 커스텀 사이드바가 실제로 렌더링됨을 curl로 확인.

### 3. 페이지별 히스토리 + diff

- `WikiService.history()`(GitRepository.getHistory에 path 필터로 위임, 최신순),
  `WikiService.diff(commitId)`/`compare(revA, revB)`(위 getPatchForPath 재사용, unified diff
  텍스트). `templates/wiki/history.html`이 리비전 목록 + 라디오 2개로 비교 선택 + 선택한 리비전의
  diff를 `+`/`-`/`@@` 줄별 색상 처리해 렌더링.
- 커밋 하나가 "항상 그 페이지 파일 하나만" 바꾸도록 commitPage/deletePage가 보장하므로, 커밋
  전체 patch가 곧 "그 페이지의 diff"와 정확히 같다(다만 실제 git push로 외부에서 여러 파일을
  한 커밋에 섞어 넣는 경우까지 대비해 PathFilter로 명시적으로 스코프했다).
- 검증: `WikiServiceImplSpec`(history가 그 경로만의 git log를 반환함을 이름변경 시나리오로
  검증 — rename 커밋은 옛 경로/새 경로 양쪽 히스토리에 다르게 나타남을 실제로 확인하며 초기
  테스트 작성 시 이 사실을 몰라 RED가 났던 것을 실제 git 동작에 맞게 수정), diff/compare가
  다른 페이지 변경과 섞이지 않음을 검증. `WikiRestApiControllerIntegrationSpec`(history/diff
  REST 엔드포인트 end-to-end). 실사용: 아래 절 참고.

### 4. 커밋 메시지 커스터마이징

- `WikiServiceImpl.savePage()`/`deletePage()`가 `message`를 받아 비어있으면
  "Create <title>"/"Update <title>"/"Rename <old> to <new>"/"Delete <title>"를 자동 생성.
  웹 폼에 "Commit message" 입력란(placeholder로 기본값 미리보기), REST API/CLI/MCP 도구 모두
  `message` 파라미터를 노출.
- 검증: `WikiServiceImplSpec`("커밋 메시지 커스터마이징" describe 블록, 기본 메시지 3종 +
  사용자 지정 메시지 유지 둘 다 확인). 실사용: REST API로 커스텀 메시지("첫 커밋 메시지" 등)를
  보내고 `/wiki/_history/Home` 화면 및 `yona-cli wiki history`에서 그대로 노출됨을 확인.

### 5. git clone/push 접근

- 기존 `GitServletConfig`/`GitAuthorizationFilter`(Git smart HTTP 서빙 인프라)를 그대로
  재사용/확장:
  - `GitAuthorizationFilter`: URL의 프로젝트명에서 `.wiki` 접미어를 떼고 실제 프로젝트로 권한을
    판정하도록 수정(안 그러면 "<project>.wiki"라는 이름의 프로젝트가 없어 항상 404).
  - `GitServletConfig`의 저장소 리졸버: 위키 저장소이면서 아직 디스크에 없고, 그 이름에 해당하는
    프로젝트가 실제로 존재할 때만 빈 bare 저장소를 지연 생성 — 웹 UI로 페이지를 한 번도 만들지
    않은 상태에서 `git clone`/`git push`로 먼저 접근해도(요구사항 원문 시나리오) 정상 동작한다.
- 검증: `GitAuthorizationFilterSpec`에 위키 전용 테스트 2건 추가(PUBLIC 위키 clone 통과,
  PRIVATE 위키 push 비멤버 403). **실사용**: 실제 `git clone`/`git commit`/`git push` CLI
  바이너리로 (1) 이미 페이지가 있는 위키 저장소를 clone해 파일 구조(중첩 디렉터리 포함) 확인,
  (2) 그 로컬 클론에서 새 파일을 만들어 실제로 push해 서버에 반영되고 REST API/웹 UI에서
  곧바로 조회됨을 확인, (3) **한 번도 웹 UI로 건드리지 않은 새 프로젝트**의 위키를 clone(빈
  저장소 경고 정상 출력) → 로컬에서 첫 커밋 → push 성공 → 웹 UI에 즉시 반영됨을 확인(지연
  초기화 회귀 테스트), (4) 인증 없이 push 시도 시 git이 자격증명을 요구하며 거부됨을 확인.

### 6. 권한(프로젝트 쓰기 권한과 동일)

- 읽기: `AccessControl.isAllowedToReadProject()`(기존 로직 재사용, PUBLIC은 게스트 제외 누구나,
  PRIVATE은 멤버/조직관리자만). 쓰기: 프로젝트 멤버십(`existsByProjectIdAndUserId`) — 코드
  push와 동일 문턱.
- 검증: `WikiRestApiControllerIntegrationSpec`("프로젝트 멤버가 아닌 로그인 사용자는 읽기는
  되지만 쓰기는 403이어야 한다", "멤버가 되면 위키에 쓸 수 있어야 한다"),
  `GitAuthorizationFilterSpec`(git 프로토콜 레벨 403/401). 실사용: 위 5번의 (4).

### 7. 슬래시 하위 경로/중첩 페이지

- `WikiService.titleToPath()`가 "Guides/Setup" → `Guides/Setup.md`로 변환, `pathToTitle()`이
  역변환. 웹 라우팅은 `{*title}`(Spring PathPattern 나머지-경로 캡처)로 슬래시 포함 제목을
  그대로 받는다. 템플릿의 위키 내부 링크는 Thymeleaf `@{}` 경로변수 치환이 아니라
  `#uris.escapePath()`(슬래시는 보존, 그 외 문자만 escape)로 생성 — `@{}` 경로변수는 값 전체를
  한 세그먼트로 취급해 "/"까지 `%2F`로 인코딩해버려 중첩 페이지 링크가 깨지는 문제를 실제로
  발견하고 고쳤다.
- 검증: `WikiServiceImplSpec`(중첩 생성/조회/재귀 목록), `WikiRestApiControllerIntegrationSpec`
  (`GET .../wiki/pages/Guides/Setup`), `BareCommitWikiSpec`(중첩 경로 커밋). 실사용: `Guides/Setup`
  페이지를 실제로 만들어 `/admin/wikitest/wiki/Guides/Setup` 웹 뷰가 200으로 렌더링되고,
  `git clone`한 로컬 워킹디렉터리에 실제 `Guides/` 하위 디렉터리가 생김을 확인, yona-cli
  `wiki view "Guides/Setup"`/`wiki edit "CliPage" --new-title "CliPage/Renamed"`로도 확인.

### 8. 위키 페이지 제목 검색

- `WikiService.search(query)` — `listPages()` 결과를 제목 대소문자 무시 부분일치로 필터링(파일
  개수가 위키 규모상 적어 별도 인덱스 없이 충분). 웹: `/wiki/_search?q=`, REST:
  `GET .../wiki/pages?q=`, CLI: `yona wiki list --query`, MCP: `list_wiki_pages`의 query 인자.

이 과정에서 실제로 발견해 고친 버그 2건:
1. `wiki/edit.html`의 `th:replace` 프래그먼트 파라미터에 삼항연산자(`isNew ? 'New Page' :
   editTitle`)를 직접 쓰면 Thymeleaf의 제한된 SpEL 평가기가 "Instantiation of new objects...
   forbidden"로 500을 냄 — `th:with`에서 미리 계산한 단순 변수로 분리해 해결(실제 서버로
   `_edit`/`_new` 폼에 접근해보지 않았다면 발견하지 못했을 버그).
2. `@Configuration` 클래스(`GitServletConfig`)의 생성자 파라미터에 Kotlin 기본값(`= "main"`)을
   주면 컴파일러가 마스크 생성자를 추가로 만들어 생성자가 2개가 되고, Spring의 CGLIB 프록시
   생성이 어느 쪽을 써야 할지 못 찾아 `NoSuchMethodException`으로 전체 통합 테스트 컨텍스트
   로딩이 깨짐 — 기본값을 제거하고 필수 인자로 바꿔 해결(통합 테스트를 실제로 돌려보지 않았다면
   발견하지 못했을 버그).

## 후속 수정(2026-09-10) — `isWikiEnabled` 프로젝트 토글 누락

사용자가 실제 서버로 `/projectform`(프로젝트 생성 폼)을 직접 열어보고 "왜 위키 생성 옵션이
빠져있냐"고 신고했다. 확인해보니 `Project` 엔티티에 Code/Issue/PullRequest/Review/
Milestone/Board는 전부 `isXEnabled` 토글(프로젝트 생성 폼 체크박스 + 설정 화면 체크박스 +
메뉴 탭 노출 여부)이 있는데 위키만 빠져 있었다 — 애초 구현 당시 "DB 엔티티 없이 항상 켜져
있다"고 의도적으로 설계했던 부분인데, 다른 5개 기능과의 일관성을 깨는 실사용 결함이었다.

**수정**: `Project.isWikiEnabled: Boolean = true`(다른 토글과 동일하게 기본값 true, 기존
프로젝트도 위키가 계속 보이도록) 추가 후, 다른 5개 토글이 지나는 모든 경로에 동일하게 배선:
- `project/create.html`/`project/setting.html` 체크박스 + `project/importing.html`(git
  import 폼)에도 동일 체크박스 추가.
- `ProjectViewController.newProject()`(`NewProjectForm.wiki`)/`ImportViewController`
  (`ImportForm.wiki`)/`ImportApiController`(`ImportApiRequest.wiki`)/
  `ProjectRestApiController`(`CreateProjectRequest.isWikiEnabled`)/
  `ProjectController.UpdateProjectRequest`/`UpdateProjectParam`/
  `ProjectServiceImpl.updateProject()`까지 전 구간에 `isWikiEnabled` 배선.
- `project/menu.html`의 위키 탭을 다른 탭과 동일하게 `th:if="${project.isWikiEnabled}"`로
  게이트(기존엔 무조건 노출). 단축키 매핑(`htKeyMap["W"]`)도 동일 조건으로 감쌈.
- `yona-cli`의 `internal/api/project.go` `UpdateProjectRequest`에도 `IsWikiEnabled *bool`
  추가(다른 토글과 동일하게 필드만 존재 — CLI `project edit` 명령 자체는 어떤 토글도 아직
  플래그로 노출하지 않는 기존 상태를 그대로 따름, 위키만 예외적으로 노출하지 않음).
- 위키 컨트롤러(`WikiViewController`/`WikiRestApiController`) 자체는 `isWikiEnabled`를
  검사하지 않는다 — Board/Issue 등 다른 기능도 컨트롤러 레벨에서 자기 자신의 `isXEnabled`를
  검사하지 않고 메뉴 탭 노출 여부로만 쓰는 기존 관례를 그대로 따른 것(직접 URL로는 계속
  접근 가능, 회귀 아님).

**테스트**: 관련 스펙 컴파일 에러(새 생성자 파라미터로 인한 기존 positional 호출부/
data class 생성 누락) 수정 — `ProjectViewControllerSpec`/`ProjectServiceImplSpec`/
`UpdateProjectParamSpec`/`ProjectControllerSpec`/`ProjectRestApiControllerSpec`/
`ImportViewControllerSpec`/`ImportApiControllerSpec` 총 412건 재실행 GREEN 확인.
yona-cli `go build ./...` 클린.
