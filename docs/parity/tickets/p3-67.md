# P3-67: 웹훅 등록 폼에 Payload URL 필수 입력 클라이언트측 검증이 없음

## 배경

`service/yona.project.Webhook.js`는 웹훅 등록 폼(`project/setting_webhook.html`)의
`payloadUrl` 필드가 비어 있으면 `submit` 이벤트를 막고
`$yona.alert(Messages("project.webhook.payloadUrl.empty"))`로 안내 메시지를 보여주는
클라이언트측 검증을 제공한다(legacy에서도 동일한 파일이 동일 화면에 로드됨,
`app/views/project/setting_webhook.scala.html` 대조 확인).

`project/setting_webhook.html`의 실제 인라인 스크립트는 JSON 타입 선택 시 "Git Push" 이벤트를
강제 체크하는 로직만 있고, `yona.project.Webhook.js` 자체는 어디에도 `<script src>`로 로드되지
않는다(`$yona.loadModule`도 아님 — 이 파일은 `service/` 디렉터리에 있지만 legacy 방식대로
직접 `<script src>`로 로드되는 파일이었다).

## 실제 영향

- 사용자가 Payload URL을 비운 채 "웹훅 등록" 버튼을 누르면 클라이언트측에서 아무 안내 없이
  그대로 폼이 제출된다.
- 서버측(`WebhookController.kt:82`, `payloadUrl.isBlank()` 체크)이 최종 방어선으로 남아있어
  **데이터 무결성 문제는 없다** — 빈 값으로 웹훅이 실제로 생성되지는 않는다. 다만 서버 응답이
  legacy가 제공하던 즉각적인 인라인 안내(`Messages("project.webhook.payloadUrl.empty")`)만큼
  친절한 UX인지는 미확인(리다이렉트+플래시 메시지인지, 별도 확인 필요).
- 우선순위: 낮음(보안/데이터 문제 아님, 순수 UX 격차).

## 완료 기준

- [x] `project/setting_webhook.html`에 `yona.project.Webhook.js`를 실제로 로드(`<script src>`
      또는 동등한 초기화 호출)하고, 빈 Payload URL 제출 시 클라이언트측에서 즉시 차단+안내되는지
      Playwright로 확인.
- [x] 위 배선 후 `_isFormValid()`가 실제로 이 폼의 `payloadUrl` 필드(`name="payloadUrl"`)를
      정확히 찾는지(마크업 계약 일치) 확인 — 포팅 과정에서 name/id가 달라졌을 가능성 배제 필요.
- [x] 서버측 거부 시(현재 동작) 응답이 사용자에게 최소한의 안내를 주는지 별도 확인, 필요시
      함께 개선. (확인만 완료 — 아래 완료 로그의 "범위 밖 발견" 참고. 실제 개선은 이번
      티켓 범위에서 하지 않았다.)

## 감사 방법론 참고 (재사용 가능)

`static/javascripts/{common,service,template}`의 JS 파일이 실제로 "적용"되는 경로는 3가지이며,
이 중 하나라도 없으면 죽은 파일이다:

1. 템플릿의 `<script src="...">`(또는 `th:src="@{...}"`) 직접 로드.
2. `support-script/js-bundle/minify-js.sh`의 `--js` 재료 목록에 포함되어
   `yona-lib.js`/`yona-common.js`/`yona-layout.js` 번들에 컴파일됨(이 스크립트의 재료 목록
   자체가 SSOT — 여기 없으면 번들에도 없다).
3. `service/` 파일 한정, `$yona.loadModule("X.Y")` 동적 로드(`common/yona.Common.js`의
   `loadModule()`이 `service/yona.<X.Y>.js`를 런타임에 fetch) — 파일명이 아니라
   `loadModule("...")` 호출 문자열로 검색해야 함(파일명 자체는 템플릿에 전혀 안 나타남).

이번 감사에서 위 3가지 전부에 해당하지 않은 파일은 최종적으로 이 티켓(Webhook) 하나만
남았다 — 나머지는 P3-52가 이미 "다른 방식으로 재구현됨/원래 죽은 코드"로 결론 낸 것과
일치하거나(`yona.Interval.js`/`yona.Sha1.js`), 템플릿 인라인 주석에 "REST API로 직결,
loadModule 대신"이라고 이미 설계상 대체가 문서화돼 있음(`yona.organization.Member.js`/
`yona.project.Member.js` — `project/members.html`/`organization/members.html`이 REST API를
직접 호출), 또는 legacy에도 로드되지 않던 완전한 죽은 코드였다(`yobi.WatcherList.js`/
`yobi.ui.Mergely.js`/`yobi.CodeTemplate.js`).

### 착수 전 재확인 지시(뉘앙스)에 대한 결론 — **사실로 확인됨**

지시받은 대로 착수 전 Playwright로 현재/목표 상태를 먼저 실측했다. 결론:
`project/setting_webhook.html:25`의 `<input type="url" id="payloadUrl" name="payloadUrl"
... required ...>`는 이미 존재했고, 실제로 **브라우저 네이티브 HTML5 제약 검증(required +
type=url)이 커스텀 JS `submit` 리스너보다 항상 먼저 개입해 제출을 막는다** — 표준
브라우저 동작상 `<form>`이 제약 위반 상태면 `submit` 이벤트 자체가 디스패치되지 않으므로,
`yona.project.Webhook.js`를 배선해도 실사용 화면에서 빈 Payload URL 제출 시 보이는 안내는
legacy 스타일 `$yona.alert(...)` 커스텀 메시지가 아니라 **브라우저 기본 툴팁**("Please fill
out this field." 등, 로케일에 따라 다름)이다. 즉 이 티켓의 실질 격차는 애초 설명대로
"검증이 아예 없음"이 아니라 "legacy와 다른 안내 채널(네이티브 vs 커스텀)" 동치성 격차였다.

이를 Playwright로 직접 분리 검증했다(`payloadUrl`의 `required`/`type=url`을 런타임에
제거한 뒤 다시 제출):
- `required`+`type=url`이 있는 상태(실제 화면 그대로) → 제출이 막히고
  `#payloadUrl.validationMessage === "Please fill out this field."`,
  `document.activeElement === #payloadUrl`(네이티브 검증이 필드에 포커스) — 브라우저가
  가로챈 것이 실측으로 확인됨. 이 경로에서는 `#yonaDialog`가 열리지 않는다.
- `required`/`type=url`을 제거한 뒤 동일하게 제출 → `yona.project.Webhook.js`의
  `_isFormValid()`가 정상 동작해 `$yona.alert("Payload URL is a required field.")`가
  호출되고, 실제로 `<dialog id="yonaDialog" open>`의 `.msg`에 정확히 그 문구가 렌더링됨을
  확인했다(legacy 메시지 키 `project.webhook.payloadUrl.empty`의 영문 기본값과 일치).
  - 디버깅 메모: `yona.ui.Dialog._initElement()`가 원본 `#yonaDialog`를
    `cloneNode(true)`해서 `document.body`에 추가해 보여주므로, 같은 id를 가진 엘리먼트가
    문서에 2개 존재한다(원본은 항상 닫힌 채로 남음). `document.querySelector('#yonaDialog')`
    는 첫 번째(원본, 닫힘)만 찾으므로 첫 시도에서 "다이얼로그가 안 뜬다"는 오탐이
    있었다 — `dialog[open]`으로 다시 찾아 실제로는 정상 동작함을 확인했다. 이 clone 기반
    설계 자체는 이 티켓 이전부터 있던 기존 구현이라 손대지 않았다.
- `submit` 이벤트를 직접 `dispatchEvent`로 발생시켜 확인한 결과도 `defaultPrevented ===
  true`로, `_attachEvent()`의 리스너가 정확히 연결돼 있고 정상 동작함을 재확인했다.

**판단**: 이 뉘앙스는 사용자가 실제로 겪는 안내 문구가 legacy와 100% 동일하지 않다는
잔여 격차이지만(네이티브 vs 커스텀 텍스트/스타일), (1) 제출이 즉시 차단된다는 핵심 동작은
legacy와 동치이고, (2) `required` 속성은 이번 티켓 범위(스크립트 배선) 이전부터 있던
기존 마크업이며 이를 제거해 커스텀 메시지를 강제로 노출시키는 것은 "새로운 부가 기능"에
해당하는 별도 판단이 필요한 변경이라 이번 티켓에서 임의로 건드리지 않았다. 완료 기준
1번("클라이언트측에서 즉시 차단+안내되는지 확인")은 이 사실 그대로 충족한 것으로 보고,
과장 없이 위 내용을 그대로 기록한다.

### 완료 기준 2번 — `_isFormValid()`의 마크업 계약 확인

`yona.project.Webhook.js`의 `_initElement()`는
`elements.form.querySelector('input[name="payloadUrl"]')`로 필드를 찾는데,
`project/setting_webhook.html:25`의 실제 필드는 `name="payloadUrl"`로 정확히 일치한다
(포팅 과정에서 이름이 달라지지 않았음을 확인). Playwright 실측에서도
`window.yona.project.Webhook`이 정상 등록되고 `submit` 리스너가 실제로 동작함을 확인해
간접적으로도 재확인됐다.

### 완료 기준 3번 — 서버측 거부 응답 확인(범위 밖 발견, 고치지 않음)

클라이언트측(네이티브+커스텀 JS) 검증을 모두 우회해(`fetch`로 직접 POST, payloadUrl 빈 값)
서버 응답을 직접 확인했다: `WebhookController`는 `HTTP 400 Bad Request`를 반환하되 바디는
`{"timestamp":...,"status":400,"error":"Bad Request","path":"..."}` 형태의 Spring 기본 에러
JSON이며, legacy가 주던 것과 같은 사람이 읽을 수 있는 안내 메시지는 없다. 다만 이 경로는
정상적인 브라우저 사용(네이티브 HTML5 검증이 항상 선행)에서는 도달 불가능한 엣지 케이스이고,
티켓 본문에도 "우선순위: 낮음"으로 이미 명시돼 있어 이번 패스에서는 개선하지 않고 사실만
기록한다(향후 필요시 별도 티켓 후보).
