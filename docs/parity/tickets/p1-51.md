## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-51**: 코드리뷰 댓글/커밋 댓글 알림 메일에 `References` 헤더가 채워지지 않아, 메일 클라이언트에서 같은 스레드로 묶여 보이지 않던 문제 수정(yona `NotificationMail.java:336-365 EventEmail.addReferences()` 대응). `computeReferences()`의 기존 주석은 "NEW_REVIEW_COMMENT/REVIEW_THREAD_STATE_CHANGED는 아직 생산되지 않는다"고 적혀 있었는데, 이는 [[tickets/p1-27|P1-27]]을 작성하던 시점([[tickets/p1-50|P1-50]] 이전)에는 사실이었지만 이후 [[tickets/p1-50|P1-50]]이 실제로 이 이벤트들을 생산하게 되면서 stale해진 설명이었다 — 즉 "상위 기능이 없어 자연히 커버가 안 되는" 상황이 아니라 [[tickets/p1-50|P1-50]]이 [[tickets/p1-27|P1-27]]의 References 로직을 갱신하지 않고 지나간 실제 결손이었다(사용자가 코드를 직접 읽고 이 점을 지적해 발견).
  - yona `addReferences()`는 `resource.getContainer()` 기반의 범용 알고리즘이다: 컨테이너 타입이 `COMMENT_THREAD`면 "그 스레드의 첫 리뷰 댓글" Message-ID를 참조하는 특수 케이스, 그 외엔 컨테이너 자신의 Message-ID를 참조하는 default 케이스. yona에서 `ReviewComment.asResource().getContainer()` = `thread.asResource()`(COMMENT_THREAD)이고, `CommitComment.asResource().getContainer()` = `Commit.getAsResource(project, commitId)`(COMMIT)임을 확인해 그대로 이식.
  - `computeReferences()`에 두 케이스 추가: `ResourceType.REVIEW_COMMENT` → `ReviewCommentRepository.findByThreadIdOrderByCreatedDateAsc(threadId)`의 첫 항목(스레드의 첫 리뷰 댓글) Message-ID, `ResourceType.COMMIT_COMMENT` → `computeMessageId(COMMIT, "{projectId}:{commitId}")`([[tickets/p1-50|P1-50]]의 `getCommitWatchers()`가 이미 쓰던 것과 동일한 합성 키 포맷). `ResourceType.COMMENT_THREAD`(REVIEW_THREAD_STATE_CHANGED 이벤트 자신)는 legacy `CommentThread.asResource()`도 `getContainer()`를 오버라이드하지 않아(컨테이너 없음) References를 채우지 않는 게 정확한 동작이므로 손대지 않음 — 회귀 테스트로 명시적으로 확인.
  - 같은 파일의 `getReplyTo()`(Reply-To 헤더 로직, [[tickets/p1-28|P1-28]])는 이미 `REVIEW_COMMENT`/`COMMIT_COMMENT`를 정확히 처리하고 있어 References만 뒤처져 있었다.
  - 테스트: `NotificationMailDigestSchedulerSpec.kt` +3(REVIEW_COMMENT → 스레드 첫 댓글 Message-ID를 References로 지정, COMMIT_COMMENT → 커밋 리소스 Message-ID를 References로 지정, REVIEW_THREAD_STATE_CHANGED → References 미지정 확인) — 먼저 레드 상태(신규 두 케이스가 미구현이라 `IllegalStateException`, 세 번째는 이미 그린)를 확인한 뒤 구현. 커버리지: `computeReferences` LINE 69%(9/13) — 나머지는 기존에도 테스트되지 않던 방어적 null 가드(`comment 조회 실패`/`thread 없음` 등, 이 저장소의 다른 서비스들과 동일하게 실무상 도달 불가능한 방어 코드로 간주해 별도 테스트 미작성).
  - 검증: `./gradlew test --tests "com.github.yonaprojects.yona.domain.notification.*" --tests "com.github.yonaprojects.yona.domain.pullrequest.*" --tests "com.github.yonaprojects.yona.YonaApplicationTests"` 전체 통과, `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공.
  - **추가 발견(사용자 지적)**: computeReferences를 고친 뒤 사용자가 "같은 이유([[tickets/p1-50|P1-50]]이 새 producer를 추가하면서 [[tickets/p1-27|P1-27]]의 소비자 쪽을 함께 갱신하지 않음)로 `NotificationEventMerger`(이벤트 병합)도 영향받았을 것"이라고 정확히 지적 — 확인 결과 사실이었다. `NotificationEventMerger`의 클래스 KDoc에도 동일한 패턴의 stale한 주석("REVIEW_THREAD_STATE_CHANGED/NEW_REVIEW_COMMENT는 이 이식 시점 기준 yona에 실제 프로듀서가 없는 이벤트 타입")이 있었다. yona `mergeEvents()`의 `EventHashKey`는 `event.getResource().getContainer()`를 범용으로 계산하는데, yona의 `containerMergeKey()`는 `ISSUE_COMMENT`/`NONISSUE_COMMENT`만 처리하고 `REVIEW_COMMENT`는 처리하지 않아 리뷰 댓글이 스레드 상태변경과 절대 병합되지 않았다(항상 컨테이너 키 계산이 `null`이라 `stateChangedEvents.remove(key)`가 항상 미스).
  - `NotificationEventMerger.containerMergeKey()`에 `ResourceType.REVIEW_COMMENT` 케이스 추가 — `ReviewCommentRepository.findById()`로 댓글을 조회해 `comment.thread.id`를 `MergeKey(COMMENT_THREAD, threadId, senderId)`로 반환. `REVIEW_THREAD_STATE_CHANGED`는 `CodeReviewServiceImpl`이 이미 `resourceType=COMMENT_THREAD`로 발행하므로 `selfMergeKey()`가 별도 정규화 없이 그대로 키로 쓸 수 있어 손대지 않음(이미 정확).
  - **의도적으로 추가하지 않은 케이스**: `COMMIT_COMMENT`(NEW_COMMENT로 발행, [[tickets/p1-50|P1-50]])는 legacy에도 "커밋 상태변경"이라는 개념 자체가 없어 대응하는 self-key가 `stateChangedEvents`에 결코 존재하지 않는다 — 즉 컨테이너 키를 계산해도 항상 미스해 동작 차이가 없으므로(죽은 코드가 되므로) 정규화를 추가하지 않았다. `ReviewComment`와 달리 실질적 영향이 없다는 점을 코드 주석에 명시.
  - `NotificationEventMerger` 생성자에 `ReviewCommentRepository` 신규 주입.
  - 테스트: `NotificationEventMergerSpec.kt` +2(리뷰 댓글+스레드 상태변경, 같은 수신자면 하나로 병합 / 수신자 집합이 다르면 세 갈래로 분할) — 기존 `ISSUE_COMMENT`+`ISSUE_STATE_CHANGED` 병합/분할 테스트를 그대로 미러링. 먼저 생성자 시그니처 변경만으로 컴파일 레드를 확인한 뒤 구현.
