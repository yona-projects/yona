# P1-143: **(2026-08-21 [[tickets/p1-134|P1-134]] 착수 중 발견)** Hangout Chat 웹훅 응답에서 `thread.name`을 파싱해 `WebhookThread`로 저장하는 쓰기 경로가 yona에 아예 없음 — `webhookThreadRepository.save(...)` 호출이 전체 main 소스에 0건(코드 검색으로 확인). `WebhookServiceImpl.buildPayload()`의 DETAIL_HANGOUT_CHAT 분기는 `webhookThreadRepository.findByWebhookIdAndResourceTypeAndResourceId(...)`로 "조회"만 하므로 항상 null이 반환돼, [[tickets/p1-134|P1-134]](스레드 키가 댓글 자신으로 계산되는 문제)를 고쳐도 스레드 그룹핑 자체가 애초에 동작하지 않는다. yona `Webhook.java:622-658` `sendRequest(payload, webhookId, resource)`는 비동기 HTTP 응답의 `response.asJson().findPath("thread").findPath("name").asText()`를 파싱해, 기존 `WebhookThread.getWebhookThread(webhookId, resource)`가 없을 때만 `WebhookThread.create(webhookId, resource, threadId)`로 저장한다. yona `WebhookServiceImpl.sendRequestAsync()`(성공/실패 로그만 남기고 응답 본문의 thread 파싱·저장 자체가 없음)에 이 로직을 이식해야 [[tickets/p1-134|P1-134]]도 실질적으로 의미가 생긴다.

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P1-143**: yona `Webhook.java:622-658` `sendRequest(payload, webhookId, resource)`의 "HTTP 응답에서 `thread.name`을 파싱해 `WebhookThread`가 없을 때만 저장" 쓰기 경로를 신설.
  - 새 `@Component` `WebhookThreadRecorder.recordThreadIfAbsent(webhookId, resourceType, resourceId, threadId)`를 별도 빈으로 분리(단순히 `WebhookServiceImpl` 안의 private 메서드로 넣지 않은 이유: `sendRequestAsync()`의 HTTP 비동기 콜백은 JDK `HttpClient`의 자체 워커 스레드에서 실행돼 원래 요청의 `@Transactional` 스코프 밖이다 — 같은 클래스 안에서 `this.xxx()`로 직접 호출하면 Spring AOP 프록시를 우회해 트랜잭션이 걸리지 않으므로, 별도 스프링 빈의 메서드로 호출해야 그 시점에 새 트랜잭션이 열린다).
  - `WebhookServiceImpl.sendRequestAsync()`가 `webhook`/`resource`를 받도록 시그니처를 확장(기존엔 payloadUrl/secret만 받아 응답 처리에 필요한 컨텍스트가 없었음), HTTP 성공(2xx) 시 새 `recordHangoutThreadIfNeeded(webhook, resource, responseBody)`를 호출 — DETAIL_HANGOUT_CHAT 타입이 아니면 스킵, 응답 바디가 JSON이 아니면 예외 없이 스킵, `thread.name`이 비어있으면(threadId.isBlank()) `WebhookThreadRecorder`가 저장을 건너뜀.
  - **주의**: 저장에 쓰는 resourceType/resourceId는 아직 [[tickets/p1-134|P1-134]]가 고치기 전의 "댓글 자신" 키 그대로다(조회 쪽과 동일 키를 써야 P1-143 단독으로도 read/write가 맞물려 동작하므로, 키 자체를 옳게 만드는 건 여전히 [[tickets/p1-134|P1-134]]의 몫 — 범위를 섞지 않음).
  - 테스트: `WebhookThreadRecorderSpec.kt`(신규) 4건(신규 저장/기존 있으면 스킵/threadId 빈값 스킵/존재하지 않는 webhookId면 스킵), `WebhookServiceSpec.kt`의 `recordHangoutThreadIfNeeded` +3(Hangout이고 thread.name 있으면 저장 요청/Hangout이 아니면 스킵/응답이 JSON이 아니면 예외 없이 스킵). 관련 스펙(WebhookServiceSpec/WebhookThreadRecorderSpec/WebhookNotificationEventListenerSpec/WebhookControllerSpec/ProjectServiceImplSpec) 전체 통과.
