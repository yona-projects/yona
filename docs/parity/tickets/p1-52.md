## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-52**: 사용자가 [[tickets/p1-05|P1-05]] 완료 로그의 "범위 조정" 문구("PR 타임라인에 새 커밋 이벤트를 추가하는 부분은 [[tickets/p1-08|P1-08]]이 아직 없어서 제외했다")를 [[tickets/p1-08|P1-08]] 완료 후 다시 검증해달라고 요청. 확인 결과 여전히 미이식이었고, yona `PullRequestActor.processPullRequestMerging()`을 줄 단위로 대조하자 원래 알려진 "타임라인 기록 누락" 하나가 아니라 같은 뿌리(`attemptMerge()`가 부수효과 없이 diff만 계산)에서 나오는 5가지 결손이었음을 확인 — 사용자가 "모든 작업은 레거시 요나와 동일해야 함"을 명시해 5가지 전부 이식했다.
  - **yona 구조 파악**: yona는 `attemptMerge()`(부수효과 없는 미리보기, `PullRequestApp` 뷰 액션이 페이지 렌더링마다 호출)와 `updateMerge()`(부수효과 있음, `PullRequestActor.processPullRequestMerging()`이 PR 생성/관련 PR 재검사 시에만 호출)를 처음부터 별개 메서드로 분리해뒀다. yona의 `attemptMerge()`는 사실 yona의 `attemptMerge()`(뷰 전용, 임시 브랜치로 fetch 후 삭제)에 대응하고, `PullRequestViewController`가 페이지 렌더링마다 그대로 재호출한다 — 그래서 부수효과를 `attemptMerge()` 안에 넣으면 PR 페이지를 열 때마다 알림/이벤트가 잘못 발생한다. 이 경계를 그대로 지키기 위해 부수효과는 전부 신규 `processMergeCheck()`에 넣고, `attemptMerge()` 자체는 건드리지 않았다.
  - **`PullRequestServiceImpl.processMergeCheck(pullRequestId, sender, isNewPullRequest)`(신규, `PullRequestService` 인터페이스에도 추가)**: `attemptMerge()`를 호출한 뒤 yona `processPullRequestMerging()`의 분기를 그대로 재현.
    - `hasDiffCommits()`가 true면 `updatePullRequestCommits()`(기존 `merge()`가 실제 병합 시에만 쓰던 private 헬퍼를 재사용, 반환값을 `List<PullRequestCommit>`로 바꿔 새로 저장된 커밋을 돌려주도록 확장)로 새 커밋을 `PullRequestCommit`에 영속화. 새 커밋이 있으면(①) `isNewPullRequest`가 아닐 때만 `NotificationEvent(PULL_REQUEST_COMMIT_CHANGED)` 발행(②, yona `!message.isNewPullRequest()` 가드와 동일), (③) `PullRequestEvent(PULL_REQUEST_COMMIT_CHANGED)`는 `isNewPullRequest` 여부와 무관하게 항상 기록(yona도 이 부분은 가드가 없음 — PR 생성 시에도 최초 커밋 목록이 타임라인에 남는다), (④) `pullRequest.reviewers.clear()`로 기존 리뷰어 전원 해제.
    - `hasDiffCommits()`가 false이고 `state != MERGED`면(⑤) diff가 다른 경로로 이미 사라졌다는 뜻이라 실제 병합 동작 없이 `isConflict=false`+`receiver=sender` 설정 후 기존 `changeState(id, MERGED, senderLoginId)`([[tickets/p1-08|P1-08]]에서 이미 완성된 NotificationEvent+PullRequestEvent 기록 로직)를 그대로 재사용해 MERGED로 자동 전환.
  - **`PullRequestEvent.addCommitEvents()` 특이사항 그대로 재현**: yona의 이 메서드는 다른 모든 `PullRequestEvent` 생성 지점과 달리 draft-time 병합/취소 최적화(`add()`, [[tickets/p1-40|P1-40]])를 거치지 않고 항상 그대로 저장한다 — 그래서 `recordPullRequestEvent()`(내부적으로 `recordWithDraftMerge()` 경유)를 재사용하지 않고 `pullRequestEventRepository.save()`를 직접 호출하는 `recordCommitChangedEvent()`를 별도로 뒀다.
  - **의도적으로 조정한 부분(oldValue 필드)**: yona의 `PullRequestEvent.oldValue`는 `mergedCommitIdTo`(가상 병합 커밋 ref, `updateMerge()`가 매 재검사마다 갱신)의 변경 전/후 쌍인데, yona는 이 가상 병합 ref 메커니즘 자체를 이식하지 않았다([[tickets/p0-10|P0-10]]/11/12에서 이미 확립된 범위 조정과 같은 기조). 대신 yona가 실제로 매 `attemptMerge()`마다 갱신·영속화하는 `lastCommitId`(소스 브랜치 tip)의 변경 전/후 쌍으로 대체 — `NotificationMessageResolver`가 이 이벤트 타입의 `oldValue`를 애초에 쓰지 않으므로(`newValue.orEmpty()`, [[tickets/p1-27|P1-27]]에서 이미 확인) 화면 표시에는 영향이 없다.
  - **`createPullRequest()`/`PullRequestMergeEventListener.handleRelatedPullRequestMergeEvent()` 재배선**: 둘 다 기존 `attemptMerge(id)` 단독 호출을 `processMergeCheck(id, sender, isNewPullRequest)`로 교체(전자는 `true`, 후자는 `false`) — yona도 `PullRequestMergingActor`(PR 생성)/`RelatedPullRequestMergingActor`(관련 브랜치 push) 둘 다 결국 `processPullRequestMerging()` 하나로 수렴하는 구조와 동일하다.
  - 테스트: `PullRequestServiceSpec.kt` +3(새 커밋 발견 시 커밋 영속화·리뷰어 초기화·PullRequestEvent·알림 전부 확인/PR 생성 시점엔 알림만 생략되고 PullRequestEvent는 남음(NEW_PULL_REQUEST+PULL_REQUEST_COMMIT_CHANGED 2건)/diff 소멸 시 자동 MERGED 전환). `PullRequestMergeEventListenerSpec.kt`는 기존 5개 테스트의 `attemptMerge` 스텁을 `processMergeCheck`로 교체(레드 확인 후 구현). 기존 "PR을 생성하면 NotificationEvent(NEW_PULL_REQUEST)와 PullRequestEvent가 모두 생성되어야 한다([[tickets/p1-39|P1-39]])" 테스트는 커밋이 없는 빈 저장소를 쓰고 있어(`attemptMerge`가 내부에서 예외를 던지고 `createPullRequest`의 try/catch가 삼킴) 영향받지 않음을 확인. 커버리지: `processMergeCheck`/`notifyCommitChanged`/`buildCommitChangedMessage`/`recordCommitChangedEvent` 전부 LINE 100%.
