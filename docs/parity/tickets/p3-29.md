# P3-29: MCP `review_pull_request` 도구가 P3-15(실제 Approve/Request changes) 대신 낡은 "리뷰어 등록"에만 매핑돼 있음

## 배경

사용자가 "PR 승인에 대한 이슈가 있던 걸로 기억한다"고 언급해 재조사한 결과 확정. MCP 서버
(P3-07, AI 에이전트용 도구)의 `review_pull_request` 도구가 다음과 같이 구현돼 있었다:

```kotlin
@Tool(description = "풀 리퀘스트를 리뷰합니다(yona는 승인/변경요청 상태가 없어 리뷰어로 등록하는 동작으로 처리됩니다).")
fun review_pull_request(...): Any {
    pullRequestController.addReviewer(found.id!!, number, currentAuth())
        .requireSuccessForMcp(...)
    return mapOf("status" to "reviewer_added", "number" to number)
}
```

주석/설명 그대로 "yona에는 GitHub 같은 APPROVE/REQUEST_CHANGES 정식 리뷰 상태 기계가 없다"는
전제로 만들어졌는데, 이 MCP 서버(P3-07)가 만들어진 **이후** [[tickets/p3-15|P3-15]]가
`PullRequestReview`(APPROVE/REQUEST_CHANGES/COMMENT, `PullRequestController.submitReview()`)
정식 API를 이미 구현했다 — 하지만 이 MCP 도구는 그 사실을 반영하지 못한 채 방치돼, **AI
에이전트가 이 MCP 서버로는 실제 PR 승인/변경요청을 전혀 할 수 없고 그냥 리뷰어 목록에 이름만
추가되는** 실제 기능 갭이었다.

## 완료 로그

**(2026-09-09) 발견 즉시 수정.**

- `PullRequestMcpTools.kt`의 `review_pull_request`를 `PullRequestController.submitReview()`
  (P3-15)에 연결하도록 재작성 — `state`(APPROVE/REQUEST_CHANGES/COMMENT, 대소문자·공백
  무관하게 파싱)와 `body`(선택) 파라미터를 새로 받는다. 알 수 없는 state 값은
  `McpToolException`으로 명확히 거부(대상 값 그대로 메시지에 포함). 자기 자신의 PR에 대한
  Approve/Request changes 시도는 `SelfReviewException`(400)이 `unwrapForMcp()`를 통해
  그대로 사람이 읽을 수 있는 예외로 전달됨(기존 REST API와 동일한 보장).
- 기존 `review_pull_request`(판정 없이 리뷰어로만 등록)의 동작 자체는 없애지 않고
  `add_reviewer`라는 새 도구로 분리 보존(하위 호환 — 이 이름으로 예전 방식을 쓰던 MCP
  클라이언트가 있을 수 있음).
- 클래스 상단 설계 주석의 낡은 전제("yona에는 정식 리뷰 상태 기계가 없다")도 정정.
- `PullRequestMcpToolsSpec.kt`에 새 시나리오 5개 추가(APPROVE 실제 위임 확인, state 대소문자/
  공백 정규화, 알 수 없는 state 거부, 스코프 없으면 호출 안 함, 신규 `add_reviewer` 도구의
  기존 동작 보존 확인) — 전부 GREEN.

## 완료 기준

- MCP `review_pull_request` 도구로 실제 APPROVE/REQUEST_CHANGES/COMMENT 판정을 남길 수 있다.
- 기존에 이 도구로 "리뷰어 등록만" 하던 워크플로가 `add_reviewer`로 계속 동작한다.
