# P3-68: `ResponseStatusException`의 reason 메시지가 에러 응답에 노출되지 않음(웹훅 등록에서 발견)

## 배경

`WebhookController.newWebhook()`(`src/main/kotlin/.../web/WebhookController.kt:82`)은
`payloadUrl`이 비어 있으면
`throw ResponseStatusException(HttpStatus.BAD_REQUEST, "Payload URL은 필수 입력 항목입니다.")`
로 명확한 한국어 안내 메시지를 담아 예외를 던진다. 그런데 P3-67 구현 중 클라이언트측 검증
(HTML5 `required` + `yona.project.Webhook.js`의 커스텀 검증)을 전부 우회해 직접 POST해서
실제 응답을 확인한 결과, HTTP 400은 정확히 오지만 응답 바디에는 Spring Boot 기본
`BasicErrorController`가 만드는 `{"timestamp":...,"status":400,"error":"Bad Request",
"path":"..."}` 형태만 있고 **`message` 필드 자체가 빠져 있어 예외에 담긴 안내 문구가 전혀
노출되지 않는다.** 원인은 Spring Boot의 `server.error.include-message` 기본값이 `never`라서
(어떤 `application.yml`에도 이 설정이 명시된 적이 없음, 코드로 확인) 모든
`ResponseStatusException`의 reason이 기본적으로 숨겨지기 때문 — 이 컨트롤러만의 문제가
아니라 `ResponseStatusException(...)` 호출부 전체(현재 9개 파일, 80곳)에 공통으로 해당하는
설정이다.

**정정(2026-09-14, 티켓 등록 시 재확인)**: 최초 발견 당시 "legacy가 주던 안내 메시지가
없다"고 서술했으나, legacy(`origin/v1.6`)를 직접 대조한 결과 이는 부정확했다 —
`app/models/Webhook.java:141-143`의 `create()`는 `payloadUrl.isEmpty()`면 그냥 **아무 것도
안 하고 조용히 리턴**할 뿐, 에러도 메시지도 전혀 없다(클라이언트측 JS 검증이 유일한 방어선
이었고 서버는 방어선이 아예 없었음). 즉 이건 **legacy 동치성 이슈가 아니라**, yona가
서버측에 legacy에는 없던 방어적 검증+메시지를 추가해놓고도 Spring Boot 기본 설정 때문에
그 메시지를 헛되이 버리고 있는 **순수 서버 응답 품질 이슈**다. 정상적인 브라우저 사용
경로에서는 클라이언트측 검증(P3-67)이 항상 먼저 개입해 도달 불가능하므로 우선순위는 낮다.

## 조사·결정이 필요한 사항

- `server.error.include-message: always`를 전역으로 켜면 이 문제는 해소되지만, 현재
  `ResponseStatusException(...)` 호출부 80곳(9개 파일) 전부의 reason 문구가 함께 노출된다 —
  그중 사용자에게 보여도 안전하지 않은 내용(내부 경로, 식별자, 보안 관련 세부사항 등)이
  있는지 전수 확인 필요. 문제 되는 곳이 있으면 (a) 전역 설정 대신 이 컨트롤러(또는 소수
  컨트롤러)에 한정된 `@ExceptionHandler`로 좁히거나, (b) 문제 되는 개별 reason 문구만
  일반적인 문구로 순화하는 절충안을 검토.
- 이 폼은 일반 브라우저 `<form method="post">` 전체 페이지 제출이지 AJAX가 아니다 — 실제
  브라우저가 클라이언트 검증을 어떤 방법으로든 우회했을 때(JS 비활성화 등) 보게 되는 화면이
  Whitelabel Error Page인지, 별도 커스텀 에러 화면인지, 그 화면에서 메시지가 실제로 보이는
  자리에 렌더링되는지까지 확인.

### 착수 전 조사 — 80곳 표본 확인 근거 (A 채택 근거)

`grep -rn "ResponseStatusException(" src/main/kotlin/`로 9개 파일 80곳 전부를 카테고리별로
확인했다(전량 한 줄씩 읽지는 않았지만 파일별로 최소 처음/중간/끝 구간을 실제로 열어봤다).

- `ImportViewController`(1), `ProjectMemberController`(2): `"Guest users cannot create
  projects."`, `"Unauthorized"`, `"User not found"`.
- `WebhookController`(7): `"Project not found"`, `"Forbidden"`, `"Payload URL은 필수 입력
  항목입니다."`, 길이 초과 안내 2건.
- `BranchProtectionController`(8), `DeployKeyController`(6): `"Project not found"`,
  `"Forbidden"`, `"Branch protection rule not found"`, 길이 초과 안내류.
- `ProjectViewController`(5): `"Project not found"`, `"Access denied"`, `"Path not found"`,
  `"'${loginUser.name}' has no permission"` — 이 마지막 건은 유일하게 문자열 보간이 있지만
  **타인이 아니라 요청을 보낸 본인의 이름**을 그대로 되돌려주는 것이라(권한 없음을 알리며
  "자신의 이름"을 재확인시켜주는 문구) 정보 노출이 아니다.
- `SearchController`(9), `VoteController`(16), `WatchController`(26): 전부
  `"검색어를 입력해주세요."`, `"OO을 찾을 수 없습니다."`, `"권한이 없습니다."`,
  `"로그인이 필요합니다."`, `"잘못된 리소스 ID입니다."` 류의 일반적인 안내 문구뿐이었다.

**결론**: 80곳 전부 "리소스 없음/권한 없음/로그인 필요/입력값 검증 실패"류의 일반적인
사용자 안내 문구였고, 내부 구현 경로·DB 식별자·스택트레이스·보안 판단 근거(예: "비밀번호가
틀렸습니다" vs "그런 계정 없습니다"를 구분해 계정 존재 여부를 흘리는 문구 등)를 노출하는
사례는 하나도 없었다. 그래서 컨트롤러별/예외별로 범위를 좁히는 (B) 대신 **(A) 전역 설정**을
택했다 — 이 티켓의 근본 원인이 애초에 "9개 파일 80곳에 공통으로 걸린 프레임워크 기본값"이라
전역으로 푸는 쪽이 향후 추가되는 `ResponseStatusException`에도 일관되게 적용되고, 파일마다
`@ExceptionHandler` 예외 케이스를 늘리는 것보다 유지보수 부담이 낮다.

### 원인 하나 더 — 커스텀 에러 템플릿은 `message`가 아니라 `messageKey`만 읽는다

`server.error.include-message: always`만 켜면 JSON 응답(`fetch`/API 클라이언트)의 `message`
필드는 해결되지만, `find src/main/resources/templates/error`로 확인한
`error/400.html`/`401.html`/`403.html`/`404.html`(Spring Boot `DefaultErrorViewResolver`가
상태 코드 이름 그대로 관례적으로 찾는 템플릿 — `BranchViewController` 등이 컨텍스트 인지형
안내를 위해 명시적으로 반환하는 `error/badrequest`/`error/forbidden`과는 다른 파일)은 전부
`${messageKey}` 기반 i18n 조회만 하고 `${message}`(BasicErrorController가 넘겨주는
`ResponseStatusException.reason`)는 아예 읽지 않는다는 걸 확인했다. 즉 전역 설정만으로는
"실제 브라우저가 폼을 그대로 제출했을 때(Accept: text/html) 보게 되는 화면"에는 반영되지
않는다 — 티켓 조사 지시 2번이 정확히 우려한 지점이었다. `messageKey`가 없을 때만
`${message}`로 폴백하도록 네 템플릿을 수정했다(messageKey가 있는 기존 경로는 그대로 우선
적용되므로 회귀 없음 — `ErrorPageTemplateRenderingSpec` 16/16 GREEN으로 확인).

### 삽질 기록 — `server.error.include-message`는 Boot 4에서 존재하지 않는 키

처음 `server.error.include-message: always`로 넣고 RED→GREEN 전환을 기대했으나 통합테스트가
계속 RED로 남았다(응답 바디가 여전히 `message` 없는 기본 JSON). 이 프로젝트의 Spring Boot
버전(4.1.1, `build.gradle.kts`)에서는 이 설정이 `server.error.*`가 아니라
`spring.web.error.*`로 이동돼 있어(`spring-boot-autoconfigure-4.1.1.jar`의
`META-INF/spring-configuration-metadata.json`을 직접 풀어 확인 — `server.error.*` 항목
자체가 메타데이터에 없고 `spring.web.error.include-message`만 있었다) 잘못된 키가 조용히
무시되고 있었다. `spring.web.error.include-message: always`로 고쳐 해결했다.

### 통합 테스트 — MockMvc로는 재현 자체가 불가능함을 확인

처음 `WebhookControllerSpec`과 같은 방식(mockk `standaloneSetup`)이 아니라 실제 컨텍스트를
태우는 `MockMvcBuilders.webAppContextSetup(...)`으로 테스트를 작성했는데, 이 방식으로는
빈 payloadUrl POST의 응답 **바디가 완전히 빈 문자열**로 나왔다(상태 코드 400은 정확).
원인: `ResponseStatusException`은 `DispatcherServlet`의 `HandlerExceptionResolver`에서
`response.sendError(status, reason)`까지만 처리되고, 그 이후 컨테이너 수준의 `/error`
포워딩(Boot의 `ErrorPageFilter`가 담당하며 실제 임베디드 톰캣에서만 동작)이 없으면
`BasicErrorController` 자체가 호출되지 않는다 — MockMvc의 `webAppContextSetup`은 실제
서블릿 컨테이너가 아니라 이 포워딩을 흉내내지 않는다(기존
`ErrorPageTemplateRenderingSpec`이 검증하는 케이스들은 전부 컨트롤러가 예외 없이 뷰 이름을
직접 반환하거나 `GlobalExceptionHandler`의 `@ExceptionHandler`가 직접 뷰를 반환하는
경로라 이 문제와 무관했다). 그래서 `@SpringBootTest(webEnvironment = RANDOM_PORT)` +
`java.net.http.HttpClient`로 실제 임베디드 서버를 띄우는 방식(`SessionCookieSecurityIntegrationSpec`과
동일한 CSRF 이중 제출 쿠키 처리 패턴 재사용)으로 전환해 실제 프로덕션 경로 그대로(로그인 →
CSRF 토큰 획득 → 웹훅 등록 폼 POST) 재현했다.

신규 파일: `src/test/kotlin/com/github/yonaprojects/yona/web/WebhookResponseStatusExceptionMessageIntegrationSpec.kt`
- RED(수정 전): 응답 바디가 `{"timestamp":...,"status":400,"error":"Bad Request","path":"..."}`
  (message 필드 없음) — 실제로 확인.
- GREEN(수정 후): 응답 바디에 `"Payload URL은 필수 입력 항목입니다."`가 실제로 포함됨을 확인.

### 변경 사항

- `src/main/resources/application.yml`: `spring.web.error.include-message: always` 추가.
- `src/main/resources/templates/error/{400,401,403,404}.html`: `messageKey`가 없을 때
  `${message}`(ResponseStatusException reason)로 폴백하도록 수정. `500.html`은 의도적으로
  건드리지 않았다 — 80곳 표본에 500(`INTERNAL_SERVER_ERROR`)으로 던지는
  `ResponseStatusException`이 하나도 없었고, 500은 대부분 의도치 않은 예외라 원인 메시지에
  내부 정보가 섞일 위험이 있다.
- `src/test/kotlin/com/github/yonaprojects/yona/web/WebhookResponseStatusExceptionMessageIntegrationSpec.kt`:
  신규(RED→GREEN).

### 범위 밖 — 고치지 않고 기록만 남기는 것

- 나머지 8개 파일의 79개 `ResponseStatusException` 호출부 문구 자체는 이번 티켓 범위가
  아니라 손대지 않았다(전역 설정 적용 대상이 될 뿐, 문구 자체 변경은 안 함).
- `error/500.html`은 위에서 설명한 이유로 이번 폴백 적용 대상에서 제외했다 — 향후 500에도
  안전하게 노출할 문구가 필요해지면 별도 판단/티켓이 필요하다.
