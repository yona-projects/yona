# P3-68: `ResponseStatusException`의 reason 메시지가 에러 응답에 노출되지 않음(웹훅 등록에서 발견)

## 배경

`WebhookController.newWebhook()`(`src/main/kotlin/.../web/WebhookController.kt:82`)은
`payloadUrl`이 비어 있으면
`throw ResponseStatusException(HttpStatus.BAD_REQUEST, "Payload URL은 필수 입력 항목입니다.")`
로 명확한 한국어 안내 메시지를 담아 예외를 던진다. 그런데 P3-67 구현 중 클라이언트측 검증
(HTML5 `required` + `yona.project.Webhook.js`의 커스텀 검증)을 전부 우회해 직접 POST해서
실제 응답을 확인한 결과, HTTP 400은 정확히 오지만 응답 바디에는 Spring Boot 기본
`BasicErrorController`가 만드는 `{"timestamp":...,"status":400,"error":"Bad Request",
"path":"..."}` 형태만 있고 **`message` 필드 자체가 빠져 있어 예외에 담긴 안내 문구가 전혀
노출되지 않는다.** 원인은 Spring Boot의 `server.error.include-message` 기본값이 `never`라서
(어떤 `application.yml`에도 이 설정이 명시된 적이 없음, 코드로 확인) 모든
`ResponseStatusException`의 reason이 기본적으로 숨겨지기 때문 — 이 컨트롤러만의 문제가
아니라 `ResponseStatusException(...)` 호출부 전체(현재 9개 파일, 80곳)에 공통으로 해당하는
설정이다.

**정정(2026-09-14, 티켓 등록 시 재확인)**: 최초 발견 당시 "legacy가 주던 안내 메시지가
없다"고 서술했으나, legacy(`origin/v1.6`)를 직접 대조한 결과 이는 부정확했다 —
`app/models/Webhook.java:141-143`의 `create()`는 `payloadUrl.isEmpty()`면 그냥 **아무 것도
안 하고 조용히 리턴**할 뿐, 에러도 메시지도 전혀 없다(클라이언트측 JS 검증이 유일한 방어선
이었고 서버는 방어선이 아예 없었음). 즉 이건 **legacy 동치성 이슈가 아니라**, yona가
서버측에 legacy에는 없던 방어적 검증+메시지를 추가해놓고도 Spring Boot 기본 설정 때문에
그 메시지를 헛되이 버리고 있는 **순수 서버 응답 품질 이슈**다. 정상적인 브라우저 사용
경로에서는 클라이언트측 검증(P3-67)이 항상 먼저 개입해 도달 불가능하므로 우선순위는 낮다.

## 조사·결정이 필요한 사항

- `server.error.include-message: always`를 전역으로 켜면 이 문제는 해소되지만, 현재
  `ResponseStatusException(...)` 호출부 80곳(9개 파일) 전부의 reason 문구가 함께 노출된다 —
  그중 사용자에게 보여도 안전하지 않은 내용(내부 경로, 식별자, 보안 관련 세부사항 등)이
  있는지 전수 확인 필요. 문제 되는 곳이 있으면 (a) 전역 설정 대신 이 컨트롤러(또는 소수
  컨트롤러)에 한정된 `@ExceptionHandler`로 좁히거나, (b) 문제 되는 개별 reason 문구만
  일반적인 문구로 순화하는 절충안을 검토.
- 이 폼은 일반 브라우저 `<form method="post">` 전체 페이지 제출이지 AJAX가 아니다 — 실제
  브라우저가 클라이언트 검증을 어떤 방법으로든 우회했을 때(JS 비활성화 등) 보게 되는 화면이
  Whitelabel Error Page인지, 별도 커스텀 에러 화면인지, 그 화면에서 메시지가 실제로 보이는
  자리에 렌더링되는지까지 확인.

## 완료 기준

- [ ] 위 조사를 거쳐 전역 설정/좁은 범위 처리 중 하나를 결정하고 구현.
- [ ] 클라이언트 검증을 우회한 웹훅 등록 요청의 응답(또는 렌더링된 에러 화면)에 실제로
      "Payload URL은 필수 입력 항목입니다."가 노출됨을 통합 테스트로 확인.
- [ ] 전역 설정을 택했다면, 기존 `ResponseStatusException` 80곳 중 노출돼도 안전한지 표본
      확인한 근거를 완료 로그에 남길 것(전수 검토가 비현실적이면 최소한 카테고리별 대표
      사례 확인).
