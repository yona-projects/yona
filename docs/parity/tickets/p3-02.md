- **우선순위 구분**: P3
- **상태(원본 체크박스)**: `[~]`
- **비고(원문)**: **2026-08-21 사용자 제안, 설계 논의만 진행됨 — 코드 0줄.** 용도: 이슈/PR 등 사용자 워크플로 + 관리자 운영(백업/웹훅/권한) + CI/CD 자동화 세 가지 전부 커버. 언어는 **Go로 결정**(설치 직후 바로 실행 요구사항 때문에 JVM 콜드스타트가 있는 Kotlin 제외, 단일 정적 바이너리로 `gh`(Go+Cobra)와 동일 스택 채택). **명령 트리 초안**(전부 미구현): `yona auth login/logout/status`, `yona issue list/create/view/close/comment`, `yona pr list/create/view/merge/review`, `yona project list/view`, `yona admin backup create/restore`, `yona admin webhook list/create/delete`, `yona admin permission audit`, `yona api <method> <path>`. 배포 계획(미구현, 계획만): `goreleaser`로 GitHub Releases + Homebrew tap + Scoop bucket + `.deb`/`.rpm`. 인증 방식은 Personal Access Token 필요 → **yona 서버 쪽에 토큰 인증 경로가 있는지 자체가 아직 미확인**(있는지 없는지도 안 알아봄, 착수 전 최우선 확인 필요). **2026-08-24 추가(토큰 스코프 재설계 필요, 코드 검증 완료)**: 위 미확인 사항은 확인됨 — `ApiTokenAuthenticationFilter.kt`(`src/main/kotlin/.../config/`)가 `Authorization: token <값>`/`Yona-Token` 헤더를 파싱해 `userRepository.findByToken(token)`으로 사용자를 찾고, 매칭되면 그 유저의 `authorities` 전체를 그대로 부여하는 구조로 **이미 동작 중**임을 확인. 문제는 토큰이 저장소·권한 단위로 전혀 스코프되지 않는 **전권 단일 토큰**이라는 점 — CLI(P3-02)에 이 토큰을 그대로 쓰면 토큰 하나 유출 시 그 사용자의 전체 저장소·전체 권한이 노출됨. **GitHub Fine-grained PAT 모델 채택 결정**: 저장소 단위 접근 범위(전체 저장소 vs 선택한 저장소 목록) + 리소스별 세분화된 권한(예: contents/issues/pull-requests/metadata/administration/webhooks 각각 none·read·write)을 토큰에 부여하는 구조로 재설계. `User.token` 단일 필드를 대체할 `ApiToken` 엔티티(owner, token_hash, 저장소 범위, 리소스별 권한 맵, 만료일, 마지막 사용일) 신설 필요(미생성), `ApiTokenAuthenticationFilter`도 단순 `userDetails.authorities` 전체 부여 방식에서 **요청 대상 저장소+요청 리소스를 토큰의 스코프와 대조하는 인가 체크**로 재작성 필요(미착수). **2026-08-24 추가(기존 리소스 taxonomy 재사용 검토, 코드 검증 완료)**: 권한 스코프 카테고리를 GitHub처럼 `contents`/`issues`/`pull-requests` 등 새 이름으로 만들지, 이미 있는 `domain/enumeration/ResourceType.kt`의 **33종 enum**(`ISSUE_POST`/`PULL_REQUEST`/`WEBHOOK`/`CODE` 등, 개수 코드로 확인됨)을 스코프 매트릭스 축으로 재사용할지는 검토 필요 — 기존 taxonomy가 알림/감사 로그 전반에 이미 쓰이고 있어 일관성 면에서 유리하지만, GitHub 스타일 대분류보다 훨씬 세분화돼 있어(32개) 토큰 발급 UI에서 사용자가 다루기엔 카테고리를 묶어야 할 수 있음(예: `ISSUE_POST`/`ISSUE_COMMENT`/`ISSUE_LABEL`을 issues로 그룹핑). 최종 채택 여부 미결정. **토큰 만료 정책(2026-08-24 결정)**: `ApiToken`의 만료일을 선택적 필드가 아니라 **필수로 강제**(무기한 토큰 발급 자체를 막음) — GitHub Fine-grained PAT처럼 최대 유효기간 설정을 의무화. **2026-08-28 1라운드 TDD 착수(Part1 Step1~3 완료, Step4~6/Part2 CLI는 다음 라운드)**: `docs/yona-wiki/plans/p3-02-cli-and-rest-api.md` 완료 로그 참고. `domain/apitoken/` 패키지에 `ApiToken`/`ApiTokenScope` 엔티티(`expiresAt` DB NOT NULL로 무기한 토큰 저장 거부 강제, repo scope는 `allRepositories`+`scopedProjects` ManyToMany, resource scope는 그룹별 permission을 담는 별도 엔티티), `ApiTokenScopeGroup`(8개 그룹으로 기존 `ResourceType` 33종 전수 매핑 확정), `ApiTokenAuthorizer`(순수 판정 로직) 신설. `ApiTokenAuthenticationFilter`는 신규 `/api/v1/projects/{owner}/{project}/{resource}` 네임스페이스로 오는 요청만 스코프 판정을 거치도록 재작성했고, 그 외 기존 URL은 레거시 전권 토큰 경로를 그대로 유지(마이그레이션 전략은 여전히 미정, co-existence로 임시 처리). 검증 중 실제 버그 2건 발견/수정: (1) `findByTokenHash`가 연관관계를 지연 로딩해 필터(트랜잭션 경계 밖)에서 `LazyInitializationException` 발생 → JOIN FETCH 쿼리로 즉시 로딩 전환 (2) `scopedProjects`의 `CascadeType.PERSIST`가 이미 저장된(detached) Project를 담아 토큰을 저장할 때 예외 발생 → cascade 제거.  **2026-08-29 추가(Part1 Step4~6 REST API 구현 완료, TDD)**: `docs/yona-wiki/plans/p3-02-cli-and-rest-api.md` 2라운드 — 이슈 REST API(`web/IssueRestApiController.kt`, `/api/v1/projects/{owner}/{project}/issues` 목록/생성/조회/수정/댓글/클로즈), PR REST API(`web/PullRequestApiController.kt`, `/api/v1/projects/{owner}/{project}/pull-requests` 목록/생성/조회/머지/리뷰어등록), 프로젝트 조회 REST API(`web/ProjectRestApiController.kt`, `/api/v1/projects/{owner}[/{project}]` 목록/조회)를 신설. 세 컨트롤러 모두 기존 숫자 projectId 기반 컨트롤러(`IssueController`/`PullRequestController`)에 owner/project 이름을 projectId로 바꿔 위임하는 얇은 어댑터로 구현해 신규 서비스 로직을 최소화했다. `SecurityConfig.kt`에 `/api/v1/projects/**` 쓰기 경로(GET 제외) `.authenticated()` 방어선 추가. **알려진 한계(미해결로 이월)**: 프로젝트 조회 API는 URL에 리소스 세그먼트가 없어(owner/project 2단뿐) `ApiTokenAuthenticationFilter`의 scopedApiPattern(owner/project/resource 3단 필수)과 맞지 않아 Fine-grained 스코프 토큰으로는 아직 호출 불가(세션/레거시 전권 토큰만 가능) — 상세는 계획 문서 리스크 표 참고. **2026-09-06 추가(사용자 제보 확인 — Part2 CLI 본체가 별도 저장소 `gh:yona-projects/yona-cli`(구 `github.com/search5/yona-cli`, 최근 조직 이전)에 실제로 존재함을 코드 clone·빌드·테스트로 검증 완료)**: 이 표의 요약문은 위 2026-08-29 항목(Part1 REST API)까지만 반영돼 있어 **Part2 CLI 진행 상황이 표에서 누락된 상태**였다 — 실제로는 계획 문서 `docs/yona-wiki/plans/p3-02-cli-and-rest-api.md`에 4~13라운드(Step7~10, 실서버 골든패스 수동 검증 2회, 실버그 7건 이상 발견·수정 포함)의 상세 완료 로그가 이미 존재하며 이번에 표와 동기화한다. `yona-cli` 저장소 실사 결과: 커밋 17개, Go 소스 약 9,600줄, `cmd/`(auth/server/browse/issue/pr/project/label/search/org/admin/api 전체 명령 트리)+`internal/api/`(REST 클라이언트)+`internal/gitutil/`+`internal/weburl/`+`internal/config/` 구조로 `gh` CLI
