# P3-35: `project fork`가 REST API/CLI로는 조직(organization) 목적지를 지원하지 않음

## 배경

`docs/yona-wiki/plans/p3-02-cli-and-rest-api.md`의 11라운드가 이미 발견해 "미해결(다음
라운드 이후로 이월)"로 남겨뒀던 항목을 코디네이터가 재확인했다.

- `domain/project/ProjectService.kt`의 `forkProject(projectId, forkerId, destinationOwner,
  destinationName)`은 서비스 계층에 이미 `destinationOwner` 파라미터가 있다.
- 웹 UI(`web/ProjectViewController.kt`의 세션 기반 `fork()`)는 폼 파라미터로 조직을 목적지로
  선택할 수 있다(GitHub의 "Fork to organization" 동작과 동일).
- 하지만 `web/ProjectRestApiController.fork()`(`POST /api/v1/projects/{owner}/{project}/fork`,
  `yona-cli`가 쓰는 경로)는 요청 바디를 전혀 받지 않고 `web/ProjectController.forkProject()`에
  위임하는데, 이 메서드는 `projectService.forkProject(project.id!!, user.id!!)`만 호출해
  `destinationOwner`를 항상 빈 문자열(기본값, forker 본인 계정)로 고정한다.
- `yona-cli`의 `yona project fork`(`cmd/project.go`)도 대응하는 플래그가 없다.

즉 REST API/CLI로는 항상 forker 본인 계정으로만 fork되고, 조직으로는 fork할 방법이 없다.
"깨진 기존 기능"이 아니라 "서비스 계층엔 있는데 REST에 노출이 안 된 것"이라, 스키마 변경 없이
얇은 배선만 추가하면 되는 작음+명확한 갭이다.

## 범위

1. `web/ProjectRestApiController.fork()`에 선택적 요청 바디(`destinationOwner: String?`)를
   추가해 `ProjectController.forkProject()`에 전달.
2. `web/ProjectController.forkProject()`가 `destinationOwner`를 받아
   `projectService.forkProject(project.id!!, user.id!!, destinationOwner ?: "")`로 위임하도록
   수정(세션 기반 `ProjectViewController.fork()`가 이미 하는 것과 동일한 위임 방식 확인 후 통일).
3. `yona-cli`의 `internal/api/project.go`에 fork 요청 바디 필드 추가, `cmd/project.go`의
   `newProjectForkCmd()`에 `gh repo fork --org` 관례를 따르는 `--to-owner` 플래그 추가.
4. 컴파일 확인 → 관련 테스트(`ProjectRestApiControllerSpec`/`ProjectControllerSpec` 등) 재실행 →
   실사용 검증(실제 조직을 만들고 그 조직으로 실제 fork REST 호출 + `yona-cli`로 재현, fork된
   프로젝트의 owner가 실제로 그 조직인지 확인).

## 완료 기준

- REST API(`POST /api/v1/projects/{owner}/{project}/fork`)로 `destinationOwner`를 지정하면
  그 조직 소유로 fork된다(빈 값이면 기존과 동일하게 forker 본인 계정).
- `yona-cli`의 `yona project fork --to-owner <org>`로 동일하게 동작한다.
- 기존(목적지 미지정) 동작은 회귀 없이 그대로 유지된다.

## 완료 로그

### 2026-09-09 — 구현 중 실제 보안 취약점 발견 및 근본 수정 (인가 우회 방지)

착수 전 웹 UI의 세션 기반 fork 흐름(`ProjectViewController.newFork()`/`fork()`/`doClone()`)을
읽던 중, `newFork()`(GET, 폼 렌더링)만 `organizationUserRepository.findByUserIdAndRoleId(...,
ORG_ADMIN)`으로 목적지를 forker 본인 또는 forker가 실제로 관리하는 조직으로 제한하고, 실제로
fork를 수행하는 `fork()`/`doClone()`(POST) 두 곳은 클라이언트가 보낸 `owner` 파라미터를 아무
검증 없이 그대로 `ProjectServiceImpl.forkProject(destinationOwner=...)`에 넘긴다는 것을
발견했다. `ProjectServiceImpl.forkProject()` 자체에도 이름 충돌 검사(`findByOwnerAndName`)
외에는 목적지 소유권 검증이 전혀 없었다 — `Project.owner`가 실제 User/Organization과 참조
무결성이 없는 자유 문자열이라, **로그인만 한 임의 사용자가 자신이 속하지 않은 조직 이름이나
다른 사용자의 loginId를 destinationOwner로 지정해, 그 이름에 아직 프로젝트가 없기만 하면
그 네임스페이스에 프로젝트를 만들고 스스로 MANAGER가 될 수 있는** 인가 우회(namespace
squatting/impersonation) 취약점이었다. 기존 `ProjectServiceImplSpec.kt`의 "MANAGER 역할을
찾지 못하면 예외가 발생해야 한다" 테스트가 임의의 `destinationOwner`("dest-owner2")로 forkProject를
호출하면서도 이 문제를 검증 없이 통과시키고 있었던 것으로 실제 코드에서 이 결함이 이미 방치돼
있었음을 재확인했다(RED로 직접 재현: 이 테스트에 org 설정을 넣지 않고 실행하면 통과해버림).

**근본 수정**: `ProjectServiceImpl`에 `acceptTransfer()`가 이미 쓰고 있던
`isAuthorizedToAcceptTransfer(destination, acceptor)`(본인 계정이거나, 그 이름의 Organization이
실재하고 호출자가 그 조직의 ORG_ADMIN인 경우만 true)를 `forkProject()`에도 그대로 재사용해,
이름 충돌 검사보다 먼저 목적지 인가를 검증하도록 수정했다. 권한이 없으면
`IllegalArgumentException`(400, 명확한 한국어 메시지)으로 거부하고 어떤 DB/파일시스템 작업도
일어나지 않는다(`findByOwnerAndName`조차 호출 전에 차단 — 저장 시도 이전에 거부됨을 테스트로
확인).

**회귀 정리**: 이 검증 추가로 기존 `ProjectServiceImplSpec.kt`의 하드링크 복제 메커니즘
전용 테스트 7개(임의의 `destOwner` 문자열을 쓰면서 조직 설정을 하지 않았던 것들)가 깨졌다 —
이 테스트들이 검증하려는 것은 인가가 아니라 파일시스템 복제 로직이므로, forker의 `loginId`를
그 `destOwner`와 동일하게 맞춰(자기 자신에게 fork) 새 인가 검사를 자연스럽게 통과시키는 방식으로
수정했다(로직 자체는 변경 없음, 픽스처만 조정). 신규 테스트 2개 추가: "본인 계정도 아니고
ORG_ADMIN으로 속한 조직도 아닌 임의의 destinationOwner로는 fork가 거부돼야 한다"(저장 시도
0회까지 확인), "forker가 ORG_ADMIN으로 속한 조직으로는 fork가 허용돼야 한다".

### 2026-09-09 — 원래 범위(REST API/CLI 조직 목적지 노출) 구현

- `web/ProjectController.kt`의 `forkProject()`에 선택적 요청 바디
  `ForkProjectRequest(destinationOwner, destinationName)` 추가, `ProjectService.forkProject()`에
  그대로 전달(생략 시 기존과 동일하게 forker 본인 계정).
- `web/ProjectRestApiController.kt`의 `fork()` 어댑터가 그 요청 바디를 그대로 위임하도록 수정.
- `yona-cli`: `internal/api/project.go`에 `ForkProjectRequest` 타입 추가,
  `ForkProject()`가 이를 받아 요청 바디로 전송하도록 시그니처 변경. `cmd/project.go`의
  `newProjectForkCmd()`에 `gh repo fork --org` 관례를 따르는 `--to-owner`/`--to-name` 플래그
  추가.

- **실사용 검증(실제 서버+실제 CLI 바이너리, H2 격리 인스턴스, 포트 18299)**:
  1. admin이 관리자인 조직(`acme-org`)으로 `yona project fork admin/acme-fork-src --to-owner
     acme-org` → 성공(`acme-org/acme-fork-src`로 실제 생성 확인).

     정확한 거부 메시지 확인.

     (`admin/bobs-project`).
  4. **실존하는 다른 사용자(bob)의 네임스페이스를 사칭**해 fork 시도(`--to-owner bob`) → 실제
     HTTP 400으로 거부 확인 — 가장 현실적인 공격 시나리오까지 실제로 막히는 것을 재확인.
