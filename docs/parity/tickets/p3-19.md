# P3-19: GPG 커밋 서명 검증(Verified/Unverified 배지)을 Git 실사용 검증 + Mercurial까지 확장

## 배경

P3-03에서 Git 커밋의 GPG 서명 검증(`GpgSignatureVerifier`, `Commit.getGpgVerificationStatus()`,
커밋 목록/상세 화면의 Verified/Unverified 배지)을 TDD로 구현·완료했다고 기록돼 있으나, 실제
브라우저/CLI로 GitHub와 동일하게 동작하는지 사용자가 직접 확인한 적은 없다. 또한 Mercurial
쪽은 커밋 서명 검증 자체가 아직 없다(P3-12 범위에 포함되지 않았음 — Mercurial은 git과
서명 메커니즘 자체가 다르다: 커밋 오브젝트에 서명이 내장되는 git과 달리, Mercurial은
`gpg` 익스텐션이 저장소의 `.hgsigs` 파일에 "리비전 해시 + 서명자 + 서명" 한 줄을 별도로
커밋하는 방식이다).

## 범위

1. **Git**: 이미 구현된 `GpgSignatureVerifier`/Verified·Unverified 배지가 실제로 GitHub와
   동일하게 동작하는지 실사용 검증 — 실제 GPG 키로 서명한 커밋을 push한 뒤 커밋 목록/커밋
   상세 화면에서 배지가 올바르게(서명 있고 검증됨=Verified, 서명 없거나 검증 실패=Unverified)
   뜨는지 브라우저 또는 API 응답으로 직접 확인. 버그가 있으면 이번 티켓에서 수정.
2. **Mercurial**: 커밋 서명 검증 기능 자체가 없으므로 새로 설계·구현해야 한다 — Mercurial의
   `gpg` 익스텐션 방식(`.hgsigs` 파일)을 사용할지, 아니면 yona 자체적으로 다른 방식을 쓸지는
   착수 시 결정 필요(모호하면 GitHub 방식 우선 원칙에 따라, 최종적으로 사용자에게 보여지는
   Verified/Unverified 배지의 UX는 git 쪽과 동일하게 맞출 것). hg4j에 `.hgsigs` 파싱/서명
   검증 지원이 있는지 먼저 확인 필요.

## 완료 기준

- Git: 실제 서명된 커밋 → 커밋 목록/상세 양쪽에 Verified 배지, 서명 없는 커밋 → Unverified
  (또는 배지 없음, GitHub 컨벤션 확인 후 결정) 확인.
- Mercurial: 위와 동일한 사용자 경험을 Mercurial 저장소에서도 재현.

1. 회원가입(`gpgtester`) → 실제 `gpg --batch --generate-key`로 키 생성 → `/user/editform/gpg-keys`로
   공개키 등록.
2. `git clone`/`git push` (HTTP Basic 인증)로 실제 저장소에 커밋 3개를 만들어 각각 확인:
   - 서명 없는 커밋 → 커밋 목록/상세 양쪽 배지 없음(UNSIGNED, GitHub 컨벤션과 동일).

   - 등록되지 않은(다른 GNUPGHOME의) 키로 서명 → 커밋 상세 `Unverified`(회색) 배지.
3. 셋 다 실제 렌더링된 HTML(`code/history.html`, `code/diff.html`)에서 직접 확인 — 버그 없음,
   추가 수정 불필요. Git 쪽 범위는 완료.

### 2026-09-08 — Mercurial 쪽 설계 결정 + hg4j에서 발견한 버그

**설계 조사 결과**: hg4j에 이미 `io.github.search5.hg4j.gpg.GpgSignature`(BouncyCastle 기반 실제
OpenPGP sign/verify)와 `CommitCommand.setGpgSignature()`가 존재했으나, 실제로는 **아무도 호출하지
않는 죽은 코드**였고, 게다가 **버그가 있었다**: `CommitCommand.java`(commit() 메서드, ~926-941줄)가
서명을 `clMeta` 맵에 담아 `changelog.appendRevision(changelogTextBytes, clMeta, ...)`로 넘기는데,
이 오버로드는 내부적으로 `Revlog.wrapMetadata()`를 타서 `"\x01\n key: value \n...\x01\n"` 형태의
블록을 콘텐츠 앞에 붙인다 — 이건 실제 Mercurial의 **filelog rename/copy 메타데이터 포맷**(예:
`hg mv` 추적, LFS 포인터)이지 changelog(커밋) 리비전에는 전혀 해당하지 않는 포맷이다. 이 경로가
실행되면 changelog 리비전의 원문 바이트가 "40자 매니페스트 헥스로 시작"이라는 계약을 깨서
`LogCommand`의 파서(및 실제 `hg` 자신)가 그 커밋을 파싱하다 깨진다 — 즉 지금 이 상태로 쓰면
changelog가 손상된다. (다행히 yona 쪽에서 이 API를 호출하는 곳이 전혀 없어 실사용 피해는 없었음.)

**최종 설계 결정** (티켓의 "모호하면 GitHub 방식 우선" 원칙 적용): 실제 Mercurial의 `gpg`
익스텐션(`.hgsigs` 파일 — 리포지토리에 커밋되는 별도의 버전관리 파일에 "리비전 여러 사람이 각자
서명 추가" 방식으로 기록, "이 커밋 자체에 내장된 서명"이 아니라 "누군가 나중에 이 리비전을
검토·서명했다"는 제3자 attestation 성격)을 따르지 않는다. 대신 git의 `gpgsig` 커밋 헤더와 완전히
동일한 셰이프로, changelog의 **`extra` 딕셔너리**(현재 `branch`/`close`가 이미 쓰는 바로 그 필드 —
날짜 줄에 `\0`로 join되어 붙는 key:value 목록)에 `gpgsig`(armored 서명, git과 동일하게 `\n`→`\\n`
이스케이프)/`gpgfingerprint`를 추가하는 방식을 채택한다. 커밋 작성자 본인이 만든 이 특정 리비전에
내장된 서명이라는 의미가 git과 완전히 동일해지고, 최종 사용자에게 보이는 Verified/Unverified 배지
UX도 git과 100% 동일하게 만들 수 있다 (`.hgsigs` 방식은 "이 정확한 커밋이 검증됐는가"라는 배지
질문 자체와 셰이프가 맞지 않는다 — 별도 파일의 리비전에 따라 달라지고 여러 사람이 각자 다른 시점에
추가할 수 있어 단일 배지로 환원되지 않음).

**Mercurial 실사용 검증 시 유의점(다음 담당자에게)**: 위 결정에 따라 실제 `hg sign`/`.hgsigs`로는
이 배지를 만들 수 없다 — hg4j 자체 API로 서명된 커밋을 만들어야 한다(실제 `hg` CLI로는 재현 불가,
git 때처럼 `git commit -S`를 실제 바이너리로 실행하는 방식이 여기선 안 통함). 실사용 검증은 (1)
hg4j 자체 API/테스트로 서명 커밋 생성 → (2) yona에 실제로 push(HTTP, `vcs=MERCURIAL`) → (3) 커밋
목록/상세 화면 HTML을 직접 curl로 받아 Verified/Unverified 배지 확인, 순서로 진행할 것 (Git 때와
동일한 실사용 검증 스크립트/계정을 재사용 가능 — 이 로그 위에 기록된 절차 참고).

### 2026-09-08 — Mercurial 쪽 구현·테스트·실사용 검증 완료

앞선 로그의 설계 결정("git의 gpgsig 헤더와 완전히 동일한 셰이프로 changelog `extra`에 내장")과
hg4j 버그 진단을 그대로 이어받아 구현했다. 두 저장소 모두 커밋·푸시 완료.

**hg4j 쪽 (`CommitCommand.java`/`LogCommand.java`/`HgCommit.java`)**

- 죽은 코드였던 `CommitCommand.gpgSignature` 필드/`setGpgSignature()`/`clMeta`
  (→`Revlog.wrapMetadata()`, filelog rename/copy 메타데이터 포맷 오용 버그)를 완전히 제거했다.
- 새 API: `CommitCommand.setGpgSigner(String fingerprint, GpgSigner signer)` —
  `GpgSigner`는 `String sign(byte[] unsignedChangelogText) throws Exception` 함수형 인터페이스.
  `commit()`은 (1) `branch`/`close`/(서명 시에만) `gpgfingerprint`를 담은 `extraParts`로
  "서명 대상" changelog 원문 바이트를 먼저 조립해 `signer.sign(...)`에 그대로 넘기고,
  (2) 반환된 armored 서명을 `gpgsig` extra로 추가한 뒤 최종 changelog 원문을 다시 조립한다.
  두 조립 모두 새 private 헬퍼 `buildChangelogText(...)`를 재사용해 "gpgsig 필드만 다르고
  나머지는 byte-for-byte 동일"을 구조적으로 보장한다(git
  `GpgSignatureVerifier.signedDataOf()`의 "gpgsig 헤더만 제거" 계약과 동일한 정신).
  `gpgfingerprint`는 서명 이전에 이미 extra에 들어가므로(서명 대상 페이로드에도 포함됨) 이
  필드는 서명 검증과 무관한 순수 정보용이다(실제 서명 키 식별은 git처럼 서명 패킷 자체의
  issuer key ID로 한다).
  extra 항목은 `buildChangelogText`가 join 직전에 항상 정렬한다(실제 hg의
  `changelog.encodeextra`가 키 알파벳순 정렬을 요구 — branch < close < gpgfingerprint < gpgsig).
- 새 public 헬퍼 `CommitCommand.stripExtraKey(extraPart, key)` — 인코딩된 extra 문자열에서
  특정 키 항목"만" 제거(다른 항목은 원문 그대로 보존). `LogCommand.call()`이 이걸 이용해
  저장된 리비전의 원문에서 `gpgsig`만 제거한 "서명 대상이었던 바이트"를 재구성해
  `HgCommit.getUnsignedChangelogText()`로 노출한다 — 서명 시점에 실제로 서명된 바이트와
  정확히 일치함을 hg4j 자체 라운드트립 테스트로 확인(아래).
- `HgCommit`(hg4j 값 객체)에 `getGpgSignature()`/`getGpgFingerprint()`/
  `getUnsignedChangelogText()` 3개 접근자 추가(기존 9-인자 생성자는 유지해 하위 호환).
- 테스트: `GpgSignatureTest.testCommitWithGpgSignerRoundTripsAndVerifies` — 실제
  BouncyCastle RSA 키로 서명 → `LogCommand`로 읽어옴 → `GpgSignature.verify()`로 암호학적
  검증 성공 확인 + 변조된 페이로드/무관한 공개키에 대해서는 검증 실패 확인(negative case).
  `CommitCommandTest.testGpgSignatureIsStoredInChangelogExtraNotMetadata` — 예전에 버그난
  metadata 경로를 검증하던 테스트를 새 포맷 검증으로 재작성: changelog 리비전의 filelog
  metadata 채널은 완전히 비어있고, 원문은 여전히 40자 매니페스트 헥스로 시작하며,
  `gpgsig`/`gpgfingerprint`는 `LogCommand`로 정상적으로 읽힘을 확인. hg4j 전체 테스트
  스위트(2301개) 재실행 — 1개 실패(`Wire1CommandsCoverageTest`,
  changegroup-on-empty-repository)는 이 작업 시작 전 커밋(`git stash`)에서도 동일하게
  재현되는 기존 결함으로 확인(이번 변경과 무관, 수정하지 않음 — 아래 "기타 발견 사항" 참고).

**yona 쪽 (`GpgSignatureVerifier.kt`/`HgCommit.kt`/`HgRepository.kt`/`RepositoryService.kt`)**

- `GpgSignatureVerifier`의 검증 코어(서명 파싱 → 후보 키 조회
  `findByAssociatedKeyIdsContaining` → 후보별 암호학적 검증 → author 이메일이 그 키의
  `verifiedEmails`에 있는지)를 `verifyRaw(rawSignature, signedData, authorEmail,
  commitLabel)` private 함수로 뽑아, git용 `verify(RevCommit)`과 신규
  `verify(io.github.search5.hg4j.api.HgCommit)` 둘 다 이 하나의 함수를 그대로 재사용한다 —
  "등록되지 않은 키/타인의 키/이메일 불일치는 절대 VERIFIED 안 됨"이라는, 이미 git 테스트로
  핀(pin)된 보안 실패 모드가 Mercurial에서도 코드 경로 자체가 같아 자동으로 보장된다(로직을
  두 번 구현하지 않음).
  `verify(NativeHgCommit)`은 `HgCommit.getGpgSignature()`(armored 서명)/
  `getUnsignedChangelogText()`(서명 대상 페이로드)를 그대로 쓰고, author 이메일은
  hg4j의 `"Name <email>"` 원본 문자열에서 뽑는다(아래).
- `HgCommit.kt`: `AUTHOR_PATTERN` 정규식으로 이메일만 뽑는 로직을 companion object의 public
  `parseAuthorEmail(raw: String): String?`로 분리해 `GpgSignatureVerifier`와 공유(정규식
  중복 방지). `getGpgVerificationStatus()` 스텁을 제거하고 `GitCommit.kt`와 동일한 패턴의
  주입형 `gpgVerifier: (NativeHgCommit) -> GpgVerificationStatus` 람다(기본값
  no-op UNSIGNED, 기존 테스트 영향 없음)로 교체.
- `HgRepository.kt`: 동일 패턴의 `gpgVerifier` 파라미터를 생성자에 추가하고, `HgCommit(...)`
  생성 지점 8곳 전부(`getMetaDataFromPath`/`fileAsJson`/`getHistory`/`getCommit`/
  `getBranches`/`getHeadBranch`/`getTags`/`getParentCommitOf`)에 실제로 전달.
- `RepositoryService.kt`: `MERCURIAL`/`HG` 분기의 `HgRepository(...)` 생성 시
  `gpgVerifier = { nativeHgCommit -> gpgSignatureVerifier.verify(nativeHgCommit) }` 주입
  (git 분기와 동일한 패턴).
- 새 통합 테스트 `HgGpgSignatureVerifierSpec.kt`(`GpgSignatureVerifierSpec.kt`와 동일한
  5개 케이스: UNSIGNED/VERIFIED/UNVERIFIED-미등록/UNVERIFIED-타인키/UNVERIFIED-이메일불일치) —
  실제 `gpg` 바이너리로 만든 키를 그대로 쓰되(git 테스트와 동일 신뢰 수준), 서명 생성 자체는
  실제 `hg` CLI가 이 포맷을 만들 수 없으므로 `gpg --detach-sign`을 직접 셸아웃해 hg4j
  `CommitCommand.setGpgSigner()`에 넘기는 방식으로 실제 서명된 Mercurial 커밋을 만든다.
  5개 전부 통과(`./gradlew test --tests
  "...HgGpgSignatureVerifierSpec" -x jacocoTestReport` → `tests="5" ... failures="0"
  errors="0"`, VERIFIED 케이스가 실제로 성공해 서명→내장→읽기→암호학적 검증 전체 왕복이
  end-to-end로 검증됨). 기존 `GpgSignatureVerifierSpec`(git, 7케이스)/`HgRepositorySpec`
  포함 gpgkey+vcs 패키지 전체 376개 테스트 재실행 — 전부 통과(0 failures/0 errors), 리팩터링이
  기존 git 검증 로직/기존 Hg 기능을 회귀시키지 않았음을 확인. yona 전체 테스트 스위트
  (6267개)도 재실행 — 14개 실패는 전부 `TemplateHelperSpec`/`GitAuthorizationFilter
  IntegrationSpec`/`DeployKeyGitAuthorizationIntegrationSpec`에서 발생한
  `project_pushed_branch` FK 위반(`DataIntegrityViolationException`)으로, gpgkey/vcs/hg와
  무관하고 공유 테스트 DB(다른 동시 실행 에이전트/세션과 공유되는 컨테이너)의 상태 오염이
  원인으로 보이는 기존 이슈 — 이 작업과 무관해 수정하지 않음.

**실사용 검증(실제 앱 기동, H2 프로필)**: git 검증 때와 동일한 레시피로
`./gradlew bootJar` → `--spring.profiles.active=h2`로 실제 부팅 → `bootstrap-setup`(첫 유저,
재시작 1회) → `hgtester` 계정 회원가입/로그인 → `POST /projectform`으로 `vcs=MERCURIAL`
프로젝트(`hgproj2`) 생성 → 실제 `gpg --batch --generate-key`(EDDSA/ed25519, git 테스트와
동일 알고리즘)로 키 생성 → `POST /user/editform/gpg-keys`로 공개키 등록 → hg4j 자체 API로
직접 서명 커밋 생성(실제 `hg` CLI로는 이 포맷을 재현할 수 없음, 계획대로) →
`hg.push()`(hg4j 포셀린 API, HTTP Basic 인증)로 실제 hg wire protocol을 통해 서버에 push →
렌더링된 `/{owner}/{project}/commits/{branch}` 페이지를 curl로 받아 배지 클래스 확인:

```
$ curl .../hgtester/hgproj2/commits/default | grep -o 'class="label-head gpg-[a-z]*"'
class="label-head gpg-unverified"
class="label-head gpg-verified"
```

- 등록된 키로 서명(author 이메일 일치) → `gpg-verified`(초록 Verified) 배지.
- 등록되지 않은(다른 GNUPGHOME) 키로 서명 → `gpg-unverified`(회색 Unverified) 배지.

둘 다 실제 렌더링된 HTML에서 직접 확인 — Git 쪽 결과와 완전히 동일한 UX.

**개별 커밋 상세 페이지(`/commit/{id}`)는 확인 못 함 — 이유는 P3-19와 무관한 기존 결함**:
`CodeViewController.showCommit()`이 마지막에 `repository.getDiff(commitId)`를 호출하는데,
`HgRepository.getDiff()`는 P3-12 1라운드부터 `throw UnsupportedOperationException()`으로
남아있는 미구현 상태(`getPatch`도 동일) — 예외를 잡아 `fileDiffs == null`이면 무조건
`error/404`로 떨어지는 기존 로직 때문에, GPG 서명 여부와 무관하게 Mercurial 프로젝트의
커밋 상세 페이지 자체가 이미 항상 404였다(직접 `HgRepository.getCommit(id)`를 호출해보면
정상적으로 커밋을 반환함을 별도 확인 — 배지 판정 로직 자체는 문제 없음, 순수히 diff
미구현 때문에 상세 페이지 렌더링까지 못 감). 이 티켓 범위 밖(P3-12 2라운드 과제로 이미
문서화돼 있던 gap)이라 수정하지 않았다 — 커밋 목록/히스토리 페이지(`/commits/{branch}`)에서
배지가 정확히 렌더링됨을 확인했으므로 `Commit.getGpgVerificationStatus()`가 화면에 반영되는
것 자체는 실사용으로 증명됐다.

**기타 발견 사항(수정하지 않음, 범위 밖)**:
1. hg4j `PushCommand`/`HgRemoteClient`가 목적지 URL의 userinfo(`user:pass@host`)를 전혀
   파싱하지 않고 자격증명을 설정할 방법도 포셀린 API에 없다 — 인증이 필요한 저장소로의
   `hg.push()`가 항상 401로 실패한다(`HgRemoteClient.setCredentials()`는 있지만
   `PushCommand`가 호출부에서 쓸 방법이 없음). 실사용 검증에서는 JDK의
   `java.net.Authenticator.setDefault(...)`로 우회했다(hg4j 자체는 건드리지 않음).
2. `Wire1CommandsCoverageTest.changegroupOnAnEmptyRepositoryReturnsAnEmptyStream`이
   이번 변경 전 커밋에서도 동일하게 실패하는 기존 결함으로 확인됨(관련 없음).

**결론**: Git/Mercurial 양쪽 모두 완료. 커밋 목록/히스토리 화면의 Verified/Unverified 배지가
두 VCS에서 동일한 UX로 동작함을 실사용으로 확인했다. hg4j·yona 양쪽 커밋·푸시 완료.
