# P3-19: GPG 커밋 서명 검증(Verified/Unverified 배지)을 Git 실사용 검증 + Mercurial까지 확장

## 배경

P3-03에서 Git 커밋의 GPG 서명 검증(`GpgSignatureVerifier`, `Commit.getGpgVerificationStatus()`,
커밋 목록/상세 화면의 Verified/Unverified 배지)을 TDD로 구현·완료했다고 기록돼 있으나, 실제
브라우저/CLI로 GitHub와 동일하게 동작하는지 사용자가 직접 확인한 적은 없다. 또한 Mercurial
쪽은 커밋 서명 검증 자체가 아직 없다(P3-12 범위에 포함되지 않았음 — Mercurial은 git과
서명 메커니즘 자체가 다르다: 커밋 오브젝트에 서명이 내장되는 git과 달리, Mercurial은
`gpg` 익스텐션이 저장소의 `.hgsigs` 파일에 "리비전 해시 + 서명자 + 서명" 한 줄을 별도로
커밋하는 방식이다).

## 범위

1. **Git**: 이미 구현된 `GpgSignatureVerifier`/Verified·Unverified 배지가 실제로 GitHub와
   동일하게 동작하는지 실사용 검증 — 실제 GPG 키로 서명한 커밋을 push한 뒤 커밋 목록/커밋
   상세 화면에서 배지가 올바르게(서명 있고 검증됨=Verified, 서명 없거나 검증 실패=Unverified)
   뜨는지 브라우저 또는 API 응답으로 직접 확인. 버그가 있으면 이번 티켓에서 수정.
2. **Mercurial**: 커밋 서명 검증 기능 자체가 없으므로 새로 설계·구현해야 한다 — Mercurial의
   `gpg` 익스텐션 방식(`.hgsigs` 파일)을 사용할지, 아니면 yona 자체적으로 다른 방식을 쓸지는
   착수 시 결정 필요(모호하면 GitHub 방식 우선 원칙에 따라, 최종적으로 사용자에게 보여지는
   Verified/Unverified 배지의 UX는 git 쪽과 동일하게 맞출 것). hg4j에 `.hgsigs` 파싱/서명
   검증 지원이 있는지 먼저 확인 필요.

## 완료 기준

- Git: 실제 서명된 커밋 → 커밋 목록/상세 양쪽에 Verified 배지, 서명 없는 커밋 → Unverified
  (또는 배지 없음, GitHub 컨벤션 확인 후 결정) 확인.
- Mercurial: 위와 동일한 사용자 경험을 Mercurial 저장소에서도 재현.

## 완료 로그

### 2026-09-08 — Git 쪽 실사용 검증 완료

기존 `GpgSignatureVerifierSpec`(실제 `gpg`/`git commit -S` 바이너리 + 실제 DB를 쓰는 Spring
통합 테스트, VERIFIED/UNVERIFIED(미등록 키/타인 키/이메일 불일치)/UNSIGNED/키 등록 보안 검증까지
7개 케이스)이 이미 실행돼 전부 통과함을 재확인(`./gradlew test --tests
"...GpgSignatureVerifierSpec" -x jacocoTestReport` → BUILD SUCCESSFUL). 이에 더해 이번 티켓이
요구하는 "브라우저/API로 직접 확인"을 위해 실제로 앱을 기동해(H2 프로필, `bootJar` 산출물,
scratchpad에 격리된 data/git 디렉터리) 다음을 end-to-end로 검증했다:

1. 회원가입(`gpgtester`) → 실제 `gpg --batch --generate-key`로 키 생성 → `/user/editform/gpg-keys`로
   공개키 등록.
2. `git clone`/`git push` (HTTP Basic 인증)로 실제 저장소에 커밋 3개를 만들어 각각 확인:
   - 서명 없는 커밋 → 커밋 목록/상세 양쪽 배지 없음(UNSIGNED, GitHub 컨벤션과 동일).
   - 등록된 키로 서명(author 이메일 일치) → 커밋 목록/상세 양쪽 `Verified`(초록) 배지.
   - 등록되지 않은(다른 GNUPGHOME의) 키로 서명 → 커밋 상세 `Unverified`(회색) 배지.
3. 셋 다 실제 렌더링된 HTML(`code/history.html`, `code/diff.html`)에서 직접 확인 — 버그 없음,
   추가 수정 불필요. Git 쪽 범위는 완료.

### 2026-09-08 — Mercurial 쪽 설계 결정 + hg4j에서 발견한 버그

**설계 조사 결과**: hg4j에 이미 `io.github.search5.hg4j.gpg.GpgSignature`(BouncyCastle 기반 실제
OpenPGP sign/verify)와 `CommitCommand.setGpgSignature()`가 존재했으나, 실제로는 **아무도 호출하지
않는 죽은 코드**였고, 게다가 **버그가 있었다**: `CommitCommand.java`(commit() 메서드, ~926-941줄)가
서명을 `clMeta` 맵에 담아 `changelog.appendRevision(changelogTextBytes, clMeta, ...)`로 넘기는데,
이 오버로드는 내부적으로 `Revlog.wrapMetadata()`를 타서 `"\x01\n key: value \n...\x01\n"` 형태의
블록을 콘텐츠 앞에 붙인다 — 이건 실제 Mercurial의 **filelog rename/copy 메타데이터 포맷**(예:
`hg mv` 추적, LFS 포인터)이지 changelog(커밋) 리비전에는 전혀 해당하지 않는 포맷이다. 이 경로가
실행되면 changelog 리비전의 원문 바이트가 "40자 매니페스트 헥스로 시작"이라는 계약을 깨서
`LogCommand`의 파서(및 실제 `hg` 자신)가 그 커밋을 파싱하다 깨진다 — 즉 지금 이 상태로 쓰면
changelog가 손상된다. (다행히 yona 쪽에서 이 API를 호출하는 곳이 전혀 없어 실사용 피해는 없었음.)

**최종 설계 결정** (티켓의 "모호하면 GitHub 방식 우선" 원칙 적용): 실제 Mercurial의 `gpg`
익스텐션(`.hgsigs` 파일 — 리포지토리에 커밋되는 별도의 버전관리 파일에 "리비전 여러 사람이 각자
서명 추가" 방식으로 기록, "이 커밋 자체에 내장된 서명"이 아니라 "누군가 나중에 이 리비전을
검토·서명했다"는 제3자 attestation 성격)을 따르지 않는다. 대신 git의 `gpgsig` 커밋 헤더와 완전히
동일한 셰이프로, changelog의 **`extra` 딕셔너리**(현재 `branch`/`close`가 이미 쓰는 바로 그 필드 —
날짜 줄에 `\0`로 join되어 붙는 key:value 목록)에 `gpgsig`(armored 서명, git과 동일하게 `\n`→`\\n`
이스케이프)/`gpgfingerprint`를 추가하는 방식을 채택한다. 커밋 작성자 본인이 만든 이 특정 리비전에
내장된 서명이라는 의미가 git과 완전히 동일해지고, 최종 사용자에게 보이는 Verified/Unverified 배지
UX도 git과 100% 동일하게 만들 수 있다 (`.hgsigs` 방식은 "이 정확한 커밋이 검증됐는가"라는 배지
질문 자체와 셰이프가 맞지 않는다 — 별도 파일의 리비전에 따라 달라지고 여러 사람이 각자 다른 시점에
추가할 수 있어 단일 배지로 환원되지 않음).

**Mercurial 실사용 검증 시 유의점(다음 담당자에게)**: 위 결정에 따라 실제 `hg sign`/`.hgsigs`로는
이 배지를 만들 수 없다 — hg4j 자체 API로 서명된 커밋을 만들어야 한다(실제 `hg` CLI로는 재현 불가,
git 때처럼 `git commit -S`를 실제 바이너리로 실행하는 방식이 여기선 안 통함). 실사용 검증은 (1)
hg4j 자체 API/테스트로 서명 커밋 생성 → (2) yona에 실제로 push(HTTP, `vcs=MERCURIAL`) → (3) 커밋
목록/상세 화면 HTML을 직접 curl로 받아 Verified/Unverified 배지 확인, 순서로 진행할 것 (Git 때와
동일한 실사용 검증 스크립트/계정을 재사용 가능 — 이 로그 위에 기록된 절차 참고).
