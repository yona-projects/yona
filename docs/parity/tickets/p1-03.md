# P1-03: OAuth 다중 계정 연동/병합 소실

## 원본 표 정보

- **우선순위 구분**: P1
- **상태(원본 체크박스)**: `[x]`
- **yona 근거**: `models/LinkedAccount.java`
- **yona 대상**: `domain/user/LinkedAccount.kt`(신규), `config/oauth2/CustomOAuth2UserService.kt`
- **비고(원문)**: **완료(의도적 축소, 아래 참고)** — 이메일 일치를 통한 자동 연결까지만 지원, 서로 다른 이메일 계정을 사용자가 수동으로 병합하는 UI는 이식하지 않기로 확정. **2026-08-23 재검증(TASK-0263)**: 이 "UI 미이식"이 실제로 legacy 소스를 건너뛴 것인지 재조사 — `legacy-yona/app/controllers/UserApp.java`/`conf/routes`를 전수 검색한 결과 계정 병합 관련 컨트롤러/라우트가 **0건**, `app/views/`에도 병합 화면 템플릿이 **0건**임을 확인했다. 실제 병합 로직(`YonaUserServicePlugin.merge()`)은 서드파티 `play-authenticate` 라이브러리가 자기 SPI 콜백으로 호출하는 것이고, 그 확인 화면도 라이브러리 자체가 번들로 제공하는 뷰(legacy-yona 저장소 밖, JAR 안)라 애초에 포팅할 legacy-yona 소스 자체가 존재하지 않는다 — 이 프로젝트 전체를 관통하는 "legacy 원본을 그대로 옮긴다" 원칙을 적용할 대상이 없는 유일한 사례. yona는 Spring Security OAuth2로 아키텍처 자체가 다르므로 화면을 새로 지어 넣는 것은 반대로 "yona식 독자 구현" 금지 원칙에 위배된다 — 그대로 미이식 유지가 맞는 판단임을 재확인

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-19 — P1-03**: `CustomOAuth2UserService`가 소셜 로그인마다 이메일/loginId로만 매칭해, 서로 다른 provider(예: Google, GitHub)로 로그인하면 provider 연결 이력이 전혀 남지 않던 문제 해결. yona의 `UserCredential`(play-authenticate 플러그인 산물, `active`/`emailValidated` 등 프레임워크 종속 필드 포함)은 이식하지 않고, 핵심 기능만 `LinkedAccount`(User ↔ provider+providerUserId) 엔티티로 단순화해 이식.
  - 로그인 시 (1) `LinkedAccount`로 이미 연결된 provider면 그 계정으로 즉시 로그인, (2) 처음 보는 provider면 이메일/loginId로 기존 계정을 찾아 자동으로 `LinkedAccount`를 만들어 연결(사실상 자동 병합), (3) 기존 계정도 없으면 신규 가입 + 연결.
  - **의도적 축소(확정, 후속 없음)**: 이메일이 서로 다른 두 계정을 사용자가 수동으로 병합하는 UI(yona의 `UserCredential.merge()`에 해당)는 이식하지 않음 — 이메일 일치를 통한 자동 연결까지만 지원.
  - 테스트: `CustomOAuth2UserServiceSpec.kt` 기존 1건 + 신규 2건(이미 연결된 계정 재로그인, 이메일 일치로 새 provider 자동 연결) = 3 tests 전체 통과. 커버리지 INSTRUCTION 92%(151/164).
