# P1-144: **(2026-08-21 [[tickets/p2-27|P2-27]] 조사 중 발견)** 같은 소유자를 유지한 채 프로젝트 이름만 바꾸는 "개명" 기능이 yona에 아예 없음 — yona `ProjectApp.settingProject()`는 설정 폼에서 `project.name` 변경을 감지하면(`!project.name.equals(updatedProject.name)`) 저장소를 rename하고 `project.update()`로 이름만 바꾸는데(소유자는 그대로), yona `ProjectServiceImpl.updateProject()`가 받는 `UpdateProjectParam`/REST `UpdateProjectRequest`엔 애초에 `name`/`title` 필드 자체가 없다. yona에서 프로젝트 이름이 바뀌는 유일한 경로는 소유권 이전(`acceptTransfer`, 목적지 유저가 필요)뿐이라, "이름만 바꾸고 싶은" 사용자가 쓸 방법이 없다

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-22 — P1-144**: 같은 소유자를 유지한 채 프로젝트 이름만 바꾸는 "개명" 경로 자체가 yona에 없던 문제 해결 — yona `ProjectApp.settingProject()`의 개명 분기(`validateWhenUpdate()`의 `projectNameChangeable()` 중복 검사 → `recordRenameOrTransferHistoryIfLastChangePassed24HoursFrom()` → `repository.renameTo()` → `FavoriteProject.updateFavoriteProject()`)를 그대로 이식.
  - `ProjectRepository`에 `existsByOwnerIgnoreCaseAndNameIgnoreCaseAndIdNot(owner, name, id)` 추가 — legacy `.ieq("name",...).ieq("owner",...).ne("id", id)`와 동일하게 대소문자 무시 + 본인 제외 비교.
  - `UpdateProjectParam`/`UpdateProjectRequest`에 `name: String? = null` 추가(값이 없거나 현재 이름과 같으면 무시). `ProjectServiceImpl.updateProject()` 최상단에서 이름이 바뀌는 경우에만: 중복이면 `IllegalArgumentException`(다른 필드 변경 전 즉시 실패, legacy가 폼 검증 실패 시 아무 것도 반영 안 하는 것과 동일) → 기존에 [[tickets/p1-76|P1-76]]으로 이미 이식돼 있던 `recordRenameOrTransferHistoryIfLastChangePassed24HoursFrom()`을 그대로 재사용(신규 로직 아님) → 이미 존재하던 `PlayRepository.renameTo()`(`GitRepository`/`SvnRepository` 양쪽에 구현돼 있던, 지금까지 아무도 호출하지 않던 코드)를 호출해 실패 시 `IllegalStateException` → 성공하면 `project.name` 갱신 후 이 프로젝트를 즐겨찾기한 사용자들의 `owner`/`projectName`을 동기화(`acceptTransfer()`가 이미 쓰던 것과 동일한 `favoriteProjectRepository` 패턴 재사용).
  - **아키텍처 차이로 이식하지 않은 부분(의도적 축약이 아님, 근거 명시)**: legacy `User.updateFavoriteProject()`(Ebean 캐시된 연관관계를 `.refresh()`로 재조회)는 요청 스코프 트랜잭션 안에서 항상 최신 상태를 읽는 JPA/Hibernate에는 대응하는 캐시 무효화 문제 자체가 없어 이식 대상에서 제외 — 실질적으로 상태를 바꾸는 쪽은 `FavoriteProject.updateFavoriteProject()`(정적 메서드) 하나뿐이고 그건 이미 이식했음.
  - `ProjectController.updateProject()`는 `try/catch`로 `IllegalArgumentException`(400)/`IllegalStateException`(500)을 매핑 — 이 컨트롤러의 다른 엔드포인트(`requestTransfer` 등)가 이미 쓰던 것과 동일한 패턴.
  - UI는 사용자 지시에 따라 이번 범위에 포함하지 않음(REST API 필드만 우선 이식) — `UpdateProjectRequest.name`은 화면이 붙기 전까지는 클라이언트가 안 보내면 그냥 무시된다.
  - 테스트(TDD, 레드 확인 후 그린): `ProjectServiceImplSpec.kt`에 `describe("ProjectServiceImpl.updateProject - 개명 (P1-144)")` 신규 5 tests(이름 미변경 시 rename 미호출/같은 소유자 내 이름 중복 시 예외+무변경/저장소 rename 실패 시 예외+무변경/정상 개명 시 저장소·이력·즐겨찾기 동시 갱신/24시간 이내 재개명 시 previousName 보존). `ProjectControllerSpec.kt` +2(name 필드 전달 확인/중복 시 400).
