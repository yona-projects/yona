## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-91~95**: 2026-08-20 [[tickets/p2-15|P2-15]] 확정 조사에서 발견됐던 5건의 "매니저 전용으로 과잉 제한" 버그를 모두 [[tickets/p1-85|P1-85]] 1b의 리소스 타입별 `isAllowed(...)`/`isProjectResourceCreatable(...)` 오버로드로 교체해 legacy와 동일하게(프로젝트 멤버 전원 허용) 바로잡았다. 각 컨트롤러의 이제 아무 데서도 쓰이지 않는 사설 `isManagerOrAuthor`/`isManagerOrContributor`(단, PullRequestController는 다른 3곳에서 여전히 사용 중이라 유지)/`isAuthorOrManager`/`isProjectManager` 헬퍼는 삭제하고, 그로 인해 불필요해진 `RoleType`/`ProjectUserRepository` import도 함께 정리했다.
  - **P1-91** `BoardController`: `isManagerOrAuthor(project, posting.authorId, user)` 3곳(`updatePosting`/`updatePostLabels`=UPDATE, `deletePosting`=DELETE) → `accessControl.isAllowed(user, project, posting, Operation.UPDATE/DELETE)`.
  - **[[tickets/p1-92|P1-92]]** `PullRequestController`: `updatePullRequest`의 `isManagerOrContributor(...)` 단독 호출 1곳만 → `accessControl.isAllowed(user, project, pullRequest, Operation.UPDATE)`로 교체(나머지 3곳은 이미 `isManagerOrContributor(...) || checkWritePermission(...)`으로 사실상 멤버 전원을 이미 허용하고 있어 정상이었으므로 그대로 둠). 이 교체로 "비멤버 컨트리뷰터가 수정 가능했던" 반대방향 느슨함도 함께 해소(중앙 함수는 컨트리뷰터 여부와 무관하게 멤버십만 봄 — legacy도 PULL_REQUEST를 author 바이패스 대상에 넣지 않으므로 동일).
  - **[[tickets/p1-93|P1-93]]** `CodeHistoryController`: `deleteComment`의 `isAuthorOrManager(...)` → `accessControl.isAllowed(user, project, comment, Operation.DELETE)`.
  - **[[tickets/p1-94|P1-94]]** `IssueLabelController`: Serena LSP로 legacy `IssueLabelApp.java`를 직접 대조해 7곳을 두 그룹으로 정확히 분리 — 생성 3곳(`createLabel`/`createCategory`/`copyLabels`, legacy `@IsCreatable`) → `accessControl.isProjectResourceCreatable(user, project, ResourceType.ISSUE_LABEL[_CATEGORY])`, 수정·삭제 4곳(`updateLabel`/`updateCategory`/`deleteLabel`/`deleteCategory`, legacy `@IsAllowed(UPDATE/DELETE, ...)`) → `accessControl.isAllowed(user, project, ResourceType.ISSUE_LABEL[_CATEGORY], Operation.UPDATE/DELETE)`(엔티티가 아니라 리소스 타입만으로 판단하는 범용 오버로드 사용 — 이 두 타입엔 작성자 개념이 없음).
  - **[[tickets/p1-95|P1-95]]** `MilestoneController`: 마찬가지로 legacy 대조 결과 생성(`createMilestone`, `@IsCreatable`) → `isProjectResourceCreatable(user, project, ResourceType.MILESTONE)`, 수정/삭제(`updateMilestone`/`deleteMilestone`, `@IsAllowed(UPDATE/DELETE, MILESTONE)`) → `isAllowed(user, project, milestone, Operation.UPDATE/DELETE)`. 이 항목이 원래 권장했던 기존 `isAllowedToUpdateMilestone()` 재사용 대신 새 함수를 쓴 이유: 그 헬퍼는 `isAllowedIfGroupMember` 분기가 빠져 있어(legacy UPDATE는 `isMemberOf || isAllowedIfGroupMember`) 새로 이식한 오버로드보다 덜 정확했다.
  - **테스트에서 발견한 기존 fixture의 잘못된 전제**: 5개 스펙 파일에 "일반 멤버(또는 비관리자)가 시도하면 403"이라는, 이제는 틀린 전제의 테스트가 있었다 — 실제로는 프로젝트 멤버라면 매니저가 아니어도 항상 허용돼야 한다. 이런 테스트들은 "멤버가 성공한다"는 기대값으로 고치고, 진짜 403 케이스(프로젝트 비멤버)를 별도로 추가했다(BoardControllerSpec/PullRequestControllerSpec/CodeHistoryControllerSpec/IssueLabelControllerSpec(3곳)/MilestoneControllerSpec).
