# P1-104: **(2026-08-21 검증규칙 전수 대조에서 발견)** 로그인ID 형식 검증(정규식)이 전혀 없음 — 원본은 `@Pattern`으로 허용 문자(영문/숫자/한글/하이픈, `_`/`.` 구분자)를 강제하는데 yona는 중복 여부와 예약어만 체크해 공백·슬래시 등 임의 문자가 포함된 로그인ID도 가입이 통과될 수 있음(URL 라우팅과 충돌 소지)

- **우선순위 구분**: P1
- **상태(원본 체크박스)**: `[x]`

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P1-104**: 회원가입 로그인ID 형식(정규식) 검증 신규 이식.
  - Serena LSP로 yona `models/User.java:65-66,80`을 재확인 — `LOGIN_ID_PATTERN = "[a-zA-Z0-9가-힣-]+([_.][a-z_.A-Z0-9가-힣-]+)*"`가 `@Pattern`으로 `loginId` 필드에 걸려 있고, `UserApp.java:377-404 newUser()`에서 Play의 폼 바인딩이 이 애노테이션을 자동 검증한 뒤(스캔 순서상 가장 먼저) `validate()`의 수동 중복/예약어 체크와 합쳐져 한 번의 400 응답으로 반환됨을 확인. 별도 로그인ID 변경 엔드포인트는 존재하지 않음(가입 시 1회만 검증).
  - `domain/user/LoginIdFormatValidator.kt` 신규 — 기존 `ReservedWordsValidator`([[tickets/p2-01|P2-01]])와 동일한 "컨트롤러가 명시적으로 호출하는 유틸 object" 컨벤션을 따름(이 코드베이스는 엔티티에 Bean Validation 애노테이션을 걸지 않는 컨벤션이라, `@Valid`/`@Pattern` 도입 대신 기존 패턴에 맞춤). 정규식은 yona 문자열과 문자 클래스가 완전히 동일(순서만 다름, 기능적으로 동치).
  - `AuthController.kt signup()`에 `ReservedWordsValidator` 체크와 같은 위치·스타일로 `LoginIdFormatValidator.isValid()` 실패 시 `bindingResult.rejectValue("loginId", "pattern", ...)` 추가 — 중복/예약어 체크와 마찬가지로 즉시 return하지 않고 누적, 마지막 `hasErrors()`에서 한 번에 걸러져 yona의 "폼 바인딩 애노테이션 오류 + 수동 검증 오류가 한 응답에 함께 반환" 동작과 동일하게 재현.
  - **범위 밖 발견 사항(착수 안 함)**: yona `Organization.java:42`도 조직명에 동일한 `LOGIN_ID_PATTERN`을 재사용하는데, yona `OrganizationServiceImpl.createOrganization`에는 이 형식 검증이 없음(예약어 체크만 있음) — 이번 항목은 "로그인ID"로 좁게 등록돼 있어 조직명 쪽은 범위 밖으로 남기고 사용자 지시로 [[tickets/p1-108|P1-108]]로 정식 등록.
  - 테스트: `LoginIdFormatValidatorSpec.kt` 신규 9건(영문/숫자/한글/하이픈/구분자 허용, 공백·슬래시·특수문자·구분자로 시작하는 경우·빈 문자열 거부), `AuthControllerSpec.kt` +2(공백 포함 아이디 거부, 올바른 형식은 정상 가입).
  - 검증: `./gradlew test --tests "...LoginIdFormatValidatorSpec" --tests "...AuthControllerSpec"` 전체 통과, 이어서 `./gradlew test` 전체 1005 tests 통과(회귀 없음 확인).
