# P3-24: hg4j `GpgSignature`가 RSA 키로 하드코딩돼 있어 다른 알고리즘 서명을 검증 못 함

## 배경

`hg4j/src/main/java/io/github/search5/hg4j/gpg/GpgSignature.java`의 `sign()`/`verify()`가
`PGPPublicKey.RSA_GENERAL`을 하드코딩하고 있다(`JcaPGPKeyConverter.getPGPPublicKey(...)`
호출 3곳 전부). 실제로는 EdDSA/Ed25519, ECDSA 등 다른 알고리즘 키로는 이 클래스로
서명/검증이 아예 안 된다(RSA 공개키로 강제 변환을 시도해 실패하거나 잘못된 결과를 낸다).

yona 쪽 실제 GPG 배지 판정 로직(`GpgSignatureVerifier.kt`)은 이 클래스를 쓰지 않고
BouncyCastle의 `PGPSignature`/`PGPPublicKey`를 직접 다뤄 알고리즘 무관하게 동작하므로
프로덕션 경로에는 영향이 없었지만, `GpgSignature`는 hg4j의 공개 API이고 다른 소비자(hg4j를
직접 쓰는 코드, 향후 기능)가 이 클래스로 서명하면 조용히 RSA로만 동작한다고 착각할 수 있는
잠재적 결함이다 — 사용자 지시로 실사용 영향 여부와 무관하게 근본적으로 고친다.

## 범위

1. `sign()`: `PrivateKey`/대응 `PublicKey`의 실제 알고리즘(`getAlgorithm()` — "RSA"/"EC"/
   "Ed25519"/"Ed448"/"EdDSA" 등)을 판별해 그에 맞는 `PublicKeyAlgorithmTags` 상수를 골라
   `JcaPGPKeyConverter.getPGPPublicKey(...)`에 넘긴다. RSA 공개키를 개인키에서 역산하는
   기존 로직(모듈러스+고정 지수 65537)은 RSA 전용이므로, 다른 알고리즘에서는 이 방식 자체가
   성립하지 않는다 — 애초에 서명 대상 공개키를 인자로 받도록 API를 바꾸는 게 정확한 해법일
   가능성이 높다(호출부 확인 후 결정, 하위 호환이 꼭 필요하면 오버로드 추가).
2. `verify()`: 마찬가지로 `publicKey.getAlgorithm()`을 보고 알고리즘 태그를 정확히 선택.
3. RSA/EC(P-256 등)/Ed25519 최소 3개 알고리즘으로 실제 sign→verify 왕복 테스트 추가(real
   BouncyCastle 키 생성, 실제 서명/검증 성공 확인 + 변조 데이터/다른 키 실패 확인 — 기존
   `GpgSignatureTest`의 RSA 케이스와 동일한 엄격도).
4. hg4j 전체 테스트 스위트 재실행해 회귀 없는지 확인.

## 완료 기준

- RSA/EC/Ed25519 세 알고리즘 모두 실제 서명·검증 왕복이 성공한다.
- 기존 RSA 기반 테스트(`GpgSignatureTest`, `CommitCommandTest`)가 계속 GREEN.

## 완료 로그

(2026-09-09) 착수 및 완료. 커밋: `hg4j@1f209ea` ("fix: GpgSignature가 RSA 키를 하드코딩해
EC/Ed25519 서명·검증을 못 하던 버그 수정"), `origin/main`에 push 완료.

**최종 설계**

- `hg4j`의 `PublicKeyAlgorithmTags` 상수는 BouncyCastle `bcpg-jdk18on:1.78` 기준
  `RSA_GENERAL=1`, `ECDSA=19`, `EDDSA_LEGACY=22`, `Ed25519=27`, `Ed448=28`.
  `JcaPGPKeyConverter.getPGPPublicKey(int algorithm, PublicKey, Date)`는 넘긴 `algorithm`
  값과 실제 `PublicKey`(RSA/EC/`EdECKey`)의 실제 타입이 맞아야 올바른 `BCPGKey`를 만든다는 걸
  BouncyCastle 소스(`getPublicBCPGKey`, `OperatorHelper.createSignature`)로 직접 확인했다.
  특히 EdDSA는 declared hash algorithm과 무관하게 항상 순수 `"Ed25519"`/`"Ed448"` JCA
  `Signature`를 쓴다는 것도 확인(해시 알고리즘 태그는 서명 패킷 메타데이터에만 기록됨).
- `resolvePgpAlgorithmTag(PublicKey)` private 헬퍼를 추가: `getAlgorithm()`이 "RSA"→
  `RSA_GENERAL`, "EC"/"ECDSA"→`ECDSA`. JDK 15+ `KeyPairGenerator.getInstance("Ed25519"/"Ed448")`로
  만든 키는 `getAlgorithm()`이 뭉뚱그려 `"EdDSA"`를 반환하므로(실측 확인, JDK 17), 이 경우
  `java.security.interfaces.EdECKey#getParams().getName()`으로 커브명("Ed25519"/"Ed448")을
  구분해 정확한 태그를 고른다. 그 외 알고리즘은 `GeneralSecurityException`을 던진다.
- `verify(byte[], PublicKey)`: `RSA_GENERAL` 하드코딩을 제거하고 `resolvePgpAlgorithmTag(publicKey)`
  결과를 사용하도록 수정 — 이제 알고리즘 무관하게 동작.
- `sign()`은 **오버로드를 추가하는 방식**을 채택했다(공개키를 함께 받는 새 시그니처가
  "더 정확한 해법"이라는 티켓의 판단을 따름):
  - 기존 `sign(byte[], PrivateKey, String)` 3-인자 시그니처는 하위 호환을 위해 **그대로 유지**
    (RSA 개인키 모듈러스+F4 지수 역산 트릭 그대로, RSA 아니면 기존과 동일하게
    `GeneralSecurityException` 발생). `grep -rn "GpgSignature.sign"` 확인 결과 호출부
    (`GpgSignatureTest`, `GpgSignatureCoverageTest`)가 전부 3-인자 시그니처와 `toAsciiArmored()`만
    사용하고 있어 시그니처 변경이 아닌 오버로드 추가가 안전한 선택이었다.
  - 신규 `sign(byte[] contentToSign, PrivateKey privateKey, PublicKey publicKey, String fingerprint)`를
    추가: `resolvePgpAlgorithmTag(publicKey)`로 고른 태그를 `JcaPGPKeyConverter.getPGPPublicKey(...)`와
    `JcaPGPContentSignerBuilder(...)` 양쪽에 넘겨 RSA/EC/Ed25519/Ed448 전부를 실제로 지원한다.

**테스트 결과**

- `GpgSignatureTest`에 `@ParameterizedTest(strings={"RSA","EC","Ed25519"})`로
  `testSignAndVerifyRoundTripAcrossAlgorithms` 추가 — 신규 4-인자 `sign()` 오버로드로 실제
  BouncyCastle/JDK 키 생성 후 서명→검증 성공 + 변조 데이터 검증 실패 + 다른 키 검증 실패까지
  기존 RSA 케이스와 동일한 엄격도로 검증. EC는 `KeyPairGenerator.getInstance("EC")` +
  `ECGenParameterSpec("secp256r1")`, Ed25519는 `KeyPairGenerator.getInstance("Ed25519")`(JDK 17
  표준 지원) 사용.
- `./gradlew test --tests "io.github.search5.hg4j.gpg.GpgSignatureTest" -x jacocoTestReport` → GREEN
  (신규 파라미터라이즈드 테스트 3케이스 포함 전부 통과).
- `./gradlew test --tests "io.github.search5.hg4j.gpg.*" -x jacocoTestReport` → GREEN
  (`GpgSignatureCoverageTest`의 기존 부정 케이스도 회귀 없이 통과 — 특히
  `testSignWithNonRsaPrivateKeyThrowsGeneralSecurityException`(DSA 3-인자 호출 시 예외)과
  `testVerifyWithUnsupportedPublicKeyAlgorithmThrows`(RSA로 서명한 걸 EC 공개키로 검증 시 예외)
  둘 다 verify()가 알고리즘을 정확히 고르게 된 후에도 여전히 `GeneralSecurityException`을
  던진다는 걸 BouncyCastle `PGPSignature.init()`/`JcaPGPContentVerifierBuilderProvider` 소스로
  사전 확인하고 실제로도 GREEN임을 검증).
- `./gradlew test -x jacocoTestReport` (전체 스위트, 2309 테스트) → `BUILD SUCCESSFUL`, 실패/에러
  0건 (테스트 결과 XML 전수 확인). 다른 세션이 동시에 `Wire1CommandsCoverageTest.java`를 수정
  중이었고 그 변경 덕분인지 이번 실행에서는 언급된 flaky 케이스도 통과했다 — 이 파일은 스코프
  규율에 따라 건드리지 않았다.

**발견했지만 손대지 않은 것**

- 작업 중 `hg4j` 워킹트리에 `.project`(untracked)와 `Wire1CommandsCoverageTest.java`(수정됨)가
  이미 존재/변경되어 있었다 — 다른 세션/에이전트의 동시 작업으로 추정, 스코프 규율에 따라
  전혀 건드리지 않고 커밋 스테이징에서도 제외했다.
- `GpgSignatureCoverageTest.testVerifyWithUnsupportedPublicKeyAlgorithmThrows`의 주석은 여전히
  "internal converter.getPGPPublicKey(RSA_GENERAL, ecKey, ...) call cannot reconcile..."라고
  옛 구현을 설명하는데, 수정 후에는 실패 지점이 `getPGPPublicKey` 호출이 아니라 그 뒤
  `signature.init()`에서 `Signature.getInstance("SHA256withRSA").initVerify(ecPublicKey)`가
  `InvalidKeyException`을 던지는 지점으로 바뀌었다(여전히 `GeneralSecurityException`으로 감싸져
  테스트 자체는 그대로 통과). 스코프 규율(`GpgSignature.java`와 그 테스트 파일 외 불가침, 또한
  이 코멘트 수정이 필수는 아님)에 따라 손대지 않았다 — 필요하면 별도 후속 정리로 처리.
