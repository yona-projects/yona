# P3-62: "내 이슈"(cross-project, `/user/issues`) 화면에 마일스톤 필터 자체가 없음(legacy에는
`milestoneId` 파라미터 지원 + 진행률 카드가 있었음)

## 배경

legacy `app/views/issue/my_partial_search.scala.html`은 `param.milestoneId`가 설정돼 있으면
(대시보드/특정 마일스톤 화면 등에서 링크로 넘어온 경우) 좌측 사이드바에 진행률 카드를 보여준다:

```scala
// legacy-yona/app/views/issue/my_partial_search.scala.html:47-54
@if(param.milestoneId != null){
    @defining(Milestone.findById(param.milestoneId)){ milestone =>
        @if(milestone != null){
            <hr>
            @views.html.milestone.partial_status(milestone, project)
        }
    }
}
```

단, legacy도 이 화면 자체에 마일스톤 선택용 `<select>` 드롭다운을 직접 그리지는 않는다 —
`my_partial_list_quicksearch.scala.html`(좌측 퀵링크: 내게 할당됨/내가 작성함/내가 댓글단/
멘션됨/공유받음/즐겨찾기)의 각 링크가 `data-milestone-id="@param.milestoneId"`로 **현재
선택된 마일스톤을 유지**만 할 뿐, 마일스톤을 새로 고르는 UI는 없다. 즉 legacy에서
`milestoneId`는 URL 쿼리 파라미터로 진입(예: 특정 마일스톤 상세 화면에서 "내 이슈 보기" 같은
링크, 또는 사용자가 직접 URL을 조작하는 경우)했을 때만 의미가 있고, 그 경우에도 진행률 카드는
정확히 표시된다.

## 현재 yona 상태 (격차 확정)

- `src/main/kotlin/com/github/yonaprojects/yona/web/UserViewController.kt`의 `userIssues()`
  (`GET /user/issues`, legacy `IssueApp.userIssues()` 대응)는 `milestoneId` 관련
  `@RequestParam`이 아예 없다(grep 결과 0건) — URL에 `?milestoneId=...`를 붙여도 컨트롤러가
  읽지도, 필터링에 쓰지도 않는다.
- `src/main/resources/templates/issue/my_partial_search.html`에도 `milestone` 관련 마크업이
  전혀 없다(grep 결과 0건) — 진행률 카드는커녕 `milestoneId`를 유지하는 `data-milestone-id`
  속성조차 없다.
- `IssueRepository`의 이 화면 전용 조회 메서드들(`findByAssigneeAndState`,
  `findByAuthorIdAndState`, `findCommentedByState`, `findMentionedByState`,
  `findFavoriteByState`, `findSharedByState`, `findByState`)은 전부 프로젝트 단일 쿼리
  구조라 마일스톤 조건을 끼워 넣으려면 각 메서드(또는 대응하는 Specification)를 확장해야
  한다 — 이슈 목록(`issue/list.html`)이 `IssueSpecification.filterIssues(...)`(단일 프로젝트
  스코프)로 이미 `milestoneId`를 처리하는 것과 달리, 이 화면은 애초에 프로젝트가 여러 개일 수
  있어(cross-project) `milestone.project`가 이슈마다 다를 수 있다는 점까지 고려해야 한다.

## 참고: P3-61과의 관계

P3-61은 legacy `issue/partial_searchform.scala.html`(프로젝트 범위 `issue/list.html`)의
마일스톤 진행률 카드 누락만 다뤘고, 완료 처리됐다. 이 티켓은 P3-61 작업 중 "내 이슈 화면도
같이 배선하라"는 원 지시를 이행하려다 발견한 것으로, 코디네이터가 "카드 배선"이 아니라
"마일스톤 필터 신규 기능(파라미터+리포지토리 쿼리+최소한의 UI 또는 URL 파라미터 지원) 구현"에
해당한다고 판단해 분리했다.

## 제안

1. `UserViewController.userIssues()`에 `milestoneId: Long?` 파라미터를 추가하고, 선택 시
   이슈 목록을 그 마일스톤으로 추가 필터링한다(cross-project이므로 `Milestone` 엔티티 자체는
   프로젝트 무관하게 `milestoneId`로 조회 가능 — `MilestoneRepository.findById`).
2. 기존 6개 조회 메서드(assignee/author/commenter/mention/favorite/sharer + 기본)에 milestone
   조건을 추가하는 방법 결정 필요(각 메서드에 오버로드 추가 vs `Specification` 기반으로
   리팩터링) — 여러 유효한 설계가 있어 착수 시 확인 필요.
3. `issue/my_partial_search.html`에 legacy와 동일하게 `milestoneId`가 있을 때
   `milestone/partial_status :: status(milestone, project)`(이때 `project`는 `milestone.project`)
   카드를 보여준다.
4. legacy 자체에도 이 화면엔 마일스톤 선택 `<select>`가 없었다는 점을 그대로 유지할지, 아니면
   yona에서 사용성 개선 차원에서 드롭다운을 새로 추가할지는 legacy 동치성 원칙상 별도 확인/승인
   필요(작업 원칙: legacy와 다르게 갈 경우 반드시 먼저 확인).
5. TDD로 "milestoneId로 필터링하면 내 이슈 목록도 그 마일스톤 이슈만 보이고 진행률 카드가
   보인다" 회귀 스펙을 먼저 세울 것.

## 해결 (2026-09-12)

착수 전 재확인한 결과, "제안" 1번 항목(이슈 목록 자체를 마일스톤으로 필터링한다)은 틀린
전제였다 — legacy `IssueApp.userIssues()`가 실제로 호출하는 `SearchCondition
.asExpressionList()`(프로젝트 파라미터 없는 버전, `SearchCondition.java:251-275`)는
`milestoneId`를 전혀 참조하지 않는다. milestoneId로 쿼리를 필터링하는 코드(`el.eq
("milestone.id", milestoneId)`)는 프로젝트 범위 버전(`asExpressionList(Project project)`,
369행 이하)에만 있고, 이건 P3-61이 이미 배선한 `issue/list.html` 쪽 경로다. 즉 legacy에서
`milestoneId`는 이 화면의 이슈 목록을 전혀 걸러내지 않고, 오직 진행률 카드 표시 여부만
결정한다.

이에 따라 실제 구현 범위는 원래 제안보다 훨씬 작아졌다(리포지토리 변경 없음):

1. `UserViewController.userIssues()`(`GET /user/issues`)에 `milestoneId: Long?`
   `@RequestParam`을 추가.
2. `milestoneId`가 유효하면 `milestoneRepository.findById(milestoneId).orElse(null)`로
   조회해 `selectedMilestone` 모델 속성으로 노출(legacy `Milestone.findById`와 동치 —
   존재하지 않는 id는 카드 미표시).
3. `issue/my_partial_search.html`에 `selectedMilestone != null`일 때
   `milestone/partial_status :: status(selectedMilestone, selectedMilestone.project)`
   카드를 배선(cross-project라 `project` 모델 변수가 없으므로 `milestone.project`를 사용).
4. 기존 hidden 검색폼 필드들과 같은 패턴으로 `milestoneId`도 hidden input에 추가해 필터/정렬
   변경 시 값을 유지.
5. 마일스톤 선택 드롭다운은 만들지 않음(legacy도 이 화면엔 없었음 — 아래 "향후 개선 방안"
   참고).

TDD로 구현(`UserIssuesMilestoneProgressCardTemplateRenderingSpec.kt` 신규 — milestoneId
없음/유효/존재하지 않음 3가지 케이스 검증) 후 전체 회귀(6,638건, 실패 0) 확인, Playwright로
실제 브라우저 동작까지 검증(`/user/issues?milestoneId=<id>`로 진입 시 `.milestone-info`
카드가 정상 표시됨을 스크린샷으로 확인).

## 향후 개선 방안 (착수 안 함 — 사용자 결정 대기)

legacy도 이 화면엔 마일스톤을 새로 선택하는 `<select>` UI가 없었고(URL 파라미터로만 진입),
이번 구현도 legacy 동치성 원칙에 따라 그대로 유지했다. 다만 GitHub 등 다른 이슈 트래커의
관례를 따르면, "내 이슈" 화면에도 `issue/list.html`(프로젝트 범위)과 동일한 마일스톤 선택
드롭다운을 추가해 URL을 직접 조작하지 않고도 마일스톤 필터를 고를 수 있게 하는 편이 사용성이
낫다. 이 경우 6개 조회 메서드(assignee/author/commenter/mention/favorite/sharer) 전부에
milestone 조건을 추가해야 하는데, 이 메서드들이 전부 네이티브 SQL(`@Query(nativeQuery
= true)`)이라 각 쿼리에 `AND (:milestoneId IS NULL OR ...)` 조건을 개별 추가하는 오버로드
방식이 적합해 보인다(Specification 리팩터는 네이티브 쿼리를 전부 JPA Criteria로 새로
작성해야 하고 기존 MockK 기반 테스트도 대부분 다시 써야 해서 범위 대비 리스크가 크다).

실제 구현(1번안, legacy와 동일 - 드롭다운 없음)과 드롭다운을 추가한 모습(2번안, 목업)을
Playwright로 각각 스크린샷 떠서 비교 확인함(코드에는 반영하지 않은 순수 시각적 목업).
드롭다운 추가 여부는 사용자 결정이 필요해 보류 상태로 남긴다.
