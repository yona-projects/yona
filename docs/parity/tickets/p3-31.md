# P3-31: 로컬 로그인 시 비밀번호가 틀리면 정상 오류 대신 500이 나던 회귀 수정

## 배경

P3-30(순환참조/비밀번호 노출 수정) 실사용 검증을 위해 격리된 H2 인스턴스에 관리자 계정을 만들고
`/users/login`으로 로그인을 시도하던 중 발견. 올바른 비밀번호로는 우연히 성공해버려 드러나지
않고, **틀린 비밀번호로 로그인을 시도할 때만** 500 에러가 재현됐다:

```
java.lang.IllegalArgumentException: Given that there is no default password encoder
configured, each password must have a password encoding prefix. ...
	at org.springframework.security.crypto.password.DelegatingPasswordEncoder$UnmappedIdPasswordEncoder.matchesNonNull
	at org.springframework.security.authentication.dao.DaoAuthenticationProvider.additionalAuthenticationChecks
```

## 근본 원인

`SecurityConfig.kt`의 캐치올 체인(@Order 4)은 `.authenticationProvider(deployKeyAuthenticationProvider)
.authenticationProvider(yonaAuthenticationProvider)`로 두 provider만 명시 등록해뒀지만(P3-03에서
YonaAuthenticationProvider가 자동수집 비활성화로 통째로 빠지는 회귀를 겪은 뒤 도입한 대응),
이 호출은 `@Bean securityFilterChain()` 메서드가 **실행되는 시점**에 전역(global)
`AuthenticationManagerBuilder`에 provider를 추가하는 것이라, 그 실행 시점이 다른
`@Bean SecurityFilterChain`(`AuthorizationServerConfig` @Order1 등, Spring의 빈 생성 순서에 달려
있어 보장되지 않음)보다 늦으면 문제가 생긴다: 다른 체인이 먼저 전역 빌더에 접근하면서 Spring
Security의 `InitializeUserDetailsBeanManagerConfigurer`(별개의 자동설정기, 항상 늦게 돎)가
"`UserDetailsService` 빈 하나 + `PasswordEncoder` 빈 하나가 있으니" `DaoAuthenticationProvider`를
몰래 끼워 넣어버린다 — 여기서 재사용된 `PasswordEncoder` 빈은 `AuthorizationServerConfig`가
OAuth2 confidential client secret 검증 전용으로 노출한 것으로, yona의 로컬 로그인 비밀번호
해시 방식(SHA-256+salt 반복 해시, 프리픽스 없음)과는 전혀 다른 계약이다.

그 결과 ProviderManager 목록이 `[DaoAuthenticationProvider, deployKey, yona]` 순이 되고,
로컬 로그인 시 비밀번호가 틀리면 `YonaAuthenticationProvider`가 정상적으로
`BadCredentialsException`을 던지는데, `ProviderManager`는 이를 삼키고 **다음 provider인
`DaoAuthenticationProvider`로 계속 진행**한다(표준 동작 — 여러 provider에게 기회를 준다).
`DaoAuthenticationProvider`는 프리픽스 없는 해시를 `DelegatingPasswordEncoder`로 비교하려다
`IllegalArgumentException`을 던지는데, 이건 `AuthenticationException`이 아니라서
`ProviderManager`가 잡지 못하고 그대로 전파돼 500이 된다.

## 수정

Spring Security가 공식적으로 보장하는 훅을 사용 — 아무 `@Configuration` 빈에나 있는
`@Autowired fun xxx(auth: AuthenticationManagerBuilder)` 형태의 메서드는, 전역 빌더를
자동으로 스캔하는 `Initialize*BeanManagerConfigurer`들(둘 다 항상 가장 낮은 우선순위로 맨
나중에 돎)보다 **항상, 결정적으로 먼저** 실행된다. `SecurityConfig`에
`configureGlobalAuthentication(auth: AuthenticationManagerBuilder)`를 추가해 여기서
`deployKeyAuthenticationProvider`/`yonaAuthenticationProvider`를 등록하면, 이후 어느 체인이
먼저 만들어지든 전역 빌더가 이미 "구성됨" 상태라 `InitializeUserDetailsBeanManagerConfigurer`가
`DaoAuthenticationProvider`를 끼워 넣지 못한다. 기존 `securityFilterChain()` 안의
`.authenticationProvider()` 두 줄은 이제 같은 인스턴스를 중복 등록할 뿐이라 제거했다.

## 완료 기준

- 올바른 비밀번호 로그인은 그대로 성공한다.
- 틀린 비밀번호 로그인은 500이 아니라 `/users/loginform?error=true`로 정상 리다이렉트된다.
- OAuth2 소셜 로그인(google/github)/엔터프라이즈 OIDC/SAML2/LDAP/Deploy Key 인증 등 다른
  인증 경로에 회귀가 없다.

## 완료 로그

### 2026-09-09 — 근본원인 규명 + 수정 + 검증

- 격리된 H2 인스턴스(포트 18099, `-Dlogging.level.org.springframework.security=DEBUG`)로
  재현 후 디버그 로그에서 `"Authentication failed with provider YonaAuthenticationProvider"`
  직후 동일 loginId로 두 번째 `SELECT ... FROM n4user`가 실행되는 것을 확인 —
  `DaoAuthenticationProvider.retrieveUser()`가 같은 `UserDetailsService`를 다시 호출한
  흔적. `InitializeAuthenticationProviderBeanManagerConfigurer`의 INFO 로그
  ("Found 2 AuthenticationProvider beans... Global Authentication Manager will not be
  configured with AuthenticationProviders")는 전역 빌더가 "이미 구성됨"으로 판단해 스스로는
  아무것도 안 더했다는 뜻이라, 범인은 별개의 `InitializeUserDetailsBeanManagerConfigurer`로
  좁혀졌다.
- `SecurityConfig.kt`에 `configureGlobalAuthentication()` 훅 추가, `securityFilterChain()`의
  중복 `.authenticationProvider()` 호출 제거.
- 같은 격리 인스턴스로 재검증: 틀린 비밀번호 → `302 /users/loginform?error=true`(수정 전에는
  500), 올바른 비밀번호 → `302 /`(그대로 정상). 수정 전엔 DEBUG 로그에 있던
  "Found N AuthenticationProvider beans..." INFO 라인 자체가 수정 후엔 더 이상 안 뜸(전역
  빌더가 우리 훅으로 더 일찍 구성 완료되어 그 자동설정기가 관여할 필요조차 없어짐 — 정황
  증거로도 일치).
- 회귀 검증: `DeployKeyGitAuthorizationIntegrationSpec`(5)/`McpOAuth2SecurityIntegrationSpec`
  (10)/`OidcSignInIntegrationSpec`(3)/`LdapServiceSpec`(9)/`AuthControllerSpec`(20) 총 47개
  테스트 전부 GREEN(실패/에러 0건) — OAuth2/OIDC/LDAP/Deploy Key 인증 경로 무회귀 확인.
  SAML2는 실제 IdP 없이는 통합테스트가 없어(기존에도 마찬가지) 이번 회귀 검증 대상에서
  코드 레벨 검토만 수행 — `saml2Login { saml2.authenticationManager(saml2AuthenticationManager()) }`은
  이번 수정과 무관하게 처음부터 전용 `ProviderManager`를 별도로 쓰고 있어 이 버그의 영향을
  받지 않았음을 코드로 확인.
