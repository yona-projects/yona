# P3-48: CSRF 재활성화 이후 raw `$.ajax` PUT/DELETE/PATCH 호출들이 CSRF 토큰 없이 403으로 거부되던 문제 (2026-09-10 발견·근본 수정 완료, 화면별 전수 재현은 남음)

## 배경

[[tickets/p3-47|P3-47]](board/edit 저장 버튼 `ReferenceError`)를 수정한 뒤 Playwright로
저장 버튼을 실제로 눌러 검증하던 중, `PUT /api/projects/{id}/posts/{postId}`가 **403
Forbidden**으로 거부되는 것을 확인했다 — `board/edit.html`의 저장 핸들러가 `$.ajax({method:
'PUT', data: JSON.stringify(requestData), ...})` 형태로 직접 구성한 JSON 바디를 보내는데
CSRF 토큰을 헤더/바디 어디에도 싣지 않았기 때문이다. `static/javascripts/yona-common.js`를
확인한 결과, `meta[name=csrf-token]`을 읽어 CSRF를 자동으로 채워주는 로직은 jQuery
`.ajaxForm()`/`.ajaxSubmit()` 플러그인 경로에만 있고 raw `$.ajax({...})` 호출에는 없었다.

## 근본 수정 (완료)

Spring Security 공식 문서가 권장하는 표준 패턴을 적용했다:

1. `site/layout.html::head`에 `<meta name="_csrf" th:content="${_csrf?.token}">`/
   `<meta name="_csrf_header" th:content="${_csrf?.headerName}">` 추가(모든 화면이 이 fragment를
   씀 — 한 곳에서 전역 적용). `_csrf` 요청 속성이 없을 수 있는 경로(에러 페이지 포워딩 등)를
   위해 안전 내비게이션(`?.`) 사용 — 처음엔 `${_csrf.token}`으로 했다가 전체 스위트 실행 중
   `ErrorPageTemplateRenderingSpec` 등 13개 스펙이 `SpringEL` NPE로 깨지는 걸 발견해 정정.
2. `site/layout.html::scripts` 최상단에 그 두 meta를 읽어 **모든 `$.ajax` 호출에 일괄 적용**되는
   전역 `$.ajaxSetup({beforeSend: function(xhr){ xhr.setRequestHeader(csrfHeader, csrfToken); }})`
   추가. 개별 화면을 하나씩 고치는 대신(재발 방지 안 됨) 이 방식을 택함.

## 실제 브라우저(Playwright)로 board/edit 저장을 end-to-end 재검증하며 발견한 추가 버그

CSRF 수정 후 재검증했더니 403은 사라졌지만 **400 Bad Request**가 새로 나타났다 — 원인은
`board/edit.html`의 같은 저장 핸들러가 `var body = $("#body").val();`로 본문을 읽고 있었는데,
이 화면엔 `id="body"`인 요소 자체가 없다(마크다운 에디터는
`markdownEditor('body', ...)` 프래그먼트가 `id="editor-body-<랜덤>"`로 렌더링 — `name="body"`는
맞지만 `id`는 다름). `$("#body").val()`이 항상 `undefined`를 반환해 `JSON.stringify()`가 그
키를 통째로 빼먹어 서버가 400으로 거부했다. `$('textarea[id^=editor-]').val()`(같은 파일의
멘션 대상 셀렉터와 동일 패턴)로 수정 — **이것도 CSRF와 무관한 별도의 기존 버그**(P3-46/47/48
어느 것과도 무관, 이번 검증 과정에서 우연히 발견).

세 버그(따옴표 누락[[tickets/p3-47|P3-47]] + CSRF 헤더 누락[본 티켓] + 잘못된 `#body` 셀렉터)를
모두 고친 뒤 Playwright로 로그인→프로젝트 생성→게시글 생성→수정→저장까지 **end-to-end로 실제
저장 성공(제목 변경 반영)까지 확인했다.**

## 남은 작업 — 다른 12개 파일의 화면별 재현 (미착수)

전역 `$.ajaxSetup`을 걸어뒀으므로 **이론적으로는 raw `$.ajax` PUT/DELETE/PATCH를 쓰는 나머지
화면들도 자동으로 함께 고쳐졌어야 한다**(CSRF 헤더 누락이라는 근본 원인 자체가 전역으로
해소됐으므로). 다만 실제로 하나씩 브라우저에서 재현해 확인한 것은 board/edit뿐이다. 아래
목록을 이번 세션에서 다시 뽑아뒀다(`method:`/`type:`에 `PUT`/`DELETE`/`PATCH`를 쓰는 파일,
`site/layout.html` 자기 자신과 벤더 파일 `lib/ace/worker-coffee.js` 제외):

- `organization/members.html`
- `pullrequest/edit.html`, `pullrequest/view.html`
- `board/edit.html`(재현·수정 완료), `board/view.html`
- `code/svnDiff.html`, `code/compare.html`
- `project/members.html`, `project/setting.html`
- `common/commentDeleteModal.html`
- `issue/view.html`
- `static/javascripts/common/yona.Tasklist.js`

착수 시 이 11개(board/edit 제외)를 Playwright(또는 브라우저)로 하나씩 실제 액션을 수행해
403/400 등이 완전히 사라지는지 확인할 것 — 전역 수정으로 이미 해소됐을 가능성이 높지만,
board/edit처럼 CSRF와 무관한 별도 버그가 같은 핸들러에 숨어 있을 수 있으므로 "전역 수정
했으니 끝"으로 단정하지 않는다.

**이 과정에서 실제로 발견해 즉시 수정한 CSRF 무관 버그 5건** (모두 P3-48 화면별 실사용 검증
중이 아니었다면 발견하지 못했을 것들 — "전역 수정했으니 끝"으로 단정하지 않은 결과):

1. **`jQuery.ajaxSetup(beforeSend)`가 개별 호출의 `beforeSend` 옵션에 완전히 덮어써지는
   구조적 결함(진짜 CSRF 버그, 가장 중요)** — `common/yona.Tasklist.js`의 PATCH 호출이
   `NProgress.start()`만 하는 자기 자신의 `beforeSend`를 넘기고 있었는데, jQuery는
   `ajaxSetup`으로 등록한 기본 `beforeSend`와 호출별 `beforeSend`를 체이닝하지 않고
   후자가 전자를 완전히 대체한다 — 그 결과 tasklist 체크박스 토글 PATCH가 CSRF 헤더 없이
   나가 403이 났다(실제 클릭으로 재현). `site/layout.html`의 CSRF 주입 메커니즘을
   `jQuery.ajaxSetup({beforeSend})`에서 `jQuery(document).ajaxSend(...)`(항상 모든 핸들러가
   실행되는 전역 이벤트, 호출별 옵션과 독립적)로 전면 교체해 이 클래스의 버그 자체를
   구조적으로 봉쇄했다. 조사 중 이미 더 이전 세션(P3-legal/P3-44, CSRF 재활성화)에서 쿠키
   기반 더블서브밋(`CookieCsrfTokenRepository`+`SpaCsrfTokenRequestHandler`) 방식으로 CSRF
   아키텍처 자체가 한 차례 더 교체돼 있었고, 원래 P3-48이 도입한 meta 태그 기반
   `$.ajaxSetup` 블록은 그 이후로 완전히 죽은 코드(후속 `ajaxSetup` 호출에 덮어써짐)였다는
   것도 함께 확인 — 죽은 스크립트 블록은 제거하고 meta 태그 자체(다른 소비자 없음 확인)는
   남겨뒀다.
2. **`issue/view.html`/`board/view.html`의 tasklist 토글 폼 action URL 불일치** —
   `th:action`이 `/api/{owner}/{projectName}/issues|posts/{number}/content`를 만들어냈는데
   실제 컨트롤러(`IssueController`/`BoardController`)는 `/api/projects/{projectId}/issues|
   posts/{number}/content`(owner/projectName이 아니라 project.id)만 매핑돼 있어 항상 404였다.
   `project.id` 기반으로 정정.
3. **`board/view.html`의 같은 폼에서 2차로 발견된 id/number 혼동** — 2번을 처음
   `post.id`로 고쳤더니 단독 실행 땐 통과했지만(우연히 id==number==1) 다른 스펙과 함께
   전체 스위트를 돌리자(이번 세션 마지막 회귀 확인 단계) 404로 재현됐다 —
   `BoardController.updatePostingContent`의 `@PathVariable postId`가 이름과 달리 실제로는
   `PostingServiceImpl.getPosting(projectId, number)`에 그대로 전달돼 **게시글 번호**로
   조회된다(DB 기본키가 아님). `post.number`로 재정정 — 프로젝트의 두 번째 이상 게시글은
   전부 tasklist 저장이 깨지는 실제 운영 버그였다(테스트 격리 문제가 아니었음).
4. **`issue/view.html`/`board/view.html`의 새 댓글 등록 폼(`#comment-form`)이 완전히
   404였음** — 형제 폼(`.comment-update-form`/`.child-comment-form`)은 이미 REST(POST/PUT
   `.../comments`)로 전환돼 있었는데, 최상위 새 댓글 폼만 legacy 스타일 풀페이지
   `<form method=post>`로 남아있었고 그 `th:action`이 가리키는
   `/{owner}/{projectName}/issue/{issueNumber}/comment` · `.../post/{postNumber}/comment`
   경로 자체가 컨트롤러 어디에도 매핑돼 있지 않았다 — **로그인한 사용자가 이슈/게시글에
   최초 댓글을 다는 것 자체가 불가능한 상태**였다(Playwright로 실제 등록 시도 시 404).
   형제 폼과 동일한 REST 패턴으로 전환.
5. **`markdownService`가 GFM tasklist(`- [ ]`)를 checkbox로 렌더링하지 못함 +
   렌더링돼도 전부 `disabled`** — commonmark 확장 목록에 `commonmark-ext-task-list-items`가
   빠져있어 `- [ ] text`가 그냥 `[ ] text` 리터럴 텍스트로 남아
   `yona.Tasklist.js`가 찾을 `<input type=checkbox>` 자체가 없었다(체크박스 토글 기능
   전체가 죽어있었음). 확장 추가 후에도 라이브러리가 항상 `disabled=""`를 붙이는 것을
   추가로 발견 — legacy(marked.js, Nashorn 서버사이드 렌더링)는 기본적으로
   disabled를 안 붙이고 `yona.Tasklist.js`의 `disableCheckboxIfNeeds()`가 권한 없는
   경우에만 사후 처리하는 구조라, 렌더러가 항상 disabled로 내보내면 권한이 있어도 아무도
   클릭할 수 없었다(실제 클릭 시도로 재현). `MarkdownServiceImpl.renderCore()`에
   렌더링 직후 Jsoup으로 `disabled` 속성을 제거하는 `enableTaskListCheckboxes()` 단계를
   추가해 legacy와 동일한 기본값(활성화)으로 맞췄다.
6. **`code/svnDiff.html`의 유일한 소비처인 `common/branchItem.html`이 SVN 프로젝트
   커밋 상세 화면 자체를 완전히 깨뜨림** — `@templateHelper.branchInHtml(branch)`/
   `@templateHelper.branchItemName(branch)`처럼 SpEL "빈 참조"(`@`) 문법으로
   TemplateHelper를 호출하고 있었는데(이 저장소의 다른 모든 화면은 전부
   `${templateHelper.xxx(...)}` 일반 모델 속성 방식을 씀), `th:each` 반복 안에서 이 문법을
   쓰면 Thymeleaf가 "Instantiation of new objects and access to static classes or
   parameters is forbidden in this context" 예외를 던진다 — 브랜치가 하나라도 있는 SVN
   프로젝트의 커밋 상세 화면은 **항상** 응답이 그 지점에서 잘려나갔다(`curl`/Chrome 모두
   `net::ERR_INCOMPLETE_CHUNKED_ENCODING`/partial file로 재현 — 이미 헤더가 나간 뒤라
   500이 아니라 응답 중간에 연결이 끊기는 형태). 기존 `CodeViewControllerSpec`의 svnDiff
   관련 테스트들은 전부 `getRefNames()`를 `emptyList()`로 스텁해 `th:each` 자체가
   실행되지 않았고, 그 스펙 자체도 `standaloneSetup`이라 Thymeleaf 렌더링을 하지도
   않아 지금까지 발견되지 않았다. `${templateHelper.xxx(...)}`로 정정.
