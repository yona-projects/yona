# P3-20: Mercurial 저장소 zip 아카이브 다운로드 미구현

## 배경

`HgRepository.getArchive(os: OutputStream, branchName: String)`이 완전히 빈 no-op(`{}`)이다 —
예외조차 던지지 않는다. Git 프로젝트는 코드 브라우저의 "Download ZIP" 버튼이 정상 동작하지만,
Mercurial 프로젝트에서 같은 버튼을 누르면 아무 에러도 없이 빈/깨진 응답이 내려간다(조용한
실패 — 명시적 미구현 예외보다 더 나쁜 상태).

hg4j에는 이미 `io.github.search5.hg4j.api.ArchiveCommand`(zip/tar 아카이브 생성, `setRevision`/
`setDestination`/`setType`/`setPrefix`/`call()`)가 구현돼 있다 — hg4j 쪽에 새 기능을 만들
필요는 없어 보인다(먼저 실제로 동작하는지 확인 필요).

## 범위

1. `GitRepository.getArchive()`가 어떻게 구현돼 있는지(호출 위치: `CodeViewController`의
   `/{owner}/{projectName}/code/download/{branch}` 라우트) 확인하고 동일한 사용자 경험을
   재현한다.
2. `HgRepository.getArchive()`를 hg4j `ArchiveCommand`로 실제 구현한다 — `ArchiveCommand`가
   메모리 스트림이 아니라 `File` 목적지(`setDestination(File)`)만 받는다면, 임시 파일에 쓴 뒤
   그 내용을 `OutputStream`으로 복사하고 임시 파일을 정리하는 방식이 필요할 수 있다(직접 확인).
3. hg4j `ArchiveCommand`를 실제로 써보고 버그가 있으면(예: 특정 리비전/브랜치명 처리, 대용량
   저장소, 심볼릭 링크 등) 이 티켓 범위에서 hg4j도 함께 고친다.

## 완료 기준

- 실제 Mercurial 프로젝트에서 "Download ZIP"을 눌렀을 때 실제 커밋 내용이 담긴 유효한 zip
  파일이 내려온다(실사용 검증 — 실제 앱 기동 + 실제 다운로드 + `unzip`으로 내용 확인).
- Git 쪽과 동일한 사용자 경험(파일명 규칙, 디렉터리 구조 등).

## 완료 로그

- **2026-09-09 완료**: `HgRepository.getArchive(os, branchName)`을 hg4j `ArchiveCommand`(변경
  없이 그대로 재사용 — 3개 커맨드 파일 중 이 티켓 범위인 `ArchiveCommand.java`는 실제로 버그가
  없어 hg4j 쪽 수정이 필요 없었다)로 실제 구현했다.
  - `ArchiveCommand`는 `setDestination(File)`만 받으므로 `Files.createTempFile(..., ".zip")`에
    쓴 뒤 `Files.newInputStream(...).use { it.copyTo(os) }`로 복사하고 `finally`에서
    `Files.deleteIfExists`로 정리한다(티켓 배경에서 예상한 그대로).
  - `branchName` 해석은 이 파일의 기존 `resolveRevisionNumber()`를 재사용한다 — 단, 재사용
    과정에서 **이 헬퍼가 실제로는 bookmark 이름이나 named branch 이름을 전혀 해석하지 못하던
    잠재 버그를 발견해 함께 고쳤다**(아래 "발견한 버그" 참고, P3-23 작업과 공유되는 근본 수정).
    이 수정 없이는 "tip" 외의 실제 브랜치로 ZIP을 받는 것 자체가 불가능했다.
  - Git과 동일한 사용자 경험을 위해 `setType("zip")`, `setPrefix("")`(최상위 디렉터리 접두어
    없는 flat 경로, `GitRepository.getArchive()`와 동일한 zip 엔트리 구조)로 호출한다. hg4j
    ArchiveCommand는 항상 `.hg_archival.txt` 메타데이터 파일도 함께 넣는다(실제 `hg archive`의
    표준 동작) — Git 쪽엔 없는 파일이지만 무해한 보너스 파일이라 그대로 둔다.
  - 해석 실패(존재하지 않는 브랜치) 시 Git과 동일하게 예외 없이 조용히 빈 응답을 반환한다.
- **발견한 버그(이 티켓 범위에서 함께 수정)**: `resolveRevisionNumber()`의 마지막 분기가
  `nodeId.toString()`(12자 짧은 해시)과 `rev`를 비교하고 있었는데, 코드 브라우저/다운로드
  엔드포인트가 실제로 넘기는 값은 bookmark 이름이다 — 이 분기가 절대 매치되지 않아 "tip" 외의
  모든 브랜치가 무엇을 하든 깨지는(archive 다운로드 포함) 잠재 버그였다. bookmark → hex(40자
  분기 재귀 재사용) → named branch(P3-23에서 신설한 `BranchesCommand` 조회) 순으로 해석하도록
  고쳤다.
- **추가로 발견해 함께 고친 버그**: `CodeViewController.codeBrowser()`가 bookmark가 없는
  Mercurial 프로젝트(흔한 최초 push 직후 상태)에서 항상 `"master"`로 리다이렉트하고 있었다 —
  Mercurial엔 그런 이름의 브랜치가 있을 리 없어 코드 브라우저 진입 자체가 항상 404였다(이
  버그가 있는 한 Download ZIP 버튼에 도달하는 것조차 불가능해 실사용 검증이 불가능했다).
  Mercurial 프로젝트에 한해 `repository.getDefaultBranch()`(="default")로 정정했다(Git/SVN
  동작은 변경 없음).
- **실사용 검증**: 실제 앱을 h2 프로필로 기동(`bootstrap-setup` → 재시작 → `signup`/`login` →
  `projectform`(vcs=MERCURIAL))하고, 실제 `hg` 7.2 CLI로 파일 2개(`README.md`, `src/main.py`,
  하위 디렉터리 포함)를 커밋해 `hg push --new-branch`로 실제 push했다. 이후:
  - `GET /tester1/hgproj/code` → `302 .../code/default`(위 버그 수정 확인).
  - `GET /tester1/hgproj/code/download/default` → `200`, `Content-Type: application/zip`,
    `Content-Disposition: attachment; filename=hgproj-default.zip`.
  - 받은 zip을 실제로 `unzip`: `.hg_archival.txt`, `README.md`, `src/main.py`(하위 디렉터리
    포함, flat 구조, 최상위 접두어 없음)가 나왔고 `cat`으로 내용까지 원본과 동일함을 확인.
  - 여러 named branch가 있는 저장소(`flatproj`, default/featurebranch)에서
    `code/download/featurebranch`로 받은 zip이 `featurebranch`의 실제 헤드 커밋 내용만
    담고 있음을 확인(브랜치별로 다른 내용이 실제로 다른 zip으로 내려옴).
- **hg4j 변경 없음**: `ArchiveCommand.java`는 실사용 검증 중 버그를 찾지 못해 수정하지 않았다
  (심볼릭 링크/대용량 저장소까지는 이번 검증 범위에서 다루지 않음 — 발견하지 못한 것이지
  검증했다는 뜻은 아니다).
- **범위 밖에서 발견했지만 고치지 않은 것**(최종 보고서 참고): (1) `HgRepository.
  getMetaDataFromPath()`의 폴더 목록이 하위 디렉터리 항목에 대해 `hg.log().setFollowPath()`로
  커밋 메타데이터를 못 찾을 때가 있어(디렉터리 경로에 대한 `followPath`) `userLoginId` 등
  필드가 아예 안 채워지고, 그러면 `code/view.html`의 `file.get('userLoginId').asText()`가
  Thymeleaf에서 NPE로 죽어 폴더가 하나라도 있는 저장소는 코드 브라우저 전체가 응답 중간에
  끊긴다(별도 사전 존재 버그, P3-12 영역, 이 티켓 파일들과 무관). (2) 실제 `hg push`로 만든
  bookmark가 서버 쪽에 전혀 반영되지 않는다(bundle2의 bookmarks part가 적용되지 않는 것으로
  보임 — push/wire-protocol 영역, 이번에 허용된 hg4j 파일 범위 밖). (3) hg4j `TagsCommand`가
  실제 태그(`.hgtags`에 기록된)를 못 찾고 항상 pseudo-tag `tip`만 반환한다(P3-10 영역, 이번
  hg4j 허용 파일 범위 밖).
