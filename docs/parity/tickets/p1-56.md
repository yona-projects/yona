## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-56**: OAuth2 로그인 중 계정 병합/연결 흐름을 yona `YonaUserServicePlugin.merge()/link()` + `UserCredential.merge()/addLinkedAccount()`와 동일하게 이식.
  - **설계 재검토(중요)**: 처음에는 "병합 충돌 시 예외를 던져 확인 화면으로 넘긴다"는 흐름으로 구현했으나, `app/Global.java:222-234`를 다시 읽어보니 yona는 `PlayAuthenticate.Resolver.askLink()`/`askMerge()`를 둘 다 `null`로 설정해두고 있었다(주석: "We don't support moderated account linking/merging in this sample") — play-authenticate 라이브러리 자체 규약상 `askMerge()`가 null이면 **확인 절차 없이 즉시 자동 병합**이 실행된다. `UserCredential.merge()` 구현(단순히 `linkedAccounts`를 옮기고 `otherUser.active=false` 저장, 사용자 개입 지점 전혀 없음)도 이를 뒷받침한다. "확인 화면"은 yona에 존재하지 않는 기능이라 처음 설계가 원본과 다른 동작이었음을 깨닫고 즉시 자동 병합 방식으로 전면 수정 — 사용자가 "의도적 축약 없이 원본과 같은 설계"를 명시적으로 요구했기 때문에, 구현 도중이라도 원본과 다르다는 게 확인되면 그 자리에서 바로잡았다.
  - **`CustomOAuth2UserService.loadUser()` 4갈래 분기 재구성**: yona가 "로그인된 사용자(oldUser)가 새 provider로 인증"이라는 하나의 요청 컨텍스트 안에서 `link()`(처음 보는 provider → 그대로 연결)와 `merge()`(이미 다른 계정에 연결된 provider → 병합)를 프레임워크가 자동으로 갈라 호출하는 것과 동일하게, `SecurityContextHolder.getContext().authentication`으로 "현재 로그인 세션"을 확인(`currentlyLoggedInUser()` — `AnonymousAuthenticationToken`/미인증이면 비로그인으로 취급)한 뒤 (1) provider+providerUserId로 이미 연결된 계정이 있고 그게 currentUser 본인이면 그대로 로그인, (2) 있는데 다른 사용자면 `OAuth2AccountMergeService.merge()`로 **즉시 자동 병합**하고 currentUser로 로그인 유지(yona `merge(newUser, oldUser)`가 `oldUser`=로그인 세션을 반환해 세션이 유지되는 것과 동일), (3) 연결된 계정이 없고 로그인 중이면 이메일/loginId 매칭 없이 곧바로 현재 계정에 연결(yona `link()`과 동일), (4) 비로그인이면 기존 이메일/loginId 매칭 또는 신규가입 로직([[tickets/p1-13|P1-13]] 이후 기존 로직 무변경).
  - **`OAuth2AccountMergeService.merge(keepUserId, otherUserId)`(신규)**: yona `UserCredential.merge()` 대응 — `otherUser`(이 provider에 이미 연결돼 있던, 사라질 계정)의 모든 `LinkedAccount`를 `keepUser`(로그인 세션 계정)로 재배정(`linkedAccountRepository.findByUser(otherUser)` → `.user = keepUser` → `saveAll`)한 뒤, `otherUser.state = UserState.LOCKED`로 저장 — yona `otherUser.active = false`(UserCredential 레벨 비활성화, 다시는 `findByAuthUserIdentity`로 조회되지 않음)에 대응하는 지점을 yona에서는 `User.state`([[tickets/p0-13|P0-13]]에서 이미 구현된 LOCKED 계정 로그인 차단)로 표현해 동일한 효과(병합된 계정으로 다시 로그인 불가)를 낸다. `keepUserId == otherUserId`면 아무 것도 하지 않고 그대로 반환.
  - 테스트: `OAuth2AccountMergeServiceSpec.kt`(신규) 4 tests — LinkedAccount 이전, otherUser LOCKED 처리, 동일 id는 no-op, 존재하지 않는 id는 예외. `CustomOAuth2UserServiceSpec.kt` +4 tests(로그인 중 새 provider 연결/병합 충돌 시 자동 병합 후 로그인 유지/본인에게 이미 연결된 provider면 그대로 로그인/익명 컨텍스트는 기존 흐름으로 폴백) — 총 8 tests. MockK 이슈 2건 해결: `UsernamePasswordAuthenticationToken(loginId, "password")` 2-인자 생성자는 `authenticated=false`가 기본값이라 `currentlyLoggedInUser()`가 항상 null을 반환하던 버그를 3-인자 생성자(`GrantedAuthority` 포함)로 수정, `JpaRepository.saveAll()`의 제네릭 반환 타입(`MutableList<S>`)에 `every { ... } answers { firstArg() }`로 불변 `emptyList()`를 그대로 반환하면 MockK 프록시가 `MutableList`로 캐스트하다 `ClassCastException`이 나던 문제를 `firstArg<List<LinkedAccount>>().toMutableList()`로 수정(이 세션에서 기존에 문서화된 "JpaRepository 제네릭 `save()` 계열 MockK 캐스팅 이슈"의 또 다른 사례).
  - 검증: `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공, `./gradlew test --tests "com.github.yonaprojects.yona.config.oauth2.*"` 12 tests 전체 통과.
