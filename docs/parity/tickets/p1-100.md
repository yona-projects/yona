## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P1-100**: 웹 컨트롤러 전체에 프로젝트 "이전 위치 폴백"([[tickets/p1-76|P1-76]]) 배선.
  - 착수 전 재확인: 원 등록의 28개 파일 목록을 grep으로 재검증하는 과정에서 2곳(`ImportViewController.kt`/`ImportApiController.kt`)이 실제로는 URL 라우팅용 조회가 아니라 **신규 프로젝트 생성 시 이름 중복 체크**(`project.name.duplicate`)임을 발견 — 여기에 폴백을 적용하면 "예전에 그 이름을 쓰다가 지금은 다른 곳으로 이전한 프로젝트"가 있다는 이유로 실제로는 비어있는 이름을 "중복"으로 오판하는 새 버그를 만들 뻔했다. 이 2곳은 범위에서 명시적으로 제외, 실제 대상은 26개 파일.
  - `IssueViewController.kt`는 개인 인박스(`inbox`)/비공개 저장소(`_private`) 시스템 프로젝트 조회 2곳(loginUser 소유 고정 이름)도 섞여 있어, Serena `replace_content`의 regex negative lookahead(`findByOwnerAndName\((?!loginUser)`)로 URL 라우팅용 7곳만 정확히 골라 치환.
  - 나머지 25개 파일은 전부 `val project = projectRepository.findByOwnerAndName(owner, projectName).orElse(null)`(또는 `orElseThrow`) 단일 패턴이라 `findByOwnerAndName(` → `findByOwnerAndNameOrPreviousPlace(`([[tickets/p1-76|P1-76]]에서 이미 구현된 함수) 문자열 치환으로 일괄 배선.
  - 대응하는 24개 컨트롤러 스펙 파일(mockk 스텁)도 동일하게 갱신 — 스텁이 옛 함수명 그대로면 컨트롤러가 새 함수를 호출하는 순간 MockK가 unstubbed 호출로 예외를 던져 전체 테스트가 깨지므로, 이 스텁 갱신 자체가 "컨트롤러가 실제로 새 함수를 호출하는지"의 회귀 검증 역할을 겸함.
  - 테스트: `ProjectViewControllerSpec.kt` +1(예전 owner/name URL로 접근해도 새 위치의 프로젝트를 찾아 정상 렌더링).
