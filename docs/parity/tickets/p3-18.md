# P3-18: SSH forced command가 실제 git/hg 바이너리를 exec하는 대신 인프로세스 JGit/hg4j 로직을 재사용하도록 전환

## 배경

[[tickets/p3-03|P3-03]]이 만든 리눅스/맥 배포 경로(시스템 sshd의 `AuthorizedKeysCommand` +
forced command, `yona-cli`의 `internal ssh-shell`)는 인가만 yona API로 확인하고 그 뒤엔
**진짜 시스템 `git-upload-pack`/`git-receive-pack` 바이너리를 exec**한다(`yona-cli/cmd/internal.go`
`RunGitService()`). 반면 임베디드 Mina SSHD 경로(Windows 폴백 등, `YonaSshGitCommand.kt`)는
JGit의 `ReceivePack`/`UploadPack`을 인프로세스로 호출해 `PreReceiveHookChain`(브랜치 보호 포함)을
그대로 적용한다.

문제: 같은 정책(브랜치 보호 등)이 **두 개의 서로 다른 코드 경로**(JGit 인프로세스 훅 vs 디스크에
심어야 하는 `hooks/pre-receive` 쉘 스크립트)에 따로 존재해야 하고, 하나만 고치고 잊으면 바로
우회 취약점이 될 수 있다(P3-03 진행 중 Mina 경로에서 실제로 이런 종류의 브랜치 보호 우회 버그를
한 번 발견·수정한 전례가 있음, 계획 문서 "4부" 참고).

## 제안 설계

forced command를 얇은 바이트 릴레이로 바꾸고, 실제 git 프로토콜 처리는 이미 떠 있는 yona
메인 JVM이 담당하게 한다(Gerrit의 SSH 데몬이 쓰는 것과 같은 패턴) — JGit의
`ReceivePack`/`UploadPack`은 소켓이 아니라 `InputStream`/`OutputStream`만 있으면 되므로:

1. yona JVM이 로컬 유닉스 도메인 소켓(또는 localhost 전용 포트)을 열어둔다.
2. forced command(`yona-cli internal ssh-shell`, 로직 대폭 축소)는 인증된 principal +
   `SSH_ORIGINAL_COMMAND`를 그 소켓에 전달하고, 이후 stdin/stdout을 그 소켓에 순수 릴레이만
   한다.
3. yona JVM이 소켓 반대편에서 **HTTPS 경로와 완전히 동일한 JGit `ReceivePack`/`UploadPack` +
   `PreReceiveHookChain`** 코드를 그 스트림에 실행한다.

효과: (1) git 프로토콜 처리 코드가 HTTP/SSH 통틀어 하나만 남아 정책 드리프트 위험 제거,
(2) SSH 연결마다 새 JVM을 띄우는 게 아니라 이미 워밍업된 메인 프로세스를 재사용해 콜드스타트
비용 없음(forced command 자체는 여전히 가벼운 네이티브 바이너리).

## Hg(Mercurial)도 같은 방식이 가능한가

**가능하다 — 정정.** 최초 작성 시 "hg4j에 SSH 와이어 프로토콜 서버가 없다"고 적었는데,
`../hg4j`(`search5/hg4j`, 형제 프로젝트) 소스를 직접 열어보고 확인한 결과 **틀린 판단이었다.**
`transport/HgSshWireServer.java`가 이미 존재하며, 클래스 주석에 정확히 JGit과 같은 설계
철학이 적혀 있다: "hg4j itself does not ship a production SSH server" — 즉 `Wire1Commands`
(프로토콜 무관 코어)를 감싸 순수 `InputStream`/`OutputStream` 쌍에 대해 동작하도록 만들어져
있어, JGit의 `UploadPack`/`ReceivePack`을 아무 SSH 채널에나 꽂을 수 있는 것과 완전히 동일한
자리에 꽂을 수 있다. `registerPreChangegroupHook`/`registerPostChangegroupHook`으로 push 전
검증 훅(브랜치 보호 등에 대응하는 자리)도 이미 걸 수 있다. 심지어
`HgSshWireServerRealHgInteropTest`가 임베디드 Mina SSHD로 실제 SSH 채널을 열어 **진짜 `hg`
CLI**를 상대로 clone/push까지 검증해뒀다(hg 설치돼 있을 때만 도는 `@Tag("interop")` 테스트).

따라서 Hg는 git보다 어려운 별도 케이스가 아니라 **완전히 동일한 패턴**(소켓 릴레이 → 인프로세스
`HgSshWireServer.handleConnection(in, out)` 호출)으로 이 리팩터에 함께 포함하면 된다. 위
"장기 hg4j 신규 구현" 옵션은 불필요 — 이미 있는 걸 재확인 못 하고 다시 만드는 헛수고가 될 뻔했다.
[[tickets/p3-12|P3-12]](Hg 지원)가 아직 SSH 배선 자체를 안 했으므로, 이 항목과 P3-12의 SSH
배선을 사실상 같은 작업으로 묶어 진행하는 게 자연스럽다.

## 범위 (착수 시 확정)

- `yona` 메인 앱: 유닉스 도메인 소켓(또는 localhost 전용 포트) 리스너 신설, JGit
  ReceivePack/UploadPack을 그 스트림에 대해 실행하는 핸들러 — `GitServletConfig`가 HTTPS용으로
  이미 구성한 것과 동등한 로직 재사용.
- `yona-cli`: `internal ssh-shell`을 실제 git 바이너리 exec에서 소켓 릴레이로 교체.
- 인증된 principal을 forced command → yona JVM으로 어떻게 전달할지(현재 `SshCommandAuthorization`이
  이미 갖고 있는 project/pusher 정보 재사용 방법) 결정.
- 기존 `YonaMinaSshServerIntegrationSpec`/`SshInternalControllerIntegrationSpec` 등 P3-03
  테스트가 이 리팩터 후에도 여전히 유효한지 재검증.

  **핸드셰이크 프로토콜(yona-cli 쪽 구현자를 위한 상세 스펙)**:
  1. 클라이언트(미래의 yona-cli forced command, 이번 테스트에서는 파이썬 래퍼 스크립트가 대신함)가
     `SshRelayServer`가 바인딩한 유닉스 도메인 소켓 경로(`@Value("yona.ssh.relay.socket-path")`,
     기본값 `/tmp/yona/ssh-relay.sock`)에 연결한다.
  2. 연결 직후, 클라이언트는 **개행(`\n`)으로 구분된 정확히 두 줄**을 보낸다(버퍼링 없이
     바이트 단위로 읽으므로 그 이후 스트림 위치는 정확히 두 번째 개행 바로 다음이다):
     - 1번째 줄 — `SshAuthService.encodePrincipal()`이 만드는 문자열 그대로
       (`sshkey:<id>` 또는 `deploykey:<id>`). 이 principal은 forced command가 이미
       (`internal ssh-auth` 단계에서, P3-03 기존 설계) 검증해 넘겨받은 값을 그대로 전달하는
       것이지, 이 소켓이 다시 인증하지 않는다 — **이 소켓은 신뢰된 로컬 전용**이라는 전제다
       (파일 권한/네트워크 노출 없음으로 이 신뢰를 지켜야 한다 — yona-cli 배선 시 반드시 지킬 것).
     - 2번째 줄 — 원본 `SSH_ORIGINAL_COMMAND` 문자열 그대로.
       - git: `git-upload-pack '/owner/project.git'` / `git-receive-pack '/owner/project.git'` /
         `git-upload-archive '/owner/project.git'` (`SshAuthServiceImpl.authorizeGitCommand()`가
         이미 쓰던 정규식과 완전히 동일).
       - Hg: **새로 지어낸 규약이 아니라 real hg 클라이언트가 `ui.ssh`로 실제로 실행하는 고정
         원격 명령 그대로** — `hg -R '<path>' serve --stdio`(경로에 공백이 없으면 real hg는
         따옴표를 생략한다 — `hg -R owner/project serve --stdio`도 인식). 최초 티켓 초안은
         `hg-serve '/owner/project'`라는 새 규약을 제안했지만, real hg 바이너리가 절대 이
         문자열을 보낼 수 없으므로(hg의 sshpeer 구현이 고정) 실측(strace)으로 확인한 진짜 형식을
         그대로 채택했다 — 그래야 미래의 yona-cli forced command가 SSH_ORIGINAL_COMMAND를
         **가공 없이 그대로** 이 소켓에 전달하기만 하면 된다.
  3. 그 두 줄을 읽고 나면 소켓은 **순수 양방향 바이트 릴레이**가 된다 — 서버는 principal을
     `resolvePrincipal()`로 복원하고, 명령 문자열을 접두어로 git/Hg 중 어느 쪽인지 판별해(각각
     `authorizeGitCommand()`/`authorizeHgCommand()`) 인가한 뒤, 남은 `InputStream`과 소켓의
     `OutputStream`을 `GitSshProtocolHandler`/`HgSshProtocolHandler`에 그대로 넘긴다 —
     `UploadPack`/`ReceivePack`/`HgSshWireServer`가 그 스트림을 직접 읽고 쓴다.
  4. 인가 거부/명령 해석 실패 시 서버는 `"ERR <이유>\n"` 한 줄을 쓰고 연결을 닫는다. 이 한
     연결이 실패해도 accept 루프(리스너 자체)는 절대 죽지 않는다(연결마다 격리된 스레드,
     accept() 실패도 잡아서 계속 진행) — 회귀 테스트로 고정(아래 "테스트" 참고).
  5. **알려진 1라운드 한계(문서화, yona-cli 배선 시 재검토 필요)**: 이 소켓은 stdin/stdout 역할의
     스트림 하나뿐이라, 실제 SSH 채널의 별도 stderr 채널에 대응하는 게 없다. `GitSshProtocolHandler`는
     JGit `UploadPack`/`ReceivePack`의 "메시지"(진행률 등 부가 정보) 스트림을 그냥 버린다 — ref
     거부 사유 같은 핵심 프로토콜 응답(report-status)은 이 메시지 스트림이 아니라 주 데이터
     스트림으로 나가므로 브랜치 보호 회귀 테스트에는 영향이 없는 것으로 실측 확인했지만, 진행률
     표시(`Counting objects...` 등) 같은 사용자 경험은 이 라운드에서 소켓 릴레이 경로로는 나오지
     않는다. yona-cli가 실제 forced command로 배선될 때, 필요하면 간단한 채널 멀티플렉싱(예:
     프레임 앞에 1바이트 채널 태그)을 추가하는 게 좋다.

  **Hg 쪽 인가 설계 노트(git과 다른 점)**: git은 `git-upload-pack`/`git-receive-pack`이라는
  명령 이름 자체로 read/write를 미리 구분할 수 있지만, real hg의 SSH 원격 명령은 항상 고정된
  `hg -R <path> serve --stdio` 하나뿐이고 pull/push 여부는 그 세션 안에서 나중에(`getbundle`
  vs `unbundle` 요청으로) 결정된다. 그래서 `SshAuthServiceImpl.authorizeHgCommand()`가 계산하는
  `SshCommandAuthorization.isWrite`는 "지금 이 요청이 쓰기냐"가 아니라 "이 principal이 나중에
  push를 시도하면 허용되는가"이고, 실제 게이트는 `HgSshProtocolHandler`가 등록하는
  pre-changegroup 훅(= `unbundle` 직전)에서 건다 — git의 `authorizeGitCommand()`가 커맨드 파싱
  시점에 바로 거부하는 것과 달리, Hg는 연결은 항상 허용하고(멤버십 검사는 여전히 연결 시점에
  적용) push 시도만 나중에 거부한다는 점이 다르다. 읽기전용 Deploy Key/비멤버의 push 거부는
  실제로 검증했지만(아래 테스트 목록 참고), git 쪽과 달리 이 소켓 릴레이의 hg 경로에는 이
  "쓰기 거부"를 직접 때리는 자동 테스트는 아직 없다(clone/push 성공 경로만 검증) — 후속 과제로
  남긴다.

  **테스트 환경 격리**: `SshRelayServer`는 고정 경로(`/tmp/yona/ssh-relay.sock`)에 바인딩하므로,
  `YonaMinaSshServer`의 `yona.ssh.mina.enabled=auto`(윈도우 전용 자동활성화)와 같은 취지로
  `application.yml`의 `test` 프로파일 블록에 `yona.ssh.relay.enabled: false`를 추가해 전체
  테스트 스위트가 매 컨텍스트 기동마다 이 소켓을 열지 않게 했다. 이 기능을 실제로 검증하는
  `SshRelayServerIntegrationSpec`만 `@DynamicPropertySource`로 개별 임시 경로를 지정해 명시적으로
  켠다. 설령 어떤 환경에서 바인드가 실패하더라도(경로 충돌 등) `SshRelayServer.start()`는 예외를
  삼키고 경고 로그만 남긴 채 비활성 상태로 남는다 — 애플리케이션 기동 자체는 절대 실패하지
  않는다(`YonaApplicationTests` 컨텍스트 부팅 스모크 테스트로 확인).

  **테스트**: `SshRelayServerIntegrationSpec`(신규, 8개 시나리오) — `YonaMinaSshServerIntegrationSpec`과
  동일한 "실제 CLI를 테스트 하네스로 관통시킨다" 접근을 쓰되, 실제 SSH 세션이 없으므로(이 소켓은
  SSH가 이미 인증을 끝낸 뒤를 가정) `ssh-keygen` 대신 `SshAuthService.encodePrincipal()`로 바로
  "인코딩된 principal" 문자열을 만들어 핸드셰이크에 흘려보냈다. `GIT_SSH_COMMAND`/`hg --config
  ui.ssh=`에 파이썬 스크립트(핸드셰이크 두 줄을 보낸 뒤 stdin↔소켓↔stdout을 순수 릴레이)를
  꽂아 실제 `git`/`hg` 바이너리를 그대로 통과시켰다(hg4j의 `HgSshWireServerRealHgInteropTest`와
  동일 계열의 "real CLI interop" 테스트).
  - 리스너가 실제로 바인딩됐는지.
  - **가장 중요한 테스트**: `require_pull_request` 브랜치 보호가 소켓 릴레이를 통한 직접 push에도
    적용되는지 — `GitSshProtocolHandler`에서 `BranchProtectionPreReceiveHook` 체이닝을 의도적으로
    비활성화해서 이 테스트만 RED로 재현(다른 7개는 그대로 GREEN)한 뒤 원복해 GREEN으로 되돌아오는
    것까지 직접 확인했다(진짜 회귀 테스트임을 검증).
  - PUBLIC 저장소에 대한 SshKey principal clone 성공.
  - PRIVATE 저장소 비멤버 clone 거부.
  - 게스트 계정 clone 거부.
  - 읽기전용 Deploy Key — clone은 성공, push는 실패.

    `python3`/`hg`가 없으면 조용히 스킵한다).
  - 잘못된/알 수 없는 핸드셰이크 연결 하나가 리스너 자체를 죽이지 않는지(그 직후 정상 연결이
    여전히 성공하는지로 검증).

  **실제로 발견·고친 버그**: 테스트 하네스의 파이썬 relay 래퍼 스크립트가
  `sys.stdin.buffer.read(65536)`로 stdin을 읽었는데, CPython의 `BufferedReader.read(n)`은
  "인터랙티브가 아닌"(파이프로 연결된, 즉 서브프로세스 stdin이 항상 이 경우) 스트림에서는 EOF
  전까지 정확히 `n`바이트를 채우려고 raw read를 반복한다 — git/hg는 프로토콜 왕복마다 64KB보다
  훨씬 작은 청크를 보내고 응답을 기다리므로 이 호출이 영원히 반환되지 않는다. 결과: 이 스펙의
  첫 실행이 2시간 넘게 멈췄다(실측 재현). 코디네이터가 그 멈춘 JVM을 jstack으로 직접 떠서
  독립적으로 확인한 근본원인도 동일했다 — 서버 쪽 `yona-ssh-relay-conn` 스레드가
  `UploadPack.upload()` → `ProtocolV0Parser.recvWants()`에서 무한 대기 중이었는데, 이는 정확히
  "클라이언트(래퍼)가 git의 want 라인을 절대 보내지 못한다"는 예측과 일치한다(래퍼가 자기
  stdin에서 그 바이트를 읽지 못해 소켓으로 전달을 못 했으므로). `os.read(fd, n)`(raw 시스템 콜
  하나, 있는 만큼만 즉시 반환)으로 바꿔 해결 — yona 앱 코드 자체의 버그는 아니고 테스트
  하네스(파이썬 래퍼)만의 문제였지만, 향후 yona-cli가 Go 등으로 유사한 stdin↔소켓 릴레이를
  구현할 때도 "고정 크기 버퍼링 읽기"류 API를 피해야 한다는 실전 교훈이라 남겨둔다.

  **재발 방지(하드 타임아웃)**: 위 사고가 "테스트 하네스 버그 하나가 CI를 몇 시간이고 멈춰
  세울 수 있다"는 별도의 견고성 문제를 드러냈다고 판단해, 원인 수정과 별개로 이 스펙의 모든
  서브프로세스 호출(`runProcessWithTimeout`, 기본 30초)과 "잘못된 핸드셰이크" 테스트의 원시
  소켓 `read()`(10초 워치독 스레드가 강제로 채널을 닫음)에 하드 타임아웃을 추가했다 — 앞으로
  소켓 릴레이 쪽에 비슷한 행업 회귀가 생기면 몇 시간이 아니라 몇십 초 안에 명확한
  `AssertionError`로 실패한다. 이 타임아웃을 추가한 뒤 전체 영향 범위(`config/ssh/*`,
  `domain/sshkey/*`, `YonaApplicationTests`)를 매번 실제로 재실행되도록(`--rerun`으로 캐시
  무효화 확인) 두 차례 더 돌려 플레이키니스가 없음을 확인했다(총 3회 GREEN: 최초 통과 1회 +
  이 타임아웃 추가 후 2회).

  호환 유지 안 함 — 아직 실서비스 배포 전이라 마이그레이션 대상 없음).

- **2026-09-08 후속: forced command를 실제로 bash+socat으로 배선, yona-cli는 완전히 손 뗌
  (사용자 지시로 설계 정정)**: 위 "설계 정정" 절에서 예고한 대로, `yona-cli`(사용자용 CLI)에
  `internal ssh-auth`/`internal ssh-shell`을 새로 만드는 대신 — 확인해보니 실제 운영 가이드
  (`docs/guide/ssh-system-sshd-setup.md`, 다른 세션이 이미 작성)가 애초에 `yona-cli`를 전혀 쓰지
  않고 순수 bash(`ssh-auth.sh`)+curl+jq로 되어 있었다. 그래서:
  - `yona-cli`의 기존 `internal ssh-auth`/`internal ssh-shell`(P3-03이 만들었지만 이 가이드가
    한 번도 쓴 적 없는 죽은 코드였음)와 `internal/sshhelper` 패키지를 통째로 삭제(`go build/vet/test`
    전부 GREEN, gofmt 클린).
  - `docs/guide/ssh-system-sshd-setup.md`의 `ssh-shell.sh`(진짜 git 바이너리를 직접 exec해서
    브랜치 보호를 우회하던 원인 스크립트)를 완전히 삭제하고, `ssh-auth.sh`가 만드는 `command=`를
    `socat - UNIX-CONNECT:<소켓>` 한 줄로 바꿔 위 "핸드셰이크 프로토콜"을 직접 구현했다(별도
    스크립트/바이너리 불필요 — 표준 도구 `socat`만 있으면 됨). authorized_keys의 `command="..."`
    값 안에 리터럴 큰따옴표(`"$SSH_ORIGINAL_COMMAND"`)가 들어가므로 `\"`/`\\`로 이스케이프해야
    한다는 실제 함정을 발견해 처리했고, 셸 스니펫 전체를 직접 bash로 실행(가짜 curl/jq/socat로
    모킹)해 authorized_keys 줄 생성 → 파싱 → 최종 forced command 실행까지 왕복 검증했다(실측,
    문서에 적기만 하고 안 돌려본 게 아님).
  - `/internal/ssh/authorize`(`SshInternalController`) — `ssh-shell.sh`가 없어지면서 이것도
    아무도 안 부르는 죽은 코드가 됨을 확인해 함께 삭제(`/internal/ssh/authenticate`만 남음).
    관련 테스트 2건 제거, 이제 불필요해진 `deployKeyService`/`deployKeyRepository`/
    `projectRepository`/`Project` import도 스펙에서 정리.
  - `SshRelayServer`가 바인드하는 유닉스 도메인 소켓의 권한을 그룹 rw(`rw-rw----`)로 명시
    고정하는 코드를 추가 — forced command는 yona 앱과 다른 OS 계정("git")으로 실행되므로
    기본 umask에 기대면 그룹조차 연결 못 할 수 있었다(실제로 발견한 문제, 이론상 걱정이 아님).
  - 이 변경으로 가이드 문서가 **Git/Hg 어느 쪽인지 신경 쓸 필요가 없어졌다** — `ssh-auth.sh`는
    원본 명령을 그대로 릴레이만 하고, git/hg 구분은 `SshRelayServer`가 소켓 반대편에서 한다.
  - **`yona-cli`는 아니지만 여전히 별도 등록 절차가 필요하다는 점은 남아있음** — `ssh-auth.sh`
    자체는 이 세션에서 실제로 sshd에 등록해 검증하지 못했다(호스트 시스템을 건드리지 말라는
    제약, P3-03부터 이어짐) — 셸 스니펫 자체의 정확성만 위 방식으로 왕복 검증했다. 실제 컨테이너에
    sshd까지 띄워 end-to-end로 검증하는 건 사용자가 별도로 요청한 후속 작업.
