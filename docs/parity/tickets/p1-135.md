- **2026-08-21 — P1-135, [[tickets/p1-111|P1-111]]**: `BareCommit.kt`가 yona `BareCommit.java`의 두 `commitTextFile` 오버로드 중 3-인자(플랫 트리, 루트 파일 전용)만 이식돼 있고, `GitUtil.commitTextFile()`이 실제로 위임하는 4-인자 "Bare commit"(https://gist.github.com/porcelli/3882505 인용) 오버로드가 통째로 빠져 있었음을 확인 — 이 4-인자 오버로드가 1) `branchName` 파라미터로 지정한 `refs/heads/<branchName>`에만 커밋을 반영하고(3-인자는 `this.refName`에 고정된 단일 ref만 사용), 2) DirCache+재귀 TreeWalk로 HEAD 트리의 모든 하위 경로(nested path)를 보존하며 새 파일을 반영하는(3-인자의 `createTreeWith()`는 파일명만으로 단일 레벨 트리를 만들어 nested path 자체가 불가능) yona의 실제 온라인 커밋 경로.
  - `BareCommit.kt`에 `setRefName(refName)` 공개 메서드와 `commitTextFile(branchName, path, text, message)` 4-인자 오버로드(+ private `getRefUpdate`/`getCommitBuilder`/`createTemporaryIndex`)를 yona 249-376행 그대로 이식. `DirCacheEntry.setLastModified`가 jgit 7.6에서 `Instant`를 받도록, `CommitBuilder.setEncoding`이 `Charset`을 받도록 API가 진화한 부분만 언어/프레임워크 기계적 차이로 조정(동작은 동일). yona가 임시 파일을 bare 저장소 디렉터리 내부에 그대로 남겨두는(cleanup 없음) 점도 원본 그대로 재현.
  - 기존 3-인자 `commitTextFile`(README.md/ISSUE_TEMPLATE.md 커밋에 사용, 항상 루트 파일+기본 브랜치)은 yona도 동일 경로(`BoardApp.commitReadmeFile/commitIssueTemplateFile`)에서 3-인자만 쓰므로 변경 없음.
  - [[tickets/p1-111|P1-111]](코드브라우저 "편집" 온라인 커밋)이 이 확장에 의존해 막혀 있던 항목이라 함께 처리: `BoardViewController.createPost()`에 yona `BoardApp.newPost()`의 `if(StringUtils.isNotEmpty(post.path) && isMemberOf(project))` 분기 이식 — `PostingForm`에 `path`/`branch`/`lineEnding`(yona `Posting.java`의 `@Transient` 필드) 추가, 게시글 DB 행을 만들지 않고 지정 브랜치·경로에 바로 커밋 후 코드브라우저(`/{owner}/{project}/code/{branch}/{path}`)로 리다이렉트. `post.lineEnding` 처리를 위해 yona `utils/LineEnding.java`를 `domain/support/LineEnding.kt`로 신규 이식(DOS 변환의 `replaceAll("\\n","\\n")` no-op 버그 포함 원본 그대로 재현 — 의도적 legacy 동작 보존).
  - 테스트: `BareCommitSpec.kt`(신규, 임시 bare 저장소에 실제 커밋해 지정 브랜치만 갱신되고 master는 그대로인지·nested path 파일 내용이 정확한지 검증) 1건, `BoardViewControllerSpec.kt` +1(실제 bare 저장소로 path+branch 지정 시 게시글 생성 없이 커밋되고 코드브라우저로 리다이렉트되는지 end-to-end 검증). 전체 통과.

## 2026-09-26 — README/이슈 템플릿 기본 ref와 개행 복원

- v1.16.0 `BareCommit.commitTextFile`의 3인자 경로는 별도 ref 지정이 없으면 저장소의 `HEAD`에 쓴다.
  2.0은 설정된 초기 브랜치 `main`에 고정해, 기본 브랜치가 `develop`인 기존 저장소의 README를
  수정해도 `develop`은 그대로이고 `main`에만 새 커밋이 생겼다.
- 기본 ref를 `HEAD`로 복원하고 사용되지 않는 초기 브랜치 생성자 인자를 제거했다.
  새 Git 저장소의 초기 `main` 정책과 명시적 `setRefName`/4인자 코드 편집 경로는 유지한다.
- 기존 파일의 줄 끝 형식을 읽어 `LineEnding.changeLineEnding/addEOL`을 적용한다.
  마지막 개행을 보완하되 레거시 DOS 변환의 기존 동작을 새로 재정의하지 않는다.
- `BareCommitSpec`, `BareCommitWikiSpec`: **23 tests passed**.
- 실제 H2 HTTP + Git 검증: 빈 저장소의 첫 README는 `main`에 생성되고 LF로 끝난다.
  HEAD를 `develop`으로 변경한 뒤 README·ISSUE_TEMPLATE를 작성하면 `develop`만 전진하고
  부모 커밋·기존 README가 보존된다. `main` SHA는 그대로이며 파일 바이트의 마지막 LF도 확인했다.
