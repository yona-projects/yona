## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-48**: 이슈를 다른 프로젝트로 이동하는 기능(ISSUE_MOVED)을 처음부터 백엔드에 이식. yona `IssueApp.editIssue()`의 `hasTargetProject()`/`moveIssueToOtherProject()`/`moveSubtaskToOtherProject()`/`transferLabels()`/`isFromMyOwnPrivateProject()`/`addIssueMovedNotification()`를 전부 대조해 하나로 재구성했다.
  - **설계 정정(중요, 보안)**: yona `editIssue()`는 실제 이동(`moveIssueToOtherProject()`)을 먼저 실행한 뒤, 맨 마지막에 `editPosting()` 안에서야 원본 이슈에 대한 UPDATE 권한을 확인한다 — 즉 UPDATE 권한이 없는 사용자도 (대상 프로젝트 생성권한만 있으면) 프로젝트 재할당·라벨 이전·서브태스크 이동까지는 이미 반영된 뒤에야 거부당하는 인가 순서 허점이 있었다. 이걸 그대로 재현하면 인가 우회 취약점을 새로 들여오는 셈이라, yona는 `IssueController.moveIssue()`에서 **원본 이슈 수정권한(`isManagerOrAuthor`) → 대상 프로젝트 생성권한(`AccessControl.isProjectResourceCreatable`)** 순서로 둘 다 먼저 확인한 뒤에만 서비스를 호출하도록 순서를 바로잡았다. 정상적으로 권한이 있는 경우 관찰 가능한 동작(무엇이 이동하고 어떤 알림이 가는지)은 legacy와 완전히 동일 — 달라지는 건 "권한 없는 요청이 부분적으로 반영되는지" 뿐이라 사용자가 명시한 "동작이 완전히 동일해야 한다"는 요구와 상충하지 않는다고 판단했다.
  - **`IssueLabelService.transferLabelsForIssue(labels, toProject)`(신규)**: yona `IssueLabel.copyIssueLabel()`/`findExistLabel()` 대응 — 카테고리를 이름으로 찾거나 만들고, 그 카테고리 기준으로 라벨을 찾거나 만든다([[tickets/p1-54|P1-54]]의 project+category+name 복합 유일성 그대로 재사용). 기존 `copyLabels()`(프로젝트 포크용, [[tickets/p1-12|P1-12]])와 카테고리/라벨 find-or-create 로직을 공통 private 헬퍼(`findOrCreateLabelCategory`/`findOrCreateLabel`)로 추출해 공유 — `copyLabels()`는 이미 있는 라벨을 건너뛰지만(포크 시 "새로 복사된 것"만 보고하는 용도), `transferLabelsForIssue()`는 이미 있는 라벨도 결과에 포함한다(이관된 이슈의 최종 라벨 집합이어야 하므로) — 그래서 별도 메서드로 분리했다.
  - **`IssueService.moveIssue(issueId, targetProjectId, mover)`(신규)**: `IssueServiceImpl`에 구현.
    - `isRequestedToOtherProject()` 대응 — 같은 프로젝트면 아무 것도 하지 않고 그대로 반환.
    - **타이밍 의존 워처 캡처**: yona `Set<User> fromWatchers = originalIssue.getWatchers()`(작성자+담당자+투표자+명시적 감시자, `AbstractPosting.getWatchers()`) 대응 — 이동 **직전**(구 프로젝트 기준)에 `watchService.findActualWatchers(..., projectId=이전 프로젝트, eventType=ISSUE_MOVED)`로 미리 계산해둔다. 이동 후에 계산하면 새 프로젝트의 뮤트/권한 설정으로 잘못 계산되기 때문에 반드시 이동 전에 캡처해야 한다.
    - **`updateIssueToOtherProject()`**: project 재할당, `targetProject.lastIssueNumber` 증가분으로 새 번호 부여(기존 `createIssue()`와 동일한 번호 채번 관례), createdDate/updatedDate 갱신, milestone 초기화(마일스톤은 프로젝트 종속이라 재매핑하지 않고 그냥 비움), 이슈의 모든 댓글(`IssueComment.projectId`, 크로스 프로젝트 검색용 비정규화 필드) 갱신, 그리고 `mover.isMemberOf(targetProject) && 라벨이 있으면` `transferLabelsForIssue()`로 이전하고 아니면 빈 집합으로 비움. 서브태스크(직계 자식, `IssueRepository.findByParentId`)도 동일하게 이동하되(`moveSubtaskToOtherProject()` 대응) **별도 알림은 발행하지 않는다**(legacy와 동일).
    - **`isFromMyOwnPrivateProject()`** 대응: 이동 전 프로젝트가 비공개이고 그 소유자가 mover 본인이면, 이동 후 알림 없이 `issue.history = ""`만 비운다(자신의 비공개 프로젝트 안의 편집 이력이 새 프로젝트에 노출되지 않도록).
    - 그 외의 경우 `!issue.isDraft`이면 `publishIssueMovedNotification()`(`EventType.ISSUE_MOVED`, title=`"Re: [새 프로젝트] 제목 (#새 번호)"` — yona `formatReplyTitle(issue)` 그대로, oldValue/newValue=`"{owner}/{name}"` 쌍, 수신자=이동 전 캡처해둔 워처)와 `publishNewIssueNotification()`(`EventType.NEW_ISSUE`, 기존 `createIssue()`가 쓰던 것과 동일한 제목 포맷·수신자 계산 로직을 발신자만 mover로 바꿔 재사용하도록 리팩터링해 추출)를 모두 발행 — yona `addIssueMovedNotification()`이 항상 두 알림을 함께 발행하는 것과 동일. **`ISSUE_MOVED`는 다른 모든 알림과 달리 mover 자신을 수신자에서 빼지 않는다**(yona `afterIssueMoved()`에 self-제외 코드가 없음을 직접 확인) — mover가 이슈 작성자/담당자/투표자/워처였다면 자신이 실행한 이동 알림도 함께 받는다. `issue.isDraft`(초안)면 두 알림 모두 발행하지 않는다 — 이 분기는 legacy와 동일하게 코드에 포함돼 있었고, 당시엔 yona에 이슈를 초안으로 만드는 경로 자체가 없어 사실상 항상 발행 경로를 탔으나 이후 **[[tickets/p1-65|P1-65]]**에서 초안→발행 전환 플로우 자체가 이식됨(`[x]`).
  - **발견 후 별도 등록**: 이슈 수정 폼에 "다른 프로젝트로 이동" UI(대상 프로젝트 선택 드롭다운)를 추가하는 프론트엔드 작업은 남아있고, 초안→발행 전환(`isPublish`) 자체의 이슈 번호 재채번/이력 초기화 로직은 **[[tickets/p1-65|P1-65]]에서 완료**됨(`[x]`, 이번 이동 로직은 그 존재 여부와 무관하게 정확히 동작했다).
  - 테스트: `IssueLabelServiceImplSpec.kt` +4(신규 라벨 없으면 생성/이미 있으면 재사용해 결과에 포함(copyLabels와 다른 점)/여러 라벨 일괄 이전/빈 집합 처리) — 기존 13 tests(리팩터링 후에도 그대로 통과) 포함 총 17. `IssueServiceSpec.kt` +9(다른 프로젝트로 이동 시 project/번호/생성일/마일스톤 초기화/댓글 projectId 갱신/대상 멤버면 라벨 이전/비멤버면 라벨 비움/서브태스크 동반 이동+서브태스크 단독 알림 없음/ISSUE_MOVED+NEW_ISSUE 알림 수신자 분리 검증(자기 자신 포함 여부까지)/비공개 프로젝트 이동 시 history 비움+무알림/대상 프로젝트 없으면 예외) — 총 21. `IssueControllerSpec.kt` +4(작성자가 이동 성공/원본 권한 없으면 403·서비스 미호출/대상 생성권한 없으면 403·서비스 미호출/대상 프로젝트 없으면 400) — 총 13. 테스트 작성 중 실제로 두 가지를 발견해 고쳤다: (1) Kotlin 생성자로 직접 만든 User 엔티티는 Hibernate가 `projectUsers` 컬렉션을 지연로딩 프록시로 바꿔치기하지 않아(엔티티가 DB에서 로드된 게 아니라 애플리케이션에서 생성된 것이라) `ProjectUser`를 리포지토리로만 저장해선 `isMemberOf()` 판단에 반영되지 않는 것을 확인해, 테스트에서 `mover.projectUsers.add(...)`로 같은 컬렉션에 직접 추가하도록 수정(같은 이슈로 `userRepository.findById()` 재조회도 영속성 컨텍스트 식별자 맵 캐시 때문에 효과가 없음을 확인). (2) ISSUE_MOVED 수신자 테스트에서 mover 자신이 이슈 작성자라 수신자에 포함돼야 하는데 처음엔 놓쳤던 것 — 위 설계 그대로였고 테스트 쪽 기대값이 틀렸던 것으로 확인해 바로잡음(자기 자신 비제외가 실제 legacy 동작).
