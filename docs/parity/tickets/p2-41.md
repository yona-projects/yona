## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P2-41**: "나를 멘션한 이슈" 필터의 LIKE 텍스트 검색 근사 구현을, yona `models/Mention.java`(전용 인덱스 테이블 + `update()`/`getMentioningIssueIds()`) 대응으로 **사용자 지시에 따라 로직·구조·한계까지 그대로** 포팅했다.
  - **yona 구조 조사 결과**(구현 전에 코드로 직접 확인): `mention` 테이블(`conf/evolutions/default/1.sql:153-159`, `id/resource_type/resource_id/user_id`, 유니크 제약 없음)에 `AbstractPosting.save/saveWithNumber/update/directSave`(Issue/Posting)와 `Comment.save/update`(IssueComment/PostingComment)가 매번 `Mention.update(resource, mentionedUsers)`(diff-sync: 빠진 멘션 삭제+새 멘션 삽입)를 호출해 동기화한다. `mentionedUsers`는 `NotificationEvent.getMentionedUsers(body)` — **알림 발송에 쓰는 것과 동일한 함수**로 계산되어 `@orgname`(조직 전원)/`@owner/project`(프로젝트 전원)/직접 `@user` 세 가지를 모두 확장한다. 조회는 `Mention.getMentioningIssueIds(userId)`가 `resource_type IN (ISSUE_POST, ISSUE_COMMENT)`만 필터링하고, ISSUE_COMMENT는 부모 이슈 id로 치환해 반환한다.
  - **그대로 가져온 한계**: (1) 리소스 삭제 시 Mention 행을 정리하는 코드가 yona에 전혀 없어(`Mention.delete()`/`deleteBy()` 호출 0건) 고아 행이 남는다 — yona에도 삭제 시 정리 로직을 추가하지 않았다. (2) `ReviewComment`/`CommitComment`는 yona에서 `Comment`를 상속하지 않아 Mention 인덱스 대상이 아니다 — yona의 `CodeReviewServiceImpl`도 이미 `extractMentionedUsers()`를 알림용으로 쓰고 있지만 Mention 동기화는 추가하지 않았다.
  - `domain/mention/`(신규 패키지) — `Mention`(엔티티), `MentionRepository`(`findByResourceTypeAndResourceId`/`findByUserIdAndResourceTypeIn`), `MentionService`/`MentionServiceImpl`(`update()` diff-sync, `getMentioningIssueIds()`).
  - yona는 이미 `CommentService.extractMentionedUsers(contents)`([[tickets/p1-126|P1-126]], yona `getMentionedUsers()`와 동일하게 조직/프로젝트 그룹 확장 포함)가 존재해 재사용 — 새로 만들지 않았다.
  - 훅 지점: yona는 모델 레벨에서 모든 save/update가 무조건 `updateMention()`을 재실행하지만, yona는 서비스 메서드가 세분화돼 있어(changeState/changeAssignee/moveIssue 등은 body를 안 건드림) **본문/내용이 실제로 바뀌는 지점에만** 훅을 달았다 — `IssueServiceImpl.createIssue/updateIssue`, `PostingServiceImpl.createPosting/updatePosting`, `CommentServiceImpl.createIssueComment/createPostingComment/updateIssueComment/updatePostingComment` 8곳. body가 안 바뀌는 다른 save 호출은 yona에서도 재동기화가 무의미한 no-op이라(같은 멘션 집합 재계산) 결과적으로 Mention 테이블 최종 상태는 "모든 save에 훅을 단 것"과 동일하다.
  - `IssueRepository.findMentionedByState/countMentionedByState`의 시그니처를 `mentionKeyword: String`(LIKE 패턴)에서 `mentionedIssueIds: List<Long>`(yona `Mention.getMentioningIssueIds()`가 반환하는 실제 이슈 id 목록)로 교체. `UserViewController.userIssues()`가 `mentionService.getMentioningIssueIds(loginUser.id)`를 한 번 계산해 재사용(빈 목록이면 JPQL `IN ()` 오류를 피하기 위해 repository 호출 자체를 건너뛰고 빈 결과 반환).
  - 테스트: `MentionServiceImplSpec.kt`(신규) +4(diff-sync 추가/삭제, 멱등성, 이슈+댓글 멘션 합산, 멘션 없음), `IssueServiceSpec.kt` +2(그룹 멘션한 이슈를 직접 언급 안 된 조직원도 찾을 수 있음/본문 수정 시 멘션 인덱스도 재동기화됨 — 이 두 테스트가 P2-41이 실제로 고치려던 버그의 end-to-end 검증), `UserViewControllerSpec.kt` +2(멘션 id 목록을 repository에 그대로 전달/빈 목록이면 repository 미호출). 전체 통과(`MentionServiceImplSpec` 4/4, `IssueServiceSpec` 37/37, `UserViewControllerSpec` 9/9, `PostingServiceSpec` 12/12, `CommentServiceSpec` 11/11, `CodeReviewServiceSpec` 28/28, `PullRequestServiceSpec` 23/23 등 관련 스위트 전체 회귀 없음 확인).
