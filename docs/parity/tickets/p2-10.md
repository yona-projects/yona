# P2-10: **표현 정정**: "yona 1시간 기본값 대비 24배 차이"는 코드 레벨 fallback만 본 것 — 실제 배포용 conf 템플릿(`application.conf.default:253`)엔 6시간으로 오버라이드돼 있어 정확히는 6시간 대비 4배 차이. yona는 값을 설정 가능하게 하고 0 이하면 폴링 자체를 비활성화하는데 yona는 둘 다 하드코딩(메커니즘 자체는 동일 — git ls-remote+semver 비교)

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P2-10**: 자체 업데이트(신규 버전) 확인 주기를 설정 가능하게 만들고 legacy 기본값에 맞춤.
  - 구현 전 재확인([[tickets/p1-74|P1-74]]/[[tickets/p1-82|P1-82]] 교훈): 최초 등록 문구("1시간 vs 24시간, 24배 차이")는 yona `YobiUpdate.java` 코드 레벨 fallback만 보고 실제 배포용 conf 템플릿을 대조하지 않은 것이었음 — `conf/application.conf.default:253`에 `application.update.notification.interval = 6h`로 명시적 오버라이드가 있어, 실제 legacy 배포 시 동작은 6시간 간격이 맞다. 백로그 문구를 정정한 뒤 구현.
  - `YonaUpdateService.kt`: `intervalMillis`를 `@Value("\${yona.update.interval-ms:21600000}")`로 신규 주입(기본값을 conf 템플릿 기준 6시간으로 채택), `@Scheduled`의 `fixedDelay`/`initialDelay` 정수 리터럴을 `fixedDelayString`/`initialDelayString` 프로퍼티 참조로 전환(간격을 설정 가능하게 만드는 yona의 성격을 재현) — `initialDelayString` 기본값도 yona 코드 기본값인 5초(`5000`)로 정정(기존 yona는 10초 하드코딩).
  - yona `YobiUpdate.onStart()`의 "`interval <= 0`이면 스케줄러 자체를 등록하지 않는다"와 동일한 관찰 가능 동작(업데이트 확인이 전혀 실행되지 않음)을 재현하기 위해, 실제 네트워크 호출 로직을 `refreshVersionToUpdate()`에서 `checkForUpdate()`로 분리하고 앞단에 `if (intervalMillis <= 0) return` 가드 추가(`@Scheduled` 애노테이션 자체는 정적이라 스케줄 등록을 조건부로 만들 수 없어, 매 실행 시 즉시 스킵하는 방식으로 동일한 관찰 가능 결과를 재현).
  - `application.update.check.use`(관리자 페이지에서 즉시 수동 체크를 트리거하는 스위치, `SiteApp.java:331`)와 `unwatchUpdate()`(알림 숨기기)는 이 항목(백그라운드 폴링 주기)과 무관한 별개 기능이라 이번 범위에서 제외 — `isWatched` 필드는 기존에 이미 이식돼 있음을 확인.
  - 테스트: `YonaUpdateServiceSpec.kt` 신규 2건(interval 0 이하면 `checkForUpdate()` 미실행 검증/양수면 실행 검증 — `spyk`로 실제 네트워크 호출 유무를 간접 검증).
  - 검증: `./gradlew test --tests "...YonaUpdateServiceSpec"` 전체 통과.
