## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-88**: 접근제어 중앙화 2단계 — 산발적으로 흩어져 있던 `checkReadPermission` 계열(그룹 A/A', 17곳)을 [[tickets/p1-85|P1-85]] 1b에서 추가한 `accessControl.isAllowed(user, project, Operation.READ)`로 실제 교체(그동안 게스트가 PUBLIC 프로젝트를 읽을 수 있던 버그와 `isAllowedIfSharer` 누락을 한 번에 해소). 규모가 커서 두 그룹으로 나눠 병렬 작업했다.
  - **헬퍼형 9개 파일**(BoardController/CommentController/IssueController/IssueLabelController/MentionController/MilestoneController/ProjectController/PullRequestController/VoteController): 각 파일의 `private fun checkReadPermission(project, user)` 본문만 `accessControl.isAllowed(user, project, Operation.READ)` 한 줄로 교체(시그니처·다른 헬퍼는 그대로 유지). `IssueController`는 이미 [[tickets/p1-82|P1-82]]로 sharer까지 처리하는 3-인자 오버로드(`checkReadPermission(project, issue, user)`)가 있어 그건 건드리지 않고 2-인자 오버로드만 교체.
  - **인라인 변형 8개 파일**(BoardViewController/CodeViewController/MilestoneViewController/PullRequestViewController/ProjectViewController/BranchViewController/CompareViewController + 대상 아님으로 확인된 BranchApiController): 파일마다 제각각이던 인라인 조건문을 동일한 중앙 함수 호출로 교체. `CodeViewController`/`ProjectViewController`/`BranchViewController`/`CompareViewController`는 `project.isCodeAccessibleMemberOnly`(코드 탭 멤버 전용 설정)라는 이 그룹 특유의 추가 게이트가 있어, 이를 보존하면서 else 분기에서만 중앙 READ 체크를 적용하도록 `if/else`로 재구성(단순 치환이 아님). `BranchApiController.kt`는 조사 결과 READ 체크 자체가 없는 파일(WRITE 전용 엔드포인트만 존재)로 확인돼 대상에서 제외.
  - **기존 테스트 fixture의 숨은 결함 발견**: 다수 테스트가 멤버십을 `projectUserRepository.existsByProjectIdAndUserId(...) returns true`라는 리포지토리 스텁으로만 표현하고, 새 중앙 함수가 실제로 읽는 `User.projectUsers` 엔티티 컬렉션은 비워둔 채였다(1a 이전엔 컨트롤러가 리포지토리로 직접 멤버십을 조회해 문제되지 않았지만, `AccessControl.isAllowedXxx()`는 entity 관계 기반이라 이 간극이 드러남) — 영향받은 모든 테스트에 `user.projectUsers.add(ProjectUser(...))` 연결을 보강(assertion을 뒤집은 곳은 없음, 코멘트로 사유 명시). `PullRequestControllerSpec.kt`는 `user`를 그대로 `.user`에 연결하면 `PullRequest.contributor` 직렬화 시 `user→projectUsers→user` 순환 참조로 Jackson이 무한 재귀에 빠져(`IssueSharer.kt`의 기존 `@JsonIgnore` 사례와 동일 문제군) 판정에 영향 없는 더미 User로 연결.
