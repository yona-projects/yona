# P3-17: OAuth2 앱(클라이언트) 등록을 사이트 관리자 전용 → 사용자 셀프서비스로 전환

## 배경

[[tickets/p3-14|P3-14]] 1라운드에서 `OAuthAppsAdminController`(`/site/oauth-apps`)를 신설하며 OAuth
앱(confidential/public 클라이언트) 등록 권한을 **사이트 관리자 전용**으로 결정했다
(`docs/yona-wiki/plans/p3-14-oauth2-provider.md` "4. `OAuthAppsAdminController`" 절 참고).

사용자가 codeburg(Forgejo 인스턴스)에서는 제3자 OAuth2 앱 등록이 **사용자 단위**로 되어 있는데
왜 우리는 관리자만 하게 했냐고 질문 — 근거를 추적한 결과, 해당 결정은 GitHub/Forgejo와
비교 검토한 결과가 아니라 "`SsoAdminController`와 동일한 사이트 관리자 전용 패턴"이라는
한 줄 근거로, **SSO IdP 설정(사이트 전역 자원)의 관리자 전용 패턴을 OAuth 앱 등록(사용자가
만드는 자원)에 그대로 복사**한 것이었다. 실제로 GitHub(Settings → Developer settings →
OAuth Apps)와 Forgejo 둘 다 OAuth 앱 등록은 사용자 계정에 종속된 셀프서비스 기능이다.
이 저장소의 표준 방침("기능을 추가하다 모호한 게 있으면 항상 GitHub 방식을 차용한다")과도
어긋난다.

## 범위 (착수 시 확정)

- `OAuthAppsAdminController`(`/site/oauth-apps`, 관리자 전용)를 사용자 네임스페이스
  (예: `/user/editform/oauth-apps/new` 또는 GitHub과 동일하게 `/settings/developers` 계열)로
  이전하거나, 관리자 화면은 "사이트 전체 앱 조회/강제 해지" 용도로 남기고 별도로 사용자용
  등록 화면을 신설하는 방안 중 선택 — 착수 시 기존 `edit_oauth_apps.html`(Authorized Apps,
  이미 사용자 단위로 존재)과의 관계를 먼저 정리할 것.
- `OAuthRegisteredClient`의 소유자(owner) 개념이 현재 없다면 추가 필요(어떤 유저가 등록한
  앱인지 추적, 본인 앱만 수정/삭제 가능하도록 IDOR 방지).
- Public 클라이언트(비밀값 없는 SPA/CLI용)도 셀프서비스로 등록 가능하게 할지, confidential만
  허용할지는 GitHub 방식(둘 다 사용자가 등록 가능) 기준으로 결정.
- 기존 관리자 전용 경로/테스트(`OAuthAppsAdminControllerSpec` 등)와의 하위호환 처리.

## 완료 로그

**2026-09-07 TDD로 완료.** 범위 절 두 옵션 중 "관리자 화면은 사이트 전체 앱 조회/강제 해지 용도로
남기고 별도로 사용자용 등록 화면을 신설" 방안을 택했다(GitHub도 사이트 관리자 화면 자체가 없다는
점과, 기존 관리자 전용 테스트/라우트를 완전히 지우기보다 "역할 축소"로 남기는 편이 감사(audit)
가치가 있다고 판단).

- **소유자 추가**: `domain/oauth2server/OAuthRegisteredClient.kt`에 nullable `ownerId: Long?` 컬럼
  추가(생성자 마지막 파라미터, 기존 이름 있는 인자 호출부는 전부 영향 없음). `OAuthRegisteredClientRepository.findByOwnerId()` 추가.
- **등록/삭제 로직 공유**: 관리자 컨트롤러와 사용자 컨트롤러 둘 다 "등록"과 "삭제 시 관련
  동의/토큰 레코드 정리"를 필요로 해서, 신규 도메인 서비스
  `domain/oauth2server/OAuthAppRegistrationService.kt`로 뽑아 하나의 구현만 유지했다(컨트롤러별
  복제 대신 — 티켓이 제안한 "공유 가능하면 공유" 판단). `availableScopes()`(ApiTokenScopeGroup x
  READ/WRITE 축)도 이 서비스로 옮겨 관리자/사용자 두 화면이 재사용한다.
- **사용자 셀프서비스 신설** (`web/UserViewController.kt`):
  - `GET /user/editform/oauth-apps-owned`(목록, 본인 소유만) / `GET .../new`(등록 폼) /
    `POST .../register`(등록, 성공 시 목록으로 리다이렉트 + `registeredClientId`/`registeredPlainSecret`
    플래시 속성 — tokens 화면의 `issuedRawToken`과 동일한 컨벤션, URL에 시크릿을 절대 담지 않음,
    검증 실패 시 등록 폼을 입력값과 함께 재렌더링) / `POST .../{id}/delete`(본인 소유 확인 후
    삭제 — 아래 IDOR 항목 참고).
  - 템플릿 `user/edit_oauth_apps_owned.html`(목록) / `user/edit_oauth_apps_owned_new.html`(등록 폼)
    신규 — `edit_tokens.html`/`edit_tokens_new.html`과 동일한 tabmenu/`ybtn`/플래시 배너 컨벤션.
  - `user/partial_edit_tabmenu.html`에 `oauth-apps-owned` 탭 추가(기존 탭 항목은 손대지 않음).
    메시지 키 `userinfo.oauthAppsOwned`(탭 라벨) + `oauthapp.*`(등록 화면 전용, 기존
    `oauth2.authorizedApps.*`와는 별개) 신규 추가(en/ko 둘 다).
  - 기존 `/user/editform/oauth-apps`("인가된 OAuth 앱" = 내가 동의한 남의 앱)는 전혀 건드리지
    않았다 — URL도 템플릿도 완전히 분리.
- **IDOR 방지(가장 중요한 요구사항)**: `deleteOwnedOAuthApp()`은
  `OAuthAppRegistrationService.findOwned(id, loginUser.id)`로 "존재 + 본인 소유"를 한 번에
  확인하고, 소유자가 다르거나(또는 애초에 존재하지 않으면) 어느 쪽인지 구분해서 알려주지 않고
  그냥 403을 반환한다 — 실제 삭제(`deleteClientAndRelatedRecords`)는 호출되지 않는다.
  `UserViewControllerSpec`에 "다른 사용자가 소유한 앱을 삭제하려 하면 거부(403)해야 하고, 실제
  삭제를 호출하면 안 된다" 회귀 테스트를 추가해 검증함.
- **관리자 화면 축소** (`web/OAuthAppsAdminController.kt`, `/site/oauth-apps`):
  - `register`/`POST .../register` 라우트와 등록 폼 전부 제거 — `site/oauth_apps.html`에서도
    등록 폼 섹션을 지우고 "감사(audit) 전용" 안내 문구로 교체.
  - `GET /site/oauth-apps`는 그대로 사이트 전체 앱(사용자 셀프서비스 등록 + DCR 자동등록 전부)을
    보여주되, 각 행에 소유자(`ownerId` → `loginId`, null이면 "DCR/system")를 표시하도록
    `OAuthAppsAdminController.OAuthAppAdminRow(app, ownerLoginId)` 뷰모델을 추가했다.
  - `POST /site/oauth-apps/{id}/delete`는 그대로 유지 — 소유자와 무관하게 강제 삭제 가능(이
    저장소의 "site manager global-override" 패턴).
  - `OAuthAppsAdminControllerSpec.kt`: 등록 관련 테스트(public/confidential 등록, 등록 시
    403)는 전부 삭제하고 "POST .../register가 이제 404여야 한다"/"다른 사용자가 등록한 앱과 DCR
    앱을 모두 보여주고 소유자를 함께 표시해야 한다"/"소유자가 다른 앱도 강제 삭제할 수 있어야
    한다" 테스트로 대체.
- **실제로 발견한 갭**: 없음(기존 admin 등록/삭제 로직을 그대로 옮겨 재사용했고, IDOR 체크를 새로
  추가한 것 외에는 동작 변경이 없었다).
- **테스트**: `UserViewControllerSpec`(145건, 신규 오너십/등록/삭제/IDOR 케이스 포함) +
  `OAuthAppsAdminControllerSpec`(7건, 재작성) 전부 GREEN. 회귀 확인을 위해
  `config/oauth2server/*`, `domain/oauth2server/*`, `mcp/*`,
  `web/OAuthAuthorizedAppsControllerIntegrationSpec`도 재실행해 전부 GREEN(엔티티에 새 nullable
  컬럼 하나 추가한 것 외 스키마/동작 영향 없음 확인). `YonaApplicationTests`(context 부팅
  스모크)도 GREEN — `ownerId` 컬럼 추가가 Hibernate ddl-auto 스키마 생성에 문제를 일으키지
  않음을 확인.
- **의도적으로 손대지 않은 것**: `/user/editform/oauth-apps`(Authorized OAuth Apps, 소비자
  동의 화면), RFC7591 DCR 등록 엔드포인트(`/register`), `docs/` 하위 이 티켓 파일과
  `docs/parity/index.md` 한 줄 외 다른 문서.
