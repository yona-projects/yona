# P3-49: 이슈 댓글 화면 파일 업로드(드래그드롭/클릭/붙여넣기)가 두 가지 별개 원인으로 전부 죽어있음

## 배경

P3-46 8-1단계(EasyMDE 셸 교체) 검증 때 "textarea가 `display:none`이 되면 드래그앤드롭 첨부가
깨지는 거 아니냐"는 우려가 나왔었다. 당시 메인 세션은 관련 있어 보이는 두 파일
(`yona.CommentAttachmentsUpdate.js`, `yona.SubComment.js`)을 정적으로 읽고 "둘 다 애초에 로드된
적 없는 죽은 코드라 영향 없다"고 결론 내렸다. 그런데 사용자가 "텍스트 에어리어에 실제 파일을
드롭해본거야?"라고 재차 확인 — 실제로는 정적 코드 리딩만 했지 브라우저로 실제 드롭까지는
검증하지 않았음을 인정하고, Playwright로 로그인→프로젝트→이슈 생성→이슈 댓글창에 텍스트 파일과
PNG 이미지 파일을 각각 실제 `File`/`DataTransfer`로 드롭해 직접 재현했다.

**결과: 텍스트 파일도 이미지 파일도 전혀 업로드되지 않는다.** EasyMDE가 보이는 CodeMirror
표면에 드롭해도, 숨겨진 원본 textarea에 직접 드롭(대조군)해도 둘 다 실패 — 즉 **EasyMDE 때문이
아니라 그 이전부터 있던 별개의 버그 두 개**가 원인이었다.

## 원인 1 (더 심각) — `<script>` 태그 안에 `<th:block>`을 중첩해 써서 JS 파싱 자체가 깨짐

`issue/view.html`의 최하단 인라인 스크립트:

```html
<script type="text/javascript">
    $(function(){
        $yobi.loadModule("issue.View", { ... });   <!-- 이 호출이 실행되어야 함 -->

        <th:block th:if="${isAllowedUpdate}">
        yonaAssgineeModule(...);
        </th:block>
        ...
    });
</script>
```

Thymeleaf는 HTML5 스펙에 따라 `<script>` 요소의 내용을 "raw text"로 취급해서, 그 안에 문자
그대로 적힌 `<th:block>`을 별도 엘리먼트로 인식하지 못하고 **전혀 처리하지 않은 채 그대로
출력**한다. 실제 렌더링 결과(Playwright로 fetch해 raw HTML 확인):

```js
$yobi.loadModule("issue.View", { ... });

<th:block th:if="${isAllowedUpdate}">
yonaAssgineeModule(...);
</th:block>
```

브라우저가 이 스크립트를 파싱하다 `<th:block ...>` 문자열에서 `SyntaxError: Unexpected token
'<'`를 던진다 — **JS 파싱 단계의 문법 오류이므로 이 `<script>` 블록 전체가 통째로 실행되지
않는다**(자바스크립트는 블록 전체를 먼저 파싱한 뒤 실행하므로, 블록 뒷부분의 오류가 앞부분
문장의 실행까지 막는다). 그 결과 맨 위에 있던 `$yobi.loadModule("issue.View", {...})`도 함께
증발한다.

`yobi.issue.View`는 파일 업로더 연결(`_initFileUploader` → `yobi.Files.getUploader`)뿐 아니라
watch/unwatch 버튼, 댓글 작성 후 상태전환 버튼, `CTRL+SHIFT+ENTER` 단축키, issue-info-wrap
affix 등도 담당한다 — **이 모듈이 인스턴스화된 적이 없으니 이 기능들 전부가 이슈 보기 화면에서
죽어있다.**

**확인한 사실:**
- Playwright에서 `$yobi.loadModule("issue.View", {...})`를 콘솔에서 수동으로 호출하면 정상
  동작한다 — 모듈이 뜨고, 업로더가 붙고, 실제로 드롭하면 `POST /files`가 발생한다. 즉 메커니즘
  자체는 멀쩡하고, 문제는 순전히 저 `<th:block>` 렌더링 버그 때문에 호출 자체가 안 되는 것.
- **P3-46과 무관한, 원래 있던 버그다.** 이번 세션 P3-46 작업 이전 커밋(`db78e52da`)에도 동일한
  `<th:block th:if="${isAllowedUpdate}">`가 같은 위치에 그대로 있었다(직접 worktree로 체크아웃해
  확인).
- **레거시(Play/Scala, `origin/v1.6`)에는 이 버그가 없다.** `app/views/issue/view.scala.html`의
  대응 코드는 `@if(isAllowedUpdate) { ... }`를 쓰는데, Play 템플릿은 `@` 지시문을 HTML
  파싱과 무관하게 텍스트 치환 레벨에서 처리하므로 `<script>` 안이든 밖이든 정상 동작한다. 즉
  **Play→Spring Boot/Thymeleaf 리라이트(`8020ae92c`) 과정에서 `@if(...) {...}`를
  `<th:block th:if="...">...</th:block>`로 기계적으로 1:1 치환하면서 생긴 포팅 버그**다 —
  치환할 때 "스크립트 태그 안에서는 th: 중첩 태그가 처리되지 않는다"는 제약을 놓친 것.

**같은 패턴이 더 있는지 전수 조사(2026-09-10):** `src/main/resources/templates` 전체를 스캔해
`<script>...</script>` 안에 `<th:xxx>` 계열 태그(중첩 pseudo-element)가 문자 그대로 들어간
경우를 찾았다 — **`issue/view.html`의 이 한 곳뿐**, 다른 곳엔 없다.

다만 관련 변종을 하나 더 발견했다(별도 경미 이슈, 원인 2 아래 참고와는 무관): `site/layout.html`의
`<script type="text/x-jquery-tmpl">` 블록 2곳에 `th:text="#{...}"` 속성이 붙어있는데, 이것도
같은 이유(스크립트 내용 = raw text)로 **전혀 처리되지 않는다** — `id="tplAttachedFile"`의
`th:text="#{common.attach.clickToPost}"`, `id="tplDropFilesHere"`의
`th:text="#{common.attach.dropFilesHere}"`. 다만 이 둘은 문법을 깨진 않는다 — 그냥 `th:text`가
무시되고 템플릿에 이미 적혀있는 한국어 기본 문구("본문에 넣기"/"여기에 파일을 끌어다 놓으면
업로드 됩니다")가 항상 그대로 노출된다. **기능은 안 깨지지만 다국어(en/ja) 사용자에게는 이
두 문구만 로케일과 무관하게 항상 한국어로 보이는 i18n 버그.** (참고로 `site/userList.html:180`의
비슷한 패턴 `<h4 th:text="#{user.newPassword} + ': ${newPassword}'">`은 검토 결과 오히려
"처리 안 됨"에 의도적으로 기대는 코드로 보인다 — 리터럴 기본값 `${newPassword}` 자체가 jQuery
템플릿 런타임이 치환할 자리표시자라, th:text가 실제로 동작했다면 오히려 깨졌을 것. 버그 아님,
수정 불필요.)

## 원인 2 — 레거시의 "textarea에 바로 드롭→즉시 업로드" 기능 자체가 포팅 안 됨

원인 1이 고쳐져도 이슈 댓글 화면의 업로드가 레거시와 동일하게 동작하진 않는다. 레거시에는
사실 **서로 다른 두 업로드 경로**가 있었다:

1. `yobi.Files.js` + `yobi.Attachments` — 범용 업로더(버튼 클릭/드롭존 오버레이 + `.attached-files`
   목록 UI), `yobi.issue.View.js`의 `_initFileUploader()`가 연결(= 원인 1이 깨뜨리는 대상).
2. **`yona.CommentAttachmentsUpdate.js`** — `.textarea-box textarea`에 **직접** `dragenter`/
   `dragover`/`drop`/`paste` 핸들러를 델리게이트로 건다(`origin/v1.6` 확인). 드롭/붙여넣기 즉시
   `POST /files`로 업로드하고, 성공하면 캐럿 위치에 마크다운 링크(`![파일명](url)` 이미지 /
   `[파일명](url)` 그 외)를 **자동으로 삽입**한다. 사용자가 기대한 "드래그하면 바로 올라간다"는
   경험은 바로 이 경로다.

현재(`next`) 코드베이스에도 `static/javascripts/common/yona.CommentAttachmentsUpdate.js`
파일 자체는 그대로 존재한다(포팅됨) — **하지만 `<script src>`로 로드하는 템플릿이 단 하나도
없다.** 이번 세션에 반복적으로 발견한 "소스는 있는데 로드가 안 됨" 패턴(항목3
`yobi.Mention.js`, 항목6·7 `yobi.Markdown.js` 등)과 같은 종류의 네 번째 사례다. `yona.SubComment.js`
(대댓글)도 동일하게 존재하되 미로드 상태 — 다만 이건 이미 P3-46 8-1단계 검증 때 "죽은
코드"로 확인해뒀던 것과 같은 파일로, 그 자체가 새 발견은 아니고 여기서 맥락상 재확인만 함.

  `.temporaryUploadFiles`, `.attachment-files` — `yobi.Files.js`가 쓰는

  `yona.CommentAttachmentsUpdate.js` 하나가 담당한다.
- 레거시에서 `yona.CommentAttachmentsUpdate.js`를 로드하는 템플릿은 `issue/view.scala.html`과

**정정된 결론**: "원인 2"(새 댓글 textarea 드래그드롭 즉시업로드 미포팅)는 실재하지 않는

`yona.CommentAttachmentsUpdate.js`가 실제로 담당하는 **"기존 댓글 수정 시 첨부파일 관리"**
기능은 이 티켓이 진단한 것과는 완전히 다른, 훨씬 큰 별개의 기능 격차였다 —
`common/commentUpdateForm.html`(현재 포팅본)이 `common.fileUploader`가 아니라 범용
`common/uploadForm` 프래그먼트를 재사용해서(레거시의 전용 마크업이 아님) 기존 첨부파일
목록 자체가 아예 표시되지 않는다. 이 발견은 범위가 커서 **[[tickets/p3-50|P3-50]]으로
분리 등록**했다(이번 라운드엔 포함하지 않음).

### 기존 티켓의 검토 범위 누락 — `board/view.html`

원 티켓(원인 1/원인 2 서술)은 `issue/view.html`만 확인했다. v1.6에서 `yona.CommentAttachmentsUpdate.js`/
`yona.SubComment.js`를 로드하는 템플릿이 `board/view.scala.html`에도 있다는 사실이 빠져
있었다. 직접 대조한 결과 `board/view.html`도 같은 계열의 결함이 있었다(다만 원인 1은 아니었다
— 아래 참고):

- `board/view.html`은 `<script>` 안에 `<th:block>`을 중첩하는 원인-1급 문법 파괴는 없다
  (`board.View` 모듈은 정상적으로 인스턴스화된다 — watch/unwatch 등은 이미 살아있었다).
- 다만 새 댓글 폼이 `uploadForm('NONISSUE_COMMENT', null, null)`로 렌더링돼 `issue/view.html`과
  동일하게 `id="upload"`가 비어 `yobi.board.View.js`의 `_initFileUploader()`가
  `$("#upload")`를 못 찾아 업로드가 죽어 있었다.

### 실제 수정

1. **`issue/view.html`/`board/view.html`의 새 댓글 폼 `#upload` id 복구**: `common/uploadForm ::
   uploadForm(type, null, null)` 호출의 세 번째 인자를 `'upload'`로 수정 — 레거시
   `common.fileUploader`가 항상 하드코딩하던 값과 동일하게 맞췄다. 이 한 줄 수정만으로
   `yobi.Files.js`가 제공하는 클릭 업로드/드롭존 오버레이/textarea 드래그드롭/붙여넣기가
   두 화면 모두에서 전부 살아난다(레거시와 동일한 메커니즘 하나로 전부 커버 — 원인 2로
   지목했던 별도 스크립트 로드는 불필요했다).
2. **`issue/view.html`의 `<script>` 안 `<th:block>` 중첩 제거**: 원인 1 자체는 원 티켓
   진단이 정확했다. 다만 수정 방식은 두 번의 시행착오를 거쳤다 — 상세는 아래 "겪은 시행착오"
   참고. 최종적으로 담당자 지정 호출(`yonaAssgineeModule(...)`)을 본문 스크립트에서 완전히
   분리해, 그 호출만 담는 별도의 `<script th:if="${isAllowedUpdate}">` 태그를 새로 만들었다
   — `th:if`는 엘리먼트 속성이라 raw text(스크립트 내용) 파싱 제약을 받지 않고, 본문 스크립트의
   기존 `[[...]]` 인라인 표현식들은 원래 방식(그대로) 유지된다.

### 겪은 시행착오(정직하게 기록)

1차 시도: `<th:block th:if="...">`를 Thymeleaf의 JS 인라인 블록 주석 문법
(`/*[# th:if="..."]*/ ... /*[/]*/`, `project/menu.html`이 이미 쓰는 패턴)으로 바꾸고
`<script>` 태그에 `th:inline="javascript"`를 추가했다. 이 문법 자체는 정확히 동작했지만
(조건부 블록이 올바르게 스트립/제거됨), **부작용을 놓쳤다** — `th:inline="javascript"`를
켜는 순간 같은 `<script>` 블록 안의 **다른** `[[...]]` 표현식들(`"issueId": "[[${issue.id}]]"`
류, 원래 이 파일 전역이 "수동으로 따옴표를 감싼 `[[...]]`" 스타일로 작성돼 있었다)까지
Thymeleaf의 JSON 문자열 자동 이스케이프 대상이 되어, 결과가 `""OPEN""`(따옴표 중복)·
`"\/admin\/..."`(슬래시 이스케이프)로 깨졌다 — 실제 `curl`로 렌더링 결과를 받아보고서야
발견했다(자동 테스트만으로는 못 잡을 뻔했다 — 처음 작성한 테스트는 "호출이 존재하는지"만
확인했지 "그 값이 깨끗한지"는 확인하지 않았어서, 이후 테스트에 URL이 정확히 한 번만
따옴표로 감싸지고 이스케이프된 슬래시가 없는지 확인하는 단언을 추가했다). `th:inline`을
파일 전체가 아니라 그 조건부 호출만 담은 별도 `<script>` 태그로 국소화하는 2차 시도(최종
채택안)로 이 부작용을 제거했다.

- `CommentAttachmentUploadWidgetTemplateEquivalenceSpec`(신규, 4건) — issue/board 양쪽
