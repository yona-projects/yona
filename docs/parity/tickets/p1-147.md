# P1-147: **(2026-08-26 골든 체크 버킷C 사람 검토에서 발견)** 이슈/게시글 등 리소스 삭제 시 관련 `Watch`/`Unwatch` 레코드를 정리하던 legacy Ebean `postDelete` 훅 로직이 yona cascade 삭제 경로 어디에도 없음 — `IssueServiceImpl.deleteIssueCascade()`/`PostingServiceImpl.deletePostingCascade()`/`ProjectServiceImpl.deleteProject()`에 `watchRepository`/`unwatchRepository` 삭제 호출 없음. 리소스를 반복 생성/삭제하면 `Watch`/`Unwatch` 테이블에 고아 row가 누적되는 실질적 데이터 정합성 회귀

## 원본 표 정보

- **우선순위 구분**: P1
- **상태(원본 체크박스)**: `[x]`
- **yona 근거**: `app/models/resource/ResourcePersistAdapter.java`(`postDelete` 훅)
- **yona 대상**: `domain/watch/{WatchService,WatchServiceImpl}.kt`(`deleteAll` 신규, `AttachmentService.deleteAll`과 동일 패턴), `domain/issue/IssueServiceImpl.kt`(ISSUE_POST), `domain/board/PostingServiceImpl.kt`(BOARD_POST), `domain/milestone/MilestoneServiceImpl.kt`(MILESTONE), `domain/project/ProjectServiceImpl.kt`(PROJECT, PULL_REQUEST)
- **비고(원문)**: **완료** — legacy `postDelete()`는 `ResourceConvertible`을 구현하는 모든 엔티티(이슈/게시글/마일스톤/PR/댓글/라벨/웹훅/조직/유저 등)에 대해 전역으로 동작하지만, JPA에는 Ebean의 `BeanPersistAdapter`에 대응하는 범용 엔티티 삭제 리스너가 없어 전면 재현은 하지 않고, 기존에 `attachmentService.deleteAll(resourceType, id)`이 이미 호출되고 있던 4개 지점(Issue/Posting/Milestone 삭제)과 `ProjectServiceImpl`의 PROJECT/PULL_REQUEST 삭제 지점, 총 5곳에 동일 패턴으로 `watchService.deleteAll()`을 추가(범위를 이 5곳으로 좁힌 근거를 여기 명시 — 나머지 리소스 타입 삭제 경로는 후속 확인 필요할 수 있음). TDD로 RED 확인 후 구현, `WatchServiceSpec`/`ProjectServiceImplSpec`/`MilestoneServiceImplSpec`(신규)/`IssueServiceSpec`/`PostingServiceSpec` 전부 그린
