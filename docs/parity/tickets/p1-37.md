## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-37**: 이슈 타임라인(`IssueEvent`)에 라벨/본문/이동/공유자 변경이 기록되지 않던 문제 수정(아래 참고). yona `IssueApp.java`의 `updateLabelsIfChanged`/`addBodyChangedNotification`/`sendNotification`(공유) 등을 확인한 결과, yona는 `IssueServiceImpl.updateIssue()`(제목/본문/담당자/마일스톤/라벨을 한 번에 처리하는 통합 수정 경로, `IssueViewController.editIssue`와 `IssueController.updateIssue` REST 둘 다 이 메서드로 수렴)가 어떤 필드가 바뀌어도 이벤트를 전혀 기록하지 않는 것이 실제 원인이었음(담당자/마일스톤은 별도의 `changeAssignee`/`changeMilestone` 전용 메서드를 통할 때만 기록되고, 통합 수정 폼에서는 그 메서드들을 거치지 않음).
  - `IssueServiceImpl.updateIssue()`에 변경 전/후 본문·라벨 스냅샷 비교를 추가 — 본문이 바뀌면 `ISSUE_BODY_CHANGED`(oldValue/newValue = 변경 전/후 본문 전체), 라벨 구성(이름 집합)이 바뀌면 `ISSUE_LABEL_CHANGED`(oldValue/newValue = 정렬된 라벨명 콤마 목록)을 기존 `recordIssueEvent` 헬퍼로 기록. 값이 그대로면 이벤트를 남기지 않음(스팸 방지, yona의 `!originalIssue.body.equals(...)` 가드와 동일한 태도).
  - `IssueShareServiceImpl`에 `IssueEventRepository`를 주입하고, `sendNotification()`(공유자 추가/삭제 시 `NotificationEvent`를 만들던 기존 지점)에 동일한 정보로 `IssueEvent(eventType=ISSUE_SHARER_CHANGED)`를 함께 저장하도록 추가 — 이미 계산돼 있던 `NotificationEvent`의 oldValue/newValue를 그대로 재사용.
  - **발견 후 별도 등록**: `ISSUE_MOVED`는 단순 이벤트 기록 누락이 아니라 "이슈를 다른 프로젝트로 이동"하는 기능 자체가 yona에 전혀 없음을 확인(이슈 수정 폼에 대상 프로젝트 선택 UI 없음, 서비스 계층에 재할당 로직 없음) — 새 컨트롤러 액션/폼/서비스 로직이 필요한 별도 규모의 기능 포팅이라 **[[tickets/p1-48|P1-48]]로 별도 등록**, 이후 완료됨(`[x]`, 타임라인 기록 자체는 후속으로 [[tickets/p1-70|P1-70]]에서 마저 완료).
  - 테스트: `IssueServiceSpec.kt` +3 tests(본문 변경 시 이벤트 생성/본문 미변경 시 이벤트 미생성/라벨 변경 시 이벤트 생성), 신규 `IssueShareServiceImplSpec.kt`(공유자 추가 시 이벤트 생성) 1 test. 인접 회귀: `domain/issue/*`, `web/Issue*`, `YonaApplicationTests` 전체 재실행 통과.
  - 검증: `./gradlew compileKotlin compileTestKotlin`, `./gradlew test --tests "com.github.yonaprojects.yona.domain.issue.*" --tests "com.github.yonaprojects.yona.web.Issue*" --tests "com.github.yonaprojects.yona.YonaApplicationTests"` 모두 통과.
