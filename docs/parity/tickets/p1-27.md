- **2026-08-20 — P1-27 정정**: `MergedNotificationEvent`가 `INotificationEvent` 인터페이스 없이 `NotificationEvent`를 그냥 감싸는 단순 래퍼 클래스였던 것을, 사용자가 "단순 래퍼 클래스로 축약하지 말고 원본 요나 그대로 들고와"라고 명시적으로 지적해 yona `notification/INotificationEvent.java`+`MergedNotificationEvent.java`의 인터페이스 기반 다형성으로 되돌렸다.
  - **신규 `INotificationEvent.kt`**: yona `INotificationEvent` 대응. `senderId`/`title`/`eventType`/`resourceType`/`resourceId`/`created`/`receivers`를 인터페이스 프로퍼티로 선언 — `NotificationEvent`(단일 이벤트)와 `MergedNotificationEvent`(병합 이벤트) 둘 다 이걸 구현해, 호출부가 "단일인지 병합인지" 신경 쓰지 않고 같은 계약으로 다룰 수 있다(legacy와 동일한 다형성 구조).
  - **의도적으로 인터페이스에 넣지 않은 것**: yona `getMessage(Lang)`/`getPlainMessage(Lang)`/`getUrlToView()`/`resourceExists()`는 Ebean active-record 모델이 정적 파인더로 직접 DB를 조회하는 인스턴스 메서드였는데, yona는 이 책임을 이미 별도 Spring 서비스(`NotificationMessageResolver`/`NotificationUrlResolver`, P1-27 본편)로 분리해뒀다 — JPA 엔티티에 리포지토리를 주입하는 건 관례에 맞지 않고, 이미 잘 동작하고 테스트된 구조를 억지로 엔티티에 되돌리는 건 이번 지적의 취지(다형성 구조 자체)를 벗어나는 대규모 재작업이라 판단해 유지했다. `setReceivers()`도 인터페이스에서 뺐다 — `NotificationEvent.receivers`가 JPA `@ManyToMany` 프로퍼티라 Kotlin이 이미 `setReceivers(Set)` 합성 setter를 만드는데, 별도 `override fun setReceivers(...)`를 추가하면 JVM 타입소거 후 시그니처가 겹쳐(`@JvmName`으로도 override 함수는 우회 불가) 컴파일이 깨지는 Kotlin 고유의 제약 때문 — `NotificationEvent`를 다루는 기존 코드는 전부 `event.receivers = x` 프로퍼티 대입만 쓰고 있어 실질적인 손실이 없고, `MergedNotificationEvent`는 자신만의 `setReceivers(receivers: Set<User>)` 메서드를 구체 타입으로 그대로 노출한다(`NotificationEventMerger` 등 기존 호출부 무변경).
  - `NotificationEvent.kt`: `class NotificationEvent(...) : INotificationEvent`로 변경, 기존 `title`/`senderId`/`resourceType`/`resourceId`/`eventType`/`created`/`receivers` 생성자 프로퍼티에 `override` 추가(필드/애노테이션은 무변경).
  - `NotificationMailDigestScheduler.kt`: `resourceExists(event: NotificationEvent)`를 `resourceExists(event: INotificationEvent)`로 일반화 — 호출부가 `resourceExists(event.main)`(병합 이벤트에서 강제로 main을 꺼내야 했음)에서 `resourceExists(event)`(병합 이벤트를 그대로 전달)로 단순화됨.
  - 테스트: 신규 `INotificationEventSpec.kt`(+4) — `NotificationEvent`/`MergedNotificationEvent` 둘 다 `INotificationEvent`로 취급해도 자기 속성을 그대로 노출하는지, `MergedNotificationEvent.setReceivers()`로 재계산된 수신자가 main과 독립적으로 노출되는지, 같은 함수가 두 구현체를 구분 없이 리스트로 처리할 수 있는지 검증. 기존 `NotificationEventMergerSpec`(6)/`NotificationMailDigestSchedulerSpec`(12)/`NotificationMessageResolverSpec`(23) 등 알림 패키지 전체 회귀 없이 통과.
  - 검증: `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공, `./gradlew test --tests "com.github.yonaprojects.yona.domain.notification.*"` 전체 통과.

- **2026-08-20 — P1-27**: 알림 메일이 이벤트 발생 즉시 개별 발송되던([[tickets/p0-01|P0-01]]) 것을, yona의 지연-다이제스트-병합 아키텍처로 전면 재구현. 직전 세션에서 "충실히 이식하려면 대규모 재작업이라 후순위"로 보류했던 항목을, 사용자가 "축약하지 말고 필요하면 새로 설계해서라도 그대로 들고 오라"고 명시적으로 재지시해 다시 착수했다. Akka 스케줄러만 Spring `@Scheduled`로 대체하고(사용자가 명시적으로 허용한 유일한 예외) 나머지 알고리즘은 legacy 그대로 옮겼다.
  - **`NotificationEventRecorder.kt`(신규)**: `NotificationEvent.add()`/`addWithoutSkipEvent()` 대응. 같은 리소스에 같은 사용자가 30초 이내 같은 타입 이벤트를 연속 발생시키면 A→B→C를 A→C로 병합하거나 A→B→A를 완전히 상쇄하고(`skipWaypoint=true`, 기본값), `skipWaypoint=false`는 중간 지점은 남기되 정확히 되돌아온 경우만 상쇄한다. 저장 시 `NotificationMail` 마커(발송 대기 큐)를 함께 만든다(OneToOne cascade). 수신자가 비어있으면 아무 것도 저장하지 않는다 — 이 마지막 규칙이 [[tickets/p1-18|P1-18]]/[[tickets/p1-44|P1-44]] 등 기존 스펙 다수가 "혼자 있는 프로젝트에서 알림이 생성됨"을 가정하고 있던 걸 깨서(레거시는 애초에 그런 경우 저장 자체를 안 함), 아래 "테스트" 항목에 정리한 대로 관련 스펙들에 실제 워처를 추가해 정합성을 맞췄다.
  - **`NotificationEventMerger.kt`(신규)**: `NotificationMail.mergeEvents()` 대응. 이벤트를 최신순으로 훑으며 `ISSUE_STATE_CHANGED`/`REVIEW_THREAD_STATE_CHANGED`를 `(컨테이너 리소스, 발신자)` 키로 대기시켜뒀다가, 그보다 **이전(더 오래된)** `NEW_COMMENT`/`NEW_REVIEW_COMMENT`가 같은 키로 나타나면(레거시 클래스 주석: "이슈/리뷰스레드를 열거나 닫는 알림 + 같은 사람이 남긴 **이전** 댓글 알림") 병합하거나, 수신자 집합이 다르면 교집합/댓글전용/상태변경전용 세 갈래로 쪼갠다. `MergedNotificationEvent.kt`(신규)는 당시 legacy `INotificationEvent`/`MergedNotificationEvent` 인터페이스 쌍을 단순 래퍼 클래스로 축약했었으나, 이후 사용자 지적으로 인터페이스 기반 다형성을 그대로 되돌렸다(아래 2026-08-20 완료 로그 참고).
  - **`NotificationMessageResolver.kt`(신규)**: `NotificationEvent.getMessage(Lang)`/`getPlainMessage(Lang)`/`buildCommentedCodeMessage()` 대응. Play `Messages.get(lang,...)`를 Spring `MessageSource.getMessage(key, args, default, locale)`로 옮기되, yona가 legacy와 다르게 저장하는 이벤트 타입마다 실제 데이터에 맞춰 분기를 조정했다(각 분기 위에 근거 주석): `ISSUE_STATE_CHANGED`는 `State.toString()`(대문자 enum 이름)을 비교, `ISSUE_MILESTONE_CHANGED`는 ID 조회 없이 저장된 제목 문자열을 그대로 사용, `ISSUE_LABEL_CHANGED`는 loginId가 아니라 변경된 라벨 이름 목록을 인자로 사용, `RESOURCE_DELETED`/`PULL_REQUEST_MERGED`는 loginId/코드워드 조회 실패 시 `MessageSource`의 default 인자로 원본 값을 그대로 보여줌, `MEMBER_ENROLL_ACCEPT`/`ORGANIZATION_MEMBER_ENROLL_ACCEPT`는 legacy의 `getMessage()` switch가 애초에 이 두 타입을 다루지 않고 `default:` 분기(`EventType.getDescr()` = 요청 locale과 무관하게 항상 사이트 기본 로케일)로 빠지는 것까지 그대로 재현. `NEW_REVIEW_COMMENT`의 `buildCommentedCodeMessage()`(코드 diff hunk를 인용구로 붙이는 로직)는 yona에 이미 존재하는 `FileDiff`/`Hunk`/`CodeRange`/`RepositoryService` 인프라를 그대로 활용해 완전히 포팅했다 — 다만 이 이벤트 타입 자체를 만드는 곳이 없어([[tickets/p1-50|P1-50]]) 아직 실사용 경로는 없다.
  - **`NotificationUrlResolver.kt`(신규)**: `utils/RouteUtil.java`(리소스별 URL 리버스) + `NotificationEvent.getUrlToView()`/`getProject()` 대응. Play 라우트 리버스가 없어 yona 컨트롤러의 실제 `@GetMapping` 경로를 문자열로 직접 구성. `CommentThread.urlToContainer()`의 "outdated diff의 특정 커밋으로 링크"(`specificChange`/`isOutdated`) 세부 분기는 PR/커밋 페이지로 링크하는 것까지만 재현하고 생략 — 코드리뷰 화면 내 앵커 정밀도에 관한 UI 라우팅 미세조정이라 기능 누락으로 보지 않았다. `NEW_COMMIT`은 `resourceId`가 커밋 SHA뿐이라 프로젝트를 되짚을 수 없는 기존 아키텍처 한계([[tickets/p1-25|P1-25]]/46에서 이미 확인됨)를 그대로 반영해 `getProject()==null`일 때의 legacy 동작(null 반환)과 일치시켰다.
  - **`NotificationMailRenderer.kt`/`NotificationMailBodyProcessor.kt`(신규)**: `views/common/notificationMail.scala.html` + `NotificationMail.handleLinks()`/`handleImages()`/`removeHeadAnchor()` 대응. 렌더링 시점엔 이미 수신자별 locale이 확정돼 있어(언어별로 미리 나뉜 뒤 호출) Thymeleaf 템플릿 없이 DiffUtil/HistoryUtil과 같은 방식으로 문자열을 직접 구성. 상대경로 링크를 `yona.base-url` 기준 절대경로로 바꾸고, `application.noreferrer` 설정이 켜져 있고 외부 호스트로 가는 링크에만 `rel=noreferrer`를 붙이며, 이미지에 `max-width` 스타일 + 새 탭 링크로 감싸는 것까지 원본 그대로.
  - **`MailService`/`MailServiceImpl` 확장**: `NotificationMail.sendMail()`/`EventEmail` 대응. 다중 To/Bcc, Reply-To, HTML+텍스트 dual body(`multipart/alternative`), 발신자 표시 이름(`event.getSender().name`), 이벤트 발생 시각을 `Date` 헤더로 지정하는 `sendNotificationMail()`을 신설. **버그를 하나 찾아 고쳤다**: 처음엔 `MimeMessageHelper` 구성 후 `message.setHeader("Message-ID", ...)`로 직접 지정하면 유지될 거라 가정했는데, 테스트로 실제 `saveChanges()`를 태워보니 `jakarta.mail.internet.MimeMessage.updateHeaders()`가 Message-ID 존재 여부와 무관하게 `updateMessageID()`를 항상 호출해 새 값으로 덮어썼다 — 그래서 legacy `EventEmail`처럼 `MimeMessage`를 서브클래싱해 `updateMessageID()`를 오버라이드하는 방식(`EventNotificationMimeMessage`)으로 다시 고쳤다.
  - **`NotificationMailDigestScheduler.kt`(신규)**: `NotificationMail.startSchedule()`/`sendMail()`/`sendNotification()` 대응. `@Scheduled(initialDelayString/fixedDelayString = yona.notification.bymail.*)`로 지연시간(`delay-ms`, 기본 180초)이 지난 `NotificationMail`을 큐에서 꺼내 삭제하고, `NotificationEventMerger`로 병합한 뒤, `resourceExists()`(리소스별 `existsById`)를 통과한 이벤트만 발송한다. 수신자 정리(비활성 사용자 제외, `allowed-domains` 설정 시 `EmailDomainValidator` 재사용해 도메인 제한), `recipient-limit`+`hide-address` 조합에 따른 To/Bcc 분할(수신자 숨김이면 To=사이트 기본 주소·Bcc=실제 수신자, 아니면 반대), `getPreferredLanguage()` 기준 언어별 그룹핑 + `Lists.partition` 대응 청크 분할까지 원본 그대로. Reply-To는 [[tickets/p1-28|P1-28]]이 프로젝트 단위로 축약해뒀던 것을 이번에 리소스 상세 단위(`owner/project/<resourceType>/<resourceId>`)로 완성했다 — IncomingMailProcessingService([[tickets/p1-32|P1-32]])의 detail 파싱과 정확히 짝을 이룬다. Message-ID/References는 `Resource.getMessageId()`의 결정론적 포맷(`<resourceType/resourceId@hostname>`)을 그대로 계산하되(별도 저장 불필요), 현재 실제로 발생하는 이벤트 중 컨테이너를 갖는 게 `ISSUE_COMMENT`/`NONISSUE_COMMENT`뿐이라([[tickets/p1-50|P1-50]] 참고) References는 그 범위까지만 채운다.
  - **`NotificationCleanupScheduler.kt`(신규)**: `NotificationEvent.scheduleDeleteOldNotifications()` 대응. `yona.notification.bymail.keep-days`(기본 -1, legacy `KEEP_TIME_IN_DAYS` 기본값과 동일하게 비활성)가 양수일 때만 매일 오래된 `NotificationEvent`를 정리한다.
  - **생산자(producer) 재배선**: `NotificationEventRepository.save()` + `eventPublisher.publishEvent()`를 직접 호출하던 10개 파일(`PostingServiceImpl`, `CommentServiceImpl`, `IssueServiceImpl`, `IssueShareServiceImpl`, `OrganizationServiceImpl`, `ProjectUserServiceImpl`, `CodeReviewServiceImpl`, `PullRequestServiceImpl`, `PullRequestMergeEventListener`, `GitPostReceiveEventListener`)를 모두 `NotificationEventRecorder.record(event, skipWaypoint)`로 교체(`ApplicationEventPublisher.publishEvent`는 그대로 유지 — `WebhookNotificationEventListener`의 즉시 웹훅 발송이 다이제스트 지연에 영향받으면 안 되기 때문). `IssueShareServiceImpl`은 legacy가 `addWithoutSkipEvent()`를 쓰는 유일한 곳이라 `skipWaypoint=false`로 지정. 재배선 과정에서 발견한 기존 결손도 함께 고쳤다: (1) `IssueServiceImpl.updateIssue()`가 `ISSUE_BODY_CHANGED`를 `IssueEvent` 타임라인에만 기록하고 알림 메일은 전혀 보내지 않고 있었음(`PostingServiceImpl`의 `POSTING_BODY_CHANGED`와 대칭이 안 맞았음) — legacy `afterIssueBodyChanged()`(watcher 기반 수신자)를 참고해 알림 발행을 추가했다(다만 "본문에서 새로 @멘션된 사용자 추가" 세부 로직은 이 파일의 다른 이슈 이벤트들과 같은 watcher 기반으로 단순화). (2) `PullRequestServiceImpl.changeState()`가 PR 상태변경 수신자를 `contributor` 한 명으로 고정하고 있었음(legacy `getReceivers(sender, pullRequest)` = PR 감시자 - sender) — `watchService.findActualWatchers()`로 교체해 실제 PR 감시자에게도 알림이 가도록 고쳤다.
