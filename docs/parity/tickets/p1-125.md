  - **[[tickets/p1-126|P1-126]]** (`CommentServiceImpl.extractMentionedUsers()`): yona `NotificationEvent.getMentionedUsers()`(개별 사용자 + `findOrganizationMembers`(조직 이름 멘션 → 조직 멤버 전원) + `findProjectMembers`(`owner/project` 멘션 → 프로젝트 멤버 전원)) 로직을 이식. 정규식을 `User.LOGIN_ID_PATTERN_ALLOW_FORWARD_SLASH`(`/` 허용) 기준으로 확장.
    - 구현 중 실제 버그 2건을 디버깅으로 발견/수정: (1) 문자 클래스 `[a-zA-Z0-9-/]`에서 `-`가 `0-9` 바로 뒤에 오면 Java 정규식 range 파싱이 모호해져 하이픈 포함 매칭이 깨짐 — `-`를 클래스 끝(`[a-zA-Z0-9/-]`)으로 옮겨 명확히 리터럴로 해석되게 정정(문자 집합 자체는 동일, 파싱 모호성만 제거). (2) 조직/프로젝트 멤버 조회를 엔티티의 in-memory 컬렉션(`org.organizationUsers` 등)으로 하면, 같은 트랜잭션 안에서 방금 저장한 멤버가 이미 초기화(비어있음)된 부모 컬렉션에 반영되지 않는 Hibernate 1차 캐시 함정에 걸림 — `organizationUserRepository.findByOrganizationId()`/`projectUserRepository.findByProjectId()`로 직접 조회하도록 변경.
    - 테스트: `CommentServiceSpec.kt` +2(조직 멘션 시 조직 멤버 전원 수신, `owner/project` 멘션 시 프로젝트 멤버 전원 수신) — 디버깅 과정에서 직접 `extractMentionedUsers()` 호출/`organizationUsers.size` 검증 등 임시 진단 코드를 넣었다가 근본 원인 확인 후 정리. 전체 7건 통과.
  - **[[tickets/p1-127|P1-127]]** (`IssueServiceImpl`/`PostingServiceImpl`/`PullRequestServiceImpl`): yona `NotificationEvent.forNewIssue/forNewPost`의 `getReceivers(item, except)`(watchers + `getMentionedUsers(body)`), `afterNewPullRequest`의 `getReceiversWithRelatedAuthors`(→`getDefaultReceivers` = watchers + `getMentionedUsers(body)`, 관련 커밋 작성자 자동 추가 부분은 범위 밖으로 별도 판단 없이 보류) 대응. 세 서비스 모두 신규 게시물 알림 발행 지점에 `commentService.extractMentionedUsers(body)`를 watchers와 합류.

    - 순환 의존성 확인: `CommentServiceImpl`은 Issue/Posting 리포지토리에만 의존하고 `IssueService`/`PostingService`/`PullRequestService`를 참조하지 않아, 세 서비스가 `CommentService`를 주입받아도 순환 없음(`CodeReviewServiceImpl`이 이미 동일 패턴으로 `CommentService`+`PullRequestService`를 함께 참조 중).

  - **P1-125** (`Mention.java` 인덱스 엔티티): 재조사 결과 이 엔티티는 yona에서 오직 "나를 멘션한 이슈" 검색 필터(`getMentioningIssueIds`) 용도로만 쓰이며(`Mention.update()` 호출부가 `AbstractPosting`/`Comment`의 save/update 훅 2곳뿐), yona에는 이미 동등한 기능이 `IssueRepository.findMentionedByState`(`LIKE '%@loginId%'` 텍스트 검색, `UserViewController.userIssues`의 `mentionId` 분기에서 사용 중)로 구현돼 있어 **직접 멘션에 한해서는 사용자 관측 가능한 기능이 이미 동등** — 인덱스 테이블을 새로 이식하는 대신 기존 대체 구현을 유지하기로 판단(구현 전략 차이로 간주, 완료 처리).
