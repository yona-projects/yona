# P3-63: 코드 파일 보기 화면에서 소스 내용 자체가 렌더링되지 않음 (Ace 에디터 미포팅의 부수 효과)

## 배경

legacy v1.6.1(`app/views/code/view.scala.html:127`)은 `$yobi.loadModule("code.Browser", {...})`로
`yobi.code.Browser.js`를 로드해, 폴더 트리를 AJAX로 지연 확장하고 파일을 클릭하면 Ace 에디터
(`ace.edit("showCode")`, `lib/ace/*`)로 문법강조된 소스를 보여줬다. 이 기능은 v1.6 시점부터
있었고 지금(legacy HEAD)까지 그대로 살아있다.

yona `src/main/resources/templates/code/view.html`(108~112행)에는 이미 다음 코멘트가 있다:

> legacy `.code-browse-wrap .list-wrap { display: none; }`는 legacy JS
> `$yobi.loadModule("code.Browser", ...)`의 `$(".list-wrap").show()`로 열리는 걸 전제로 한
> 규칙인데, yona는 이 SPA 트리 전개 JS 모듈을 포팅하지 않고 일반 페이지 이동 링크로
> 단순화했다.

즉 "AJAX 트리 확장을 포팅하지 않고 페이지 이동으로 단순화했다"는 것 자체는 과거에 이미 검토되고
문서화된 의도적 결정이다. 이번 조사는 그 단순화가 **부수적으로 더 큰 문제를 남겼는지** 확인하기
위해 진행했다.

## 현재 yona 상태 (격차 확정 — 예상보다 심각함)

`code/view.html`의 파일 뷰어 영역(288~294행):

```html
<div th:if="${markdownHtml == null}">
  <div id="codeVal" class="hidden" th:text="${fileInfo.get('data').asText()}">code</div>
  <pre id="showCode" class="code-wrap" th:data-mimetype="${fileInfo.get('mimeType').asText()}"></pre>
</div>
```

- 실제 파일 내용은 `#codeVal`에 서버가 정상적으로 채워 넣는다(`fileInfo.data`) — **하지만 이
  div에는 `class="hidden"`이 붙어있어 화면에 보이지 않는다.**
- 화면에 실제로 보이는 요소는 `#showCode`(`<pre>`)인데, **완전히 빈 채로 렌더링된다.**
  `#codeVal`의 내용을 `#showCode`로 복사하거나 Ace 에디터를 붙이는 코드는
  `service/yobi.code.Browser.js`(73행 `htElement.welShowCode = $("#showCode")`, 381행
  `_getEditor("showCode")`)에만 있는데, 이 파일은 앞서 확인한 대로 **어떤 yona 템플릿에서도
  로드되지 않는다**(grep 재확인 완료 — `code/view.html` 어디에도 `<script src>`나
  `$yobi.loadModule("code.Browser", ...)` 호출이 없음). 압축 번들(`yona-common.js`/
  `yona-layout.js`/`yona-lib.js`)에도 `showCode`/`codeVal` 관련 코드가 없음(grep 0건).
- **결론: 바이너리도 마크다운도 아닌 일반 텍스트/코드 파일을 코드 브라우저에서 열면, 파일
  내용이 사용자에게 전혀 보이지 않는다** (페이지 소스나 devtools로 `#codeVal`을 직접 봐야만
  내용을 알 수 있음). 이건 "Ace 문법강조가 없다"는 수준의 격차가 아니라 **핵심 기능(소스 보기)
  자체가 비어있는 화면으로 렌더링되는 버그**다.
- 이미지(binary + image/*)와 마크다운 파일(`markdownHtml != null`)은 각각 `#showImage`/
  `#codeVal.markdown-wrap`으로 정상 렌더링된다 — 이 버그는 "일반 텍스트/소스 코드 파일" 케이스에만
  해당한다.

## 원인

`code/view.html` 작성 시 legacy의 `#showCode`(빈 `<pre>`, JS가 채움)와 `#codeVal`(실제 데이터
보관용, `display:none` 대상)의 역할 분담을 그대로 마크업만 옮겨왔지만, 그 둘을 연결하던
`yobi.code.Browser.js`의 로딩 자체가 (SPA 트리 단순화 결정과 함께) 통째로 빠지면서, 연결
로직 없이 마크업만 남아 이런 상태가 된 것으로 보인다.

## 제안

이 티켓은 순수 조사 산출물이며 구현은 하지 않았다(사용자 지시로 백로그 등록만 완료). 착수 시
고려할 방향:

1. **최소 수정(권장 우선순위)**: Ace 에디터/AJAX 트리 확장 전체를 되살리지 않고도, `#codeVal`의
   `hidden` 클래스를 제거하거나 `#showCode`에 서버 렌더링 시점에 `th:text`로 파일 내용을 직접
   채워 넣는 것만으로 "내용이 안 보이는" 핵심 버그는 해소된다(문법강조 없이 plain text로라도
   보이게). highlight.js는 이미 다른 화면(마크다운 코드블록, PR diff)에서 쓰이고 있으니
   `.code-wrap`에 highlight.js를 붙이는 것도 저비용 개선책이 될 수 있다.
2. **완전 이식**: legacy와 동치로 Ace 에디터(`lib/ace/*`, 284개 파일 이미 vendoring돼 있음)를
   실제로 붙이고, `service/yobi.code.Browser.js`를 최소한 "파일 뷰어" 부분만이라도 재작성해
   로드한다. AJAX 트리 확장(SPA 폴더 탐색)까지 되살릴지는 별도 UX 결정 필요 — 현재의 "폴더
   클릭 시 페이지 이동" 방식이 오히려 더 단순하고 접근성 있게 동작한다는 반론도 가능해, 이
   부분만은 사용자 확인이 필요하다.
3. TDD로 "코드 파일을 보면 그 내용이 렌더링된 HTML 어딘가에 화면 표시 가능한 형태로 존재한다"는
   회귀 스펙을 먼저 세울 것(현재는 이 케이스에 대한 템플릿 렌더링 테스트 자체가 없을 가능성이
   높음 — 확인 필요).

## 해결 (2026-09-12)

제안 1(최소 수정)로 처리했다. AJAX 트리(폴더 클릭 시 SPA 전개/`hashchange`)는 범위 밖으로 유지한다
— 사용자가 Playwright로 직접 확인한 뒤 "폴더 클릭 시 페이지 이동" 현재 방식이 오류 없이 더
단순/접근성 있게 동작한다고 확정했다. Ace 에디터는 아래 2026-09-12 후속 작업에서 실제로
붙였다(더 이상 범위 밖이 아님).

- `code/view.html`의 파일 뷰어 마크업에서 숨겨진 `#codeVal`(`class="hidden"`) div를 제거하고,
  `#showCode` `<pre>` 안의 `<code>` 요소에 서버 렌더링 시점(`th:text`)으로 파일 내용을 직접
  채워 넣도록 바꿨다. 마크다운(`markdownHtml != null`)과 바이너리(이미지/일반 파일) 분기는
  전혀 건드리지 않았다 — 마크다운 분기는 여전히 자신만의 `id="codeVal"`(`.markdown-wrap`)을 쓴다.
- 기존 inline `<script>`의 `$(document).ready(...)` 블록에
  `hljs.highlightElement(document.querySelector("#showCode code"))` 호출을 추가해 문법강조를
  붙였다. `hljs`는 `site/layout.html`이 이미 전역으로 로드해두므로 추가 스크립트 로드는
  필요 없었다. `#showCode`가 없는 마크다운/바이너리 케이스에서는 `querySelector`가 `null`을
  반환하므로 `if (showCodeEl && ...)` 가드로 안전하게 건너뛴다.
- `#codeVal`을 참조하는 다른 템플릿/JS/테스트는 없었다(grep 재확인 완료) — 유일한 다른 참조는
  로드되지 않는 `service/yobi.code.Browser.js`(이번 범위 밖) 뿐이었다.
- TDD: `CodeViewSourceContentRenderingSpec`(실제 Git 저장소에 `.java` 파일을 커밋 후
  `code/view.html`을 렌더링하는 통합 스펙)을 RED(`#showCode`가 빈 문자열로 렌더링되어 실패)로
  먼저 작성하고, 위 수정으로 GREEN 전환을 확인했다. `CodeViewControllerSpec`,
  `CodeBrowserListWrapRenderingSpec`, `CodeSwallowedStyleRenderingSpec`, `CodeControllerSpec`,
  `CodeHistoryControllerSpec`, `CodeRangeRequestSpec` 등 관련 기존 스펙과 전체 회귀
  (`./gradlew test`)도 모두 통과를 확인했다.
- Playwright(headless Chromium)로 실제 개발 서버(`localhost:8080`)에 새 프로젝트를 만들고
  `.java`/`README.md`를 커밋해 코드 브라우저에서 열어, `.java` 파일은 `#showCode` 안에 내용이
  보이고 highlight.js(`code.hljs`)가 적용되며, `README.md`는 기존과 동일하게 마크다운으로
  렌더링되고, 두 경우 모두 devtools 콘솔 에러가 없음을 확인했다.

## 후속: 진짜 Ace 에디터 연결 (2026-09-12)

위 최소 수정은 hljs 문법강조를 "일단 내용이 보이게" 하는 폴백이었을 뿐, legacy
`service/yobi.code.Browser.js`가 쓰던 실제 Ace 에디터는 아직 붙어있지 않았다. 이번 작업으로 그
gap을 메웠다 — 범위는 여전히 "파일 내용 보기"로 한정하고, AJAX 트리/`hashchange` 폴더 탐색은
이번에도 이식하지 않았다(사용자가 확정한 범위 밖 결정 유지).

- `code/view.html`에 이 템플릿 전용으로 `<script src="/javascripts/lib/ace/ace.js">`를
  로드했다(전역 `site/layout.html`은 건드리지 않음). Ace 정적 리소스(`static/javascripts/lib/ace/`)는
  이미 저장소에 존재해서 별도 반입이 필요 없었고, 실제로 `basePath` 설정 없이도 모드/테마 파일이
  같은 디렉터리에서 정상적으로 비동기 로드됐다(Playwright로 콘솔 404 없음 확인).
- `#showCode` `<pre>`에 `th:data-path="${path}"`를 추가해, 서버가 이미 알고 있는 파일 경로를
  클라이언트에 넘기도록 했다(`th:data-mimetype`은 기존 그대로 유지).
- 기존 인라인 `$(document).ready(...)` 블록을 hljs 단독 호출에서 "Ace 우선, 실패 시 hljs 폴백"
  구조로 강화했다: `ace.edit("showCode")`로 legacy `_getEditor`(400~412행)와 동치인 에디터를
  만들고(`setTheme("ace/theme/clouds")`, `setHighlightActiveLine(false)`, `setReadOnly(true)`,
  `setFontSize(12)` — legacy `htVar.nFontSize` 기본값, `setShowPrintMargin(false)`), legacy
  `_initCodeView`(369~394행)와 동치로 `htVar.rxSub`(`text/x-(.+)-source` mimetype 매칭)를 먼저
  시도하고 실패하면 `_getEditorModeByPath`/`ext2mode`(414~480행)의 확장자 → 모드 매핑 테이블을
  그대로 포팅해 계산한 모드로 `session.setMode("ace/mode/" + sMode)` 후 `session.setValue(...)`로
  원본 텍스트를 주입한다. `ace.edit()`가 컨테이너 내용을 지우기 전에 `textContent`를 먼저 읽어
  순서 문제를 피했다. `typeof ace === "undefined"`인 경우에는 기존 `hljs.highlightElement(...)`
  폴백이 그대로 실행된다(완전 대체가 아니라 이중 안전장치로 유지).
- TDD: 새 스펙 `CodeViewAceEditorRenderingSpec`(RED→GREEN)을 추가해 `.java` 파일 렌더링 응답에
  `<script src="/javascripts/lib/ace/ace.js">`, `ace.edit("showCode")`, `ext2mode`의 `"java": ["java"]`
  매핑 항목, `data-path="Sample.java"`, hljs 폴백 가드가 전부 포함돼 있는지 검증한다. 구현 전
  RED(스크립트/호출 부재로 실패) 확인 후, 위 구현으로 GREEN 전환을 확인했다.
  `CodeViewSourceContentRenderingSpec`/`CodeViewControllerSpec`/`CodeBrowserListWrapRenderingSpec`/
  `CodeSwallowedStyleRenderingSpec`/`CodeControllerSpec`/`CodeHistoryControllerSpec`/
  `CodeRangeRequestSpec` 등 관련 기존 스펙과 전체 회귀(`./gradlew test`, exit code 0)도 모두
  통과를 확인했다.
- Playwright(headless Chromium, 기존 dev DB 컨테이너 `yona-dev-mariadb-23306` 재사용, 다른
  컨테이너는 건드리지 않음)로 실제 개발 서버(재기동 후 새 템플릿 반영 확인)에서, 기존 검증용
  프로젝트(`admin/p363verify`)의 `Sample.java`를 열어 `#showCode`에 `ace_editor`/`ace-clouds`
  클래스, 줄번호 거터(gutter), `ace_keyword` 토큰(`public`/`class`/`void`에 실제 Java 문법강조
  적용)이 실제로 렌더링됨을 확인했고 devtools 콘솔 에러가 없음을 확인했다. `README.md`는
  회귀 없이 기존과 동일하게 `.markdown-wrap`으로 렌더링되고 `#showCode` 자체가 나타나지 않음을
  확인했다. 바이너리 파일(임시로 추가했다가 검증 후 즉시 되돌린 `tiny.png`/`sample.bin`) 경로도
  `#showCode`/Ace 관련 콘솔 에러 없이 기존 `#showImage`/`#showFile` 분기 그대로 동작함을 확인했다.
