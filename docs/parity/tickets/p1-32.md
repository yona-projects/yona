## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-32**: 수신 주소 detail이 `owner/project`까지만 해석되고 그 뒤 세그먼트(`issue_post/5` 같은 구체적 리소스 경로)는 조용히 무시되던 문제 수정(yona `EmailHandler.getResourceFromDetail()`/`Resource.findByPath()` 대응). 이제 `yona+owner/project/issue_post/50@example.com`처럼 구체적인 리소스를 직접 지정하면, `In-Reply-To`/`References` 헤더 없이 새로 작성한 메일이라도 그 리소스에 바로 댓글이 달린다.
  - `resolveDirectResource(target: EmailAddressDetail)` 신규 추가 — detail을 `/`로 나눠 4개 이상의 세그먼트가 있으면 3번째를 `ResourceType.getValue()`(yona에 이미 이식돼 있던 enum, yona의 `resource()` 전체 문자열 — 예: `issue_post`, 짧은 `asPathSegment()` 형태인 `issue`가 아님)로, 4번째를 리소스 id로 해석해 `ResolvedThread`를 만든다. 리소스가 실제로 어느 프로젝트에 속하는지는 리소스 자체를 조회해서 확인하므로(`resolveResourceProject()` 재사용), 이메일 수신 주소의 `owner/project`와 실제 리소스의 프로젝트가 다르면 자연스럽게 무시되고 일반 새 이슈 생성으로 넘어간다(별도 검증 코드 불필요).
  - `process()`에서 `threads = resolveThreads(message) + targets.mapNotNull { resolveDirectResource(it) }`로, 메시지-ID 기반 스레드와 주소 기반 직접 지정 스레드를 합쳐(yona `getThreads()`가 두 신호를 하나의 Set으로 합치는 것과 동일한 취지) `processTarget()`의 기존 "프로젝트에 매칭되는 첫 스레드" 선택 로직이 그대로 재사용되게 했다.
  - 테스트: `IncomingMailProcessingServiceSpec.kt` +3(직접 지정한 이슈에 댓글 생성 확인, 지정한 리소스가 다른 프로젝트 소속이면 무시하고 새 이슈 생성 확인, 알 수 없는 리소스 타입 세그먼트는 무시하고 새 이슈 생성 확인) — 기존 17건 포함 총 20 tests.
  - 검증: `./gradlew test --tests "com.github.yonaprojects.yona.domain.mail.*" --tests "YonaApplicationTests"` 전체 통과, `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공.
