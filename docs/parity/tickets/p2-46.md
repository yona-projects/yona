## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-22 — P2-46**: 사용자가 "다 끝나면 exports() 자매 엔드포인트를 조사해줘. 그리고 진행해줘"로 명시적으로 재지시해 착수·완료. `ProjectApi.java:46-72 exports()` + 10개 헬퍼(`getProjectScope`/`getAssginees`/`getAuthors`/`composePosts`/`getResult`/`composeAuthorJson`/`composeAssigneeJson`/`composeMembersJson`/`composeLabelJson`/`getAllLabels`/`composePlainCommentsJson`/`getCommentNode`/`getMilestoneNode`) 전체를 Serena로 라인 단위 확인 후 `ProjectApiController.kt`에 `GET /api/projects/{owner}/{projectName}/exports`로 이식.
  - **권한 게이트**: legacy `@IsAllowed(Operation.DELETE)`(프로젝트 리소스 기본 해석) 대응 — `accessControl.isAllowed(user, project, Operation.DELETE)`(매니저 또는 조직관리자만 허용, [[tickets/p1-85|P1-85]] 이식 로직 재사용).
  - **최상위 필드**: `owner`/`projectName`/`projectDescription`/`projectVcs`/`projectScope`(enum 이름 그대로 PRIVATE/PUBLIC/PROTECTED라 `getProjectScope()`의 switch 불필요, 이미 동일한 문자열)/`projectCreatedDate`(레거시 전용 포맷 `"yyyy-MM-dd a hh:mm:ss Z", Locale.ENGLISH` — [[tickets/p2-45|P2-45]]의 `parseProjectCreatedDate()`와 짝을 이루는 포맷터 재사용)/`assignees`(프로젝트 담당가능자 목록, `AssigneeRepository.findByProjectId`)/`authors`(`Project.findAuthors()` 대응 — 이슈 작성자+게시글 작성자+이 프로젝트로 들어온 PR 기여자를 순서대로 합쳐 중복 제거, legacy `LinkedHashSet<User>`를 `LinkedHashMap<Long,User>`로 동일하게 아키텍처 번역)/`memberCount`/`members`(`role.name` 그대로, yona `Role` 엔티티가 이미 legacy와 동일한 `name` 필드를 가지고 있어 그대로 재사용)/`issueCount`/`postCount`/`milestoneCount`/`labels`(project 최상위 라벨 — `getAllLabels()` 대응, `isExclusive` 포함)/`issues`/`posts`/`milestones`.
  - **`composeAuthorJson`/`composeAssigneeJson`/`getAssginees`/`getAuthors` 4개 통합**: 넷 다 `{loginId,name,email}` 완전히 동일한 출력 형태를 만드는 순수 함수라(분기·로직 차이 없음) `composeUserJson()` 하나로 합침 — 이건 "동작 단순화"가 아니라 진짜 중복 코드 제거(출력이 100% 동일함을 확인 후 결정).
  - **`composeLabelJson`(이슈 내부 라벨, `isExclusive` 없음) vs `getAllLabels`(project 최상위 라벨, `isExclusive` 있음)는 별개 함수로 유지** — 필드 구성이 실제로 다른 legacy의 진짜 분기라 통합하지 않음(테스트로 두 형태가 실제로 다름을 명시적으로 검증).
  - **이슈/게시글 본문(`getResult`)**: `number`/`id`/`title`/`type`/`author`/`createdAt`/`updatedAt`(ISO 포맷 `"yyyy-MM-dd'T'HH:mm:ssZ"`, `JodaDateUtil.ISO_FORMAT` 대응, null이면 legacy처럼 빈 문자열)/`body`/`owner`/`projectName`은 이슈·게시글 공통. `ISSUE_POST`(이슈)만 추가로 `assignees`(담당자 있을 때만)/`state`(항상, enum 이름 그대로 대문자)/`labels`(비어있지 않을 때만, `isExclusive` 없는 형태)/`milestoneId`+`milestoneTitle`(마일스톤 있을 때만)/`dueDate`(있을 때만, projectCreatedDate와 같은 레거시 포맷)/`refUrl`(`NotificationUrlResolver.getUrl()` 재사용 — [[tickets/p1-132|P1-132]]에서 이미 확립된 "URL 계산 로직 재사용" 관례 그대로 따름)이 붙는다. 게시글(`BOARD_POST`)은 이 6개 필드가 legacy의 `if (type == ISSUE_POST)` 분기 밖이라 아예 나오지 않는다(테스트로 부재를 명시적으로 검증). `attachments`/`comments`는 비어있지 않을 때만 두 타입 공통으로 붙는다.
  - **댓글 트리(`composePlainCommentsJson`/`getCommentNode`)**: `IssueComment`/`PostingComment`가 `parentComment` 필드 타입이 서로 달라(자기 자신 타입만 부모가 될 수 있음, yona 공통 상위타입 `support.Comment`엔 이 필드가 없음) 제네릭으로 합칠 수 없어 `composeIssueCommentsJson`/`composePostingCommentsJson` 두 함수로 나눔(순수 아키텍처 차이, 트리 조립 2-pass 알고리즘 자체는 legacy와 동일). **의도적으로 재현하지 않은 legacy 버그**: legacy는 부모가 top-level 목록에 없는(2단계 이상 중첩된 답글) 경우 `commentMap.get(key)`가 null이 되어 그 자리에서 NPE가 나 `exports()` 전체가 500으로 죽는다 — yona는 이걸 그대로 재현하지 않고 조용히 건너뛴다(엔드포인트 전체를 무너뜨리는 명백한 결함이라 "의도적 축약"이 아니라 "버그 재현 거부"로 판단, 테스트로 이 케이스가 크래시 없이 넘어감을 명시적으로 검증).
  - **`Attachment` 직렬화**: legacy `toJson(attachments)`(Jackson 기본 POJO 직렬화)가 yona `Attachment` 엔티티와 필드명이 1:1로 일치(`id`/`name`/`hash`/`containerType`/`containerId`/`mimeType`/`size`/`createdDate`/`ownerLoginId`)해 그대로 재사용.
  - 테스트(TDD, 레드 확인 후 그린): `ProjectApiControllerSpec.kt`에 3 tests 신규 — 프로젝트 없으면 404 / 매니저·조직관리자가 아니면 403 / 매니저가 이슈(담당자+상태+라벨+마일스톤+마감일+refUrl+첨부+중첩답글 1건+고아답글로 크래시 안 남)·게시글(이슈 전용 필드 부재 확인)·멤버·프로젝트라벨(isExclusive 포함, 이슈 내부 라벨과 형태 다름 확인)·마일스톤·작성자(이슈+게시글+PR기여자 3명 순서·중복없음)·담당가능자를 모두 포함한 전체 JSON을 성공적으로 내보냄(다수의 세부 jsonPath 단언 포함).
