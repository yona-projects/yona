## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-22 — P2-45 (최초 보류 판단)**: `ProjectApi.java newProject()`(REST) 착수를 시도했으나, 이 엔드포인트가 단순 "프로젝트 생성 API"가 아니라 사이트관리자 전용 **프로젝트 export/import 데이터 마이그레이션 도구의 한쪽 절반**임을 코드로 확인하고 규모를 재평가해 이번 세션에서는 보류하기로 결정.
  - `newProject()`는 짝을 이루는 `exports()`(같은 파일 46-67행, 프로젝트를 JSON으로 직렬화)가 만든 JSON을 다시 프로젝트로 복원하는 용도 — `exports()` 자체가 yona에 전혀 없어 이 엔드포인트 하나만 만들면 실질적으로 짝 없는 반쪽짜리 기능이 된다.
  - `ProjectUser.assignRole(User.SITE_MANAGER_ID, ..., RoleType.SITEMANAGER)`(152행)에서 `SITE_MANAGER_ID`가 **하드코딩된 `1L`**(`User.java:64`, "DB의 첫 번째 유저가 사이트매니저"라는 legacy 전제)인데, 이 값을 실제 호출자(로그인한 사이트매니저)가 아니라 그대로 프로젝트 소유자/매니저로 지정하는 것은 yona 스키마에서 `id=1`이 사이트매니저라는 보장이 전혀 없어 그대로 이식하면 명백히 잘못된 동작이 되고, 그렇다고 임의로 "호출자를 매니저로" 바꾸면 legacy 동작을 바꾸는 아키텍처 판단이 필요함.
  - `addProjectMembers(json, project)`(190-210행)이 `members` 배열(email+role 문자열)을 파싱해 `MEMBER`/`MANAGER` 역할을 일괄 부여하는 로직까지 포함돼 있어, 이 하나의 엔드포인트에 프로젝트 생성+메뉴 설정 기본값+멤버 일괄 등록+커스텀 JSON 스키마 설계가 전부 얽혀 있다.
  - [[tickets/p1-27|P1-27]]과 동일한 기준(시간 대비 규모가 과도하게 큰 아키텍처 판단이 필요한 작업)으로 판단해 이번 세션에서는 시도만 하고 보류 — 착수하려면 최소한 (1) `exports()` 카운터파트를 함께 만들지 여부, (2) `SITE_MANAGER_ID` 하드코딩을 어떻게 대체할지에 대한 사용자 결정이 선행되어야 함.
  - 검증: 코드 변경 없음(조사 및 규모 평가만 수행).

- **2026-08-22 — P2-45 (사용자 지시로 재착수, 완료)**: 사용자가 "P2-45 진행해줘"로 명시적으로 재지시해 위 두 열린 질문을 해결하고 구현.
  - **`exports()` 카운터파트 분리 결정**: `newProject()`는 `exports()`가 만든 JSON을 소비하는 쪽일 뿐 `exports()` 자체를 호출하거나 그 존재에 기술적으로 의존하지 않는다(요청 바디 스키마만 문서 삼아 그대로 소비) — `exports()`는 이슈/게시글/댓글/마일스톤/라벨까지 직렬화하는 훨씬 큰 별도 기능(`composePosts`/`getResult`/`composePlainCommentsJson`/`getMilestoneNode`/`getAllLabels` 등 10개 가까운 헬퍼)이라 `newProject()`와 규모가 다르다고 판단, 별도 항목([[tickets/p2-46|P2-46]])으로 분리 등록하고 이번 항목은 `newProject()`에만 집중.
  - **`SITE_MANAGER_ID` 하드코딩 대체**: legacy `User.SITE_MANAGER_ID=1L`(`User.java:64`, "DB 1번 유저가 사이트매니저"라는 legacy 전제)은 yona에 대응하는 개념이 없음(yona는 `User.isSiteManager`/`UserState.SITE_ADMIN` 상태값으로 판정, ID 하드코딩 관례 자체가 없음) — 이 메서드는 호출 시점에 이미 `currentUser.isSiteManager`가 검증되므로, "API로 만든 프로젝트에 사이트 차원의 소유권 role을 남긴다"는 legacy 의도를 그대로 보존하면서 실제로 존재하는 대상(호출한 사이트매니저 본인)에게 `RoleType.SITEMANAGER` 역할을 부여하는 것으로 아키텍처 번역.
  - `web/ProjectApiController.kt` 신규 — `POST /api/projects/{owner}`(legacy 경로 `-_-api/v1/owners/:owner/projects`는 yona가 이미 통일해 쓰는 `/api/projects/...` 네임스페이스로 아키텍처 번역, `ProjectController.kt`의 기존 update/delete/transfer/fork 엔드포인트와 동일 컨벤션). `newProject()` 로직 그대로: (1) 사이트매니저 아니면 400 "User creation with api is allowed by Site admin only." (2) 동일 owner/projectName 존재 시 **HTTP 400에 바디 안 `status:409`**(legacy의 실제 불일치 동작 그대로, "정정" 안 함) (3) `isGlobalResourceCreatable` + owner가 기존 조직명이면 그 조직 admin만 허용([[tickets/p2-34|P2-34]]에서 이식된 함수 재사용) 아니면 403 (4) 프로젝트 생성(`projectScope`/`projectVcs`/`projectCreatedDate`/`organization` 연동, 메뉴 설정은 `Project` 엔티티 기본값이 이미 전부 true라 `saveMenuSettingsToDefault()` 별도 호출 불필요) (5) 위에서 정리한 대로 `SITEMANAGER` role 부여 (6) `repositoryService.getRepository(project).create()`로 실제 저장소 생성 (7) `members` 배열 파싱해 `MEMBER`/`MANAGER` 역할 일괄 부여(이메일로 찾은 사용자가 없으면 조용히 건너뜀, `role` 문자열이 `member`/`manager`가 아니면 로그만 남기고 건너뜀, legacy `equalsIgnoreCase` 그대로 대소문자 무시) (8) `createdProjectNode()` 형식(`id`/`owner`/`name`/`overview`/`vcs`)으로 201 응답.
  - `Posting.findREADMEPosting()`류의 `finder...findUnique()`(단일 결과 아니면 예외) 패턴은 `findByProjectAndReadme(...).firstOrNull()`로 아키텍처 번역(정상 케이스 동작은 동일, Ebean 특유의 방어적 예외까지는 재현 안 함) — 이번 항목이 아니라 이미 [[tickets/p2-42|P2-42]]에서 확립된 패턴 재사용.
  - `Project.cleanEnrolledUsers()`(멤버 추가 시 기존 가입신청 자동수락)는 신규 생성 프로젝트에서는 `enrolledUsers`가 구조적으로 항상 비어 있어(방금 막 생성돼 그 전에는 아무도 가입 신청을 할 수 없었음) 이 호출 지점에 한해 영구적으로 no-op이므로 이식하지 않음(레거시에 없는 동작 추가가 아니라, 레거시에서도 이 지점에서는 절대 발동 불가능한 코드라 제외 — 다른 프로젝트에 멤버를 추가하는 기존 경로가 있다면 그쪽은 이번 조사 범위 밖).
