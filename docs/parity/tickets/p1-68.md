## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-68**: PR 수정(`updatePullRequest`)에 브랜치(from/toBranch) 재할당·중복 PR 검사·이슈 참조 이벤트 재동기화를 원본 요나 그대로 이식.
  - **`PullRequestService.updatePullRequest()` 시그니처 확장**: 기존 `(pullRequestId, title, body)`에 `fromBranch: String, toBranch: String`을 추가(yona `updateWith()`가 title/body뿐 아니라 from/toBranch까지 한 번에 갱신하는 것과 동일). `PullRequestController`의 `UpdatePullRequestRequest`에는 `fromBranch`/`toBranch`를 **nullable(기본 null)**로 추가해 null이면 기존 브랜치를 그대로 유지하도록 컨트롤러에서 해석(`request.fromBranch ?: pullRequest.fromBranch`) — REST 클라이언트가 브랜치 필드를 생략해도 기존 title/body-only 수정 동작이 100% 그대로 유지되는 하위호환 설계(yona 서버 렌더링 폼은 항상 두 값을 모두 제출하므로 이 nullable 처리 자체가 축약은 아니고, REST API 경계에서의 합리적 설계).
  - **중복 PR 검사(`findDuplicatedPullRequest` 대응)**: `PullRequestRepository.findByFromBranchAndToBranchAndFromProjectAndToProjectAndState()` 신규 쿼리 메서드 추가. `updatePullRequest()`는 새 from/toBranch가 현재 값과 다를 때만(`hasSameBranchesWith()` 대응) 동일한 from/to 프로젝트+새 브랜치 조합의 **OPEN** PR이 이미 있는지 검사하고, 있으면 `DuplicatedPullRequestException`(신규, `@ResponseStatus(CONFLICT)`)을 던져 어떤 필드도 변경하지 않는다. yona는 컨트롤러에서 flash 메시지+수정 폼으로 리다이렉트하지만(서버 렌더링 UI 관심사), yona REST 계층에서는 그 "거부"라는 행동 자체를 409 Conflict로 정확히 재현했다(UI 표현 방식만 REST에 맞게 치환, 판단 로직은 완전히 동일).
  - **`updateWith()`의 이슈 참조 재동기화**: `deleteIssueReferenceEvents()`(yona `deleteIssueEvents()` 대응 — 이 PR이 이전에 남긴 `ISSUE_REFERRED_FROM_PULL_REQUEST` 이벤트를 `newValue=PR id`+`senderLoginId=contributor`+`eventType`으로 찾아 전부 삭제)를 필드 갱신 **전에**, `addIssueReferenceEvents()`(yona `addNewIssueEvents()` 대응 — 새 title+body를 `IssueReferenceParser`([[tickets/p1-06|P1-06]]/커밋 파싱용으로 이미 존재하던 순수 함수를 그대로 재사용)로 재스캔해 `toProject`에서 찾은 이슈마다 새 `IssueEvent` 생성)를 저장 **후에** 호출 — 브랜치 변경 여부와 무관하게 title/body만 바뀌어도 항상 수행되는 것까지 yona와 동일(`IssueEventRepository.findByNewValueAndSenderLoginIdAndEventType()` 신규 쿼리 메서드로 삭제 대상 조회).
  - `PullRequestServiceImpl` 생성자에 `IssueRepository`/`IssueEventRepository` 신규 주입(Spring이 관리하는 유일한 생성 지점이라 다른 수동 생성 코드 영향 없음).
  - 테스트: `PullRequestServiceSpec.kt`(통합, 실제 DB+JGit) +3(브랜치 재할당 성공/중복 브랜치 조합이면 예외+변경 없음/이슈 참조가 바뀌면 이전 이슈의 이벤트는 삭제되고 새 이슈에 이벤트 생성), `PullRequestControllerSpec.kt` +2(요청에 fromBranch/toBranch 포함 시 서비스로 그대로 전달+응답에 반영/중복이면 409 Conflict) — 기존 title/body-only 수정 테스트는 새 시그니처에 맞춰 스텁 갱신(회귀 없음, 브랜치 미변경 검증도 추가).
  - 검증: `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공, `PullRequestServiceSpec` 21 tests 전체 통과, `PullRequestControllerSpec` 13 tests 전체 통과.
