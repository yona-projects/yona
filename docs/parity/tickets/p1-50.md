## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-50**: 코드리뷰 댓글 작성/커밋 댓글 작성/리뷰 스레드 열기·닫기가 `NotificationEvent`를 전혀 만들지 않아 알림이 안 가던 문제 수정. [[tickets/p1-27|P1-27]] 작업 중 발견했고, 사용자가 "레거시 요나의 동작에 100% 일치해야 함"이라고 명시적으로 지시해 legacy의 3개 producer(`forNewComment`/`forNewCommitComment`/`forNewSVNCommitComment`/`afterStateChanged(ThreadState,...)`)를 하나하나 확인해 정확히 재현했다.
  - **`CodeReviewServiceImpl.createReviewComment()`에 `publishNewReviewCommentNotification()` 추가**: legacy가 PR 위 댓글(`forNewComment`)과 PR 밖 커밋 위 댓글(`forNewCommitComment`)을 서로 다른 메서드로 나눠둔 것을 `thread.pullRequest`의 null 여부로 한 함수 안에서 분기 처리. 두 경우 모두 이벤트 타입은 `NEW_REVIEW_COMMENT`, 리소스는 `REVIEW_COMMENT`(댓글 자신)다. 수신자는 댓글 내용에서 추출한 멘션 대상(`CommentService.extractMentionedUsers()`를 그대로 재사용 — legacy `getMentionedUsers()`와 동일한 정규식 규칙) + PR 위면 PR 감시자(`watchService.findActualWatchers(PULL_REQUEST)`), PR 밖이면 커밋 단위 감시자(`getCommitWatchers()`, 아래 참고) — 여기서 작성자 본인만 제외. legacy는 신규 스레드든 기존 스레드에 대한 답글이든 구분 없이 항상 이 알림을 발행하므로(`PullRequestApp.newComment`/`CodeHistoryApp.newCommitComment` 컨트롤러 확인) 조건 없이 매번 호출한다.
  - **`CodeReviewServiceImpl.createCommitComment()`에 `publishNewCommitCommentNotification()` 추가**: legacy `forNewSVNCommitComment`가 `ReviewComment`가 아니라 `CommitComment`(SVN 전용 모델) 기반이라 이벤트 타입이 `NEW_REVIEW_COMMENT`가 아니라 **`NEW_COMMENT`**인 것까지 그대로 재현 — 처음엔 직관적으로 `NEW_REVIEW_COMMENT`로 오해하기 쉬운 부분이라 legacy 소스를 직접 대조해 확인했다. 리소스 타입은 `COMMIT_COMMENT`.
  - **`CodeReviewServiceImpl.updateThreadState()`에 `publishThreadStateChangedNotification()` 추가**: legacy `afterStateChanged(CommentThread.ThreadState oldState, CommentThread thread)` 대응. 상태 변화가 없으면(이미 같은 상태로 재요청) 조기 반환하는 가드를 추가(legacy에는 명시적 가드가 없지만 IssueServiceImpl/PullRequestServiceImpl의 다른 상태변경 메서드들과 동일한 이 코드베이스의 관례를 따름 — 상태가 실제로 안 바뀌면 알림도 의미가 없음). PR 위 스레드면 PR 감시자, PR 밖이면 커밋 단위 감시자(`getCommitWatchers()`)에서 상태를 바꾼 본인을 제외. `oldValue`/`newValue`는 `ThreadState.name()`(OPEN/CLOSED) 그대로 — [[tickets/p1-27|P1-27]]에서 이미 완성해둔 `NotificationMessageResolver`의 `REVIEW_THREAD_STATE_CHANGED` 분기가 정확히 이 포맷을 기대한다.
  - **커밋 단위 감시자(`commit.getWatchers(project)`) 정확히 구현**: 처음에는 yona에 "커밋을 감시한다"는 UI가 없다는 이유로 프로젝트 감시자로 단순화했으나, 사용자가 "의도적 단순화는 하면 안 됨"이라고 명확히 반려해 legacy `playRepository/Commit.java`를 다시 읽고 정확히 재구현했다. legacy `getWatchers()`는 (1) 커밋 작성자(게스트/익명 제외), (2) 이미 이 커밋에 댓글을 남긴 모든 사용자(git이면 `CommentThread`+`ReviewComment`, svn이면 `CommitComment`)를 기본 감시자로 모은 뒤, `Commit.asResource(project)`(`resourceType=COMMIT`, `resourceId="{project.id}:{commitId}"` 합성 키)를 대상으로 한 `Watch.findActualWatchers()`에 넘긴다 — 즉 "이 커밋 전용 Watch 엔티티"가 실제로 존재하는 완전한 메커니즘이었다. `getCommitWatchers(project, commitId, eventType)` 헬퍼로 이 셋을 그대로 재현: 커밋 작성자는 `repositoryService.getRepository(project).getCommit(commitId)?.getAuthor()`(게스트 제외, `createReviewComment`의 기존 codeAuthor 조회와 동일한 방어적 try/catch), 기존 댓글 작성자는 이미 존재하던 리포지토리 메서드 `CommentThreadRepository.findByProjectAndCommitIdAndPullRequestIsNullOrderByCreatedDateDesc`/`CommitCommentRepository.findByProjectAndCommitIdOrderByCreatedDateAsc`로 조회, 명시적 감시자는 `watchService.findActualWatchers(resourceType=COMMIT, resourceId="{projectId}:{commitId}")`로 합산. **정정(2026-08-23, 백로그 재감사로 발견)**: 이 시점에는 UI에 "이 커밋 감시" 버튼이 아직 없고, 사실 `WatchController`의 범용 `/watch`·`/unwatch` 엔드포인트도 `checkWatchPermission()`의 `when`에 `ResourceType.COMMIT` 케이스가 없어 실제로는 항상 400을 반환했다(당시 "완전히 동작한다"는 기록은 과장이었음 — `findActualWatchers()`/`getCommitWatchers()`는 알림 수신자 "계산"에만 쓰이는 별도 경로라 이 permission 게이트를 거치지 않아 그때는 발견되지 않았다). P-템플릿 그룹10 #161 재감사(TASK-0259 후속)에서 발견해 `checkWatchPermission()`에 COMMIT 케이스를 추가하고 `code/diff.html`/`code/svnDiff.html`에 실제 감시 버튼을 배선해 완료 — 상세는 `docs/TEMPLATE_BACKLOG.md` 그룹10 진행 로그 참고.
