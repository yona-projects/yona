# P3-15: PR 승인/변경요청(리뷰 판정) 워크플로 추가 — GitHub의 Approve/Request changes에 대응

## 원본 표 정보

- **우선순위 구분**: P3
- **상태(원본 체크박스)**: `[x]`
- **비고(원문)**: **2026-09-06 사용자 제안, [[tickets/p3-04|P3-04]](브랜치 보호) 작업 중 스파이크로 발견된 갭 — 2026-09-07 TDD로 전체 구현 완료(상세: `docs/yona-wiki/plans/p3-15-pr-approval-workflow.md` 완료 로그).** 설계 결정(코디네이터 사전 확정, 전부 채택): (1) `CommentThread`에 얹지 않고 PR 단위 별도 엔티티 `domain/pullrequest/PullRequestReview.kt`(pullRequest, reviewer, state=APPROVE/REQUEST_CHANGES/COMMENT, body, createdDate) 신설 — 코드 라인별 리뷰 스레드(`CommentThread`)와 "PR 전체 댓글"을 이미 구분해온 기존 구조와 일관됨. (2) 재판정 시 매번 새 로우 추가(update 아님, 이력 전부 보존·타임라인 표시), 정책 판단(`require_approvals`)에는 리뷰어별 가장 최근 APPROVE/REQUEST_CHANGES 판정만 유효(COMMENT 전용 판정은 제외 — GitHub도 Comment 리뷰는 기존 승인 상태를 바꾸지 않음). (3) 자기 자신의 PR은 APPROVE/REQUEST_CHANGES 불가(`SelfReviewException`, 400) — COMMENT는 허용(GitHub 방식). (4) stale 승인 자동 무효화 미구현(GitHub 기본값과 동일, 과도한 설계 방지). API: `POST/GET /api/v1/projects/{owner}/{project}/pull-requests/{number}/reviews`([[tickets/p3-02|P3-02]] REST 컨벤션 그대로, 기존 "pull-requests" 세그먼트 매핑을 그대로 재사용해 별도 PAT 스코프 배선 불필요 — `PULL_REQUESTS` 그룹으로 이미 인가됨), `web/PullRequestController.kt`(`submitReview`/`getReviews`, `checkWritePermission` — addReviewer와 동일 권한 수준)와 `web/PullRequestApiController.kt` 어댑터. `require_approvals` 연결: `PullRequestServiceImpl.merge()`에 `checkApprovalsForMerge()` 추가 — REQUEST_CHANGES가 하나라도 최신 판정으로 남아있으면 승인 개수와 무관하게 무조건 거부, 그렇지 않으면 APPROVE 개수가 `requireApprovals` 미만이면 거부(둘 다 `admins_can_bypass` 적용) — 이로써 [[p3-04-branch-protection]]의 "필드만 존재, 항상 통과" 갭이 해소됨([[tickets/p3-04|P3-04]] 문서 4라운드 완료 로그 참고). UI: `pullrequest/partial_info.html`(승인/변경요청 요약 뱃지 + 리뷰어 아바타별 초록 체크/빨간 X)과 `pullrequest/view.html`(리뷰 이력 목록 + Approve/Request changes/Comment 제출 폼, 자기 PR에는 Approve/Request changes 버튼 숨김)에 GitHub PR 페이지 관례 그대로 추가. CLI: `yona-cli`의 `pr review`에 `--approve`/`--request-changes`/`--comment`(+`--body`) 플래그 추가(`gh pr review` 관례 그대로, 기존 "플래그 없이 호출 시 자기등록" 동작과 `--remove`는 그대로 유지, 서로 상호배타). 검증: `PullRequestServiceSpec.kt` "5-3. PullRequestReview" describe (서비스 단위 + require_approvals 연결 통합테스트), `PullRequestControllerSpec.kt`/`PullRequestApiControllerSpec.kt`(REST 권한/자기승인 거부/404), `PullRequestReviewTemplateRenderingSpec.kt`(실제 Thymeleaf 렌더링), `ApiTokenScopedIssueAndPullRequestSubpathAuthorizationIntegrationSpec.kt`(PAT 스코프), `yona-cli`의 `cmd/pr_test.go`/`internal/api/pr_test.go` — 전부 GREEN. `./gradlew test` 전체 스위트는 이 계획이 만들거나 건드린 클래스 전부(단독/조합 실행) GREEN 확인, 전체 스위트 동시 실행 시 무관한 다수 클래스에서 공유 MariaDB 테스트 DB 경합("Table ... doesn't exist" 등, 기존에 이미 기록된 선례와 동일 패턴)으로 간헐 실패가 났으나 이 계획의 변경과 무관함을 교차검증함.
