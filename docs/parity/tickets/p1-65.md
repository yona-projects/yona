## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-65**: 이슈 초안(draft) 생성 → 발행(publish) 전환 플로우를 원본 요나 그대로 이식.
  - **발견**: yona `AbstractPosting.save()`는 `number == null`일 때마다(즉 매 최초 저장 시) `number = increaseNumber()`를 자동 호출하는 lifecycle hook이라, 초안이든 정식 이슈든 **생성 시점에 이미 번호가 배정**된다. 그런데도 `IssueApp.editIssue()`의 발행 분기(`:784-790`)는 `Project.increaseLastIssueNumber()`를 **무조건 다시** 호출해 발행 시점 기준으로 번호를 재배정한다 — "초안 작성 중 다른 이슈가 먼저 발행되면 번호 순서가 꼬이지 않도록" 발행 시점에 번호를 확정하는 설계. 이 발견이 `publishIssue()` 설계의 핵심 전제였다(재채번을 "최초 배정"이 아니라 "기존 배정을 교체"로 모델링).
  - **`IssueService.createIssue()`에 `isDraft: Boolean = false` 파라미터 추가**: `true`면 `issue.isDraft = true`, `issue.state = State.DRAFT`로 생성하고(`Issue.java:614-618` 대응) `publishNewIssueNotification()` 호출 자체를 건너뛴다(`:630-634` 대응, 초안은 알림 없음). 기본값 `false`는 기존 동작(즉시 `State.OPEN` + `NEW_ISSUE` 알림)과 100% 동일 — 회귀 없음.
  - **`IssueService.publishIssue(issueId, publisher): Issue` 신규**: `IssueApp.editIssue()`의 `if (issue.isPublish) {...}` 발행 분기(`:784-790`) + `AbstractPostingApp.editPosting()`의 history 초기화(`:106-112`)를 그대로 재현 — (1) `createdDate = now()` 재설정 (2) `state == DRAFT`일 때만(이미 OPEN이면 그대로) `state = OPEN`으로 전환 (3) `state`와 무관하게 **무조건** `project.lastIssueNumber + 1`로 재채번(생성 시 받았던 번호를 교체) (4) `isDraft = false` (5) `history = ""` (6) 기존 `publishNewIssueNotification()` 헬퍼를 재사용해 `NEW_ISSUE` 알림을 이 시점에 최초 발행. "이미 발행된(비-DRAFT) 이슈를 다시 publish 호출"해도 state 가드만 스킵될 뿐 재채번·알림은 legacy와 동일하게 그대로 수행되는 것까지 재현(legacy의 상태-무관 무조건 재채번 구조를 그대로 반영).
  - **`web/IssueController.kt`**: `CreateIssueRequest`에 `isDraft: Boolean = false` 필드 추가 후 `createIssue()`로 그대로 전달. `POST /api/projects/{projectId}/issues/{number}/publish` 신규 엔드포인트 추가 — 권한 검사는 `moveIssue`/`updateIssue`와 동일한 `isManagerOrAuthor()` 패턴 재사용.
  - 테스트: `IssueServiceSpec.kt` +5(초안 생성 시 DRAFT+알림 0건/기본값 미지정 시 기존 동작 회귀 가드/발행 시 번호·createdDate 변경+history 초기화+알림 1건을 발행 시점 기준으로 검증하기 위해 중간에 다른 이슈를 끼워 넣어 재채번이 "생성 시점"이 아니라 "발행 시점" 시퀀스를 반영함을 증명/이미 OPEN인 이슈를 발행해도 재채번은 그대로 수행/존재하지 않는 id 발행 시 예외), `IssueControllerSpec.kt` +3(초안 생성 요청이 서비스에 `isDraft=true`로 그대로 전달/작성자가 발행 성공/관리자·작성자 아니면 403+발행 미호출/존재하지 않는 이슈 404) — 기존 `POST .../issues` 테스트는 `createIssue()` 시그니처에 `isDraft` 파라미터가 추가돼 스텁을 `false`까지 명시하도록 갱신(회귀 없음).
