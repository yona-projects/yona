# P3-27: Mercurial 프로젝트의 Pull Request 병합이 동작하지 않음(JGit 하드코딩)

## 배경

P3-21/P3-22 실사용 검증 중 발견. `PullRequestServiceImpl`의 `attemptMerge`/`previewMerge`/
`merge`/`updateMerge`가 전부 `FileRepositoryBuilder().setGitDir(...)`로 JGit 저장소를 직접
여는 방식으로 하드코딩돼 있어, Mercurial 프로젝트에서는 PR 병합/충돌 계산이 동작하지 않는다.

- PR **생성**은 실패가 조용히 삼켜져 겉보기엔 성공한 것처럼 보인다.
- 관련 PR 재검사(`RelatedPullRequestMergeEvent`, push 시 자동 트리거 — P3-22에서 배선 완료)는
  실제로는 `NoRemoteRepositoryException`으로 실패한다(catch돼 로그만 남고 크래시하지 않음).

이건 P3-20~26과 달리 국소적인 버그 수정이 아니라 **PR diff/merge/conflict 계산 전체를
Mercurial 대응으로 새로 설계·구현해야 하는 대규모 작업**이다(hg4j 쪽에 병합/3-way-merge에
해당하는 API가 있는지부터 확인 필요) — 그래서 P3-20~26과 함께 처리하지 않고 별도 티켓으로
분리했다. 착수 여부는 사용자 확인 필요.

## 범위 (착수 시 확정 필요)

1. `PullRequestServiceImpl`에서 JGit에 하드코딩된 지점을 전수 조사(`FileRepositoryBuilder`
   검색).
2. hg4j에 3-way merge/병합 커밋 생성에 대응하는 API가 있는지 확인(`MergeCommand`류가
   있는지, 있다면 어느 수준까지 지원하는지).
3. 없다면 hg4j에도 신규 구현이 필요할 수 있음 — 규모가 크므로 별도 설계 논의 필요.
4. diff 계산 자체는 이미 P3-12(2026-09-09)에서 `HgRepository.getDiff()`로 해결됐으므로,
   남은 건 병합 커밋 생성/충돌 감지/미리보기 로직.

## 완료 로그

### 2026-09-09 — 설계 결정 (본 범위 착수, TDD)

hg4j에 이미 3-way merge 대응 API가 전부 갖춰져 있음을 확인(범위 항목 2/3은 hg4j 신규 구현
없이 해소됨):

- `TreeMergeCommand`(`setOurs`/`setTheirs`/`call()` → `isConflicted()`/`getConflicts()`/
  `getChangedFiles()` 등) — **작업 디렉터리를 전혀 건드리지 않는 순수 계산**(JGit
  `ThreeWayMerger`와 동등). 서버가 공유하는 프로젝트 저장소를 그대로 열어도 동시 요청 간
  경합이 없다 → `attemptMerge()`/`previewMerge()`/`updateMerge()`(내부적으로 `attemptMerge`
  재사용) 셋 다 이걸로 구현.
- `MergeCommand`(`setNodeId`/`call()` → `MergeResult`)는 실제 **작업 디렉터리(dirstate)를
  갱신**한다(real `hg merge`와 동일 — dirstate의 parent2를 세팅) → 여기에 `CommitCommand`를
  이으면 진짜 2-parent 머지 커밋이 나온다. 단, hg4j의 `add()`/`commit()` 포셀린은 실제 작업
  디렉터리 파일을 스캔하는 구조라 작업 디렉터리 없이는 커밋을 만들 수 없다 → `merge()`(실제
  확정 병합)만 `toProject` 저장소를 임시 디렉터리에 클론 → `update`(대상 브랜치) → `fetch`
  (소스 프로젝트에서) → `merge` → `commit` → `push`(임시 클론 → 원본 저장소) → 임시 디렉터리
  정리, 순서로 구현(Git의 "임시 ref로 fetch → 메모리상 병합 → ref 갱신 → 임시 ref 삭제"와
  동일한 "부수효과 격리" 목적).
- `MergeCommand`는 fast-forward 가능하면(가장 흔한 PR 형태) 2-parent 커밋을 만들지 않고
  working copy만 이동시킨다 — 기존 Git 구현(`createMergeCommitAndUpdateRef`)은 fast-forward
  여부와 무관하게 항상 명시적 머지 커밋을 만드는 정책(`--no-ff`와 동일)이라, `merge()` 성공
  후 dirstate의 parent2가 비어 있으면(=지름길을 탔다는 뜻) 커밋 직전에 부모를 수동으로
  보정해 이 정책을 Hg에서도 동일하게 재현했다.
- fromProject != toProject(포크 PR)일 때 hg4j `FetchCommand`는 원격에만 있는 bookmark를
  로컬에 그대로 새로 만든다 — Git의 임시 ref(확인 후 삭제, 목록에 노출 안 됨)와 동등한
  "겉보기 흔적 없음"을 재현하기 위해 fetch 직후 새로 생긴 bookmark만 찾아 즉시 삭제한다
  (`hgImportBranchWithoutBookmarkLeak`). 다만 실제 changeset 자체는 Mercurial이 append-only라
  되돌릴 방법이 없어 toProject 저장소에 영구히 남는다 — **알려진 한계**로 기록.

구현: `PullRequestServiceImpl.kt`에 `hgAttemptMerge`/`hgPreviewMerge`/`hgMerge`/
`hgComputeMerge`(공용 계산 core)/`hgResolveRevisionHex`/`hgDiffCommits`/
`hgImportBranchWithoutBookmarkLeak` 신설, 기존 4개 공개 메서드(`attemptMerge`/`previewMerge`/
`merge`/`updateMerge`)에 `if (playRepo is HgRepository) return hgXxx(...)` 분기 추가(Git
경로는 손대지 않음). `PullRequestMergeResult.gitCommits`/`MergePreviewResult.commits`/
`PullRequestCommit.bindPullRequestCommit()`/`suggestTitleAndBody()`의 타입을 `GitCommit`
전용에서 공통 상위 타입 `Commit`으로 넓혀 `HgCommit`도 같은 필드/함수를 그대로 재사용
(Git 쪽 동작 변화 없음 — 순수 컴파일타임 일반화).

TDD로 `PullRequestServiceSpec.kt`에 `describe("PullRequestService - Mercurial 프로젝트 PR
병합(P3-27)")` 블록 신설, 7개 시나리오(previewMerge 충돌없음/충돌있음, attemptMerge,
merge 성공(진짜 2-parent 커밋+bookmark 전진 확인), fast-forward 상황에서도 명시적 머지
커밋 생성 확인, 충돌 시 병합 안 됨(OPEN 상태·원래 bookmark 유지), 포크 PR(fromProject !=
toProject, bookmark 흔적 없음 확인)) — 전부 실제 임시 Mercurial 저장소를 만들어 실제 hg4j
API로 커밋/브랜치를 구성한 뒤 실제 병합 결과를 검증(mock 없음, 이 저장소의 확립된 "진짜
동작 검증" 관례 그대로 따름).

### 2026-09-09 — hg4j 쪽 전제 버그 발견 및 수정

범위 항목 2("hg4j에 3-way merge 대응 API가 있는지 확인")를 실사용 시나리오로 검증하던 중,
PR 병합이 실제로 만들어내는 push 패턴 — **원격에 이미 두 갈래(diverging heads)로 존재하는
병합 양쪽 부모에, 새로 만든 병합 커밋 하나만 push** — 에서 hg4j 자체의 changegroup 디코딩이
데이터를 손상시키는 버그를 발견해 수정했다. yona가 PR 병합 기능을 구현해도 이 버그가 막고
있으면 애초에 동작하지 않았을 전제 조건이라 먼저 처리.

- **원인**: `Revlog.appendChangeGroupEntry(entry, linkRev)`(2-인자 레거시 오버로드)가 cg1(암묵적
  델타베이스) 엔트리의 베이스를 "로컬 revlog에 지금 추가되는 위치가 0번째면 빈 콘텐츠, 아니면
  직전 리비전(rev-1)"이라는 위치 기반 근사치로 처리했다. 원격이 이미 갈라진 두 헤드를 갖고
  있는 상태에서 병합 커밋 하나만 담긴 changegroup을 받으면 "그룹의 첫 엔트리"가 로컬 revlog의
  마지막 리비전과 무관한데도 그걸 베이스로 델타를 풀어 콘텐츠가 깨지고, 이어지는 SHA-1
  node-hash 검증에서 거짓 "Security Integrity Error"로 실패한다.
- **수정(1차)**: `hg4j/src/main/java/io/github/search5/hg4j/storage/Revlog.java`에
  `appendChangeGroupEntry(entry, linkRev, previousGroupEntryContent)` 3-인자 오버로드를
  추가해, 그룹의 "첫" 엔트리는 `rev==0`(로컬 revlog가 비어있을 때만)일 때만 빈 콘텐츠를
  베이스로 삼도록 1차 수정했으나, **실제 yona `PullRequestServiceSpec`의 Mercurial merge()
  시나리오(대상 저장소가 비어있지 않은 상태에서 병합 커밋만 push)로 재현하니 여전히 동일한
  해시 불일치로 실패**함을 발견 — `rev==0` 조건이 "로컬 revlog가 비어있는가"만 볼 뿐, 그룹의
  첫 엔트리 자신의 실제 부모가 무엇인지는 여전히 보지 않고 있었다(1차 수정은 hg4j 자체
  `PushCommandTest`의 "빈 원격에 전체 히스토리를 한 번에 push"라는, 처음부터 선형이라
  `rev==0`과 실제 p1이 우연히 일치하는 케이스만 커버했다).
- **수정(최종)**: 그룹의 "첫" 엔트리는 `previousGroupEntryContent`가 없을 때 **엔트리 자신의
  실제 DAG 부모(`entry.p1`)를 로컬 인덱스에서 찾아(`findRevision`) 그 콘텐츠를 베이스로
  삼는다**(p1이 null/all-zero면 루트 커밋이므로 빈 콘텐츠) — 로컬 revlog가 비어있는지 여부와
  완전히 무관해졌다. 이후 엔트리는 그대로 직전에 디코딩한 콘텐츠를 베이스로 삼는다(PushCommand
  송신측 패킹 규칙과 대칭). 기존 2-인자 오버로드는 하위호환을 위해 그대로 남겨뒀다(레거시
  호출부 감사 결과 — 아래 참고).
  `hg4j/src/main/java/io/github/search5/hg4j/api/FetchCommand.java`의 changelog/manifest/filelog
  changegroup 적용 루프 3곳을 3-인자 오버로드로 전환하고, 그룹별로 `previous*EntryContent`를
  직접 추적하도록 수정.
- **레거시 2-인자 호출부 감사**: `HisteditCommand.java:448`은 `entry.deltabase`를 명시적으로
  all-zero로 세팅해 쓰는 별개 경로라 cg1 암묵적 베이스 분기를 타지 않음 — 이번 버그 영향권
  밖임을 확인. `RevlogTest`/`RevlogCoverageTest`의 2-인자 직접 호출들은 기존 단위테스트 목적
  그대로 유지(하위호환 동작 검증).
- **회귀 테스트**: `hg4j/src/test/java/io/github/search5/hg4j/api/PushCommandTest.java`에
  `pushingOnlyAMergeCommitWhoseBothParentsAlreadyExistOnRemoteDoesNotCorruptTheChangegroup`
  추가(원격이 이미 두 갈래 북마크를 가진 상태를 만들고, 병합 커밋만 push해 재현·검증).
- **테스트**: 관련 8개 클래스(PushCommandTest/FetchCommandTest/FetchCommandCoverageTest/
  RevlogTest/RevlogCoverageTest/HisteditCommandTest/MergeCommandTest/MergeCommandCoverageTest)
  총 150개 전부 통과. hg4j의 `test` 태스크가 `jacocoTestReport`→`interopTest`(Docker/native-hg
  기반, 느림)를 자동으로 딸려 실행한다는 점을 발견해(`-x interopTest -x jacocoTestReport`로
  회피) 검증. 전체 unit 스위트(`interopTest` 제외)는 9분+ 걸려 타임아웃으로 중단됐는데, 중단
  시점까지 관찰된 실패 2건(`TreeManifestWriteTest#realHgAcceptsHg4jWrittenTreemanifest`,
  `PerformanceBenchmarkTest#testHighLoadPerformanceBenchmark`)은 각각 격리 재실행 시 전자는
  통과(Docker 동시부하로 인한 우연한 실패로 판단), 후자는 SLA 2000ms 대비 2476ms로 근소 초과
  (본 세션에 Chrome/다른 Gradle 데몬 등이 동시에 떠 있던 시스템 부하 영향으로 판단) — 둘 다
  이번 변경(push/fetch/revlog changegroup 경로)과 무관한 영역이라 회귀로 보지 않음.
- **범위**: 이 항목은 hg4j(별도 리포, `../hg4j`)에서만 수정.
