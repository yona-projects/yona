## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-62**: PR 리뷰어 추가/제거의 `PullRequestService`/`CodeReviewService` 중복 구현을 하나로 통합.
  - 두 구현을 줄 단위로 대조한 결과 `NotificationEvent`(제목 포맷만 미묘히 다름 — 별도로 [[tickets/p1-63|P1-63]] 기록)/`receivers` 계산/`PullRequestEvent` 타임라인 기록까지 완전히 동일한 로직이 두 곳에 복제돼 있었음을 확인.
  - **`PullRequestServiceImpl.addReviewer/removeReviewer`를 유일한 구현으로 유지**(변경 없음) — `PullRequestServiceSpec`의 "최소 리뷰어 수 미달 시 머지 실패" 테스트가 이 경로에 의존하고 있어 회귀 위험이 없는 쪽을 그대로 남겼다.
  - **`CodeReviewServiceImpl.addReviewer/removeReviewer`를 위임으로 교체**: `PullRequestService`를 새 생성자 의존성으로 주입받아 `userRepository.findById(reviewerId)`로 `User`를 조회한 뒤 `pullRequestService.addReviewer/removeReviewer(pullRequestId, user)`를 그대로 호출 — 자체 `NotificationEvent`/`PullRequestEvent` 생성 로직 전부 제거. 그 결과 이제 쓰이지 않게 된 전용 헬퍼 `recordPullRequestEvent()`와, 그 헬퍼에서만 쓰이던 `pullRequestEventRepository` 생성자 의존성도 함께 제거(죽은 코드 정리).
  - `CodeReviewServiceImpl`이 `@Autowired constructor`로 Spring이 관리하는 빈이라(수동 생성자 호출 코드 없음) 생성자 시그니처 변경이 기존 테스트 배선을 깨뜨리지 않았다.
  - `PullRequestServiceImpl`은 `CodeReviewService`를 참조하지 않아 순환 의존성 위험이 없음을 확인 후 진행.
  - 테스트: 기존 `CodeReviewServiceSpec.kt`(리뷰어 추가/제거 관련 3 tests — `eventType`/`newValue`/`senderLoginId`/draft-time 병합·취소 검증, 제목 텍스트는 원래도 검증 대상이 아니었음)와 `PullRequestServiceSpec.kt`(리뷰어 추가/제거+최소 리뷰어 수 머지 검증)가 통합 후에도 수정 없이 그대로 통과 — 위임 방식이 관찰 가능한 동작을 그대로 보존함을 확인. 신규 테스트는 추가하지 않음(리팩터링으로 새 동작이 생기지 않았고, 기존 두 스펙이 이미 위임 경로 전체를 충분히 덮음).
  - 검증: `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공, `./gradlew test --tests "com.github.yonaprojects.yona.domain.pullrequest.CodeReviewServiceSpec" --tests "com.github.yonaprojects.yona.domain.pullrequest.PullRequestServiceSpec"` 43 tests 전체 통과.
