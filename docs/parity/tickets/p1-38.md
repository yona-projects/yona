## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-38**: `IssueEvent` 타임라인이 동일 사용자의 연속된 동일 타입 변경을 병합/상쇄하지 않아, 예를 들어 상태를 30초 안에 OPEN→CLOSED→REJECTED로 두 번 바꾸면 타임라인에 두 줄이 그대로 남던 문제 수정. yona `models/IssueEvent.java`의 `add()`/`addWithoutSkipEvent()` 알고리즘을 그대로 이식.
  - 신규 `domain/issue/IssueEventRecorder.kt`: `IssueEventRepository.recordWithDraftMerge(event, skipWaypoint)` 확장 함수 추가. 같은 이슈에서 30초 이내(`DRAFT_WINDOW`)에 생성된 마지막 이벤트가 같은 `eventType`+같은 `senderLoginId`이면: `skipWaypoint=true`(`add()`)일 때는 새 이벤트의 oldValue를 이전 이벤트의 oldValue로 덮어써 병합(A→B→C ⇒ A→C)한 뒤, 병합 결과 oldValue==newValue면(A→B→A) 아예 저장하지 않고 이전 이벤트도 삭제 — 완전 상쇄. `skipWaypoint=false`(`addWithoutSkipEvent()`)일 때는 중간 지점은 그대로 두고, 정확히 되돌리는 경우(새 이벤트의 oldValue/newValue가 이전 이벤트의 newValue/oldValue와 정확히 일치)만 둘 다 상쇄.
  - `IssueEventRepository`에 `findFirstByIssueAndCreatedAfterOrderByIdDesc(issue, created)` 파생 쿼리 추가(legacy의 `.gt("created", draftDate).orderBy("id desc").setMaxRows(1)`에 대응).
  - `IssueServiceImpl.recordIssueEvent()`에 `skipWaypoint: Boolean = true` 파라미터 추가 — 상태/담당자/마일스톤/본문([[tickets/p1-37|P1-37]]) 4종은 기존처럼 기본값(병합)을 쓰고, 라벨 변경([[tickets/p1-37|P1-37]])만 yona와 동일하게 `skipWaypoint = false`로 호출(라벨은 addWithoutSkipEvent 사용). `IssueShareServiceImpl`의 공유자 변경 기록([[tickets/p1-37|P1-37]])도 동일한 병합 정책(`skipWaypoint = true`)을 적용.
  - 테스트: `IssueServiceSpec.kt` +3 tests(연속 상태변경 병합/정확히 되돌리면 완전 상쇄/라벨 연속변경은 중간지점 보존+정확한 되돌림만 상쇄), `IssueShareServiceImplSpec.kt` 기존 테스트에 신규 `findFirstByIssueAndCreatedAfterOrderByIdDesc` 스텁 추가로 회귀 없이 통과.
  - 검증: `./gradlew compileKotlin compileTestKotlin`, `./gradlew test --tests "com.github.yonaprojects.yona.domain.issue.*" --tests "com.github.yonaprojects.yona.web.Issue*" --tests "com.github.yonaprojects.yona.YonaApplicationTests"` 모두 통과.
