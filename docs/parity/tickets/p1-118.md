## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P1-118**: `UserApi.java`의 site-manager 전용 API 4종(`newUser`/`newToken`/`users`/`updateUserState`)을 `UserController.kt`에 신규 이식.
  - 착수 전 `newToken`(아이디+비밀번호로 API 토큰 발급)이 로컬 비밀번호 인증을 전제로 하는데 yona 로그인은 OAuth2 전용으로 재설계된 것처럼 보여(BCrypt/PasswordEncoder 코드 전무) 아키텍처 차이로 판단해 사용자에게 처리 방향을 확인 — 이후 `AuthController.signup()`/`YonaAuthenticationProvider`를 재확인한 결과 **로컬 비밀번호 인증(Shiro Sha256Hash+salt+1024회 반복과 동일한 알고리즘)이 이미 완전히 구현돼 있었음**을 확인(오판이었음, 사용자 승인 후 진행 방향은 동일하게 유지: 전부 이식).
  - `newUser`(`POST /api/users`): 사이트관리자가 아니면 yona와 동일하게(403이 아닌) 400을 반환. `EmailDomainValidator.isAllowed()`(기존 [[tickets/p1-77|P1-77]]/서비스 인프라 재사용) → 이메일 중복 체크(409) 순으로 검증 후 생성. yona `createUserNode`가 `SecureRandomNumberGenerator`로 만든 불투명한 값을 다시 salt+해시하는 2단계 구조를 그대로 재현(결과적으로 어떤 비밀번호로도 로그인 불가능한 계정 — 별도 재설정 절차 전제, legacy와 동일).
  - `newToken`(`POST /api/users/token`): 아이디 또는 이메일로 사용자 조회(`findByLoginKey` 대응) → LOCKED/DELETED 상태면 401 "No valid user by id" → 비밀번호 검증은 새로 로직을 만들지 않고 `YonaAuthenticationProvider.authenticate()`에 위임(로그인 폼과 동일 경로 재사용, LDAP 활성화 환경도 자동 지원) → 실패 시 401 "No user by id and password" → 성공 시 `resetApiToken()`과 동일한 SHA-256 기반 토큰 발급.
  - `users`(`GET /api/admin/users`)/`updateUserState`(`PATCH /api/admin/users/{loginId}`): 둘 다 사이트관리자 전용(403), `updateUserState`는 `UserState.SITE_ADMIN`으로의 변경을 명시적으로 금지(legacy와 동일한 제약, 별도 절차 필요).
  - 라우팅은 yona의 `-_-api/v1/*`(Play 프레임워크 전용 라우팅 우회 접두사, 프레임워크 아티팩트라 이식 대상 아님)를 yona 기존 컨벤션인 `/api/*`로 적응하되, `/users` vs `/admin/users`라는 legacy의 의미 있는 경로 구분(일반 API vs 관리자 전용)은 그대로 보존.
  - `UserRepository`에 `findByState(state)` 추가.
  - 테스트: `UserControllerSpec.kt`에 12건 추가(newUser 3, newToken 4, users 2, updateUserState 3) — 신규 생성자 파라미터(`yonaAuthenticationProvider`/`allowedEmailDomains`/`requireAdminConfirm`) 반영. 25건 전부 통과.

### 2026-09-09 — 정정: "`-_-api/v1`은 프레임워크 아티팩트"라는 판단이 틀렸음을 확인, [[tickets/p3-37|P3-37]]로 원본 경로 복원

위 완료 로그의 "yona의 `-_-api/v1/*`는 Play 프레임워크 전용 라우팅 우회 접두사, 프레임워크
아티팩트라 이식 대상 아님" 판단은 **검증 없이 내린 잘못된 결론**이었다. 실제로는 v1.6(원본
legacy) `conf/routes`에 이 4종(newUser/newToken/users/updateUserState) 전부가
`-_-api/v1/*` 경로 그대로 존재하는 실제 API 계약이었고, 그 사실은 코드 한 줄만 확인해도 알 수
있었다. 게다가 이 판단이 내려진 일주일 뒤([[tickets/p2-54|P2-54]]~[[tickets/p2-61|P2-61]],
"legacy `-_-api/v1` Open API 전수 대조") 같은 프로젝트가 정반대 결론(이건 실제 외부 클라이언트
계약이니 경로까지 그대로 지켜야 한다)을 내려 35개 엔드포인트를 원본 경로 그대로 이식했는데도,
이 4종은 그 재검토 대상에서 빠진 채 방치돼 있었다.

사용자가 직접 이 모순을 지적해 재조사 → [[tickets/p3-37|P3-37]]로 원본 경로를 복원했다
(잘못됐던 `/api/*` 경로는 내부에서 쓰는 곳이 없음을 확인 후 완전히 제거 — 별칭이 아니라
치환). `StatisticsController.kt`의 `userStatistics()`도 같은
성격의 오판("legacy엔 통계 API가 존재한 적 없다")이 있었음을 함께 발견·수정했다(원본
`UserApi.statistics()`가 issue/posting/assignedIssue 등 동일한 집계를 반환하는 실제 대응
기능이었다).
