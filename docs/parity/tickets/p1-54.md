## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-54**: 이슈 라벨 유일성 정책이 yona `IssueLabel.exists()`(project+category+name 복합 유일성) 대신 project+name 단일 유일성으로 축약돼 있던 것을 사용자가 지적 — [[tickets/p1-12|P1-12]](라벨 복사) 완료 로그에 "이 코드베이스가 처음부터 택한 단순화"라고 명시돼 있던 부분을 legacy와 동일하게 되돌렸다.
  - `IssueLabelRepository`에 `findByProjectAndCategoryAndName(project, category, name)` 신규 추가, 더 이상 쓰이지 않게 된 `findByProjectAndName(project, name)`(라벨 단건 조회용, 카테고리 카테고리 리포지토리의 동명 메서드와는 별개)는 삭제.
  - `createLabel()`: 중복 검사를 `findByProjectAndName(project, name)`에서 `findByProjectAndCategoryAndName(project, category, name)`으로 교체 — 이제 같은 프로젝트라도 카테고리가 다르면 같은 이름의 라벨을 만들 수 있다(yona와 동일).
  - `copyLabels()`: yona `copyIssueLabelCategory()`가 카테고리를 먼저 찾거나 만든 뒤 `copyIssueLabel().exists()`로 중복을 판단하는 순서를 그대로 따르도록 재배열 — 기존엔 라벨 이름 중복 검사를 카테고리 해석보다 먼저 했는데(순서가 결과에 영향은 없었지만 yona와 다른 순서였음), 이제 카테고리를 먼저 정하고 그 카테고리 기준으로 중복을 판단한다.
  - `updateLabel()`/`updateCategory()`는 원래도 이름 중복 검사를 안 하거나(라벨) 카테고리 단위 검사(카테고리)라 이번 변경과 무관 — 손대지 않음.
  - 테스트: `IssueLabelServiceImplSpec.kt` — `createLabel` describe 블록 신규 2 tests(카테고리가 다르면 같은 이름도 신규 생성/같은 프로젝트+카테고리+이름이면 재사용), 기존 `copyLabels` 3 tests를 새 호출 순서·복합 키에 맞게 갱신(레드 확인 후 구현: `findByProjectAndCategoryAndName` 미해결 참조로 컴파일 실패). `IssueLabelControllerSpec.kt`는 서비스가 mock이라 영향 없음(기존 13 tests 그대로 통과). 커버리지: `createLabel`/`copyLabels` 둘 다 LINE 100%.
  - 검증: `./gradlew test --tests "com.github.yonaprojects.yona.domain.issue.*" --tests "com.github.yonaprojects.yona.web.IssueLabel*" --tests "com.github.yonaprojects.yona.YonaApplicationTests"` 전체 통과, 전체 스위트 `./gradlew test`(744 tests, 1 failed — `DataBackupServiceIntegrationSpec`, 이전부터 기록된 것과 동일한 환경 이슈이며 이번 변경과 무관), `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공.
