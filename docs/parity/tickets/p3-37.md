# P3-37: `UserApi.java` 이식 4종(+통계 1종)이 `-_-api/v1` 원본 경로를 안 지킨 판단 오류 수정

## 배경

[[tickets/p1-118|P1-118]](2026-08-21)가 `UserApi.newUser`/`newToken`/`users`/`updateUserState`
4종을 이식하면서 "yona의 `-_-api/v1/*`는 Play 프레임워크 전용 라우팅 우회 접두사, 프레임워크
아티팩트라 이식 대상 아님"이라 판단해 `/api/*`로만 배치했다. 이 판단은 **검증 없이 내려진 오판**이었다
— v1.6(원본 legacy) `conf/routes`를 직접 확인한 결과 이 4종 전부 `-_-api/v1/*` 경로 그대로
실재하는 API였다. 게다가 일주일 뒤 [[tickets/p2-54|P2-54]]~[[tickets/p2-61|P2-61]] 라운드가
"`-_-api/v1`은 실제 외부 클라이언트가 호출 중일 수 있는 진짜 계약이니 경로까지 지켜야 한다"는
정반대 결론으로 35개 엔드포인트를 원본 경로 그대로 이식했는데, 같은 소스 클래스(`UserApi.java`)
소속인 이 4종은 그 재검토 대상에서 누락된 채 방치돼 있었다.

`StatisticsController.userStatistics()`도 동일 계열 오판이 있었다: "legacy `-_-api/v1`
네임스페이스에 통계 API가 존재한 적이 없다"는 주석이 있었는데, 원본 `UserApi.statistics()`
(issue/posting/assignedIssue/issueComment/postingComment/issueVoter/issueCommentVoter
집계 반환)를 직접 확인한 결과 명백히 같은 기능이 존재했다 — 이 주석도 사실과 다른 잘못된
주장이었다.

## 범위

5개 엔드포인트를 잘못된 `/api/*` 경로에서 원본 legacy 경로로 **교체**한다(별칭이 아니라
치환 — 사용자 지시: "기존 거는 없어도.." → `/api/*` 경로를 실제로 쓰는 곳이 내부에 전혀
없음을 확인 후 완전히 걷어냄):

| 기능 | 이전(제거됨) | 이후(원본 경로) |
|---|---|---|
| `UserApi.newUser` | `POST /api/users` | `POST /-_-api/v1/users` |
| `UserApi.newToken` | `POST /api/users/token` | `POST /-_-api/v1/users/token` |
| `UserApi.users` | `GET /api/admin/users` | `GET /-_-api/v1/admin/users` |
| `UserApi.updateUserState` | `PATCH /api/admin/users/{loginId}` | `PATCH /-_-api/v1/admin/users/{loginId}` |
| `UserApi.statistics` | `GET /api/users/{loginId}/statistics` | `GET /-_-api/v1/users/{loginId}/statistics` |

착수 전 `/api/users`(POST)/`/api/users/token`/`/api/admin/users`/`/api/admin/users/{loginId}`/
`/api/users/{loginId}/statistics`를 템플릿·JS·`yona-cli`·서버 코드 전체에서 grep으로
전수 검색해 내부적으로 참조하는 곳이 하나도 없음을 확인한 뒤 제거했다(참고: 완전히 다른
기능인 `GET /api/users`(사용자 검색)는 같은 경로 접두사를 쓸 뿐 무관한 엔드포인트라 그대로
유지했다 — HTTP 메서드가 달라 라우팅 충돌 없음).

## 완료 로그

### 2026-09-09 — 1차: TDD로 별칭(다중 경로) 추가

**RED**: 각 컨트롤러 스펙에 legacy 원본 경로 호출 테스트를 먼저 추가(수정 전에는 매핑이
없어 404). **GREEN**: `UserController.kt` 4곳, `StatisticsController.kt` 1곳에
`value = [...]` 다중 경로 배열 추가(기존 `/api/*` + 원본 `-_-api/v1/...` 둘 다 매핑).
`UserControllerSpec.kt`(78건, 신규 5건 포함)/`StatisticsControllerSpec.kt`(5건, 신규 1건
포함) 전부 GREEN.

### 2026-09-09 — 2차: 사용자 지시로 잘못된 경로 완전 제거(별칭→치환)

사용자가 "기존 거는 없어도.."라고 지적 — 잘못됐던 `/api/*` 경로를 굳이 남겨둘 이유가
있는지 재확인을 요청받아, 템플릿/JS/`yona-cli`/서버 코드 전체를 grep으로 전수 검색한 결과
이 5개 경로를 내부적으로 실제 참조하는 곳이 **단 한 곳도 없음**을 확인했다(오직 컨트롤러
자기 자신과 테스트에만 존재). 별칭으로 남겨두는 대신 잘못된 경로를 완전히 제거하고 원본
경로 하나만 남기도록 정정 — `@PostMapping(value = [...])` 다중 매핑을 단일 경로
`@PostMapping("/-_-api/v1/...")`로 되돌리고, 이제 중복이 된 별칭 테스트 4건(+통계 1건)을
삭제, 기존 본 테스트들의 호출 경로를 원본 경로로 치환. `UserControllerSpec.kt`(74건)/
`StatisticsControllerSpec.kt`(4건) 전부 GREEN.

**실사용 검증**: 실제 서버(H2 격리 인스턴스, 포트 18599)로 원본 경로(`GET /-_-api/v1/admin/users`,
`GET /-_-api/v1/users/admin/statistics`)는 200, 제거된 옛 경로(`GET/PATCH /api/admin/users*`,
`POST /api/users`, `POST /api/users/token`, `GET /api/users/{id}/statistics`)는 전부 404/405로
실제로 사라졌음을 확인. 완전히 무관한 `GET /api/users`(사용자 검색 기능, 같은 경로 접두어를
우연히 공유할 뿐)는 그대로 200으로 무회귀 확인.
