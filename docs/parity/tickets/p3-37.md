# P3-37: `UserApi.java` 이식 4종(+통계 1종)이 `-_-api/v1` 원본 경로를 안 지킨 판단 오류 수정

## 배경

[[tickets/p1-118|P1-118]](2026-08-21)가 `UserApi.newUser`/`newToken`/`users`/`updateUserState`
4종을 이식하면서 "yona의 `-_-api/v1/*`는 Play 프레임워크 전용 라우팅 우회 접두사, 프레임워크
아티팩트라 이식 대상 아님"이라 판단해 `/api/*`로만 배치했다. 이 판단은 **검증 없이 내려진 오판**이었다
— v1.6(원본 legacy) `conf/routes`를 직접 확인한 결과 이 4종 전부 `-_-api/v1/*` 경로 그대로
실재하는 API였다. 게다가 일주일 뒤 [[tickets/p2-54|P2-54]]~[[tickets/p2-61|P2-61]] 라운드가
"`-_-api/v1`은 실제 외부 클라이언트가 호출 중일 수 있는 진짜 계약이니 경로까지 지켜야 한다"는
정반대 결론으로 35개 엔드포인트를 원본 경로 그대로 이식했는데, 같은 소스 클래스(`UserApi.java`)
소속인 이 4종은 그 재검토 대상에서 누락된 채 방치돼 있었다.

`StatisticsController.userStatistics()`도 동일 계열 오판이 있었다: "legacy `-_-api/v1`
네임스페이스에 통계 API가 존재한 적이 없다"는 주석이 있었는데, 원본 `UserApi.statistics()`
(issue/posting/assignedIssue/issueComment/postingComment/issueVoter/issueCommentVoter
집계 반환)를 직접 확인한 결과 명백히 같은 기능이 존재했다 — 이 주석도 사실과 다른 잘못된
주장이었다.

## 범위

5개 엔드포인트에 원본 legacy 경로를 별칭으로 추가(기존 `/api/*` 경로는 그대로 유지, 하위 호환):

| 기능 | 기존(유지) | 신규 별칭(legacy 원본) |
|---|---|---|
| `UserApi.newUser` | `POST /api/users` | `POST /-_-api/v1/users` |
| `UserApi.newToken` | `POST /api/users/token` | `POST /-_-api/v1/users/token` |
| `UserApi.users` | `GET /api/admin/users` | `GET /-_-api/v1/admin/users` |
| `UserApi.updateUserState` | `PATCH /api/admin/users/{loginId}` | `PATCH /-_-api/v1/admin/users/{loginId}` |
| `UserApi.statistics` | `GET /api/users/{loginId}/statistics` | `GET /-_-api/v1/users/{loginId}/statistics` |

`ProjectController.kt`가 라벨 API에 이미 쓰고 있던 동일한 다중 경로 매핑 패턴
(`@PostMapping(value = ["/api/...", "/-_-api/v1/..."])`)을 그대로 재사용했다 — 새 컨벤션이
아니라 기존 관례를 놓쳤던 곳에 마저 적용한 것.
