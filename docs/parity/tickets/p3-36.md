# P3-36: `/api/v1/search/**`, `/api/v1/organizations/**`에 Fine-grained PAT 스코프 인증 지원

## 배경

`docs/yona-wiki/plans/p3-02-cli-and-rest-api.md`의 리스크 표에 "미해결(다음 라운드 이후로
이월) — 저장소 비종속 스코프 개념을 새로 설계해야 한다"고 남아있던 항목을 재조사했다. 실제로는
그 기록 이후(16라운드, `gh status` 구현) 정확히 이 문제를 풀기 위한 `AccountLevelTarget`
메커니즘(URL 패턴 → `ResourceType` 목록 매핑, `project=null`로 판정)이 이미
`ApiTokenAuthenticationFilter`에 만들어져 있었다 — 새로 설계할 필요 없이 그 매핑 테이블
(`parseAccountLevelTarget()`)을 확장하는 것만으로 해소 가능함을 확인했다.

수정 전 실제 동작: `/api/v1/search/**`, `/api/v1/organizations/**`는 `ApiTokenAuthenticationFilter`의
어떤 URL 패턴과도 매칭되지 않아 Fine-grained PAT 헤더가 있어도 전혀 인식되지 않고, 그 결과
익명 취급되어 `ResourceServerConfig.apiResourceServerSecurityFilterChain`의
`anyRequest().authenticated()`에 막혀 **401**(스코프 부족이 아니라 인증 자체 실패)이 났다.

## 범위

TDD로 진행:
1. `ApiTokenAccountLevelAndLegacyAuthorizationIntegrationSpec.kt`에 RED 테스트 추가(수정 전
   401로 막힘을 먼저 확인) → 프로덕션 코드 미변경 상태로 실행해 실제로 401임을 확인.
2. `ApiTokenAuthenticationFilter`에 4개 URL 패턴 신설(`searchIssuesApiPattern`,
   `searchPullRequestsApiPattern`, `searchProjectsApiPattern`, `organizationsApiPattern`)과
   `parseAccountLevelTarget()` 분기 추가:
   - `GET /api/v1/search/issues` → `ResourceType.ISSUE_POST`(ISSUES 그룹)
   - `GET /api/v1/search/prs` → `ResourceType.PULL_REQUEST`(PULL_REQUESTS 그룹)
   - `GET /api/v1/search/projects` → `ResourceType.PROJECT`(ADMINISTRATION 그룹, 기존 프로젝트
     생성/조회와 동일 컨벤션)
   - `GET /api/v1/organizations`, `GET /api/v1/organizations/{name}` → `ResourceType.ORGANIZATION`
     (이미 ADMINISTRATION 그룹에 매핑돼 있던 기존 타입 재사용 — 신규 타입/그룹 불필요)
   - 전부 `requireAllRepositories = false`(읽기 전용 계정 수준 조회라 `user/issues/status`와
     동일한 컨벤션, `PROJECT` 생성/`SITE_SETTING`처럼 "전체 저장소" 토큰만 허용해야 하는
     특권 액션이 아님).
3. RED 테스트 재실행 → GREEN 확인.
4. `SearchRestApiController.kt`/`OrganizationRestApiController.kt`에 남아있던 "스코프 인가 갭"
   낡은 주석 정리.
5. `ApiTokenAuthenticationFilter`의 클래스 KDoc에 신규 패턴 반영.

## 완료 로그

### 2026-09-09 — TDD로 구현 완료

**RED**: `ApiTokenAccountLevelAndLegacyAuthorizationIntegrationSpec.kt`에 "search/organizations
네임스페이스의 스코프 인가" describe 블록 신설, 프로덕션 코드 변경 전 실행해 다음 10개 테스트가
전부 401(스코프 부족이 아니라 인증 자체 실패)로 실패함을 확인 — 가설(패턴 미매칭 → 익명 취급 →
`anyRequest().authenticated()` 차단)이 정확했음을 실증.

**GREEN**: 위 "범위" 2번 그대로 구현. 같은 스펙 재실행 결과 25개 테스트(신규 10개 포함) 전부
GREEN. 회귀 확인을 위해 `com.github.yonaprojects.yona.config.*` 패키지 전체(약 700개 테스트,
`ApiTokenScoped*`/`AccessControl*`/OAuth2/SSH/SVN 인가 관련 스펙 전부 포함) +
`SearchRestApiControllerSpec`/`OrganizationRestApiControllerSpec`/`SearchControllerSpec`/
`OrganizationViewControllerSpec`까지 함께 재실행 — 전부 GREEN(실패 0건), 기존 세션 로그인/
레거시 전권 토큰 경로 무회귀 확인.

**부수 효과**: `OAuthApiScopeAuthorizationFilter`가 이 필터와 동일한 `resolveRequiredScope()`를
재사용하므로, OAuth2 JWT로 이 API를 호출하는 제3자 앱(P3-14)도 별도 작업 없이 동일한 스코프
판정 혜택을 받는다.
