# P3-51: `spring.messages.fallback-to-system-locale`가 켜져 있어(Spring Boot 기본값) 서버
배포 환경의 JVM 기본 로케일에 따라 i18n 메시지가 요청 로케일과 무관하게 뒤바뀔 수 있음

## 배경

Java `ResourceBundle`(그리고 이를 감싸는 Spring `ResourceBundleMessageSource`)의 기본 동작은,
요청 로케일 전용 번들 파일(`messages_en.properties`)이 없으면 **root 기본 번들
(`messages.properties`)을 시도하기 전에 먼저 "JVM 시스템 기본 로케일" 번들을 시도한다**
(`fallbackToSystemLocale=true`가 Spring의 기본값). 이 저장소는 `messages.properties`(root,
영어 - "Click to post" 등), `messages_ko.properties`/`messages_ko_KR.properties`(한국어),
`messages_ja_JP.properties` 등을 갖추고 있는데, `application.yml`에 `spring.messages.
fallback-to-system-locale`를 명시하지 않아 Spring Boot 기본값(`true`)을 그대로 쓴다.

**실제 재현**: 이 개발 샌드박스의 JVM 기본 로케일은 `ko_KR`이다. `MessageSource.getMessage(
"common.attach.clickToPost", null, Locale.ENGLISH)`를 직접 호출하면(요청 로케일을 명시적으로
영어로 지정했음에도) **"Click to post"가 아니라 "본문에 넣기"(한국어)가 반환된다** — "en"
전용 파일이 없으니 root보다 먼저 JVM 기본 로케일(ko_KR) 파일을 찾아 써버리기 때문이다.

**영향**: 실제 배포 환경(서버 컨테이너)의 시스템 로케일이 무엇이냐에 따라, 사용자가 브라우저
`Accept-Language`로 무슨 언어를 요청하든 **그 언어 전용 번들 파일이 없는 모든 케이스**가
서버의 시스템 로케일로 조용히 뒤바뀐다 — 배포 환경마다 다르게 동작하는 비결정적 버그다.
legacy(Play)는 `application.langs="en-US, ko-KR, ja-JP, ru-RU, uz-UZ"`(conf/
application.conf.default)로 결정적 로케일 폴백 순서를 직접 관리했고, JVM/OS 시스템 로케일과
전혀 무관하게 동작했다 — 이 비결정성 자체가 포팅 과정에서 새로 생긴 회귀다.

## 착수했다가 되돌린 이력 (2026-09-11)

이 세션에서 `spring.messages.fallback-to-system-locale: false`로 끄는 수정을 실제로
적용했었다(root 기본값으로만 폴백하게 함 — legacy의 결정적 동작과 동등). 그런데 이 변경
하나로 **`./gradlew test -Dyona.it.db=h2` 전체 스위트에서 53건이 새로 실패**했다 — 이
개발/CI 환경의 JVM 기본 로케일이 ko_KR이라, 그동안 "Accept-Language 미지정 요청은 한국어로
보인다"는 이 버그의 부작용에 암묵적으로 의존해 작성된 테스트가 최소 14개 스펙 파일에
걸쳐 있었다(`IndexControllerIntegrationSpec` 등 — 로케일을 명시하지 않은 채 한국어 UI
문구를 기대하는 assertion들).

**이번 세션 범위에서는 되돌렸다.** 이유: (1) 이 버그 자체는 Twirl-vs-Thymeleaf 템플릿
렌더링 차이가 아니라 Spring Boot MessageSource 설정 문제라 이번 감사의 본래 범위(A~E) 밖이고,
(2) 영향 범위(53개 테스트, 최소 14개 스펙 파일)가 이번 세션에서 이미 진행 중이던 보안
회귀(P3-51 발견의 계기가 된 알림 XSS, 아래 [[tickets/p3-49|관련 문서]] 참고) 수정과 뒤섞어
처리하기엔 너무 크고, (3) "시작 시점 기준 실패 3건 외에 실패를 늘리지 않는다"는 이 세션의
원칙을 지키려면 53건 전부를 이번 라운드에서 개별 검토해 로케일을 명시하도록 고쳐야 하는데,
그 각각이 "정말 한국어 UI를 검증하려는 의도인지 vs 그냥 기본 동작을 무심코 테스트한 것인지"
판단이 필요해 안전하게 한 번에 끝내기 어렵다고 판단했다.

## 제안하는 다음 단계

1. `application.yml`에 `spring.messages.fallback-to-system-locale: false` 추가.
2. 그 결과 실패하는 모든 테스트(대략 53건, 14개 스펙 파일 — 이번 세션 조사로 최소
   `IndexControllerIntegrationSpec`은 확인됨, 전체 목록은 재실행해서 재확인 필요)를 개별
   검토 — 각 테스트가 실제로 "한국어 UI 검증"이 의도라면 `.locale(Locale.KOREAN)`을 명시,
   단순히 기본 동작에 우연히 의존한 것이라면 그 페이지의 실제 올바른 기본 로케일이 무엇이어야
   하는지(legacy `application.langs`의 첫 번째 값인 en-US가 기본이어야 하는지, 아니면 사이트
   운영 관행상 한국어가 기본이어야 하는지 — 이건 제품 판단이 필요할 수 있음) 확인 후 수정.
3. 실서버로 실제 `Accept-Language: en`/`ko`/헤더 없음 세 케이스를 모두 curl로 재검증해
   결정적으로 동작하는지 확인.
