# P3-43: yona 자체(로컬) 로그인에 2FA(WebAuthn 우선 + TOTP 폴백) 선택 인증 옵션 추가

## 배경

legacy v1.6은 2FA 관련 코드가 전혀 없다(`conf/play.plugins` 등 전수 검색 결과 OAuth2
`GoogleAuthProvider`만 있을 뿐, TOTP/WebAuthn/two-factor 관련 플러그인·코드 0건) — 이건
"동치성 이식 누락"이 아니라 [[tickets/p3-42|P3-42]](위키)와 같은 **완전 신규 기능** 요청이다.

현재 yona의 로그인 경로는 `SecurityConfig.kt`가 폼 로그인(세션 쿠키) + `YonaAuthenticationProvider`
(로컬/LDAP 자격증명 검증)로 처리하며, OAuth2(Google 등)/SAML2 SSO(`SAML2ssoSettings`)도 이미
별도 인증 경로로 존재한다. 사용자 요청은 이 중 "yona 자체 로그인"(로컬 비밀번호 인증) 경로에
한해, 계정별로 **선택적**(강제 아님) 2단계 인증을 켤 수 있게 하는 것 — 로그인 흐름은 다음과
같이 확정됐다: **계정에 WebAuthn과 TOTP를 둘 다 등록할 수 있고, WebAuthn이 등록돼 있으면
로그인 시 WebAuthn 인증을 먼저 띄운다. 실패/거부/취소 시 곧장 TOTP로 넘기지 않고, 구글
로그인처럼 "다시 시도"와 "다른 방법 사용(TOTP)" 두 선택지를 보여준다.**

## 목표 수준 (GitHub 계정 2FA 설정 화면 기준 — WebAuthn 우선 + TOTP 폴백)

1. **등록**: 계정당 WebAuthn(보안 키/생체인증)과 TOTP를 **둘 다, 각각 여러 개까지** 등록
   가능(예: 보안 키 2개 + TOTP 앱 1개 — 기기 분실 대비, GitHub와 동일).
   - TOTP: 사용자 설정 화면에서 QR코드(또는 시크릿 문자열 수동 입력)를 발급하고, 앱에서 생성한
     6자리 코드로 1회 검증해야 활성화 확정(코드 검증 없이 바로 켜지면 오탈자로 스스로 잠길
     위험이 있어 배제).
   - WebAuthn: 브라우저 `navigator.credentials.create()`로 플랫폼 인증기(지문/Face ID/
     Windows Hello) 또는 로밍 보안 키(YubiKey 등)를 등록 — attestation은 검증만 하고 저장은
     credential public key + credential id + sign counter만 하면 충분(GitHub/GitLab 관례).
2. **로그인 흐름**: 1차 비밀번호 인증 통과 후,
   - 계정에 WebAuthn이 하나 이상 등록돼 있으면 **WebAuthn 인증을 먼저** 띄운다
     (`navigator.credentials.get()`).
   - 사용자가 WebAuthn을 거부/취소/실패하면(또는 등록된 WebAuthn이 아예 없으면), 구글 로그인
     방식처럼 화면에 **"다시 시도"(WebAuthn 재시도)와 "다른 방법 사용"(TOTP 코드 입력으로
     전환) 두 선택지를 함께 보여준다** — 실패를 바로 TOTP 화면으로 흘려보내지 않고, 사용자가
     스스로 재시도할지 전환할지 고르게 한다("다른 방법 사용"은 TOTP도 등록돼 있을 때만
     노출).
   - 이 "1차 통과, 2차 대기" 중간 상태를 어떻게 표현할지(Spring Security
     `AuthenticationProvider` 체이닝 vs 세션에 임시 인증 상태를 두는 커스텀 필터)는 기존
     `YonaAuthenticationProvider`/OAuth2/SAML2 경로를 깨지 않아야 하므로 착수 시 코드를 보고
     설계한다 — WebAuthn/TOTP 두 방식이 이 중간 상태를 공유하는 구조로 간다. "다시 시도"는
     같은 대기 상태를 유지한 채 WebAuthn 챌린지만 재발급하면 되고, "다른 방법 사용"은 같은
     대기 상태에서 검증 방식만 TOTP로 바꾸면 되므로 두 선택지 모두 이 중간 상태 하나로
     자연스럽게 처리 가능.
3. **복구 수단**: 백업 코드 **8개 생성**, 1회용(사용 즉시 소모), **재발급 시 기존 코드
   전량 무효화**.
4. **비활성화**: 사용자가 언제든 끌 수 있어야 하고(비밀번호 재확인 요구), **사이트 관리자가
   계정 잠금 시 강제로 끌 수 있는 관리자 경로 필수**(사용자 확정).
5. **API 토큰/PAT 경로와의 관계**: Fine-grained PAT([[tickets/p3-02|P3-02]])/레거시 전권 토큰
   인증은 세션 로그인과 별개 경로이므로 2FA 대상에서 제외(GitHub도 PAT는 2FA 우회).

## 설계 결정(확정)

- **DB 스키마 — 신규 테이블 3개를 분리해서 둔다(제안, 확정)**:
  - `user_totp_credential`(user_id FK, 암호화된 secret, 활성화 시각, 활성화 여부) — TOTP는
    "여러 개 등록"이 앱을 여러 대 등록하는 상황에 해당하므로 1:N으로 두되(계정당 앱 여러
    대에 같은 QR을 등록하는 방식이 아니라 각 등록 = 별도 secret), 실무상 TOTP 앱을 굳이
    여러 개 등록할 필요는 크지 않아 1:1로 시작하고 필요 시 1:N으로 넓혀도 무방.
  - `user_webauthn_credential`(user_id FK, credential_id, public_key, sign_count, 별명,
    등록 시각) — 1:N(보안 키/기기별로 여러 개).
  - `user_backup_code`(user_id FK, code_hash, 사용 시각 nullable) — 1:N, 8개 생성.
  - `User` 엔티티엔 `isTwoFactorEnabled`류 요약 플래그 하나만 두고 실제 등록 정보는 위 세
    테이블에 위임(코드/이슈/PR 등 다른 기능이 `isXEnabled` 플래그 하나로 켜고 끄는 것과
    유사한 요약 필드 패턴, [[tickets/p3-42|P3-42]] 후속 수정에서 확인한 관례와 일관).
  - 근거: TOTP(암호화된 대칭 비밀 1개)와 WebAuthn(공개키+계정당 여러 개, attestation 관련
    필드)은 저장해야 할 데이터 형태가 근본적으로 달라 한 테이블에 합치면 안 쓰는 컬럼이
    서로 nullable로 뒤섞인다. 이미 이 코드베이스도 `ssh_key`(계정당 여러 개인 자격증명)를
    `User`와 분리된 별도 테이블로 두고 있어, 그 관례를 그대로 따르는 것이 일관적이다.
    백업 코드도 "1회용 자격증명 묶음"이라 성격이 또 달라 별도 테이블이 자연스럽다.
    Hibernate `ddl-auto: update`라 세 테이블 추가에 별도 마이그레이션 스크립트는 불필요.
- **라이브러리 — 현재 스택에 맞는 것으로 확정**:
  - WebAuthn: **서드파티 불필요.** 이 프로젝트가 이미 쓰는 Spring Security 버전(7.1.1,
    `./gradlew dependencies`로 직접 확인)은 WebAuthn/패스키를 자체 내장 지원한다
    (`org.springframework.security:spring-security-webauthn`, 내부적으로 WebAuthn4J 사용,
    `HttpSecurity` DSL 안에서 설정). 이미 SAML2/OAuth2 Authorization Server도 같은 Spring
    Security BOM으로 버전 고정 없이 쓰고 있는 구조와 그대로 맞아떨어진다.
  - TOTP: Spring Security엔 내장 기능이 없어 별도 라이브러리가 필요하다 — **`dev.samstevens.totp`**
    채택(RFC 6238 구현 + QR코드 PNG 생성까지 한 라이브러리로 해결, 이 프로젝트엔 QR/zxing류
    의존성이 전혀 없어 어차피 신규 추가가 필요한 상황이었음).
- **웹 UI**: GitHub 계정 보안 설정 화면 관례(2FA 방식 목록에서 보안 키/TOTP를 나란히
  추가·조회, 로그인 시 WebAuthn 프롬프트 우선 → "다른 방법 사용" 링크로 TOTP 폴백 UX)를
  따른다(이 세션의 표준 원칙).
- **yona-cli/MCP**: 세션 로그인이 아니라 PAT 인증을 쓰므로 이번 기능의 CLI/MCP 노출 대상은
  아님(단, "2FA 계정 관리"용 REST API를 CLI에 노출할지는 착수 시 재검토 가능).

## 완료 로그(2026-09-10)

**전부 완료.** WebAuthn(보안 키/생체인증) + TOTP 이중 폴백 2FA를 로컬 로그인 경로에만 게이트로
추가했다. 아래 항목별로 무엇을 구현했고 무엇으로 검증했는지 기록한다.

### 착수 시 확인/재검토한 사항

- `./gradlew dependencies --configuration runtimeClasspath`로 Spring Security 7.1.1 확인, 이
  버전에서 `org.springframework.security:spring-security-webauthn`(WebAuthn4J 0.31.9.RELEASE
  내장)이 Maven Central에 정식 배포돼 있고 milestone이 아님을 확인 — 티켓 우려와 달리 대안
  라이브러리로 전환할 필요가 없었다.
- 다만 이 아티팩트가 노출하는 `webauthn()` HttpSecurity DSL/`WebAuthnAuthenticationFilter`는
  패스워드리스(passkey) 로그인을 1차 인증으로 쓰는 시나리오 전용으로 설계돼 있어("1차
  비밀번호 인증 후 2단계"라는 이 요구사항과 맞지 않음, `residentKey=REQUIRED` 강제 등), 그
  필터/DSL은 쓰지 않고 한 단계 아래의 building block인 `WebAuthnRelyingPartyOperations`
  (`Webauthn4JRelyingPartyOperations`)만 빈으로 노출해 로그인 2FA 컨트롤러와 설정 화면
  컨트롤러에서 직접 호출하는 구조로 설계했다(`config/webauthn/WebauthnRelyingPartyConfig.kt`).
  `setCustomizeCreationOptions`로 residentKey를 PREFERRED로 완화해 구형 보안 키와도 호환.
- 이 프로젝트가 Jackson 3(`tools.jackson`)을 쓰는 것을 확인하고, spring-security-webauthn이
  Jackson 2/3 두 버전의 모듈을 모두 제공하는 것 중 `WebauthnJacksonModule`(tools.jackson용)을
  빈으로 등록 — 실제 서버에서 옵션 JSON 응답(`challenge`/`user.id` 등 base64url 인코딩)이
  스펙대로 나오는 것을 curl로 확인했다.

### DB 스키마

- `user_totp_credential`/`user_webauthn_credential`/`user_backup_code` 3개 테이블 신규
  (`domain/twofactor/*.kt`) — 모두 계정당 1:N(요구사항 확정대로 TOTP도 여러 개 등록 가능).
  `User.isTwoFactorEnabled: Boolean?`은 요약 캐시일 뿐이고, 로그인 게이트를 포함한 모든 보안
  판단은 `TwoFactorService.isTwoFactorEnabled()`(실제 테이블 조회)를 단일 진실 공급원으로 쓴다
  — 캐시가 어긋나도 로그인 우회로 이어지지 않도록 설계.
- 세 엔티티의 `user` FK에 `@OnDelete(action = OnDeleteAction.CASCADE)`(DB 레벨 ON DELETE
  CASCADE)를 추가했다 — 다른 기존 통합테스트들이 `sshKeyRepository.deleteAll()` 등으로 자식
  테이블을 먼저 정리한 뒤 `userRepository.deleteAll()`을 호출하는 명시적 순서 관례를 쓰는데,
  이 신규 테이블들은 그 관례를 모르는 기존 테스트 전부를 건드리지 않고도 안전하게 만들기
  위해 DB 제약으로 해결했다(실제로 회귀 스윕 중 FK violation으로 발견하고 수정 — 아래 검증
  절 참고).
- TOTP secret은 로그인 시 원문 비교가 필요한 대칭 비밀이라 `TotpSecretEncryptor`(Spring
  Security Crypto `Encryptors.text`, AES)로 암호화해 저장(`yona.security.totp.*`,
  운영 배포 시 반드시 환경변수로 덮어써야 하는 개발용 기본값). 백업 코드는 원문 비교가
  필요 없어 SHA-256 단방향 해시(`BackupCodeGenerator`).

### 로그인 필터 체인

- `Pre2faAuthenticationToken`(권한 `ROLE_PRE_2FA` 하나만, 원래의 완전한 Authentication을
  내부 필드로 보유) + `Pre2faGateFilter`(이 토큰만 SecurityContext에 있으면 2FA 검증
  경로/로그아웃/정적 자원 외 전부 `/users/login/2fa`로 강제 리다이렉트).
- `YonaAuthenticationSuccessHandler`가 1차 인증 성공 직후 `TwoFactorService.isTwoFactorEnabled()`
  로 판단해, 등록된 2FA가 있으면 완전한 Authentication 대신 `Pre2faAuthenticationToken`을
  세션에 심고 `/users/login/2fa`로 리다이렉트한다. 없으면 기존과 동일하게 동작(회귀 없음).
- `TwoFactorLoginController`(`/users/login/2fa*`)가 WebAuthn 우선(등록돼 있으면)/TOTP
  폴백/백업 코드 검증을 전부 같은 대기 상태(Pre2faAuthenticationToken) 위에서 처리 —
  "다시 시도"/"다른 방법 사용"/"복구 코드 사용"은 `?method=` 쿼리 파라미터로 같은 화면의
  단계만 바꾸는 것으로 자연스럽게 구현됐다(별도 상태 기계 불필요). 검증 성공 시
  `SecurityContext`를 원래의 완전한 Authentication으로 교체하고 기존 `HttpSessionRequestCache`
  (변경 없음)가 들고 있던 원래 목적지로 리다이렉트한다.
- OAuth2/SAML2/LDAP(→ 로컬 폴백 제외)/PAT 로그인 경로는 이 성공 핸들러를 타지 않는 별도
  필터/AuthenticationManager를 쓰므로 이 게이트 대상이 아니다(코드 경로상 분리 확인, 회귀
  스윕에도 관련 스펙 전부 포함해 GREEN 확인).

### WebAuthn 등록/관리

- `config/webauthn/UserWebauthnEntityRepositoryAdapter`(`PublicKeyCredentialUserEntityRepository`)
  + `WebauthnUserCredentialRepositoryAdapter`(`UserCredentialRepository`) — User.id를 8바이트
  빅엔디언으로 결정론적으로 인코딩해 별도 매핑 테이블 없이 WebAuthn user handle을 만든다.
  `WebauthnRegistrationController`(`/user/editform/security/webauthn/{options,}`)가 브라우저
  navigator.credentials.create() JSON을 받아 `Webauthn4JRelyingPartyOperations.registerCredential()`
  로 실제 서명/attestation을 검증하고 저장한다.
- 설정 화면(`user/edit_security*.html`, `TwoFactorSettingsController`)에 목록/삭제/추가
  버튼 배선. 계정이 처음으로 2FA를 켜는 순간(WebAuthn이든 TOTP든) 백업 코드 8개가 자동
  발급되고 1회만 평문으로 보여진다(`TwoFactorService.completeWebauthnRegistration`/
  `verifyAndActivateTotp`가 공유하는 `ensureBackupCodesInitialized`).

### 비활성화

- 사용자 본인: `POST /user/editform/security/disable`(비밀번호 재확인, 기존 레거시 해시
  알고리즘 그대로 재사용).
- 관리자: `POST /-_-api/v1/admin/users/{loginId}/disable-2fa`(사이트관리자 전용, 기존
  `/-_-api/v1/admin/users/{loginId}` PATCH 엔드포인트와 동일한 인가 패턴) — 별도 엔드포인트로
  분리해 기존 상태 변경 계약을 건드리지 않았다.

### 테스트

- `TwoFactorServiceImplSpec`(10건) — TOTP 등록/활성화/로그인 검증, 백업 코드 발급/재사용

### 실사용 검증

`bootJar` 빌드 후 h2 프로파일로 실제 기동, 아래를 전부 실제 HTTP 요청으로 재현했다:
1. `/bootstrap-setup`(loginId는 레거시 제약상 반드시 "admin") → 재시작 → `admin` 로그인
   (2FA 없음 → 정상 리다이렉트).
2. `/signup`으로 `totpuser` 생성 → 로그인(2FA 없음, 회귀 없음 확인).
3. `GET /user/editform/security/totp/new`로 실제 secret+QR 발급 → 별도 python 스크립트
   (stdlib hmac/hashlib만 사용한 RFC 6238 재구현, 서버와 다른 독립 구현)로 그 시각의 6자리
   코드를 계산 → `POST .../totp/{id}/verify`로 실제 활성화 성공, 백업 코드 8개 발급 확인.
4. 새 세션으로 재로그인 → `/users/login/2fa`로 리다이렉트 확인 → `GET /` 등 다른 페이지가
   전부 2FA 화면으로 강제 리다이렉트되는 것 확인 → 오답 코드로는 통과하지 못함 확인 → 같은
   python 스크립트로 새로 계산한 정답 코드로 완전히 로그인되는 것을 확인.
5. 백업 코드로 2단계 인증 통과 → 같은 코드 재사용 시도가 거부되는 것 확인.
6. 관리자로 로그인 후 `POST /-_-api/v1/admin/users/totpuser/disable-2fa` 호출 →
   `totpuser`가 이후 2FA 없이 정상 로그인되는 것 확인.
7. `POST /user/editform/security/webauthn/options`가 실제로 스펙에 맞는 JSON(challenge/
   user.id가 base64url, residentKey=preferred로 완화 반영)을 반환하는 것 확인.

**한계(정직하게 기록)**: WebAuthn 등록/인증 전체를 실제 브라우저 navigator.credentials
세리모니로 curl 재현하는 것은 원천적으로 불가능하다(개인키가 브라우저/OS 보안 모듈
안에만 있고 JS로도 추출 불가 — WebAuthn 스펙 자체의 설계 목적). 대신 위 "테스트" 절의
`WebauthnRelyingPartyIntegrationSpec`이 WebAuthn4J의 가상 인증기로 서버 측 검증 로직(서명
검증 포함) 전체 경로를 실제로 태우고, 실사용 검증 7번이 등록 JSON API가 실제 서버에서
스펙대로 응답하는 것까지 확인했다 — 다만 브라우저의 `navigator.credentials.create()/get()`
JS 호출 자체(로그인 화면/설정 화면의 `login_2fa.html`/`edit_security_webauthn_new.html`
인라인 스크립트)는 실제 하드웨어 보안 키나 플랫폼 인증기가 있는 브라우저에서 사람이
직접 눌러보지 않는 한 끝까지 확인할 방법이 없다.
