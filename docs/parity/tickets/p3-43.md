# P3-43: yona 자체(로컬) 로그인에 2FA(TOTP 또는 WebAuthn) 선택 인증 옵션 추가

## 배경

legacy v1.6은 2FA 관련 코드가 전혀 없다(`conf/play.plugins` 등 전수 검색 결과 OAuth2
`GoogleAuthProvider`만 있을 뿐, TOTP/WebAuthn/two-factor 관련 플러그인·코드 0건) — 이건
"동치성 이식 누락"이 아니라 [[tickets/p3-42|P3-42]](위키)와 같은 **완전 신규 기능** 요청이다.

현재 yona의 로그인 경로는 `SecurityConfig.kt`가 폼 로그인(세션 쿠키) + `YonaAuthenticationProvider`
(로컬/LDAP 자격증명 검증)로 처리하며, OAuth2(Google 등)/SAML2 SSO(`SAML2ssoSettings`)도 이미
별도 인증 경로로 존재한다. 사용자 요청은 이 중 "yona 자체 로그인"(로컬 비밀번호 인증) 경로에
한해, 계정별로 **선택적**(강제 아님) 2단계 인증을 켤 수 있게 하고, 방식은 **TOTP 또는
WebAuthn 중 계정마다 하나를 선택**(GitHub 계정 보안 설정처럼 두 방식을 나란히 제공)하는
것으로 범위가 확정됐다.

## 목표 수준 (GitHub 계정 2FA 설정 화면 기준 — TOTP/보안 키(WebAuthn) 둘 다 지원)

1. **등록**:
   - TOTP: 사용자 설정 화면에서 QR코드(또는 시크릿 문자열 수동 입력)를 발급하고, 앱에서 생성한
     6자리 코드로 1회 검증해야 활성화 확정(코드 검증 없이 바로 켜지면 오탈자로 스스로 잠길
     위험이 있어 배제).
   - WebAuthn: 브라우저 `navigator.credentials.create()`로 플랫폼 인증기(지문/Face ID/
     Windows Hello) 또는 로밍 보안 키(YubiKey 등)를 등록 — 서버는 attestation은 검증만 하고
     보관은 credential public key + credential id만 하면 충분(GitHub/GitLab 관례).
   - 계정당 두 방식 중 하나만 강제하지 않고 **여러 개 동시 등록도 허용**할지(예: TOTP + 보안 키
     둘 다, 기기 분실 대비)는 착수 시 결정 — GitHub는 여러 보안 키 + TOTP 병행 등록을 허용.
2. **로그인 흐름 통합**: 2FA가 켜진 계정은 1차 비밀번호 인증 통과 후 TOTP 코드 또는 WebAuthn
   인증(`navigator.credentials.get()`) 단계를 추가로 거쳐야 세션이 발급된다(현재
   `YonaAuthenticationProvider`/`SecurityConfig`의 필터 체인에 2단계를 어떻게 끼워넣을지 —
   별도 `AuthenticationProvider` 체이닝 vs 중간 세션 상태를 두는 커스텀 필터 — 착수 시 설계
   필요, TOTP/WebAuthn 두 방식이 이 중간 상태를 공유하는 구조가 자연스러움).
3. **복구 수단**: 기기 분실 시 계정 잠금을 막기 위한 백업 코드(1회용 코드 묶음, GitHub/GitLab
   관례) 최소 1종은 있어야 한다 — 방식과 무관하게 공통.
4. **비활성화**: 사용자가 언제든 끌 수 있어야 하고(비밀번호 재확인 요구), 사이트 관리자가
   계정 잠금 시 강제로 꺼줄 수 있는 관리자 경로도 필요할 수 있음(범위 확정 시 결정).
5. **API 토큰/PAT 경로와의 관계**: Fine-grained PAT([[tickets/p3-02|P3-02]])/레거시 전권 토큰
   인증은 세션 로그인과 별개 경로이므로 2FA 대상에서 제외(GitHub도 PAT는 2FA 우회).

## 범위 확정 필요 사항 (착수 시 먼저 결정할 것)

- TOTP 시크릿/WebAuthn credential 저장 위치 — `User` 엔티티에 직접 컬럼 추가 vs 별도
  `user_verification`/`user_setting` 테이블(이미 존재, 용도 확인 필요) 재사용 vs 신규
  `user_credential`류 테이블(WebAuthn은 계정당 여러 개 등록 가능해 1:N 구조가 자연스러움).
  TOTP 시크릿은 평문 저장 금지 — 최소한 애플리케이션 레벨 암호화 필요(비밀번호 해시와 달리
  원문 검증이 필요한 대칭 비밀이므로 해시가 아니라 암호화). WebAuthn은 공개키만 저장하면 되어
  이 문제가 없음.
- 라이브러리 선정 — TOTP(예: `dev.samstevens.totp`, `com.warrenstrange:googleauth`),
  WebAuthn(예: Spring Security 6+ 내장 `spring-security-webauthn`, 또는 Yubico
  `java-webauthn-server`) — 각각 표준(RFC 6238 / W3C WebAuthn) 준수 여부·유지보수 상태 확인
  필요. Spring Security 버전이 WebAuthn을 내장 지원하는 버전인지 먼저 확인.
- 로그인 필터 체인에 2단계 인증을 끼워 넣는 구체적 방식(Spring Security
  `AuthenticationProvider` 체이닝, 중간 인증 상태를 세션에 임시 저장하는 커스텀 필터, 또는
  별도의 "2FA 대기" 인증 객체 등) — 기존 `YonaAuthenticationProvider`/OAuth2/SAML2 경로를
  깨지 않아야 함.
- 백업 코드 형식/개수/재발급 정책.
- 웹 UI는 GitHub 계정 보안 설정 화면 관례(2FA 방식 목록에서 TOTP/보안 키를 나란히 추가하는
  UX)를 따를 것(이 세션의 표준 원칙).
- yona-cli/MCP는 세션 로그인이 아니라 PAT 인증을 쓰므로 이번 기능의 CLI/MCP 노출 대상은
  아님(단, "2FA 계정 관리"용 REST API를 CLI에 노출할지는 착수 시 재검토 가능).
