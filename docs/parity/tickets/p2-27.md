## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P2-27**: yona `FavoriteProject.java:41-50` `updateFavoriteProject(project)`(즐겨찾기한 사용자들의 비정규화된 owner/projectName 갱신, `FavoriteOrganization` 쪽 [[tickets/p2-19|P2-19]]와 동일 패턴) 대응을 `ProjectServiceImpl.acceptTransfer()`에 추가.
  - **조사 과정에서 확인한 사실**: yona는 이 동기화를 `ProjectApp.settingProject()`(동일 소유자 내 개명 전용 경로)에서만 호출하고, 소유권 이전 경로인 `acceptTransfer()`에서는 호출하지 않는다 — 이관 후에도 즐겨찾기 화면에 옛 owner/projectName이 남는 yona 자체의 누락으로 보인다.
  - **적용 지점 판단**: yona는 `settingProject()`에 대응하는 "동일 소유자 개명" 경로 자체가 없고(신규 [[tickets/p1-144|P1-144]]로 별도 등록), 프로젝트의 owner/name이 실제로 바뀌는 유일한 지점이 `acceptTransfer()`뿐이다. 관심사(즐겨찾기 표시 최신화)와 메커니즘(`FavoriteProject.updateFavoriteProject`)은 yona 원본에서 그대로 가져오되, yona가 두 메서드로 나눠뒀던 것을 yona의 실제 코드 구조(하나로 통합된 acceptTransfer)에 맞춰 배치한 것 — "레거시에 없는 동작 추가"가 아니라 [[tickets/p1-137|P1-137]]과 동일한 "동일 관심사의 구조 번역"으로 판단.
  - `ProjectServiceImpl`에 `favoriteProjectRepository: FavoriteProjectRepository`(이미 존재하는 `findByProjectId` 재사용) 주입 추가.
  - 테스트: `ProjectServiceImplSpec.kt` +1(이관 완료 시 즐겨찾기한 사용자의 owner/projectName이 새 값으로 갱신되는지 검증). 전체 20/20 통과.
  - **새로 발견해 [[tickets/p1-144|P1-144]]로 등록**: yona에 "같은 소유자를 유지한 채 이름만 바꾸는" 개명 기능 자체가 없음(`UpdateProjectParam`/`UpdateProjectRequest`에 `name` 필드 부재) — 소유권 이전 없이 이름만 바꾸고 싶은 사용자가 쓸 방법이 없는 실제 기능 결손.
