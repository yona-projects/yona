# P3-22: Mercurial push 시 알림/웹훅/PushedBranch(최근 push 브랜치) 추적 미발행

## 배경

Git은 push 성공 시 `GitPushHooks.kt`의 post-receive 훅 체인이 (1) 알림 메일 발행
(`GitPostReceiveEvent`), (2) 웹훅 발행, (3) `PushedBranch`(최근 push된 브랜치 — "최근 push한
브랜치로 PR 만들기" GitHub UX) 갱신, (4) 관련 PR 재검사(`RelatedPullRequestMergeEvent`)를
전부 수행한다. Mercurial push는 이 중 아무것도 하지 않는다 — 조용히 반영만 되고 아무 이벤트도
안 난다.

**P3-21과 정확히 같은 근본 원인/전제조건을 공유한다**: hg4j의 `unbundle` 훅은 "어떤
브랜치(북마크)가 갱신됐는지" 정보가 없고, 실제 북마크 이동은 `pushkey` 처리에서 일어나는데
거기엔 훅 자체가 없다. **P3-21에서 hg4j에 추가하는 `registerPostPushkeyHook`을 그대로
재사용**한다 — 별도로 새 hg4j 기능을 또 만들 필요는 없다(단, P3-21 담당자가 이 티켓도 함께
처리하거나, 순서상 P3-21의 hg4j 확장이 먼저 끝나 있어야 한다).

## 범위

### yona

1. `GitPushHooks.kt`를 참고해 `HgPushHooks.kt`(가칭) 신설 — JGit의 `PostReceiveHook` 인터페이스는
   재사용 불가(git 전용 타입)이므로, hg4j의 `HgHook`을 감싸는 형태로 새로 작성하되 내부 로직
   (알림/웹훅 이벤트 발행, `PushedBranch` upsert, 관련 PR 재검사 트리거)은 git 쪽과 최대한
   동일한 서비스/이벤트 타입을 재사용한다(`GitPostReceiveEvent` 같은 git 전용 이벤트가 있다면
   VCS-neutral하게 다시 쓸 수 있는지, 아니면 대응하는 새 이벤트 타입이 필요한지 확인해서
   판단).
2. `HgSshProtocolHandler.kt`/`HgController.kt` 양쪽에 `registerPostPushkeyHook`으로 연결.
3. 웹훅 페이로드(P1/P2에서 이미 완성된 push 이벤트 JSON 스키마)를 Mercurial push에도 동일하게
   채워 보낼 것 — commit 목록/head_commit 등 기존 필드 구조를 그대로 따르되, Mercurial 커밋
   메타데이터(브랜치=북마크 이름, node hex 등)로 채운다.
4. `PushedBranch` 추적("최근 push한 브랜치" — PR 생성 유도 UX)도 Mercurial 북마크에 대해
   동일하게 동작하게 만든다.
5. 관련 PR 재검사(`RelatedPullRequestMergeEvent` 대응) — Mercurial PR이 실제로 지원되는지
   먼저 확인하고(안 되면 이 항목은 범위에서 자연히 빠짐, 문서화할 것), 지원된다면 push된
   브랜치를 대상 브랜치로 하는 열린 PR들의 diff/충돌 상태를 재계산하도록 연결한다.

## 완료 기준

- 실제 앱 기동으로: Mercurial 프로젝트에 push하면 (1) 웹훅이 실제로 발송되고 페이로드가
  Git과 동일한 스키마를 갖는다, (2) watch 중인 사용자에게 알림 메일이 발행된다, (3) push한
  브랜치가 "최근 push한 브랜치" UI에 노출된다 — 전부 실사용으로 확인.
- 회귀 테스트 GREEN.

## 완료 로그

**2026-09-09 완료.** P3-21과 같은 세션·같은 커밋 세트로 함께 구현했다 — hg4j의
`registerPrePushkeyHook`/`registerPostPushkeyHook`(P3-21에서 신설)을 그대로 재사용했고,
새 hg4j 기능은 추가하지 않았다. hg4j/yona 양쪽 구현 상세, context 스키마, 실사용 검증 절차,
발견했지만 고치지 않은 문제(순환 참조 직렬화 버그, Mercurial PR 병합 미지원)는
[[tickets/p3-21]]의 완료 로그에 전부 기록했다 — 여기서는 P3-22 고유 항목만 요약한다.

### yona 변경 (P3-22 고유 부분만 — 나머지는 P3-21 로그 참고)

- `domain/vcs/HgPushHooks.kt`의 `HgYonaPostPushkeyHook` — git `YonaPostReceiveHook`의
  `notifyPushedCommits`/`notifyRelatedPullRequestsForUpdatedBranches`/
  `cleanupPullRequestsForDeletedBranches`/`updateRecentlyPushedBranches`를 전부 대응 이식.
- `domain/event/HgPostReceiveEvent.kt`/`HgPostReceiveEventListener.kt`(신설) — 알림 메일
  (`NotificationEventRecorder`+`WatchService`)과 이슈 참조(`IssueReferenceParser`) 처리는
  git 쪽과 완전히 동일한 서비스를 재사용.
- `domain/webhook/PushedHgCommits.kt`(신설)+`WebhookServiceImpl.buildPushPayloadForHg()` —
  기존 push 웹훅과 동일한 JSON 스키마(ref/commits/head_commit/sender/pusher/repository)를
  hg4j `HgCommit` 값으로 채운다. Mercurial은 author/committer 구분이 없어 두 필드에 동일한
  값을 채운다.
- `PushedBranch` upsert/정리, 오래된 레코드 정리(1시간 윈도) 로직은 git과 완전히 동일한
  `PushedBranchRepository`를 그대로 재사용.
- 관련 PR 재검사(`RelatedPullRequestMergeEvent`) — VCS 무관 이벤트 타입이라 수정 없이 그대로
  재사용 가능함을 확인, `HgYonaPostPushkeyHook`에서 UPDATE/UPDATE_NONFASTFORWARD 시 발행하도록
  연결. **단, 실제 재검사(diff/충돌 계산)는 Mercurial 프로젝트에서 동작하지 않는다** — 상세
  원인(`PullRequestServiceImpl`이 JGit에 하드코딩됨, 실측 스택트레이스 포함)은 [[tickets/p3-21]]
  참고.

### 실사용 검증 결과 요약 (상세 로그·명령·응답은 [[tickets/p3-21]] 참고)

- (1) 웹훅 실제 발송 + Git과 동일 스키마 페이로드: **확인 완료** — 실제 컨테이너에 Python
  HTTP 리시버를 붙여 실제 push 후 수신된 JSON 페이로드 전체를 확인(ref/commits/head_commit/
  sender/pusher/repository 필드 전부 정확).
- (2) watch 중인 사용자에게 알림 메일 발행: `NotificationEventRecorder.record()`/
  `WatchService.findActualWatchers()` 호출 및 `NotificationEvent` 저장까지 서버 로그로 확인
  (`[NOTIFICATION] Pushed Hg commits notification created and saved: ...`). 실제 이메일
  발송(SMTP)까지는 이번 검증에서 별도로 확인하지 않았다 — git 쪽과 동일한
  `NotificationEventRecorder`/메일 발송 파이프라인을 그대로 타므로(코드 경로 100% 동일,
  분기 없음) 이미 검증된 git 경로와 다르게 동작할 이유가 없다는 판단.
- (3) 최근 push한 브랜치 UI 노출: DB(`project_pushed_branch` 테이블 INSERT/UPDATE)에는
  정상 반영됨을 Hibernate SQL 로그로 확인. 이 데이터를 노출하는
  `/api/{owner}/{projectName}/pushedBranches` REST 응답 자체는 위에서 언급한 기존(무관)
  순환 참조 버그로 깨져 있어 API 응답으로는 직접 확인하지 못했다 — 근본 데이터가 정확함은
  SQL 로그로 대체 확인했다.
