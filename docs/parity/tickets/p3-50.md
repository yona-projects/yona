# P3-50: 댓글 수정 폼에서 기존 첨부파일 목록이 보이지 않고 관리도 불가능함

## 배경

[[tickets/p3-49|P3-49]]("이슈 댓글 화면 파일 업로드가 죽어있음")를 착수하며 v1.6을 다시
끝까지 대조한 결과, 원래 티켓이 "새 댓글 작성 폼의 textarea 드래그드롭 즉시업로드"로
진단했던 "원인 2"는 실재하지 않는 문제였고(정정 내용은 P3-49 완료 로그 참고), 대신
`yona.CommentAttachmentsUpdate.js`가 실제로 담당하던 기능은 **완전히 다른 화면** —
"기존에 작성된 댓글을 수정할 때, 그 댓글에 이미 첨부돼 있는 파일 목록을 보여주고 관리하는
UI" — 였다는 게 드러났다.

## v1.6 원본 대조 결과

`app/views/common/commentUpdateForm.scala.html`(댓글 수정 폼)은 범용 업로드 위젯
(`common.fileUploader`)을 쓰지 않고, 전용 마크업을 직접 렌더링한다:

```scala
<div class="upload-drop-here"> ... </div>
<span class="file-upload">
    <label for="upload-@comment.id" class="file-upload__label ybtn">@Messages("button.upload")</label>
    <input id="upload-@comment.id" class="file-upload__input" type="file" name="filePath" multiple>
</span>
...
<input type="hidden" name="temporaryUploadFiles" class="temporaryUploadFiles" value="">
<div class="attachment-files">
@for(file <- files.get("attachments")) {
    @attachmentFile(file, resourceType, comment.id)
}
</div>
```

여기서 `files`는 `AttachmentApp.getFileList(resourceType, comment.id)`로 **그 댓글에 이미
첨부된 파일 목록**을 조회한 것이고, `attachmentFile(...)` 파샬이 각 파일을 카드 형태로
렌더링한다(삭제 버튼 포함). 새 파일 업로드(버튼 클릭/드래그드롭/붙여넣기)와 기존 파일
삭제 전부 `yona.CommentAttachmentsUpdate.js`가 담당한다(`.file-upload__input`
change 이벤트, `.textarea-box textarea`의 drag/drop/paste 델리게이트, `.attached-file-marker`의
삭제 버튼 클릭).

## 현재(next) 상태

`common/commentUpdateForm.html`은 이 전용 마크업 대신 새 글/새 댓글 작성 폼과 동일한 범용
`common/uploadForm` 프래그먼트를 그대로 재사용한다:

```html
<div th:replace="~{common/uploadForm :: uploadForm(${resourceType}, ${comment.id}, null)}"></div>
```

이 프래그먼트는:
- 이미 첨부된 파일 목록을 조회/렌더링하는 로직이 전혀 없다(항상 빈 `<ul class="attached-files">`).
- `yona.CommentAttachmentsUpdate.js`가 기대하는 클래스(`.file-upload__input`,
  `.temporaryUploadFiles`, `.attachment-files`)를 쓰지 않는다(`.attach-wrap`/`input.file`/
  `.attached-files`로 완전히 다른 체계) — 이 스크립트를 그대로 로드해도 현재 마크업과는
  애초에 맞물리지 않는다.
- "알림 메일 받기" 체크박스(`send-notification-check`, 댓글 작성자 본인에게만 노출)도 없다.

**결과**: 첨부파일이 있는 댓글을 수정하려고 열면, 그 첨부파일들이 전부 안 보인다(삭제도
불가능하고, 이미 몇 개나 첨부돼 있는지도 알 수 없다) — 단순 UX 저하가 아니라 **기존
데이터(첨부파일)에 접근할 수 없게 되는 기능 손실**이다. 백엔드 데이터 자체는 멀쩡하다
(`AttachmentRepository.findByContainerTypeAndContainerId(...)`가 이미 존재 — 조회 자체는
가능, 그저 이 화면에 연결이 안 돼 있을 뿐).

## 범위

1. `common/commentUpdateForm.html`을 legacy 마크업(`.file-upload__input`/
   `.temporaryUploadFiles`/`.attachment-files`)에 맞게 다시 작성 — 이미 첨부된 파일 목록을
   백엔드에서 조회해 모델에 담아 렌더링(컨트롤러/뷰 양쪽 변경 필요 — `board/view.html`/
   `issue/view.html`이 댓글 목록을 렌더링하는 지점에서 각 댓글의 첨부파일 목록도 함께
   조회해 넘겨야 함).
2. `yona.CommentAttachmentsUpdate.js`를 `issue/view.html`/`board/view.html` 양쪽에
   `<script src>`로 로드(레거시와 동일 — 두 화면에서만 필요).
3. "알림 메일 받기" 체크박스(댓글 작성자 본인 조건부 노출) 포함 여부 — legacy와 동일하게
   포팅할지, 이 체크박스가 현재 알림 인프라와 실제로 연결돼 있는지부터 확인 필요.
4. 첨부파일 삭제 API가 현재 존재하는지 확인(`deleteAttachment()`가 호출하는
   `$.post(url)` 대상 엔드포인트) — 없으면 백엔드부터 추가.
5. `attachmentFile(...)` 파샬에 해당하는 Thymeleaf 프래그먼트 신규 작성(파일명/크기/
   삭제버튼 카드 UI).

**8) (조사 중 발견·해결, 이번 세션에서 가장 크고 심각했던 버그) `common/yobi.Files.js`·
`common/yobi.Attachments.js`가 site/layout.html의 전역 `scripts` fragment를 포함해 어느
템플릿에서도 `<script src>`로 로드된 적이 없었다** — 이 저장소가 `yobi.Markdown.js`에 대해
이미 명시적으로 문서화해둔 것과 **완전히 동일한 함정**(전역 레거시 번들 `yona-lib.js`
안에 박혀있는, EasyMDE(P3-46)를 전혀 모르는 구버전 사본이 대신 실행되고 있었음). 그 결과:
- 새 댓글/게시글 작성 폼에서 파일을 업로드하고 카드를 클릭해("본문에 넣기") 마크다운 링크를
  삽입해도, 그 삽입은 `yona-lib.js`의 구버전이 raw `<textarea>`에 직접 쓰는 것이었다.
  EasyMDE(CodeMirror)가 이 변경을 전혀 인지하지 못해(단방향 동기화, CodeMirror -> textarea만
  존재 — `yobi.ui.MarkdownEditor.js` 참고), 저장 버튼 클릭 등으로 에디터에서 포커스가
  빠지는 순간 CodeMirror가 "자신은 안 바뀐" 내부 버퍼를 textarea에 다시 덮어써 방금 넣은
  링크가 통째로 사라졌다 — **실제 서버에 제출되는 내용에서 첨부파일 참조가 사라지는
  데이터 손실급 버그**였다(Playwright로 실제 재현: 업로드 → 카드 클릭 → 코드미러 버퍼는
  링크 포함 확인 → 저장 버튼 클릭 → 서버가 받은 JSON 바디에 링크가 없음 `{"contents":""}`).
  같은 문제가 댓글 수정 폼(`yona.CommentAttachmentsUpdate.js`)에도 동일하게 있었다.
- 고친 방법: (a) `site/layout.html::scripts`에서 `yona-lib.js` 바로 다음 줄에
  `yobi.Files.js`/`yobi.Attachments.js`를 명시적으로 로드(`yobi.Markdown.js`와 동일한 순서
  원칙 — 반드시 `yona-lib.js`보다 뒤에 와야 전역 `yobi.Files`/`yobi.Attachments`가 이
  최신 버전으로 최종 덮어써짐). (b) 그것만으로는 부족해서(EasyMDE 인스턴스 조회 시점·
  호출 경로에 따라 CodeMirror API 분기 자체가 항상 타지 못하는 경우가 실측으로 확인됨)
  `yobi.Attachments.js`/`yona.CommentAttachmentsUpdate.js`의 링크 삽입/삭제 함수들
  (`_insertLinkToTextarea`/`_clearLinkInTextarea`/`_replaceLinkInTextarea`,
  `insertLinkIntoTextarea`/`removeLinkFromTextarea`)을 "먼저 raw 로직으로 최종 문자열을
  계산 → 그 문자열을 `easyMDE.value()`로 무조건 다시 밀어넣기" 방식으로 재작성해, 호출
  경로와 무관하게 raw textarea가 항상 최종 소스오브트루스가 되고 EasyMDE가 그 값을
  강제로 따라가도록 했다.
- **메모(참고용)**: 이 "raw 계산 -> easyMDE.value()로 강제 재동기화" 패턴은 P3-46
  8단계-3(atjs→Tribute.js, 멘션 자동완성)이 CodeMirror 레벨에서 프로그램적으로 텍스트를
  삽입해야 하는 것과 동일한 근본 문제를 겪을 가능성이 높다 — 그 단계 착수 시 이 패턴을
  그대로 재사용할 수 있다. 이번 세션 범위는 첨부파일 링크 삽입/삭제로 한정했고
  멘션/체크리스트 쪽은 손대지 않았다(사용자 지시로 범위 확정).

**실사용 검증(Playwright, `/tmp/.../scratchpad/pw/helpers.js` 재사용 로그인 헬퍼로 1회
종합 시나리오)**:

2. 저장된 댓글의 수정 폼을 열어 `.attachment-files .attached-file-marker` 1개 확인(같은
   세션에서 새로 발견한 컨테이너 이전 버그가 고쳐졌음을 실증).
3. 업로드 카드의 삭제 버튼 클릭 → raw/CodeMirror 버퍼 둘 다 링크가 사라짐 확인.
4. 이미 저장된 댓글의 수정 폼에서 `.file-upload__input`으로 새 파일 업로드 → 즉시 raw/

   반영됨 확인.
