  - (원본 열 3) yona 동치성과 무관 — legacy에 태그 관련 코드 0건, 완전 신규 기능. 착수 당시(2026-09-03) 계획 문서가 스스로를 "[[tickets/p3-10|P3-10]]"이라 칭했는데, 이 표의 [[tickets/p3-10|P3-10]]은 이미 2026-08-28에 "전체 의존성 최신 버전 업데이트"가 선점하고 있어 우연히 번호가 충돌한 단순 채번 실수였다 — 2026-09-07 완료 시점에 발견해 계획 문서를 이 표의 실제 빈 번호(P3-16)에 맞춰 정정했다(파일명도 `docs/yona-wiki/plans/p3-16-git-tags.md`로 리네임, frontmatter id도 갱신 — 두 개의 독립된 채번 체계가 있는 게 아니라 이 표(PARITY_BACKLOG.md)가 유일한 SSOT다)
  
  **완료** — 계획 문서의 "범위 확정" 절 참고. 서버: `domain/vcs/GitTag.kt`(신규 뷰모델) + `PlayRepository`/`GitRepository`/`SvnRepository`에 `getTagNames()`/`getTags()`/`deleteTag()`/`createTag()`(lightweight+annotated 둘 다 지원 — JGit `TagCommand.setAnnotated()`) 추가, `web/TagViewController.kt`(`GET /{owner}/{project}/tags` 목록 화면)/`TagApiController.kt`(`DELETE /{owner}/{project}/tags/{tag}` 웹 UI 액션, `BranchApiController.deleteBranch()`와 동일 권한(Operation.DELETE, 매니저/조직관리자 전용))/`TagRestApiController.kt`(`GET/POST/DELETE /api/v1/projects/{owner}/{project}/tags`, JGit `Repository.isValidRefName()`으로 경로 탈출/인젝션 방지) 신규, `ApiTokenAuthenticationFilter`에 `"tags" -> ResourceType.CODE` 스코프 매핑 추가. UI: `code/view.html`/`code/history.html`의 브랜치 셀렉터를 GitHub 방식의 브랜치/태그 통합 ref 셀렉터(`<optgroup>` 그룹 헤더)로 확장(레거시로 이식만 되고 미사용이던 `TemplateHelper.branchItemType()`/`branchInHtml()`을 실제로 배선), `code/tags.html`(신규 태그 목록 화면) + 브랜치/태그 탭 연결. 웹 UI에는 브랜치와 마찬가지로 "새 태그 만들기" 폼을 두지 않음(생성은 REST API/CLI 전용 — GitHub도 릴리즈 없이 독립된 새 태그 버튼을 두지 않고, 이 저장소의 브랜치도 생성 폼이 없다). CLI(`yona-cli`, 별도 저장소): `internal/api/tag.go` + `cmd/tag.go`로 `yona tag list/create/delete` 추가(`cmd/label.go`와 동일한 `internal/api/` 클라이언트 패턴). 테스트: `GitRepositorySpec`(도메인 로직 TDD) + `TagViewControllerSpec`/`TagApiControllerSpec`/`TagRestApiControllerSpec`(mockk 단위) + `TagRestApiControllerIntegrationSpec`(실제 bare 저장소+DB end-to-end, 경로 탈출 이름 400 검증 포함) + `ApiTokenScopedTagAuthorizationIntegrationSpec`(PAT 스코프 필터 통합) 전부 GREEN, 기존 `CodeViewControllerSpec`/`BranchViewControllerSpec`/`BranchApiControllerSpec` 회귀 없음 재확인. `yona-cli`는 `cmd/tag_test.go` + `go build/test/vet ./...`+`gofmt -l .` 전부 클린.
