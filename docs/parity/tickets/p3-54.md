# P3-54: `site/postList.html`/`site/issueList.html`이 작성자가 탈퇴(또는 authorLoginId가
null)한 게시글/이슈를 목록에 렌더링할 때 500 에러

## 배경

`site/postList.html`/`site/issueList.html`이 각각 다음과 같이 게시글/이슈 작성자를
조회한다:

```html
th:with="user=${userRepository.findByLoginId(post.authorLoginId).orElse(null)}"
th:with="user=${userRepository.findByLoginId(issue.authorLoginId).orElse(null)}"
```

`UserRepository.findByLoginId(loginId: String)`는 파라미터 타입이 non-null(Kotlin)이라
Spring Data의 null 안전성 검사기(`NullnessMethodInvocationValidator`)가 호출 자체를
`IllegalArgumentException("Parameter loginId ... must not be null")`으로 막는다.
`.orElse(null)`은 "조회했지만 못 찾았을 때"만 처리할 뿐, "애초에 null을 넘겨 호출이 실패하는
경우"는 막지 못한다. `post.authorLoginId`/`issue.authorLoginId`가 null인 레코드(작성자
탈퇴 등으로 발생 가능)가 하나라도 있으면 사이트 관리자 게시글/이슈 목록
(`/sites/postList`, `/sites/issueList`) 전체가 `TemplateProcessingException`으로 500
에러가 난다.

## 발견 경위

이 두 건은 이미 `docs/TWIRL_THYMELEAF_RENDERING_AUDIT_2026-09-11.md`(2026-09-11) 시점에
baseline 실패 3건 중 2건(`SiteAdminTemplateEquivalenceSpec`)으로 기록돼 있던 것으로,
이번 P3-48/50/51/52 작업과 무관한 기존 결함이다. 작업 완료 후 마지막 전체 회귀 스위트
(6,594건 중 실패 2건, 에러 0건)를 코디네이터가 재확인하며 재차 확인했다 — 4개 티켓의
변경분과는 파일이 전혀 겹치지 않음을 `git diff`로 직접 검증.

참고로 담당 TDD 에이전트가 이 감사 도중 자체적으로 RED→GREEN 수정(널 가드 삼항연산자
추가 + 전용 회귀 테스트 2건)까지 만들어뒀으나, **사용자 지시로 이번 라운드에서는 채택하지
않고 되돌렸다** — 백로그 등록만 하고 별도 라운드에서 착수하기로 결정.

## 제안하는 다음 단계

`th:with="user=${post.authorLoginId != null ? userRepository.findByLoginId(post.authorLoginId).orElse(null) : null}"`
식의 널 가드 추가(또는 `UserRepository`에 null-safe 오버로드 신설)로 간단히 해결 가능할
것으로 보인다 — 착수 시 TDD로 `authorLoginId`가 null인 게시글/이슈 픽스처를 만들어 RED를
먼저 확인한 뒤 진행할 것.

## 완료 로그 (2026-09-11)

"제안하는 다음 단계"에 적힌 대로 널 가드 삼항연산자로 수정했다.

### 근본 원인 재확인

`UserRepository.findByLoginId(loginId: String)`는 Kotlin non-null 파라미터라, Spring Data가
호출 시점에 `Parameter loginId ... must not be null`로 막는다. `post.authorLoginId`/
`issue.authorLoginId`가 null이면 `.orElse(null)`이 실행되기도 전에 `findByLoginId(null)`
호출 자체가 예외를 던져 `TemplateProcessingException`으로 화면 전체가 깨진다.

### 수정

- `src/main/resources/templates/site/postList.html` — `th:with="user=${post.authorLoginId
  != null ? userRepository.findByLoginId(post.authorLoginId).orElse(null) : null}"`.
- `src/main/resources/templates/site/issueList.html` — 동일 패턴(`issue.authorLoginId`).

### TDD

`SiteAdminTemplateEquivalenceSpec.kt`에 `[SiteAdmin-8]` describe 블록 신규 추가, 생성자에
`PostingRepository`/`ProjectRepository`/`IssueRepository` 주입:
- "site/postList: authorLoginId가 null인 게시글이 있어도 500 없이 렌더링돼야 한다" —
  `authorLoginId = null`인 `Posting` 픽스처로 재현.
- "site/issueList: authorLoginId가 null인 이슈가 있어도 500 없이 렌더링돼야 한다" —
  `authorLoginId = null`인 `Issue` 픽스처로 재현.

수정 전 두 테스트 모두 정확히 이 티켓이 지목한 `TemplateProcessingException:
"userRepository.findByLoginId(post/issue.authorLoginId).orElse(null)"`로 RED 확인 →
수정 후 GREEN 확인.

### Playwright 실브라우저 검증 (완료 시점 1회)

이 버그의 전제 조건(`authorLoginId = null`)은 현재 앱의 어떤 UI 플로우로도 도달할 수
없다(계정 삭제 시 관련 게시글/이슈의 `authorLoginId`를 null로 되돌리는 로직이 코드베이스
어디에도 없음 — 순수 방어적 수정 대상). 그래서 다음과 같이 실제 서버 + 실제 DB로 그
조건을 그대로 재현해 검증했다:
1. Playwright로 실제 회원가입(`p354admin`) + 프로젝트/게시글/이슈 생성(전부 실제 UI 폼
   제출).
2. `AUTO_SERVER=TRUE` H2에 직접 연결(`org.h2.tools.Shell`)해 (a) 그 계정을 SITE_ADMIN으로
   승격(사이트 관리자 화면 접근에 필요), (b) 방금 만든 게시글/이슈 딱 1건씩의
   `AUTHOR_LOGIN_ID`만 `NULL`로 변경(작성자 탈퇴 등으로 실제 발생 가능한 데이터 상태를
   재현 — 다른 컬럼은 전혀 손대지 않음).
3. 서버 재기동(설정 변경은 hot-reload 안 됨) 후 Playwright로 `p354admin` 로그인 →
   `/sites/postList`, `/sites/issueList` 접속.

결과: 두 화면 모두 `200 OK`로 정상 렌더링되고, 응답 본문에 방금 만든(현재는
`authorLoginId = null`인) 게시글/이슈 제목이 실제로 보임 — 수정 전 상태(재기동 전, 즉
버그가 있는 코드로 같은 데이터를 조회했을 때는 500)와 대조 확인.

```json
{
  "/sites/postList": { "status": 200, "containsOurPosting": true },
  "/sites/issueList": { "status": 200, "containsOurPosting": true }
}
```
