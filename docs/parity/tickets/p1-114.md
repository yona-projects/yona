## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P1-114**: `PullRequestViewController.viewChangesInternal()`/`viewPullRequest()`(tab=="changes")의 comment thread 노출에 yona `PullRequest.java:1063-1103 getCodeCommentThreadsForChanges()` 필터링을 적용.
  - yona 원본 재확인: `getCodeCommentThreadsForChanges(commitId)`는 `CodeCommentThread`(ranged)만 대상으로, commitId 지정 시 그 커밋 것만, 미지정("전체 변경사항") 시 커밋단위 스레드(`isCommitComment()`)와 outdated 스레드(git diff 비교, yona `CodeReviewServiceImpl.isThreadOutdated`가 [[tickets/p1-20|P1-20]]에서 이미 동일 로직 구현해둔 것을 재사용)를 제외. **그러나 `git/viewChanges.scala.html:142 renderNonRangedThreads(pull.commentThreads.toList, commitId, ...)`를 대조 중, yona는 ranged 스레드(필터링됨)와 `NonRangedCodeCommentThread`(PR 전체에 붙는 비-ranged 스레드, commitId 일치 시에만 노출·outdated 필터 없음)를 서로 다른 두 목록으로 분리 렌더링한다는 걸 발견** — yona 템플릿(`pullrequest/view.html`, `code/diff.html`)은 이 둘을 `commentThreads` 모델 속성 하나로 합쳐서 쓰므로, 초안대로 `filterIsInstance<CodeCommentThread>()`만 적용했으면 `NonRangedCodeCommentThread`가 통째로 누락되는 새 회귀가 생길 뻔함 — 두 필터를 각각 적용 후 합치는 `buildCommentThreadsForChanges(pullRequest, commitId)` 헬퍼로 정정.
  - `viewChangesInternal()`과 `viewPullRequest()`의 "changes" 탭 분기가 동일한 로직을 중복 소유하고 있던 것도 `buildCommentThreadsForChanges()` 공용화로 정리.
  - 테스트: `PullRequestViewControllerSpec.kt`에 신규 생성자 파라미터(`codeReviewService`) 반영 + 2건 추가(commitId 미지정 시 커밋단위/outdated 제외·non-ranged 포함, commitId 지정 시 해당 커밋 스레드만 포함) — 전부 통과, 기존 18건 회귀 없음.
  - **범위 외 발견, 백로그 등록**: PR "conversation" 탭이 댓글 스레드를 이벤트와 함께 타임라인으로 보여주는 기능([[tickets/p1-106|P1-106]]) 자체가 yona 원본(`git/view.scala.html`은 댓글 없이 이벤트만 표시)에는 없던 확장 기능이었음([[tickets/p2-39|P2-39]]) — 되돌릴지는 UX 영향이 있어 사용자 결정 대기.
