  계획서: [`docs/yona-wiki/plans/p3-12-mercurial-hg4j.md`](yona-wiki/plans/p3-12-mercurial-hg4j.md). 사용자가 지정한 라이브러리는 Maven Central의 구버전 TMate `org.tmatesoft.hg4j`가 아니라 **자체 개발 중인 [`github.com/search5/hg4j`](https://github.com/search5/hg4j)**이며, **인터페이스를 JGit과 동일하게 맞출 예정**이라고 확인됨 — 그렇다면 `domain/vcs/GitRepository.kt`의 구현 패턴을 hg4j API로 옮겨 적는 방식으로 `HgRepository : PlayRepository`를 구현 가능할 것으로 기대(실제 API 확정 전까지는 가정). `RepositoryService.getRepository()`의 GIT/SVN 이분기에 세 번째 분기 추가, 프로젝트 생성 폼에 VCS 옵션 추가, `GitAuthorizationFilter`/`SvnAuthorizationFilter`와 대칭인 `HgAuthorizationFilter` 신설까지가 yona 쪽 통합 범위. **가장 큰 미확정 사항**: `search5/hg4j`가 JGit의 `GitServlet`에 해당하는 프로토콜 서빙 컴포넌트(smart HTTP)까지 제공하는지, 아니면 저장소 읽기/쓰기 API만 제공하고 Mercurial wire protocol 자체는 yona가 직접 구현해야 하는지 — hg4j 저장소 진행 상황을 먼저 확인해야 착수 가능(사실상의 외부 블로커)

  - **브랜치/태그 CRUD (`domain/vcs/HgRepository.kt`)**: yona의 git 모양 "브랜치" 개념을
    Mercurial **bookmark**에 매핑(사용자가 이미 확정한 설계 — Mercurial의 진짜 named
    branch(`hg branch`, 커밋에 영구히 새겨짐)와는 별개 개념이라 재론의하지 않음. Bitbucket이 과거
    Mercurial을 git 모양 UI로 노출할 때 쓰던 것과 동일한 매핑, "모호하면 주류 forge 관례" 원칙에
    부합). hg4j의 `BookmarkCommand`(getBranches/createBranch/deleteBranch/getHeadBranch)와
    `TagCommand`/`TagsCommand`(getTagNames/getTags/createTag/deleteTag)로 실제 구현, `getRefNames()`도
    bookmark 이름 + "tip"을 반환하도록 갱신. `GitBranch`/`GitTag`는 기존 git 전용 값 객체를 그대로
    재사용(`refs/heads/`/`refs/tags/` 접두어 계약 동일하게 준수) — Hg 태그는 git의 annotated
    태그처럼 별도 태거 신원/GPG 서명이 없으므로 `tagger`/`message`는 항상 null, `annotated=false`로
    고정(지어내지 않음, `GitTag`의 기존 invariant와 일치). hg4j가 항상 끼워 넣는 pseudo-tag
    "tip"은 목록에서 걸러낸다. "tip"이라는 이름으로 브랜치/태그를 만들려는 시도, 이미 존재하는
    이름 재사용, 존재하지 않는 시작점은 전부 `IllegalArgumentException`으로 거절(실제 hg CLI의
    "the name 'tip' is reserved"/"already exists (use -f to force)" 동작을 근사). `HgRepositorySpec`
    신규 16 tests + 기존 14 tests = 30 tests GREEN.
  - **HTTP 서빙**: `web/HgController.kt`(신규) — hg4j `HgHttpWireServer`(순수 `HttpServlet`)를
    `SvnController`와 동일한 "프로젝트별 인스턴스 캐시" 패턴으로 감싼다(키는 `$owner/$project` —
    SVN의 owner당 하나와 달리 Hg는 저장소당 인스턴스 하나가 필요, `HgHttpWireServer` 생성자가
    hg4j 자체 `lib.HgRepository`를 직접 받는 구조라서). `web/HgServletRequestWrapper.kt`(신규) —
    `HgHttpWireServer.service()`가 `getRequestURI()` 하나만으로 라우팅을 결정하는데(루트 "/"=v2
    capabilities-discovery, "/api/"=v2 명령) Spring MVC 매핑 밑에서는 항상 원본 전체 경로가
    보이므로, `SvnServletRequestWrapper`와 동일한 이유로 저장소 루트 기준 상대경로를 만들어준다.
    라우트는 지시대로 `/hg/{owner}/{project}/**`(git/svn과 동일한 접두어 관례). OPTIONS 우회는
    불필요함을 `HgHttpWireServer` 소스로 직접 확인 후 의도적으로 생략(hg wire protocol은 순수
    GET/POST `?cmd=` 기반, WebDAV가 아님).
