## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-22 — P2-37**: 최초 등록(2026-08-21) 당시 "legacy도 동일 범위까지만 처리한다"고 판단했던 것이 재조사 결과 **오판이었음을 확인** — legacy `CommentThread.deleteByPullRequest(pullRequest)`(`CommentThread.java:236-240`)는 `pullRequest` FK만으로 스레드를 찾아 `thread.project` 값과 무관하게(원본이든 fork든 제3 프로젝트든) 무조건 지우는데, yona `ProjectServiceImpl.deleteProject()`는 `commentThreadRepository.findByProject(project)`로 **삭제 대상 프로젝트 소속 스레드만** 지우고 그 아래 `deletePullRequestCascade()`(PR 삭제 단위)에는 CommentThread 정리가 전혀 없었다 — fork(1단계만으로도 충분, `Project.delete()`의 `forkingProjects` 루프가 직계 fork의 `deletePullRequests()`를 호출하고 그 안에서 `CommentThread.deleteByPullRequest()`가 호출되므로 legacy는 fork→제3프로젝트 PR 시나리오를 완전히 커버함)가 제3 프로젝트로 보낸 PR뿐 아니라, **원본 프로젝트 자신이 보낸 PR(toProject≠자신)에 달린 스레드까지** 정리되지 않는 더 넓은 범위의 회귀였다(`CommentThread.pullRequest`가 `nullable=false`인데 `@OnDelete` cascade 지정이 없어, FK 제약이 있는 DB에서는 PR 삭제 자체가 무결성 위반으로 실패할 잠재 위험도 있었음).
  - `ProjectServiceImpl.deletePullRequestCascade(pullRequest)` 최상단에 `commentThreadRepository.deleteAll(commentThreadRepository.findByPullRequest(pullRequest))`를 추가 — legacy `CommentThread.deleteByPullRequest()` + `pullRequest.delete()` 순서(스레드 먼저, PR 나중) 그대로. 위쪽 `findByProject` 단계에서 이미 지워진 스레드(project==삭제 대상 프로젝트인 것)는 이 시점에 재조회해도 나오지 않으므로 중복 삭제 걱정 없이 안전하게 재사용된다 — project 단위 1차 정리 + PR 단위 2차 정리라는 legacy와 동일한 이중 커버리지 구조가 됨.
  - **범위를 넘어서지 않은 부분(legacy와 동일하게 남겨둠)**: fork-of-fork(손자 fork) 단계는 legacy도 재귀하지 않으므로 yona도 그대로 미처리 — 이 부분만은 최초 등록 당시 서술("동일 범위")이 정확했다.
  - 테스트(TDD, 레드 확인 후 그린): `ProjectServiceImplSpec.kt`의 두 기존 `deleteProject` 테스트("연관 데이터를 모두 정리한 뒤 프로젝트 자체를 삭제해야 한다", "이 프로젝트를 fork한 자식 프로젝트는...")에 `commentThreadRepository.findByPullRequest(...)` 스텁 추가(회귀 아님, 새 호출에 대한 스텁 보강) + fork PR 테스트에 `commentThreadRepository.deleteAll(listOf(forkThread))` 검증 신규 추가로 실제 fork→제3프로젝트 시나리오의 스레드 정리를 직접 증명.
  - 검증: `./gradlew test --tests "com.github.yonaprojects.yona.domain.project.ProjectServiceImplSpec"` 전체 통과, 전체 스위트 `./gradlew test` 통과(실패 0).
