# P1-55: IMAP 수신메일 폴링(`ImapMailboxPoller`)이 yona의 IDLE 우선+영속 UID 워터마크 방식 대신 `\Seen` 플래그를 자체 북마크로 쓰는 5분 주기 폴링으로 축약됨([[tickets/p0-02|P0-02]] 완료 로그에 "단순화"로만 명시, 정확한 위험도는 분석 안 돼 있었음)

## 원본 표 정보

- **우선순위 구분**: P1
- **상태(원본 체크박스)**: `[x]`
- **yona 근거**: `app/mailbox/MailboxService.java`(`startEmailListener`/`startEmailPolling`/`updateLastSeenUID`), `EmailHandler.java:69-86 handleNewMessages()`
- **yona 대상**: `domain/mail/ImapMailboxPoller.kt`
- **비고(원문)**: 사용자 요청으로 2026-08-20 코드 대조 분석. yona는 (1) IMAP `IDLE` 명령으로 실시간 push 수신, 서버가 IDLE 미지원일 때만 폴링(기본 5분)으로 폴백, (2) 진행 상황을 메일함의 `\Seen` 플래그가 아니라 **DB `Property`(`MAILBOX_LAST_SEEN_UID`/`MAILBOX_LAST_UID_VALIDITY`) 워터마크**로 별도 추적하며 폴더를 `READ_ONLY`로 열어 메일함 자체는 절대 건드리지 않는다(`getMessagesByUID(lastSeenUID+1, uidNext)`로 UID 구간 조회). 반면 yona `ImapMailboxPoller`는 폴더를 `READ_WRITE`로 열고 처리 후 `message.setFlag(SEEN, true)`를 직접 호출해 `\Seen` 자체를 진행 상황 표시로 재활용한다. 단순히 "실시간성이 떨어진다"보다 실질적으로 더 큰 문제 2가지를 확인: **(a) 외부 간섭에 취약** — 누군가(운영자 webmail 로그인, 다른 스크립트 등)가 yona의 폴러보다 먼저 메일을 읽어(`\Seen`으로 표시) 버리면 그 메일은 "이미 처리됨"으로 오인돼 영구히 스킵되며 이슈/댓글이 생성되지 않는데도 아무 에러도 안 남는다 — yona는 DB 워터마크가 메일함 상태와 완전히 독립적이라 이런 실패 경로 자체가 없음. **(b) 공유 자원 오염** — yona는 메일함을 읽기 전용으로 열어 다른 IMAP 클라이언트가 보는 읽음/안읽음 상태에 전혀 영향을 주지 않지만, yona는 폴링할 때마다 실제로 메일을 "읽음" 처리해 다른 클라이언트의 뷰를 바꿔버린다. (참고로 "처리 실패해도 워터마크/플래그를 전진시켜 재시도하지 않는다"는 점은 yona `handleMessage()`도 `catch(Exception)` 후 `updateLastSeenUID()`를 그대로 호출해 동일하게 동작하므로 이건 축약이 아니라 원본과 같은 동작.) **완료 — 아래 완료 로그 참고**

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-55**: IMAP 수신메일 폴링을 yona `MailboxService`/`EmailHandler`와 동일한 설계로 전면 재작업 — 사용자가 "축약하지 말고 원본과 같은 설계, 같은 코드를 가져오라"고 명시적으로 재지시.
  - **신규 `Property`(엔티티)/`PropertyRepository`/`PropertyService`**: yona `models/Property.java`(이름-값 범용 엔티티, `Property.Name` enum) 대응. yona도 실제로는 `MAILBOX_LAST_SEEN_UID`/`MAILBOX_LAST_UID_VALIDITY` 두 값에만 쓰여서(전체 코드베이스에서 이 두 값 말고 다른 사용처가 없음을 확인) 그대로 범용 key-value 엔티티로 이식하되 `PropertyName` enum도 이 두 값만 우선 두었다("Add property you need here"라는 yona 주석과 같은 취지 — 필요해지면 늘리면 됨).
  - **`ImapMailboxPoller` 전면 재작성**: `@PostConstruct`로 시작(`start()`, yona `MailboxService.start()`), `@PreDestroy`로 종료(`stop()`). 폴더를 항상 `READ_ONLY`로 열어 메일함 자체(다른 IMAP 클라이언트가 보는 읽음 상태)는 절대 건드리지 않는다 — 기존 버전의 핵심 문제(`\Seen` 플래그를 자체 북마크로 재활용해 외부에서 먼저 읽힌 메일을 영구 스킵하던 것)를 근본적으로 제거.
    - `handleNewMessagesAndStartListener()`: `handleNewMessages()`를 한 번 동기 실행한 뒤 `startEmailListener()`(IDLE) 시도, 실패하면 `startEmailPolling()`(폴백)로 전환 — yona와 동일한 순서.
    - `handleNewMessages()`: `PropertyService`에서 `lastUidValidity`/`lastSeenUid`를 읽어 `shouldFetchByUidRange()`(순수 함수로 분리, 단위테스트)가 true면 `getMessagesByUID(lastSeenUid+1, uidNext)`로 UID 구간만 조회 — yona `EmailHandler.handleNewMessages()`와 동일.
    - `startEmailListener()`: `IMAPStore.hasCapability("IDLE")` 확인 후 `MessageCountListener` 등록, 데몬 스레드에서 `folder.idle()`을 반복 호출하는 블로킹 루프 — `FolderClosedException`이면 `reopenFolder()`로 재연결, 그 외 예외면 스레드 중단. yona `MailboxService.startEmailListener()`의 idle 스레드와 동일한 구조.
    - `startEmailPolling()`: `TaskScheduler.scheduleWithFixedDelay(...)`(`yona.mailbox.imap.polling-interval-ms`, 기존 설정 키 그대로 재사용, 기본 5분) — yona가 Akka 스케줄러로 하던 걸 Spring `TaskScheduler`로 대체([[tickets/p1-27|P1-27]]에서 이미 사용자가 승인한 것과 동일한 유일한 예외 기조: 스케줄러 구현체만 프레임워크에 맞게 바꾸고 알고리즘/주기는 그대로).
    - `updateLastSeenUid()`: 처리 성공/실패와 무관하게 `finally`에서 호출(yona도 `handleMessage()`가 예외를 삼키고 `updateLastSeenUID()`를 그대로 호출 — 재시도 안 함은 legacy와 동일한 동작이라 그대로 유지). `advancedSeenUid()`(순수 함수로 분리, 단위테스트)가 "새 uid가 기존보다 클 때만 전진"을 판단.
    - `handleMessages()`: 크래시 시 메일을 건너뛰는 걸 막기 위해 UID 오름차순으로 정렬 후 처리 — yona 주석의 크래시 시나리오 설명과 동일한 이유로 그대로 이식.
  - **의존성 추가**: `spring-boot-starter-mail`이 `angus-mail`(yona의 `com.sun.mail.imap.IMAPFolder`에 대응하는 Jakarta Mail 구현체)을 `runtimeOnly`로만 끌어와 `IMAPFolder`/`IMAPStore`(IDLE, UID 조회)가 컴파일 시점에 안 보이는 문제가 있어 `build.gradle.kts`에 `implementation("org.eclipse.angus:angus-mail")` 명시 추가(버전은 Spring Boot 의존성 관리로 고정).
  - **`toInboundEmailMessage`/`extractBody`/`extractAttachments`([[tickets/p1-29|P1-29]]/[[tickets/p1-47|P1-47]]) 등 MIME 파싱 로직은 완전히 무변경** — 이번 작업은 오직 "언제, 어떻게 새 메일을 찾아내는가"의 재작업이라 이미 검증된 파싱 로직을 다시 건드릴 이유가 없었다.
  - 테스트: `PropertyServiceSpec.kt`(신규) 4 tests(get/getLong null 처리, set 신규/갱신). `ImapMailboxPollerSpec.kt`(생성자 시그니처 변경으로 컴파일 레드 확인 후 구현) — 기존 MIME 파싱 5 tests 무변경 유지 + `shouldFetchByUidRange` 4 tests(최초 실행/uidValidity 불일치/lastSeenUid 없음/정상 케이스) + `advancedSeenUid` 3 tests(최초/전진/전진 불필요 2가지) 신규, 총 12 tests. IDLE 스레드/실제 IMAP 연결 자체는 이 저장소의 다른 `*Config`류와 동일하게 순수 글루로 남겨 단위테스트 대상에서 제외(문서화됨). 커버리지: `shouldFetchByUidRange`/`advancedSeenUid` 둘 다 BRANCH 100%, `PropertyService` 전 메서드 LINE 100%.
  - 검증: `./gradlew test --tests "com.github.yonaprojects.yona.domain.mail.*" --tests "com.github.yonaprojects.yona.domain.support.*" --tests "com.github.yonaprojects.yona.YonaApplicationTests"` 전체 통과(신규 `Property` 엔티티/빈 배선 확인, `ImapMailboxPoller`는 `yona.mailbox.imap.enabled=false` 기본값이라 테스트 컨텍스트에 로드 안 됨 — 기존과 동일), `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공.
