## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-82**: 이슈 공유자(IssueSharer)의 READ 권한을 `IssueController`에 연결.
  - 구현 전 재확인([[tickets/p1-74|P1-74]] 교훈 적용): 최초 등록 문구는 "DRAFT/PRIVATE 이슈 한정"이었으나, yona `AccessControl.java`를 직접 읽어보니 `isAllowedIfSharer()`는 그런 제약이 없고 ISSUE_POST(및 그 부모, 하위 이슈의 경우)/ISSUE_COMMENT의 READ 판단 일반 분기(`:274-279`)에서 무조건 적용됨을 확인 — 백로그 문구를 정정한 뒤 구현.
  - `config/security/AccessControl.kt`에 `isAllowedIfSharer(issue, user)` 신규(이슈 자신의 `sharers` 또는, 하위 이슈면 `issue.parent.sharers`에 해당 유저가 있는지 확인 — yona `isAllowedIfSharer()`의 parent 우선 체크와 동일 순서).
  - `IssueController.kt`에 이슈 인지형 `checkReadPermission(project, issue, user)` 오버로드 추가(기존 프로젝트 레벨 체크 실패 시 sharer 체크로 폴백) — `getIssue()`/`getTimeline()` 두 곳에 배선(yona `IssueApp.java:250,299`의 `issue()`/`timeline()` 두 핸들러 모두 동일하게 `isAllowedIfSharer`를 포함한 READ 체크를 탐을 확인하고 둘 다 반영).
  - **부수적으로 발견·수정한 버그**: sharer가 채워진 `Issue`를 REST 응답으로 직접 직렬화하자 `Issue.sharers` ↔ `IssueSharer.issue` 순환 참조를 Jackson이 무한 중첩으로 시도해 `HttpMessageNotWritableException`(nesting depth 500 초과)이 발생 — 지금까지 `sharers`가 채워진 채로 컨트롤러 응답에 실린 적이 없어 드러나지 않았던 기존 결함. `IssueSharer.issue`에 `@JsonIgnore` 추가로 해결(반대 방향인 `Issue.sharers`는 클라이언트가 필요로 하는 정보라 유지).
  - **발견 후 별도 등록**: 같은 `issue()` 메서드를 읽다가 draft 이슈는 작성자 본인만 볼 수 있게 하는 별도 게이트(`AccessControl.isAllowed()`보다 먼저 실행)가 yona에 전혀 없음을 확인 — 이번 항목의 대상(공유자 READ 연결)과는 다른 결함이라 **[[tickets/p1-84|P1-84]]로 별도 등록**, 이후 완료됨(`[x]`).
  - 테스트: `IssueControllerSpec.kt` +3(비멤버라도 이슈 공유자면 상세 조회 허용/공유자도 멤버도 아니면 403/비멤버라도 공유자면 타임라인 조회 허용).
  - 검증: `./gradlew test --tests "com.github.yonaprojects.yona.web.IssueControllerSpec"` 23 tests 전체 통과.
