## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-53**: [[tickets/p1-52|P1-52]]의 `PullRequestEvent.oldValue`를 `lastCommitId` 전/후 쌍으로 축약했던 것을 사용자가 반려("yona도 yona의 메커니즘을 그대로 들고와서 적용") — yona `PullRequest.updateMerge()`/`updateMergedCommitId()`를 그대로 이식했다.
  - **yona 구조 재확인**: yona는 `attemptMerge()`(뷰 전용 — `PullRequestApp`이 페이지 렌더링마다 호출, 임시 브랜치로 fetch 후 삭제, DB에 아무것도 안 남김)와 `updateMerge()`(액터 전용 — PR 생성/관련 PR 재검사 시에만 호출, 소스를 영구 ref `refs/yobi/pull/{id}/head`로 fetch하고 충돌이 없으면 실제 "미리보기 병합 커밋"을 만들어 `refs/yobi/pull/{id}/merged` ref를 갱신, 그 커밋의 부모/자신 해시를 `mergedCommitIdFrom`/`mergedCommitIdTo`에 기록)을 처음부터 별개 메서드로 분리해뒀다. [[tickets/p1-52|P1-52]]에서 이미 확립한 "`attemptMerge()`는 부수효과 없는 미리보기라 손대지 않는다"는 경계를 그대로 지켜, `processMergeCheck()`가 호출하는 대상만 `attemptMerge()`에서 신규 `updateMerge()`로 교체했다(`attemptMerge()` 자체와 그 API 계약은 무변경).
  - **`createMergeCommitAndUpdateRef()`(신규, 공용 헬퍼)**: 기존 `merge()`(실제 병합 시)의 머지 커밋 생성+`refs/yobi/pull/{id}/merged` ref 갱신 로직(`CommitBuilder`+`ObjectInserter`+`RefUpdate`)을 그대로 추출 — `merge()`와 신규 `updateMerge()` 둘 다 "머지 커밋을 만들어 이 ref를 갱신"하는 동일한 절차를 쓰므로 중복 없이 공유. `merge()`는 이 헬퍼를 호출하도록 리팩터링만 하고 동작은 그대로(기존 테스트 무변경 통과로 확인).
  - **`updateMerge()`(신규, private)**: yona `PullRequest.updateMerge()` 그대로 — 소스를 `refs/yobi/pull/{id}/head`로 fetch, 충돌 없으면 `createMergeCommitAndUpdateRef()`로 미리보기 병합 커밋 생성 후 `mergedCommitIdFrom`/`mergedCommitIdTo` 기록, 있으면 `setConflictStateOfPullRequest()`. 커밋 작성자는 yona가 `Config.getSiteName()`/`getSystemEmailAddress()`(사이트 시스템 계정, 실제 push한 사용자가 아님)를 쓰는 것과 동일하게 `PersonIdent(siteName, "yona@yona.io")`로 고정(신규 `@Value("\${yona.site-name:Yona}")` 주입) — `merge()`(실제 병합, `PersonIdent(updater.name, updater.email)`)와는 의도적으로 다른 신원.
  - **`recordCommitChangedEvent()` oldValue 계산 교체**: `beforeLastCommitId` 대신 `beforeMergedCommitIdTo`(재검사 전 `mergedCommitIdTo`)를 캡처해 `getCommitEventOldValue(oldMergeCommitId, newMergeCommitId)`와 동일하게 "이전,새" 쌍으로 조립(이전 값이 없으면 `null`).
  - **부수 효과로 활성화된 기존 코드**: `getDiff(pullRequest)`가 이미 `if (mergedCommitIdFrom != null && mergedCommitIdTo != null)`일 때 그 고정 스냅샷으로 diff를 계산하는 분기를 갖고 있었지만(과거 세션에서 미리 준비해둔 것으로 보임) `merge()` 전엔 항상 null이라 죽은 코드였다 — 이번 변경으로 OPEN 상태에서도 재검사 한 번만 거치면 이 분기가 실제로 켜진다.
  - 테스트: `PullRequestServiceSpec.kt` +1(`processMergeCheck`를 두 번 호출 — 1차는 `mergedCommitIdFrom`/`mergedCommitIdTo`가 채워지고 `PullRequestEvent.oldValue`는 `null`, 소스에 새 커밋을 추가한 2차는 `mergedCommitIdTo`가 갱신되고 새 `PullRequestEvent.oldValue`가 "이전,새" 쌍인지 확인) — 레드(`mergedCommitIdFrom shouldNotBe null` 실패) 확인 후 구현. 기존 [[tickets/p1-52|P1-52]] 테스트 3건과 `merge()`/`attemptMerge()` 관련 기존 테스트 전부 무변경 통과. 커버리지: `updateMerge` LINE 91%(31/34), `createMergeCommitAndUpdateRef` LINE 95%(21/22), `recordCommitChangedEvent` LINE 100% — 미달분은 ref 갱신 실패 등 기존 `merge()`에서도 미검증이던 것과 동일한 방어 분기.
