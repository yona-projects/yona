# P3-44: 로그아웃 성공 시 302 리다이렉트 대신 204가 반환됨

## 배경

CSRF 재활성화 작업(`docs/CSRF_INVESTIGATION_2026-09-10.md`) 중 `LogoutCsrfIntegrationSpec.kt`를
작성하는 과정에서 발견된, CSRF와는 무관한 기존 결함이다.

`SecurityConfig.kt:255-258`의 로그아웃 설정:

```kotlin
.logout { logout ->
    logout
        .logoutUrl("/users/logout")
        .logoutSuccessUrl("/users/loginform?logout")
}
```

`.logoutSuccessUrl(...)`만 지정하고 커스텀 `LogoutSuccessHandler`를 등록하지 않았는데, 실제로는
로그인 페이지(`/users/loginform?logout`)로 302 리다이렉트되지 않고 **204 No Content**가 반환된다.
`LogoutCsrfIntegrationSpec.kt`에서 CSRF를 disable()한 상태로도 동일하게 재현을 확인했다 —
CSRF 재활성화와 무관한 기존 버그다.

`site/layout.html`의 로그아웃 링크는 이번 CSRF 작업으로 `<a href="/users/logout">`(GET)에서
`.js-logout-link` 클릭 핸들러(`$.post`, `site/layout.html :: scripts`)로 바뀌었다. 브라우저의
기본 폼/링크 네비게이션이 아니라 AJAX POST이므로, 응답이 204여도 사용자 눈에 당장 크게 티가
나지는 않는다(페이지 전환이 없을 뿐). 다만 원래 의도(로그인 페이지로 리다이렉트해 "로그아웃되었습니다"
안내를 보여주는 것, `?logout` 쿼리 파라미터가 그 용도로 보임)가 지금은 전혀 동작하지 않는다.

## 요구사항

1. 실패하는(RED) 테스트로 현재 동작(204 반환, 302/Location 헤더 없음)을 먼저 확정 재현한다 —
   `LogoutCsrfIntegrationSpec.kt`를 참고하되, 이번엔 상태 코드와 `Location` 헤더까지 명시적으로
   검증하는 스펙으로 작성(기존 스펙은 204를 "정상"으로 간주하고 있으므로 그대로 재사용하면 안 되고,
   이번 티켓 작업 후에는 302로 기대값을 바꿔야 한다).
2. 왜 `SimpleUrlLogoutSuccessHandler`(또는 이 앱이 실제로 쓰는 핸들러)가 302 대신 204를 내는지
   근본 원인을 코드/설정에서 직접 확인한다(추측 금지) — 예: 컨텐츠 협상(content negotiation)
   설정이 AJAX/API 요청으로 오판하는지, 별도 `RequestMatcher`/`ExceptionHandlingConfigurer`/
   `HttpStatusReturningLogoutSuccessHandler`류가 개입하는지, 혹은 다른 원인인지.
3. 로그인 페이지(`/users/loginform?logout`)로 정상적으로 302 리다이렉트되도록 수정한다.
4. `LogoutCsrfIntegrationSpec.kt`를 204 기대값에서 302+`Location` 기대값으로 갱신하고, GREEN
   전환을 확인한다.
5. `.js-logout-link` 클릭 핸들러(`site/layout.html :: scripts`)가 AJAX POST를 쓰고 있으므로,
   302 응답을 받았을 때 브라우저가 실제로 로그인 페이지로 이동하도록 JS 쪽도 함께 손봐야 한다
   (예: `$.post` 성공 콜백에서 `location.href = '/users/loginform?logout'`로 이동, 또는 애초에
   AJAX 대신 폼 제출 방식으로 전환 — 둘 중 더 낫다고 판단되는 쪽을 선택하고 근거를 남긴다).
6. 전체 회귀(`./gradlew test -Dyona.it.db=h2`)로 기존 스위트(현재 6,494건 GREEN 상태)가 계속
   통과하는지 확인한다.

## 완료 로그

### 1. RED — 현재(수정 전) 동작 재확인

`LogoutCsrfIntegrationSpec.kt`의 로그아웃 응답 검증에 `logoutResponse.statusCode() shouldBe 204`와
`logoutResponse.headers().firstValue("Location").isPresent shouldBe false` 두 단언을 명시적으로
추가해 실행 — 수정 전 코드로 통과함을 확인(즉 204, `Location` 헤더 없음이 실제 현재 동작임을
재확인). 위 두 단언은 이후 4단계에서 302/`Location` 기대값으로 교체됐다.

### 2. 근본 원인 (추측 없이 라이브러리 소스로 직접 확인)

`spring-security-config-7.1.1-sources.jar`(실제 의존 버전 — Spring Boot 4.1.1이 끌어오는
spring-security-web/config 7.1.1)의 `HttpBasicConfigurer.java`를 열어 확인:

```java
private void registerDefaultLogoutSuccessHandler(B http, RequestMatcher preferredMatcher) {
    LogoutConfigurer<B> logout = http.getConfigurer(LogoutConfigurer.class);
    if (logout == null) return;
    logout.defaultLogoutSuccessHandlerFor(
        postProcess(new HttpStatusReturningLogoutSuccessHandler(HttpStatus.NO_CONTENT)), preferredMatcher);
}
```

`HttpBasicConfigurer.init()`이 `registerDefaults()`에서 항상 이 메서드를 호출한다. 즉 `SecurityConfig.kt`가
`.httpBasic { }`를 호출하는 순간(HTTP Basic 자체를 쓰든 안 쓰든 무조건 `init()`은 실행됨), `LogoutConfigurer`에
"이 요청은 204로 응답하라"는 기본 매핑이 자동 등록된다. `preferredMatcher`는
`OrRequestMatcher(X-Requested-With: XMLHttpRequest, (Accept가 text/html이 아님) AND (atom/xml·form-urlencoded·json·octet-stream·xml·multipart·text/xml 중 하나), Accept가 정확히 */*)`이고,
`HeaderContentNegotiationStrategy`는 `Accept` 헤더가 아예 없는 요청도 `*/*`로 협상하므로 여기 포함된다.

`LogoutConfigurer.createDefaultSuccessHandler()`(같은 jar의 `LogoutConfigurer.java`)는:

```java
private LogoutSuccessHandler createDefaultSuccessHandler() {
    SimpleUrlLogoutSuccessHandler urlLogoutHandler = new SimpleUrlLogoutSuccessHandler();
    urlLogoutHandler.setDefaultTargetUrl(this.logoutSuccessUrl);
    if (this.defaultLogoutSuccessHandlerMappings.isEmpty()) return urlLogoutHandler;
    DelegatingLogoutSuccessHandler successHandler = new DelegatingLogoutSuccessHandler(this.defaultLogoutSuccessHandlerMappings);
    successHandler.setDefaultLogoutSuccessHandler(urlLogoutHandler);
    return successHandler;
}
```

`.logoutSuccessUrl(...)`만 쓰면 `this.logoutSuccessHandler` 필드가 null이라 이 메서드가 호출되는데,
`httpBasic{}`이 이미 매핑을 채워뒀으므로 `DelegatingLogoutSuccessHandler`로 감싸진다 — 요청이
`preferredMatcher`에 맞으면 우리가 설정한 URL 대신 204 핸들러(`HttpStatusReturningLogoutSuccessHandler`)가
선택된다. **`SimpleUrlLogoutSuccessHandler` 자체는 정상 동작한다** — 실측으로 직접 검증: 이 진단
과정에서 `.logoutSuccessHandler { ... SimpleUrlLogoutSuccessHandler() ... }`로 동일 객체를 직접
호출하도록 임시로 바꿔 실행한 결과 `isCommitted=false status=200` → 핸들러 실행 후
`isCommitted=true status=302`로 정확히 302를 반환함을 확인했다(임시 진단 코드는 이후 제거).

실제 재현 경로: `site/layout.html::scripts`의 `.js-logout-link` 핸들러는 jQuery `$.post`를 쓰는데,
jQuery는 AJAX 요청에 `X-Requested-With: XMLHttpRequest` 헤더를 자동으로 붙인다 — 이 헤더 하나만으로도
`preferredMatcher`(X_REQUESTED_WITH 매처)에 걸려 204로 새어나간다. `LogoutCsrfIntegrationSpec.kt`의
테스트 요청은 `X-Requested-With`를 붙이지 않지만 `Accept` 헤더 자체를 생략하므로 `*/*` 협상 경로로
동일하게 204에 걸린 것도 확인했다. 즉 CSRF와는 완전히 무관하고, `httpBasic()` 활성화 자체가 원인이었다.

### 3. 수정 — `SecurityConfig.kt`

`.logout { }` 블록에서 `.logoutSuccessUrl("/users/loginform?logout")` 대신
`.logoutSuccessHandler(SimpleUrlLogoutSuccessHandler().apply { setDefaultTargetUrl("/users/loginform?logout") })`로
핸들러를 직접 지정했다. `LogoutConfigurer.getLogoutSuccessHandler()`는 필드가 non-null이면 그 값을
즉시 반환해 `defaultLogoutSuccessHandlerMappings`(= httpBasic이 채워둔 204 매핑)를 아예 참조하지
않으므로, 이후 어떤 요청 특성(Accept/X-Requested-With)이든 항상 우리가 지정한 302 리다이렉트가 나간다.
`import org.springframework.security.web.authentication.logout.SimpleUrlLogoutSuccessHandler` 추가.

### 4. GREEN — `LogoutCsrfIntegrationSpec.kt` 갱신

1단계에서 추가한 두 RED 단언을 `logoutResponse.statusCode() shouldBe 302` +
`logoutResponse.headers().firstValue("Location").orElse(null) shouldBe "http://localhost:$port/users/loginform?logout"`로
교체하고, describe/it 설명 및 스펙 상단 주석(더 이상 "부수 발견, 손대지 않음"이 아니라 근본 원인과
수정 내용을 반영)도 갱신. `./gradlew test -Dyona.it.db=h2 --tests "...LogoutCsrfIntegrationSpec"`
GREEN 확인.

### 5. `site/layout.html`의 `.js-logout-link` — AJAX 콜백 리다이렉트로 유지(폼 제출 전환 안 함)

서버가 이제 실제 302를 반환하지만, `.js-logout-link` 핸들러는 `<a>` 클릭을 가로챈 XHR(`$.post`)이라
브라우저가 same-origin 302를 자동으로 "조용히" 따라가 버릴 뿐(XHR 표준 동작) 주소창/화면 전환은
일어나지 않는다 — 그래서 302 자체만으로는 여전히 사용자 눈엔 아무 일도 안 일어난다. 두 방식을
검토했다:

- **A) AJAX 콜백에서 `location.href`로 이동** (선택)
- B) `<a>`를 `<form method="post">` 자동 제출로 전환

A를 선택한 이유: 기존 코드가 이미 이 골격(`$.post(...).always(...)` 안에서 `window.location.href`
이동)을 갖추고 있어 마크업/CSS 변경이 전혀 없고, 로그인 모달 등 이 링크 주변의 다른 상호작용과
일관성이 유지된다. B(폼 제출)로 바꾸면 `<a>` 태그를 `<form>`으로 바꾸고 CSS/레이아웃(`user-menu-wrap`
안 인라인 배치)을 다시 맞춰야 해서 "로그아웃 관련 부분만 최소 침습으로" 수정하라는 제약과 맞지
않고, 로그아웃 자체의 동작(세션 무효화+302)에 실질적 이득도 없다.

다만 기존 코드는 `.always()`라서 요청이 실패해도(네트워크 오류, CSRF 토큰 만료로 403 등) 무조건
`/users/loginform?logout`으로 이동시켜 "로그아웃됨" 화면을 보여줬다 — 실제로는 세션이 살아있을 수
있는데도 사용자에게 로그아웃된 것처럼 오인시키는 결함이라 `.done()`(성공/2xx만) + `.fail()`(실패 시
`window.alert`로 안내, 화면 유지)로 좁혔다. 이는 순수 방어적 개선으로 기존 정상 경로(200대 응답)
동작은 그대로다.
