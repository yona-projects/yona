# P3-69: PR 뷰 화면의 머지 가능 여부(mergeable/conflict) 상태가 실시간 자동 갱신되지 않음

## 배경

legacy(`app/views/git/view.scala.html`, `service/yobi.git.View.js`)는 PR 뷰 화면에서
10초 간격(`nStateUpdateInterval`)으로 `GET /:owner/:project/pullRequest/:id/state`
(`PullRequestApp.pullRequestState`)를 폴링해 `#state` div(`git/partial_state.scala.html`)를
새 HTML로 갈아끼우고, 결과에 따라 "Accept(머지)" 버튼 표시 여부(`isConflict`)도 함께
갱신했다 — 페이지를 새로고침하지 않아도 다른 사람이 브랜치를 바꾸면 머지 가능 여부가
자동으로 업데이트된다.

현재 yona의 `pullrequest/view.html`도 legacy와 동일한 구조로 `<div id="state">`가
`pullrequest/partial_state :: state(...)` 프래그먼트를 감싸고 있고(101행),
`PullRequestViewController.viewPullRequest()`(264행)가 `pullRequestService.attemptMerge()`로
매 페이지 로드마다 충돌 여부를 **실제로 재계산**해서 넘겨준다(`addCommonPrAttributes()`가
`isAcceptable`/`disabledAcceptReason` 등을 계산). 즉 **서버측 재계산 로직은 완전히
동치**이지만, 이 상태를 **주기적으로 다시 조회하는 클라이언트측 폴링 메커니즘 자체가
없다** — 페이지를 열어둔 채로는 상태가 절대 갱신되지 않고, 새로고침해야만 최신 상태를
본다.

**참고**: 백엔드에는 이미 push/머지 이벤트가 생길 때마다 `isConflict`를 재계산하고
`notifyMergeConflictChanged()`(P1-71)로 워처에게 알림을 보내는 이벤트 기반 경로가 있다 —
다만 이건 "알림함에서 상태 변화를 안다"는 것이지 "지금 열어서 보고 있는 PR 페이지가
자동으로 갱신된다"는 것과는 다르다. 사용자 확인 결과 legacy와 동일한 폴링 UX를
구현하기로 결정(2026-09-14).

## 구현 방향(조사 완료)

- **신규 서버 엔드포인트 필요**: legacy `pullRequestState`에 대응하는 GET 엔드포인트가
  현재 `PullRequestViewController`/`PullRequestApiController`에 없다(전체 매핑 목록 확인
  완료). `viewPullRequest()`의 `attemptMerge()` + `addCommonPrAttributes()` 계산 로직을
  재사용해 `pullrequest/partial_state` 프래그먼트만 다시 렌더링해 반환하는 엔드포인트를
  추가해야 한다(예: `GET /{owner}/{projectName}/pull/{number}/state`, 라우트 이름은
  기존 관례에 맞게 자유롭게 결정).
- **클라이언트측**: `yona.pullrequest.Write.js`는 create/edit 폼 전용이라 view 페이지와는
  무관하다 — PR view 페이지 전용 폴링 로직을 새로 작성해야 한다(파일 위치는
  `service/yona.pullrequest.View.js` 신설 또는 기존 관례에 맞는 곳에 배치, `$yona.loadModule`
  경유로 배선). Legacy의 `yobi.Interval`(단순 `setInterval`/`clearInterval` 래퍼) 자체는
  포팅 대상이 아니다 — 이미 P3-52에서 "재구현됨/필요없음"으로 정리된 유틸리티이므로 네이티브
  `setInterval`을 직접 써도 무방.

## 완료 기준

- [ ] PR 뷰 화면(`pullrequest/view.html`, overview 탭)에서 10초 간격(legacy와 동일 주기)으로
      `#state` 프래그먼트를 재조회해 내용이 바뀌었을 때만 DOM을 교체한다(legacy의 "HTML이
      바뀐 경우만 갱신" 최적화도 동일하게 재현).
- [ ] 갱신 시 "Accept(머지)" 버튼의 표시/비활성 여부도 함께 갱신된다(`isAcceptable`/
      `disabledAcceptReason` 최신값 반영).
- [ ] PR이 닫히거나(closed) 병합됐거나(merged) 병합 진행 중(isMerging)인 상태에서는 legacy와
      동일하게 폴링을 하지 않거나 멈춘다(불필요한 폴링 방지 — `partial_state`의 최상위
      조건문 참고).
- [ ] TDD로 진행: 신규 엔드포인트/프래그먼트 재렌더링 검증 스펙 + 폴링 스크립트 배선 검증
      스펙(RED→GREEN). 실제 브라우저(Playwright)로 한쪽 브라우저 세션에서 브랜치 상태를
      바꾼 뒤 다른 세션에서 페이지를 새로고침하지 않고 상태가 자동 갱신되는지 실측 확인.
- [ ] 기존 PR 관련 스펙 회귀 없음(`PullRequestViewControllerSpec` 등 개별 `--tests`로 확인).
