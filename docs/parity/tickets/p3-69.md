# P3-69: PR 뷰 화면의 머지 가능 여부(mergeable/conflict) 상태가 실시간 자동 갱신되지 않음

## 배경

legacy(`app/views/git/view.scala.html`, `service/yobi.git.View.js`)는 PR 뷰 화면에서
10초 간격(`nStateUpdateInterval`)으로 `GET /:owner/:project/pullRequest/:id/state`
(`PullRequestApp.pullRequestState`)를 폴링해 `#state` div(`git/partial_state.scala.html`)를
새 HTML로 갈아끼우고, 결과에 따라 "Accept(머지)" 버튼 표시 여부(`isConflict`)도 함께
갱신했다 — 페이지를 새로고침하지 않아도 다른 사람이 브랜치를 바꾸면 머지 가능 여부가
자동으로 업데이트된다.

현재 yona의 `pullrequest/view.html`도 legacy와 동일한 구조로 `<div id="state">`가
`pullrequest/partial_state :: state(...)` 프래그먼트를 감싸고 있고(101행),
`PullRequestViewController.viewPullRequest()`(264행)가 `pullRequestService.attemptMerge()`로
매 페이지 로드마다 충돌 여부를 **실제로 재계산**해서 넘겨준다(`addCommonPrAttributes()`가
`isAcceptable`/`disabledAcceptReason` 등을 계산). 즉 **서버측 재계산 로직은 완전히
동치**이지만, 이 상태를 **주기적으로 다시 조회하는 클라이언트측 폴링 메커니즘 자체가
없다** — 페이지를 열어둔 채로는 상태가 절대 갱신되지 않고, 새로고침해야만 최신 상태를
본다.

**참고**: 백엔드에는 이미 push/머지 이벤트가 생길 때마다 `isConflict`를 재계산하고
`notifyMergeConflictChanged()`(P1-71)로 워처에게 알림을 보내는 이벤트 기반 경로가 있다 —
다만 이건 "알림함에서 상태 변화를 안다"는 것이지 "지금 열어서 보고 있는 PR 페이지가
자동으로 갱신된다"는 것과는 다르다. 사용자 확인 결과 legacy와 동일한 폴링 UX를
구현하기로 결정(2026-09-14).

## 구현 방향(조사 완료)

- **신규 서버 엔드포인트 필요**: legacy `pullRequestState`에 대응하는 GET 엔드포인트가
  현재 `PullRequestViewController`/`PullRequestApiController`에 없다(전체 매핑 목록 확인
  완료). `viewPullRequest()`의 `attemptMerge()` + `addCommonPrAttributes()` 계산 로직을
  재사용해 `pullrequest/partial_state` 프래그먼트만 다시 렌더링해 반환하는 엔드포인트를
  추가해야 한다(예: `GET /{owner}/{projectName}/pull/{number}/state`, 라우트 이름은
  기존 관례에 맞게 자유롭게 결정).
- **클라이언트측**: `yona.pullrequest.Write.js`는 create/edit 폼 전용이라 view 페이지와는
  무관하다 — PR view 페이지 전용 폴링 로직을 새로 작성해야 한다(파일 위치는
  `service/yona.pullrequest.View.js` 신설 또는 기존 관례에 맞는 곳에 배치, `$yona.loadModule`
  경유로 배선). Legacy의 `yobi.Interval`(단순 `setInterval`/`clearInterval` 래퍼) 자체는
  포팅 대상이 아니다 — 이미 P3-52에서 "재구현됨/필요없음"으로 정리된 유틸리티이므로 네이티브
  `setInterval`을 직접 써도 무방.

### 실측 검증(Playwright) — 실제 10초를 기다리는 방식을 택함

이유: 폴링 함수를 직접 호출하는 대안도 고려했으나, `docs/guide/technical/
javascript-module-guide.md`에 따르면 `$yona.loadModule`은 모듈을 `new`로 생성만 할 뿐 별도
공개 인터페이스를 반환하지 않는 관례라, 테스트만을 위해 내부 함수를 전역에 노출시키는 것은
프로덕션 코드에 테스트 전용 훅을 추가하는 셈이라 배제했다. 대신 실제 폴링 주기(10초)를
그대로 둔 채 실제 대기하는 쪽을 택했다.

절차: `SPRING_PROFILES_ACTIVE=h2`로 앱을 로컬 구동(`YONA_DATA`/`YONA_GIT_BASE_DIR`을
스크래치패드 경로로 격리) → 최초 관리자 부트스트랩(`/bootstrap-setup`) → 프로젝트 생성
(`admin/demo-pr`, GIT) → 로컬에서 bare 저장소에 `main`/`feature` 두 브랜치를 실제로 push →
REST API(`POST /api/projects/1/pullrequests`)로 feature→main PR 생성(최초엔 충돌 없음) →
Playwright(Chromium)로 로그인 후 PR 뷰 페이지를 열어둔 채 유지 → **다른 터미널에서(같은
브라우저 세션을 새로고침하지 않고 열어둔 채) `main` 브랜치에 실제로 충돌하는 커밋을 직접
push** → 페이지를 새로고침하지 않고 10~20초 관찰.

- **실측 결과**: `#state`가 "This pull request can be merged safely."(초록)에서
  "A conflict occurred when merging..."(빨강, 충돌 해결 가이드 포함)로 자동 전환됨을
  확인(`pollingRequestCount=2`, 즉 10초·20초 두 번째 폴링에서 실제로 갱신). 같은 응답에서
  `#pr-accept-button`도 `<a id="btnAccept">`(활성 병합 버튼)에서
  `<button class="ybtn ybtn-disabled" title="A conflict occurred when merging...">`
  (비활성, 최신 사유 반영)로 함께 바뀜을 확인 — 완료 기준 2번 실측 완료.
- PR을 `CLOSED`로 전환한 뒤 새로고침한 세션에서는 15초 동안 `/pull/{number}/state` 요청이
  **0건**(`pollingRequestCountWhileClosed=0`)임을 확인 — 완료 기준 3번(폴링 미시작) 실측 완료.

### 삽질 기록 — Kotlin 컨트롤러 스펙(mockk `standaloneSetup`)만으로는 템플릿 렌더링 버그를 못 잡음

`partial_state_poll.html`의 최상위 `th:fragment="poll(project, pull, currentUser, ...)"`을
처음에 `partial_state.html`/`partial_info.html` 내부에서 쓰는 지역 파라미터명 그대로
`pull`로 지었다. 그런데 이 프래그먼트는 컨트롤러가 `"pullrequest/partial_state_poll ::
poll"`을 뷰 이름으로 직접 반환하는 방식(다른 템플릿이 인자를 명시해 `th:insert`로 호출하는
게 아님)이라, `partial_merge_result.html`의 기존 관례(`mergeResult(fromProject,
pullRequestTitle, ...)` — 파라미터명이 컨트롤러 Model의 속성명과 정확히 일치)를 따라야
했는데, 컨트롤러가 실제로 채우는 모델 속성명은 `pr`이지 `pull`이 아니었다. `PullRequestViewControllerSpec`은
`MockMvcBuilders.standaloneSetup(...)`(실제 Thymeleaf `ViewResolver` 없이 뷰 이름 문자열과
모델 맵만 검증)이라 이 불일치를 전혀 잡지 못하고 GREEN이었다 — 실제로는 요청마다 500
(`Exception evaluating SpringEL expression: "pull.state.name()"`, `pull`이 null로
바인딩됨)이 났다. 위 Playwright 실측 절차 중 `curl`로 `/pull/1/state`를 직접 호출해 500을
먼저 재현하고 `bootrun.log`의 Thymeleaf 스택트레이스로 원인을 특정한 뒤, 파라미터명을
`pr`로 고쳐 해결했다(내부에서 `partial_state`/`partial_info` 프래그먼트를 호출할 때 넘기는
인자도 `${pull}` → `${pr}`로 함께 수정). **교훈**: mockk 기반 컨트롤러 스펙은 뷰 이름/모델
속성 존재 여부만 검증하고 실제 템플릿 렌더링(SpEL 바인딩)은 검증하지 않는다 — 프래그먼트
파라미터명을 모델 속성명과 다르게 짓는 실수는 이런 스펙만으로는 절대 못 잡으며, 이번처럼

### 범위 밖 — 고치지 않고 기록만 남기는 것

- Playwright 실측에 쓴 로컬 앱 구동(H2 프로필, 스크래치패드 격리 데이터)은 이번 검증
  전용이며 저장소에 흔적을 남기지 않았다(스크래치패드 파일, 실행 중이던 프로세스는 검증 후
  종료).
- legacy `yobi.git.View.js`의 `beforeRequest`에서 accept 버튼을 즉시 `disabled` 처리하는
  NProgress 연동은 yona에 NProgress 자체가 없어(이 저장소 전수 확인 없이도 기존
  `#btnAccept` 클릭 핸들러에 이미 없었음을 확인) 포팅하지 않았다 — 이 티켓 범위(주기적
  상태 폴링) 밖이라 신규로 추가하지 않았다.
