# P1-60: UI에서 직접 작성한 리소스(이슈/리뷰 댓글 등)의 첫 알림 메일에 대한 IMAP 답장이 In-Reply-To/References만으로는 해당 스레드로 연결되지 않음

## 원본 표 정보

- **우선순위 구분**: P1
- **상태(원본 체크박스)**: `[x]`
- **yona 근거**: `app/mailbox/EmailHandler.java findResourcesByMessageId()`(`OriginalEmail` 미스 시 `IMAPMessageUtil.getIdLeftFromMessageId()`+`Resource.findByPath()` 폴백), `getThreads()`(`REVIEW_COMMENT` → 컨테이너 리다이렉트)
- **yona 대상**: `domain/mail/IncomingMailProcessingService.kt`(`resolveThreads`)
- **비고(원문)**: **완료** — 아래 완료 로그 참고. 최초 분석("발신 시점에 `OriginalEmail`을 기록해야 한다")은 부정확했음이 구현 중 확인됨

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-60**: UI에서 만든 리소스에 대한 첫 답장이 In-Reply-To/References만으로 스레드에 연결되지 않던 결손 수정.
  - **최초 분석 정정(중요)**: 백로그의 최초 가설("`NotificationMailDigestScheduler`가 발신 시점에 `OriginalEmail`을 기록해야 한다")은 yona 원본을 다시 대조한 결과 틀린 것으로 확인됐다 — yona `CreationViaEmail.java`도 `OriginalEmail`을 오직 3곳(전부 **수신** 메일 처리 지점)에서만 기록하고, 발신(`NotificationMail.java`) 쪽에는 `OriginalEmail` 기록이 전혀 없다. 대신 yona `EmailHandler.findResourcesByMessageId()`는 `OriginalEmail` 조회가 미스면 `IMAPMessageUtil.getIdLeftFromMessageId()`(Message-ID의 `<`~`@` 사이 문자열 추출)+`Resource.findByPath()`(`type/id` 파싱)로 **발신 Message-ID 자체의 결정론적 포맷을 역파싱**해 리소스를 찾는 폴백을 갖추고 있었다 — `Resource.getMessageId()`가 애초에 `"<{type}/{id}@{host}>"` 결정론적 포맷이라 별도 저장 없이도 역산 가능하기 때문. yona의 `computeMessageId()`([[tickets/p1-27|P1-27]]/51)도 정확히 동일한 포맷이라 같은 방식의 폴백이 가능함을 확인하고 설계를 정정해 구현했다.
  - `IncomingMailProcessingService.resolveThreads()`에 `originalEmailRepository.findByMessageId()`가 미스일 때 신규 `resolveByDeterministicMessageId()`를 호출하는 폴백 추가. yona `getThreads()`의 `switch(resource.getType())`를 그대로 재현: `COMMENT_THREAD`/`ISSUE_POST`/`BOARD_POST`는 그대로 스레드로 채택, `REVIEW_COMMENT`(리뷰 댓글 자신 — yona `NEW_REVIEW_COMMENT` 이벤트의 `resourceType`, [[tickets/p1-50|P1-50]]에서 이미 확인)는 `resource.getContainer()`처럼 그 댓글이 속한 스레드(`COMMENT_THREAD`)로 리다이렉트, 그 외(default)는 스킵. `COMMIT_COMMENT`는 yona `CommitComment.java`(default 분기라 실제로는 답장 라우팅에 안 쓰임) 대신 yona 고유의 커밋 댓글 1급 모델([[tickets/p0-16|P0-16]], [[tickets/p1-59|P1-59]]에서 이미 REVIEW_COMMENT와 동급으로 다룸)에 맞춰 폴백 대상에 포함 — yona에 없는 유일한 확장이며 그 이유를 코드 주석에 명시.
  - `IncomingMailProcessingService` 클래스 KDoc의 "REVIEW_COMMENT/COMMIT_COMMENT는 아직 발신 쪽에서 안 쓰인다"는 stale 설명을 새 폴백 동작으로 갱신.
  - 테스트: `IncomingMailProcessingServiceSpec.kt` +3(UI로 만든 이슈의 알림 메일에 답장 시 `OriginalEmail` 없이도 그 이슈에 댓글 추가/UI로 만든 리뷰 댓글의 알림 메일에 답장 시 댓글 자신이 아니라 스레드에 답글 추가/역파싱해도 알 수 없는 타입이면 폴백하지 않고 새 이슈로 처리) — 총 28 tests.
  - 검증: `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공, `./gradlew test --tests "com.github.yonaprojects.yona.domain.mail.IncomingMailProcessingServiceSpec"` 28 tests 전체 통과.
