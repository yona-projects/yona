# P3-06: 엔터프라이즈 SSO(SAML2 / 범용 OIDC)

## 원본 표 정보

- **우선순위 구분**: P3
- **상태(원본 체크박스)**: `[x]`
- **비고(원문)**: **2026-08-24 사용자 제안, 코드 검증 완료(LDAP은 이미 이식 완료 확인)**: `LdapService.kt`/`LdapUserProvisioningService.kt`/`LdapQueryBuilder.kt`/`LdapUser.kt` 및 `YonaAuthenticationProvider.kt`의 LDAP 연동, `application.yml`의 `yona.ldap.*` 설정까지 전부 구현·테스트(`LdapQueryBuilderSpec`, `LdapUserProvisioningServiceSpec`, `YonaAuthenticationProviderSpec`) 확인됨 — **이 항목의 신규 대상은 SAML2와 범용 OIDC 두 가지뿐**, LDAP은 범위에서 제외. 설계 방향(미착수): LDAP과 동일한 "외부 IdP 인증 성공 → 로컬 User로 JIT(Just-In-Time) 프로비저닝/재조정" 패턴을 재사용 — `LdapUserProvisioningService`처럼 `SamlUserProvisioningService`/`OidcUserProvisioningService`를 두어 이메일 기준 기존 유저 매칭 또는 신규 생성. SAML2는 Spring Security의 `spring-security-saml2-service-provider`(SP 역할), 범용 OIDC는 `spring-security-oauth2-client`로 임의 IdP(Okta/Azure AD/Keycloak 등)를 등록 가능하게 구성. `YonaAuthenticationProvider`의 LDAP 분기(`if (ldapService.enabled) ...`)와 나란히 SAML/OIDC 분기를 추가할지, 별도 `SecurityFilterChain` 다중 등록으로 분리할지는 미결정 — SAML/OIDC는 리다이렉트 기반 흐름이라 LDAP처럼 단순 `AuthenticationProvider` 위임만으로는 부족할 가능성이 높음(추가 조사 필요). **2026-09-06 TDD로 전체 구현 완료(상세: `docs/yona-wiki/plans/p3-06-enterprise-sso.md` 완료 로그)** — 스파이크 해소: 새 `SecurityFilterChain` 불필요, 기존 하나뿐인 필터체인(`SecurityConfig.kt`)에 `.saml2Login{}`과 `.oauth2Login{}.userInfoEndpoint{}.oidcUserService{}`만 나란히 추가하면 됐다. 소셜 로그인(google/github)과의 분리는 Spring Security가 `ClientRegistration`의 scope에 `openid` 포함 여부로 `userService()`/`oidcUserService()`를 자동 분기해줘 registrationId 기반 분기 코드 자체가 불필요했다. `domain/user/OidcUserProvisioningService.kt`/`Saml2UserProvisioningService.kt`(신규) — LDAP과 동일하게 이메일 매칭 우선, 없으면 신규 생성(리다이렉트 로그인 특성상 신규 계정은 로컬 비밀번호 없이 생성, 항상 SSO로만 로그인). `config/sso/`(신규 패키지) — `EnterpriseOidcUserService`(`OAuth2UserService<OidcUserRequest, OidcUser>` 직접 구현, `OidcUserService` 상속 시 자기참조 순환 발생해 인터페이스 구현으로 전환), `EnterpriseSaml2ResponseAuthenticationConverter`(기본 `OpenSaml5AuthenticationProvider`의 컨버터에 위임 후 JIT 프로비저닝), `YonaOidcUser`/`YonaSaml2AuthenticatedPrincipal`(`getName()`이 IdP의 sub/NameID가 아니라 로컬 `User.loginId` 반환), `YonaClientRegistrationRepository`/`YonaRelyingPartyRegistrationRepository`(DB/설정 파일 값을 매 로그인 시도마다 동적 조립, 비활성화 시 null 반환으로 온오프). 관리자 UI(사용자가 "필요하면 임의 구현" 지시로 확장) — `web/SsoAdminController.kt` + `templates/site/sso.html`(`/site/sso`, GitHub Enterprise의 "SAML single sign-on" 화면 필드 구성 차용), `domain/sso/OidcSsoSettings.kt`/`Saml2SsoSettings.kt`+Repository+`SsoSettingsService`(DB 값 우선, 없으면 `application.yml`의 `yona.sso.oidc.*`/`yona.sso.saml2.*` 기본값 — LDAP과 동일한 "설정 파일만으로도 최소 동작" 원칙). 실측으로 드러난 제약 3건(상세는 계획 문서): (1) `EnterpriseOidcUserService` 자기참조 순환, (2) `YonaClientRegistrationRepository` 정의 시 Spring Boot의 `OAuth2ClientProperties` 자동구성 백오프로 소셜 로그인 설정이 깨져 `@EnableConfigurationProperties` 직접 추가로 해소, (3) Spring Boot 4.1.1엔 SAML2 relyingparty 자동구성 모듈이 없어 애초 계획대로 수동 빈 구현. 검증: 신규 스펙 8개(`OidcUserProvisioningServiceSpec` 4, `Saml2UserProvisioningServiceSpec` 5, `EnterpriseOidcUserServiceSpec` 1, `EnterpriseSaml2ResponseAuthenticationConverterSpec` 1, `SsoSettingsServiceSpec` 5, `YonaClientRegistrationRepositorySpec` 4, `YonaRelyingPartyRegistrationRepositorySpec` 4, `SsoAdminControllerSpec` 6) 전부 mockk 기반 순수 단위테스트로 GREEN, `AuthControllerSpec`(20 tests) 회귀 없음. LDAP/OAuth2 소셜로그인/API 토큰 필터 관련 기존 스펙(`LdapUserProvisioningServiceSpec`/`LdapQueryBuilderSpec`/`YonaAuthenticationProviderSpec`/`config.oauth2.*`/`config.security.*`) 전부 회귀 없이 GREEN. `./gradlew test` 전체 스위트는 5,925 tests 중 이 계획과 무관한 8개 클래스(`GitAuthorizationFilterIntegrationSpec`/`TemplateHelperSpec`/`ApiTokenServiceImplSpec`/`PostingCommentRepositorySpec`/`PostingRepositorySpec`/`PostingServiceSpec`/`CommentServiceExtraSpec`/`CommentServiceSpec`)에서 53건 실패했으나, 8개 클래스 모두 SSO/OIDC/SAML 코드를 전혀 참조하지 않음을 grep으로 확인했고 단독 재실행 시 전부 GREEN으로 교차검증 — 동시 세션의 공유 MariaDB 테스트 DB 경합(`docs/COVERAGE_BACKLOG.md`/[[tickets/p3-04|P3-04]] 완료 로그와 동일 선례 패턴)으로 판단, 이 계획의 변경과 무관함.
