# P3-23: Mercurial named branch(`hg branch`) 읽기/쓰기 지원 및 UI 노출 없음

## 배경

P3-12에서 yona의 git 스타일 "브랜치" 개념은 Mercurial **bookmark**(움직이는 포인터, git
브랜치와 가장 유사)에 매핑하기로 결정했다(GitHub/Bitbucket 컨벤션 우선 원칙). 하지만
Mercurial 고유의 **named branch**(`hg branch`로 지정, 커밋에 영구적으로 새겨지는 진짜
브랜치 — bookmark와는 완전히 다른, 삭제가 사실상 불가능한 개념)는 전혀 다루지 않았다.

hg4j에는 이미 `io.github.search5.hg4j.api.BranchCommand`(현재 워킹 디렉터리의 "다음 커밋이
속할 브랜치" 조회/설정 — `hg branch [name]`에 대응, 사실상의 쓰기)와 `BranchesCommand`
(저장소 전체의 named branch 헤더 목록 조회 — `hg branches`에 대응, 읽기)가 이미 구현돼
있다 — **hg4j 쪽 API는 이미 읽기/쓰기 둘 다 갖춰져 있다**. 없는 건 yona 쪽 도메인/API/UI
배선뿐이다.

## 범위 (사용자 지시: 읽기/쓰기 모두 필수, UI는 GitHub/옛날 Bitbucket 방식)

옛 Bitbucket(Mercurial을 정식 지원하던 시절)은 named branch와 bookmark를 저장소 화면에서
**서로 다른, 명확히 구분된 섹션**("Branches" / "Bookmarks")으로 노출했다 — 커밋 히스토리의
브랜치/태그 통합 셀렉터(P3-10에서 이미 만든 패턴)에 "북마크"와 "네임드 브랜치"를 구분되는
그룹으로 함께 노출하는 방식을 권장한다(둘 다 "이 커밋에서 시작하는 히스토리를 본다"는
동일한 사용성을 가지므로 같은 셀렉터 UI를 재사용하되 그룹 헤더로 구분).

1. **읽기**: `HgRepository`에 named branch 목록 조회 메서드 추가(hg4j `BranchesCommand`
   재사용) — `getBranches()`(bookmark 전용, 기존)와 별개로 `getNamedBranches()`(가칭) 신설,
   또는 기존 API를 확장해 둘 다 반환하되 타입으로 구분. 코드 브라우저의 브랜치 셀렉터
   템플릿에 "Bookmarks"/"Branches" 두 그룹으로 노출(REST API로도 노출할 것 — 기존 브랜치
   목록 API가 있다면 대칭적으로 확장).
2. **쓰기**: Mercurial의 named branch는 "생성 커맨드"가 없다 — `hg branch <name>`으로 워킹
   디렉터리 상태를 바꾼 뒤 다음 커밋이 그 브랜치에 속하게 되는 방식이다. yona가 이미 지원하는
   "온라인 커밋"(코드 브라우저에서 직접 파일을 편집해 커밋하는 기능, P1-111 참고)이 있다면
   그 커밋 폼에 "브랜치" 선택/입력 필드를 추가해 새 named branch로 커밋할 수 있게 한다(신규
   이름을 입력하면 새 브랜치가 그 커밋으로 시작된다 — 이게 Mercurial에서 실질적인 "브랜치
   생성"이다). 온라인 커밋 기능이 실제로 어디 있는지, 어떤 형태인지 먼저 코드베이스에서
   확인하고 그 지점에 통합할 것.
3. 브랜치 닫기(`hg commit --close-branch`)까지는 이번 티켓에서 다루지 않아도 된다(과도한
   확장 — 사용자가 명시적으로 요청하면 별도 티켓).
4. hg4j `BranchCommand`/`BranchesCommand`를 실제로 써보고 버그가 있으면(예: 닫힌 브랜치
   헤더 처리, 여러 헤드가 있는 브랜치 등) 이 티켓 범위에서 hg4j도 함께 고친다.

## 완료 기준

- 실제 Mercurial 프로젝트에서: named branch 목록이 코드 브라우저 브랜치 셀렉터에
  bookmark와 구분되어 노출된다(실사용 검증).
- 온라인 커밋으로 새 named branch를 만들 수 있고, 그 브랜치로 커밋 히스토리를 조회할 수
  있다(실사용 검증 — 실제 커밋 생성 후 `hg log -b <branch>`로 서버 쪽에서도 실제로 그
  브랜치에 속하는지 직접 확인).

## 완료 로그

- **2026-09-09 완료 — 읽기**: `PlayRepository`에 `getNamedBranchNames(): List<String>`/
  `getNamedBranches(): List<GitBranch>` 기본 메서드(Git/SVN은 빈 목록, `getBranches()`의 SVN
  선례와 동일 패턴)를 추가하고, `HgRepository`에서 hg4j `BranchesCommand`(변경 없이 그대로
  재사용 — 이 티켓 범위인 3개 커맨드 파일 중 `BranchesCommand.java`도 실제로 버그를 찾지
  못해 hg4j 수정이 필요 없었다)로 실제 구현했다. `getBranches()`(bookmark 전용, 기존)와는
  완전히 별개의 신규 API로 뒀다(기존 계약을 바꾸지 않는 확장).
  - `CodeViewController`의 `codeBrowserWithBranch()`/`history()`(코드 브라우저 `code/view.html`,
    커밋 히스토리 `code/history.html`)에 `namedBranches` 모델 속성을 추가했다.
  - 두 템플릿의 브랜치 셀렉터(P3-10에서 만든 브랜치/태그 통합 `<select id="branches">`)에
    named branch를 별도 `<optgroup>`으로 추가했다. 사용자 지시(옛 Bitbucket 방식)에 맞춰
    Mercurial 프로젝트에서는 기존 bookmark 그룹의 라벨을 "Bookmarks"(신규 `title.bookmarks`
    메시지 키)로, named branch 그룹을 "Branches"(신규 `title.namedBranches`)로 표시한다 — Git
    프로젝트는 기존 라벨("Branches")과 항상 빈 named branch 그룹(미노출) 그대로다(회귀 없음).
  - REST API: 기존에 branch 전용 목록 REST 엔드포인트가 없었다(`TagRestApiController`처럼
    태그는 `/api/v1/projects/{owner}/{project}/tags` GET이 있지만, 브랜치는
    `BranchApiController`가 폼 액션(`setAsDefault`/`delete`)만 제공하는 `@Controller`이고
    Git 전용이다) — "기존 API가 있으면 대칭적으로 확장"이라는 조건이 성립하지 않아 신규 REST
    엔드포인트는 만들지 않았다(범위 규율에 따라 이 티켓과 무관한 새 REST 표면을 만들지 않기로
    결정 — 코드 브라우저/커밋 히스토리 템플릿 노출로 완료 기준을 충족).
  - 다운로드 ZIP과 동일한 근본 수정을 공유한다: `resolveRevisionNumber()`가 bookmark/named
    branch 이름을 전혀 해석 못하던 버그를 고치면서 named branch 이름 조회 분기
    (`hg.branches().setIncludeClosed(true).call().find { it.branch == rev }`)를 추가했다 —
    이게 없으면 셀렉터에 named branch가 나열은 되지만 클릭해도 항상 404였다.
  - **발견해 함께 고친 버그**: 기존 `resolveRevisionNumber()`는 `"default"`를 `"tip"`/`"HEAD"`와
    같은 그룹으로 묶어 무조건 전역 tip으로 해석했다. 그런데 `"default"`는 실제로 모든
    Mercurial 저장소가 갖는 진짜 named branch 이름이라(이제 셀렉터에 그대로 노출된다) 다른
    named branch가 더 최근에 커밋되면 "default"를 선택해도 엉뚱한(더 최신인 다른 브랜치의)
    커밋 내용이 나오는 실제 버그가 있었다 — named branch 조회 분기로 흘려보내 "default" 브랜치
    자체의 진짜 헤드로 해석하도록 고쳤다(named branch가 하나뿐인 흔한 저장소에서는 결과가
    동일해 회귀 없음).
- **2026-09-09 완료 — 쓰기(온라인 커밋)**: 온라인 커밋 기능이 실제로 존재하는지 먼저
  코드베이스에서 확인했다 — **존재한다**(P1-111, `BoardViewController.createPost()`가
  `PostingForm.path`가 채워지면 게시글 DB 행 대신 지정 브랜치/경로에 텍스트 파일을 바로
  커밋하고 코드 브라우저로 리다이렉트, `board/create.html`의 숨은 `path`/`branch` 필드로
  코드 브라우저 "새 파일"/"편집" 버튼에서 진입). 다만 기존 구현은 `BareCommit`(JGit 전용,
  bare 저장소를 직접 다룸)만 썼다 — Mercurial은 bare 개념이 없어 이 경로를 그대로 못 쓴다.
  - `PlayRepository.commitTextFile(branchBookmark, namedBranchName, path, content, message,
    authorName, authorEmail)`을 신설(기본 구현은 `UnsupportedOperationException`, Git은
    기존 `BareCommit` 경로를 그대로 쓰고 이 인터페이스를 거치지 않음)하고 `HgRepository`에서
    실제 구현했다: 파일을 작업 디렉터리에 쓰고 → (namedBranch 지정 시) `hg.branch()
    .setBranchName(name)` → `hg.add()` → `hg.commit()` → (branchBookmark가 실제 bookmark
    이름이면, 즉 "tip"/"default"/"HEAD"/빈 문자열이 아니면) `hg.bookmark()`로 그 이름을 새
    커밋으로 전진(GitHub 스타일 "이 브랜치로 커밋" UX와 동일 — 없는 이름이면 새로 생성).
  - `BoardViewController.createPost()`의 온라인 커밋 분기에서 `project.vcs == "MERCURIAL"`이면
    `BareCommit` 대신 이 메서드로 위임하도록 분기를 추가했다. `PostingForm`에 Mercurial
    전용 `namedBranch` 필드를 신설하고, `board/create.html`에 Mercurial 프로젝트의 온라인
    커밋 화면에서만 보이는 "네임드 브랜치" 텍스트 입력을 추가했다(비우면 현재 브랜치 유지,
    새 이름을 입력하면 그 커밋으로 시작하는 새 named branch가 생성됨 — Mercurial에 별도
    "브랜치 생성" 커맨드가 없어 이게 유일한 생성 방법이라는 티켓 배경과 정확히 일치).
  - **실사용 검증 중 발견해 함께 고친 실제 데이터 유실 버그**: yona는 Mercurial을 push(hg
    unbundle)로만 갱신하고 그 후 작업 디렉터리를 갱신하지 않는다 — 이 상태에서 파일만 쓰고
    바로 커밋하면 dirstate의 부모가 null이라 새 커밋이 **고아 루트 커밋**이 되어 기존
    저장소의 다른 모든 파일이 그 커밋의 매니페스트에서 통째로 사라졌다(`hg log`로 직접
    확인). `commitTextFile()`에 파일을 쓰기 전 `hg.update().setRevision(baseRev)
    .setForce(true)`로 먼저 브랜치 헤드로 체크아웃하는 단계를 추가해 고쳤다 — 이제 새
    커밋은 그 리비전의 정상적인 자식이고 기존 파일이 전부 보존된다.
  - **실사용 검증**: 실제 앱을 기동해 `POST /{owner}/{project}/posts`(path/branch/namedBranch
    폼 필드)를 실제로 호출했다.
    1. `path=newfile.txt&branch=default&namedBranch=feature-x` → 서버 저장소에서 실제
       `hg log -b feature-x` 실행 결과: `branch: feature-x`, 커밋 메시지/작성자 일치,
       `hg branches`에 `feature-x`/`default`가 별개 브랜치로 나열됨을 확인.
    2. 데이터 유실 버그 수정 후 재검증: `hg log -G`로 새 커밋이 이전 커밋의 정상적인 자식임을
       (`parents=` 필드가 첫 부모를 가리킴), `hg files -r feature-x`로 기존 파일
       (`README.md`, `src/main.py`) + 새 파일(`newfile.txt`)이 모두 매니페스트에 있음을 확인.
    3. `branch=mybookmark`(없는 bookmark 이름)로 커밋 → `hg bookmarks`에 `mybookmark`가 그
       새 커밋을 가리키며 실제로 생성됨을 확인(GitHub 스타일 "커밋으로 브랜치 생성" UX 재현).
    4. `namedBranch`를 비운 후속 커밋은 실제 hg의 "sticky branch" 동작대로 직전에 설정한
       named branch에 그대로 이어짐을 확인(의도된 동작, 코드 주석에 명시).
    5. `branch=default`로 커밋한 새 named branch(`release-1`)가 실제로 "default" 브랜치의
       헤드(다른 브랜치가 아니라)를 부모로 삼음을 확인 — 위 "default" 해석 버그 수정이
       온라인 커밋 경로에도 정확히 적용됨을 검증.
  - **UI 노출 검증**: `board/create.html`에서 Mercurial 프로젝트 + 온라인 커밋 모드에서만
    "네임드 브랜치" 입력이 렌더링되고 Git 프로젝트에서는 렌더링되지 않음을 실제 HTML 응답으로
    확인.

  재현하지 않음).
