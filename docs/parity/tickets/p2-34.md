## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-22 — P2-34**: `AccessControl.isGlobalResourceCreatable`/`isResourceCreatable`(yona `utils/AccessControl.java:32-34,100-118`) 미이식 문제를 조사한 결과, 단순 함수 이식을 넘어 실제 기능 결손 2건을 발견해 함께 수정.
  - **`isGlobalResourceCreatable(user)`**: `AccessControl.kt`에 `user != null`(legacy `!user.isAnonymous()`, `isAnonymous()`가 사실상 `id == null`과 동치임을 legacy `User.java:507-509`/`NullUser.java:47-49`로 확인)로 신규 추가.
  - **`isResourceCreatable`의 ISSUE_COMMENT/NONISSUE_COMMENT 케이스**: 제네릭 `Resource` 다형성이 없는 JPA 구조에 맞춰([[tickets/p1-85|P1-85]] 1b와 동일한 아키텍처 판단) `isIssueCommentCreatable(user, project, issue)`/`isPostingCommentCreatable(user, project, posting)` 오버로드로 신규 추가 — 댓글을 달 대상 Issue/Posting의 작성자(+ Issue는 담당자/공유대상도, legacy `isAllowedIfAuthor`/`isAllowedIfAssignee`/`isAllowedIfSharer` 우회, `isAllowedIfSharer`는 [[tickets/p1-82|P1-82]]에서 이미 이식된 것을 재사용)면 프로젝트 멤버 여부와 무관하게 항상 허용하고, 아니면 기존 `isProjectResourceCreatable`로 위임.
  - **`isOrganizationAdmin(Organization?, User?)`**: private → public으로 가시성만 변경(로직 변경 없음) — `ProjectViewController`가 외부에서 호출해야 해서.
  - **`CommentController.createIssueComment`/`createPostingComment`(실제 기능 결손 수정)**: 기존에는 `accessControl.isAllowed(user, project, Operation.READ)`(프로젝트 READ 권한)로만 게이트했는데, 이 경로엔 legacy의 작성자/담당자/공유대상 우회가 전혀 없어 프로젝트 비멤버인 이슈 담당자/공유대상은 댓글을 달 수 없었다(실사용 시나리오: 비공개 프로젝트에 초대 없이 담당 배정만 된 사용자, 또는 이슈를 공유받은 사용자). `isIssueCommentCreatable`/`isPostingCommentCreatable`로 교체 — 이 판단에 이슈/게시글 엔티티 자체가 필요해 그 조회를 권한체크보다 앞으로 옮김(legacy `IssueApp.newComment`/`BoardApp.newComment`도 동일 순서로 리소스를 먼저 찾은 뒤 권한을 확인함).
  - **`IncomingMailProcessingService.createComment`의 ISSUE_POST 분기(메일 답장, legacy `IssueApp.newReferComment` 대응)**: 기존엔 상위 `processTarget`의 `isAllowedToReadProject`(프로젝트 READ)만 거치고 바로 댓글을 생성했는데, 마찬가지로 작성자/담당자/공유대상 우회가 없었다. 이슈를 먼저 조회한 뒤 `isIssueCommentCreatable`로 재검사하도록 수정, 거부 시 legacy처럼 조용히 `Rejected`(발신자에게 노출되지 않는 내부 로그성 사유)로 처리. BOARD_POST(게시글) 메일 답장 분기는 legacy에 대응 기능 자체가 없어(legacy는 이슈 메일 답장만 지원, `newReferComment`가 `IssueApp.java`에만 존재) 손대지 않음(yona 자체의 범위 확장, 이번 항목과 무관).
  - **`ProjectViewController.newProject`(실제 기능 결손 수정)**: yona `ProjectApp.java:168-186`의 "owner가 기존 조직명이면 그 조직 admin만 생성 가능" 가드와 "그 조직으로 `project.organization` 연동" 로직이 yona에 전혀 없어, 로그인만 하면 임의 조직 이름을 owner로 지정해 그 조직 소속인 것처럼 프로젝트를 만들 수 있었고(권한 구멍), 설사 실제 조직 admin이 만들어도 `project.organization`이 채워지지 않아 조직 프로젝트 목록/조직관리자 권한에서 누락되고 있었다. 로그인 확인 직후, owner명과 일치하는 Organization을 조회해 존재하면 `isOrganizationAdmin`으로 게이트(아니면 403)하고, 통과 시 `project.organization`을 연동하도록 수정.
  - **범위 밖으로 확인해 손대지 않은 것**: `ImportViewController.newProject`/`ImportApiController.importProject`(Git import 경로)는 이미 각각 `validateImportForm`/인라인 검증에서 owner-is-user 검증과 조직 admin 가드를 legacy `ImportApp.validateForm`과 동일하게 완전히 구현하고 있음을 직접 코드로 재확인(사전 조사 에이전트가 "미이식"으로 잘못 보고했던 부분 — 항상 직접 검증하는 이 세션의 원칙에 따라 재확인 후 정정, 코드 변경 없음).
  - **범위 외 발견, 새 항목([[tickets/p2-45|P2-45]])으로 등록**: legacy `ProjectApi.java:135 newProject()`(REST API 경로)에 대응하는 REST 엔드포인트 자체가 yona에 없음 — permission 함수 이식과는 별개로 컨트롤러/엔드포인트 신설이 필요한 더 큰 작업이라 분리.
  - 테스트(TDD 방식 — 이번 항목은 구현과 거의 동시에 작성해 개별 RED 확인은 생략했고, 컴파일 실패로 대체 확인함): `AccessControlSpec.kt`에 `isGlobalResourceCreatable`(2 tests) + `isIssueCommentCreatable`/`isPostingCommentCreatable`(10 tests) 신규. `CommentControllerSpec.kt`에 이슈/게시글 각각 "작성자도 담당자도 공유대상도 멤버도 아니면 403"(기존 403 테스트를 새 판단 기준에 맞게 갱신) + "비멤버 작성자는 201" 신규 4 tests. `IncomingMailProcessingServiceSpec.kt`에 "비공개 프로젝트에서 권한 없으면 Rejected" 1 test. `ProjectViewControllerSpec.kt`에 `POST /projectform` describe 블록 신규(개인 프로젝트 성공/조직 admin 성공+organization 연동 확인/조직 non-admin 403) 3 tests.
