# P3-05: CI/Actions — GitHub Actions 러너 아키텍처 이식 (워크플로 YAML + 러너 등록/폴링)

## 원본 표 정보

- **우선순위 구분**: P3
- **상태(원본 체크박스)**: `[ ]`
- **비고(원문)**: **2026-08-24 사용자 결정: GitHub Actions 아키텍처를 그대로 이식.** 범위는 핵심만 — ① 워크플로 YAML(`on:`/`jobs:`/`steps:`/`runs-on:` 스키마), ② 러너 등록·폴링 프로토콜, ③ `run:` 직접 명령어 스텝. `uses:`(서드파티 액션 다운로드·실행)은 이번 범위에서 제외하되, 나중에 통합할 방향을 전제로 설계 — 잡/스텝 스키마를 `run:` 전용으로 못박지 말고 스텝 종류를 구분 가능한 형태(스텝 하나가 `run:` 또는 `uses:` 중 하나를 갖는 구조)로 처음부터 열어둔다. 코드 검증 완료: yona에 워크플로 파싱·잡 모델·러너 관련 코드 **0건**(완전 신규). 다만 **트리거 레이어는 재사용 가능** — 매 git push마다 `GitPushHooks.kt`의 `YonaPostReceiveHook`이 `eventPublisher.publishEvent(GitPostReceiveEvent(project, pusher, commands))`를 발행하고, PR 생성/갱신 시 `PullRequestServiceImpl.kt`가 `PullRequestMergeEvent`를 발행함을 확인 — 웹훅 시스템(`WebhookNotificationEventListener`)처럼 이 기존 이벤트 버스에 새 `@EventListener`(예: `CiWorkflowTriggerListener`)를 얹어 `on: push`/`on: pull_request` 트리거를 구현하면 됨(core git 서빙 로직 변경 불필요). **트리거 전제 조건**: 워크플로 정의 파일이 저장소에 실제로 있을 때만 트리거해야 함 — `CiWorkflowTriggerListener`는 이벤트를 받는 즉시 잡을 만드는 게 아니라, 먼저 해당 push/PR이 가리키는 커밋의 트리에서 워크플로 디렉터리(**`.github/workflows`가 아니라 `.yona/workflows/*.yml`|`*.yaml`** — GitHub 경로를 그대로 쓰지 않고 yona 자체 네임스페이스로 이식)를 조회해 파일이 하나도 없으면 즉시 no-op해야 함. JGit으로 `RevCommit`의 트리를 열어 해당 경로만 조회하는 방식(전체 워킹 카피 체크아웃 불필요)으로 구현 가능 — `GitPostReceiveEvent`가 이미 `commands`(변경된 ref 목록)를 들고 있으므로 그 대상 커밋들의 트리만 확인하면 됨. 워크플로 파일이 있어도 YAML 파싱 실패/스키마 오류인 경우 처리(잡 자체를 안 만들지, 에러 상태의 실패한 워크플로 런을 하나 만들지)는 미결정. **아키텍처 결정 — 별도 Pluggable Backend 인터페이스 설계 불필요**: GitHub 실제 러너 모델은 서버가 잡을 어디서 실행할지 직접 관리하지 않는다 — 러너가 등록 토큰으로 자신을 등록하고, 아웃바운드 롱폴링으로 자기 라벨(`runs-on:`)에 맞는 잡을 서버에 물어보고, 받으면 자신이 위치한 곳에서 실행 후 로그·결과를 보고하는 구조다. 이 프로토콜을 그대로 이식하면 러너가 로컬 프로세스든 VM이든 K8s Pod(GitHub 공식 `actions-runner-controller`와 동일 패턴)든 서버 쪽 코드 변경 없이 동작한다 — 즉 애초에 구상했던 `CiBackend` 전략+어댑터 인터페이스는 **불필요**, 러너 등록/폴링 프로토콜 자체가 이미 백엔드 독립적이다. **러너 에이전트 구현(2026-08-24 추가, 레퍼런스 아키텍처 확인)**: `run:`/`uses:` 실행 엔진을 처음부터 새로 짤 필요 없이 기존 오픈소스를 재사용할 여지가 큼. `nektos/act`(Go, **MIT 라이선스** 확인됨)가 워크플로 실행 엔진 자체를 이미 구현하고 있고 `run:` 스텝뿐 아니라 `uses:`의 Docker 컨테이너 액션·Composite 액션 실행까지 지원한다. Gitea가 이미 동일한 문제(자체 포지 서비스에 GitHub Actions 호환 CI 얹기)를 풀어둔 선례가 있음 — Gitea의 `act_runner`는 Gitea 서버와 등록/폴링 프로토콜로 통신하는 얇은 Go 코디네이터이고, 실제 워크플로 실행은 내부적으로 `act` 라이브러리를 호출해 잡마다 Docker 컨테이너를 띄우는 구조다(러너 라벨은 `ubuntu-latest` 등 `runs-on` 값과 매칭). yona 러너도 이 구조를 그대로 채택하면([[tickets/p3-02|P3-02]] CLI와 같은 Go 스택이라 라이브러리 임베드 자연스러움), 자체 구현 범위가 "등록·폴링·서버 API 연동" 정도로 줄고 워크플로 실행 엔진은 `act`에 위임할 수 있다 — `act` 임베드를 전제로 하면 `uses:`도 사실상 이번 단계에 큰 추가 비용 없이 같이 들어올 수 있음(검토 필요, 미착수). 워크스페이스 준비·로그 전송은 `act`/`act_runner` 쪽 기존 구현 방식을 참고. **신규 설계 항목(전부 미착수)**: 서버 쪽 — 워크플로 YAML 파서, 잡 모델(`WorkflowRun`/`Job`/`Step` 엔티티), 러너 등록 API(등록 토큰 발급·검증, 러너 라벨 저장), 러너 폴링 API(라벨 매칭 잡 할당), 로그 스트리밍 수신 엔드포인트(러너→서버, 잡 실행 중 로그 업로드). **실시간 로그 뷰(2026-08-24 추가, 사용자 제기 — GitHub처럼 실행 중인 로그가 실시간으로 보여야 함)**: 위 "로그 스트리밍 수신"은 러너→서버 방향뿐이라 서버→브라우저로 뷰어에게 실시간 push하는 다른 절반이 빠져 있었음. 코드 검증 완료: yona 전체에 `SseEmitter`/WebSocket/STOMP 등 실시간 푸시 인프라가 **0건**(전통적인 서블릿 기반 Spring MVC + Thymeleaf 구조만 확인됨, 리액티브 스택 아님). 다행히 Spring MVC는 서블릿 스택에서도 컨트롤러가 `SseEmitter`를 반환하는 방식으로 SSE를 네이티브 지원하므로 WebFlux 전환이나 별도 WebSocket 의존성 추가 없이 구현 가능 — 로그는 서버→클라이언트 단방향이라 WebSocket보다 SSE가 더 적합. 설계 방향(미착수): 러너가 로그 청크를 업로드하면 서버가 기존 패턴대로 `eventPublisher.publishEvent(JobLogAppendedEvent(...))`를 발행하고, 워크플로 런 조회 페이지에 연결된 `SseEmitter` 구독자(같은 잡을 여러 명/여러 탭에서 볼 수 있으므로 잡 단위 구독자 목록 필요)에게 그 이벤트를 실시간 전달하는 `@EventListener` 추가. 완료된 로그는 별도 저장(DB/파일)해서 나중에 재접속하거나 실행 종료 후 보는 경우에도 처음부터 재생 가능하게. 시크릿 — 저장소별 암호화 시크릿을 잡 실행 시 러너에 안전하게 전달하는 방법 미결정. K8s/VM 배포는 이 러너 바이너리를 **어디에 띄우느냐**의 배포 문제로 격하됨 — K8s에서는 잡 도착 시 임시 러너 Pod를 띄우는 컨트롤러(actions-runner-controller 패턴, 선택적 ephemeral 실행)를, VM에서는 상시 설치된 정적 러너를 쓸 수 있음(둘 다 동일 프로토콜). CLI 명령 초안(미구현, [[tickets/p3-02|P3-02]]와 연계): `yona runner register/unregister`, `yona workflow list/view/rerun`, `yona workflow logs <run-id>`. **2026-09-06 추가(사용자 지시로 자동 진행 대상에서 제외)**: 사용자가 "ci/actions는 이번 구현에서 제외해!"라고 명시적으로 지시함 — P3 백로그를 순서대로 자동 진행하는 현재 작업 흐름에서 이 항목(P3-05)은 착수하지 않는다. 백로그 자체를 취소/삭제하는 것은 아니며(설계 내용은 그대로 유효), 순번이 와도 건너뛰고 다음 항목으로 넘어간다 — 재개 여부는 사용자가 별도로 지시할 때까지 보류.
