  - **[[tickets/p1-73|P1-73]]**: `acceptTransfer()`에 `project.organization = organizationRepository.findByName(newOwner).orElse(null)` 추가 — 목적지가 조직이면 그 조직으로, 개인이면 명시적으로 `null`로 갱신.
  - **[[tickets/p1-74|P1-74]]**: 구현 전 yona 코드를 다시 정독하니 최초 등록 때의 "반대 방향 대기 요청 정리" 해석이 틀렸음을 발견(코드 주석만 보고 실제 쿼리 조건을 안 봤던 실수) — `ProjectTransfer.deleteExisting(project, pt.sender, pt.destination)`의 쿼리 조건이 pt 자신과 동일한 3중키라 실제로는 "완료된 이관 요청 행 자체를 삭제"하는 게 진짜 동작. `acceptTransfer()` 마지막의 `pt.accepted = true; projectTransferRepository.save(pt)`를 `pt.accepted = true; projectTransferRepository.delete(pt)`로 교체(in-memory `accepted=true` 대입은 yona도 삭제 직전까지만 존재하는 값이라 그대로 재현, 영속화만 save→delete로 변경).
  - **[[tickets/p1-75|P1-75]]**: 구현 착수 전 재확인 중 `ProjectServiceImpl.kt`(서비스 계층)에는 메일 발송이 없지만 `web/ProjectViewController.kt`(웹 계층)의 `transferProject()`가 이미 `sendTransferRequestMail()`(확인 링크+목적지 사용자/조직 관리자 BCC 발송)을 완전히 구현해뒀음을 발견 — 최초 감사가 서비스 계층만 보고 컨트롤러 계층을 놓친 오탐이었다. 코드 변경 없이 백로그 표기만 정정.
  - 테스트: `ProjectServiceImplSpec.kt` +5(동명 충돌 없으면 이름 그대로/충돌 있으면 -1,-2... 자동 rename, 조직에게 이관 시 organization 설정/개인에게 이관 시 organization 명시적 null, 수락 시 `save` 대신 `delete` 호출 검증). 기존 4 tests도 새 `organizationRepository.findByName()` 호출에 맞춰 스텁 보강. 인접 회귀: `ProjectTransferForkSpec.kt` 3 tests 그대로 통과.
