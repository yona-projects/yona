## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P2-07**: 데이터 백업/복원 시 auto-increment/시퀀스 재설정 방식을 yona `DefaultExchanger.exportData()`/`importSequence()`와 정확히 동일한 "export 시점 값 캡처→복원" 방식으로 교체(이전에는 백업된 행의 `max(id)+1`을 복원 시점에 재계산해 삭제로 생긴 시퀀스 갭을 없애버렸음).
  - `exportAll()`: 테이블 행을 덤프하는 동시에 각 테이블의 "다음 채번 값"을 `nextSequenceValue()`로 조회해 함께 저장. MySQL/MariaDB는 `INFORMATION_SCHEMA.TABLES.AUTO_INCREMENT`(yona와 동일 쿼리), PostgreSQL은 `pg_get_serial_sequence(table, 'id')`로 시퀀스명을 찾은 뒤 그 시퀀스 자체를 직접 조회(`is_called`면 `last_value+1`, 아니면 `last_value`)해 다음 값을 계산. id 컬럼이 없는 조인 테이블 등은 두 방언 모두 자연히 null이 나와 스킵된다(yona `hasSequence()=false`와 동일한 효과를 하드코딩 목록 없이 달성).
  - JSON 포맷을 `{tables: {...}, sequences: {...}}`로 변경(이전엔 테이블명이 최상위 키인 flat 구조) — export/import가 자체적으로만 주고받는 내부 포맷이라 외부 호환성 이슈 없음.
  - `importAll()`: 테이블별 DELETE+INSERT 후 캡처해둔 시퀀스 값이 있으면 `restoreSequence()`로 그 값 그대로 복원(재계산 없음). MySQL은 `ALTER TABLE ... AUTO_INCREMENT = <값>`, Postgres는 `setval(seq, <값>, false)`(`is_called=false`로 설정해 다음 `nextval()`이 정확히 그 값을 반환하도록).
  - `DataBackupServicePostgresIntegrationSpec.kt`의 수동 구성 백업([[tickets/p1-33|P1-33]]/34 재현 시나리오)도 새 `{tables, sequences}` 포맷에 맞게 갱신(`sequences.n4user = 2`로 명시).
  - 테스트: `DataBackupServiceIntegrationSpec.kt` +1(복원 도중 카운터를 의도적으로 훼손해도 export 시점에 캡처해둔 값으로 정확히 되돌아오는지 검증 — 우연히 `max(id)`와 일치해서 통과하는 약한 검증이 아니라 "캡처된 값을 그대로 복원한다"는 메커니즘 자체를 증명). 인접 회귀: 기존 MariaDB 2 tests, Postgres 1 test 모두 통과.
  - 검증: `./gradlew compileKotlin compileTestKotlin`, `DataBackupServiceIntegrationSpec` 3 tests, `DataBackupServicePostgresIntegrationSpec` 1 test 모두 통과.
  - **추가 수정(같은 날, 별도 발견)**: 전체 스위트에서만 가끔 실패하던 `DataBackupServiceIntegrationSpec`을 "known flake"로 넘기지 말고 근본 원인까지 파보라는 사용자 지시로 조사한 결과, **flake가 아니라 datetime(`Instant`) 컬럼에 실제 값이 있으면 100% 결정적으로 재현되는 진짜 버그**였다(단독 실행 시 통과했던 건 그 스펙 자체가 datetime 컬럼에 값을 채우는 픽스처가 우연히 없었기 때문). `exportAll()`이 `Instant`를 JSON에 ISO-8601 문자열로 직렬화하는데, `importAll()`은 타입 정보 없는 `Map<String, Any?>`로 역직렬화해 평범한 String이 되고, 그 String을 그대로 바인딩하면 MariaDB가 ISO-8601('T'/'Z')을 datetime으로 파싱하지 못해 거부했다. `insertRow()`가 테이블의 실제 JDBC 컬럼 타입(`dateTimeColumns()`, `DatabaseMetaData.getColumns()`)을 조회해 TIMESTAMP/DATE/TIME 계열이면 String→`Instant`→`Timestamp`로 되돌려 바인딩하도록 수정(`DataBackupServiceImpl.kt`). yona는 애초에 `DefaultExchanger`가 `putTimestamp()`/`timestamp()`로 각 필드를 타입 그대로 다뤄 이 문제 자체가 없었다 — 이 항목의 "테이블 자동 탐지 방식" 단순화 과정에서 yona에는 없던 새 결함이 생겼던 것. `organization`에 `created` 값을 채워 export/import 왕복하는 재현 테스트를 `DataBackupServiceIntegrationSpec.kt`에 +1 추가(수정 전 100% 재현, 수정 후 통과 확인).
