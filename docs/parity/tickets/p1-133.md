- **2026-08-21 — P1-133**: `WebhookServiceImpl.buildPayload()`의 DETAIL_SLACK attachment를 yona `Webhook.java`의 `buildIssueDetails()`(:284-298)/`buildJsonWithPullReqtuestDetails()`(:502-515)/`buildCommentDetails()`(:376-384)/`buildAttachmentJSON()`(:545-552)에 맞게 재구성.
  - Issue: "State" 필드 하나뿐이던 것을 마일스톤(있을 때만, title="마일 스톤 변경")+담당자(title="", yona `Messages.get(lang,"")` 그대로 재현)+상태(title="상태") 3필드로 복원.
  - PullRequest: DETAIL_SLACK attachment 자체가 전혀 없던 것을 신설 — 보낸사람("보낸 사람")/보낸브랜치("코드 보내는 곳")/받는브랜치("코드 받을 곳") 필드 + PR 본문.
  - **1차 구현에서 사용자가 "레거시에 없는 동작은 넣지 말라"고 지적해 재검증·수정**: CommitComment는 yona `Webhook.java`에 대응 오버로드 자체가 없는(전체 파일 검색으로 확인) yona 전용 리소스인데, 1차 구현에서 링크([[tickets/p1-132|P1-132]])와 attachment 본문/필드(P1-133)를 새로 만들어 붙였던 것을 모두 제거 — CommitComment는 링크도 attachment도 만들지 않도록 되돌림(관련 회귀 테스트 추가). ReviewComment도 1차 구현에서 "댓글 자신의 contents"를 attachment 본문으로 썼으나, yona `Webhook.java:476-478`은 실제로는 `buildJsonWithPullReqtuestDetails(eventPullRequest, ...)`를 그대로 재사용해 **부모 풀 리퀘스트의 본문+필드(보낸사람/보낸브랜치/받는브랜치)**를 담는다는 걸 재확인해 정정.
  - color 필드는 yona가 `Play.application().configuration().getString("slack."+eventType, "")`로 조회하나 yona에는 이 설정 자체가 없어(그리고 yona 저장소에도 기본값 설정이 없어 항상 "") 빈 문자열로 고정.
  - 테스트: `WebhookServiceSpec.kt` +7(이슈 마일스톤/담당자/상태 필드, 마일스톤 없을 때 2필드만, PR 필드 3종, CommitComment는 링크·필드 모두 없어야 함 — 레거시 부재 동작 회귀 방지). 전체 통과.
  - **새로 발견해 백로그 등록([[tickets/p2-36|P2-36]])**: yona는 Posting 이벤트에 DETAIL_SLACK 전용 분기가 없어(평문 텍스트만 전송) 게시글은 SLACK 웹훅이어도 attachments가 안 붙는데, yona는 webhookType 하나로만 분기하는 구조라 Posting도 다른 타입과 동일하게 attachments가 붙는다 — 이번 티켓 범위 밖의 기존 상태라 이번 커밋에서는 건드리지 않음.
