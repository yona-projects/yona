# P2-17: **(2026-08-21 백엔드 전수 감사에서 발견 — 게시판 도메인)** 새 댓글 알림의 "인용 이전 내용"(oldValue) 미채움 — `NotificationMessageResolver.kt:58-60`에 이미 인지된 상태로 null-safe 우회 처리가 돼 있음이 확인됨. 단순 누락이 아니라 "알고도 방치"임.

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P2-17**: 새 댓글 알림의 "인용 이전 내용"(oldValue)이 항상 비어있던 것을 yona `BoardApp.java:428-446`/`IssueApp.java:1020-1057` `AddPreviousContent()`+`getPrevious()` 대응으로 채움. `NotificationMessageResolver.kt:58-60`에 "yona의 현재 NEW_COMMENT 생성 경로에서 항상 null"이라는 우회 주석이 이미 있었던 것으로 보아 알고도 방치된 상태였다.
  - `CommentServiceImpl`에 `resolvePostingPreviousContents`/`resolveIssuePreviousContents`(각각 저장 직전에 계산 — 지금 만드는 댓글이 "마지막 댓글"에 섞이지 않도록) + 공용 `quotePrevious`/`formatShortDate`(yona `getPrevious()`/`JodaDateUtil.getOptionalShortDate()` 대응) 신설. 첫 댓글이면 원본 게시물/이슈 본문을, 답글이면 같은 부모의 마지막 형제 답글(없으면 부모 댓글 자신)을, 그 외 최상위 새 댓글이면 게시물/이슈의 마지막 댓글을 인용.
  - `IssueApp.AddPreviousContent()`의 `numOfComments` 불일치 자가복구(가비지 댓글 삭제) 로직은 Ebean 캐시 특유의 데이터 정합성 땜질이라 이식하지 않음 — yona는 매 댓글 저장 시 count를 직접 재계산해 이 문제 자체가 발생할 수 없다.
  - `NotificationMessageResolver.kt`의 스테일 주석("항상 null이라 null-safe 처리")을 실제 구현을 가리키도록 갱신. 기존 `newValue.orEmpty() + oldValue.orEmpty()` 연결 로직 자체는 legacy와 이미 일치해 수정 불필요.
  - 테스트: `CommentServiceSpec.kt` +4(이슈 첫 댓글은 원본 이슈 본문 인용/두 번째 최상위 댓글은 첫 댓글 인용/답글은 부모 댓글 인용/게시글 첫 댓글은 원본 게시글 본문 인용). 새 댓글의 30초 초안 병합([[tickets/p1-27|P1-27]])이 oldValue를 이전 이벤트 것으로 덮어써 테스트를 오염시키는 걸 피하려 각 시나리오의 두 댓글을 서로 다른 발신자로 작성하도록 설계. 전체 통과(위 `@Service` 복구 후).
