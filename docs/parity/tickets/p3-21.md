# P3-21: Mercurial 브랜치 보호 정책(require_pull_request 등) 미적용

## 배경

Git은 `require_pull_request`/`require_approvals`/`require_signed_commits` 등 브랜치 보호
정책이 HTTP(`GitAuthorizationFilter`+`GitPushHooks.BranchProtectionPreReceiveHook`)와
SSH(`GitSshProtocolHandler`) 양쪽 경로 모두에 적용된다. Mercurial은 어느 경로에도 이 정책이
전혀 없다 — `HgController.kt`/`HgSshProtocolHandler.kt`에 "브랜치 보호 미적용(TODO)"라고
이미 명시돼 있었다(P3-12 2라운드 범위 밖으로 의도적으로 미뤄뒀던 것).

정책 데이터 모델(`domain/branchprotection/ProtectedBranch.kt`)은 이미 `project` + `branchPattern`
기준으로 VCS와 완전히 무관하게 설계돼 있고, GPG 서명 검증(`GpgSignatureVerifier`)도 이미
git/hg 공용이다(P3-19) — 즉 **정책 저장/설정 UI(`BranchProtectionController`)는 이미 있고
그대로 재사용 가능**하다. 새로 만들어야 하는 건 "Mercurial push 시점에 이 정책을 실제로
검사해서 거부하는 적용 지점"뿐이다.

## 핵심 발견: hg4j에 필요한 훅 지점이 없다

Mercurial의 push는 두 단계다: (1) `unbundle`(새 changeset을 changegroup으로 반영),
(2) `pushkey`(namespace="bookmarks", 북마크를 새 tip으로 이동 — yona가 브랜치 개념으로 쓰는
바로 그것, P3-12 참고). hg4j의 기존 `registerPreChangegroupHook`(`HgHook`, `HgHttpWireServer`/
`HgSshWireServer`)은 `unbundle` 단계에만 걸리고, context에 `repository`/`nodes`(반영될 changeset
node hex 목록)만 담는다 — **"어떤 브랜치(북마크)가 어떻게 이동하는가"에 대한 정보가 전혀
없다**. 실제 북마크 이동은 `Wire1Commands.pushkey()` → `Wire2Commands.applyPushkey(repo,
namespace, key, old, new)`에서 일어나는데, 이 경로에는 **훅 자체가 없다**(코드 주석에도
"no server-side hooks to capture"라고 명시돼 있음).

즉 브랜치 보호(그리고 P3-22의 push 알림/웹훅/PushedBranch 추적도 마찬가지)를 구현하려면
**hg4j에 pushkey 전용 pre/post 훅을 새로 추가**해야 한다 — 그래야 "북마크 X가 노드 A에서
노드 B로 이동하려 한다"는 시점에 개입해 거부하거나(pre), 성공 후 이벤트를 낼 수 있다(post).

## 범위

### hg4j (신규 기능 필요)

1. `Wire1Commands.pushkey()`에 pre/post 훅 리스트를 매개변수로 추가(기존
   `registerPreChangegroupHook`과 동일한 `HgHook` 인터페이스 재사용). `namespace`가
   `"bookmarks"`일 때만 실행하거나, 모든 namespace에 대해 실행하되 context에 `namespace`를
   담아 호출자가 걸러내게 하거나 — 설계는 맡기되, 최소한 context에 `namespace`/`key`(북마크
   이름)/`old`(이전 노드 hex, 없으면 빈 문자열)/`new`(새 노드 hex)/`repository`는 반드시 담을
   것(Git의 `ReceiveCommand`가 주는 정보와 동등한 수준).
2. `HgHttpWireServer`/`HgSshWireServer`에 `registerPrePushkeyHook(HgHook)`/
   `registerPostPushkeyHook(HgHook)` 추가(기존 `registerPreChangegroupHook`과 대칭적인 API).
3. pre-훅이 거부하면 `Wire1Commands.pushkey()`는 실제 hg의 `pushkey` 실패 응답
   (`"0\n"`)을 돌려줘야 한다(이미 `applyPushkey()`가 실패했을 때와 동일한 응답 경로 재사용).
4. 실제 hg CLI로 "push가 북마크 이동에서 거부되면 클라이언트에 어떻게 보이는지" 검증할 것 —
   git의 브랜치 보호 거부처럼 깔끔한 사유 메시지가 나오는지, 아니면 P3-12/P3-18에서 이미
   문서화한 "clone/fetch 거부처럼 지저분한 메시지"가 되는지 확인하고 문서화(후자라도 괜찮다,
   실제 동작이 정확하면 된다 — 이미 그런 선례가 있다).
5. 회귀 테스트: 실제 `hg`/BouncyCastle 등으로 pre-pushkey 훅이 실제로 거부/허용하는지, post
   훅이 실제로 성공한 이동 정보를 정확히 받는지 검증.

### yona

1. `HgSshProtocolHandler.kt`의 이미 마련된 "훅 걸 자리"에 실제 브랜치 보호 검사 로직 연결 —
   `ProtectedBranchRepository`로 이 프로젝트의 정책을 조회하고, pushkey context의 북마크
   이름이 보호된 브랜치 패턴에 매치하면서 `requirePullRequest`가 true면 거부. `git`의
   `BranchProtectionPreReceiveHook` 로직(`GitPushHooks.kt`)을 최대한 그대로 참고해 동등한
   판정을 내린다(사유 메시지 포맷도 git 쪽과 동일하게 맞출 것 — "이 브랜치는 보호되어 있어
   직접 push할 수 없습니다. PR을 통해서만 병합 가능합니다" 류).
2. `HgController.kt`(HTTP 경로)에도 동일한 검사를 건다 — `HgHttpWireServer`에
   `registerPrePushkeyHook`을 등록.
3. `require_signed_commits`도 지원할 것 — 이미 git/hg 공용인 `GpgSignatureVerifier`를 그대로
   재사용해, push되는 changeset들의 서명 상태를 확인.
4. `require_approvals`(PR 승인 수 기준)는 이 정책이 "PR을 통한 병합"에만 의미가 있으므로,
   직접 push 거부 자체는 `requirePullRequest`만으로 충분하다 — git 쪽 판정 로직을 그대로
   참고해 정확히 동일하게 처리할 것(PR 병합 시점 검사는 `PullRequestServiceImpl`이 이미
   VCS 무관하게 처리하고 있는지 확인 — Mercurial PR 병합 자체가 지원되는지도 함께 확인).
5. UI 추가는 필요 없다 — `BranchProtectionController`/설정 화면은 이미 프로젝트 단위로
   VCS와 무관하게 동작한다(직접 확인해서 정말 그런지 검증할 것, 아니라면 최소한의 노출만
   추가).

## 완료 기준

- 실제 컨테이너(sshd+yona) 또는 실제 앱 기동으로: 보호된 브랜치(북마크)에 직접 push하면
  거부되고, 보호 안 된 브랜치는 정상 push된다 — HTTP/SSH 둘 다.
- `require_signed_commits=true`인 보호된 브랜치에 서명 안 된 커밋을 push하면 거부된다.
- 회귀 테스트(hg4j pushkey 훅 API 단위 테스트 + yona 통합 테스트) GREEN.
