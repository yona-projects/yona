# P3-21: Mercurial 브랜치 보호 정책(require_pull_request 등) 미적용

## 배경

Git은 `require_pull_request`/`require_approvals`/`require_signed_commits` 등 브랜치 보호
정책이 HTTP(`GitAuthorizationFilter`+`GitPushHooks.BranchProtectionPreReceiveHook`)와
SSH(`GitSshProtocolHandler`) 양쪽 경로 모두에 적용된다. Mercurial은 어느 경로에도 이 정책이
전혀 없다 — `HgController.kt`/`HgSshProtocolHandler.kt`에 "브랜치 보호 미적용(TODO)"라고
이미 명시돼 있었다(P3-12 2라운드 범위 밖으로 의도적으로 미뤄뒀던 것).

정책 데이터 모델(`domain/branchprotection/ProtectedBranch.kt`)은 이미 `project` + `branchPattern`
기준으로 VCS와 완전히 무관하게 설계돼 있고, GPG 서명 검증(`GpgSignatureVerifier`)도 이미
git/hg 공용이다(P3-19) — 즉 **정책 저장/설정 UI(`BranchProtectionController`)는 이미 있고
그대로 재사용 가능**하다. 새로 만들어야 하는 건 "Mercurial push 시점에 이 정책을 실제로
검사해서 거부하는 적용 지점"뿐이다.

## 핵심 발견: hg4j에 필요한 훅 지점이 없다

Mercurial의 push는 두 단계다: (1) `unbundle`(새 changeset을 changegroup으로 반영),
(2) `pushkey`(namespace="bookmarks", 북마크를 새 tip으로 이동 — yona가 브랜치 개념으로 쓰는
바로 그것, P3-12 참고). hg4j의 기존 `registerPreChangegroupHook`(`HgHook`, `HgHttpWireServer`/
`HgSshWireServer`)은 `unbundle` 단계에만 걸리고, context에 `repository`/`nodes`(반영될 changeset
node hex 목록)만 담는다 — **"어떤 브랜치(북마크)가 어떻게 이동하는가"에 대한 정보가 전혀
없다**. 실제 북마크 이동은 `Wire1Commands.pushkey()` → `Wire2Commands.applyPushkey(repo,
namespace, key, old, new)`에서 일어나는데, 이 경로에는 **훅 자체가 없다**(코드 주석에도
"no server-side hooks to capture"라고 명시돼 있음).

즉 브랜치 보호(그리고 P3-22의 push 알림/웹훅/PushedBranch 추적도 마찬가지)를 구현하려면
**hg4j에 pushkey 전용 pre/post 훅을 새로 추가**해야 한다 — 그래야 "북마크 X가 노드 A에서
노드 B로 이동하려 한다"는 시점에 개입해 거부하거나(pre), 성공 후 이벤트를 낼 수 있다(post).

## 범위

### hg4j (신규 기능 필요)

1. `Wire1Commands.pushkey()`에 pre/post 훅 리스트를 매개변수로 추가(기존
   `registerPreChangegroupHook`과 동일한 `HgHook` 인터페이스 재사용). `namespace`가
   `"bookmarks"`일 때만 실행하거나, 모든 namespace에 대해 실행하되 context에 `namespace`를
   담아 호출자가 걸러내게 하거나 — 설계는 맡기되, 최소한 context에 `namespace`/`key`(북마크
   이름)/`old`(이전 노드 hex, 없으면 빈 문자열)/`new`(새 노드 hex)/`repository`는 반드시 담을
   것(Git의 `ReceiveCommand`가 주는 정보와 동등한 수준).
2. `HgHttpWireServer`/`HgSshWireServer`에 `registerPrePushkeyHook(HgHook)`/
   `registerPostPushkeyHook(HgHook)` 추가(기존 `registerPreChangegroupHook`과 대칭적인 API).
3. pre-훅이 거부하면 `Wire1Commands.pushkey()`는 실제 hg의 `pushkey` 실패 응답
   (`"0\n"`)을 돌려줘야 한다(이미 `applyPushkey()`가 실패했을 때와 동일한 응답 경로 재사용).
4. 실제 hg CLI로 "push가 북마크 이동에서 거부되면 클라이언트에 어떻게 보이는지" 검증할 것 —
   git의 브랜치 보호 거부처럼 깔끔한 사유 메시지가 나오는지, 아니면 P3-12/P3-18에서 이미
   문서화한 "clone/fetch 거부처럼 지저분한 메시지"가 되는지 확인하고 문서화(후자라도 괜찮다,
   실제 동작이 정확하면 된다 — 이미 그런 선례가 있다).
5. 회귀 테스트: 실제 `hg`/BouncyCastle 등으로 pre-pushkey 훅이 실제로 거부/허용하는지, post
   훅이 실제로 성공한 이동 정보를 정확히 받는지 검증.

### yona

1. `HgSshProtocolHandler.kt`의 이미 마련된 "훅 걸 자리"에 실제 브랜치 보호 검사 로직 연결 —
   `ProtectedBranchRepository`로 이 프로젝트의 정책을 조회하고, pushkey context의 북마크
   이름이 보호된 브랜치 패턴에 매치하면서 `requirePullRequest`가 true면 거부. `git`의
   `BranchProtectionPreReceiveHook` 로직(`GitPushHooks.kt`)을 최대한 그대로 참고해 동등한
   판정을 내린다(사유 메시지 포맷도 git 쪽과 동일하게 맞출 것 — "이 브랜치는 보호되어 있어
   직접 push할 수 없습니다. PR을 통해서만 병합 가능합니다" 류).
2. `HgController.kt`(HTTP 경로)에도 동일한 검사를 건다 — `HgHttpWireServer`에
   `registerPrePushkeyHook`을 등록.
3. `require_signed_commits`도 지원할 것 — 이미 git/hg 공용인 `GpgSignatureVerifier`를 그대로
   재사용해, push되는 changeset들의 서명 상태를 확인.
4. `require_approvals`(PR 승인 수 기준)는 이 정책이 "PR을 통한 병합"에만 의미가 있으므로,
   직접 push 거부 자체는 `requirePullRequest`만으로 충분하다 — git 쪽 판정 로직을 그대로
   참고해 정확히 동일하게 처리할 것(PR 병합 시점 검사는 `PullRequestServiceImpl`이 이미
   VCS 무관하게 처리하고 있는지 확인 — Mercurial PR 병합 자체가 지원되는지도 함께 확인).
5. UI 추가는 필요 없다 — `BranchProtectionController`/설정 화면은 이미 프로젝트 단위로
   VCS와 무관하게 동작한다(직접 확인해서 정말 그런지 검증할 것, 아니라면 최소한의 노출만
   추가).

## 완료 기준

- 실제 컨테이너(sshd+yona) 또는 실제 앱 기동으로: 보호된 브랜치(북마크)에 직접 push하면
  거부되고, 보호 안 된 브랜치는 정상 push된다 — HTTP/SSH 둘 다.
- `require_signed_commits=true`인 보호된 브랜치에 서명 안 된 커밋을 push하면 거부된다.
- 회귀 테스트(hg4j pushkey 훅 API 단위 테스트 + yona 통합 테스트) GREEN.

## 완료 로그

**2026-09-09 완료.**

### hg4j 변경 (`../hg4j`)

- `Wire1Commands.pushkey(HgRepository, Map)`은 그대로 두고(하위호환), 새 오버로드
  `pushkey(HgRepository repo, Map<String,String> args, List<HgHook> prePushkeyHooks,
  List<HgHook> postPushkeyHooks)`를 추가했다 — `unbundle()`이 이미 `preChangegroupHooks`/
  `postChangegroupHooks`를 받는 것과 동일한 패턴. context는 `namespace`/`key`(북마크 이름)/
  `old`(이전 노드 hex, 없으면 `""`)/`new`(새 노드 hex, 없으면 `""`)/`repository`(네이티브
  `io.github.search5.hg4j.lib.HgRepository`) 다섯 키를 담는다. pre-훅이 하나라도 false를
  반환하면 `applyPushkey()`를 아예 호출하지 않고 즉시 `"0\n"`(실제 hg pushkey 실패 응답)을
  반환한다 — `applyPushkey()` 자신이 compare-and-swap 실패로 false를 반환하는 경우와 클라이언트
  입장에서 구분되지 않는 동일한 응답 경로다(실제 hg pushkey 와이어 프로토콜 자체가 애초에 이
  둘을 구분하지 않는다). post-훅은 `applyPushkey()`가 성공(true)했을 때만 실행된다.
- `HgHttpWireServer`/`HgSshWireServer`에 `registerPrePushkeyHook(HgHook)`/
  `registerPostPushkeyHook(HgHook)`를 추가(기존 `registerPre/PostChangegroupHook`과 대칭).
  HTTP는 `handleV1Command()`에서 `cmd.equals("pushkey")`일 때 `dispatch()`(hook 없는 경로)
  대신 새 오버로드를 직접 호출하도록 분기(= `unbundle`이 이미 하던 것과 동일한 특별 취급).
  SSH는 `HgSshWireServer.dispatch(cmd, in)`에서 `"pushkey".equals(cmd)`일 때 동일하게 분기.
  `batch`/`Wire1Commands.dispatch()`는 훅을 모른다 — 실제 hg 클라이언트가 pushkey(쓰기)를
  heads/known 같은 discovery 명령과 배치로 묶어 보내는 사례가 없어(주석에 이미 문서화됨)
  문제가 되지 않는다.
- 실사용 검증: 실제 `hg`(호스트 7.2, 컨테이너 6.1.1) 클라이언트로 HTTP/SSH 양쪽에서 실제
  push를 실행해, pre-pushkey 훅이 거부하면 클라이언트에 `updating bookmark <name> failed`로
  뜨는 것을 확인(체인지그룹 자체는 이미 반영되고 북마크만 안 움직임 — git의 "push 성공, ref만
  거부"와 동일한 셰이프). 사유 텍스트는 클라이언트에 전달되지 않는다(pushkey 와이어 응답
  자체가 `output`을 안 담는 실제 hg 스펙의 한계 — P3-12/P3-18에서 이미 문서화한 것과 동일한
  선례, 서버 로그에는 사유가 정확히 남는다).
- 회귀 테스트: `Wire1CommandsTest`(순수 유닛, pre-훅 거부/post-훅 성공·context 값 검증),
  `HgHttpWireServerTest`/`HgSshWireServerTest`(실제 HTTP/SSH 와이어 프레이밍을 통한 hg4j 자체
  클라이언트 왕복) 신규 테스트 전부 GREEN.
- 건드리지 않은 파일: `Wire2Commands.java`(applyPushkey 로직 자체는 무수정, 그대로 재사용),
  `GpgSignature`/`DiffCommand` 등 다른 최근 세션이 만졌을 수 있는 파일은 손대지 않음.

### yona 변경

- `domain/vcs/HgPushHooks.kt`(신설) — git의 `GitPushHooks.kt`와 1:1 대응:
  - `HgBookmarkAncestry`(internal object) — hg4j 포셀린 `HgCommit`에는 부모 리비전이 없어(P3-19
    설계 시점부터 알려진 한계), `Wire2Commands.changelog()`와 동일한 저수준
    `Revlog`(00changelog.i/.d)를 직접 열어 `IndexRecord.getParent1()/getParent2()`로 진짜 조상
    관계를 판정한다. `classify()`가 git의 `ReceiveCommand.Type`(CREATE/UPDATE/
    UPDATE_NONFASTFORWARD/DELETE)에 대응하는 값을 계산하고, `newlyIntroducedRevisions()`가
    git의 `oldId..newId` RevWalk 범위에 대응하는 새 리비전 목록을 계산한다(force-push 시
    "old의 조상이 아닌 new의 조상 전체"로 근사 — 실제 hg 자신도 강제 push된 체인지셋을 그냥
    "새 체인지셋"으로 취급하는 것과 동일).
  - `HgBranchProtectionPrePushkeyHook` — `GitPushHooks.BranchProtectionPreReceiveHook`과 검사
    순서·사유 메시지를 최대한 동일하게 재현(require_pull_request → disallow_delete →
    disallow_force_push → require_signed_commits → restrict_push_to, admins_can_bypass는
    맨 앞에서 전체 우회). `require_signed_commits`는 P3-19에서 이미 만든
    `GpgSignatureVerifier.verify(io.github.search5.hg4j.api.HgCommit)` 오버로드를 그대로
    재사용. 차이점: 거부 사유는 `command.setResult()`가 아니라 `HgHook.run()`의 boolean
    반환값으로만 전달된다(로그에는 git과 동일한 포맷의 사유 문자열을 남긴다) — 실제 hg pushkey
    응답 자체가 사유 텍스트를 안 담는 구조적 한계.
  - `HgYonaPostPushkeyHook` — `YonaPostReceiveHook`과 1:1 대응(lastPushedDate 갱신,
    `HgPostReceiveEvent` 발행, `RelatedPullRequestMergeEvent` 발행(UPDATE/
    UPDATE_NONFASTFORWARD만), 브랜치 삭제 시 관련 PR 정리, `PushedBranch` upsert/정리).
    git의 `PostReceiveHook`은 push 하나의 커맨드 전체를 한 번에 받지만 hg4j의 pushkey 훅은
    북마크 하나당 한 번 호출되므로, 이 훅도 북마크 하나만 다룬다(여러 북마크를 한 번에 옮기면
    그만큼 여러 번 실행되어 최종 상태는 git과 동일).
- `domain/event/HgPostReceiveEvent.kt`(신설) — `project`/`user`/`move: HgBookmarkMove`
  (VCS 무관, JGit `ReceiveCommand`에 결합된 `GitPostReceiveEvent`와 달리 재사용 가능한 형태).
- `domain/event/HgPostReceiveEventListener.kt`(신설) — `GitPostReceiveEventListener`와 대칭.
  새로 들여온 커밋 계산에 `HgBookmarkAncestry`를 재사용하고, 알림/이슈참조/웹훅은 git 쪽과
  동일한 서비스(`NotificationEventRecorder`/`WatchService`/`WebhookService`)를 그대로
  재사용한다.
- `domain/webhook/PushedHgCommits.kt`(신설) + `WebhookServiceImpl.kt`에
  `buildPushPayloadForHg()`/`getResourceType`/`getResourceId`/`buildTextMessage` 분기 추가 —
  `PushedCommits`(JGit `RevCommit` 전용, 구체 클래스라 hg4j `HgCommit`을 감쌀 합성 객체를 만들
  방법이 없음)와 정확히 동일한 JSON 스키마(ref/commits/head_commit/sender/pusher/repository)를
  Mercurial push에도 채운다. 기존 `PushedCommits`/git 관련 코드·테스트는 전혀 건드리지 않았다
  (병렬 타입으로 분리해 회귀 위험 제거).
- `web/HgController.kt`(HTTP) — 프로젝트당 캐시되는 `HgHttpWireServer` 인스턴스 생성 시
  `registerPrePushkeyHook`/`registerPostPushkeyHook`을 등록한다. 캐시된 인스턴스가 여러 요청에
  재사용되므로, 훅 람다 내부에서 매 호출마다 `project`/`pusher`를 새로 조회한다(project는
  개명 대응을 위해 `findByOwnerAndNameOrPreviousPlace`로, pusher는 `SecurityContextHolder`로 —
  HTTP 요청 스레드가 `HgHttpWireServer.service()`→`Wire1Commands.pushkey()`→훅까지 동기 호출로
  이어지므로 안전하다).
- `config/ssh/HgSshProtocolHandler.kt`(SSH) — 이미 마련돼 있던 "훅 걸 자리"(TODO 주석)에
  `HgBranchProtectionPrePushkeyHook`/`HgYonaPostPushkeyHook`을 연결. SSH는 연결 하나당 새
  `HgSshWireServer`가 만들어지므로 `authorization.project`/`authorization.pusher`(이미
  `SshAuthService`가 계산해둔 값)를 훅 생성 시점에 그대로 캡처한다(HTTP처럼 매번 재조회할
  필요 없음).
- `config/ssh/SshRelayServer.kt` — `HgSshProtocolHandler`에 새로 필요해진 의존성
  (`ProjectRepository`/`PullRequestRepository`/`PushedBranchRepository`/
  `ApplicationEventPublisher`/`MeterRegistry`) 배선 추가.
- `require_approvals`(P3-21 범위 확인 항목): `PullRequestServiceImpl.checkApprovalsForMerge()`
  자체는 이미 완전히 VCS 무관(오직 `PullRequestReview` 레코드만 검사)하다 — 확인 완료. 단,
  이 메서드를 호출하는 `merge()` 전체가 `FileRepositoryBuilder().setGitDir(gitDir)`로 시작해
  Mercurial 프로젝트에서는 애초에 도달 불가능한 코드다(아래 "발견했지만 고치지 않은 것" 참고).
- UI(`BranchProtectionController`): 확인 결과 VCS 관련 코드가 전혀 없음 — 이미 프로젝트 단위로
  완전히 VCS 무관하다. 추가 작업 없음.

### 실사용 검증 (실제 컨테이너, sshd+yona)

`docs/guide/ssh-system-sshd-setup.md`가 설명하는 것과 동일한 아키텍처(system sshd +
AuthorizedKeysCommand + socat 소켓 릴레이)를 담은 기존 검증용 도커 이미지
(`yona-hg-ssh-e2e`, 이전 세션에서 만든 것)에 새로 빌드한 jar를 넣어 재빌드 후 컨테이너로
기동(포트 12222→22, 18080→8080)해 검증했다.

- **HTTP**: `hg clone http://localhost:18080/hg/admin/hgproj` → 성공. `main` 브랜치에
  `require_pull_request=true` + `do_not_allow_bypassing=true`(관리자 우회 차단) 규칙을 걸고
  관리자 계정으로 직접 push → `hg push -B main`이 `updating bookmark main failed`로 실패,
  서버 로그에 `bookmark 'main' protected: 이 브랜치는 Pull Request를 통해서만 갱신할 수
  있습니다(require_pull_request). (project=admin/hgproj, pusher=admin)` 정확히 기록됨. 서버
  쪽 `listkeys`로 북마크가 실제로 안 움직였음을 직접 확인(체인지그룹 자체는 반영됨 — git과
  동일한 셰이프). 보호 안 된 `feature-1` 북마크는 동일 세션에서 정상 push됨.
  (참고: `admins_can_bypass` 기본값 true 상태에서 프로젝트 매니저로 push하면 정책과 무관하게
  통과하는 것도 함께 확인 — GitHub와 동일한 의도된 동작이며 버그 아님.)
- **SSH**: 동일 컨테이너, `hg clone ssh://hg@localhost/admin/hgproj`(포트 12222) → 성공.
  `hg push -B ssh-feature`(보호 안 됨) → 성공, `hg push -B main`(보호됨) →
  `updating bookmark main failed`로 실패. 서버 로그에 스레드명 `yona-ssh-relay-conn`(=P3-18
  소켓 릴레이 경로를 실제로 탔다는 증거)과 함께 동일한 거부 사유가 기록됨 — HTTP/SSH 두 경로가
  완전히 동일한 정책을 공유함을 실측으로 확인.
- **require_signed_commits**: 실제 컨테이너 대신(컨테이너 6.1.1엔 최신 hg4j 서명 임베딩 포맷
  검증기가 없어서가 아니라, 단순히 순수 크립토 흐름이라 컨테이너가 굳이 필요 없어서)
  `HgPushHooksIntegrationSpec.kt`(신규 Spring 통합 테스트, 실제 `gpg` 바이너리 + 실제
  hg4j `CommitCommand.setGpgSigner()` + 실제 `GpgSignatureVerifier`/`GpgKeyRepository` 빈)로
  end-to-end 검증했다 — HgGpgSignatureVerifierSpec.kt(P3-19)와 동일한 신뢰 수준. 서명 없는
  커밋 거부/실제 서명+키 등록+이메일 인증된 커밋 허용/서명은 됐지만 키 미등록인 커밋 거부
  3가지 케이스 전부 GREEN(실제 gpg 서명 검증, mock 아님).

### 발견했지만 고치지 않은 것(범위 밖)

- **Mercurial PR 병합은 동작하지 않는다**(실측 확인) — `PullRequestServiceImpl.attemptMerge()/
  previewMerge()/merge()/updateMerge()`가 전부 `FileRepositoryBuilder().setGitDir(gitDir)`로
  시작해 JGit 전용으로 하드코딩돼 있다. PR "생성" 자체는 `createPullRequest()`가
  `processMergeCheck()` 예외를 의도적으로 삼키게(`catch (e: Exception) { }`) 만들어져 있어
  겉보기엔 201로 성공하지만(실측: `POST /api/projects/{id}/pullrequests`로 실제 Mercurial
  PR 생성 성공 확인), 이후 관련 PR 재검사(`RelatedPullRequestMergeEvent`)가 실제로 발동되면
  `org.eclipse.jgit.errors.NoRemoteRepositoryException: <hg 저장소 경로>: not found`로 실패한다
  (실측 확인, 서버 로그의 스택트레이스로 정확히 재현 — `PullRequestMergeEventListener`가 이
  예외를 잡아 ERROR로 로깅만 하고 앱은 죽지 않는다). 즉 diff/충돌 계산·머지 커밋 생성 등 PR의
  핵심 기능은 Mercurial 프로젝트에서 전혀 동작하지 않는다 — `PullRequestServiceImpl`을
  `RepositoryService`/`PlayRepository` 추상화 위로 다시 쓰는 별도의 큰 작업이 필요해(P3-21/
  P3-22 범위를 크게 벗어남) 이번 티켓에서 손대지 않았다. 관련 PR 재검사 이벤트 발행
  (`RelatedPullRequestMergeEvent`) 배선 자체는 완료했고 정상 동작한다 — 리스너가 예외를 잡아
  로그만 남기고 앱이 죽지 않는 것도 확인했다.
- **`/api/{owner}/{projectName}/pushedBranches` REST 엔드포인트의 순환 참조 직렬화 버그**
  (실측 발견, Git/Mercurial 무관 — 이번 작업과 무관한 기존 버그) — 최초 실사용 검증 시
  `HttpMessageNotWritableException`으로 응답이 깨진다고 기록했으나, **코디네이터가 직접
  재검증한 결과 진단이 정정됐다**: 실제로는 예외 없이 **HTTP 200**이 정상 응답되며(끝까지
  올바르게 닫힌 JSON, 60154바이트), `User.projectUsers` ↔ `ProjectUser.user`의 양방향 순환
  참조가 Jackson 기본 최대 중첩 깊이에 걸릴 만큼 깊게 반복되면서 **`User.password`/
  `passwordSalt`(해시된 값이지만)까지 API 응답에 그대로 노출**되는, 예외로 실패하는 것보다
  더 나쁜 정보 노출 문제였다. Git 프로젝트로도 동일하게 재현(60KB, 동일 패턴)해 VCS와
  무관한 순수 기존 결함임을 확정했다. **P3-26으로 별도 등록해 발견 즉시 수정 완료**
  (`ProjectController.PushedBranchDto`로 교체, 수정 후 실제 응답:
  `[{"id":1,"name":"protected-branch","pushedDate":"..."},...]`).
