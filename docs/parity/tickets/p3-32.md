# P3-32: SAML 로그인 사용자가 yona를 OAuth2 공급자로 쓰면 동의/토큰 발급이 500으로 깨지던 버그 수정

## 배경

사용자가 "SAML SSO로 로그인한 사용자가 그대로 yona를 OAuth2 공급자(Sign in with yona)로도 쓸 수
있는가"라고 질문. 정적 코드 분석(`principal.name`만 쓰는 제네릭한 설계 — `OAuthConsentController`/
`ResourceIndicatorTokenCustomizer` 등)으로는 문제가 없어 보였으나, 실제로 검증해달라는 요청에
따라 `kristophjunge/test-saml-idp` 테스트용 SAML IdP를 실제로 컨테이너로 띄우고, 실제 브라우저로
SAML 로그인 → OAuth2 앱 등록 → `/oauth2/authorize` → 동의 → `/oauth2/token`까지 전체 플로우를
실사용 검증하는 과정에서 **두 단계에서 각각 500 에러가 재현됐다.**

## 근본 원인 (2단계)

`OAuthObjectMapper`(P3-07 Step6에서 이미 확립된 패턴)는 OAuth2 동의 처리 과정에서 인증된
Principal을 JSON으로 저장했다가 나중에 다시 읽어오는데(`JpaOAuth2AuthorizationService`),
Jackson의 `PolymorphicTypeValidator` 화이트리스트에 없는 타입은 역직렬화 시점에
`InvalidTypeIdException`으로 거부된다.

1. **1단계(Authorize 클릭 시 500)**: 로컬 폼 로그인의 `YonaUserDetails`는 이미 화이트리스트에
   있었지만, SAML 로그인의 `YonaSaml2AuthenticatedPrincipal`은 없었다 — SAML이라는 세 번째
   로그인 경로가 이 화이트리스트 메커니즘의 존재 자체를 몰랐던 것.
2. **2단계(토큰 교환 시 500, 1단계 수정 후 재현)**: `YonaSaml2AuthenticatedPrincipal`을
   화이트리스트에 추가해도, 그 안에 raw JPA `User` 엔티티(`val user: User`)를 통째로 물고 있어서
   `User` 타입 자체가 또 다른 다형성 슬롯으로 걸렸다. `User`까지 화이트리스트에 추가하는 안은
   기각했다 — 이 세션에서 이미 여러 번([[tickets/p3-26]]/[[tickets/p3-28]]/[[tickets/p3-30]])
   고친 "raw 엔티티 직렬화 시 순환 참조/필드 노출" 문제군과 같은 함정이기 때문.

## 수정

1. `OAuthObjectMapper.kt`: `YonaUserDetails`와 동일한 방식으로
   `allowIfSubType(YonaSaml2AuthenticatedPrincipal::class.java)` 추가.
2. `YonaSaml2AuthenticatedPrincipal.kt`: `val user: User`로 엔티티 전체를 물고 있던 설계를
   `YonaUserDetails`와 동일한 패턴(필요한 값만 원시 타입으로 평탄화 + `@JsonCreator`/
   `@JsonProperty`)으로 리팩터링. `userId: Long?`/`loginId: String`/`attributes`/
   `relyingPartyRegistrationId`/`sessionIndexes`만 보관, `(user: User, delegate)` 보조
   생성자는 기존 호출부(`EnterpriseSaml2ResponseAuthenticationConverter`) 호환을 위해 유지.
3. 테스트 1곳(`EnterpriseSaml2ResponseAuthenticationConverterSpec`)의
   `principal.user.id shouldBe 11L`을 `principal.userId shouldBe 11L`로 갱신(설계 변경에
   따른 필수 수정).

## 완료 기준

- SAML 로그인 → OAuth2 앱 등록 → `/oauth2/authorize` → 동의 → `/oauth2/token`까지 500 없이
  끝까지 성공.
- 발급된 토큰(id_token)의 `sub` 클레임이 SAML로 로그인한 사용자의 loginId와 일치.
- 관련 테스트 전부 GREEN.

## 완료 로그

### 2026-09-09 — 실사용 검증으로 발견, 근본원인 규명, 수정, 재검증까지 완료

**재현 환경**: `docker run kristophjunge/test-saml-idp`(포트 18081/18444)를 yona 임시
인스턴스(H2, 포트 18099, `--yona.sso.saml2.*`/`--yona.base-url` 부트 인자로 SAML SP 설정,
관리자 UI 없이 구성 — `SsoSettingsService`가 프로퍼티를 DB 기본값으로 읽는 점 활용)와 연동.
IdP 메타데이터에서 entityId/SSO URL/서명 인증서를 추출해 yona SP 설정에 반영, IdP 쪽에는
`SIMPLESAMLPHP_SP_*` 환경변수로 yona의 SP entityId(`{base-url}/saml2/service-provider-metadata/saml2`)/
ACS(`{base-url}/login/saml2/sso/saml2`, registrationId 기본값 `"saml2"` 확인)를 등록.

**1차 재현 시도 실패**: `yona.base-url` 기본값(`http://localhost:8080`)이 실제 포트(18099)와
달라 AuthnRequest의 Issuer가 틀려 IdP가 "Unable to locate metadata" 500을 냄 —
`--yona.base-url=http://localhost:18099`로 해결(`YonaRelyingPartyRegistrationRepository`가
이 프로퍼티로 SP entityId/ACS를 조립하는 것 확인).

**실제 브라우저(claude-in-chrome)로 전체 플로우 재현**: curl로 SAML POST 바인딩/리다이렉트
체인을 직접 흉내내려다 세션 연속성 문제로 실패해 실제 브라우저로 전환 — `user1`/`user1pass`
(test-saml-idp 기본 계정)로 IdP 로그인 → yona가 JIT 프로비저닝(loginId=`user1`,
email=`user1@example.com`)까지 정확히 확인 → `/user/editform/oauth-apps-owned/new`(이번 세션
앞부분에서 이미 고친 P3-17 버그 덕에 정상 동작)로 confidential OAuth2 클라이언트 등록 →
`/oauth2/authorize` → 동의 화면(`User: user1` 정상 표시) → **"Authorize" 클릭 시 500 재현**
(위 1단계 원인) → 수정 → 재검증 시 동의는 통과했으나 **`/oauth2/token` 교환 시 500 재현**(위
2단계 원인) → 수정 → 재검증: `/oauth2/authorize`(scope=openid) → 동의 없이 바로 인가 코드
발급(단일 openid 스코프라 자동 승인된 것으로 보임) → `/oauth2/token`(resource 파라미터 필요 —
`ResourceIndicatorTokenCustomizer` 계약과 일치, `resource=http://localhost:18099/api/v1`
추가)으로 access_token/refresh_token/id_token 200 정상 발급, id_token payload의 `sub`가
`user1`로 정확히 일치함을 JWT 디코딩으로 직접 확인.

**회귀 검증**: `EnterpriseSaml2ResponseAuthenticationConverterSpec`(1)/
`JpaOAuth2AuthorizationServiceSpec`(3)/`McpOAuth2SecurityIntegrationSpec`(10)/
`OidcSignInIntegrationSpec`(3)/`OAuthAppRegistrationServiceSpec`(4)/`UserViewControllerSpec`
(145) 총 166개 테스트 전부 GREEN(실패/에러 0건) — 소셜/엔터프라이즈 OIDC 로그인, MCP OAuth2,
OAuth 앱 등록 경로 전부 무회귀 확인.

**결론**: SAML SSO + yona OAuth2 공급자 조합은 이제 실사용 검증까지 완료된 상태로 정상
동작한다. 테스트 IdP 컨테이너/임시 yona 인스턴스는 검증 후 모두 정리(삭제)했다 — 이 조합에
대한 상시 자동화 통합테스트는 이번 라운드 범위 밖으로 남겨둔다(다음 담당자가 필요하다고
판단하면 이 티켓의 재현 레시피를 그대로 Testcontainers화할 수 있음).
