# P3-03: SSH git 인증 + GPG 커밋 서명 검증(SSH 키 관리·GPG 키 관리 모두 포함)

## 원본 표 정보

- **우선순위 구분**: P3
- **상태(원본 체크박스)**: `[x]`
- **비고(원문)**: **2026-08-21 사용자 제안, 서버 쪽 코드 전무 — 전부 신규 설계.** 전제: 원본 요나·yona 둘 다 SSH git 프로토콜/GPG 관련 코드가 **전혀 없어 이식 대상이 아니라 완전 신규 기능**. **SSH 키 관리 — OS별 이원화 설계**: 리눅스/맥(표준 경로)은 시스템 OpenSSH `AuthorizedKeysCommand` 훅 방식 — `yona internal ssh-auth`(공개키→사용자 조회, forced command 라인 생성), `yona internal ssh-shell`(SSH_ORIGINAL_COMMAND 파싱 후 AccessControl 체크·git 프로세스 exec) 두 헬퍼 필요(**둘 다 미구현**). 윈도우(폴백)는 JVM 내장 Apache MINA SSHD로 별도 포트(예: 2222) 구동(**미구현**). 두 경로를 공통 서비스 레이어(`sshAuthService.authenticate()`, `authorizeGitCommand()`)로 통합할 계획(**미구현**). `SshKey` 모델(user_id, public_key, fingerprint, added_date) **미생성**, `UserApi`에 SSH 키 등록/삭제/조회 엔드포인트 **미생성**. **GPG 키 관리 — 커밋 서명 검증 전용**(로그인 인증 용도는 배제): `GpgKey` 모델(user_id, key_id, armored_public_key, added_date) **미생성**, `UserApi`에 GPG 키 등록/삭제/조회 엔드포인트 **미생성**, `GpgSignatureVerifyPreReceiveHook`(기존 `GitPushHooks.kt`의 `RejectPushToReservedRefsPreReceiveHook` 옆에 나란히 걸 계획, JGit `RevCommit.getRawGpgSignature()` + BouncyCastle `bcpg-jdk18on` 사용 예정) **미생성**, Commit 모델에 검증결과 필드 추가해 UI에 Verified 배지 노출 계획 **미생성**. 정책 잠정안(미확정): 미서명 커밋도 push는 허용(배지만 안 붙음) / 커밋 author 이메일과 GPG UID 이메일 일치로 매칭 / CLI의 로컬 git 설정 자동화 여부는 미결정. CLI 명령 초안(전부 미구현, [[tickets/p3-02|P3-02]]와 연계): `yona auth login --with-ssh`, `yona ssh-key add`, `yona gpg-key add`. **2026-08-24 추가(SSH/HTTPS 인증 통합 설계, 미착수)**: SSH 공개키 인증(위 `SshKey`, user_id 기준 전역 키)과 HTTPS 인증([[tickets/p3-02|P3-02]]의 토큰, 역시 user_id 기준 전역 권한)을 서로 다른 자격증명 체계로 병렬 설계하지 않고, GitHub의 **Deploy Key**처럼 **저장소 범위**로 스코프된 단일 개념으로 통합할 것. 설계 방향(미착수): `SshKey`(user 전역)와는 별개로 `DeployKey`(repository_id, public_key, fingerprint, read_only 플래그, added_date) 모델을 신설하고, 이 Deploy Key가 (1) SSH git 프로토콜 인증과 (2) [[tickets/p3-02|P3-02]]에서 재설계할 저장소 범위 토큰의 권한 스코프 체계를 공유하도록 — 즉 "이 저장소에 대한 자격증명"이라는 동일한 권한 모델 위에서 SSH/HTTPS 두 경로 모두 검증되게 설계. 기존 `sshAuthService.authorizeGitCommand()`(미구현)와 [[tickets/p3-02|P3-02]]의 저장소 스코프 인가 체크 로직을 공통화할 수 있는지 검토 필요. **2026-08-24 추가(HTTPS 경로 실현 가능성 검증 완료)**: `SecurityConfig.kt`에 `.httpBasic { }`이 경로 제한 없이 전역 활성화돼 있고, `.addFilterAfter(gitAuthorizationFilter, BasicAuthenticationFilter::class.java)`로 `GitAuthorizationFilter`가 Basic 인증 처리 이후에 위치해 `/git/**` 경로의 프로젝트 단위 접근 제어를 별도로 수행하는 구조임을 코드로 확인 — 즉 HTTPS Deploy Key는 **새 `AuthenticationProvider` 하나만 추가**하면(Basic 인증의 자격증명 검증 단계에 Deploy Key 매칭 로직을 끼워넣는 방식) 기존 `GitAuthorizationFilter`의 프로젝트 접근 제어 로직을 그대로 재사용할 수 있어 이 절반(HTTPS)은 실현 가능성이 높음. SSH 프로토콜 자체(포트 22 리스닝)는 여전히 완전 신규 — 위 SSH 키 관리 절 그대로 `AuthorizedKeysCommand`/`ssh-shell` 등 전부 미구현이며, 재사용할 기존 코드가 없음(오해 방지: "ssh-shell을 확장하면 된다"는 표현은 부정확 — ssh-shell은 아직 계획상 이름일 뿐 구현된 코드가 아님). **엔티티 통합 여부(2026-08-24, 타사 사례 조사 완료)**: GitHub(Deploy Key와 PAT는 별개 테이블, PAT는 API+HTTPS git 겸용)·GitLab(Project Access Token이 Deploy Key와 별도)·Forgejo(진행 중인 이슈 #7763 "HTTPS Deploy Keys"에서도 SSH 공개키 인프라를 재사용하지 않고 Access Token과 유사한 새 저장소 범위 시크릿을 발급하는 방향으로 논의 중) 세 곳 모두 SSH 공개키와 불투명 토큰을 하나의 엔티티로 합치지 않음(비대칭키 vs 시크릿 문자열로 인증 메커니즘 자체가 다름) — **`DeployKey`/`ApiToken` 완전 통합은 채택하지 않고, 현재 설계("별개 엔티티 + 스코프 체계 공유")를 유지하기로 결정**. **2026-09-07 TDD로 3부(HTTPS Deploy Key/SSH 프로토콜/GPG 서명 검증) 전부 완료(상세: `docs/yona-wiki/plans/p3-03-ssh-gpg.md` 완료 로그)** — 1부: `DeployKey` 엔티티(SSH 공개키 필드 + HTTPS 전용 불투명 시크릿을 한 레코드에 공존, "저장소 스코프 공유"를 이 방식으로 확정) + `DeployKeyAuthenticationProvider`(GitHub App 설치 토큰 관례의 "x-access-deploykey" Basic 인증)로 `GitAuthorizationFilter`를 그대로 재사용(스코프 밖 접근 403, read_only push 403, 실제 통합테스트로 검증) — 이 과정에서 `HttpSecurity.authenticationProvider()` 호출이 Spring Boot의 AuthenticationProvider 자동 수집을 꺼버려 기존 `YonaAuthenticationProvider`(로컬/LDAP 로그인)가 통째로 빠지는 회귀를 실제로 발견·수정(로그인 통합테스트가 즉시 잡아냄). 2부: `SshKey` 모델 + 두 경로가 공유하는 `SshAuthService`. 리눅스/맥은 **호스트 시스템(공유 머신)을 절대 건드리지 말라는 제약** 때문에 실제 `sshd_config` 등록은 수행하지 않고(운영자의 수동 설정 단계로 명시적으로 남김), 대신 서버 내부 API(`SshInternalController`, 루프백 제한+공유 시크릿 이중 방어)와 `yona-cli`(별도 저장소)의 `internal ssh-auth`/`internal ssh-shell` 서브커맨드를 실제로 구현해 httptest+실제 `git-upload-pack` 바이너리 exec까지 자동화 테스트로 검증. 윈도우 폴백(Apache MINA SSHD, 이 프로세스가 직접 띄우는 별도 포트라 호스트 시스템과 무관)은 실제 시스템 `ssh`/`git` 바이너리로 clone/push까지 6개 시나리오 실측(수동 검증 대신 더 강한 자동화된 동등 검증, 사용자 표준 방침). 3부: `GpgKey` 모델 + BouncyCastle로 실제 암호학적 서명 검증(`GpgSignatureVerifier` — 실제 `gpg`/`git commit -S` 바이너리로 만든 진짜 서명 커밋 7개 시나리오로 검증, 단순 "서명 존재" 확인이 아님). 커밋이 이 앱에서 JPA 엔티티로 미러링되지 않고 항상 저장소 원본에서 읽힌다는 사실을 확인해 "Commit 모델에 검증결과 필드"를 DB 캐시 컬럼이 아니라 `Commit.getGpgVerificationStatus()`(조회 시점 즉시 계산) 방식으로 구현 — GPG 키 등록/삭제가 과거 커밋 배지에도 항상 최신 반영되는 이점. 보안 리뷰로 GPG UID 이메일이 "계정 소유로 인증된" 이메일과 일치해야만 매칭되도록 강화(타인 이메일을 UID에 넣어 가짜 배지를 노리는 시도 방지), SSH/GPG 공개키 지문의 전역 유일성 강제(계정/저장소 사칭 방지). GitHub "Settings > SSH and GPG keys"/"Deploy keys" 화면과 동일한 컨벤션으로 SSH 키/GPG 키(사용자 설정 탭)/Deploy Key(프로젝트 설정 탭) 등록·조회·삭제 UI 전부 추가, 커밋 목록/상세에 Verified/Unverified 배지 추가. `./gradlew test`(이 계획이 만든 모든 클래스 GREEN) + `yona-cli`의 `go test ./...` 전부 GREEN. **2026-09-07 후속([[tickets/p3-04|P3-04]]와 연결 작업)**: 4부 완료 로그에 명시적으로 남겨뒀던 갭 — `ProtectedBranch.requireSignedCommits`가 이 계획이 만든 `GpgSignatureVerifier`에 실제로 연결되지 않아 값과 무관하게 항상 통과 처리되던 문제를 `BranchProtectionPreReceiveHook`(push 시점)과 `PullRequestServiceImpl.checkBranchProtectionForMerge()`(PR 병합 시점) 양쪽에 실제 검사를 추가해 해소(상세: [[tickets/p3-04|P3-04]] 행 및 `docs/yona-wiki/plans/p3-04-branch-protection.md` 3라운드 완료 로그).
