## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-30**: 코드리뷰 스레드/커밋 댓글에 대한 메일 답장이 `ISSUE_POST`/`BOARD_POST`만 인식하는 `resolveResourceProject`/`createComment` 분기에 걸려 조용히 스킵되던 문제 수정(yona `EmailHandler.getThreads()`의 `COMMENT_THREAD`/`REVIEW_COMMENT→컨테이너` 분기 대응).
  - `IncomingMailOutcome`에 `ReviewCommentCreated(commentId, threadId)`/`CommitCommentCreated(commentId)` 추가. `resolveResourceProject`에 `ResourceType.COMMENT_THREAD`(→ `CommentThreadRepository`)/`COMMIT_COMMENT`(→ `CommitCommentRepository`) 케이스 추가. `createComment`에서 `COMMENT_THREAD`면 `CodeReviewService.createReviewComment(project, null, null, body, null, threadId, sender)`로 같은 스레드에 리뷰 댓글을 추가, `COMMIT_COMMENT`면 원본 댓글의 commitId/path/line/side를 그대로 재사용해 `CodeReviewService.createCommitComment(...)`로 새 커밋 댓글을 만든다(yona는 [[tickets/p0-16|P0-16]]에서 커밋 댓글에 별도 스레드 개체 없이 단순 `CommitComment` 목록으로 이식했으므로, "답장"은 같은 위치에 댓글을 추가하는 것으로 표현).
  - `ReviewCommentCreated`의 `OriginalEmail.resourceId`는 새 댓글이 아니라 **스레드 id**를 추적한다 — yona도 `REVIEW_COMMENT` 리소스가 오면 `resource.getContainer()`(스레드)를 추적 대상으로 삼는 것과 동일한 이유(한 스레드에 달리는 여러 댓글이 전부 같은 스레드로 수렴해야 함).
  - **발견 후 별도 등록, 이후 해소**: 당시엔 "이미 메일로 만들어진 리뷰/커밋 댓글에 대한 재답장" 체인만 동작하고, UI에서 직접 작성한 리뷰/커밋 댓글의 첫 알림 메일에 대한 답장은 스레드로 연결되지 않는 gap이 있어 **[[tickets/p1-60|P1-60]]으로 별도 등록**했다. [[tickets/p1-60|P1-60]]에서 재조사한 결과 최초 가설("발신 시점에 `OriginalEmail`을 기록해야 한다")은 틀렸음이 확인됐고, 대신 `Resource.getMessageId()`의 결정론적 포맷(`"<{type}/{id}@{host}>"`)을 역파싱하는 yona `EmailHandler.findResourcesByMessageId()`의 폴백 방식을 그대로 이식해 별도 저장 없이 해결됨(`[x]`, 아래 [[tickets/p1-60|P1-60]] 완료 로그 참고).
  - 테스트: `IncomingMailProcessingServiceSpec.kt` +2(COMMENT_THREAD 답장 시 리뷰 댓글 생성 및 스레드id 추적 확인, COMMIT_COMMENT 답장 시 동일 위치에 새 커밋 댓글 생성 확인) — 기존 12건 포함 총 14 tests. `com.github.yonaprojects.yona.domain.pullrequest.*`/`YonaApplicationTests` 재실행으로 회귀 없음 확인.
  - 검증: `./gradlew test --tests "com.github.yonaprojects.yona.domain.mail.*" --tests "com.github.yonaprojects.yona.domain.pullrequest.*" --tests "YonaApplicationTests"` 전체 통과, `./gradlew compileKotlin compileTestKotlin` 전체 컴파일 성공.
