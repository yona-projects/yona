## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-71**: PR 병합 재검사 시 conflict 상태 전환(충돌 발생/해소)이 알림·PR 타임라인 어디에도 기록되지 않던 문제 수정.
  - `PullRequestServiceImpl.processMergeCheck()`에 `wasConflict`를 `updateMerge()` 호출 **전**(재검사 이전 상태)에 미리 캡처하도록 추가(yona `PullRequestActor.processPullRequestMerging()`의 `boolean wasConflict = pullRequest.isConflict` 대응). 재검사 후 diff/커밋 처리 분기와는 완전히 독립적으로 `!wasConflict && result.conflicts()`(충돌 발생)/`wasConflict && !result.conflicts()`(충돌 해소) 두 조건을 확인해 새 헬퍼 `notifyMergeConflictChanged(pullRequest, sender, state)`를 호출한다.
  - `notifyMergeConflictChanged()`: yona `NotificationEvent.afterMerge()`/`PullRequestEvent.addMergeEvent()` 대응 — `eventType=PULL_REQUEST_MERGED`(이름과 달리 "머지 완료"가 아니라 conflict 전환 전용이라는 점을 주석으로 명시 — 실제 "머지 완료"는 기존 `changeState(..., MERGED, ...)`의 `PULL_REQUEST_STATE_CHANGED`가 담당), `newValue=state.state()`("conflict"/"resolved"). 수신자 계산은 기존 `changeState()`와 동일한 패턴(`watchService.findActualWatchers(baseWatchers=contributor)`, sender 자기 자신 제외) 재사용, `recordPullRequestEvent()` 재사용으로 타임라인도 함께 기록.
  - 테스트: `PullRequestServiceSpec.kt` +1(실제 JGit으로 충돌하는 두 브랜치를 만들어 1차 재검사에서 `PULL_REQUEST_MERGED`/`newValue="conflict"` 알림+타임라인 생성 확인 → 소스 브랜치를 대상과 동일 내용으로 갱신해 충돌 해소 → 2차 재검사에서 `newValue="resolved"` 알림+타임라인이 추가로 생성됨을 확인, 실제 conflict→resolved 왕복을 real merge로 검증). 인접 회귀: 기존 21 tests 그대로 통과.
  - 검증: `./gradlew compileKotlin compileTestKotlin`, `PullRequestServiceSpec` 22 tests 전체 통과.
