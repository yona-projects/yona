# P3-46: 클라이언트 위젯 라이브러리 현대화 (2026-09-10 사용자 제안)

## 배경

[[tickets/p3-45|P3-45]](Tailwind CSS + htmx 템플릿 리팩터링) 계획서 작성 중, yona가 현재 쓰는
클라이언트 전용 위젯 라이브러리 상당수가 오래되거나 사실상 유지보수가 멈춘 것이 확인됐다. 사용자가
이를 지적하며 최신·활발히 유지되는 라이브러리로 교체할 것을 제안했다.

P3-45는 "화면 재설계 없이 CSS/상호작용 구현 방식만 교체"하는 낮은 리스크의 작업으로 범위를
한정하면서, 클라이언트 위젯 라이브러리 교체는 **비범위로 명시적으로 제외**했다 — 위젯 하나하나가
자체 API/이벤트 모델을 가진 별도 라이브러리라 교체마다 고유한 회귀 리스크가 있고, 182개 템플릿
리팩터링에 얹으면 리스크가 배가되기 때문이다. 이 티켓은 그 제외된 범위를 별도로 추적하기 위해
신설한다.

### 8번 항목 세부 결정사항 (2026-09-10, 실제 화면 스크린샷 비교 후 사용자와 확정)

항목1~7 완료 후, Playwright로 **현재 yona 에디터 실제 화면**과 **EasyMDE 기본 모양** 스크린샷을
나란히 찍어 비교한 뒤 다음을 확정했다:

- **편집 엔진**: EasyMDE(CodeMirror 기반) — 확정, 재검토 불필요.
- **편집/미리보기 전환**: EasyMDE 기본값(단일 뷰 토글)을 그대로 쓴다 — yona의 기존 탭(편집/
  미리보기 별도 탭) UI는 유지하지 않는다(사용자 확정: "mde 기본값으로 하자").
- **겉모양**: EasyMDE 기본 스타일(회색 톤, FontAwesome류 아이콘)을 그대로 쓰지 않고, yona
  기존 버튼/아이콘 체계(`.ybtn`, `yobicon-*` 아이콘 폰트)로 재스킨한다.
- **"마크다운 도움말" 패널(`help/markdown.html` 프래그먼트)은 변경 없이 그대로 유지한다.**
  조사 결과 이 패널은 텍스트 삽입 툴바가 아니라 "마크다운 입력→출력" 예시를 보여주는 접이식
  치트시트(Header/Text Style/Link/List/Checklist/Image/Blockquote/Code/Table + yona 고유의
  "Short Link"—`#이슈번호`/`@멘션`/`@커밋해시` 문법 설명)였고, 텍스트에어리어/에디터 엔진과
  완전히 독립된 별도 조각이라 에디터 교체와 무관하게 그대로 둘 수 있다(EasyMDE 자체 도움말로는
  yona 전용 문법을 설명 못 해 대체 불가하기도 함).
- EasyMDE 자체 내장 `?`(도움말) 툴바 버튼은 끈다 — 범용 외부 가이드로 링크되어 위 yona 도움말
  패널과 중복/상충.
- 체크리스트 삽입 버튼("체크리스트 추가"): 직접 구현 대신 EasyMDE 내장 체크리스트 툴바 버튼으로
  대체한다.
- "임시저장 지우기" 버튼, "알림수신자 목록"(notification-receiver-list)은 yona 고유 기능이라
  EasyMDE에 없음 — 새 에디터 기준으로 별도 연동 필요(아래 0단계 조사 대상).
- 미리보기 렌더링: EasyMDE 내장 마크다운 렌더러 대신 `yobi.Markdown`(marked v18 + highlight.js
  v11 + `$yobi.xssClean`, 항목6/7에서 완성)을 그대로 재사용하도록 `previewRender` 옵션을
  연결한다 — 조회 화면 렌더링 결과와 100% 동일 보장.

### 8번 작업 단계 (분할정복 기준, 2026-09-10 합의)

분할 기준 3가지: (1) 각 단계가 독립적으로 TDD 가능하고 자기완결적일 것, (2) 의존 순서대로(셸
교체 → 그 위에 얹는 기능들), (3) 위험도/불확실성이 큰 것부터 — 특히 에디터 UI의 상당 부분
(체크리스트/임시저장/알림수신자 로직)이 읽을 수 있는 소스에 없고 `yona-lib.js` 번들에만
박혀있음을 이미 확인했다(항목3/6·7과 동일한 패턴 — `yona.ReceiverList.js` 소스 파일이 있지만
로드되지 않음).

1. [x] **0단계(조사, 2026-09-10 완료)**: 체크리스트/임시저장/알림수신자 실제 동작 확인.
   **당초 가정("전부 yona-lib.js 번들에만 박혀있다")은 틀렸다** — 실제로는:
   - **"체크리스트 추가" 버튼**: `.js` 파일에는 핸들러가 없었지만(0단계에서 `.js` 파일만
     grep해서 놓침), **1단계 에이전트가 발견 — `site/layout.html`에 직접 박힌 인라인
     `&lt;script&gt;`(`$(".add-task-list-button").on('click', ...)`)에 실제 동작하는 핸들러가
     있었다.** 커서 위치에 체크리스트 템플릿 텍스트를 삽입하는 기능으로 실제 동작 중이었음
     (정정 — "완전히 죽은 버튼"이 아니었음). 다만 EasyMDE 내장 체크리스트 버튼으로 대체하는
     결정 자체는 바뀌지 않음(동등 기능 제공) — 1단계 완료 후 이 인라인 스크립트는 대상 없는
     죽은 코드로 남음(에러 없이 조용히 no-op).
   - **"임시저장 지우기" 버튼**: 클릭 핸들러 없어 죽어있음. 다만 **임시저장(초안 자동저장) 시스템
     자체는 살아있고 정상 작동 중**(`temporarySaveHandler`/`removeCurrentPageTemprarySavedContent`
     전역 함수 — 소스 파일 `service/yona.temporarySaveHandler.js`는 어디서도 로드 안 되고
     `yona-lib.js` 번들의 사본만 실행 중이지만, 내용은 소스와 동일해 항목3/6·7 같은 "구버전 사본"
     문제는 아님. 댓글/이슈/마일스톤/게시글/PR 작성 화면 전부에서 실제 호출되는 걸 확인). **사용자
     결정: 지금 함께 고침** — 버튼을 `removeCurrentPageTemprarySavedContent()`에 연결.
   - **"알림수신자 목록"**: 관련 소스(`common/yona.ReceiverList.js`,
     `findNotiReceiversHandler($textarea, url)` — 입력 내용 기준 1초 디바운스로 서버에 물어
     알림 받을 사람 미리보기)가 **소스·번들 어디에서도 호출된 적 없어 완전히 죽어있음**, 게다가
     대응하는 백엔드 API 자체가 yona에 아직 이식되어 있지 않음(`docs/parity/index.md`에도
     미등록). legacy에 `POST .../issues/:number/commentNotiReceivers` →
     `IssueApi.commentNotiRecivers()`(이슈 댓글 전용, 임시 `IssueComment` 객체를 만들어
     `NotificationEvent.getMandatoryReceivers(comment, EventType.NEW_COMMENT)`로 계산)로 존재 —
     이 로직에 대응하는 `getMandatoryReceivers` 계열 함수가 yona
     `IssueServiceImpl.kt`에 이미 있어 백엔드 이식 자체의 난도는 낮음. **사용자 결정: 이번에
     같이 살림** — 이슈 댓글에 한정(legacy와 동일 범위)해 새 REST 엔드포인트 이식 + JS 연동.
2. [ ] **1단계(셸 교체)**: textarea+수제 탭 UI → EasyMDE 인스턴스(기본 토글), yona 스타일로
   재스킨. `name`/`value`/폼 제출 동기화만 우선 보장, 나머지 기능은 이 단계에서 끊어놔도 됨.
3. [ ] **2단계(미리보기 연동)**: `previewRender`를 `yobi.Markdown` 재사용하도록 연결.
4. [ ] **3단계(멘션 연동)**: Tribute(항목3)를 EasyMDE의 실제 입력 DOM(CodeMirror)에 연결.
5. [ ] **4단계(나머지 기능 재구현)**: 체크리스트는 EasyMDE 내장으로 대체. 임시저장 지우기
   버튼을 `removeCurrentPageTemprarySavedContent()`에 연결(승인됨). 알림수신자 목록은 이슈
   댓글 한정으로 새 REST 엔드포인트(`IssueApi.commentNotiRecivers` 이식, `IssueServiceImpl`의
   기존 mandatory-receivers 로직 재사용) + `findNotiReceiversHandler` 연동으로 되살림(승인됨).
   EasyMDE 자체 `?` 버튼 끔.
6. [ ] **5단계(전면 회귀 + 브라우저 실사용 검증)**: `markdownEditor` fragment를 쓰는 모든 화면
   개별 확인, 저장/업로드처럼 마크업만으론 못 잡는 부분은 Playwright로 실제 확인(이번 세션의
   CSRF/board-edit 사례처럼 숨은 버그가 나올 가능성 높음).

## 착수 원칙(사용자 지시, 2026-09-10)

- **TDD 에이전트로 라이브러리별 순차 진행.** 각 라이브러리 전환은 별도 작업 단위로 다룬다.
- **기존 라이브러리와 동작이 완전히 일치해야 한다** — TEMPLATE_BACKLOG/P3-45와 동일한 정신의
  "동치성 우선" 원칙. 새 라이브러리가 제공하는 부가 기능이 있어도 켜지 않는다(예: Tom Select의
  태그 생성 기능이 Select2엔 없었다면 끈 채로 유지). 옵션/이벤트/키보드 동작까지 최대한 맞춘다.

### 6+7. marked.js + highlight.js 버전업 (2026-09-10)

**TDD 에이전트가 계획만 세우고 구현 전에 턴이 끝나(항목3과 비슷한 패턴 — "테스트 대기 중"),
메인 세션이 직접 이어받아 완료했다.** 에이전트가 남긴 신규 스펙
(`MarkdownRendererWidgetTemplateEquivalenceSpec`, 매우 꼼꼼하게 설계돼 있었음)을 그대로
살려서 구현했다.

**착수 전 번들 중복 확인(항목3/5 교훈 적용, 이번엔 실제로 걸림)**: `marked(...)`/`hljs.*`를
실제로 호출하는 `common/yobi.Markdown.js`가 **이번에도 어느 템플릿에서도 `<script src>`로
로드되지 않고**, `yona-lib.js` 번들에 박힌 구버전 사본만 실행되고 있었음을 착수 전 확인.
`site/layout.html`의 `markdown(project)` fragment에 `yobi.Markdown.js`를 실제로 로드하는
`<script src>` 태그를 추가해 해결(항목3과 동일 패턴 — 스크립트 실행 순서상 새 정의가 번들의
구식 정의를 덮어씀).

**추가로 발견한 변형 함정**: `pullrequest/view.html`만 유일하게 `markdown(project)`
fragment를 `scripts` fragment(yona-lib.js 포함)**보다 먼저** include하고 있어서, 위 수정만으로는
부족했다 — 나중에 로드되는 `yona-lib.js`가 방금 로드한 새 정의를 다시 구버전으로 덮어써버림.
페이지 구조를 재배치하는 대신 `markdown` fragment의 include 위치를 `scripts` fragment 뒤로
옮겨서(다른 모든 페이지와 동일한 순서로 통일) 해결.

**버전**: marked **v18.0.12**(npm `marked` 패키지의 `lib/marked.umd.js` — 최신 버전은
사전 빌드된 `marked.min.js`를 배포하지 않아 UMD 번들을 직접 사용), highlight.js
**v11.12.0**(`@highlightjs/cdn-assets` 공식 CDN 번들, 전체 언어 포함 — 기존과 동일하게
`hljs.configure({languages:[]})`로 자동감지 비활성 유지).

**API 이식 상세**:
- `marked(text, options)` 함수형 호출 → `marked.parse(text, options)`.
- 구버전 `highlight` 콜백 옵션(marked v5+에서 제거됨) → `marked.use({renderer: {code(token){...}}})`
  커스텀 렌더러로 이식. `hljs.getLanguage(lang)`으로 언어 지원 여부를 먼저 확인(구버전은
  예외로만 판별) 후 `hljs.highlight(code, {language: lang}).value`(신버전 시그니처 — 코드가
  첫 인자) 호출. 원본의 `langPrefix:''`(클래스 접두어 없음, "hljs" 클래스도 원래 안 붙어있었음)
  동작을 그대로 재현 — 언어가 있으면 `<code class="lang">`, 없으면 `<code>`, HTML 이스케이프는
  직접 구현(`marked`가 커스텀 렌더러 사용 시 이스케이프를 대신 안 해줌).
- `hljs.highlightBlock(block)` → `hljs.highlightElement(block)`(서버사이드 렌더링 경로,
  `_render()`의 AJAX 성공 콜백).
- `hljs.initHighlightingOnLoad()`(v11에서 제거) → `hljs.highlightAll()`.
- highlight.js 테마 CSS(`styles/*.css`, 70여 개) 파일은 업데이트하지 않음 — v9→v11 사이
  `.hljs-*` 클래스 네이밍 체계가 안정적으로 유지돼 색상 테마와는 무관하다고 판단(메인 세션 판단,
  변경 없이 그대로 둠).

메인 세션이 npm으로 marked v18/highlight.js v11을 직접 설치해 `renderer.code(token)` 콜백
시그니처(`{type,raw,lang,text}`)와 `hljs.highlight()` 신버전 반환값을 실측 검증한 뒤 이식.
신규 `MarkdownRendererWidgetTemplateEquivalenceSpec`(14케이스, `pullrequest/view`의 fragment
순서 검증 포함) 전부 GREEN(도중 테스트 픽스처 자체 버그 하나 발견·수정 — `pull/new` 테스트가
git 저장소 없이 프로젝트를 만들어서 `PullRequestViewController.createPullRequestForm()`이
`error/badrequest`로 리다이렉트해버리는 바람에 실패했었음, 브랜치가 있는 bare git 저장소를
만들어주는 기존 패턴을 추가해 해결) + `IssueViewControllerSpec`/`PullRequestViewControllerSpec`/
`BoardViewControllerSpec` 회귀 없음, 전부 개별 `--tests` 실행.

**범위 밖 발견**: 서버사이드 마크다운 렌더링 경로(`_render()`, `htVar.sMarkdownRendererUrl`로
POST 후 HTML을 받아오는 방식)는 Kotlin 서버 쪽 렌더러 문제라 이번 작업(클라이언트 JS 라이브러리
버전업) 범위 밖으로 확인만 하고 손대지 않음.

**수동 브라우저 확인 필요(미착수)**: 마크다운 렌더링 결과 HTML이 기존과 동일한지, 코드블록
문법 강조가 정상 동작하는지, XSS 정화가 여전히 잘 되는지.
