# P3-07: yona MCP 서버 (이슈/PR 읽기·쓰기)

## 원본 표 정보

- **우선순위 구분**: P3
- **상태(원본 체크박스)**: `[x]`
- **비고(원문)**: **2026-08-24 사용자 제안, 범위: 읽기+쓰기 결정.** AI 에이전트(Claude Code 등)가 MCP(Model Context Protocol)로 yona 저장소의 이슈/PR을 직접 다루도록 지원 — 조회·검색(읽기)뿐 아니라 이슈 생성·코멘트·클로즈, PR 생성·리뷰·코멘트·머지(쓰기)까지, GitHub 공식 MCP 서버와 동등한 수준. **코드 검증 완료(선행 의존성 확인)**: 현재 yona에 이슈/PR을 개별적으로 생성·조회·수정하는 범용 JSON REST API가 없음 — `web/` 패키지의 `@RestController`는 `ProjectApiController.kt`(프로젝트 내보내기/가져오기 전용, `exports`/`composeIssueCommentsJson` 등 export용 JSON 조립 메서드뿐)와 `ImportApiController.kt` 단 둘뿐이고, 나머지 이슈/PR 컨트롤러는 전부 HTML(Thymeleaf) 렌더링용 웹 MVC 컨트롤러다. **따라서 MCP 서버는 [[tickets/p3-02|P3-02]](CLI)와 정확히 같은 선행 의존성을 공유** — 이슈/PR/저장소 CRUD를 다루는 범용 JSON REST API를 먼저 만들어야 하고, MCP 서버와 CLI 둘 다 그 API 위에 얇게 얹는 클라이언트로 설계해 비즈니스 로직을 중복 구현하지 않아야 함. **2026-08-28 인증 방식 재설계(사용자 요청, 리서치 완료)**: 최초 설계([[tickets/p3-02|P3-02]] Fine-grained PAT 단독)를 OAuth 2.1 + PAT 이중 체계로 변경 — Claude 등 대화형 클라이언트는 MCP 공식 인가 스펙(OAuth 2.1, PKCE, RFC9728 Protected Resource Metadata, RFC7591 Dynamic Client Registration, RFC8707 Resource Indicators)에 따라 접속 시 자동으로 브라우저 인가 화면을 띄우는 걸 기대함(리서치로 확인) — yona를 리소스 서버(`spring-boot-starter-oauth2-resource-server`) + 인가 서버(`spring-security-oauth2-authorization-server`, 로그인 화면은 기존 폼+LDAP 재사용, 향후 [[tickets/p3-06|P3-06]] SSO 추가 시 자동 상속)로 구성. PAT는 CI/헤드리스용으로 병행 유지. 참고 선례: `spring-ai-community/mcp-security`. 상세 설계는 `docs/yona-wiki/plans/p3-07-mcp-server.md` 참고. 전송 방식(미결정): stdio는 로컬 실행 전제라 원격 호스팅된 yona 인스턴스에는 부적합 — Streamable HTTP/SSE 기반 원격 MCP 서버 방식 검토 필요. 구현 언어/배치 방식(미결정, 단 인가 서버는 Kotlin 확정): [[tickets/p3-02|P3-02]] CLI(Go)가 REST API를 감싸는 방식으로 같이 구현할지(`yona mcp serve`), yona Kotlin/Spring 서버 자체에 MCP 트랜스포트 엔드포인트를 추가할지 결정 필요. CLI 명령 초안(미구현, [[tickets/p3-02|P3-02]]와 연계): `yona mcp serve`. **완료(2026-09-07, TDD로 완료)** — 구현 언어/배치는 안 B(Kotlin/Spring 서버 내장, MCP 트랜스포트+인가 서버 전부 같은 프로세스)로 확정: `IssueController`/ `PullRequestController`가 이미 `Authentication.name`(로그인 방식 무관하게 항상 `loginId`)만으로 로그인 사용자를 찾으므로, 자체 운영하는 Spring Authorization Server가 발급한 JWT를 그대로 전달하면 스코프 검증 이후의 모든 기존 비즈니스 로직(AccessControl, 브랜치 보호([[tickets/p3-04|P3-04]]))이 완전히 동일하게 동작해 프로세스를 둘로 쪼갤 이유가 없었다. `spring-ai-community/mcp-security`는 라이선스/버전 확인까지 마쳤으나 pre-1.0·단일 메인테이너라는 이유로 보안 신뢰 경계 최소화 원칙에 따라 **채택하지 않고** `spring-security-oauth2-authorization-server`(PKCE/DCR 기본 제공) + RFC8707(Resource Indicators)만 직접 구현 + `spring-ai-starter-mcp-server-webmvc`(MCP 프로토콜/Streamable HTTP 전송)로 구성. OAuth 스코프는 [[tickets/p3-02|P3-02]]의 `ApiTokenScopeGroup`/`ApiTokenPermission`을 `"issues:read"`/`"issues:write"` 형식으로 그대로 재사용(신규 축 설계 없음, [[tickets/p3-14|P3-14]]가 이미 언급해둔 재사용 가능성 확정). RFC9728/RFC8414/RFC7591/RFC8707 전부 구현하고 DCR 엔드포인트에는 IP당 분당 10건 레이트리밋을 추가. MCP 도구 11개(읽기 4 + 쓰기 이슈 3 + 쓰기 PR 4) 구현 — `merge_pull_request`는 새 머지 경로를 만들지 않고 기존 `PullRequestServiceImpl.merge() -> checkBranchProtectionForMerge()`를 그대로 호출해 브랜치 보호를 우회할 수 없게 했고, 스코프 부족 시 그 호출 자체가 실행되지 않음을 테스트로 직접 증명. "Claude Code로 실제 접속해 브라우저 팝업 확인"(수동 검증 항목)은 대신 공식 MCP Java SDK 클라이언트(Claude Code가 쓰는 것과 동일한 라이브러리)로 실제 소켓을 통해 DCR→PKCE→동의→토큰 발급→`initialize`→`tools/call`까지 전부 자동화해 동등한 신뢰도로 검증(`McpToolsEndToEndSpec`) — 이 과정에서 MockMvc 전용 테스트로는 잡을 수 없었던 실버그 6건(Lob 컬럼 길이로 인한 TINYTEXT 절단, Jackson 폴리모픽 타입 화이트리스트 누락, `YonaUserDetails` 왕복 직렬화 불일치, 인가 서버 예외 처리 범위 오류로 인한 302/HTML 오응답, JWT `scope` 클레임이 문자열이 아니라 배열이라 스코프 검증이 무력화되던 회귀, 테스트의 `state` 파라미터 오용 2건)을 추가로 발견해 수정. GitHub의 "Settings > Applications > Authorized OAuth Apps"에 대응하는 UI(`/user/editform/oauth-apps`, 인가한 앱 조회 + 즉시 토큰 무효화까지 포함한 취소)도 함께 구현(백엔드만 만들고 관리 방법이 없는 상태로 남기지 않기 위함). 상세 설계/완료 로그는 `docs/yona-wiki/plans/p3-07-mcp-server.md` 참고.
