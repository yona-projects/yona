# P1-141: **(2026-08-21 백엔드 전수 감사 재검증 중 발견 — PR/코드리뷰 도메인)** PR 생성(`createPullRequest`)이 yona보다 과도하게 제한됨 — yona `PullRequestApp.newPullRequest()`는 `@IsCreatable(ResourceType.FORK)`로 게이트되고 `AccessControl.isProjectResourceCreatable()`의 공개 프로젝트 허용 타입에 `FORK`가 포함돼 있어, 로그인한 비멤버도 공개 프로젝트에 PR을 보낼 수 있다. yona `PullRequestController.createPullRequest`는 `checkWritePermission`(멤버 또는 그룹멤버만)만 써서 비멤버는 아예 차단됨 — 게시판 결손([[tickets/p1-113|P1-113]])과 동일 유형의 회귀.

## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-21 — P1-141**: `PullRequestController.createPullRequest()`의 권한 체크를 `checkWritePermission`(멤버/그룹멤버 전용)에서 `accessControl.isProjectResourceCreatable(user, project, ResourceType.FORK)`로 교체 — yona `PullRequestApp.java:254` `@IsCreatable(ResourceType.FORK)` 대응. `AccessControl.isProjectResourceCreatable()`은 이미 `FORK`를 공개 프로젝트 비멤버 허용 타입에 포함하고 있어([[tickets/p1-113|P1-113]]/[[tickets/p1-129|P1-129]] 등에서 이미 재사용해온 정답 패턴) 새 로직 없이 한 줄 교체로 해결.
  - `mergePullRequest`/`changeState`/`deleteFromBranch`/`restoreFromBranch`/`addReviewer`/`removeReviewer`는 여전히 `checkWritePermission`을 그대로 쓴다 — 이쪽은 [[tickets/p1-78|P1-78]](ACCEPT 권한)을 정확히 재현한 것이라 이번 대상이 아니다([[tickets/p1-113|P1-113]] 완료 로그에서 이미 확인된 판정).
  - 테스트: `PullRequestControllerSpec.kt` +2(공개 프로젝트 비멤버도 PR 생성 가능/비공개 프로젝트 비멤버는 여전히 403). 전체 통과.
