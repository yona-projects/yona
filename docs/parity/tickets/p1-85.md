## 완료 로그 (원문, `PARITY_BACKLOG.md`의 "완료 로그" 섹션에서 이관)

- **2026-08-20 — P1-85 (1a+1b)**: yona `app/utils/AccessControl.java`의 단일 진입점 `isAllowed(User, Resource, Operation)`를, JPA 엔티티는 legacy의 `Resource` 다형성을 가질 수 없어 리소스 타입별 오버로드를 가진 `@Component class AccessControl`로 중앙화(설계는 `docs/P1-85_PLAN.md`, Serena LSP로 legacy `AccessControl.java` 전 메서드를 라인 단위로 읽어 이식 — 사용자의 "의도적 축약, 단순화 절대 금지" 지시에 따름).
  - **1a(object→class 전환, TASK-0083, 별도 커밋)**: 기존 5개 공개 함수(`isAllowedToReadProject` 등) 로직은 완전히 그대로 두고, `object` → `@Component class`(생성자로 `ProjectUserRepository`/`OrganizationUserRepository` 주입)로만 전환. `isOrganizationAdmin()`이 entity 컬렉션 순회와 리포지토리 조회를 뒤섞어 쓰던 것을 리포지토리 조회로 통일. 컨트롤러/필터 28개 파일(컨트롤러 25 + `GitAuthorizationFilter`/`SvnAuthorizationFilter`/`IncomingMailProcessingService`) 전부 `accessControl: AccessControl` 생성자 주입으로 기계적 전환(71개 호출부, `search_for_pattern`으로 직접 재검증 — 계획서의 78곳 추정치와 다름을 확인 후 실측치 사용). 검증은 "기존 스위트 전체 그린 = characterization test"(신규 로직 없음, TDD 불필요 — 사용자가 "왜 TDD로 안 하냐" 질문해 이 판단 근거를 명시적으로 설명).
  - **1b(Operation enum + 신규 isAllowed 오버로드 전체, addition-only, 별도 커밋)**: legacy `models/enumeration/Operation.java`를 `domain/enumeration/Operation.kt`로 그대로 이식(READ/UPDATE/DELETE/ACCEPT/REOPEN/CLOSE/WATCH/LEAVE/ASSIGN_ISSUE, `operation()`/`getValue()` 포함). `config/security/AccessControl.kt`에 legacy `isGlobalResourceAllowed()`(119-203행)·`isProjectResourceAllowed()`(205-301행)·`isAllowedIfAuthor()`(340-365행)·`isAllowedIfAssignee()`(385-405행)를 리소스 타입별로 그대로 이식한 15개 `isAllowed(...)`/`isAllowedAttachment(...)` 오버로드 신규 추가(PROJECT/ORGANIZATION/ISSUE_POST/ISSUE_COMMENT/BOARD_POST/NONISSUE_COMMENT/PULL_REQUEST/COMMIT_COMMENT/COMMENT_THREAD/REVIEW_COMMENT/MILESTONE/WEBHOOK/일반 ResourceType/PROJECT_TRANSFER/ATTACHMENT). **이 단계에서 어떤 컨트롤러도 이 함수들을 호출하지 않는다(순수 추가) — 계획서 그대로**.
  - **legacy와 대조해 확인한, 겉보기엔 의외이지만 정확히 그대로 이식한 규칙들**(테스트로 명시적으로 고정): UPDATE/DELETE/ACCEPT/CLOSE/REOPEN 등 일반 연산은 "작성자 또는 매니저"가 아니라 **프로젝트 멤버 전원**에게 허용된다(`isMemberOf(project)`만 있으면 충분, 작성자/매니저 우회는 그 위의 추가 허용 경로일 뿐 하한이 아님) — 이는 이미 [[tickets/p1-90|P1-90]]~95로 등록된 결함들(`CommentServiceImpl.hasPermission()`/`BoardController.isManagerOrAuthor`/`PullRequestController.isManagerOrContributor`/`CodeHistoryController.isAuthorOrManager`/`IssueLabelController.isProjectManager`/`MilestoneController.isProjectManager`가 전부 legacy보다 과도하게 제한적)이 옳았음을 이번 이식으로 재확인. `PULL_REQUEST`/`MILESTONE`/`WEBHOOK`은 legacy `isAllowedIfAuthor` 스위치에 없는 타입이라 작성자 자동 승격이 없음(WEBHOOK도 매니저 전용이 아니라 멤버 전원 UPDATE 가능 — [[tickets/p1-87|P1-87]]이 참조할 근거). CODE 리소스는 DELETE가 일반적으로 항상 거부되지만, 매니저/조직관리자 우회가 그 특수 케이스보다 앞서 평가돼 매니저는 예외적으로 삭제 가능(legacy 186-192행이 264-267행보다 먼저 옴).
  - **`isAllowedAttachment()`(유일하게 컨테이너를 동적으로 해석)**: legacy `Attachment.asResource()`(373-436행)의 컨테이너 동적 조회를, yona가 실제로 `Attachment.containerType`에 쓰는 값(코드 전수 검색으로 확인: `ORGANIZATION`/`ISSUE_POST`/`MILESTONE`/`BOARD_POST`/`COMMIT_COMMENT`/`REVIEW_COMMENT`/`USER_AVATAR`/`USER`/`NOT_A_RESOURCE`) 전부에 대해 실제 컨테이너 엔티티를 리포지토리로 조회한 뒤 그 컨테이너 기준 `isAllowed(...)`로 위임하도록 구현(READ는 `isAllowed(container,READ)`, UPDATE/DELETE는 `isAllowed(container,UPDATE)` — legacy 248-251행과 동일). `USER`/`NOT_A_RESOURCE`(아직 실제 리소스에 붙기 전 임시 첨부)는 legacy의 "containerType==USER면 업로더 본인만" 특수 케이스(140-144행)를, yona는 `containerId`를 파싱하는 대신 이미 있는 `ownerLoginId` 필드로 판별(이동 후에도 원 업로더가 남아있어 더 안정적).
  - **범위 밖으로 확인, 새 항목 등록**: legacy `isAnonymousNotAllowed()`(사이트 설정 `application.allowsAnonymousAccess`, 기본값 true) 게이트는 yona에 대응 사이트 설정 자체가 없어(코드 전수 검색으로 부재 확인) 이식하지 않고 기본값(익명 허용)에 해당하는 동작만 반영 — **[[tickets/p1-99|P1-99]]로 별도 등록**(의도적 축약이 아니라 대응 인프라 부재, 코드에도 동일 사유를 명시).
