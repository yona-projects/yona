# 주석 트리밍 기준

## 배경

이 코드베이스(레거시 yobi/Play → Kotlin/Spring Boot 포팅)의 주석은 정상적인 오픈소스/상용
코드보다 훨씬 장황하다. 여러 세션에 걸쳐 에이전트들이 "왜 이렇게 짰는가"를 남기라는 지침을
과하게 적용하면서, 티켓ID·날짜·라운드 번호·"실측 재현" 같은 작업일지성 서술까지 코드에 그대로
박아 넣은 결과다. 이 문서는 그것을 정리할 때 적용하는 기준을 담는다.

## 제거 대상 (거의 항상 삭제)

- 티켓/라운드 참조: `yona-wiki P3-XX`, `P#-##`, `TASK-XXXX`, `Step#.#`, `#178` 같은 이슈 번호
- 날짜/세션 참조: `(2026-09-07)`, `(실서버 동시요청 10개로 재현: ...)` 같은 검증 시점 서술
- `[GL-xxx_yyy-NNN]` 형태의 자동 생성 추적 태그
- "코디네이터 발견/수정", "실측 확인", "재검증 결과" 같은 세션 내부 작업 서술
- legacy 파일의 정확한 줄 번호 인용(`AccessControl.java:205-301`처럼) — 코드가 바뀌면 즉시
  stale해지고, 짧은 함수명 언급만으로 충분한 경우가 대부분
- 함수/변수 이름이 이미 말해주는 내용을 그대로 되풀이하는 문장("XXX 대응.", "YYY 케이스
  처리.")
- 동일 파일 안에서 똑같이 반복되는 상용구(예: "raw 엔티티 반환 시 순환 직렬화/비밀번호 노출
  방지" 같은 문구가 메서드마다 토씨 하나 안 틀리고 반복되는 경우) — 처음 한 번만 남기거나,
  그마저도 함수명이 self-explanatory하면 제거

## 보존 대상 (내용은 남기고 티켓/날짜 껍데기만 벗김)

다음에 해당하면 **절대 통째로 지우지 말고**, 티켓ID·날짜·세션 서술만 제거한 뒤 기술적 실체는
그대로 남긴다:

- 숨은 제약/불변조건: "이 순서를 바꾸면 안 된다", "이 값이 -1이면 특별한 의미"
- 실제로 발견된 버그의 근본 원인과 수정 방법(재현 절차의 서술은 지우되, "왜 버그였는지"와
  "무엇을 고쳤는지"는 남김)
- 프레임워크/라이브러리의 놀라운 동작(Spring 빈 초기화 순서, JPA dirty checking, H2 SELECT FOR
  UPDATE가 실제로는 안 막는다는 것 등)
- 보안/인가 관련 결정과 그 이유(레거시의 인가 우회 허점을 어떻게 막았는지 등)
- 설계 결정과 트레이드오프(왜 A 대신 B를 택했는지, 대안이 왜 안 되는지)
- 실제 데이터 손상/보안 사고로 이어질 뻔한 경위에 대한 경고

## 판단이 애매할 때

- **의심스러우면 짧게 줄여서 남긴다** — 완전 삭제보다 안전하다.
- 레거시 소스 파일/메서드명 인용은 "무엇과 대응되는지"를 압축해서 남기되, 정확한 줄 번호는
  뺀다(줄 번호는 legacy 소스가 그대로 남아있다는 전제에서만 유효하고 검증 불가능하다).
- 히스토리(왜 이 버그가 생겼는지, 몇 번 시도 끝에 이 방식을 택했는지)의 서사적 디테일은
  이미 `docs/parity/tickets/*.md` 완료 로그와 git 커밋 메시지에 더 상세히 남아있다 — 코드
  주석은 "지금 이 코드를 읽는 사람이 알아야 할 것"만 남기면 된다.

## 작업 방식 (세션 간 이어서 할 때)

1. `docs/COMMENT_TRIMMING_PROGRESS.md`의 "잔여 파일" 표에서 위(참조 밀도 높은 순)부터 진행한다.
2. **sed 등 기계적 일괄 치환으로 처리하지 않는다.** 이 작업의 본질은 주석을 읽고 "남길 가치가
   있는 WHY인지"를 판단하는 것이라, 문자열 패턴 매칭으로 자동화할 수 없다. `grep`은 대상 줄을
   찾는 용도로만 쓰고, 실제 정리는 파일을 Read로 열어 문맥을 읽은 뒤 Edit로 한 곳씩 고친다.
   (완전히 동일한 문장이 같은 파일 안에 토씨 하나 안 틀리고 반복되는 극히 드문 경우 — 예:
   메서드마다 붙는 상용구 한 줄 — 에 한해서만, 그 문장을 실제로 읽고 판단을 마친 뒤 정확히
   그 문자열에 한정해 일괄 치환하는 것은 예외로 허용한다. 그 외에는 전부 손으로 한다.)
3. 파일 하나(또는 밀접하게 연관된 소수)를 끝낼 때마다:
   - `grep -n "yona-wiki\|P[0-9]-[0-9][0-9]*\|20[0-9]\{2\}-[0-9]\{2\}-[0-9]\{2\}\|TASK-\|실측\|재현\|코디네이터\|GL-" <파일>`로 남은 참조가 없는지 재확인
     (단, `docs/...` 경로를 가리키는 정상적인 문서 링크나 "재현"이 일반 동사로 쓰인 경우는
     false positive이니 무시)
   - 진행 문서의 해당 행을 완료로 갱신
4. 로직은 손대지 않으므로 컴파일/테스트 검증은 원칙적으로 불필요하다 — 매 파일 돌릴 필요 없다.
   `./gradlew compileKotlin -Dyona.it.db=h2`는 세션 마무리 시점에 한 번 정도만 돌려 편집
   경계 실수(괄호/따옴표가 깨진 경우)가 없는지 확인하면 충분하고, 스펙 테스트는 커밋 전에
   반드시 돌릴 필요는 없다(순수 주석 변경이라 실패해도 거의 항상 인프라 문제 — 아래 참고).
5. 템플릿(`.html`)은 Thymeleaf 주석(`<!--/* ... */-->` 등) 안의 동일한 패턴을 대상으로 한다 —
   기준은 코드와 동일.

## 알려진 인프라 이슈 (실제 코드 문제 아님)

- Gradle `:test` 태스크가 `java.io.EOFException` 또는
  `NoSuchFileException: .../in-progress-results-generic*.bin`으로 실패하는 경우가 있다 —
  같은 저장소 디렉터리에서 다른 세션이 동시에 `./gradlew test`를 돌리고 있거나(동시 실행
  세션 확인: 실행 중인 `GradleWorkerMain` 프로세스 확인), 직전 실행의 결과 디렉터리가 꼬여있을
  때 발생한다. `rm -rf build/test-results/test/binary` 후 단독으로 재실행하면 대개 해결된다.
  이 오류는 순수 주석 변경 자체와는 무관하다.
