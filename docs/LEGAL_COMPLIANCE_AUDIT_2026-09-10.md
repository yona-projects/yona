## 상세 발견사항

### 1. 개별 2FA 자격증명 삭제에 서버 측 재인증 없음 — **이미 수정됨**

`TwoFactorSettingsController.deleteTotp()`/`deleteWebauthn()`이 원래 클라이언트 JS
`confirm()` 대화상자만 거치고 서버가 비밀번호를 재확인하지 않았다(세션 탈취 시 확인창만
눌러도 2FA 방어 수단을 지울 수 있는 상태였음). "전체 비활성화" 경로는 처음부터 비밀번호
재확인이 있었는데 개별 삭제만 빠져 있어 방어 수준이 불일치했다.

**조치**: 2026-09-10 커밋 `4ff9535e3`에서 개별 삭제 두 엔드포인트에도 동일한 비밀번호
재확인을 추가하고, 실제 서버로 틀린 비밀번호 거부/올바른 비밀번호 삭제 성공을 재현
검증했다. **추가 조치 불필요.**

### 2. TOTP 암호화 키가 운영에서도 개발용 기본값으로 동작 가능

`application.yml`:
```yaml
yona.security.totp:
  encryption-password: "${YONA_TOTP_ENCRYPTION_PASSWORD:yona-totp-dev-only-password}"
  encryption-salt: "${YONA_TOTP_ENCRYPTION_SALT:596f6e6132303236}"
```

환경변수를 안 주면 리포지토리에 그대로 커밋된 placeholder 값으로 조용히 기동된다.
운영 배포 시 반드시 덮어써야 한다는 **주석은 있지만 강제(fail-fast) 로직이 없다** —
배포 실수로 이 기본값이 그대로 운영에 올라가면, 모든 사용자의 TOTP 시크릿이 공개된
키로 암호화된 것과 동일해져 2FA 자체가 무력화된다.

**권고**: `@PostConstruct`나 `ApplicationRunner`에서 `spring.profiles.active`가
`prod`/운영 프로파일일 때 이 값이 기본값과 같으면 애플리케이션 기동을 막는 안전장치
추가. (TOTP 시크릿 암호화 자체는 정상 설계 — `TotpSecretEncryptor`, AES 기반. 문제는
"운영에서 기본값을 못 쓰게 막는 장치"의 부재.)

**조치(완료됨)**: 이 저장소에는 prod/dev 같은 환경 프로파일 개념이 없고(profile은
DB 엔진 선택 용도), 표준 로컬 검증 워크플로와 6,400여 건 테스트 전체가 env var
없이 이 placeholder 기본값으로 컨텍스트를 띄운다 — 그래서 hard fail 대신
`TotpEncryptionKeyGuard`(`ApplicationRunner`)를 추가해, 값이 커밋된 기본값과 같으면
기동을 막지 않으면서 ERROR 레벨의 눈에 띄는 경고를 로그로 남긴다. 단위테스트
(`TotpEncryptionKeyGuardSpec`)로 기본값/비기본값 각각의 동작을 검증했고, 환경변수 없이
h2로 기동해 실제로 이 경고가 로그에 찍히는 것과, 전체 테스트 스위트가 그대로 통과하는
것을 재확인했다.

### 3. CSRF 보호가 애플리케이션 전역에서 비활성화됨

`SecurityConfig.kt:145`:
```kotlin
.csrf { csrf -> csrf.disable() }
```

이유를 설명하는 주석이 전혀 없다. 이 애플리케이션은 세션 쿠키 기반 폼 로그인
(`.formLogin`)을 웹 UI 전체에 쓰고 있어, CSRF가 꺼져 있으면 로그인된 사용자가 악성
사이트를 방문했을 때 공격자가 그 사용자의 세션으로 임의의 상태 변경 요청(설정 변경,
2FA 비활성화, 게시글 작성/삭제 등)을 강제로 실행시킬 수 있다. REST API(PAT/OAuth2
Bearer 토큰 인증)라면 CSRF가 구조적으로 의미 없어 꺼도 되지만, 이 체인은 폼 로그인도
함께 처리하는 캐치올 체인이라 그 논리가 그대로 적용되지 않는다.

**권고**: 왜 껐는지(레거시 이식 편의? 특정 API 클라이언트 호환?) 먼저 확인 필요 —
의도적이었다면 그 근거를 문서화하고, 실수/이식 편의였다면 최소한 세션 쿠키 인증이
적용되는 경로(`/users/**`, `/user/editform/**`, 폼 제출 전체)에는 CSRF 보호를 다시
켜는 것을 검토해야 한다. PCI-DSS/SOC2 등 웹 보안 통제 항목에서 CSRF 방어 여부를 직접
확인하는 경우가 많다.

### 4. 로그인 실패 횟수 기반 자동 계정 잠금 없음

`YonaAuthenticationProvider.checkAccountState()`가 `LockedException`을 던지는 조건은
`user.state == UserState.LOCKED`뿐이고, 이 상태로 바뀌는 자동 트리거(예: N회 연속
로그인 실패 시 자동 잠금)를 찾지 못했다 — 관리자가 수동으로 잠그는 경로만 있는 것으로
보인다. 즉 로그인 엔드포인트에 무차별 대입(brute-force) 공격을 자동으로 막는 장치가
없다.

**권고**: 계정별 또는 IP별 실패 횟수 카운팅 + 임시 잠금/지연(예: Spring Security의
`AuthenticationFailureHandler`에서 카운터 증가, 캐시나 DB에 기록) 도입 검토.

**조치(완료됨)**: `User`에 `failedLoginAttempts`/`lockedUntil` 필드를 추가하고(기존
`UserState.LOCKED`와는 완전히 별개 축 — 상태를 바꾸지 않는다), `YonaAuthenticationProvider`가
계정별 실패 횟수를 세어 5회 도달 시 15분간 자동 잠근다. 로그인 성공 시 카운터는 항상
리셋되고, `lockedUntil`이 지나면 별도 조작 없이 자동 해제된다 — 실수로 잠긴 계정이
영구 잠기지 않도록 관리자 즉시 해제 API(`POST /-_-api/v1/admin/users/{loginId}/unlock`,
감사 로그 기록 포함)도 추가했다. 단위테스트(`YonaAuthenticationProviderSpec`)와 실제
`springSecurityFilterChain` 위에서 검증하는 통합테스트(`BruteForceLockoutIntegrationSpec`)로
실패 누적→잠금→거부, 성공 시 리셋을 확인했다.

### 5. 비밀번호 해시 알고리즘이 현재 업계 권고 대비 약함

`YonaAuthenticationProvider.hashPassword()`/`UserController.hashPassword()` (두 곳에
동일 로직 중복):
```kotlin
val digest = MessageDigest.getInstance("SHA-256")
// salt 선행 + 1024회 단순 반복
```

v1.6 legacy부터 그대로 이식된 방식이다. OWASP Password Storage Cheat Sheet(2023
개정판) 기준 권고는 bcrypt/scrypt/Argon2id, 혹은 PBKDF2-HMAC-SHA256이라면 60만 회
이상 반복이다. 1024회 단순 SHA-256 반복은 GPU/ASIC 기반 오프라인 크래킹에 상대적으로
취약하다. PCI-DSS(요구사항 8.3.2 등)나 보안 인증 심사에서 "업계 표준 암호화" 여부를
확인할 때 지적될 수 있다.

**권고**: 신규 가입/비밀번호 변경 시점부터 Argon2id 등으로 전환하고, 기존 해시는
"다음 로그인 성공 시 재해싱"하는 점진적 마이그레이션 전략 검토(레거시 해시와 신규
해시를 구분하는 prefix/버전 필드 필요 — 스키마 변경 수반, 별도 설계 필요한 규모의
작업).

**조치(완료됨)**: `PasswordEncodingService`를 신설해 이전에 아홉 곳(로그인/비밀번호
변경/2FA 비활성화 재확인/신규가입/부트스트랩 관리자 생성/LDAP 동기화/관리자 비밀번호
초기화/비밀번호 찾기 등)에 중복돼 있던 SHA-256×1024 구현을 이곳 하나로 통일했다.
Spring Security Crypto가 이미 제공하는 `Argon2PasswordEncoder`(신규 외부 의존성 추가
없음)로 새 비밀번호는 항상 Argon2id로 저장하고, 저장된 해시가 `$`로 시작하면 Argon2,
아니면 레거시 포맷으로 자동 판별해 검증한다(별도 DB 컬럼 불필요). 레거시 포맷 계정은
로그인 성공 시 그 자리에서 즉시 Argon2id로 재해싱해 저장하므로, 기존 가입자는 강제
재설정 없이 그대로 로그인하면서 점진적으로 이전된다. 회귀 검증: 레거시 해시 픽스처로
로그인하는 기존 테스트(`YonaAuthenticationProviderSpec` 등 legacyHash 사용 전체)가
그대로 통과함을 확인했고(=레거시 계정이 여전히 로그인된다는 검증이기도 함), 로그인
성공 직후 DB 해시가 Argon2 포맷으로 바뀌는 것과 재로그인도 성공하는 것을 신규
테스트로 확인했다. 전체 테스트 스위트도 그대로 GREEN이다.

### 6. 보안 관련 관리자 조치/로그인 이벤트에 대한 감사 로그 없음

프로젝트 전체에서 `audit` 관련 모듈을 찾지 못했다(파일명 검색 0건). 다음 이벤트들이
별도 감사 추적 없이 DB 상태만 바뀐다:
- 관리자의 2FA 강제 비활성화(`POST /-_-api/v1/admin/users/{loginId}/disable-2fa`)
- 관리자의 사용자 상태 변경(`PATCH /-_-api/v1/admin/users/{loginId}`)
- 로그인 성공/실패(단순 `AccessLogFilter`의 텍스트 로그만 존재 — 구조화된 보안
  이벤트 로그가 아니라 일반 접속 로그)
- 비밀번호 변경, 이메일 변경

SOC2(CC6 계열 통제)나 ISO 27001(A.8.15 로깅) 심사에서는 "누가, 언제, 무엇을,
왜 바꿨는지"를 조회 가능한 감사 추적을 흔히 요구한다.

**권고**: 최소한 관리자 조치(계정 잠금/해제, 2FA 강제 해제, 권한 변경)만이라도 별도
`audit_log` 테이블에 행위자/대상/시각/사유를 기록하는 것부터 시작 권장.

**조치(완료됨 — 관리자 조치 범위)**: `audit_log` 테이블(`AuditLog`/`AuditLogRepository`/
`AuditLogService`)을 신설해, 관리자의 사용자 상태 변경(`PATCH
/-_-api/v1/admin/users/{loginId}`), 2FA 강제 비활성화(`POST
/-_-api/v1/admin/users/{loginId}/disable-2fa`), 이번에 4번 항목과 함께 추가한 브루트포스
잠금 강제 해제(`POST /-_-api/v1/admin/users/{loginId}/unlock`) 세 곳에 행위자/대상/액션/
사유/시각을 기록한다. 조회는 최소 범위로 `GET /-_-api/v1/admin/audit-logs`(사이트관리자
전용) REST 엔드포인트만 추가했고, 별도 목록 UI는 이번 범위에 포함하지 않았다. 단위테스트
(`AuditLogServiceSpec`)와 실제 DB 왕복을 확인하는 통합테스트(`AuditLogServiceIntegrationSpec`),
그리고 세 관리자 엔드포인트가 실제로 올바른 필드로 기록을 호출하는지 확인하는
`UserControllerSpec` 테스트로 검증했다. 로그인 성공/실패, 비밀번호/이메일 변경 등 나머지
이벤트의 감사 로그는 이번 범위 밖으로 남겨둔다.

### 7. 계정 탈퇴가 실제 삭제·익명화가 아니라 상태 플래그뿐

`UserState.DELETED`로 상태만 바뀌고(`UserController.kt`, `YonaUserDetails.kt`),
이메일/이름 등 개인정보 필드 자체를 지우거나 익명화하는 로직은 찾지 못했다.

GDPR 17조(삭제권, "잊혀질 권리")나 한국 개인정보보호법 21조(파기)를 문자 그대로
적용하면, "탈퇴 = 개인정보의 실질적 파기/익명화"가 필요할 수 있다(다만 서비스 운영상
합법적 보유 사유 — 예: 게시물 작성자 표시 유지, 법적 분쟁 대비 — 가 있다면 예외가
인정될 수 있으므로, 이 부분은 특히 법무 검토가 필요).

**권고**: 탈퇴 시 정책을 명확히 정의(즉시 파기 vs. 유예기간 후 파기 vs. 익명화 유지)하고
그에 맞는 배치 작업 또는 즉시 처리 로직 추가.

### 8. 접속 로그에 IP·사용자ID가 보존기간 정책 없이 무기한 남을 수 있음

`AccessLogFilter.kt`가 모든 요청에 대해 `request.remoteAddr`(IP), 로그인 사용자명,
요청 경로, User-Agent, Referer를 텍스트 로그로 남긴다(Apache Combined Log Format
동등). IP 주소는 GDPR상 개인정보로 취급되는 경우가 많다. 로그 파일의 보존기간/자동
삭제(로그 로테이션+파기) 설정을 코드/설정에서 찾지 못했다(운영 인프라의 로그
수집기(예: ELK, CloudWatch) 쪽에서 별도로 관리 중일 가능성은 있음 — 코드 자체에는
없다는 뜻).

**권고**: 로그 보존기간 정책을 명시적으로 정의하고(예: 90일 후 자동 삭제), 인프라
레벨(logback rolling policy, 로그 수집기 보존 설정)에서 실제로 적용되는지 확인.

**조치(완료됨 — 문서화)**: `logback-spring.xml`을 다시 확인한 결과, 이 애플리케이션은
파일 appender가 전혀 없이 전부 STDOUT JSON(`LogstashEncoder`, Loki/Promtail 등 외부
로그 수집기 전제)으로만 로깅한다 — 즉 애플리케이션 코드/설정 레벨에서 "보존기간"을
구현할 파일 로테이션 대상 자체가 없다. 실질적인 조치는 코드가 아니라 문서화였다:
`docs/logging.md`가 "이 저장소엔 logback-spring.xml이 없다"고 틀리게(구조화 JSON
로깅으로 바뀌기 전 상태로) 적혀 있던 것을 현재 상태에 맞게 정정하고, "로그 보존기간은
이 저장소 책임 범위 밖이며 배포 환경의 로그 수집기에서 설정해야 한다"는 절을 명시적으로
추가했다.

### 9. 개인정보처리방침/이용약관 페이지가 애플리케이션 안에 없음

`src/main/resources/templates`에 privacy/terms/policy 관련 템플릿을 찾지 못했다.
회원가입 시 개인정보 수집·이용에 대한 동의를 받는 절차도 확인되지 않았다(가입 폼에
약관 동의 체크박스 등이 없어 보임). 대부분의 개인정보보호 법제(GDPR, 한국 PIPA 포함)는
서비스 내에서 개인정보처리방침 고지 및 (필요시) 동의 획득을 요구한다.

**권고**: 법무팀과 협의해 개인정보처리방침/이용약관 문서를 작성하고, 회원가입 폼에
동의 절차를 추가.

### 10. 보안 민감 이벤트에 대한 사용자 알림 없음

2FA 활성화/비활성화, 새 WebAuthn 키 등록, 비밀번호 변경, 새 기기/위치에서의 로그인 시
이메일 등으로 계정 소유자에게 알려주는 로직이 없다(GitHub/GitLab 등은 이런 이벤트마다
알림 이메일을 보낸다). 법적 강제사항은 아니지만 SOC2 등 보안 모범사례 심사에서
자주 언급되는 항목이다.

**조치(완료됨 — 2FA 비활성화 범위)**: 계정 탈취 시나리오에서 가장 민감한 이벤트인
"2FA 비활성화"부터 구현했다. `TwoFactorServiceImpl.disableAll()`(본인 요청과 관리자
강제 비활성화가 공통으로 거치는 단일 지점)에 기존 `MailService`(신규 메일 발송 인프라
없이 재사용)로 계정 소유자에게 알림 메일을 보내는 로직을 추가했다 — 실제로 등록돼
있던 2FA를 껐을 때만 보내고(빈 계정에 대고 눌러도 스팸이 되지 않도록), 메일 발송 실패가
비활성화 자체를 막지 않도록 예외를 삼키고 로그만 남긴다. 단위테스트
(`TwoFactorServiceImplSpec`)로 발송/미발송 분기를 검증했다. 2FA 활성화, 새 WebAuthn
등록, TOTP 삭제, 새 기기 로그인 등 나머지 이벤트는 이번 범위 밖으로 남겨둔다.

### 11. 데이터 이동권(내 정보 다운로드) 기능 없음

GDPR 20조는 정보주체가 자신의 개인정보를 구조화된 형식으로 내려받을 권리를 규정한다.
현재 사용자가 자신의 데이터(프로필, 게시물, 이슈 등)를 일괄 내보내는 기능은 찾지
못했다. (해당 규제 적용 대상 사용자층이 있는 경우에만 문제.)

### 12. 세션 쿠키 Secure/SameSite/타임아웃 미설정

`application.yml`에 `server.servlet.session.cookie.*` 관련 설정이 없다 — Spring
Boot 기본값에 의존한다(요청이 HTTPS면 `Secure` 플래그는 보통 자동 적용되지만, 리버스
프록시/로드밸런서에서 TLS를 종료하는 구성이라면 `server.forward-headers-strategy`
설정 없이는 애플리케이션이 HTTPS 여부를 못 알아채 `Secure` 플래그가 안 붙을 수 있다 —
현재 이 설정도 없음). `SameSite` 속성과 세션 타임아웃도 명시적 설정이 없다.

**권고**: 운영 배포 아키텍처(리버스 프록시 유무)를 확인하고, 필요하면
`server.forward-headers-strategy: framework`(또는 `native`)와
`server.servlet.session.cookie.secure=true`, `same-site=lax` 또는 `strict`를 명시.

**조치(완료됨)**: `application.yml`에 `server.forward-headers-strategy: framework`
(리버스 프록시가 TLS를 종료하는 배포에서 `Secure` 플래그가 자동으로 붙도록, 프록시
없는 로컬 배포에는 영향 없음), `server.servlet.session.cookie.same-site: lax`(`strict`는
OAuth2/SAML2 로그인의 최상위 탐색 리다이렉트를 깰 수 있어 제외), `server.servlet.session.timeout:
30m`을 명시했다. `cookie.secure`는 의도적으로 고정하지 않았다 — 로컬 h2 개발과 이
저장소의 표준 HTTP 기반 실사용 검증 워크플로가 깨지기 때문이다. 실제 임베디드 서버를
띄우는 통합테스트(`SessionCookieSecurityIntegrationSpec`)로 로그인 성공 시
`Set-Cookie` 헤더에 `SameSite=Lax`가 실제로 붙는 것을 확인했고, curl로도 직접
재현했다. 기존 OAuth2/SAML2/일반 로그인 통합테스트 전체가 회귀 없이 통과함을 확인했다.

### 13. (정보) 신규 2FA 의존성 라이선스 — 문제없음

이번 P3-43에서 추가한 라이브러리:
- `dev.samstevens.totp:totp:1.7.1` — MIT 라이선스.
- `org.springframework.security:spring-security-webauthn`(WebAuthn4J 포함) —
  Apache 2.0 라이선스.
- `com.webauthn4j:webauthn4j-test`(테스트 전용) — Apache 2.0 라이선스.

모두 permissive 라이선스로 이 프로젝트(Apache 2.0, `LICENSE` 파일 확인)와 호환되며
상업적 운영에 제약이 없다. **다만 이번에 조사한 것은 신규 추가분 3개뿐이며, 전체
의존성 트리(수십~수백 개)에 대한 라이선스 전수 감사는 수행하지 않았다** — 필요하면
`./gradlew dependencies`와 라이선스 스캐너(예: `com.github.jk1.dependency-license-report`
Gradle 플러그인)로 별도 점검 권장.

## 권고 우선순위(리스크 대비 작업량 기준 제안)

1. **2번(운영 암호화 키 강제)** — 코드 몇 줄로 배포 실수를 원천 차단할 수 있는 가장
   저비용·고효과 조치.
2. **3번(CSRF)** — 왜 껐는지부터 확인 필요(의도적 설계였을 가능성도 있음), 그다음
   조치 결정.
3. **6번(감사 로그)** — 관리자 조치부터 최소 범위로 시작 가능.
4. **4번(브루트포스 방어)** — Spring Security 표준 패턴으로 비교적 간단히 추가 가능.
5. **5번(비밀번호 해시)** — 영향 범위가 크고(기존 해시 마이그레이션 전략 필요) 설계
   검토가 선행돼야 하는 작업.
6. **7·8·9·11번(개인정보 처리 관련)** — 기술적 구현보다 **정책 결정(법무팀 판단)이
   선행**돼야 하는 항목들 — 어떤 정책을 채택할지 결정된 뒤에 구현.
7. **10·12·13번** — 상대적으로 낮은 우선순위/정보성.

어느 항목부터 실제로 착수할지 알려주면 바로 진행한다.
