# yona-wiki: P3 구현 계획 카탈로그

`docs/parity/index.md`의 **P3(신규 인프라 개선 — yona 동치성과 무관)** 항목을 우선순위 순으로 정리하고,
각 항목의 개별 구현 계획서를 담은 폴더다. P0~P2가 "레거시와 동일하게 만들기"였다면 P3는 "yona를 실제 운영
가능한 서비스로 만들기 위한 신규 도입"이라 완료 기준도 다르다(설계 검토 후 구현이 완료 기준, yona 원본 대조 아님).

형식은 `~/megabird/megabird-wiki`, `~/megabird/ums-wiki`의 관례(folder=type 대신 이 규모에서는 `plans/` 단일
폴더, frontmatter로 상태/의존성 추적, `[[wikilink]]`로 상호 참조, 마스터 인덱스가 진입점)를 이 저장소 단일 문서
세트 규모에 맞게 축소 적용했다 — 훅/자동화 하네스는 이식하지 않고 **문서 컨벤션만** 가져왔다.

**2026-08-28 우선순위 재정렬**: P3-08(H2)이 완료되고, P3-09(Swagger)가 새로 생기고, P3-07(MCP 서버)이 OAuth 2.1
인가 서버 구현까지 포함하도록 범위가 커지면서(원래는 "REST API 위에 얇게 얹는 클라이언트" 정도였음) 전체
순서를 다시 짰다. 아래는 그 결과.

## 우선순위 판단 근거

이번 재정렬의 기준은 "**진짜 공짜인 것부터, 그다음 허브, 그다음 나머지**"다 — 이전 정렬은 "허브부터"만 고려했는데,
지금은 착수 비용이 사실상 0에 가까운 항목이 두 개(P3-09, P3-01) 새로 명확해져서 그것부터 두는 게 맞다.

1. **P3-09(Swagger)를 1순위로 둔 이유**: 8개 항목 중 유일하게 "의존성 하나 추가하면 끝"인 항목이다. 의존도
   그래프에 전혀 안 걸려 있고(아무것도 안 막고, 아무것도 안 기다림), 리스크도 사실상 없다. 가장 먼저 끝내서
   빠른 성과를 확보하는 게 합리적이다.
2. **P3-01(Observability)을 2순위로 둔 이유**: 이것도 완전히 독립적이고, 계측 지점 6곳이 이미 구체적으로
   특정돼 있어 설계 리스크가 낮다. P3-09보다 살짝 크지만 여전히 "빠르게 끝낼 수 있는" 축에 속하고, 앞으로 지을
   모든 신규 서브시스템(특히 P3-05 러너)을 처음부터 관측 가능한 상태로 짓는 게 나중에 계측을 끼워 넣는 것보다 싸다.
3. **P3-02(CLI+API+Token)를 3순위로 둔 이유**: 8개 항목 중 **후속 항목을 가장 많이 막고 있는 허브**다 — P3-03
   (Deploy Key가 토큰 스코프 재사용), P3-07(MCP가 동일 REST API·토큰 그대로 사용), P3-05(CLI와 같은 Go 스택
   재사용)까지 세 항목이 여기 걸려 있다. 앞의 두 항목(P3-09/P3-01)을 먼저 빠르게 해치운 뒤에는, "값싼 것부터"가
   아니라 "허브부터 뚫어서 뒤가 막히지 않게"로 기준이 바뀐다. 특히 현재 "전권 단일 토큰" 구조가 남아 있는 채로
   P3-07(MCP, AI 에이전트에게 쓰기 권한 부여)을 먼저 만들면 보안 리스크가 크다.
4. **P3-04, P3-06을 4~5순위로 둔 이유**: 둘 다 완전히 독립적이고 범위가 상대적으로 명확해 P3-02와 병렬로도
   진행 가능하다. P3-04는 스파이크 1개(`ThreadState` 확인)만 먼저 하면 막힘이 없고, P3-06은 LDAP 프로비저닝
   패턴을 그대로 재사용할 수 있어 설계 리스크가 낮다.
5. **P3-07을 6순위로 둔 이유(순위 하락)**: 2026-08-28 인증 재설계로 범위가 커졌다 — 원래는 "P3-02 REST API 위에
   얇게 얹는 MCP 클라이언트" 정도였는데, 이제 **OAuth 2.1 인가 서버(RFC9728/RFC8414/RFC7591/RFC8707 전부
   구현)까지 자체 운영**하는 게 설계 방향으로 확정되면서 사실상 신규 서브시스템 하나(인증 서버)를 통째로 더
   지어야 하는 항목이 됐다. P3-02 완료가 여전히 강한 선행 조건이라 순번 자체는 P3-03보다 앞이지만(신규 인프라
   없이 P3-02 산출물만으로 착수 가능하다는 이점은 여전함), 예전보다 "가벼운 항목"은 아니라는 걸 순위 설명에
   명시해둔다.
6. **P3-03을 7순위로 둔 이유**: P3-02 완료가 실질적 선행 조건이고, SSH 프로토콜 부분은 재사용할 기존 코드가
   전혀 없는 완전 신규 구현이라 준비 비용이 크다.
7. **P3-16(Git 태그, 착수 당시엔 "P3-10"으로 잘못 채번됨 — 2026-09-07에 `docs/parity/index.md`의
   실제 빈 번호로 정정, 계획서 파일도 `p3-16-git-tags.md`로 리네임)을 8순위로 둔 이유(2026-09-06
   사용자 지시로 재배치)**: 원래는 범위 미확정 상태로 맨 뒤(11순위)에 있었으나, 사용자가 "git 태그
   지원은 ssh git 인증 뒤에 추가해줘"라고 명시적으로 지시해 P3-03 바로 다음으로 옮겼다. 비용/편익
   재분석에 따른 재정렬이 아니라 **사용자가 직접 지정한 순서**임을 기록해둔다.
8. **P3-05를 9순위로 둔 이유**: 8개 항목 중 범위·신규성이 압도적으로 크다(워크플로 파서, 잡 모델,
   러너 프로토콜, 실시간 로그 뷰까지 4개 서브시스템). 다른 항목들이 끝나 조직의 P3 진행 리듬(TDD 사이클,
   커밋 규율)이 자리잡은 뒤 가장 큰 항목에 들어가는 편이 리스크 관리 측면에서 유리하다. 단, 트리거 레이어는
   기존 이벤트 버스를 그대로 재사용 가능하다는 게 이미 확인돼 있어 "크지만 막막하지는 않은" 항목이다.
   **2026-09-06 추가**: 사용자 지시로 현재 자동 진행 대상에서 제외됨(위 표 참고) — 순위와 별개로 착수하지 않는다.
9. **P3-15(PR 승인/변경요청 워크플로)를 10순위로 둔 이유(2026-09-07 신규 편입)**: P3-04(브랜치 보호)
   작업 중 발견된 갭 — `require_approvals`를 실제로 구현하려면 이 워크플로가 먼저 있어야 하는데,
   yona에 승인/반려 판정 개념 자체가 없어(`ThreadState`가 OPEN/CLOSED뿐) 그때는 백로그 항목으로만
   등록해뒀다(`docs/parity/tickets/p3-15.md`). 다른 계획의 완료를 기다릴 필요가 없는 순수 신규
   도메인 기능이라 선행 조건이 없고, P3-14보다 범위가 작고 위험도 낮아(기존 승인 개념 확장이지
   제3자 클라이언트에 위임 접근을 여는 것이 아님) 먼저 배치한다.
10. **P3-14(yona를 OAuth2 서버로 제공)를 11순위로 둔 이유(2026-09-07 신규 편입)**: P3-07(MCP 서버)이
    완료되며 이 계획이 재사용하려던 OAuth 2.1 인가 서버 인프라가 실제로 존재하게 돼 선행 조건이
    풀렸다. P3-15보다 뒤에 둔 이유는 범위가 더 크고(제3자 OAuth 클라이언트 등록·동의 모델 확장,
    `docs/parity/tickets/p3-14.md`의 미결 설계 사항 다수) 신뢰 경계를 넓히는 항목이라 P3-15보다
    신중하게 접근하는 편이 낫다고 판단했다.
11. **P3-12(Mercurial/hg4j)를 12순위(맨 뒤)에 둔 이유**: 2026-08-31에 추가된 항목이라 위 1~7번의 비용/편익
   비교 분석 대상에는 포함되지 않았다 — 다른 항목과 상대 우선순위를 다시 매기지 않고 그냥 맨 뒤에 이어
   붙였다. 더 결정적인 이유는 **이 저장소 안에서 판단할 수 있는 착수 조건이 아니라는 것**: 통합 대상
   라이브러리(`search5/hg4j`, JGit과 동일한 인터페이스를 지향하는 자체 개발 중인 프로젝트)가 아직 API를
   확정하지 않은 상태라 실질적인 외부 블로커를 안고 있다 — 다른 항목들처럼 "언제든 스스로 착수 가능"이
   아니다.
12. **P3-13(프런트엔드 분리)을 13순위(맨 뒤)에 둔 이유**: 역시 2026-08-31에 추가된 항목이고 위 비교 분석
    대상이 아니다. P3-02를 약한 선행 조건으로 둔 건 REST API·인증 토대를 그대로 재사용할 수 있어서지만,
    프레임워크 선정부터 인증 방식·마이그레이션 전략까지 이 문서 작성 시점엔 전부 미결정 상태라 — 다른
    항목들과 달리 "설계가 이미 상당히 구체화된 신규 기능"이 아니라 "결정 자체가 남은 탐색적 항목"에
    가깝다.

## 문서 규칙

- 각 계획서는 `_templates/plan.md`를 따른다.
- frontmatter의 `status`는 `planned → in-progress → blocked → done` 순으로 갱신한다. 실제 착수 시 이 index.md의
  상태 컬럼도 함께 갱신한다.
- frontmatter의 `priority`는 이 문서의 "우선순위 순서" 표와 항상 일치해야 한다 — 순위를 바꿀 때는 계획서
  frontmatter와 이 표를 함께 갱신한다.
- 계획 간 상호 참조는 `[[plans/p3-XX-slug]]` wikilink로 남긴다.
- 각 계획서는 원본 백로그 항목(`docs/parity/index.md`)을 요약하되 전문을 복사하지 않는다 — SSOT는 여전히
  `parity/index.md`이며, 이 wiki는 그것을 실행 가능한 단계로 분해한 것이다.
