# 결정 기록

기술 스택과 정책에 관한 모든 결정을 여기에 시간순으로 남긴다. **누가 무엇을 언제 결정했는지, 선택지는 무엇이었는지, 권장안이 있었다면 왜 그것을 권했는지**를 추적할 수 있어야 한다. 새 결정이 생기면 이 파일에 먼저 항목을 추가하고, 요약은 [architecture/technology-decisions.md](architecture/technology-decisions.md)에 반영한다.

## 읽는 법

| 칸 | 뜻 |
|---|---|
| 결정자 | **선생님**: 선생님이 정하셨다. **합의**: 제가 제안하고 선생님이 확정하셨다. **에이전트**: 제가 구현 중에 정했고 선생님의 확인을 기다린다(맨 아래 표) |
| 권장안 | 제가 권했던 선택지. 선생님이 다른 안을 고르셨으면 그 사실도 적는다 |
| 상태 | 확정, 변경됨, 확인 대기 |

## 결정 목록

### D-01. Spring Boot 버전 (2026-10-22)

- **질문**: `AGENTS.md`의 "Spring Framework 3.5"를 어떻게 해석할 것인가.
- **처음 판단(에이전트)**: Spring Boot 3.5.16으로 해석했다. 이유는 `Spring Framework 3.5`가 존재하지 않는 버전이라 Boot 3.5의 오기로 보았기 때문이다.
- **결정(선생님)**: "스프링 부트 4로 올려서 진행". Spring Boot 4.1.1(Spring Framework 7, Hibernate 7)로 상향했다.
- **상태**: 확정.

### D-02. 쿼리 계층 (2026-10-22)

- **선택지**: (a) Spring Data JPA + Criteria(Specification), (b) Spring Data JPA + QueryDSL, (c) Spring Data JPA + jOOQ.
- **권장안**: (a).
- **권장 이유**: 코드 생성이 필요 없고 JPA 표준만 쓴다. DB별 SQL 생성을 Hibernate 방언에 맡기므로 이식성이 가장 높다(Cubrid는 `hibernate-community-dialects`). Boot 4와 Hibernate 7에서 호환 문제가 없다. (b)는 Kotlin에서 KSP 코드 생성이 필요하고 Hibernate 7 지원이 불안정하다. (c)는 JPA와 이중 모델이 되어 복잡해진다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-03. 스키마 관리 방식 (2026-10-22)

- **선택지**: (a) Hibernate 생성(`ddl-auto`) 유지 + v1.6 기준 스키마 대조 테스트, (b) Liquibase, (c) Flyway + DB별 SQL.
- **권장안**: (a).
- **권장 이유**: 엔티티가 유일한 원천이라 DB마다 SQL을 따로 유지하지 않아도 된다. 구조 보증은 대조 테스트가 맡는다. Cubrid는 Liquibase, Flyway의 공식 지원 목록에 없다. 단점은 운영 DB의 변경 이관 도구가 없다는 점이며, 릴리즈 전이라 감수한다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정. 운영 이관이 필요해지는 시점에 다시 논의한다.

### D-04. 스키마와 통합 테스트를 검증할 DB 범위 (2026-10-22)

- **선택지**: (a) H2 + PostgreSQL + MariaDB, (b) 위 3종 + MySQL, (c) 6종 전부(Cubrid, MSSQL 포함).
- **권장안**: (a).
- **권장 이유**: 선생님이 처음 말씀하신 범위와 같다. MySQL, Cubrid, MSSQL은 컨테이너 이미지와 드라이버 준비 비용이 크고 실행 시간이 길어진다.
- **결정(선생님)**: (a)로 하되 "test container와 docker compose로 상시 띄워놓고 테스트"하자고 하셨다.
- **반영(에이전트)**: PostgreSQL, MariaDB 테스트 컨테이너는 Testcontainers `reuse` 모드로 띄워 테스트가 끝나도 내리지 않는다. `docker-compose.yml`은 개발 중 앱 실행용으로 따로 둔다. 두 가지를 분리한 이유는 테스트 컨테이너는 스키마를 만들고 지우는 반면, 개발용 컨테이너는 데이터를 보존해야 하기 때문이다.
- **상태**: 확정. 이 반영 방식(두 컨테이너 분리)은 선생님의 확인을 받지 않았다.

### D-05. 테스트 라이브러리 (2026-10-22)

### D-07. enum 컬럼의 DB 제약 (2026-10-22)

- **계기**: 선생님이 "v1.6에서 enum 필드의 값이 프로그램에서 자유롭게 입력되는 값인지 아닌지에 따라 DB에 enum 타입을 둘지 말지가 결정될 것"이라고 물으셨다.
- **조사(에이전트)**: v1.6의 enum 값은 `State.getValue`, `ResourceType.getValue`, `UserState.of` 등으로 변환한 닫힌 집합이며 자유 입력이 아니다. 그런데도 v1.6은 `1.sql`의 `CHECK` 제약을 `20.sql`에서 21개 모두 제거했다. 새 enum 값을 추가할 때마다 DB를 고치지 않기 위해서다.
- **선택지**: (a) 제약 없이 문자열/정수로 저장(v1.6 최종 스키마와 같음), (b) `CHECK` 제약 유지, (c) DB 고유 `ENUM` 타입.
- **권장안**: (a).
- **권장 이유**: 테이블 구조를 v1.6과 같게 유지하라는 원칙과 맞는다. DB 고유 `ENUM`은 PostgreSQL(`CREATE TYPE`), MSSQL, Cubrid에서 방식이 달라 이식성이 낮다. `ddl-auto=update`는 이미 만든 `CHECK`를 갱신하지 않아 새 enum 값을 저장할 때 오류가 난다.
- **결정(선생님)**: "일단은 지금 결정 유지" = (a).
- **상태**: 확정. DB에서도 값을 강제하려면 v1.6과 달라지는 결정이므로 선생님의 승인이 필요하다.

### D-08. LESS 빌드 (2026-10-22)

- **계기**: v1.6이 CSS를 sbt 빌드 때 LESS에서 만든다는 사실을 구현 중 발견했다.

- **권장안**: (a).
- **권장 이유**: v1.6과 같은 방식(빌드 시점 생성)이라 소스와 결과가 어긋나지 않는다. (b)는 LESS를 고칠 때마다 다시 컴파일해 커밋해야 한다. (c)는 Less 1.x 문법 일부만 지원해 결과가 달라질 위험이 있다. 단점은 빌드 환경에 Node와 npm이 필요하다는 점이다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-18. 알림 메일은 v1.6처럼 비동기 스케줄러로 보낸다 (2026-10-23)

- **계기**: 4단계 알림 서브시스템의 발송 방식을 정해야 했다.
- **v1.6 동작**: 이벤트는 요청 안에서 `notification_event` 행으로 저장하고, Akka 스케줄러가 시작 5초 뒤부터 60초마다(`application.notification.bymail.initdelay`, `interval`) 만든 지 180초(`delay`)가 지난 이벤트를 골라 메일로 보낸다. 180초 지연은 연달아 고친 이벤트를 합칠 시간을 준다.
- **선택지**: (a) 같은 방식(DB 대기열 + 스케줄러), (b) 요청 안에서 즉시 발송.
- **권장안**: (a). v1.6을 그대로 따르고, 이벤트가 DB에 남아 재시작에도 유실되지 않는다. D-14의 `@Scheduled`로 구현한다.
- **결정(선생님)**: v1.6이 비동기라는 점을 확인하고 (a)로 진행.
- **상태**: 확정.

### D-19. 시스템 메일은 v1.6처럼 메일마다 만들고 보내는 방식을 달리한다 (2026-10-23, 선생님)

- **계기**: A-60(시스템 메일은 요청 스레드에서 만들고 발송만 비동기)을 재결정 대기로 올렸다.
- **v1.6 동작(2026-10-23 정정)**: 처음에는 `Mailer.send`가 Akka 액터로 비동기라고 적었으나 틀렸다. `play-2-mailplugin`의 `Mailer.send`는 동기로 보내고 결과 문자열을 돌려준다(jar를 `javap`로 확인했고 Akka를 쓰지 않는다). 메일마다 달랐다: 비밀번호 재설정과 프로젝트 이전 요청은 요청 안에서 만들고 동기로 보낸다. 보조 이메일 확인은 Akka 액터(`ValidationEmailSender`)가 만들고 보낸다. 가입 인증은 `play-easymail`로 보내며(설정에 "Seconds between sending mail through Akka"가 있다) 본문은 요청 안에서 만든다. 알림 메일은 Akka 스케줄러 스레드가 만들고 보낸다.
- **선택지(재확인)**: (a) 네 가지 모두 비동기, (b) 메일마다 v1.6과 같게, (c) 모두 동기. 권장안은 (b)("v1.6 그대로" 원칙).
- **결정(선생님)**: 처음에는 (b) 모두 비동기로 정했으나, 근거가 "v1.6 `Mailer.send`가 비동기"라는 제 잘못된 설명이어서 정정 후 다시 물었고 "메일마다 v1.6과 같게"로 확정했다.
- **구현**: 비밀번호 재설정과 프로젝트 이전 요청은 요청 안에서 만들고 요청 스레드에서 바로 보낸다(`MailDispatcher.sendNow`). 가입 인증은 요청 안에서 만들고 발송만 전용 스레드에 맡긴다(`sendAsync`). 보조 이메일 확인은 언어와 사이트 주소(`SiteUrls.withOrigin`)를 모아 만들기와 보내기를 모두 전용 스레드가 한다(`dispatch`). 메일 서버를 설정하지 않았거나 보내지 못하면 경고만 남긴다.
- **상태**: 확정.

### D-20. 외부 API의 토큰 인증 경로는 v1.6처럼 프로젝트 권한을 확인하지 않는다 (2026-10-23, 선생님)

- **계기**: A-63(외부 이슈 API에 프로젝트 권한 확인을 추가)을 재결정 대기로 올렸다.
- **v1.6 동작**: `Authorization: token` 헤더의 토큰만 확인하고 프로젝트 권한은 확인하지 않아, 유효한 토큰이면 비공개 프로젝트의 이슈도 읽고 고칠 수 있었다.
- **선택지**: (a) 권한 확인 유지, (b) 토큰은 v1.6처럼 허용, (c) 읽기만 확인.
- **결정(선생님)**: 보안 토큰에 관해서는 허용한다(b).

- **상태**: 확정. 구현은 [web/subversion.md](web/subversion.md)에 기록한다.

### D-27. `GET /_init`은 v1.6 그대로 재현한다 (2026-10-25, 선생님)

## 정책 결정

### P-01. v1.6을 그대로 따른다 (AGENTS.md)

- 기능, 동작, 요청·응답 계약, DB 테이블이 v1.6과 같아야 한다. 임의로 기능을 추가하거나 판단하지 않는다.
- v1.6의 결함은 같게 재현하고 [refactoring-backlog.md](refactoring-backlog.md)에 올린다. 개선은 선생님의 승인을 받은 뒤에만 한다.
- 구조가 달라지는 부분은 이유와 함께 위키에 기록한다.

### P-02. AGENTS.md는 저장소 루트의 전역 프롬프트다 (2026-10-22, 선생님)

- 내려받은 `AGENTS.md`를 저장소 루트에 두고, `CLAUDE.md`(`@AGENTS.md`)로 불러와 전역 지침으로 취급한다.

### P-03. 커밋은 주요 작업 단위로 하고 주석과 위키를 소홀히 하지 않는다 (2026-10-22, 선생님)

- 테스트 통과, 코드, 한글 주석(API 수준), 위키를 같은 단위에서 함께 갱신한 뒤 커밋한다. 푸시는 지시가 있을 때만 한다.

### P-04. 화면 캡처와 브라우저 검증은 Playwright로만 한다 (2026-10-22, 선생님)

- Claude in Chrome 확장 같은 다른 브라우저 도구는 쓰지 않는다. 검증은 작업 단위를 마칠 때 한 번만 하고 로그인 절차는 도우미로 재사용한다.
- **보충(2026-10-22, 선생님)**: v1.6 화면은 여러 문제로 캡처할 수 없다. 새로 만든 화면만 캡처한다. 이에 따라 v1.6과 나란히 비교하는 화면 검증 계획은 폐기하고, v1.6과의 일치는 템플릿 소스 대조와 테스트(DOM 구조, 문구, 링크)로 확인한다. 이 방식의 한계는 색상, 간격 같은 시각적 차이를 잡지 못한다는 점이며, CSS와 JS 자원을 v1.6에서 그대로 가져왔다는 사실이 이를 줄여 준다.

### P-05. R-03 승인 (2026-10-22, 선생님)

- 로그아웃 요청에 Referer가 없으면 v1.6은 오류가 나지만, v2는 홈으로 보낸다. 결함을 재현하지 않는 유일한 예외로 승인되었다.

### P-06. 결정은 위키에 근거와 함께 기록한다 (2026-10-22, 선생님)

- 기술 스택과 정책에 관한 결정은 반드시 이 파일에 남긴다. 권장안이 있었다면 권장 이유도 함께 적는다.
- 결정이 필요한 일은 구현에 앞서 선생님께 먼저 묻는다.

### P-07. 외부 API 작성자 대체, 권한 확인 순서, 댓글 상태 전환 (2026-10-26, 선생님)

v1.6과 v2의 불일치 점검에서 나온 세 항목에 대한 결정이다.

1. **`findAuthor`(외부 REST로 이슈, 게시글, 댓글을 가져올 때의 작성자)**: v1.6으로 되돌린다. 이메일로 사용자를 찾고 없으면 만들며, 만들 수 없으면 익명 사용자(번호 -1)가 작성자가 된다. 권장안과 같다. 이유: AGENTS.md가 v1.6 완전 재현을 원칙으로 하고, 이전에는 v2가 임의로 `400`을 돌려주었다. 구현: `ApiUsers.findOrCreateByEmail`, 테스트 `ExternalIssueApiTest`.
2. **`editIssue`, `deleteIssue`의 권한 확인 순서**: v2의 현재 동작을 유지하고 v1.6 결함을 [R-73](refactoring-backlog.md)에 올린다. 권장안과 같다. 이유: 권한 없는 사용자가 이슈를 옮기거나 삭제 알림을 보낼 수 있는 동작을 되살릴 이유가 없다.
3. **댓글의 `withStateTransition`**: v1.6으로 맞춘다. 하위 이슈를 댓글로 다시 열어도 닫힌 부모 이슈는 열지 않는다. 구현: `IssueService.toNextState(reopenParent = false)`, 테스트 `IssueCommentTest`.

### P-08. 점검 결과의 처리 기준 (2026-10-26, 선생님)

- 화면에서 닿는 불일치는 v1.6 동작으로 맞추고 TDD로 고친다(기본값 v1.6, 별도 결정 대기 없음). 권장안과 같다. 이유: AGENTS.md가 v1.6 완전 재현을 원칙으로 한다.
- v1.6이 오류를 내는 경우(500, NPE)는 v2의 현재 동작을 유지한다. 직접 만든 요청으로만 닿는 항목은 A-24에 따라 재현하지 않고 [hand-crafted-request-differences.md](architecture/hand-crafted-request-differences.md)에 근거를 남긴다.
- 이번에 v1.6에 맞춘 화면 항목: 비밀번호 재설정 메일 실패 안내, 멘션 후보 순서 두 곳, `attachLabel` category, `newWebhook` 오류 화면, `massUpdate` 삭제 알림, `referCommentId` 파생 이슈 댓글, 첨부 목록 403의 Content-Type.

### P-09. 실패 경로와 중복 행도 v1.6 상태를 유지한다 (2026-10-26, 선생님)

- R-74(`changeVCS` 실패 시 README 해제와 포크 분리가 남는 중간 상태), R-76(`accept`의 병합 중 표시 고착), R-82(REST 프로젝트 생성의 SITEMANAGER 행 2개)는 v1.6 상태를 그대로 유지한다. 권장안은 v2의 롤백과 1행이었으나 선생님이 v1.6 재현을 택하셨다. 구현: `ProjectVcsService`와 `PullRequestWorkflow.accept`, `PullRequestActionController.accept`에서 트랜잭션을 제거하고, `ExternalProjectService.create`가 SITEMANAGER 행을 두 번 넣는다.
- 5차 검증에서 나온 v1.6 결함 후보 전체는 [v16-defect-catalog.md](architecture/v16-defect-catalog.md)에 항목별로 기록한다. 가볍게 지나가지 않도록 후보마다 v1.6 소스 줄, v2 상태, 기록 위치를 남긴다.

### P-10. v1.6 위키 9~11차 갱신분 대조의 처리 (2026-10-26, 선생님)

v1.6 위키가 9차(Antigravity CLI 판정), 10차(소스 재검증), 11차(재확인)로 크게 바뀌어 GitHub의 위키로 로컬을 갱신하고, 바뀐 127개 페이지를 v2 소스와 대조하라고 하셨다. 처리 기준은 P-08과 같다(화면과 정상 호출로 닿는 불일치는 v1.6에 맞추고, v1.6의 오류는 v2 유지, 직접 만든 요청은 기록만).

- 대조는 에이전트 18개가 후보를 냈고, 후보마다 다른 에이전트가 v1.6과 v2 소스를 다시 읽어 확정했다. 확정된 항목을 고쳤고(두 결정 대기 항목은 선생님이 v1.6으로 정하셔서 이어서 고쳤다) 결과는 [v16-sync-9-11.md](architecture/v16-sync-9-11.md)에 있다.
- **결정 1: Git/SVN Basic 인증의 세션 (선생님이 v1.6으로 정하심).** 자격이 맞으면 사용자를 세션에 로그인시켜 세션 쿠키를 심고, 틀리거나 없으면 세션, 토큰, 로그인 유지 쿠키 사용자로 되돌아간다. 쿠키가 없는 git 요청마다 서버 세션이 하나씩 생기는 비용은 감수한다. 구현: `BasicAuthResolver`, 테스트 `GitHttpTest`.
- **결정 2: 가져오기 API의 `createdAt`, `updatedAt` 생략 (선생님이 v1.6으로 정하심).** 이슈, 게시글, 게시글 댓글은 시각을 비운 채(NULL) 저장한다. 이슈 댓글은 v1.6도 현재 시각이므로 그대로다. NULL이어도 이슈와 게시글 화면은 오류 없이 그려진다(`ExternalIssueApiTest`, `ExternalBoardApiTest`). v1.6 화면이 NULL에서 오류를 내는지는 확정하지 못했고, 내더라도 v2는 오류 없이 그린다.
- **결정 3: 내부 서술 검증에서 나온 불일치도 v1.6으로 맞춘다 (선생님, 2026-10-27).** JGit, Tika 같은 라이브러리는 수정하지 않고 우리 코드에서 동작만 v1.6에 맞춘다(예: 이진 파일 판정, 파일의 최근 커밋 선택, `HistogramDiff` 결과). v1.6의 오류(500/NPE)는 v2가 오류 없이 처리하는 쪽을 유지한다(P-08). 권장안과 같다. 이유: AGENTS.md가 v1.6 완전 재현을 원칙으로 하고, 라이브러리 수정은 유지보수 부담이 크다.
- **결정 4: 포크 저장소는 v1.6 방식으로 만든다 (선생님, 2026-10-27).** v1.6은 `Repository.create()`(`create(false)`, 비-bare)로 포크를 만든다. v2의 `create(true)`를 v1.6 방식으로 바꾼다. 권장안은 화면 영향이 없어 v2 유지였으나 선생님이 v1.6 재현을 택하셨다.
- **결정 5: 데이터 가져오기는 v1.6의 `TRUNCATE` 의미를 따른다 (선생님, 2026-10-27).** 테이블 이름이 맞으면 먼저 비워 즉시 확정하고, 값이 배열이 아니면 테이블만 비워지며, 행을 넣다 실패하면 넣은 행만 되돌려 테이블은 빈 채로 남는다. 권장안은 실패 시 이전 데이터를 복구하는 v2 동작 유지였다(가져오기 실패로 데이터가 사라지는 것을 막기 위해). 선생님이 v1.6 재현을 택하셨다. 구현: `DataService.truncate`, 테스트 `SiteDataTest`.
- **결정 6: 문자 집합 감지기는 juniversalchardet 1.0.3으로 고정한다 (선생님, 2026-10-27).** v1.6과 같은 아티팩트(`com.googlecode.juniversalchardet:juniversalchardet:1.0.3`)로 되돌려 Big5, 태국어 등 감지 모델 차이를 없앤다. 권장안과 같다. 이유: 모델 차이는 코드로 되돌릴 수 없다. 오래된 라이브러리라 보안 점검 대상이다(A-112).
- **결정 7: 127쪽 전수 대조는 모든 수정이 끝난 뒤 한 번 수행한다 (선생님과 협의, 2026-10-27).** 줄 단위 장부와 스크립트 검증으로 빠짐없이 확인한다.
- **결정 8(확정: v1.6 유지, 2026-10-27, 선생님): 외부 API 작성자 조회는 사용자를 만들지 않는다 (에이전트가 v1.6 소스로 정정했고 선생님이 그대로 두기로 하셨다).** P-07.1은 "이메일로 사용자를 찾고 없으면 만든다"를 v1.6 동작으로 보고 정했으나, v1.6 `User.findByEmail`은 사용자가 없으면 `null`이 아니라 `NullUser`를 돌려주어 `IssueApi.findAuthor`의 `createUserNode` 분기에 닿을 수 없다. 그래서 v1.6은 모르는 이메일의 작성자를 익명 사용자(번호 -1)로 저장한다. 선생님이 정하신 "v1.6대로"를 따라 `ApiUsers.findAuthor`로 바꾸고, 이메일 조회는 대표, 보조, 대소문자 무시의 3단계(`UserLookup`)를 쓴다. 담당자와 구성원 조회도 같다. 사용자를 만드는 이전 동작이 필요하면 선생님이 다시 정해 주셔야 한다.
- **결정 9(확정: v1.6 유지, 2026-10-27, 선생님. 구현은 A-127): 세션 사용자의 권한 판정 캐시.** v1.6은 세션 사용자 인스턴스가 요청을 넘어 재사용되어 사이트 관리자 여부, 프로젝트 매니저 여부, 조직 소속 판정이 로그인 동안 남는다. 승격이나 해임 뒤에도 이미 판정한 곳에서는 이전 결과가 유지된다. v2는 매번 새로 조회한다. 같게 하려면 세션에 판정 캐시를 두어야 하는데 설계가 필요하고 보안상 불리하다. 권장: 재현하지 않는다(즉시 반영이 더 안전하다). 선생님 결정을 기다린다.
- **결정 10(확정: v1.6 유지, 2026-10-27, 선생님. 구현은 A-128): 잠긴 사용자의 로그인 유지 쿠키.** v1.6은 `yobi.token` 쿠키 사용자가 잠겨 있어도 계속 로그인 상태이고 v2는 쿠키를 지워 익명으로 만든다. Basic 인증은 삭제된 계정도 통과한다(A-122). 권장: 재현하지 않는다. 선생님 결정을 기다린다.
