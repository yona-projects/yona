# 결정 기록

기술 스택과 정책에 관한 모든 결정을 여기에 시간순으로 남긴다. **누가 무엇을 언제 결정했는지, 선택지는 무엇이었는지, 권장안이 있었다면 왜 그것을 권했는지**를 추적할 수 있어야 한다. 새 결정이 생기면 이 파일에 먼저 항목을 추가하고, 요약은 [architecture/technology-decisions.md](architecture/technology-decisions.md)에 반영한다.

## 읽는 법

| 칸 | 뜻 |
|---|---|
| 결정자 | **선생님**: 선생님이 정하셨다. **합의**: 제가 제안하고 선생님이 확정하셨다. **에이전트**: 제가 구현 중에 정했고 선생님의 확인을 기다린다(맨 아래 표) |
| 권장안 | 제가 권했던 선택지. 선생님이 다른 안을 고르셨으면 그 사실도 적는다 |
| 상태 | 확정, 변경됨, 확인 대기 |

## 결정 목록

### D-01. Spring Boot 버전 (2026-10-22)

- **질문**: `AGENTS.md`의 "Spring Framework 3.5"를 어떻게 해석할 것인가.
- **처음 판단(에이전트)**: Spring Boot 3.5.16으로 해석했다. 이유는 `Spring Framework 3.5`가 존재하지 않는 버전이라 Boot 3.5의 오기로 보았기 때문이다.
- **결정(선생님)**: "스프링 부트 4로 올려서 진행". Spring Boot 4.1.1(Spring Framework 7, Hibernate 7)로 상향했다.
- **상태**: 확정.

### D-02. 쿼리 계층 (2026-10-22)

- **선택지**: (a) Spring Data JPA + Criteria(Specification), (b) Spring Data JPA + QueryDSL, (c) Spring Data JPA + jOOQ.
- **권장안**: (a).
- **권장 이유**: 코드 생성이 필요 없고 JPA 표준만 쓴다. DB별 SQL 생성을 Hibernate 방언에 맡기므로 이식성이 가장 높다(Cubrid는 `hibernate-community-dialects`). Boot 4와 Hibernate 7에서 호환 문제가 없다. (b)는 Kotlin에서 KSP 코드 생성이 필요하고 Hibernate 7 지원이 불안정하다. (c)는 JPA와 이중 모델이 되어 복잡해진다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-03. 스키마 관리 방식 (2026-10-22)

- **선택지**: (a) Hibernate 생성(`ddl-auto`) 유지 + v1.6 기준 스키마 대조 테스트, (b) Liquibase, (c) Flyway + DB별 SQL.
- **권장안**: (a).
- **권장 이유**: 엔티티가 유일한 원천이라 DB마다 SQL을 따로 유지하지 않아도 된다. 구조 보증은 대조 테스트가 맡는다. Cubrid는 Liquibase, Flyway의 공식 지원 목록에 없다. 단점은 운영 DB의 변경 이관 도구가 없다는 점이며, 릴리즈 전이라 감수한다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정. 운영 이관이 필요해지는 시점에 다시 논의한다.

### D-04. 스키마와 통합 테스트를 검증할 DB 범위 (2026-10-22)

- **선택지**: (a) H2 + PostgreSQL + MariaDB, (b) 위 3종 + MySQL, (c) 6종 전부(Cubrid, MSSQL 포함).
- **권장안**: (a).
- **권장 이유**: 선생님이 처음 말씀하신 범위와 같다. MySQL, Cubrid, MSSQL은 컨테이너 이미지와 드라이버 준비 비용이 크고 실행 시간이 길어진다.
- **결정(선생님)**: (a)로 하되 "test container와 docker compose로 상시 띄워놓고 테스트"하자고 하셨다.
- **반영(에이전트)**: PostgreSQL, MariaDB 테스트 컨테이너는 Testcontainers `reuse` 모드로 띄워 테스트가 끝나도 내리지 않는다. `docker-compose.yml`은 개발 중 앱 실행용으로 따로 둔다. 두 가지를 분리한 이유는 테스트 컨테이너는 스키마를 만들고 지우는 반면, 개발용 컨테이너는 데이터를 보존해야 하기 때문이다.
- **상태**: 확정. 이 반영 방식(두 컨테이너 분리)은 선생님의 확인을 받지 않았다.

### D-05. 테스트 라이브러리 (2026-10-22)

### D-07. enum 컬럼의 DB 제약 (2026-10-22)

- **계기**: 선생님이 "v1.6에서 enum 필드의 값이 프로그램에서 자유롭게 입력되는 값인지 아닌지에 따라 DB에 enum 타입을 둘지 말지가 결정될 것"이라고 물으셨다.
- **조사(에이전트)**: v1.6의 enum 값은 `State.getValue`, `ResourceType.getValue`, `UserState.of` 등으로 변환한 닫힌 집합이며 자유 입력이 아니다. 그런데도 v1.6은 `1.sql`의 `CHECK` 제약을 `20.sql`에서 21개 모두 제거했다. 새 enum 값을 추가할 때마다 DB를 고치지 않기 위해서다.
- **선택지**: (a) 제약 없이 문자열/정수로 저장(v1.6 최종 스키마와 같음), (b) `CHECK` 제약 유지, (c) DB 고유 `ENUM` 타입.
- **권장안**: (a).
- **권장 이유**: 테이블 구조를 v1.6과 같게 유지하라는 원칙과 맞는다. DB 고유 `ENUM`은 PostgreSQL(`CREATE TYPE`), MSSQL, Cubrid에서 방식이 달라 이식성이 낮다. `ddl-auto=update`는 이미 만든 `CHECK`를 갱신하지 않아 새 enum 값을 저장할 때 오류가 난다.
- **결정(선생님)**: "일단은 지금 결정 유지" = (a).
- **상태**: 확정. DB에서도 값을 강제하려면 v1.6과 달라지는 결정이므로 선생님의 승인이 필요하다.

### D-08. LESS 빌드 (2026-10-22)

- **계기**: v1.6이 CSS를 sbt 빌드 때 LESS에서 만든다는 사실을 구현 중 발견했다.

- **권장안**: (a).
- **권장 이유**: v1.6과 같은 방식(빌드 시점 생성)이라 소스와 결과가 어긋나지 않는다. (b)는 LESS를 고칠 때마다 다시 컴파일해 커밋해야 한다. (c)는 Less 1.x 문법 일부만 지원해 결과가 달라질 위험이 있다. 단점은 빌드 환경에 Node와 npm이 필요하다는 점이다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-18. 알림 메일은 v1.6처럼 비동기 스케줄러로 보낸다 (2026-10-23)

- **계기**: 4단계 알림 서브시스템의 발송 방식을 정해야 했다.
- **v1.6 동작**: 이벤트는 요청 안에서 `notification_event` 행으로 저장하고, Akka 스케줄러가 시작 5초 뒤부터 60초마다(`application.notification.bymail.initdelay`, `interval`) 만든 지 180초(`delay`)가 지난 이벤트를 골라 메일로 보낸다. 180초 지연은 연달아 고친 이벤트를 합칠 시간을 준다.
- **선택지**: (a) 같은 방식(DB 대기열 + 스케줄러), (b) 요청 안에서 즉시 발송.
- **권장안**: (a). v1.6을 그대로 따르고, 이벤트가 DB에 남아 재시작에도 유실되지 않는다. D-14의 `@Scheduled`로 구현한다.
- **결정(선생님)**: v1.6이 비동기라는 점을 확인하고 (a)로 진행.
- **상태**: 확정.

### D-19. 시스템 메일은 v1.6처럼 메일마다 만들고 보내는 방식을 달리한다 (2026-10-23, 선생님)

- **계기**: A-60(시스템 메일은 요청 스레드에서 만들고 발송만 비동기)을 재결정 대기로 올렸다.
- **v1.6 동작(2026-10-23 정정)**: 처음에는 `Mailer.send`가 Akka 액터로 비동기라고 적었으나 틀렸다. `play-2-mailplugin`의 `Mailer.send`는 동기로 보내고 결과 문자열을 돌려준다(jar를 `javap`로 확인했고 Akka를 쓰지 않는다). 메일마다 달랐다: 비밀번호 재설정과 프로젝트 이전 요청은 요청 안에서 만들고 동기로 보낸다. 보조 이메일 확인은 Akka 액터(`ValidationEmailSender`)가 만들고 보낸다. 가입 인증은 `play-easymail`로 보내며(설정에 "Seconds between sending mail through Akka"가 있다) 본문은 요청 안에서 만든다. 알림 메일은 Akka 스케줄러 스레드가 만들고 보낸다.
- **선택지(재확인)**: (a) 네 가지 모두 비동기, (b) 메일마다 v1.6과 같게, (c) 모두 동기. 권장안은 (b)("v1.6 그대로" 원칙).
- **결정(선생님)**: 처음에는 (b) 모두 비동기로 정했으나, 근거가 "v1.6 `Mailer.send`가 비동기"라는 제 잘못된 설명이어서 정정 후 다시 물었고 "메일마다 v1.6과 같게"로 확정했다.
- **구현**: 비밀번호 재설정과 프로젝트 이전 요청은 요청 안에서 만들고 요청 스레드에서 바로 보낸다(`MailDispatcher.sendNow`). 가입 인증은 요청 안에서 만들고 발송만 전용 스레드에 맡긴다(`sendAsync`). 보조 이메일 확인은 언어와 사이트 주소(`SiteUrls.withOrigin`)를 모아 만들기와 보내기를 모두 전용 스레드가 한다(`dispatch`). 메일 서버를 설정하지 않았거나 보내지 못하면 경고만 남긴다.
- **상태**: 확정.

### D-20. 외부 API의 토큰 인증 경로는 v1.6처럼 프로젝트 권한을 확인하지 않는다 (2026-10-23, 선생님. **D-36으로 대체될 예정**: 선생님이 2026-10-29에 이 동작을 버그로 보고 모든 토큰이 권한을 확인하게 하기로 했다)

- **계기**: A-63(외부 이슈 API에 프로젝트 권한 확인을 추가)을 재결정 대기로 올렸다.
- **v1.6 동작**: `Authorization: token` 헤더의 토큰만 확인하고 프로젝트 권한은 확인하지 않아, 유효한 토큰이면 비공개 프로젝트의 이슈도 읽고 고칠 수 있었다.
- **선택지**: (a) 권한 확인 유지, (b) 토큰은 v1.6처럼 허용, (c) 읽기만 확인.
- **결정(선생님)**: 보안 토큰에 관해서는 허용한다(b).

### D-29. Apache Magpie 연동을 위한 읽기 전용 API (2026-10-28, 결정 대기)

### D-30. Git 태그 기능(X-18)은 브랜치와 분리한 전용 화면으로 구현한다 (2026-10-29, 선생님)

- **배경**: v1.6의 브랜치 화면(`BranchApp.branches`)은 `getBranches()`가 `refs/heads`, `refs/tags`, `refs/remotes`를 모두 모아 태그도 "브랜치"로 보여 준다. 태그를 눌러 코드를 보는 것과 지우는 것(`DELETE /:user/:project/code/:branch/`, 매니저 전용)은 이미 된다. 없는 것은 주석 태그의 메시지와 태거, 주석과 경량의 구분, 날짜순 정렬, 삭제 확인, REST이다. 슬래시가 든 태그 이름(`release/1.0`)은 지금도 목록, 열기, 삭제가 된다(링크는 `refs%252Ftags%252F…`처럼 두 번 인코딩한 형태). 커밋이 아닌 대상을 가리키는 태그(`tree-tag`)가 있으면 브랜치 화면이 500이다(v1.6도 같다). 근거 화면은 2026-10-29 캡처로 확인했다. GitHub은 태그 목록을 Releases 안의 Tags로 두고 브랜치 화면은 브랜치만 다룬다(공식 문서).
- **결정(선생님)**: 아래 일곱 가지로 진행한다. 동등성 점검이 끝났으므로 v1.6 템플릿이 달라지는 것은 불가피한 추가로 본다.
  1. 진입 링크: 코드 화면의 탭에 "태그"를 추가한다(`view`, `history`, `diff`, `branches` 네 곳).
  2. 브랜치 목록 함수(`BranchService.branches`, v1.6 `getBranches`)가 `refs/heads/*`만 돌려준다. 이 함수를 쓰는 브랜치 화면, 풀 리퀘스트 생성 화면과 병합 결과 미리보기, 풀 리퀘스트 수정 폼이 모두 이에 따른다. 그래서 풀 리퀘스트의 출발, 도착 목록과 출발 기본값에서 태그가 빠지고, 커밋이 아닌 대상을 가리키는 태그의 500도 사라진다(목록을 만들 때 커밋을 읽기 전에 거른다). 풀 리퀘스트 생성 요청의 서버 검증은 v1.6대로 둔다. 원격 참조(`refs/remotes/*`)도 목록에서 빠진다. 원격 참조는 서버 저장소에서 의미 있는 개념이 아니고 v1.6에도 그 기능이 없었다(`isWellKnownRef`를 옮긴 부산물이다). 푸시로 만들 수는 있다(2026-10-29 v2, v1.6 모두 `master:refs/remotes/origin/feature` 푸시가 성공했다). 이미 만들어진 참조는 저장소에서 지우지 않는다.
  3. 코드 화면의 브랜치/태그 선택 목록은 "브랜치", "태그" 두 구역(`optgroup`)으로 나눈다. 선택된 값과 항목 앞의 `branch`, `tag` 배지는 유지한다. `yobi.ui.Select2.js`의 `branch` 포맷터가 구역 제목을 배지 없이 보이게 고친다. 새 메시지 키는 `title.tags`이다(6개 언어). 원격 구역은 만들지 않는다.
  4. 신규 태그 화면(`GET /:user/:project/tags`)은 커밋이 아닌 대상을 가리키는 태그도 500 없이 "커밋이 아님"으로 보여 준다. 주석 태그의 메시지와 태거, 주석과 경량 배지, 태그 날짜 기준 최신순을 보인다. SVN 프로젝트는 400이다.
  5. 삭제는 신규 화면 전용 경로(`DELETE /:user/:project/tags/:tag`)로 하고 확인창을 둔다. 슬래시가 든 이름을 받는다. 권한은 브랜치 삭제와 같은 `Operation.DELETE`(매니저). 기존 삭제 경로는 v1.6대로 유지한다.
  6. REST API는 X-19(일반 REST)로 옮기고 태그 생성 폼은 두지 않는다(생성은 `git push --tags`). GitHub의 태그 목록 화면에도 생성 폼이 없다.
  7. (기록만) `refs/heads`, `refs/tags` 밖의 참조에 대한 푸시를 거부하는 정책은 이번에 하지 않는다. v1.6의 git 계약을 바꾸는 일이라 X-13(브랜치 보호 규칙) 계열의 후보로만 둔다. 선생님이 2026-10-29에 **나중에 다루기로(보류)** 하셨다.
- **참조를 읽는 코드**는 참조 종류를 인자로 받는 형태로 작성한다. 화면과 라우트까지 미리 일반화하지는 않는다.
- **용어(선생님, 2026-10-29)**: 화면의 `주석 태그`(Annotated), `경량 태그`(Lightweight) 표현은 현재대로 유지한다. 풀어 쓰는 표현("메시지 있음" 등)으로 바꾸지 않는다.
- **상태**: 확정(위 일곱 가지), 구현 완료(2026-10-29). 풀 리퀘스트 브랜치 목록에서 태그를 뺄지에 대한 선생님의 질문은 2번으로 닫았다. 구현 기록은 [web/tags.md](web/tags.md)를 본다.

### D-31. 브랜치 삭제에도 확인창을 둔다 (2026-10-29, 선생님)

### D-34. 풀 리퀘스트의 담당자와 라벨(X-14)은 연결 테이블 두 개로 구현한다 (2026-10-29, 선생님과 권장안)

- **배경**: 풀 리퀘스트의 담당자(`assignee`)는 "처리가 끝나기 전에 이 풀 리퀘스트를 맡은 사람"으로, 작성자, 리뷰어, 받은 사람(`receiver`, 처리 결과)과 다른 역할이다. v1.6에는 풀 리퀘스트의 담당자와 라벨이 없다. GitHub은 담당자를 한 건에 최대 10명까지 지정한다(공식 문서). `next`는 `pull_request.assignee_id` 컬럼 하나(1명)와 연결 테이블 `pull_request_issue_label`로 구현했고 담당자와 라벨의 REST와 화면이 있다. 선생님이 나중에 1명에서 여러 명으로 키울 가능성을 물으셨다.
- **저장 구조 선택지**: (A) `next`처럼 컬럼 하나. 확장 때 연결 테이블 추가, 데이터 옮기기(마이그레이션 도구가 없어 시작 때 한 번 도는 코드를 직접 작성), 쓰이지 않는 옛 컬럼, REST 응답 모양 변경(`assignee`에서 `assignees`)이 든다. (B) 처음부터 연결 테이블을 두고 서비스 규칙으로 1명까지만 받는다. 확장은 한도 상수와 화면의 다중 선택만 고치면 된다. 이슈의 담당자(컬럼)와 구조가 달라진다.
- **권장안과 이유**: (B). 확장 때의 데이터 옮기기와 REST 호환 문제를 지금 비용 거의 없이 피한다.

  2. **스키마 시험**: `V16SchemaTest`는 "의도한 추가 목록"을 허용하도록 고치고 새 테이블 2개를 올린다(H2, PostgreSQL, MariaDB 모두).

  6. 담당자는 1명까지(서비스의 한도 상수 하나). 키울 때는 상수와 화면의 다중 선택만 고친다.

### D-35. 풀 리퀘스트 리뷰 판정(X-12)은 GitHub 기준의 단일 리뷰 모델로 구현하고 v1.6의 "리뷰 완료"를 그 안에 흡수한다 (2026-10-29, 선생님 확정: 방침과 권장안, 13번은 (가), 구현 전)

- **배경**: v1.6의 "리뷰 완료/취소"(`ReviewApp.review`, `unreview`)는 리뷰어 집합(`pull_request_reviewers`)에 본인을 넣고 빼는 승인 표시뿐이며 본문과 판정이 없다. 선생님이 2026-10-29에 "동치 이후의 변경은 모두 의도된 동작이므로 필요하면 v1.6 동작을 바꿔도 되고, 가능하면 GitHub 기준으로 채운다"고 하셨다. 그래서 처음 권장안(리뷰 완료와 Approve를 별개로 둔다)을 접고 GitHub처럼 **하나의 리뷰 모델**로 합친다.
- **GitHub 기준(공식 문서 확인, 2026-10-29)**: 리뷰는 Comment, Approve, Request changes 세 가지이고 요약 댓글과 함께 제출한다. 작성자는 자기 풀 리퀘스트를 승인할 수 없다. 병합 요건에 드는 승인은 쓰기 이상 권한자의 것만 센다. 변경 요청은 풀 리퀘스트를 필수로 하는 보호 규칙이 있을 때만 병합을 막고 없으면 표시일 뿐이다(현재 문서). 쓰기 권한자가 사유를 적어 리뷰를 해제(dismiss)하면 일반 댓글이 된다. 새 커밋 때 승인을 자동 해제하는 것은 선택 설정이다. 소유자와 관리자는 승인 없이 병합할 수 있다. "리뷰어별 최신 판정만 쓴다"는 규칙은 공식 문서로 직접 확인하지 못했다(로드맵 설계를 따른다).
- **권장 설계**:
  1. **판정과 저장**: 새 테이블 `pull_request_review`(리뷰어, 판정, 본문, 제출 시각, 해제 여부와 사유)에 이력을 쌓고, 정책에는 리뷰어별 최신 판정만 쓴다. 해제된 리뷰는 Comment로 취급한다.
  2. **v1.6 "리뷰 완료"의 흡수**: "리뷰 완료" 버튼은 **Approve**가 된다. v1.6 테이블 `pull_request_reviewers`는 **현재 승인한 사람 집합**으로 계속 쓰며 판정과 함께 갱신한다(Approve면 넣고, 이후 Comment나 Request changes나 해제면 뺀다). 그래서 병합 조건의 필요한 리뷰어 수(`isUsingReviewerCount`)와 병합 커밋의 `Reviewed-by:`는 구조를 바꾸지 않고 그대로 동작한다. 이미 들어 있는 기존 리뷰어 행은 승인으로 본다. "리뷰 취소"는 GitHub에 같은 버튼이 없으므로 다음 판정(Comment)으로 대체한다.
  3. **Request changes의 효과**: 프로젝트가 리뷰어 수를 켠 경우(v1.6의 보호 장치에 해당)에는 리뷰어별 최신 판정에 Request changes가 하나라도 남아 있으면 병합을 막는다(GitHub 보호 규칙과 같다). 켜지 않은 프로젝트에서는 표시만 한다. 해제하거나 같은 리뷰어가 다시 승인하면 풀린다.
  4. **권한**: 읽기 권한이 있는 로그인 사용자는 Comment를, 쓰기 권한(프로젝트 구성원)이 있는 사람은 Approve와 Request changes를 할 수 있다(v1.6 "리뷰 완료"의 `ACCEPT` 권한 요건을 GitHub 기준으로 맞춘다). 작성자 본인은 Approve와 Request changes를 할 수 없다. 해제는 쓰기 권한자가 사유를 적어 한다.
  5. **새 커밋과 오래된 승인**(선생님 지시 2026-10-29: 시스템 설정 메뉴에 추가): v1.6은 새 커밋이 들어오면 리뷰어를 모두 비운다(`PullRequestActor`의 `clearReviewers`, v2 `PullRequestMergeProcessor`). 이는 GitHub의 "새 커밋에 오래된 승인 해제" 설정을 항상 켠 것과 같다(처음에 "자동 해제하지 않는다"고 적은 것은 틀렸다). 이를 **사이트 관리자의 시스템 설정 항목 "새 커밋이 올라오면 오래된 승인을 해제한다"**로 만든다. 기본값은 **켬**(v1.6 동작 유지)이고 GitHub처럼 끌 수 있다. 켜져 있으면 현재 승인(APPROVED)들을 시스템이 해제 처리하며(`dismissed_date` 기록, 사유 "새 커밋", 해제한 사람 비움) 승인 집합도 비운다. 꺼져 있으면 승인이 새 커밋 뒤에도 남는다. Request changes와 Comment는 어느 쪽이든 해제하지 않는다(GitHub과 같다). **설정 위치는 (A) 프로젝트 설정으로 확정(선생님 2026-10-29)**. 선택 과정:  선생님이 기억하신 "알림을 받는다/안 받는다" 화면은 **사용자 개인 알림 설정**(`user/edit-notifications`, 종류별 켜고 끄기)으로 확인했다. 사이트 전체 설정 화면은 아니다. v1.6의 `site/setting`(사이트 관리자 "설정")은 `TODO`뿐인 빈 화면이고 v2에도 값을 고치는 사이트 설정 화면이 없다(설정은 모두 `yona.*` 설정 파일). 값을 고치는 화면은 프로젝트 설정(`project/setting`)과 조직 설정에만 있고, 프로젝트 설정에는 이 기능과 같은 영역인 **"리뷰어 수 사용"(`isUsingReviewerCount`, `defaultReviewerCount`)**이 이미 있다. 선택지: (A) **프로젝트 설정**의 리뷰어 수 옆에 켜고 끄는 항목을 둔다(프로젝트 테이블에 열 `is_dismissing_stale_approvals` 추가, 기본 켬). GitHub도 이 규칙을 저장소의 보호 규칙마다 두고, 기존 설정 화면과 저장 구조(프로젝트 열)를 그대로 쓰므로 새 설정 인프라가 없다. 열은 내보내기, 가져오기가 이미 다룬다(새 열만 스키마 시험의 의도한 추가 목록에 올린다). (B) 사이트 관리자 시스템 설정(첫 DB 저장 설정: 새 테이블 `site_setting`과 "설정" 화면, 내보내기 포함). 모든 프로젝트에 같은 값이 적용된다. (C) 설정 파일 키만(`yona.pull-request-dismiss-stale-approvals`, 화면 없음). 권장은 (A)이고, 이유는 GitHub이 저장소 단위이고 리뷰어 수와 같은 화면에서 정하며 새 인프라가 필요 없기 때문이다. 선생님이 "시스템 설정"을 사이트 전체 값으로 원하시면 (B)로 한다. → 선생님이 (A)를 고르셨다. 세부: 프로젝트 테이블에 열 `is_dismissing_stale_approvals`(기본 켬)을 더하고 프로젝트 설정 화면의 "리뷰어 수" 영역에 켜고 끄는 항목을 둔다(요청 매개변수 이름은 같은 영역의 `isUsingReviewerCount`처럼 `isDismissingStaleApprovals`). 새 열은 스키마 시험의 의도한 추가 목록에 올리고 내보내기, 가져오기는 열 단위로 이미 다룬다. 포크는 v1.6에서 리뷰어 설정을 물려받지 않으므로 이 설정도 새 프로젝트처럼 기본값에서 시작한다. 이 열이 없는 옛 DB는 시작 때 열이 추가되고(기존 프로젝트는 기본 켬이라 v1.6 동작이 그대로 이어진다) 가져오기 파일에 열이 없으면 기본값으로 채운다.
  6. **화면**: 개요 오른쪽 열에 리뷰어별 최신 판정을, 타임라인에 판정, 본문, 해제 이벤트를 보인다. 폼은 댓글 영역 근처에 둔다. 코드 리뷰 스레드(줄 댓글)는 이번에 바꾸지 않는다.
  7. **알림과 웹훅**: 작성자에게 알리고 이벤트 종류와 알림 설정 항목을 X-14와 같은 방식으로 더한다. 웹훅도 같다.
  8. **새 테이블의 이름과 컬럼 규칙**(선생님 지시 2026-10-29: 기존 이름 규칙을 추론해 적용): v1.6 풀 리퀘스트 계열 테이블(`pull_request_commit`, `pull_request_event`, `comment_thread`, `review_comment`)에서 읽은 규칙을 따른다. 테이블은 소문자 스네이크 단수형이고 풀 리퀘스트 하위는 `pull_request_` 접두사이다. 기본 키는 `id` 자동 증가 `BIGINT`, 외래 키는 `pull_request_id`처럼 `<대상>_id`, 사용자 참조는 `author_id`와 로그인 ID 사본 `author_login_id`를 함께 둔다(댓글과 같다. 사용자가 지워져도 이름이 남는다). 열거형은 이름 그대로 `VARCHAR`, 긴 글은 `LONG_TEXT`, 시각은 `Date`이다. 따라서 **`pull_request_review`** 열은 `id`, `pull_request_id`, `author_id`, `author_login_id`, `verdict`(`APPROVED`, `CHANGES_REQUESTED`, `COMMENTED`, `VARCHAR(17)`), `contents`(`LONG_TEXT`), `created_date`, `dismissed_date`, `dismissed_by_login_id`, `dismissed_reason`(`LONG_TEXT`)이다. 색인은 `pull_request_id`와 `author_id`에 둔다. 이름은 구현 때 기존 열 이름과 한 번 더 대조한다.
  9. **내보내기와 가져오기에 포함한다**(선생님 지시 2026-10-29): 새 테이블은 사이트 데이터 내보내기, 가져오기 대상(`DataTables`, 49개에서 50개)에 넣고 자식 테이블 순서(풀 리퀘스트 다음)를 지킨다. 함께 챙기는 것: 고아 정리(`DataService.cleanOrphanLinks`), 프로젝트와 풀 리퀘스트와 사용자 삭제 연쇄(`ProjectDeletionService`, `SiteUserService`), 스키마 시험의 의도한 추가 목록(`SchemaMetadata.INTENDED_ADDITIONS`)과 `AddedTablesSchemaTest`, `DataExchangeTest`, `DataTablesTest`.
  10. **타임라인 이벤트**: v1.6에 이미 `PULL_REQUEST_REVIEW_STATE_CHANGED`(리뷰 완료/취소, 알림 종류 14번)가 있다. 새 판정은 이벤트 종류 `PULL_REQUEST_REVIEW_SUBMITTED`(판정과 본문)와 `PULL_REQUEST_REVIEW_DISMISSED`를 새로 더하고, 옛 이벤트는 기존 데이터 표시를 위해 남긴다. 리뷰 완료와 취소의 짧은 시간 되돌림을 지우는 규칙(`notificationDraftTime`)은 새 판정에는 적용하지 않는다(판정은 본문이 있는 이력이다).
  11. **병합 우회는 GitHub 기준으로 둔다**(선생님 지시 2026-10-29 "GitHub 기준으로 가자"): GitHub은 저장소 관리자가 승인 요건을 채우지 못해도 병합할 수 있다(보호 규칙에서 "관리자에게도 적용"을 켜야 막힌다). 그래서 v1.6에는 없던 동작으로, **프로젝트 관리자(매니저)와 사이트 관리자는 필요한 리뷰어 수와 변경 요청에 막혀도 병합할 수 있게** 한다. 병합 화면에는 요건 미달이라는 안내를 함께 보이고, 타임라인과 병합 커밋의 `Reviewed-by:`는 실제 승인자만 담는다. "관리자에게도 적용" 옵션은 X-13이 규칙으로 들어올 때 더한다.
  12. **작성자 본인의 승인은 막는다**(선생님 지시 2026-10-29: "애초에 막아야 할 기능, GitHub 기준으로 바꾸자"): 작성자는 자기 풀 리퀘스트에 Approve와 Request changes를 할 수 없고(Comment는 가능) 폼에서 그 선택지를 보이지 않으며 서버도 거절한다(403). 필요한 리뷰어 수를 셀 때도 작성자의 승인은 세지 않는다. 구성원이 한 명뿐인 프로젝트는 11번의 관리자 우회로 병합할 수 있다. 앞서 적은 선택지 (A), (B), (C)는 이 결정으로 정리되었다((A)와 같고 우회가 보완한다).
  13. **기존 데이터를 새 구조로 이어 주는 보정**(선생님 지시 2026-10-29: 이관이든 기존 DB 그대로 바이너리만 교체하든 같은 결과가 나오게): 서버 시작 때 한 번 도는 **멱등 보정**(`PullRequestStartup`처럼 `ApplicationRunner`, A-104 선례)을 둔다. `pull_request_reviewers`에 있으나 `pull_request_review`에 해당 사용자의 승인 기록이 없는 행마다 `APPROVED` 리뷰를 만든다(시각은 그 사용자의 가장 가까운 옛 리뷰 완료 이벤트 시각, 없으면 풀 리퀘스트 생성 시각, 본문은 비움). 이미 보정된 행은 건너뛰므로 몇 번을 돌려도 같다. **이관(내보내기 파일 가져오기)** 뒤에도 같은 보정을 부른다(`DataService.import` 끝). 가져오는 파일이 X-12 이전 것이라 새 테이블이 없어도 가져오기가 실패하지 않아야 하며(없는 테이블은 건너뛴다), 새 테이블이 든 파일은 보정이 중복을 만들지 않는다. 옛 `PULL_REQUEST_REVIEW_STATE_CHANGED` 이벤트는 지우거나 바꾸지 않고 그대로 보인다. 작성자 본인이 옛 방식으로 승인해 둔 행은 기록은 남기되 12번에 따라 개수에는 세지 않는다. 이 때문에 **열린 풀 리퀘스트의 병합 가능 여부가 바뀔 수 있으므로** 다음 보완을 둔다(선생님 지시 2026-10-29).
     - **영향 점검**: 보정이 끝난 뒤 열린 풀 리퀘스트 가운데 "이전 규칙으로는 필요한 리뷰어 수를 채웠으나 새 규칙(작성자 승인 제외)으로는 모자란" 요청을 찾아낸다. 이 점검은 보정과 같은 멱등 작업이며 이미 통지한 요청에는 다시 통지하지 않는다.
     - **통지**: 찾은 요청마다 작성자와 프로젝트 관리자에게 알림("작성자의 승인은 세지 않게 되어 승인이 더 필요합니다")을 보내고 타임라인에 시스템 이벤트로 남긴다. 시작 로그에도 건수와 목록을 적는다.
     - **병합 길 보장**: 11번의 관리자 우회로 병합할 수 있고, 다른 구성원이 승인하면 바로 풀린다. 개요 화면 승인 영역에는 "작성자의 승인은 세지 않습니다"를 안내한다.
     - **시험**: 보정 전후의 병합 가능 여부를 요청 상태별로 확인한다(작성자만 승인, 작성자와 타인이 함께 승인, 타인만 승인, 닫힌 요청은 대상 아님). 통지는 한 번만 가는지도 확인한다.
     - **선택지(참고)**: (가) 위처럼 GitHub 규칙을 즉시 적용하고 통지한다(권장. 규칙이 하나이고 영구 예외가 없다). (나) 이관 시점에 이미 열려 있던 요청의 작성자 승인만 계속 세고 새 요청부터 적용한다(기존 흐름은 끊기지 않으나 영구 예외 데이터와 두 갈래 규칙이 남는다).
- **권장 이유**: 별개 개념 둘(리뷰 완료와 승인)을 두면 화면에 사실상 같은 버튼이 둘이 되고 병합 조건이 어느 쪽을 세는지 혼란스럽다. 합치면 v1.6의 병합 조건, `Reviewed-by:`, 기존 데이터를 그대로 살리면서 GitHub과 같은 모델이 된다.
  14. **리뷰 경로는 GitHub 경로에서 `/repos/{owner}/{repo}/pulls/{n}` 접두사만 Yona의 `/:user/:project/pullRequest/:id`로 바꾼다**(선생님 확정 2026-10-29: "/repos 접두사만 사라지면 되는 거 아니냐"): v1.6에는 `POST /:user/:project/pullRequest/:number/review`와 `.../unreview`가 있었다(`conf/routes:383-384`, v2도 같은 경로). 둘 다 화면 버튼이 보내는 POST 폼 요청이라 북마크할 수 없고 v1.6에는 풀 리퀘스트 REST가 없어 쓰는 곳은 사실상 화면뿐이다. GitHub REST는 리뷰를 `POST .../pulls/{n}/reviews`(`APPROVE`는 본문 선택, `REQUEST_CHANGES`와 `COMMENT`는 본문 필수), 해제를 `PUT .../reviews/{id}/dismissals`(`message` 필수)로 하고 승인 철회 전용 동작이 없다(제출한 리뷰는 지울 수 없고 해제나 새 판정만). Yona도 만들기를 복수형으로 두므로(`POST .../pullRequest/:id/comments`, `POST .../pullRequests`) 모양이 어긋나지 않는다. 따라서 **판정 제출은 `POST /:user/:project/pullRequest/:id/reviews`**(`verdict`: `APPROVED`, `CHANGES_REQUESTED`, `COMMENTED`, `contents`), **해제는 `POST /:user/:project/pullRequest/:id/reviews/:reviewId/dismissals`**(`message` 필수. 화면 폼 요청이라 GitHub의 PUT 대신 POST)이다. **v1.6의 `review`와 `unreview`는 없앤다**(제출 경로가 `reviews`로 대체되고 승인 철회는 자기 리뷰를 해제하거나 새 판정을 내는 것이다). REST(X-15)는 같은 모양에 `/-_-api/v1/owners/{owner}/projects/{project}` 접두사를 붙여 얹는다. 대안은 옛 `review`, `unreview`를 얇은 별칭으로 남기는 것이다(비용은 경로와 시험과 의미 혼선, 이득은 이론상의 폼 자동화).
- **GitHub 현재 문서로 확인한 것(2026-10-29)**: "읽기 권한이 있으면 누구나 리뷰와 댓글을 남길 수 있다"(Comment 허용 확정), "작성자는 자기 풀 리퀘스트를 승인할 수 없다", 리뷰 요청에는 쓰기 권한이 필요하다. 문서는 작성자의 Request changes 금지를 적지 않았다(화면이 실제로 막는 것으로 알려져 있어 12번대로 막되 문서 근거는 없다).
- **남은 의문**: 이전 "읽기 권한자의 Comment 허용" 우려는 위 확인으로 풀렸다. 병합 조건과 `Reviewed-by:`가 해제나 재판정 뒤에도 일관되는지는 구현 시 시험으로 확인한다.
- **상태**: 확정(선생님, 2026-10-29, 5번은 (A), 13번은 권장 (가), 14번 경로와 `review`, `unreview` 폐지 포함). 상세 설계와 시험 계획은 [web/pull-request-review.md](web/pull-request-review.md)에 있다. 구현 완료(2026-10-29, A-195~A-202).

### D-36. 개인용 API 토큰(X-5)은 GitHub의 Classic 토큰 방식으로 먼저 도입하고 옛 사용자 토큰은 레거시 Classic 토큰으로 옮긴다 (2026-10-29, 선생님 방향과 권장안, **확인 대기**)

- **배경**: v1.6의 사용자 토큰은 사용자마다 하나(`n4user.token`, 평문 저장), `Authorization: token <값>`, 범위와 만료가 없고 D-20에 따라 프로젝트 권한도 확인하지 않는다. (이전(Migration) 화면은 이 토큰을 쓰지 않는다. 화면의 `token`은 GitHub OAuth 토큰이고 이전 화면이 부르는 API는 세션 로그인을 쓴다.) X-15(풀 리퀘스트 REST), X-19(일반 REST), X-23(Magpie), X-6(MCP)의 선행 조건이며 선생님이 "GitHub처럼 Fine-grained, Classic 토큰을 도입해야 하는 것 아니냐"고 하셨다.
- **확정된 방향**: (1) 옛 토큰의 "권한을 확인하지 않는" 동작은 버그로 보고 **모든 토큰이 사용자 권한도 확인한다**. D-20은 이 결정으로 **대체된다**(선생님 2026-10-29: "기존 동작은 버그니까 (가) 안으로"). (2) 어느 경우든 Classic 토큰(범위 지정)의 설계가 필요하다.
- **권장 설계**: 상세는 [architecture/api-token.md](architecture/api-token.md).
  1. **Classic을 먼저, Fine-grained는 그 위에 따로**(별도 항목 X-5b). Fine-grained는 프로젝트 선택과 항목별 읽기/쓰기, 필수 만료이며 Yona의 권한 모델을 항목별로 매핑하는 일이 더 크다.
  2. **범위(scope)**: GitHub의 Classic 범위를 그대로 대응시킨다(2026-10-29 재조사로 바꿈. 처음의 자원별 읽기/쓰기 쌍은 GitHub에 없어 접었다): `repo`, `public_repo`, `admin:repo_hook`, `write:repo_hook`, `read:repo_hook`, `admin:org`, `write:org`, `read:org`, `user`, `read:user`, `user:email`, 사이트 관리자만 고를 수 있는 `site_admin`, 그리고 `notifications`, `delete_repo`, 공개키와 GPG 키 계열, `workflow`는 해당 기능이 생길 때까지 예약이다. 항목별 분리는 Fine-grained(X-5b)가 맡는다. 전체(`*`)는 레거시 토큰만 가진다.
  3. **형식과 저장**: `yona_pat_` + 임의 40자. 해시(SHA-256)만 저장하고 만들 때 한 번만 보여 준다. 목록에는 접두사만 보인다.
  4. **권한**: 토큰 범위와 사용자의 실제 권한의 교집합만 가능하다. 세션 요청은 범위를 보지 않는다.
  5. **옛 토큰**: 새 테이블의 레거시 Classic 토큰(범위 `*`)으로 시작 때와 가져온 뒤 멱등 보정으로 옮긴다. 같은 값이 계속 동작하고 `n4user.token`은 보정 뒤 비운다.
  6. **만료**(GitHub 문서로 재조사, **권장 수용: 선생님 2026-10-29**): 7, 30, 60, 90일, 사용자 지정, 없음(경고)이고 기본 30일이다. 최대 수명은 설정 키, 사용자당 50개, 1년 미사용 자동 삭제.
  7. **로그인 발급 API**(`POST /-_-api/v1/users/token`): 정확한 현황을 [architecture/api-token.md](architecture/api-token.md)에 정리했다(v1.6은 세션 로그인을 시작하고 사용자의 유일한 토큰을 덮어쓴다, Yona 코드에는 호출하는 곳이 없다, GitHub은 2020-11-13에 비밀번호 API 인증을 없앴다). 권장은 (a) 유지하되 호출마다 이름이 `API login`인 토큰 하나를 교체. 선생님 확인 대기.
  8. **대응표**(선생님 요청 2026-10-29): GitHub 범위를 Yona 안에서 어떻게 해석하는지(자원, 연산, 프로젝트 공개 범위, 지금 있는 API별 필요 범위)를 api-token.md 1-1절에 문서화했다. 새 API를 더할 때 이 표에 한 줄을 더하는 것을 완료 조건에 넣는다.
- **권장 이유**: 레거시를 즉시 없애면 이 토큰으로 v1.6 외부 API를 부르는 외부 스크립트와 도구가 깨진다. 이관해 유지하면 호환을 지키면서 권한 확인과 해시 저장을 얻는다. Classic은 Yona의 현재 API 면적(이슈, 게시글, 사용자)에 충분하고 Fine-grained는 REST(X-15, X-19)가 넓어진 뒤에 의미가 크다.
- **선생님 확인이 필요한 점**: [architecture/api-token.md](architecture/api-token.md)의 "결정 필요"에 정리했다.
- **상태**: 방향(모든 토큰이 권한 확인, D-20 대체), 레거시 토큰 유지, Fine-grained는 이번에 하지 않음은 확정(선생님 2026-10-29). 범위, 만료, 로그인 발급 API는 GitHub 기준으로 재조사해 권장안을 갱신했고 재확인 대기. 구현 전.

## 정책 결정

### P-01. v1.6을 그대로 따른다 (AGENTS.md)

- 기능, 동작, 요청·응답 계약, DB 테이블이 v1.6과 같아야 한다. 임의로 기능을 추가하거나 판단하지 않는다.
- v1.6의 결함은 같게 재현하고 [refactoring-backlog.md](refactoring-backlog.md)에 올린다. 개선은 선생님의 승인을 받은 뒤에만 한다.
- 구조가 달라지는 부분은 이유와 함께 위키에 기록한다.

### P-02. AGENTS.md는 저장소 루트의 전역 프롬프트다 (2026-10-22, 선생님)

- 내려받은 `AGENTS.md`를 저장소 루트에 두고, `CLAUDE.md`(`@AGENTS.md`)로 불러와 전역 지침으로 취급한다.

### P-03. 커밋은 주요 작업 단위로 하고 주석과 위키를 소홀히 하지 않는다 (2026-10-22, 선생님)

- 테스트 통과, 코드, 한글 주석(API 수준), 위키를 같은 단위에서 함께 갱신한 뒤 커밋한다. 푸시는 지시가 있을 때만 한다.

### P-04. 화면 캡처와 브라우저 검증은 Playwright로만 한다 (2026-10-22, 선생님)

- Claude in Chrome 확장 같은 다른 브라우저 도구는 쓰지 않는다. 검증은 작업 단위를 마칠 때 한 번만 하고 로그인 절차는 도우미로 재사용한다.
- **보충(2026-10-22, 선생님)**: v1.6 화면은 여러 문제로 캡처할 수 없다. 새로 만든 화면만 캡처한다. 이에 따라 v1.6과 나란히 비교하는 화면 검증 계획은 폐기하고, v1.6과의 일치는 템플릿 소스 대조와 테스트(DOM 구조, 문구, 링크)로 확인한다. 이 방식의 한계는 색상, 간격 같은 시각적 차이를 잡지 못한다는 점이며, CSS와 JS 자원을 v1.6에서 그대로 가져왔다는 사실이 이를 줄여 준다.

### P-05. R-03 승인 (2026-10-22, 선생님)

- 로그아웃 요청에 Referer가 없으면 v1.6은 오류가 나지만, v2는 홈으로 보낸다. 결함을 재현하지 않는 유일한 예외로 승인되었다.

### P-06. 결정은 위키에 근거와 함께 기록한다 (2026-10-22, 선생님)

- 기술 스택과 정책에 관한 결정은 반드시 이 파일에 남긴다. 권장안이 있었다면 권장 이유도 함께 적는다.
- 결정이 필요한 일은 구현에 앞서 선생님께 먼저 묻는다.

### P-07. 외부 API 작성자 대체, 권한 확인 순서, 댓글 상태 전환 (2026-10-26, 선생님)

v1.6과 v2의 불일치 점검에서 나온 세 항목에 대한 결정이다.

1. **`findAuthor`(외부 REST로 이슈, 게시글, 댓글을 가져올 때의 작성자)**: v1.6으로 되돌린다. 이메일로 사용자를 찾고 없으면 만들며, 만들 수 없으면 익명 사용자(번호 -1)가 작성자가 된다. 권장안과 같다. 이유: AGENTS.md가 v1.6 완전 재현을 원칙으로 하고, 이전에는 v2가 임의로 `400`을 돌려주었다. 구현: `ApiUsers.findOrCreateByEmail`, 테스트 `ExternalIssueApiTest`.
2. **`editIssue`, `deleteIssue`의 권한 확인 순서**: v2의 현재 동작을 유지하고 v1.6 결함을 [R-73](refactoring-backlog.md)에 올린다. 권장안과 같다. 이유: 권한 없는 사용자가 이슈를 옮기거나 삭제 알림을 보낼 수 있는 동작을 되살릴 이유가 없다.
3. **댓글의 `withStateTransition`**: v1.6으로 맞춘다. 하위 이슈를 댓글로 다시 열어도 닫힌 부모 이슈는 열지 않는다. 구현: `IssueService.toNextState(reopenParent = false)`, 테스트 `IssueCommentTest`.

### P-08. 점검 결과의 처리 기준 (2026-10-26, 선생님)

- 화면에서 닿는 불일치는 v1.6 동작으로 맞추고 TDD로 고친다(기본값 v1.6, 별도 결정 대기 없음). 권장안과 같다. 이유: AGENTS.md가 v1.6 완전 재현을 원칙으로 한다.
- v1.6이 오류를 내는 경우(500, NPE)는 v2의 현재 동작을 유지한다. 직접 만든 요청으로만 닿는 항목은 A-24에 따라 재현하지 않고 [hand-crafted-request-differences.md](architecture/hand-crafted-request-differences.md)에 근거를 남긴다.
- 이번에 v1.6에 맞춘 화면 항목: 비밀번호 재설정 메일 실패 안내, 멘션 후보 순서 두 곳, `attachLabel` category, `newWebhook` 오류 화면, `massUpdate` 삭제 알림, `referCommentId` 파생 이슈 댓글, 첨부 목록 403의 Content-Type.

### P-09. 실패 경로와 중복 행도 v1.6 상태를 유지한다 (2026-10-26, 선생님)

- R-74(`changeVCS` 실패 시 README 해제와 포크 분리가 남는 중간 상태), R-76(`accept`의 병합 중 표시 고착), R-82(REST 프로젝트 생성의 SITEMANAGER 행 2개)는 v1.6 상태를 그대로 유지한다. 권장안은 v2의 롤백과 1행이었으나 선생님이 v1.6 재현을 택하셨다. 구현: `ProjectVcsService`와 `PullRequestWorkflow.accept`, `PullRequestActionController.accept`에서 트랜잭션을 제거하고, `ExternalProjectService.create`가 SITEMANAGER 행을 두 번 넣는다.
- 5차 검증에서 나온 v1.6 결함 후보 전체는 [v16-defect-catalog.md](architecture/v16-defect-catalog.md)에 항목별로 기록한다. 가볍게 지나가지 않도록 후보마다 v1.6 소스 줄, v2 상태, 기록 위치를 남긴다.

### P-10. v1.6 위키 9~11차 갱신분 대조의 처리 (2026-10-26, 선생님)

v1.6 위키가 9차(Antigravity CLI 판정), 10차(소스 재검증), 11차(재확인)로 크게 바뀌어 GitHub의 위키로 로컬을 갱신하고, 바뀐 127개 페이지를 v2 소스와 대조하라고 하셨다. 처리 기준은 P-08과 같다(화면과 정상 호출로 닿는 불일치는 v1.6에 맞추고, v1.6의 오류는 v2 유지, 직접 만든 요청은 기록만).

- 대조는 에이전트 18개가 후보를 냈고, 후보마다 다른 에이전트가 v1.6과 v2 소스를 다시 읽어 확정했다. 확정된 항목을 고쳤고(두 결정 대기 항목은 선생님이 v1.6으로 정하셔서 이어서 고쳤다) 결과는 [v16-sync-9-11.md](architecture/v16-sync-9-11.md)에 있다.
- **결정 1: Git/SVN Basic 인증의 세션 (선생님이 v1.6으로 정하심).** 자격이 맞으면 사용자를 세션에 로그인시켜 세션 쿠키를 심고, 틀리거나 없으면 세션, 토큰, 로그인 유지 쿠키 사용자로 되돌아간다. 쿠키가 없는 git 요청마다 서버 세션이 하나씩 생기는 비용은 감수한다. 구현: `BasicAuthResolver`, 테스트 `GitHttpTest`.
- **결정 2: 가져오기 API의 `createdAt`, `updatedAt` 생략 (선생님이 v1.6으로 정하심).** 이슈, 게시글, 게시글 댓글은 시각을 비운 채(NULL) 저장한다. 이슈 댓글은 v1.6도 현재 시각이므로 그대로다. NULL이어도 이슈와 게시글 화면은 오류 없이 그려진다(`ExternalIssueApiTest`, `ExternalBoardApiTest`). v1.6 화면이 NULL에서 오류를 내는지는 확정하지 못했고, 내더라도 v2는 오류 없이 그린다.
- **결정 3: 내부 서술 검증에서 나온 불일치도 v1.6으로 맞춘다 (선생님, 2026-10-27).** JGit, Tika 같은 라이브러리는 수정하지 않고 우리 코드에서 동작만 v1.6에 맞춘다(예: 이진 파일 판정, 파일의 최근 커밋 선택, `HistogramDiff` 결과). v1.6의 오류(500/NPE)는 v2가 오류 없이 처리하는 쪽을 유지한다(P-08). 권장안과 같다. 이유: AGENTS.md가 v1.6 완전 재현을 원칙으로 하고, 라이브러리 수정은 유지보수 부담이 크다.
- **결정 4: 포크 저장소는 v1.6 방식으로 만든다 (선생님, 2026-10-27).** v1.6은 `Repository.create()`(`create(false)`, 비-bare)로 포크를 만든다. v2의 `create(true)`를 v1.6 방식으로 바꾼다. 권장안은 화면 영향이 없어 v2 유지였으나 선생님이 v1.6 재현을 택하셨다.
- **결정 5: 데이터 가져오기는 v1.6의 `TRUNCATE` 의미를 따른다 (선생님, 2026-10-27).** 테이블 이름이 맞으면 먼저 비워 즉시 확정하고, 값이 배열이 아니면 테이블만 비워지며, 행을 넣다 실패하면 넣은 행만 되돌려 테이블은 빈 채로 남는다. 권장안은 실패 시 이전 데이터를 복구하는 v2 동작 유지였다(가져오기 실패로 데이터가 사라지는 것을 막기 위해). 선생님이 v1.6 재현을 택하셨다. 구현: `DataService.truncate`, 테스트 `SiteDataTest`.
- **결정 6: 문자 집합 감지기는 juniversalchardet 1.0.3으로 고정한다 (선생님, 2026-10-27).** v1.6과 같은 아티팩트(`com.googlecode.juniversalchardet:juniversalchardet:1.0.3`)로 되돌려 Big5, 태국어 등 감지 모델 차이를 없앤다. 권장안과 같다. 이유: 모델 차이는 코드로 되돌릴 수 없다. 오래된 라이브러리라 보안 점검 대상이다(A-112).
- **결정 7: 127쪽 전수 대조는 모든 수정이 끝난 뒤 한 번 수행한다 (선생님과 협의, 2026-10-27).** 줄 단위 장부와 스크립트 검증으로 빠짐없이 확인한다.
- **결정 8(확정: v1.6 유지, 2026-10-27, 선생님): 외부 API 작성자 조회는 사용자를 만들지 않는다 (에이전트가 v1.6 소스로 정정했고 선생님이 그대로 두기로 하셨다).** P-07.1은 "이메일로 사용자를 찾고 없으면 만든다"를 v1.6 동작으로 보고 정했으나, v1.6 `User.findByEmail`은 사용자가 없으면 `null`이 아니라 `NullUser`를 돌려주어 `IssueApi.findAuthor`의 `createUserNode` 분기에 닿을 수 없다. 그래서 v1.6은 모르는 이메일의 작성자를 익명 사용자(번호 -1)로 저장한다. 선생님이 정하신 "v1.6대로"를 따라 `ApiUsers.findAuthor`로 바꾸고, 이메일 조회는 대표, 보조, 대소문자 무시의 3단계(`UserLookup`)를 쓴다. 담당자와 구성원 조회도 같다. 사용자를 만드는 이전 동작이 필요하면 선생님이 다시 정해 주셔야 한다.
- **결정 9(확정: v1.6 유지, 2026-10-27, 선생님. 구현은 A-127): 세션 사용자의 권한 판정 캐시.** v1.6은 세션 사용자 인스턴스가 요청을 넘어 재사용되어 사이트 관리자 여부, 프로젝트 매니저 여부, 조직 소속 판정이 로그인 동안 남는다. 승격이나 해임 뒤에도 이미 판정한 곳에서는 이전 결과가 유지된다. v2는 매번 새로 조회한다. 같게 하려면 세션에 판정 캐시를 두어야 하는데 설계가 필요하고 보안상 불리하다. 권장: 재현하지 않는다(즉시 반영이 더 안전하다). 선생님 결정을 기다린다.
- **결정 10(확정: v1.6 유지, 2026-10-27, 선생님. 구현은 A-128): 잠긴 사용자의 로그인 유지 쿠키.** v1.6은 `yobi.token` 쿠키 사용자가 잠겨 있어도 계속 로그인 상태이고 v2는 쿠키를 지워 익명으로 만든다. Basic 인증은 삭제된 계정도 통과한다(A-122). 권장: 재현하지 않는다. 선생님 결정을 기다린다.
