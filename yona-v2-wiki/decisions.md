# 결정 기록

기술 스택과 정책에 관한 모든 결정을 여기에 시간순으로 남긴다. **누가 무엇을 언제 결정했는지, 선택지는 무엇이었는지, 권장안이 있었다면 왜 그것을 권했는지**를 추적할 수 있어야 한다. 새 결정이 생기면 이 파일에 먼저 항목을 추가하고, 요약은 [architecture/technology-decisions.md](architecture/technology-decisions.md)에 반영한다.

## 읽는 법

| 칸 | 뜻 |
|---|---|
| 결정자 | **선생님**: 선생님이 정하셨다. **합의**: 제가 제안하고 선생님이 확정하셨다. **에이전트**: 제가 구현 중에 정했고 선생님의 확인을 기다린다(맨 아래 표) |
| 권장안 | 제가 권했던 선택지. 선생님이 다른 안을 고르셨으면 그 사실도 적는다 |
| 상태 | 확정, 변경됨, 확인 대기 |

## 결정 목록

### D-01. Spring Boot 버전 (2026-10-22)

- **질문**: `AGENTS.md`의 "Spring Framework 3.5"를 어떻게 해석할 것인가.
- **처음 판단(에이전트)**: Spring Boot 3.5.16으로 해석했다. 이유는 `Spring Framework 3.5`가 존재하지 않는 버전이라 Boot 3.5의 오기로 보았기 때문이다.
- **결정(선생님)**: "스프링 부트 4로 올려서 진행". Spring Boot 4.1.1(Spring Framework 7, Hibernate 7)로 상향했다.
- **상태**: 확정.

### D-02. 쿼리 계층 (2026-10-22)

- **선택지**: (a) Spring Data JPA + Criteria(Specification), (b) Spring Data JPA + QueryDSL, (c) Spring Data JPA + jOOQ.
- **권장안**: (a).
- **권장 이유**: 코드 생성이 필요 없고 JPA 표준만 쓴다. DB별 SQL 생성을 Hibernate 방언에 맡기므로 이식성이 가장 높다(Cubrid는 `hibernate-community-dialects`). Boot 4와 Hibernate 7에서 호환 문제가 없다. (b)는 Kotlin에서 KSP 코드 생성이 필요하고 Hibernate 7 지원이 불안정하다. (c)는 JPA와 이중 모델이 되어 복잡해진다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-03. 스키마 관리 방식 (2026-10-22)

- **선택지**: (a) Hibernate 생성(`ddl-auto`) 유지 + v1.6 기준 스키마 대조 테스트, (b) Liquibase, (c) Flyway + DB별 SQL.
- **권장안**: (a).
- **권장 이유**: 엔티티가 유일한 원천이라 DB마다 SQL을 따로 유지하지 않아도 된다. 구조 보증은 대조 테스트가 맡는다. Cubrid는 Liquibase, Flyway의 공식 지원 목록에 없다. 단점은 운영 DB의 변경 이관 도구가 없다는 점이며, 릴리즈 전이라 감수한다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정. 운영 이관이 필요해지는 시점에 다시 논의한다.

### D-04. 스키마와 통합 테스트를 검증할 DB 범위 (2026-10-22)

- **선택지**: (a) H2 + PostgreSQL + MariaDB, (b) 위 3종 + MySQL, (c) 6종 전부(Cubrid, MSSQL 포함).
- **권장안**: (a).
- **권장 이유**: 선생님이 처음 말씀하신 범위와 같다. MySQL, Cubrid, MSSQL은 컨테이너 이미지와 드라이버 준비 비용이 크고 실행 시간이 길어진다.
- **결정(선생님)**: (a)로 하되 "test container와 docker compose로 상시 띄워놓고 테스트"하자고 하셨다.
- **반영(에이전트)**: PostgreSQL, MariaDB 테스트 컨테이너는 Testcontainers `reuse` 모드로 띄워 테스트가 끝나도 내리지 않는다. `docker-compose.yml`은 개발 중 앱 실행용으로 따로 둔다. 두 가지를 분리한 이유는 테스트 컨테이너는 스키마를 만들고 지우는 반면, 개발용 컨테이너는 데이터를 보존해야 하기 때문이다.
- **상태**: 확정. 이 반영 방식(두 컨테이너 분리)은 선생님의 확인을 받지 않았다.

### D-05. 테스트 라이브러리 (2026-10-22)

- **선택지**: (a) JUnit 5 + MockK + Testcontainers, (b) Kotest + MockK + Testcontainers.
- **권장안**: (a).
- **권장 이유**: Spring Boot 기본 조합이라 추가 의존성이 적다. Kotest는 Boot 4와의 호환 확인이 추가로 필요하다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정. (MockK는 아직 쓰지 않았다.)

### D-06. 뷰 템플릿 엔진 (2026-10-22)

- **처음 판단(에이전트)**: v1.6 화면을 최대한 같게 재현하려고 Thymeleaf로 가정하고 선생님께 이의가 있으면 알려 달라고 했다.
- **결정(선생님)**: "템플릿은 타임리프로 확정".
- **상태**: 확정.

### D-07. enum 컬럼의 DB 제약 (2026-10-22)

- **계기**: 선생님이 "v1.6에서 enum 필드의 값이 프로그램에서 자유롭게 입력되는 값인지 아닌지에 따라 DB에 enum 타입을 둘지 말지가 결정될 것"이라고 물으셨다.
- **조사(에이전트)**: v1.6의 enum 값은 `State.getValue`, `ResourceType.getValue`, `UserState.of` 등으로 변환한 닫힌 집합이며 자유 입력이 아니다. 그런데도 v1.6은 `1.sql`의 `CHECK` 제약을 `20.sql`에서 21개 모두 제거했다. 새 enum 값을 추가할 때마다 DB를 고치지 않기 위해서다.
- **선택지**: (a) 제약 없이 문자열/정수로 저장(v1.6 최종 스키마와 같음), (b) `CHECK` 제약 유지, (c) DB 고유 `ENUM` 타입.
- **권장안**: (a).
- **권장 이유**: 테이블 구조를 v1.6과 같게 유지하라는 원칙과 맞는다. DB 고유 `ENUM`은 PostgreSQL(`CREATE TYPE`), MSSQL, Cubrid에서 방식이 달라 이식성이 낮다. `ddl-auto=update`는 이미 만든 `CHECK`를 갱신하지 않아 새 enum 값을 저장할 때 오류가 난다.
- **결정(선생님)**: "일단은 지금 결정 유지" = (a).
- **상태**: 확정. DB에서도 값을 강제하려면 v1.6과 달라지는 결정이므로 선생님의 승인이 필요하다.

### D-08. LESS 빌드 (2026-10-22)

- **계기**: v1.6이 CSS를 sbt 빌드 때 LESS에서 만든다는 사실을 구현 중 발견했다.
- **선택지**: (a) Gradle 빌드에서 `lessc`(Less 1.7.5) 실행, (b) 한 번 컴파일한 CSS를 저장소에 포함, (c) JVM 전용 less4j.
- **권장안**: (a).
- **권장 이유**: v1.6과 같은 방식(빌드 시점 생성)이라 소스와 결과가 어긋나지 않는다. (b)는 LESS를 고칠 때마다 다시 컴파일해 커밋해야 한다. (c)는 Less 1.x 문법 일부만 지원해 결과가 달라질 위험이 있다. 단점은 빌드 환경에 Node와 npm이 필요하다는 점이다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-09. 보안 기반 (2026-10-22)

- **선택지**: (a) Spring Security 필터 체인(모든 URL 허용, 인가는 애플리케이션 계층), (b) 자체 필터 + HttpSession.
- **권장안**: (a).
- **권장 이유**: 세션 고정 방어와 보안 헤더 같은 검증된 기능을 직접 책임지지 않아도 된다. v1.6은 인가를 컨트롤러에서 하므로 URL 규칙은 모두 허용하면 같은 구조가 유지된다. 단점은 v1.6 요청 계약을 지키려면 CSRF를 꺼야 한다는 점이다(결함 R-02).
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-10. 레이아웃 감싸기 방식 (2026-10-22)

- **선택지**: (a) Thymeleaf 기본 프래그먼트(`th:replace`에 본문을 인자로 전달), (b) thymeleaf-layout-dialect.

- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

### D-11. 템플릿 이식 방식 (2026-10-22)

### D-12. 구현 순서 (2026-10-22)

- **제안(에이전트)**: 홈 소개 -> AccessControl과 프로젝트·조직 -> 이슈·게시판·마일스톤 -> 알림과 로그인 사용자용 홈 -> 코드 저장소와 풀 리퀘스트.
- **이유**: 홈의 알림 목록은 이슈, 마일스톤, 풀 리퀘스트, 코드 리뷰 등 거의 모든 도메인에 의존하므로 알림을 뒤로 미루는 것이 의존 방향에 맞다.
- **결정(선생님)**: "의존 방향 순으로 진행. 단, 결정이 필요하면 물어보도록."
- **상태**: 확정. 진행 상태는 [roadmap.md](roadmap.md).

### D-13. VCS 지원 범위 (2026-10-22)

- **선택지**: (a) Git(JGit) 먼저, SVN(SVNKit)은 마지막, (b) 둘을 함께, (c) Git만.
- **권장안**: (a).
- **권장 이유**: 프로젝트 생성이 저장소 디렉터리 생성에 의존하므로 범위를 먼저 정해야 한다. (a)는 Git을 완성한 뒤 SVN을 더하므로 작업량이 단계마다 불어나지 않는다. `project.vcs` 필드는 처음부터 두 값을 모두 담는다. (c)는 v1.6과 기능이 달라지므로 명시 승인이 필요한 선택이다.
- **결정(선생님)**: (a) 권장안 채택.
- **상태**: 확정.

- **결정(선생님)**: (a) 권장안 채택.

## 정책 결정

### P-01. v1.6을 그대로 따른다 (AGENTS.md)

- 기능, 동작, 요청·응답 계약, DB 테이블이 v1.6과 같아야 한다. 임의로 기능을 추가하거나 판단하지 않는다.
- v1.6의 결함은 같게 재현하고 [refactoring-backlog.md](refactoring-backlog.md)에 올린다. 개선은 선생님의 승인을 받은 뒤에만 한다.
- 구조가 달라지는 부분은 이유와 함께 위키에 기록한다.

### P-02. AGENTS.md는 저장소 루트의 전역 프롬프트다 (2026-10-22, 선생님)

- 내려받은 `AGENTS.md`를 저장소 루트에 두고, `CLAUDE.md`(`@AGENTS.md`)로 불러와 전역 지침으로 취급한다.

### P-03. 커밋은 주요 작업 단위로 하고 주석과 위키를 소홀히 하지 않는다 (2026-10-22, 선생님)

- 테스트 통과, 코드, 한글 주석(API 수준), 위키를 같은 단위에서 함께 갱신한 뒤 커밋한다. 푸시는 지시가 있을 때만 한다.

### P-04. 화면 캡처와 브라우저 검증은 Playwright로만 한다 (2026-10-22, 선생님)

- Claude in Chrome 확장 같은 다른 브라우저 도구는 쓰지 않는다. 검증은 작업 단위를 마칠 때 한 번만 하고 로그인 절차는 도우미로 재사용한다.
- **보충(2026-10-22, 선생님)**: v1.6 화면은 여러 문제로 캡처할 수 없다. 새로 만든 화면만 캡처한다. 이에 따라 v1.6과 나란히 비교하는 화면 검증 계획은 폐기하고, v1.6과의 일치는 템플릿 소스 대조와 테스트(DOM 구조, 문구, 링크)로 확인한다. 이 방식의 한계는 색상, 간격 같은 시각적 차이를 잡지 못한다는 점이며, CSS와 JS 자원을 v1.6에서 그대로 가져왔다는 사실이 이를 줄여 준다.

### P-05. R-03 승인 (2026-10-22, 선생님)

- 로그아웃 요청에 Referer가 없으면 v1.6은 오류가 나지만, v2는 홈으로 보낸다. 결함을 재현하지 않는 유일한 예외로 승인되었다.

### P-06. 결정은 위키에 근거와 함께 기록한다 (2026-10-22, 선생님)

- 기술 스택과 정책에 관한 결정은 반드시 이 파일에 남긴다. 권장안이 있었다면 권장 이유도 함께 적는다.
- 결정이 필요한 일은 구현에 앞서 선생님께 먼저 묻는다.

## 에이전트가 단독으로 정한 구현 판단 (확인 대기)

선생님께 묻지 않고 구현 중에 제가 정한 것들이다. 되돌릴 수 있는 크기로 정했지만 선생님이 보시면 바꾸고 싶은 것이 있을 수 있어 모아 둔다. 바꾸라고 하시면 바로 반영한다.

| ID | 판단 | 이유 | 대안과 영향 |
|---|---|---|---|
