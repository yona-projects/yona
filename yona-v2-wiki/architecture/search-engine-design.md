# 이슈 검색 개선과 검색 엔진 선택 구조 (제안)

**상태: 제안이다. 구현하지 않았다.** v1.6에 없던 기능이라 D-28의 "추가 개발 항목"으로 선생님의 결정이 필요하다. 로드맵은 X-56부터 X-61이다.

GitHub 이슈 #843("이슈 본문·댓글 전문 검색, 기본은 DB 검색, Lucene·OpenSearch는 선택")을 검토한 결과를 독립적으로 진행할 수 있는 항목으로 나눠 남긴다.

## 1. 이슈가 가리키는 검색은 어디인가

이슈의 대상은 **이슈의 제목, 본문, 댓글 검색**이다(게시글, PR, 위키는 후속, 코드와 첨부 파일 내용은 제외). 이 프로그램에서 이슈를 검색하는 곳은 두 계통이고, 이슈가 지적한 "위치마다 범위가 다르다"는 이 두 계통의 차이이다. 코드로 확인했다.

| 계통 | 서비스 | 진입점 | 이슈를 찾는 범위 |
|---|---|---|---|
| **통합 검색** | `SearchService` | 웹 `/search`, `/organizations/{조직}/search`, `/{소유자}/{프로젝트}/search`. REST `/-_-api/v1/search`, `/orgs/{조직}/search`, `/owners/.../search` | 이슈(`ISSUE`)는 **제목과 본문**. 댓글은 별도 결과 유형(`ISSUE_COMMENT`)으로만 찾는다 |
| **이슈 목록 필터** | `IssueSearchService` | 웹 프로젝트 이슈 목록 `/{소유자}/{프로젝트}/issues`, 내 이슈 `/user/issues`, 조직 이슈 목록 `/organizations/{조직}/issues`. REST `GET .../projects/{프로젝트}/issues?q=` | **제목, 본문, 댓글**을 함께 보고 상태, 담당자, 라벨, 마일스톤 필터와 조합 |

- 이슈의 "통합 검색은 제목·본문만 본다"는 정확히는 이슈 결과 유형에 대한 말이다. 댓글은 다른 결과 유형으로 따로 나온다.
- 이슈가 제안한 기능 중 "상태, 담당자, 라벨, 마일스톤, 프로젝트 필터와 조합"은 **이슈 목록 필터 쪽**에, "관련도순, 스니펫, 댓글 일치 시 해당 댓글로 이동"은 **통합 검색 결과 쪽**에 해당한다. 그래서 제안은 두 계통을 모두 건드리고 "웹과 REST에 같은 동작"을 요구한다.
- 현재 비교 방식은 두 계통 모두 검색어 전체를 `%검색어%` 하나로 비교하는 `LIKE`이다(`LikeEscape.contains`). 그래서 본문에 `로그인 처리 중 인증 오류`가 있어도 `로그인 오류`로는 찾지 못한다. v1.6도 같았다(구문 전체 `LIKE`).

## 2. 항목을 나눈 이유

이슈는 한 번에 많은 것을 담았다(검색 구조, Lucene, OpenSearch, 머리말 필터, 스니펫, 색인 운영). 아래 순서로 나누면 앞의 것이 뒤의 것에 의존하지 않고, 앞에서 문제가 풀리면 뒤는 하지 않아도 된다.

| 로드맵 | 내용 | 의존 | 새 인프라 |
|---|---|---|---|
| X-56 | 검색 범위 통일과 **단어 AND 검색(DB)** | 없음 | 없음 |
| X-57 | 제목 머리말 `titleHead` 필터와 `LikeEscape`의 `[` 이스케이프 | 없음 | 없음 |
| X-58 | **쓰기 이음새**(아웃박스) | 없음 | 표 하나 |
| X-59 | 검색 엔진 어댑터 구조(`yona.search.backend`) | X-58 | 없음 |
| X-60 | 내장 Lucene(선택) | X-58, X-59 | Lucene, Nori |
| X-61 | OpenSearch와 Elasticsearch 어댑터(선택) | X-58, X-59 | 외부 서버 |

**X-60은 X-56으로 부족하다는 수치가 나올 때 한다.** 이슈 제안자의 PoC는 LIKE 17.79%, Lucene 95.78%(최초 표본 1,731건)를 보였는데, 이 LIKE는 구문 전체 비교이다. 이슈의 문제를 가장 싸게 푸는 단어 AND `LIKE`와의 비교가 없고, 전체 57.79% 대 97.83%에는 두 방식이 모두 100%인 항목이 섞여 차이가 희석된다. 단어 AND와 Lucene을 같은 표본으로 비교한 수치를 먼저 받는다.

### X-57의 `LikeEscape` 문제
`LikeEscape.escape`는 `\`, `%`, `_`만 이스케이프한다. SQL Server의 `LIKE`는 `[`를 문자 클래스의 시작으로 읽으므로 머리말 `[Bug]`로 검색하면 의도와 다른 결과가 나올 가능성이 크다. 코드를 읽은 판단이고 MSSQL에서 실행해 확인하지는 않았다. 시험 전에 MSSQL에서 먼저 재현해야 한다.

## 3. 쓰기 이음새 (X-58)

선생님 의견(2026-11-17): **색인을 제대로 쓰려면 실제 DB에 쓰는 부분에 인터페이스를 두어야 한다.** 엔진 후보가 많기(Lucene, Solr, Elasticsearch, OpenSearch, Meilisearch) 때문에 엔진과 무관한 쓰기 이음새가 먼저이다.

### 왜 JPA 콜백만으로는 부족한가
이슈와 댓글은 서비스 계층의 저장소 호출(`issues.save` 계열 약 12곳)로 쓰이지만, 아래 경로는 JPA 저장 이벤트를 거치지 않는다.

- `ProjectDeletionService`: 프로젝트를 지울 때 `delete from IssueComment c where ... in :ids` 같은 JPQL과 네이티브 쿼리로 이슈와 댓글을 한꺼번에 지운다.
- `IssueMassUpdateService`(일괄 수정), `ProjectTransferService`(프로젝트 이동).
- `DataService`(JDBC 일괄 적재로 가져오기), v1.6 데이터 이관.

엔티티 콜백만 걸면 이 경로에서 색인이 조용히 어긋나고, 이슈가 말한 "삭제된 내용이 재시도로 되살아나지 않게"가 깨진다.

### 구조
1. **아웃박스**: 같은 트랜잭션에서 `종류(이슈, 댓글), 번호, 프로젝트, 동작(생성, 수정, 삭제, 이동, 프로젝트 삭제), 시각`만 적는다. 문서 내용은 적지 않는다.
2. **반영 작업**: 아웃박스를 읽어 그 시점에 DB에서 **최신 내용을 읽어** 문서를 만들어 엔진에 반영한다. 그래서 오래된 내용이 되살아나지 않고 엔진 장애가 이슈 작성을 막지 않으며 롤백된 쓰기가 색인에 남지 않는다.
3. **개별 엔티티 경로**는 Hibernate 이벤트 리스너 한 곳에서 잡아(캐스케이드 포함) 아웃박스에 쓰고, **일괄 경로**는 이음새를 명시적으로 부른다.
4. **전체 재색인과 대조 작업**: DB가 원본이고 인덱스는 언제든 다시 만들 수 있는 파생 데이터이다. 놓친 쓰기가 있어도 복구된다.
5. 기본 구현(`backend=db`)은 아무 일도 하지 않는다. 기존 설치에는 표 하나 외에 부담이 없다.

착수 첫 단계는 **쓰기 경로 지도**를 만드는 것이다(이슈, 댓글, 게시글, PR 전부). 지금의 12곳은 `save` 호출을 세어 본 대략치이다.

이 이음새는 검색 엔진을 끝내 도입하지 않아도 알림, 웹훅, 감사 기록(서비스마다 흩어진 `ApplicationEventPublisher`)을 정리하는 데 쓸 수 있다.

## 4. 엔진 어댑터 (X-59 이후)

- 어댑터가 할 일은 `색인하기, 지우기, 검색하기`뿐이다. 엔진마다 다른 점(Lucene은 프로세스 안, Elasticsearch, OpenSearch, Solr은 외부 서버라 네트워크, 인증, 일괄 API, 반영 지연이 있음)은 어댑터 안에 가둔다.
- **권한 재확인, 필터, 결과 모양은 엔진 위의 공통 계층**에 두고, 비공개 이슈의 제목, 스니펫, 건수가 새지 않도록 조회 시점의 권한으로 결과를 다시 거른다. 엔진이 달라져도 같은 시험으로 검증한다.
- 가장 까다로운 곳은 쓰기가 아니라 **검색 쪽**(검색어와 필터, 정렬을 엔진 문법으로 바꾸기)과 **한국어 분석**이다(Lucene, Elasticsearch, OpenSearch, Solr은 Nori로 가능, Meilisearch는 약함). 공통 질의 모델은 구현하는 엔진에 맞춰 만들고 두 번째 엔진을 붙일 때 일반화한다.
- 지원 범위: DB(기본), 내장 Lucene, OpenSearch와 Elasticsearch(API가 거의 같아 어댑터 하나). Solr는 API가 달라 요청이 있을 때 외부 기여로 받는다. "전부 지원"을 목표로 하지 않는다.

## 5. 운영과 검증 (이슈의 요구를 그대로 가져옴)

- 초기 색인이 끝난 뒤에 전문 검색을 켜고 재색인의 진행과 실패를 관리 화면에서 본다.
- 엔진 장애 때 DB 검색으로 전환할지는 논의가 필요하다. 전환한다면 화면에 표시한다.
- 검증: 익명화한 실제 이슈 문장으로 방식 비교(떨어진 단어, 조사와 띄어쓰기, 복합명사, 영문 오류 메시지와 식별자), 머리말 필터(본문과 댓글에만 `[머리말]`이 있는 이슈 제외, 연속 머리말, 기존 `filter=[xxx]` URL), 6종 DB(MariaDB, PostgreSQL, MySQL, SQL Server, CUBRID, H2)에서 기존 검색 회귀, 대표 규모의 색인 시간, 검색 지연, 메모리와 디스크 측정.

## 6. 결정이 필요한 것

1. 이 개선을 D-28의 추가 개발 항목으로 받을지, 받는다면 X-56부터 X-61의 순서.
2. 이슈 제안자에게 단어 AND `LIKE`와 Lucene의 같은 표본 비교를 요청할지.
3. 쓰기 이음새(X-58)를 검색과 별개로 먼저 진행할지.

이 문서를 쓰는 시점에 GitHub 이슈에는 아무것도 쓰지 않았다.
