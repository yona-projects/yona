# 개인용 API 토큰 설계 (X-5, D-36)

**상태: 설계 제안, 확인 대기, 구현 전.** 결정과 이유는 [decisions.md D-36](../decisions.md)이다.

## 현황

| 항목 | v1.6, v2 현재 |
|---|---|
| 저장 | `n4user.token`(사용자당 하나, 평문). 값은 시각의 SHA-256 Base64 |
| 사용 | `Authorization: token <값>`(`UserApi`), 설정 화면의 "토큰 다시 만들기"(`UserApp.editToken`) |
| 발급 | `POST /-_-api/v1/users/token`(로그인 정보를 보내면 `access_token`) |
| 범위 | 없음(전체). 만료 없음 |
| 권한 | 토큰 경로는 프로젝트 권한을 확인하지 않는다(D-20, **D-36으로 대체 예정**) |
| 쓰는 곳 | 외부 API(`/-_-api/v1/**`)를 부르는 외부 스크립트와 도구. 이전(Migration) 화면의 `token`은 GitHub OAuth 토큰이라 Yona 사용자 토큰과 무관하고, 이전 화면이 부르는 이슈, 게시글 가져오기 API는 세션 로그인을 쓴다 |

## GitHub과의 대응

| | Classic | Fine-grained | Yona 현재 토큰 |
|---|---|---|---|
| 범위 | 계정 전체에 걸친 범위(`repo` 등) | 저장소 선택과 항목별 읽기/쓰기 | 없음(전체) |
| 만료 | 선택 | 필수 | 없음 |
| 저장 | 해시 | 해시 | 평문 |

Yona의 현재 토큰은 범위 없이 전부 허용하는 Classic에 가장 가깝다.

## 제안

### 1. 범위 (GitHub 기준으로 재조사, 2026-10-29)

GitHub 공식 문서([OAuth 앱의 범위](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps))의 Classic 범위는 자원별 읽기/쓰기 쌍이 아니라 **굵은 묶음**이다. `repo` 하나가 코드, 이슈, 풀 리퀘스트, 웹훅까지 비공개 저장소 전체를 준다. 항목별 분리는 Fine-grained의 몫이다. 처음 제안한 `read:issue`, `write:issue` 같은 자원별 쌍은 GitHub에 없으므로 접고 GitHub 범위를 Yona에 대응시킨다.

| GitHub 범위 | 뜻(GitHub) | Yona 대응 |
|---|---|---|
| (범위 없음) | 공개 정보 읽기 | 공개 프로젝트와 프로필 읽기 |
| `repo` | 공개와 비공개 저장소 전체 권한(코드, 이슈, 풀 리퀘스트, 웹훅 포함) | 사용자가 접근할 수 있는 **모든 프로젝트**의 코드, 이슈, 풀 리퀘스트, 게시글, 마일스톤, 라벨, 웹훅 |
| `public_repo` | 공개 저장소만 | **공개 프로젝트**만 |
| `admin:repo_hook`, `write:repo_hook`, `read:repo_hook` | 저장소 웹훅 관리, 쓰기, 읽기(`repo`가 이미 포함) | 프로젝트 웹훅만 제한해서 줄 때 |
| `read:org`, `write:org`, `admin:org` | 조직 구성원, 프로젝트 읽기, 쓰기, 전체 관리 | 조직 정보, 구성원, 조직 설정 |
| `user`(`read:user`, `user:email`을 포함) | 프로필 읽기와 쓰기 | 프로필, 내 이슈 목록, 통계, 이메일 |
| `notifications` | 알림 읽기와 읽음 처리 | 알림 API(예약. 알림 REST가 생길 때) |
| `delete_repo` | 저장소 삭제 | 프로젝트 삭제 API(예약) |
| `admin:public_key`, `admin:gpg_key` 계열 | 공개키 관리 | SSH 키(X-3)와 GPG 키(X-4)가 생길 때(예약) |
| `workflow` | Actions 워크플로 파일 | CI/Actions(X-25)가 생길 때(예약) |
| `site_admin` | 엔터프라이즈 사이트 관리 | 사이트 관리자 API(`/-_-api/v1/admin/**`). 사이트 관리자만 고를 수 있다 |

묶음 규칙은 GitHub과 같다. `user`는 `read:user`와 `user:email`을 포함하고, `admin:org`는 `write:org`와 `read:org`를, `repo`는 프로젝트 웹훅 권한을 포함한다(문서가 계층을 명시하지 않은 계열은 `admin`이 `write`, `read`를 포함하는 것으로 둔다). 전체(`*`)는 **레거시 토큰만** 가진다.

**장단점**: GitHub 방식은 단순하지만 이슈 자동화처럼 일부 권한만 필요한 토큰도 `repo`(코드 쓰기 포함)를 받아야 한다. 그 분리는 Fine-grained(X-5b)가 한다. 자원별 분리를 Classic에서 미리 하려면 GitHub에 없는 범위를 만들어야 해서 권장하지 않는다.

### 1-1. 대응표: GitHub 범위를 Yona 안에서 어떻게 해석하는가

**기본 규칙**

- 토큰으로 할 수 있는 일 = **범위가 허용하는 일 ∧ 토큰 주인의 실제 권한**이다(D-36). 범위는 권한을 더하지 못하고 줄이기만 한다.
- 범위 없는 토큰은 공개 프로젝트와 공개 프로필 읽기만 한다(GitHub의 "범위 없음"과 같다).
- Yona의 프로젝트 공개 범위는 `PUBLIC`, `PROTECTED`, `PRIVATE` 셋이다(GitHub은 공개와 비공개 둘). `public_repo`는 **`PUBLIC` 프로젝트만**이고 `PROTECTED`와 `PRIVATE`는 `repo`가 필요하다.
- 연산은 Yona 권한 모델의 `Operation`(`READ`, `UPDATE`, `DELETE`, `ACCEPT`(병합), `REOPEN`, `CLOSE`, `WATCH`, `LEAVE`, `ASSIGN_ISSUE`)과 만들기 권한(`isProjectResourceCreatable`)을 그대로 쓴다. 토큰은 새 연산을 만들지 않는다.

**범위별 허용 범위**

| 범위 | 허용하는 자원(`ResourceType`) | 연산 | 프로젝트 공개 범위 |
|---|---|---|---|
| (없음) | 공개 프로젝트와 공개 프로필 | `READ` | `PUBLIC` |
| `public_repo` | `PROJECT`, `CODE`, `COMMIT`, `ISSUE_*`, `ISSUE_COMMENT`, `ISSUE_LABEL*`, `LABEL`, `MILESTONE`, `BOARD_*`, `NONISSUE_COMMENT`, `PULL_REQUEST`, `REVIEW_COMMENT`, `COMMENT_THREAD`, `COMMIT_COMMENT`, `ATTACHMENT`, `WEBHOOK`, `WIKI_PAGE` | 사용자에게 허용된 모든 연산 | `PUBLIC`만 |
| `repo` | 위와 같음 | 사용자에게 허용된 모든 연산 | `PUBLIC`, `PROTECTED`, `PRIVATE` |
| `read:repo_hook` | `WEBHOOK` | `READ` | `repo`나 `public_repo`가 이미 포함하므로 웹훅만 줄 때 |
| `write:repo_hook` | `WEBHOOK` | `READ`, 만들기, `UPDATE` | 위와 같음 |
| `admin:repo_hook` | `WEBHOOK` | `READ`, 만들기, `UPDATE`, `DELETE` | 위와 같음 |
| `read:org` | `ORGANIZATION` | `READ`(정보, 구성원, 조직 프로젝트 목록) | 조직 공개 범위를 따른다 |
| `write:org` | `ORGANIZATION` | `READ`, 구성원 가입 요청 처리, 조직 프로젝트 만들기 | 위와 같음 |
| `admin:org` | `ORGANIZATION` | `read:org`, `write:org`에 더해 `UPDATE`(설정), `DELETE` | 위와 같음 |
| `read:user` | `USER`, `USER_AVATAR` | `READ`(프로필, 통계) | 공개 정보와 본인 정보 |
| `user:email` | `USER` | 본인 이메일 `READ` | 본인 |
| `user` | `USER`, `USER_AVATAR` | `read:user`와 `user:email`에 더해 `UPDATE`(프로필) | 본인 |
| `site_admin` | `SITE_SETTING`, `USER`(관리) | 사이트 관리자 API | 사이트 관리자만 고를 수 있다 |
| `notifications`, `delete_repo`, `admin:public_key`, `admin:gpg_key`, `workflow` 계열 | (예약) | 해당 기능(알림 REST, 프로젝트 삭제 API, X-3, X-4, X-25)이 생길 때 | |

**GitHub 범위 중 Yona에 대응이 없어 만들지 않는 것**: `repo:status`, `repo_deployment`, `repo:invite`, `security_events`, `admin:org_hook`, `user:follow`, 패키지, 토론, 게시물(gist) 계열(해당 기능이 Yona에 없다).

**지금 있는 외부 API가 요구하는 범위** (모두 토큰 주인의 실제 권한도 확인한다. D-20 대체)

| 엔드포인트 | 인증 | 필요 범위 | 확인하는 권한 |
|---|---|---|---|
| `GET /-_-api/v1/hello` | 없음 | 없음 | 없음 |
| `GET .../issues/{number}` | 토큰 | `public_repo`(공개 프로젝트) 또는 `repo` | `READ` |
| `POST .../issues` | 토큰이나 세션 | 위와 같음 | 이슈 만들기 권한 |
| `PUT, PATCH .../issues/{number}` | 토큰 | 위와 같음 | `UPDATE`(상태는 `CLOSE`, `REOPEN`) |
| `POST .../issues/{number}/comments` | 토큰이나 세션 | 위와 같음 | 댓글 만들기 권한 |
| `POST .../issuelabel/{number}` | 토큰이나 세션 | 위와 같음 | 이슈 라벨 수정 권한 |
| `POST .../issues/imports` | 토큰이나 세션 | 위와 같음 | 프로젝트 이슈 만들기 권한 |
| `POST .../posts`, `.../posts/{number}/comments` | 토큰이나 세션 | 위와 같음 | 게시글, 댓글 만들기 권한 |
| `GET /-_-api/v1/user/issues` | 토큰 | `repo`(비공개 이슈 포함) 또는 `public_repo`(공개만 걸러 줌) | 이슈별 `READ` |
| `GET /-_-api/v1/users/{user}/statistics` | 토큰 | `read:user` | 로그인 사용자 |
| `POST /-_-api/v1/users/token` | 아이디와 비밀번호 | 해당 없음(토큰을 만든다) | 비밀번호 |
| Git, SVN HTTP 접근(`/{user}/{project}.git/**`, `/svn/**`) | 비밀번호 칸의 토큰 | `repo` 또는 `public_repo` | 코드 읽기, 쓰기 권한 |
| `POST /-_-api/v1/users` | 세션 | `site_admin` | 사이트 관리자 |
| `GET /-_-api/v1/admin/users`, `PATCH .../admin/users/{user}` | 세션이나 토큰 | `site_admin` | 사이트 관리자 |

앞으로 생기는 API는 같은 규칙으로 정한다. 풀 리퀘스트(X-15)는 `repo`, `public_repo`, 프로젝트와 마일스톤과 라벨(X-19)도 같고, 조직은 `read:org` 계열, 웹훅은 `repo`나 웹훅 범위, 사용자 상태는 `site_admin`이다. 새 API를 더할 때는 이 표에 한 줄을 더하는 것을 완료 조건에 넣는다.

### 2. 저장 구조

새 테이블 `api_token`. 이름과 열은 v1.6 규칙(소문자 스네이크, `<대상>_id`)을 따른다.

| 열 | 형식 | 설명 |
|---|---|---|
| `id` | `BIGINT` 자동 증가 | 기본 키 |
| `user_id` | `BIGINT` | 토큰 주인(`n4user`). 색인 |
| `name` | `VARCHAR(100)` | 사용자가 붙인 이름 |
| `token_hash` | `VARCHAR(64)` | SHA-256 16진수. 유일 색인. 토큰 값은 임의 값이라 소금 없이 쓴다 |
| `token_prefix` | `VARCHAR(16)` | 목록에 보일 앞부분(`yona_pat_ab12`) |
| `scopes` | `VARCHAR` | 쉼표로 이은 범위 |
| `is_legacy` | `BOOLEAN` | 옛 사용자 토큰에서 옮긴 것 |
| `created_date`, `expires_date`, `last_used_date` | 시각 | 만료와 마지막 사용은 없을 수 있다 |

새 테이블은 내보내기와 가져오기에 포함하고(`DataTables` 50개에서 51개), 삭제 연쇄(사용자, 프로젝트가 아닌 사용자 삭제 처리)와 스키마 시험의 의도한 추가 목록에 올린다. 마지막 사용 시각은 요청마다 쓰지 않고 1분에 한 번만 갱신한다.

### 3. 형식과 노출

토큰은 `yona_pat_` + 임의 40자(Base62)이다. 만들 때 한 번만 보여 주고 이후에는 접두사와 마지막 사용 시각만 본다. 다시 볼 수 없으므로 잃으면 새로 만든다.

### 4. 인증과 권한

- 현재 `YonaAuthenticationFilter`는 `Authorization: token <값>`과 `Yona-Token: <값>` 헤더의 토큰을 **모든 경로에서** 사용자 인증으로 받는다(세션에는 기록하지 않는다. 첨부 올리기 등 `/-_-api` 밖의 웹 경로에서도 토큰으로 동작한다). 새 구조는 토큰 요청이 갈 수 있는 경로를 `/-_-api/**`와 범위가 선언된 경로로 **기본 거부**하고 나머지 웹 폼 경로에는 토큰을 받지 않는다(구현 때 현재 쓰이는 경로를 조사해 허용 목록을 만든다).
- `Authorization: token <값>`(v1.6 호환), `Yona-Token: <값>`(v1.6 호환), `Authorization: Bearer <값>`을 받는다. 값의 해시로 찾고 만료된 것은 거절한다(401).
- **Git과 SVN의 HTTP 접근**(선생님 정정 2026-10-29: 사용자 이름과 비밀번호(토큰)를 함께 입력받는다): 사용자 이름 칸은 로그인 ID나 이메일(`findByLoginKey`, v1.6 Basic 인증과 같다)이고 비밀번호 칸에 토큰을 넣는다. **토큰은 그 사용자 소유여야 한다**(해시를 사용자 번호와 함께 찾는다). 이름과 토큰이 다른 사용자의 것이면 401이다. 두 접근이 함께 쓰는 `BasicAuthResolver` 한 곳에서 처리한다. 새 토큰은 접두사로, 이관한 이전 토큰은 형식(44자 Base64)으로 알아보고 토큰 확인을 먼저 한다. **새 토큰 형식(`yona_pat_` 접두사)은 확인에 실패해도 비밀번호 확인으로 넘기지 않고 거절한다**(토큰을 비밀번호 추측에 쓰지 못하게 한다). 이관한 이전 토큰 형식은 비밀번호와 겹칠 수 있어 토큰 확인에 실패하면 비밀번호 확인으로 넘어간다. 그 밖의 값은 기존 비밀번호 확인으로 간다(아래 "비밀번호 인증" 결정 대기). 코드 접근에는 `repo`나 `public_repo`가 필요하고 이관한 이전 토큰도 범위에 `repo`가 있어 쓸 수 있다(위험과 완화는 5절). 2단계 인증(X-2)이 생기면 2단계 인증 사용자는 토큰이 필수가 된다.
- **OpenAPI**(`/-_-api/**`)는 토큰만으로 인증하고 사용자 이름은 필요 없다. 토큰의 주인이 사용자이고 **범위를 통과해도 그 사용자의 실제 권한을 항상 확인한다**.
- API 컨트롤러에 필요한 범위를 선언한다(예: 이슈 수정은 `write:issue`). 범위가 모자라면 403이다.
- 범위를 통과해도 **사용자의 실제 권한을 확인**한다. 이슈 조회가 비공개 프로젝트의 구성원이 아닌 사용자에게는 403이다(D-20 대체). 세션으로 부른 요청은 범위를 보지 않는다.

### 5. 옛 토큰: 일반 Classic 토큰 형태로 고쳐 이관하고 Git, SVN에도 쓴다 (선생님 지시 2026-10-29)

이관한 옛 토큰은 특별한 예외가 아니라 **새 Classic 토큰과 같은 형태의 행**으로 고쳐 옮긴다. 값(추측 가능한 시각 해시)은 그대로 두어 같은 값이 계속 동작하게 한다. Git과 SVN의 HTTP 접근에도 쓸 수 있어야 의미가 있다는 지적에 따라 앞선 "이관한 토큰은 API 전용" 안을 접었다.

| 구분 | 이관한 옛 토큰 | 새로 만드는 토큰 |
|---|---|---|
| 값 | 지금 값 그대로(시각 해시, 추측 가능) | `yona_pat_` + 임의 40자(`SecureRandom`) |
| 저장 | 값을 해시해 새 테이블 행으로 이관, `n4user.token`은 비움 | 해시만 저장 |
| 범위 | 그 사용자가 가질 수 있는 **모든 범위를 명시한 목록**(`repo`, `read:org`, `user` 등. 사이트 관리자는 `site_admin`도). 특수 값 `*`가 아니라 일반 범위 목록이다 | 고른 범위 |
| Git, SVN HTTP | 범위에 `repo`가 있으므로 **쓸 수 있다** | `repo`나 `public_repo`가 있으면 쓸 수 있다 |
| 만료 | 없음(무제한, 기존 사용자 유지) | 기본 30일(선택) |
| 표시 | 이름 "이전 토큰", `is_legacy` 표시와 경고(추측 가능한 값이니 새로 만들 것) | |

**위험**: 추측 가능한 값이 이제 코드 쓰기(Git push)까지 열 수 있다. Git과 SVN은 사용자 이름도 맞아야 하지만 이름은 공개 정보라 큰 방어가 되지 못하고, OpenAPI는 토큰 값만 맞히면 된다. 토큰을 만든 시각을 분 단위로 알면 후보가 6만 개 안팎이라, 막는 장치가 없으면 비공개 프로젝트까지 노출될 수 있다.

**위험 완화 (선생님 확정 2026-10-29)**

1. **토큰 인증 실패 제한**(선생님 확정 2026-10-29: **5회**): 같은 주소(IP)에서 토큰 인증에 **5회** 실패하면 일정 시간(기본 15분, 설정 키) 그 주소의 토큰 인증을 막고(429) 성공하면 횟수를 지운다. OpenAPI와 Git, SVN 공통이다. Yona에는 로그인 실패 제한이 어디에도 없었으므로(v1.6, v2 모두) 이것이 첫 제한 장치이다. 같은 장치를 Git, SVN의 **비밀번호 시도**에도 적용할지는 아래 "비밀번호 인증"과 함께 정한다.
2. **이관한 토큰은 만료 없음(무제한)**: 기존 사용자를 위해 현재 동작을 그대로 유지한다(만료를 부여하지 않는다).
3. **경고와 교체 유도**: 설정 화면에서 이관한 토큰에 경고를 표시하고 새 토큰 만들기를 권한다.
4. 사용자가 이관한 토큰을 삭제하면 같은 값은 다시 만들 수 없다.

- 이관은 `n4user.token`이 비어 있지 않고 그 사용자에 이관 행이 없으면 값을 해시해 `is_legacy` 행으로 옮긴다. 서버 시작 때 돈다(X-12 보정과 같은 방식, 멱등). **정정(구현 중 확인)**: v1.6의 사용자 내보내기에는 `token` 열이 없다(`DataTables`의 `N4USER`). 그래서 이관 보정은 **DB를 그대로 쓰며 프로그램만 바꾸는 경우**에만 일하고, 내보내기 파일로 이관하면 v1.6처럼 토큰은 옮겨지지 않는다(사용자가 새로 만든다).
- 한 번 옮기면 v1.6 바이너리로 되돌릴 수 없다(열을 비우므로). 되돌릴 일이 있으면 보정 전에 DB를 백업한다.
- 설정 화면은 더 이상 토큰이 없을 때 시각 해시 토큰을 **자동으로 만들지 않는다**.
- 옛 URL `POST /-_-api/v1/users/token`이 만드는 토큰은 이관 토큰이 아니라 **새 토큰**이다(아래 6절).

### 5-1. 비밀번호 인증 (선생님 지적 2026-10-29: 기존 비밀번호 확인으로 넘어가는 것은 보안상 문제, 결정 대기)

Git과 SVN의 HTTP는 지금 비밀번호도 받는다(v1.6 동작). 같은 입력 칸에 비밀번호와 토큰이 함께 오므로 토큰 확인이 실패한 값을 비밀번호로 다시 확인하면 비밀번호 추측 경로가 되고 로그인 실패 제한도 없다. GitHub은 Git 작업의 비밀번호 인증을 2021-08-13에 없앴다. 선택지는 다음과 같다.

- **(가) 토큰만 받는다(GitHub 방식)**: 가장 안전하다. 비밀번호로 clone하던 기존 사용자와 도구가 깨진다(v1.6 호환 변경).
- **(나) 설정 키로 고른다(권장)**: `yona.git-http-password-auth`(기본 `true`=지금처럼 받는다). 사이트 관리자가 `false`로 바꾸면 토큰만 받는다. 새 토큰 형식은 항상 비밀번호로 넘기지 않으며, 비밀번호 시도에도 5회 실패 제한을 건다. 안내와 이행 기간을 거쳐 기본값을 `false`로 바꾼다.
- **(다) 지금처럼 둔다**: 비밀번호 시도 제한 없이 토큰만 더한다. 추천하지 않는다.

권장은 (나)이다. 2단계 인증(X-2)이 생기면 2단계 인증 사용자는 비밀번호 경로를 쓰지 못하고 토큰이 필수가 된다.

### 6. 화면과 발급 API

- 설정의 토큰 화면(`user/edit-token`)을 목록과 만들기로 바꾼다. 목록은 이름, 접두사, 범위, 만든 날, 마지막 사용, 만료, 삭제이다. 레거시 토큰은 표시를 달고 삭제할 수 있다. 만들기는 이름, 만료, 범위 체크 상자이다. **만료는 7, 30, 60, 90일과 없음(경고) 선택지에 더해 \"사용자 지정\"을 고르면 달력(날짜 선택기)으로 만료 날짜를 정한다**(선생님 확정 2026-10-29). 달력은 마일스톤의 기한 선택(`milestone/create`)과 같은 날짜 선택기를 쓰고, 오늘 이후 날짜만 고를 수 있다. 서버도 같은 규칙으로 검사하며(오늘 이후, 설정 키의 최대 수명 이내) 어긋나면 400이다. 기본 선택은 30일이다.
- 옛 "토큰 다시 만들기"는 새 토큰 만들기로 대체한다. 옛 URL `POST /-_-api/v1/users/token`은 삭제한다.

#### 만료 (GitHub 기준으로 재조사, 2026-10-29)

[GitHub 문서](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)에서 확인한 것: 만료를 강하게 권장하고("highly recommend"), Classic은 기본 선택지나 사용자 지정 날짜를 고르며, Fine-grained는 기본 30일이고 1~366일 또는 없음이며 조직과 엔터프라이즈가 최대 수명 정책으로 막을 수 있고(Classic에 적용되는지는 문서에 없다), Fine-grained는 사용자당 50개까지이며 **1년 동안 쓰지 않은 토큰은 자동으로 삭제**된다. Classic의 고정 선택지 목록(7, 30, 60, 90일)과 "없음" 허용 여부, 만료 알림 메일은 이 문서에 없어 확인하지 못했다.

Yona 권장: 선택지는 7, 30, 60, 90일, 사용자 지정 날짜, 없음(경고 표시)이고 **기본은 30일**(GitHub Fine-grained 기본과 같다). 사이트 관리자가 최대 수명을 설정 파일 키로 정할 수 있게 하고(기본은 제한 없음), 사용자당 토큰은 50개까지, 1년 동안 쓰지 않은 토큰은 자동 삭제한다(마지막 사용 시각으로 판단). 만료 알림 메일은 하지 않는다(필요하면 후속).

#### 로그인으로 받는 토큰 (정확히 재확인, 2026-10-29)

**v1.6 동작** (`UserApi.newToken`, `UserApi.getNewUserToken`; v2 `ExternalUserApiController.newToken`이 같다)

1. 요청 본문 `{"id": "아이디나 이메일", "password": "..."}`로 사용자를 찾고 비밀번호를 확인한다. 잠기거나 지워진 사용자와 맞지 않는 비밀번호는 401이다.
2. 성공하면 **세션 로그인도 함께 시작**한다(`addUserInfoToSession`). 쿠키를 유지하는 클라이언트는 사이트에도 로그인된다.
3. 현재 시각 문자열의 SHA-256을 Base64로 만든 값을 **`n4user.token`에 덮어쓴다**. 사용자에게는 토큰 열이 하나뿐이라 이전 토큰은 무효가 된다. 설정 화면의 "토큰 다시 만들기"도 같은 열을 바꾸므로 두 경로는 서로의 토큰을 무효로 만든다.
4. `{"access_token": 값}`을 돌려준다.

**언제 쓰는가**: 2018-07-03에 NAVER Labs 개발자가 "id와 비밀번호로 HTTP 요청용 토큰을 돌려주는 API"로 더했다(커밋 `a291c0252`). 토큰이 아직 없는 외부 클라이언트(스크립트, 도구)가 설정 화면에서 토큰을 복사하지 않고 아이디와 비밀번호로 바로 토큰을 받아 이후 요청에 `Authorization: token <값>`이나 `Yona-Token: <값>` 헤더로 쓰게 하려는 용도이다. 세션 로그인을 겸하는 것은 기존 로그인 도우미를 재사용한 부산물로 보인다.

**누가 부르는가**: Yona 코드(v1.6 소스, v2의 템플릿과 스크립트, 이전 화면)에는 호출하는 곳이 **없다**. 외부 스크립트와 도구용이며 실제 사용처는 알 수 없다. (이전 화면의 `token`은 GitHub OAuth 토큰이라 이 경로와 무관하다. 앞서 "이전 화면이 깨진다"고 쓴 것은 틀렸다.)

**GitHub**: 같은 기능이 없다. 비밀번호로 API를 부르는 방식은 2020-11-13부터 받지 않고 토큰 인증만 쓰며(Authorizations API도 같은 날 제거), Git 작업의 비밀번호는 2021-08-13에 막았다. 이미 만든 토큰은 계속 동작했다. 토큰은 웹 화면의 PAT 만들기나 웹, 기기 인증 흐름으로만 받는다([변경 공지](https://github.blog/changelog/2020-11-13-token-authentication-required-for-api-operations)). 없앤 이유(비밀번호 노출, 2단계 인증 우회 등)의 공식 문구는 이번에 확인하지 못했다.

**이상한 점 (선생님 지적 2026-10-29, 코드로 확인)**

1. **토큰이 추측 가능하다.** 값이 `SHA-256(현재 시각 문자열)`의 Base64이다(`SHA256Util.hashBasedNow`, Joda `LocalDateTime.now().toString()`은 **밀리초 정밀도**). 토큰을 만든 시각을 분 단위로만 알아도 후보가 6만 개 안팎이라 공격자가 모두 계산해 API에 시험해 볼 수 있다. v1.6의 설정 화면도 토큰이 없을 때 같은 방식으로 자동 생성했으므로 v1.6에서 만들어진 토큰은 대부분 이런 값이다. **정정(면밀 검토 2026-10-29)**: v2의 설정 화면(`AccountService.token`)은 이미 `SecureRandom` 바이트로 만든 임의 값을 쓴다. 약한 시각 해시는 v1.6에서 만든 토큰과 v2의 옛 URL(`ExternalUserApiController.newToken`)이 만든 토큰에 있다.
2. **사용자 존재 여부가 드러난다.** 없는 사용자에게는 "No valid user by id", 있는 사용자의 틀린 비밀번호에는 "No user by id and password"로 응답 문구가 다르다.
3. **부수 효과가 많다.** 토큰을 받는 호출이 세션 로그인도 시작하고, 사용자의 유일한 토큰을 덮어써 설정 화면에서 보던 토큰이 갑자기 무효가 된다.
4. **비밀번호로 토큰을 받는 경로**다(GitHub이 없앤 방식). 2단계 인증이 생기면 우회 경로가 된다. 로그인 시도 제한이 이 경로에도 걸리는지는 확인하지 못했다.
5. Yona 안에는 호출하는 곳이 없다.
6. v2의 인증 필터는 `Authorization` 헤더에 문자열 `token `이 **들어 있기만 해도** 토큰으로 읽고(`contains("token ")`), `ApiRequests.tokenUser`는 `token`으로 헤더를 쪼갠다. 토큰 값에 `token`이 들어 있으면 잘못 쪼개질 수 있는 느슨한 구문 분석이다.

**새 구조에서 생기는 문제**: 토큰이 여러 개가 되므로 호출마다 새 토큰을 만들면 쌓이고, 지금처럼 덮어쓰면 다른 이름의 토큰을 지울 위험이 있다.

**방침 (선생님 확정 2026-10-29, 앞선 "호환용으로 남김"을 바꿈): 삭제한다.** 세션과 토큰을 둘 다 받는 경로를 없애면(16번) 이 URL이 줄 것은 토큰뿐이고, 토큰은 설정 화면에서 만든다. 비밀번호로 토큰을 받는 경로는 GitHub도 없앴고 값이 추측 가능했다. 그래서 폐지 예고 기간 없이 삭제한다. 쿠키로 세션 경로를 쓰던 외부 도구는 깨진다(의도된 비호환 변경). `ApiTokenService.issueLoginToken`과 이름 `API login`은 두지 않는다.

### 7. 삭제와 폐기

사용자가 삭제 처리되면 그 사용자의 토큰을 모두 지운다. 비밀번호를 바꿔도 토큰은 유지한다(GitHub과 같다).

결정이 필요한 것과 구현 때 처리할 것을 나누어 적는다. 현재 코드(`YonaAuthenticationFilter`, `AccountService`, `ApiRequests`, `BasicAuthResolver`, `SecurityConfig`)를 확인한 결과이다.

### 구현에서 반드시 처리할 것 (결정 불필요)

1. **엄격한 헤더 분석**: `Authorization: token <값>`, `Authorization: Bearer <값>`, `Yona-Token: <값>`을 정확한 형식으로만 읽는다(공백 하나, 값에 공백 없음). 지금의 `contains("token ")`와 `split("token")`은 버린다. Git 경로에서는 `Basic` 자격과 섞이지 않게 한다(`BasicCredentials.parse`는 방식 이름을 보지 않고 앞 여섯 글자를 건너뛰는 v1.6 동작이라 `Bearer`나 `token`을 Basic으로 잘못 읽는다. 토큰 헤더를 먼저 가려낸다).
2. **잠긴, 삭제된 사용자의 토큰 거절**: 지금 `authenticateByToken`은 사용자 상태를 보지 않는다(세션과 쿠키 경로는 `isLockedOut`을 본다). 토큰 인증에서도 `LOCKED`, `DELETED`를 거절한다.
3. **범위 정보를 인증에 싣는다**: `YonaAuthentication.of(user, viaToken = true)`에 토큰의 범위를 담고, 범위 검사는 한 곳(인터셉터나 필터)에서 경로와 메서드별 대응표로 한다. 세션 요청은 검사하지 않는다. 대응표에 없는 경로는 토큰 요청을 거부한다(기본 거부).
4. **토큰이 통하는 경로는 허용 목록(엔드포인트 단위)으로 제한하고 명단 밖은 거부한다**(선생님 확정 2026-10-29: 거부). 현재 인증 필터는 모든 요청에서 토큰 헤더가 있으면 그 사용자로 인정한다(v1.6 `Global`이 모든 요청에서 `UserApp.initTokenUser`를 부르던 것을 따랐다). 그래서 토큰으로 일반 화면의 폼 요청(풀 리퀘스트 만들기, 이슈 삭제, 프로젝트 설정 변경 등)도 세션 없이 보낼 수 있다. 범위는 경로별 대응표로 검사하므로 표에 없는 경로는 검사할 기준이 없고, 그대로 두면 `read:user`만 가진 토큰으로 프로젝트를 고치는 요청이 통과한다. 새 구조는 **명단에 있는 경로에서만 토큰을 인증으로 인정**하고, 명단 밖의 경로에서 토큰 헤더가 오면 **인정하지 않고 401을 돌려준다**. 명단 밖의 경로는 세션 로그인으로만 쓴다. 명단은 16번의 토큰 전용 엔드포인트와 Git, SVN의 HTTP 접근이다(`/-_-api/**` 접두사 전체가 아니다). 구현 때 현재 토큰이 닿는 경로를 코드에서 빠짐없이 찾아 명단을 확정하고 대응표(1-1절)에 필요한 범위를 한 줄씩 더한다. 숨은 외부 도구가 화면 경로에 토큰을 쓰고 있었다면 깨질 수 있으므로 이는 의도된 비호환 변경으로 기록한다(`differences-from-v16.md`). 명단 밖의 토큰 요청은 사용 로그(접두사만, 값 제외)를 남겨 사용처를 확인한다.
4-1. (구) **현재 토큰으로 갈 수 있는 웹 경로 조사**: `/-_-api/**`의 외부 API, 첨부 올리기(`AttachmentController`가 `Yona-Token`을 명시적으로 받는다)가 확인되었다. 구현 때 `authenticateByToken` 앞에서 모든 경로를 조사해 허용 목록을 만들고 대응표(1-1절)에 한 줄씩 더한다.
5. **옛 URL의 비밀번호 시도도 같은 실패 제한을 받는다**: `POST /-_-api/v1/users/token`은 비밀번호를 확인하는 경로이므로 Git과 SVN 비밀번호 시도와 같은 5회 제한을 건다.
6. **실패 제한의 주소 판별**: 리버스 프록시 뒤에서는 모든 요청이 프록시 주소로 보여 **한 사람이 5회 실패하면 모든 사용자가 막힌다**. 신뢰하는 프록시가 보낸 `X-Forwarded-For`를 쓰는 설정(기존 서버 설정과 맞춘다)을 둔다. 제한 장부는 메모리에 두고 크기와 만료를 제한한다(Yona는 단일 서버).
7. **토큰 값을 기록하지 않는다**: 접근 로그는 `Referer`와 `User-Agent`만 남기고 `Authorization`을 남기지 않는 것을 확인했다. 새 코드의 로그와 예외 메시지, 시험 출력에도 토큰 값을 쓰지 않는다. 목록 화면은 접두사만 보인다.
8. **마지막 사용 시각은 쓰기를 줄인다**: 토큰마다 1분에 한 번만 갱신한다(요청마다 쓰지 않는다). 요청마다 토큰 해시로 DB를 한 번 조회하므로 조회 색인(`token_hash` 유일 색인)을 둔다.
9. **삭제 연쇄와 상태**: 사용자가 삭제 처리되면 토큰을 모두 지우고(`SiteUserService`), 잠긴 사용자는 토큰이 남아 있어도 인증이 거절된다. 내보내기와 가져오기에 새 테이블을 넣고(`DataTables` 51개), 가져온 뒤 고아 행을 정리한다.
10. **이관 보정의 모양**: X-12와 같은 멱등 보정이며 서버 시작 때 돈다. `n4user.token`이 비어 있지 않은 사용자만 대상이다. v1.6 내보내기에는 토큰 열이 없어 가져오기 뒤에는 이관할 것이 없다. 사용자가 지운 이전 토큰은 `n4user.token`이 이미 비워져 다시 생기지 않는다. 옛 파일(토큰 테이블 없음)로 가져오면 남아 있던 토큰은 사용자 번호가 달라질 수 있어 비운다.
11. **스키마와 다중 DB**: 새 테이블 `api_token`은 H2, PostgreSQL, MariaDB 모두에서 시험하고(`token_hash` 유일 색인, `scopes` 길이), 스키마 시험의 의도한 추가 목록에 올린다.
12. **내보내기 파일의 민감성**: 내보내기에는 토큰 해시가 들어간다. 이관한 이전 토큰은 값이 추측 가능해 해시로부터 복원될 수 있다. 내보내기 파일은 이미 비밀번호 해시와 옛 평문 토큰(`N4USER.token`)을 담고 있어 새로 생기는 노출은 아니지만 문서에 적는다.
13. **누가 토큰을 만들 수 있는가**: 로그인한 활성 사용자는 누구나 만든다(소셜 로그인, LDAP 사용자 포함. 이들은 로컬 비밀번호가 없어 지금까지 Git 푸시 수단이 비밀번호뿐이었으므로 토큰의 이득이 크다). 게스트는 권한이 좁아 쓸 일이 적지만 막지 않는다. `site_admin` 범위는 사이트 관리자만 고를 수 있다.
14. **범위와 실제 권한**: 범위는 만들 때 저장하고, 이후 사용자가 사이트 관리자 권한을 잃어도 실제 권한 확인에서 막힌다(범위 ∧ 권한).
15. **언어와 화면**: 새 메시지는 5개 언어이며 `MessageParityTest`의 추가 목록에 올린다. 만든 직후의 토큰 표시는 한 번만 보이고 복사 단추를 둔다.

16. **세션과 토큰을 둘 다 받는 경로는 두지 않는다**(선생님 지시 2026-10-29): 모든 엔드포인트는 **세션 전용**이거나 **토큰 전용**이다. 사용자의 출처는 경로 종류가 정한다. 토큰 전용 경로는 토큰 인증 결과(주인과 범위)만 쓰고 `CurrentUserProvider`를 쓰지 않는다(`CurrentUserProvider`는 세션, 로그인 유지 쿠키, 토큰을 모두 인정하므로 토큰 전용 경로에서 쓰면 세션만으로 통과하고 범위 검사를 건너뛰며 CSRF가 꺼져 있어 악성 페이지에서 부를 수 있다). 세션 전용 경로는 토큰을 인정하지 않는다. **조사 결과**:
    - `/-_-api/v1/**` 접두사 전체가 외부 API가 아니다. 웹 화면이 세션으로 부르는 AJAX가 같은 접두사 아래에 많다(`titleHeads`, `assignableUsers`, `postlabel`, `upvoteWeight`, `share`, `detectChange`, `commentNotiReceivers`, `favoriteProjects`, `defultLoginPage` 등). 이들은 **세션 전용**이다. 따라서 허용 목록은 접두사가 아니라 **엔드포인트 단위**이다.
    - 지금 둘 다 받는 경로(이슈 만들기, 이슈 댓글, 이슈 라벨 바꾸기, 이슈 가져오기, 게시글과 게시글 댓글)는 **웹 화면이 부르지 않는다**. 이전(Migration) 화면의 스크립트(`yona.Migration.js`)는 Yona 쪽으로 `/migration/**`만 부르고 `/-_-api`의 이 경로들을 부르지 않는다. v1.6이 "세션도 받는다"고 한 이유는 외부 이전 도구가 `POST /-_-api/v1/users/token`으로 받은 **세션 쿠키**를 그대로 쓰게 하려던 것으로 보인다. 그러므로 이 경로들은 **토큰 전용으로 바꾼다**. 쿠키에 기대던 외부 도구는 응답으로 받은 토큰을 헤더에 넣어야 한다(의도된 비호환 변경, 장부에 기록).
    - **토큰 전용 엔드포인트 명단**(허용 목록): 이슈 조회, 만들기, 수정, 상태 변경, 댓글, 라벨 바꾸기, 가져오기, 게시글 만들기, 게시글 댓글, 내 이슈 목록, 사용자 통계, 사용자 만들기와 관리자 사용자 API(`site_admin`), `hello`. 토큰을 만드는 `POST /-_-api/v1/users/token`은 자격(아이디, 비밀번호)이 인증이다. 나머지 `/-_-api/**`와 웹 경로는 모두 세션 전용이다.
    - **첨부 올리기**(선생님 지시 2026-10-29): 기존 `POST /files`(`AttachmentController`)는 웹 편집기가 세션으로 쓰는 경로라 **세션 전용으로 바꾼다**(지금 받는 `Yona-Token` 지원은 뺀다). 토큰으로 올릴 도구를 위해 **토큰 전용 경로를 새로 만든다**: `POST /-_-api/v1/files`. 요청 형식은 기존과 같고(멀티파트 `filePath`, 선택 `authorEmail`, `authorLoginId`) 필요한 범위는 `repo`나 `public_repo`, 임시 첨부(컨테이너 `USER`)로 저장하는 동작도 같다. 내려받기, 목록, 지우기(`GET /files/{id}`, `GET /files`, `POST /files/{id}`)는 세션 전용으로 둔다. 새 경로는 대응표(1-1절)에 한 줄 더한다.
    - **첨부와 가져오기 JSON의 연결**(확인): 가져오기 흐름(세션 흐름)의 본문에는 `temporaryUploadFiles`가 있다. 도구가 `POST /files`로 첨부를 먼저 올리고(`authorEmail`로 원작성자 명의) 그 첨부 번호를 이슈, 게시글, 댓글 JSON의 `temporaryUploadFiles`에 넣어 연결한다. 그래서 토큰 전용 업로드 경로(`POST /-_-api/v1/files`)는 이 흐름을 토큰 인증으로 옮기기 위해 필요하다.
    - **이슈 댓글의 두 JSON 모양**: `POST .../issues/{number}/comments`는 v1.6부터 한 경로 안에 흐름이 둘이다(`IssueApi.newIssueComment`). `Authorization` 헤더가 있으면 토큰 흐름(본문 `{"comment": "..."}`), 없으면 세션 흐름(`createCommentByUser`, 본문 `body`, `author`, `createdAt`: 가져오기용)이다. 이는 v2가 v1.6과 달라진 것이 아니라 **v1.6 자체의 구조**이다. **응답 모양도 두 흐름이 다르다**(v1.6 `createCommentUsingToken`, `createCommentByUser`): 토큰 흐름은 `201 {"result": {이슈 정보와 이벤트}}`, 세션 흐름은 `201 {"status": 201, "location": "댓글 주소"}`이다. 모양을 그대로 유지한다. 토큰 전용으로 바꿀 때 **두 JSON 모양을 모두 토큰 인증 아래에서 받고** 인증만 하나로 합친다(모양을 바꾸면 도구가 깨진다). 어느 모양인지는 본문에 `comment`가 있는지로 가린다.
17. **토큰 헤더가 있으면 세션보다 토큰이 우선한다**: 현재 인증 필터는 세션이 유효하면 토큰을 확인하지 않아(`if (!hasValidSession())`), 세션 쿠키와 토큰 헤더를 함께 보내는 클라이언트는 **토큰의 범위가 무시되고 전체 권한**으로 동작한다. 옛 URL이 토큰과 함께 세션 쿠키도 발급하므로 쿠키를 유지하는 클라이언트가 실제로 이렇게 된다. 새 구조는 토큰 헤더가 있으면 토큰 인증을 먼저 하고 그 범위를 적용한다(세션은 무시한다).
18. **옛 URL의 세션 발급**: 세션 쿠키에 기대던 용도가 16번으로 없어지므로 이 호출이 세션 로그인을 겸할 이유가 없다. 세션 발급은 **없애고** 토큰만 돌려준다(의도된 비호환 변경). 17번(토큰 헤더 우선)은 다른 경로의 방어로 유지한다.

### 결정이 필요하거나 선생님 확인을 받은 것

- **비밀번호 인증은 (나)**(선생님 확정): 설정 키 `yona.git-http-password-auth`로 사이트 관리자가 고른다. 기본은 지금처럼 받는다. "사용자가 선택하게 하는 것이 맞다"는 말씀은 사이트 관리자가 키로 고르는 뜻으로 이해했다. **사용자 개인이 자기 계정에서 비밀번호 인증을 끄는 선택**이 필요하면 후속으로 더한다(계정 설정 항목).
- **로그인 화면에도 실패 제한이 없다**: v1.6과 v2 모두 웹 로그인 비밀번호 시도에 제한이 없다. 이 항목은 토큰과 별개이지만 같은 장치로 풀 수 있어 백로그(`refactoring-backlog.md`) 후보로 남긴다. 이번 구현의 범위에는 넣지 않는다.
- **`CSRF`**: `SecurityConfig`가 CSRF를 끈 상태(v1.6 동작)이다. 토큰 인증과 무관하게 이미 그렇고 이번 범위 밖이다.
