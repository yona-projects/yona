# DB 성능 비교 (MariaDB, PostgreSQL, Cubrid)

같은 jar, 같은 머신, 같은 자원 제한에서 세 DB를 차례로 돌려 애플리케이션 수준(HTTP)에서 읽기와 쓰기 성능을 비교했다. 요청 하나가 DB에 보내는 질의를 줄이는 개선(A-628)과 Cubrid의 JDBC 문장 캐시(A-629)를 적용한 **현재 코드** 기준이며, 개선 전 수치와 Cubrid가 느린 이유의 측정도 함께 적는다.

## 요약

- **MariaDB 10.11과 PostgreSQL 16은 서로 비슷한 수준이다.** PostgreSQL이 쓰기와 API 읽기에서 앞서고(이슈 생성 동시 8에서 약 1.4배, 이슈 단건 조회 동시 16에서 약 1.3배), MariaDB가 흔한 낱말 검색에서 앞선다(동시 16에서 약 1.2배, 드문 낱말은 비슷하다). 화면(HTML) 요청은 두 DB의 차이가 오차 범위이다.
- **Cubrid는 기본 설정에서는 개선 뒤에도 느리다.** PostgreSQL 대비 API 읽기와 쓰기는 37~53% 수준이고 낱말 검색은 24~28%이다. 개선 전에는 API 읽기 8~9%, 쓰기 19~26%, 검색 20~25% 수준이었다. 이슈 목록과 상세 화면은 PostgreSQL과 같은 수준이다(애플리케이션의 화면 그리기 시간이 지배한다).
- **Cubrid 권장 설정을 적용하면**(브로커 `SQL_LOG=OFF`와 대소문자 무시 정렬 규칙, 6절) PostgreSQL 대비 API 읽기 46~49%, 쓰기 57~59%, 낱말 검색 50~61% 수준이 된다. 그 밖의 서버와 브로커 설정(데이터 버퍼, 스레드 그룹, CAS 선기동, 질의 결과 캐시)은 효과가 없었다.
- **권장**: v1.6에서 올라오는 사이트는 **MariaDB**(같은 DB라 이관이 가장 짧고 리허설을 MariaDB에서 검증했다), 새로 설치하는 사이트는 MariaDB나 PostgreSQL 중 익숙한 쪽을 고른다. Cubrid는 조직 사정이 있을 때 쓰고, 쓴다면 JDBC 문장 캐시와 대소문자 무시 정렬 규칙은 자동으로 적용되며 브로커 `SQL_LOG=OFF`(또는 `ERROR`)는 직접 설정한다(6절). Cubrid는 MariaDB, PostgreSQL보다 보증 수준이 낮은 지원이다(v1.6과 동작이 다른 곳이 있고 PostgreSQL 대비 처리량은 절반 수준이다).
- 모든 수치는 **단일 실행**이고 합성 부하(이슈 5,000건, 댓글 4,000건)이다. 실제 운영 부하나 더 큰 데이터의 속도는 확인하지 못했다(8절).

## 4. Cubrid가 느린 이유(측정)

### 4.1 질의 하나의 비용(JDBC 단독, 같은 머신)

| 동작(ms/회) | MariaDB | PostgreSQL | Cubrid |
|---|---|---|---|
| select 1(재사용 문장) | 0.050 | 0.052 | 0.196 |
| select 1(매번 준비) | 0.048 | 0.050 | 0.375 |
| insert 1건 + 자동 커밋 | 0.378 | 0.275 | 0.665 |
| PK 단건 조회 | 0.060 | 0.050 | 0.194 |
| insert 후 commit | 0.480 | 0.375 | 1.580 |

Cubrid는 질의 한 번의 왕복이 약 4배이고 커밋도 약 4배이다. 브로커(CAS) 프로세스를 거치는 구조에다, 질의를 매번 준비할 때 한 번 더 오가는 비용(0.375ms 대 0.05ms)이 크다. 브로커 SQL 로그에서 DB 쪽 실행 시간은 질의마다 0.000초(1ms 미만)였고 시간은 왕복에 들었다.

JDBC 문장 캐시(`usePreparedStmtCache=true`)를 켜면 "매번 준비"가 0.43ms에서 0.18ms로 줄어 재사용할 때와 같아진다(A-629).

### 4.2 요청 하나가 보내는 질의 수

| 요청(이슈 12건 기준) | 개선 전 | 현재 |
|---|---|---|
| 이슈 목록 화면 | 57 | 37 |
| 이슈 상세 화면 | 38 | 33 |
| 이슈 단건 조회(API) | 18 | 18 |
| 검색(API) | 31 | 21 |

질의당 비용이 큰 DB에서는 질의 수가 곧 지연이다. 개선 전 이슈 목록 화면은 59개 중 15개가 이슈마다 라벨을 따로 읽는 N+1이었고, 프로젝트와 규칙을 요청 안에서 여덟 번씩 다시 읽었다. 이를 지연 로딩 묶음(`hibernate.default_batch_fetch_size=32`)과 요청 범위 보관소(`RequestMemo`)로 줄였다. 이슈 상세와 단건 API에는 약 4개의 중복이 남았다(규칙 `rulesets`가 즉시 로딩이라 프로젝트를 읽을 때마다 질의가 2개 나가는 것이 원인이며 매핑을 건드려야 해서 두었다).

### 4.3 CPU

동시 16 부하에서 Cubrid 컨테이너의 CPU가 상한(4코어, 400%)에 닿았다(최대 423%). PostgreSQL 컨테이너의 CPU는 측정하지 못했다. CPU를 늘리면 어디까지 따라오는지(8코어)도 측정하려다 중단해 모른다.

## 5. 설정으로 시도한 것(Cubrid, 데이터 30%)

앞의 4행은 질의 줄이기 이전 jar이고 뒤의 3행은 그 이후 jar이다. 규모가 달라 앞의 표와 숫자가 다르다.

| 변형 | 이슈 단건 조회 동시 16(건/초) | 이슈 생성 동시 8(건/초) | 검색 동시 16(건/초) | 이슈 목록 p50(ms) |
|---|---|---|---|---|
| 기본(개선 전) | 182 | 148 | 50 | 137.4 |
| 브로커 `SQL_LOG=OFF` | 196 | 154 | 56 | 137.1 |
| `SQL_LOG=OFF` + 자동 커밋 전환 제거 | 196 | 146 | 53 | 140.3 |
| `SQL_LOG=OFF` + CAS 24개 선기동 + `KEEP_CONNECTION=ON` | 196 | 155 | 54 | 140.9 |
| 질의 줄이기(A-628) | 183 | 145 | 71 | 106.9 |
| 질의 줄이기 + JDBC 문장 캐시(주소에 직접 지정) | 760 | 273 | 105 | 82.8 |
| 질의 줄이기 + 문장 캐시(기본 설정, 자동 적용) | 800 | 268 | 97 | 81.6 |

- 브로커 `SQL_LOG=OFF`는 3~8% 개선이고 나머지 설정(자동 커밋 전환 제거, CAS 선기동, `KEEP_CONNECTION`)은 효과가 없거나 오차 수준이었다.
- **효과가 컸던 것은 JDBC 문장 캐시(질의 줄이기와 함께 이슈 단건 조회 약 4.4배)와 질의 수를 줄이는 코드 개선**이다.
- 최종 전체 규모 측정(2절)에는 `SQL_LOG`를 기본값(ON)으로 두었다. 끄면 3~8%가 더해질 수 있다.

## 6. Cubrid 추가 개선: 대소문자 무시 정렬 규칙과 서버, 브로커 설정

현재 코드에서 Cubrid만 더 끌어올린 결과이다(전체 규모, 단일 실행, 2절과 같은 조건이며 2절은 기본 설정 `SQL_LOG=ON`이다).

### 6.1 효과가 있었던 것

| 항목 | 2절(기본 설정) | 대소문자 무시 정렬 규칙 | 정렬 규칙 + `SQL_LOG=OFF` | PostgreSQL |
|---|---|---|---|---|
| 이슈 단건 조회 동시 16(건/초) | 869.1 | 896.8 | 1063.6 | 2169.6 |
| 댓글 목록 동시 16(건/초) | 1095.9 | 1057.3 | 1356.7 | 2972.8 |
| 검색 흔한 낱말 동시 1 p50(ms) | 87.4 | 43.8 | 43 | 31 |
| 검색 흔한 낱말 동시 16(건/초) | 29.8 | 61.9 | 63.2 | 126.3 |
| 검색 드문 낱말 동시 16(건/초) | 28.9 | 63 | 62.9 | 102.6 |
| 이슈 생성 동시 8(건/초) | 338 | 337.5 | 378.4 | 646.6 |
| 댓글 생성 동시 8(건/초) | 536.4 | 528 | 573 | 1012.1 |

- **대소문자 무시 정렬 규칙(`utf8_en_ci`)**: 검색이 `lower(x) like 패턴`일 때 Cubrid 방언이 `x collate utf8_en_ci like 패턴`으로 그린다(A-630). 낱말 검색이 약 2배 빨라지고 다른 항목은 그대로이다. 스키마는 바꾸지 않는다. `utf8_ko_ci`는 없고(내장 규칙은 `utf8_bin`, `utf8_en_cs`, `utf8_en_ci`, `utf8_ko_cs`, `utf8_tr_cs`) 한글에는 대소문자가 없어 `utf8_en_ci`로 한글과 영문을 모두 정확히 찾는다. 조건은 **DB 문자 집합이 UTF-8**인 것이다(로케일 이름은 상관없다. ISO-8859-1 DB에서는 쓸 수 없어 시작할 때 확인하고 아니면 `lower()`로 되돌아간다).
- **브로커 `SQL_LOG=OFF`**: 읽기 +19~28%, 쓰기 +9~12%(A-631). 문제를 추적해야 하면 `ERROR`(오류가 난 질의만 기록)를 쓴다(`ERROR`는 측정하지 않았다).

### 6.2 효과가 없었던 서버와 브로커 설정(같은 조건, 정렬 규칙과 `SQL_LOG=OFF`가 기준)

| 변형 | 이슈 단건 조회 동시 16(건/초) | 댓글 목록 동시 16(건/초) | 검색 동시 16(건/초) | 이슈 생성 동시 8(건/초) |
|---|---|---|---|---|
| 기준(정렬 규칙 + `SQL_LOG=OFF`) | 1063.6 | 1356.7 | 63.2 | 378.4 |
| 서버 `data_buffer_size=2G`(기본 512M) | 1071 | 1300.8 | 61.6 | 370 |
| 서버 `thread_core_count=4`(기본은 호스트 코어 수 16) | 968.5 | 1142.4 | 61.5 | 341.2 |
| 브로커 CAS 24개 선기동 + `KEEP_CONNECTION=ON` | 1033 | 1303 | 66.8 | 356.8 |

세 변형 모두 기준과 같거나 약간 나쁘다(차이는 측정 편차 안이다). 데이터 버퍼는 DB 메모리가 919MB에서 1.29GB로 늘어 적용된 것은 확인했지만 처리량은 그대로이다.

### 6.3 서버 질의 결과 캐시(상한만 JDBC 단독으로 확인)

`max_query_cache_entries`와 `query_cache_size_in_pages`를 켜고 질의에 `/*+ QUERY_CACHE */` 힌트를 붙이면(공식 문서상 힌트가 있어야 쓰인다) 단건 조회 동시 16이 23,511에서 26,171건/초로 약 11% 늘었다. 같은 조건의 반복 측정 편차(19,584 대 23,511)가 그만큼 커서 의미 있는 이득이 아니고, 하이버네이트가 만드는 SQL에 힌트를 넣는 작업의 위험에 비해 작다고 보아 적용하지 않았다.

### 6.4 DB 순수 처리 능력(JDBC 단독, 단건 조회 동시 16, CPU 4개)

| DB | 읽기(건/초) | 쓰기 동시 8(건/초) |
|---|---|---|
| PostgreSQL | 126,982 | 21,896 |
| MariaDB | 85,298 | 13,495 |
| Cubrid(기본) | 17,245 | 13,185 |
| Cubrid(`SQL_LOG=OFF`) | 23,804 | 15,294 |
| Cubrid(`SQL_LOG=OFF` + CPU 코어 고정) | 30,560 | 12,924 |
| Cubrid(`SQL_LOG=OFF` + 호스트 네트워크) | 22,015 | 16,604 |

- Cubrid의 순수 읽기는 설정을 최대한 맞춰도 PostgreSQL의 약 1/4이다. 질의 하나의 비용이 구조적으로 크다(브로커 중계 프로세스와 서버, 두 단계). CPU를 4개에서 8개로 늘리면 읽기는 정확히 2배(16,475에서 33,963건/초)가 되고, 앱 수준에서는 이슈 단건 API 동시 16이 800에서 1,036건/초(+30%), 검색 동시 16이 97에서 204건/초(2.1배)가 되지만 쓰기와 이슈 목록 화면은 그대로이다(이 CPU 8개 측정은 문장 캐시 적용 직후 코드, 정렬 규칙 적용 전이다).
- 쓰기의 순수 능력은 MariaDB와 같다. 앱에서 쓰기가 느린 것은 커밋 때문이 아니라 요청당 질의 수 때문이다(그래서 `group_commit_interval_in_msecs`는 시험하지 않았다).
- **CPU는 브로커 중계가 더 쓴다.** 단건 조회 동시 16 부하 중 컨테이너 CPU 415% 가운데 `cub_cas`(브로커가 연결마다 띄우는 중계 프로세스) 245%(59%), `cub_server` 170%(41%)였다. 질의 하나에 CAS가 약 0.10ms, 서버가 약 0.07ms를 쓴다. 서버 매개변수는 41%만 건드리고 CAS 쪽에는 `SQL_LOG`가 유일한 의미 있는 설정이었다.
- **DB 페이지 크기는 영향이 없었다.** 4KB와 16KB에서 낱말 검색 21.91 대 21.98ms, 읽기 24,420 대 23,849건/초, 쓰기 14,237 대 14,412건/초였다(4KB가 실제로 적용되었는지는 확인하지 못했다).
- 컨테이너 조건(CPU를 한도로 줄지 코어를 고정할지, 네트워크 경로)은 결과를 ±30% 움직이지만 격차의 이유는 아니다. 이 표는 시험 조건 비교이고 운영 권장이 아니다.

## 7. CUBRID 공식 자료에서 확인한 것

출처는 CUBRID 11.4 매뉴얼의 시스템 파라미터(`admin/config`)와 JDBC(`api/jdbc`)이다.

| 항목 | 문서의 내용 | 판단 |
|---|---|---|
| JDBC `usePreparedStmtCache` | 기본 꺼짐. `preparedStmtCacheSize` 기본 25, `preparedStmtCacheSqlLimit` 기본 256자 | **적용함**(A-629): 500개, 16,384자. 접속 주소를 자동으로 보강한다 |
| 브로커 `SQL_LOG` | 기본 `ON`(모든 SQL 기록). `OFF`, `ERROR`, `NOTICE`, `TIMEOUT` 선택 | 운영에서 `ERROR`나 `OFF`를 권장(3~8% 개선 측정) |
| 서버 `group_commit_interval_in_msecs` | 기본 0. 지정한 시간 안의 커밋을 묶어 로그를 한 번에 씀 | 안전한 쓰기 개선 후보. 측정하지 않았다 |
| 서버 `async_commit` | 로그를 쓰기 전에 커밋을 끝냄. 장애 시 이미 커밋된 트랜잭션을 복구할 수 없다고 경고 | **권하지 않음**(내구성 손실) |
| 서버 `data_buffer_size` | 기본 `32,768 × 페이지 크기`. 시스템 메모리의 2/3 미만 | 이 데이터 규모에서는 충분 |
| 서버 `max_clients`와 브로커 `MAX_NUM_APPL_SERVER` | 함께 정함. `max_clients`는 모든 브로커의 CAS 최대 수 합에 약 10을 더한 값 | 운영 안내에 필요(시험은 300) |
| 브로커 `STATEMENT_POOLING` | 기본 `ON`. 문장 핸들을 풀에 둠 | 켜 둔다. 끄면 닫힌 문장 접근 오류가 난다 |
| 브로커 `JDBC_CACHE`, JDBC `clientCacheSize` | SELECT 결과를 클라이언트에 캐시 | 낡은 데이터 위험이 있어 권하지 않음 |

## 8. 한계와 확인하지 못한 것

- **단일 실행이다.** 개선 전은 두 번의 평균이지만 현재 수치는 한 번이다. 두 번 반복한 개선 전 측정에서 편차는 대부분 ±3%, 가장 큰 것이 14%였다. 차이가 작은 항목(예: MariaDB와 PostgreSQL의 일부)은 순위를 단정하지 않는다.
- **합성 부하이다.** 이슈 5,000건, 댓글 4,000건, 요청 7종의 반복이다. 혼합 부하, 더 큰 데이터, 긴 시간 운영, 장애와 복구, 이중화는 보지 않았다.
- **낱말 검색은 전체를 훑는 `like` 질의이다.** 인덱스나 검색 엔진이 없는 상태의 비교이므로 데이터가 커지면 세 DB 모두 느려진다(검색 엔진 설계는 `search-engine-design.md`). Cubrid의 검색이 특히 느리다(PostgreSQL의 약 24%).
- **DB 설정은 기본값이다.** MariaDB와 PostgreSQL을 튜닝하면 달라질 수 있다. Cubrid는 6절의 설정을 시도했고 `group_commit_interval_in_msecs`와 `ERROR` 로그 수준은 측정하지 않았다. Cubrid만 이렇게 조정한 비교이므로 세 DB를 같은 노력으로 맞춘 결과가 아니다.
- **MSSQL은 이번 비교에 넣지 않았다.**
- 호스트에 다른 컨테이너가 있었고 DB를 하나씩 번갈아 돌려 순서의 영향을 따로 상쇄하지 않았다(개선 전 측정은 순서를 거꾸로 해 한 번 반복했다).

## 10. 남은 과제와 이어서 볼 곳

Cubrid 성능 작업은 2026-11-17에 여기서 마무리했다(선생님 결정, `roadmap.md`의 보류 항목). 설정으로 더 얻을 것은 없다고 판단했고, 다시 볼 때의 후보와 근거는 다음과 같다.

| 후보 | 근거와 기대 | 상태 |
|---|---|---|
| 요청당 질의를 더 줄이기 | Cubrid는 CPU의 59%를 브로커 중계(`cub_cas`)가 쓰고 질의 하나가 CAS와 서버 CPU 약 0.17ms를 쓴다. 이슈 단건 API 18개, 상세 33개, 목록 37개에 중복이 남았다(프로젝트와 규칙을 3~4번 읽음, 규칙이 즉시 로딩이라 프로젝트를 읽을 때마다 질의 2개, 메뉴 설정이 프로젝트를 다시 읽음, 첨부 3번, 관리자 여부 2번). 규칙을 `RequestMemo`로 요청 범위에 보관하면 단건 API가 약 14개(-22%), 상세가 약 27개(-18%)가 될 것으로 추정한다 | 미구현(추정). 규칙의 즉시 로딩은 풀 리퀘스트 병합이 트랜잭션 밖에서도 읽으려는 의도(D-46)라 매핑이나 트랜잭션 경계를 건드리지 않는 방식을 권한다 |
| CPU 증설 | CPU 4개에서 8개로 늘리면 JDBC 단독 읽기가 정확히 2배, 앱 수준에서 단건 API +30%, 검색 2.1배 | 운영 배치 안내에 적을 만한 내용 |
| 페이지 크기 확인 | 4KB와 16KB가 차이 없었으나 4KB가 실제로 적용되었는지(`db_page_size`) 확인하지 못했다 | 미확인 |
| `group_commit_interval_in_msecs`, `SQL_LOG=ERROR` | 순수 쓰기 능력이 MariaDB와 같아 커밋이 병목이 아니라고 보아 시험하지 않았고, `ERROR`는 측정하지 않았다 | 미측정 |
| `lower()`와 `utf8_en_ci`의 차이 | 한글과 영문은 같으나 터키어 `İ`, 독일어 `ß`, 악센트 문자는 확인하지 못했다 | 미확인 |
| 다른 DB의 `cast` 제거 | `cast(x as string)`은 v2 첫 구현에서 들어갔고 이유를 적은 기록이 없다. PostgreSQL, MariaDB, Cubrid에서 `cast`가 없어도 결과가 같고 MariaDB는 35% 빨라졌다. MSSQL은 `cast`가 한글을 깨뜨려 방언 패치가 있다(`YonaSqlServerDialect`). H2와 MSSQL에서 직접 확인하지 못했다 | 이번 작업은 Cubrid 한정이라 하지 않았다 |

시도해 효과가 없던 설정은 6.2절과 6.3절에 있다(데이터 버퍼 2G, 스레드 그룹 수, CAS 선기동, 서버 질의 결과 캐시). `async_commit`은 장애 시 커밋된 데이터를 잃으므로 권하지 않는다.
