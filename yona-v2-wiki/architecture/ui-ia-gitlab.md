# GitLab 방식 UI 정보 구조(IA) 제안

> **상태: 선생님 승인(2026-11-11, `decisions.md` D-134).** "대체로 동의하는데 폰과 갤럭시 폴드 접힘은 사이드바 기본 접힘"이라고 하셨다. 권장안 8가지를 받아들이고 3번(기본 상태)만 이 말씀대로 고쳤다(4.5절, 8절). 구현은 아직 하지 않았다. 브랜치 `ui-improvements`에서 P0부터 진행한다.
> GitLab의 구조는 **일반 지식**을 기준으로 적었고 현재 GitLab 버전의 화면과 대조하지 않았다(9절).

## 1. 목표와 제약

- **목표**: 화면 이동의 틀을 GitLab처럼 **맥락(전역, 프로젝트, 조직, 사용자 설정, 사이트 관리)마다 왼쪽 사이드바 하나**로 모으고, 위에는 경로(breadcrumb)와 페이지 머리를 둔다. 지금은 맥락마다 틀이 제각각이다(상단 탭, 설정 탭, 관리 사이드바가 섞여 있다).
- **지킬 것**
  1. **주소(URL)와 요청, 응답 계약은 바꾸지 않는다.** 바뀌는 것은 화면의 틀(내비게이션)뿐이다. v1.6의 주소를 쓰는 외부 도구, 북마크, 문서 링크가 그대로 동작해야 한다.
  2. 화면 안의 기능과 동작은 그대로다. 메뉴의 **이름은 v1.6 용어를 유지**한다(예: "코드 주고받기"). 이름을 GitLab 용어로 바꾸는 것은 별도 결정이다(8절).
  3. 마크업은 BS5 고유 모양으로 쓴다(호환 층 금지, `decisions.md` D-56). 페이지 전환은 htmx(D-96)를 쓴다.
  4. Vue 컴포넌트와 2단 보기 개선은 **이 작업의 범위가 아니다**(나중 UI 개편, D-96). 이 IA는 그 개편이 올라탈 틀이다.
- **v1.6 동등성 원칙과의 관계**: AGENTS.md의 "v1.6을 그대로 따른다"에 비추면 내비게이션 재구성은 **화면 모양을 바꾸는 일**이라 선생님의 승인이 필요하다(D-134). 기능, 주소, 계약은 그대로이므로 동등성 점검(`tools/v16-diff` 회귀)의 응답 비교에는 영향이 없어야 하고, 영향이 나오면 결함으로 본다.

## 2. 현재 정보 구조(코드와 화면에서 확인, 2026-11-11)

| 조직 설정 | 상단 탭(`organization/partial-settingmenu`) | 설정, 그룹 멤버, 감사 로그, OAuth 앱, OAuth 앱 정책, 그룹 삭제 |

**관찰한 문제**
- 같은 종류의 "설정"이 맥락마다 다른 틀이다. 사이트 관리만 사이드바이고 사용자, 프로젝트, 조직 설정은 탭이다. 사용자 설정은 탭이 **11개**라 두 줄로 넘친다(실제 캡처에서 확인).
- 항목이 성격과 무관하게 한 줄로 나열되어 찾기 어렵다(사용자 설정의 비밀번호, 이메일, 연결된 계정은 "계정", 토큰, SSH, GPG, 2단계는 "접근과 보안"이라 묶을 수 있다).
- 프로젝트 안의 기능이 상단 가로 메뉴에 다 올라가 있어, 하위 화면(코드의 파일, 커밋, 브랜치, 태그와 이슈의 라벨, 마일스톤)이 별도의 보조 탭으로 흩어져 있다.
- 현재 위치를 알려 주는 경로(breadcrumb)가 없다.
- **왼쪽 사이드바가 이미 있지만 꺼져 있고(핀으로 켠다), 메뉴가 아니라 "프로젝트, 조직, 최근 이슈를 바꿔 가는 목록"이다.** 즉 GitLab의 맥락 전환기에 가깝고 맥락별 메뉴는 없다. 같은 세 목록이 오른쪽 패널(`#mySidenav`)에도 중복된다.
- 이 사이드바는 **iframe**으로 구현되어 있다. 핀을 켜면 같은 주소가 프레임 페이지(왼쪽 사이드바 + `mainFrame`)로 열리고 본문은 프레임 안에 들어간다(`window.parent` 분기, `layout.html`). 켠 상태는 브라우저 저장소(`shallWeOpenLeftNavigation`)에 기억한다. 프레임 안의 본문에는 맥락별 메뉴를 넣을 수 없고, 주소 표시줄과 뒤로 가기, htmx 전환이 프레임 때문에 일반 페이지와 다르게 동작한다.

**반응형 현황(2026-11-11, 레거시 화면을 Playwright로 측정, 7개 화면 x 6개 폭)**

| 폭(CSS px) | 기기 가정 | 가로 스크롤 | 비고 |
|---|---|---|---|
| 344 | 갤럭시 폴드 접힘(커버 화면) | 7개 중 5개 | 모두 정확히 +10px(354>344) |
| 390 | 일반 폰 | 7개 중 5개 | +10px(400>390) |
| 673 | 갤럭시 폴드 펼침 | 7개 중 5개 | +10px(683>673) |
| 768, 1024, 1280 | 태블릿 세로, 가로, 데스크톱 | 없음 | |

- **+10px의 원인**: Bootstrap의 `.row`가 여백 있는 `.container` 없이 `.project-page-wrap`, `.site-setting-wrap` 같은 영역에 바로 놓여 음수 여백 때문에 폭이 화면보다 20px 넓은 364px이 되고(화면 344px일 때), 그 결과 문서가 10px 넘친다. 넘치지 않는 화면은 사용자 설정과 규칙 목록뿐이었다(다른 래퍼를 쓴다). 새 셸의 본문 영역이 여백을 책임지면 근본적으로 없어진다.
- 첫 화면에서 높이나 너비가 32px 미만인 터치 대상(링크, 단추, 입력란)이 폰에서 12~23개, 태블릿에서 15~43개이다.
- 지금의 모바일 처리: 핀 사이드바는 `hide-in-mobile`로 숨고, 프로젝트 상단 메뉴는 첫 글자 약어(H C I P R W)로 줄어든다. 사용자 오른쪽 패널(`#mySidenav`)은 화면 밖에 있다. 폴드 펼침(673px)과 태블릿 세로(768px)를 위한 별도 단계는 없다.

## 3. GitLab IA의 기준(일반 지식)

- **왼쪽 사이드바 하나**가 맥락을 담는다. 맥락은 프로젝트, 그룹, 사용자 설정, 관리 영역이다. 사이드바 위에 맥락의 이름과 아이콘이 있고, 항목은 **성격별 묶음**으로 정렬되며 하위 항목은 펼쳐진다.
- **상단 바**는 전역 기능만 둔다: 사이드바 접기, 검색, 만들기(+), 이슈, 병합 요청, 할 일, 사용자 메뉴.
- 본문 위에 **경로(breadcrumb)**와 **페이지 머리**(제목, 주요 단추)를 둔다.
- 설정은 **맥락의 맨 아래 한 묶음**이고, 설정 안에서도 사이드바가 이어지거나 설정 전용 사이드바로 바뀐다.
- 프로젝트 사이드바의 묶음(버전에 따라 이름이 다르다): 개요, 관리(Manage), 계획(Plan), 코드(Code), 빌드(Build), 보안(Secure), 배포(Deploy), 운영(Operate), 모니터링(Monitor), 분석(Analyze), 설정(Settings).

## 4. 제안 IA

### 4.1 틀(셸)

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ☰  Y  프로젝트 ▾  [ 검색… ]            +  이슈  코드 주고받기  🔔  사용자 ▾ │  전역 상단 바
├───────────────┬──────────────────────────────────────────────────────────┤
│ [맥락 머리]   │  경로: 조직 / 프로젝트 / 이슈          [주요 단추]          │  경로와 페이지 머리
│  홈           │ ───────────────────────────────────────────────────────  │
│  코드  ▸      │                                                          │
│  이슈  ▸      │                     본 문                                │
│  코드 주고받기│                                                          │
│  ...          │                                                          │
│  설정  ▸      │                                                          │
└───────────────┴──────────────────────────────────────────────────────────┘
```

- 왼쪽 사이드바는 맥락마다 항목만 바뀐다. 접으면 아이콘만 남고, 좁은 화면(`< 992px`)에서는 숨겨졌다가 ☰로 연다.
- 현재 항목을 강조하고, 묶음은 현재 화면이 속하면 펼쳐 둔다.

### 4.2 맥락별 구조

**① 전역(홈)**
- 상단 바: 사이드바 열기(지금의 핀 화살표 자리), 로고, 검색(범위 선택 유지), `+`(새 프로젝트, 새 조직, 새 이슈), **내 이슈**, **코드 주고받기**(내가 관련된 것), 알림, 사용자 메뉴(프로필, 설정, 사이트 관리, 로그아웃). 오른쪽 `#mySidenav`의 중복 목록은 없앤다.
- 홈 사이드바("내 작업"): 즐겨찾기, 프로젝트, 최근 읽은 이슈, 최근 방문, 내가 만든, 지켜보는, 참여 중인. 기존 홈 탭 7개를 그대로 옮긴다. 별도로 **탐색**: 프로젝트 목록(`/projects`), 조직 목록.

**② 프로젝트**

| 묶음 | 항목 | 현재 위치 |
|---|---|---|
| (개요) | 프로젝트 홈 | 상단 메뉴 "홈" |
| 코드 | 파일, 커밋, 브랜치, 태그 | 상단 메뉴 "코드"와 보조 탭 |
| 계획 | 이슈, 라벨, 마일스톤, 게시판 | 이슈의 보조 메뉴, 상단 메뉴 "게시판" |
| 협업 | 코드 주고받기, 리뷰 | 상단 메뉴 |
| 문서 | 위키 | 상단 메뉴 |
| 설정 | 일반, 멤버, 규칙, 배포 키, Git LFS, 웹훅, **고급**(이관, 저장소 타입 변경, 삭제) | 설정 탭 10개 |

- "이슈 라벨"은 프로젝트 설정 탭에 있으나 쓰임새가 이슈 계획이라 **계획 묶음으로 옮긴다**(주소는 `/issue/labelsform` 그대로).
- 이관, 저장소 타입 변경, 삭제는 설정 맨 아래 **위험 구역**(고급)으로 모은다.

**③ 조직(그룹)**

| 묶음 | 항목 |
|---|---|
| (개요) | 조직 홈 |
| 계획 | 이슈, 게시판 |
| 협업 | 코드 주고받기 |
| 설정 | 일반, 멤버, **접근**(OAuth 앱, OAuth 앱 정책), 감사 로그, 삭제(고급) |

**④ 사용자 설정**(탭 11개를 묶음 5개로)

| 묶음 | 항목 |
|---|---|
| 프로필 | 프로필 수정 |
| 계정 | 비밀번호 변경, 이메일 설정, 연결된 계정 |
| 알림 | 알림 설정 |
| 접근과 보안 | 사용자 토큰, SSH 키, GPG 키, 2단계 인증, 보안 기록 |
| 애플리케이션 | OAuth 앱 |

**⑤ 사이트 관리**(이미 사이드바이므로 묶음만 더한다)

| 묶음 | 항목 |
|---|---|
| 개요 | 사용자, 프로젝트, 이슈, 게시물 |
| 메시지 | 메일 발송, 대량 메일 발송 |
| 시스템 | 업데이트, 시스템 진단, 감사 로그 |
| 설정 | 보안, SSO, OAuth 앱, LFS |

### 4.2.1 지금의 핀 사이드바는 "전환기"로 새 셸에 흡수한다

- 새 사이드바의 맨 위에 **전환기**(맥락 머리)를 둔다. 누르면 지금의 핀 사이드바와 같은 패널이 펼쳐진다: 즐겨찾기, 프로젝트, 최근 읽은 이슈 3탭, 이름 필터, 조직별 묶음, 새로고침. 데이터와 조회(`index/my-organization-list`, `my-project-list`, `my-recent-issue-list`)는 그대로 쓴다.
- 전환기 아래에 **맥락별 메뉴**(4.2의 묶음)가 이어진다. 그래서 "다른 프로젝트로 가기"와 "이 프로젝트 안에서 가기"가 한 사이드바 안에 있다.
- **iframe을 쓰지 않는다.** 사이드바는 본문과 같은 문서의 일부이다. 같은 주소로 열면 그냥 일반 페이지이고, 뒤로 가기와 주소 표시줄, htmx 전환이 모두 정상이다.
- 기억하는 값은 지금과 같은 키(`shallWeOpenLeftNavigation`)를 이어 쓴다. 이미 핀을 켜 둔 사용자는 새 셸에서도 펼쳐진 상태로 시작한다. 옛 `/user/sidebar?path=...` 주소는 `path`로 되돌리는 이동으로 남겨 북마크가 깨지지 않게 한다(주소 계약이므로 유지).

### 4.3 경로(breadcrumb) 규칙

`조직 또는 사용자 / 프로젝트 / 섹션 / 페이지`. 설정과 관리 화면은 `설정 / 항목`, 사이트 관리는 `사이트 관리 / 묶음 / 항목`이다. 마지막 항목은 링크가 아니다.

### 4.4 페이지 머리 규칙

제목(한 줄), 설명(선택), 주요 단추(오른쪽 정렬, 한 개는 강조). 목록 화면의 검색과 필터는 머리 아래 한 줄이다. 이 규칙은 지금 화면마다 다른 제목 크기와 단추 위치를 맞춘다.

### 4.5 반응형: 폰, 태블릿, 갤럭시 폴드(접힘과 펼침)

**기준 폭**(CSS px, 기기 값은 일반 지식이며 실제 기기로 확인하지 못했다. 9절)

| 구간 | 폭 | 대표 기기 | 사이드바 | 본문 |
|---|---|---|---|---|
| 좁음 | 600 미만 | 폰(360~430), 폴드 접힘(약 344~360) | **서랍, 기본 접힘**(화면 밖, 닫힌 채 시작). 상단 왼쪽 ☰(지금의 핀 화살표 자리)로 열고 본문 위에 겹친다. 전환기도 서랍 안에 있다 | 한 칸. 폼은 한 열, 표는 가로 스크롤 상자나 카드로 쌓기 |
| 중간 | 600~1023 | **폴드 펼침(약 673~717, 정사각에 가까움)**, 태블릿 세로(768~834) | **아이콘 레일**(약 56px)이 늘 보이고, 누르면 본문을 밀지 않고 겹쳐서 펼친다 | 레일 옆의 한 칸(폭 600 안팎 확보). 2단 보기는 900 이상에서만 |
| 넓음 | 1024 이상 | 태블릿 가로(1024~1194), 데스크톱 | **고정 사이드바, 기본 펼침**(256px). 사용자가 레일로 접을 수 있고 기억한다 | 본문 최대 폭 제한 |

**기본 상태(선생님 결정, 2026-11-11)**: 구간마다 기본이 다르다.
- 좁음(폰, 폴드 접힘): **기본 접힘.** 페이지를 열 때마다 닫힌 채 시작한다. 서랍을 열어도 **기억하지 않고**, 다른 페이지로 가면 다시 닫힌다(이동하면 본문이 보여야 하므로).
- 중간(폴드 펼침, 태블릿 세로): 레일이 기본이다(접힌 모양). 레일을 눌러 펼친 상태는 겹침일 뿐 저장하지 않는다.
- 넓음: **기본 펼침.** 접은 상태(레일)는 브라우저가 기억한다.
- **기억 값은 넓음에서만 쓴다.** 지금의 키(`shallWeOpenLeftNavigation`)가 열림으로 남아 있어도, 같은 브라우저를 폰이나 폴드 접힘 폭으로 열면 무시하고 닫힌 채 시작한다. 폴드를 접고 펴서 폭이 구간을 넘나들면 구간의 기본 상태로 돌아간다(펼침 -> 접힘이면 서랍이 닫히고, 접힘 -> 펼침이면 레일).

**새로고침과 첫 그림(깜빡임 없음)**
- 새로고침의 결과는 위 규칙 그대로다: 넓음은 펼침 또는 기억한 접힘, 중간은 레일, 좁음은 닫힘. 서랍과 레일을 눌러 펼친 상태(겹침)는 저장하지 않으므로 새로고침하면 구간의 기본 상태로 돌아간다. 사이드바 링크로 화면을 옮기는 htmx 전환은 새로고침이 아니라서 사이드바 상태가 그대로 남는다.
- **구간별 기본 상태는 CSS 미디어 쿼리만으로 처음부터 맞게 그린다**(스크립트가 필요 없다).
- **"넓음에서 접은 상태"만 저장값이 필요하므로** 깜빡임이 생길 수 있다(펼쳐 그렸다가 접힘). 이를 막으려고 `<head>` 맨 위에 **그리기 전에 도는 짧은 스크립트**(수백 바이트)를 두어 저장값을 읽고 폭이 1024 이상이며 접힘이면 `<html>`에 `data-sidebar="collapsed"`를 붙인다. CSS는 `@media (min-width: 1024px)` 안에서만 이 속성을 따른다. 저장소 접근이 막혀도(비공개 창 등) 예외를 삼키고 기본 상태(펼침)로 그린다.
- **전환 효과(transition)는 첫 그림 뒤에만 켠다.** 로드가 끝난 뒤 `<html>`에 `sidebar-ready`를 붙이고 그 뒤의 접고 펼침에만 애니메이션을 준다. 안 그러면 첫 그림에서 기본 상태에서 기억한 상태로 미끄러지며 바뀐다.
- **저장값의 이름과 이전 규칙**: 새 키 `shellSidebarCollapsed`(`true`일 때 넓음에서 접힘)를 쓰고, 예전 키 `shallWeOpenLeftNavigation`은 처음 한 번만 읽어 옮긴다. 예전 값이 `true`(핀을 켬)면 펼침, **`false`(핀을 직접 끔)면 접힘으로 옮기고**, 값이 없으면(핀을 쓴 적 없음) 펼침 기본을 따른다. 옮긴 뒤 예전 키는 지운다.
- 같은 브라우저의 다른 탭에서 바꾼 값은 `storage` 이벤트와 `pageshow`(뒤로 가기 복원)로 다시 맞춘다.
- 대안은 서버가 쿠키를 읽어 `<html>`의 속성을 그려 주는 방식이다(스크립트와 CSP 영향이 없고 스크립트를 꺼도 맞다. 대신 요청마다 쿠키가 실리고 쿠키를 쓰는 코드가 필요하다). 이 안은 기존 저장 방식과 키를 이어 쓰고 서버를 건드리지 않아 위의 스크립트 방식을 권한다(A-454).

**폴드 대응에서 지킬 것**
1. **접고 펴면 폭이 바로 바뀐다.** 새로 고침 없이 `resize`가 일어나므로 구간 전환은 순수 CSS(미디어 쿼리, 컨테이너 쿼리)로 하고, 서랍 열림, 스크롤 위치, htmx로 바꾼 본문, 폼 입력값이 전환 뒤에도 남아야 한다. 기기 판별(User-Agent)과 방향(`orientation`)에 기대지 않는다. 펼친 화면은 정사각에 가까워 "가로면 넓다"는 가정이 틀린다.
2. (폭이 바뀔 때 서랍을 열어 둔 채 구간만 바뀌면 열린 서랍이 겹쳐 남을 수 있으나, 구간의 기본 상태 규칙이 우선한다.) 높이는 `dvh`(주소 표시줄이 바뀌어도 맞는 높이)로 잡고, 반쯤 접은 자세(Flex 모드)에서도 주요 단추가 화면 안에 있게 한다.
3. 두 화면으로 나뉘는 기기용 `horizontal-viewport-segments` 미디어 쿼리는 쓰지 않는다. 삼성 폴드는 하나의 뷰포트이고, 그 쿼리가 크롬에서 어떤 기기에 적용되는지 확인하지 못했다.
4. 터치 기기에서는 `pointer: coarse`로 터치 대상을 키운다(최소 44x44px). 입력란 글자는 16px 이상(iOS 확대 방지). 호버로만 보이는 정보는 두지 않는다(`hover: none`).
5. 노치와 카메라 구멍을 위해 `viewport-fit=cover`와 안전 영역(`env(safe-area-inset-*)`)을 쓴다.
6. 접근성: 서랍은 열면 초점을 안으로 모으고(focus trap), Esc와 바깥 누르기로 닫고, 닫으면 ☰로 초점을 돌려준다. 레일의 아이콘에는 이름(`aria-label`)이 있다.

**시험(단계마다)**: Playwright 뷰포트 매트릭스 **344x882, 390x844, 673x841, 768x1024, 1024x768, 1280x800**를 각 맥락의 대표 화면에 돌려 (가) 가로 스크롤 없음, (나) 구간별 사이드바 상태(서랍, 레일, 고정), (다) 첫 화면의 터치 대상 44px 이상, (라) 서랍의 초점 이동과 Esc, (마) 폭을 바꿔도(344 -> 673 -> 344) 입력값과 스크롤 유지를 확인한다. (바) **좁음에서 불러오면 서랍이 닫혀 있다**(기억 값이 열림이어도, 344와 390 모두). (사) 넓음에서 접고 다시 불러오면 레일로 시작한다. (아) **첫 그림부터 깜빡임이 없다**: 접힘을 저장한 채 넓음 폭으로 불러올 때, 첫 레이아웃과 그 뒤의 사이드바 폭이 같고(폭이 바뀐 횟수 0) 전환 효과가 돌지 않는다. (자) 저장소 접근이 예외를 던져도 기본 상태로 정상 그려진다. (차) 예전 키 값 `true`, `false`, 없음이 각각 펼침, 접힘, 펼침으로 옮겨지고 예전 키가 지워진다. (카) 접힘 저장값은 좁음과 중간에서 무시된다. 실제 갤럭시 폴드 기기로는 확인하지 못하므로 에뮬레이션(뷰포트와 터치)이다.

## 9. 확인하지 못한 것

- 이 앱에 **내용 보안 정책(CSP)**이 있어 인라인 스크립트가 막히는지는 확인하지 못했다. 막혀 있다면 그리기 전 스크립트에 nonce가 필요하거나 쿠키 방식(4.5절 대안)으로 바꿔야 한다. P0 착수 때 확인한다.

- GitLab의 현재 화면과 용어는 대조하지 않았다(일반 지식).
- 새 셸이 모바일(폭 400px 안팎)에서 어떻게 보이는지는 구현 전이라 정하지 못했다(P0에서 정한다). 지금의 핀 사이드바는 모바일에서 숨겨진다(`hide-in-mobile`).
- **갤럭시 폴드와 태블릿 기기의 정확한 CSS 폭과 접힘 상태의 화면 비율**은 일반 지식이다. 실제 기기로는 확인하지 못했고 에뮬레이션 뷰포트(344, 673 등)로만 측정했다. 폰에서의 동작(터치, 서랍 제스처)도 실제 기기 확인이 필요하다.
- 핀 사이드바를 켠 채로 본문의 각 화면(프레임 안)이 지금 어떻게 동작하는지, 켜 둔 사용자가 얼마나 되는지는 확인하지 못했다. 화면 모양과 구조만 보았다.
- 위키 페이지 보기와 이력, OAuth 동의 화면 등 일부 화면은 이 IA에서 어느 맥락에 들어가는지(위키는 프로젝트의 문서 묶음, 동의 화면은 셸 밖의 독립 화면)만 정했고, 새 셸 안에서의 모양은 확인하지 못했다.
