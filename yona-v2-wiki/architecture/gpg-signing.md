# GPG 커밋 서명 검증 (X-4, D-65)

**상태: 구현 완료(2026-11-02).** 결정과 이유는 [decisions.md D-65](../decisions.md), 구현 판단은 A-321, A-322이다. v1.6에는 없는 추가 항목이며 서명이 없는 커밋의 화면과 응답, 기존 테이블은 바뀌지 않는다.

## 한눈에 보기

| 영역 | 내용 |
|---|---|
| 키 등록 | 사용자 설정의 "GPG 키" 탭. **목록 화면**(삭제 버튼 하나)과 **추가 화면**(이름, 공개키) 두 개로 나눈다(D-65 8번). 이후 키류 설정(X-3 SSH 공개키 등)도 같은 구성이다 |
| 저장 | 새 테이블 `gpg_key`. 공개키 한 묶음을 주 키 한 행과 하위 키 행들로 둔다(`parent_id`). 지문은 사이트 전체에서 유일하다 |
| 검증 | 서버 로컬 키링이 아니라 **등록된 공개키**로 BouncyCastle(`bcpg-jdk18on`, `bcprov-jdk18on` 1.82)가 직접 한다. JGit의 PGP 모듈(`gpg.bc`)은 `~/.gnupg`를 읽어 맞지 않는다 |
| 표시 | 커밋 이력, 커밋 상세, 풀 리퀘스트 변경 화면의 커밋 정보, 태그 목록. 서명이 없으면 아무것도 보이지 않는다(GitHub와 같다) |
| REST | `/user/gpg_keys`(목록, 한 건, 등록, 삭제), `/users/{user}/gpg_keys`, 태그와 풀 리퀘스트 커밋 응답의 `verification` |
| 규칙 | 규칙 묶음의 "서명 커밋 필수"(푸시 훅과 병합 검사) |
| 감사와 지표 | `gpg_key.added`, `gpg_key.deleted`, `yona.gpg.verifications{target, reason}` |

## 판정 (GitHub의 `verification.reason`과 같은 코드)

검증 순서는 서명 읽기, 키 찾기(주 키와 하위 키의 키 ID), 서명 수학 검증, 키 상태(만료, 폐기, 서명 용도), 키 주인, 이메일이다. 변조된 서명이 키 상태 이유에 가려지지 않도록 수학 검증을 먼저 한다.

| 코드 | 의미 |
|---|---|
| `valid` | 서명이 맞고 키 주인이 활성 사용자이며, 커밋터(태그는 태그를 단 사람) 이메일이 키의 사용자 ID에 있고 주인이 확인한 이메일이다 |
| `unsigned` | 서명이 없다 |
| `unknown_key` | 서명한 키가 등록된 키 가운데 없다 |
| `expired_key` | **검증하는 시점에** 키(또는 주 키)가 만료되었거나 폐기되었다. 폐기하면 이전 서명도 믿지 않는다(D-65 5번) |
| `not_signing_key` | 서명 용도가 없는 키로 서명했다 |
| `malformed_signature` | 서명 글을 읽을 수 없다 |
| `invalid` | 서명이 내용과 맞지 않는다(내용 변조, 다른 키) |
| `no_user` | 키 주인이 삭제되었거나 잠겼다 |
| `bad_email` | 커밋터 이메일이 키의 사용자 ID에 없다 |
| `unverified_email` | 커밋터 이메일이 주인이 확인한 이메일(대표 이메일 또는 확인한 보조 이메일)이 아니다 |

결과는 키와 이메일 등록에 따라 바뀌므로 **저장하지 않고 요청마다 계산**한다(서명 한 건은 밀리초 미만). 읽은 공개키 묶음만 캐시한다(키 행 번호가 열쇠, 행은 등록 뒤 바뀌지 않는다).

## 서명과 서명 대상 가려내기 (`GitSignatures`)

git이 만들고 검증할 때와 같은 규칙이다.

- 커밋: 머리글 `gpgsig`(이어지는 줄은 공백 하나로 시작, 빈 줄은 공백 하나)가 서명이고, 그 머리글을 뺀 원문이 서명 대상이다. 머리글 영역(첫 빈 줄 앞)만 본다. 메시지 본문의 비슷한 글은 서명이 아니다.
- 주석 태그: 원문 끝에 붙은 `-----BEGIN PGP SIGNATURE-----` 블록이 서명이고 그 앞까지가 서명 대상이다.

실제 `gpg` 2.4.8과 `git`이 만든 Ed25519와 RSA 3072 키, 커밋, 주석 태그를 시험 자료(`src/test/resources/gpg`)로 두어 호환을 확인했다.

## 서명 커밋 필수 규칙 (규칙 묶음의 `require_signed_commits`)

- **푸시**: 규칙 묶음이 대상으로 하는 브랜치로 푸시하는 **새 커밋**이 모두 `valid`여야 한다. 새 커밋은 새 팁에서 거슬러 오르되 옛 팁과 저장소의 다른 참조가 이미 가진 커밋은 뺀 것이다(그래서 규칙 이전의 서명 없는 이력은 다시 검사하지 않고, 브랜치를 새로 만들 때 기존 이력도 다시 보지 않는다). 거부 메시지에 짧은 번호와 이유를 최대 5개 보인다. 삭제는 검사하지 않는다. 바이패스를 허용한 규칙 묶음은 프로젝트 관리자와 사이트 관리자가 우회한다. 거부는 감사(`git.push_rejected`)와 지표(`ruleset_signed_commits`)에 남는다.
- **병합**: 풀 리퀘스트가 가진 현재 커밋 가운데 `valid`가 아닌 것이 있으면 병합을 막는다(화면의 병합 단추 안내, `accept`). 서버가 병합할 때 만드는 병합 커밋과 스쿼시, 리베이스 결과는 서명하지 못하므로 검사하지 않는다. 막혀도 바이패스를 허용한 규칙 묶음은 관리자가 우회한다.
- 대상은 git 브랜치뿐이다. 태그 푸시에는 적용하지 않는다.

## 설정 화면과 REST

화면: `GET /user/editform/gpg`(목록), `GET /user/editform/gpg/new`(추가), `POST /user/gpg`, `POST /user/gpg/{id}/delete`. 목록의 행 동작은 삭제 하나이고 편집과 상세는 없다.

| REST | 범위 | 설명 |
|---|---|---|
| `GET /-_-api/v1/user/gpg_keys` | `read:gpg_key` | 내 키 목록(최근 등록순, 하위 키와 이메일 포함) |
| `GET /-_-api/v1/user/gpg_keys/{id}` | `read:gpg_key` | 한 건. 없거나 남의 키면 404 |
| `POST /-_-api/v1/user/gpg_keys` | `write:gpg_key` | `{name, publicKey}`. 받을 수 없는 키 400, 이미 등록된 키 409, 201 |
| `DELETE /-_-api/v1/user/gpg_keys/{id}` | `admin:gpg_key` | 204 |
| `GET /-_-api/v1/users/{user}/gpg_keys` | `read:user` | 다른 사용자의 공개키(키 이름은 숨김) |

범위는 `admin:gpg_key`가 `write:gpg_key`와 `read:gpg_key`를, `write:gpg_key`가 `read:gpg_key`를 포함한다(GitHub와 같다). 태그 목록과 만들기 응답의 주석 태그에, 풀 리퀘스트 커밋 목록의 각 커밋에 `verification {verified, reason, signer?, keyId?}`가 붙는다. 일반 커밋 조회 REST는 아직 없다.

## 등록할 수 없는 키

비었음, 읽을 수 없음, 비밀키, 키 여러 개, 사용자 ID 없음(이메일을 맞춰 볼 수 없다), 서명할 수 있는 키 없음, 이미 만료, 이미 폐기, 지문 중복(주 키와 하위 키 모두, 사이트 전체), 사용자당 50개 초과, 이름 100자 초과.

## 사이트 데이터

`gpg_key`는 사이트 내보내기와 가져오기(`DataTables`)에 들어 있다. v1.6 파일(테이블 없음)을 가져오면 남아 있던 키는 비우고, 없는 사용자를 가리키는 행과 주 키가 없는 하위 키 행은 지운다. 사용자를 삭제 처리하면 그 사용자의 키도 하위 키부터 지운다.

## 한계

- svn에는 해당이 없다. Mercurial(X-7)의 서명은 따로 다룬다.
- SSH 키로 한 서명은 검증하지 않는다(X-3에서 `ssh_key` 테이블이 생겼으므로 이 테이블로 확장하는 것을 열어 둔다).
- 일반 커밋 조회 REST와 풀 리퀘스트 변경 화면의 커밋 선택 목록(드롭다운)에는 배지가 없다(커밋 하나를 고르면 정보에 보인다).
