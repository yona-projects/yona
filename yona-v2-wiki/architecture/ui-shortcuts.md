# 새 UI의 단축키 설계

> **상태: 설계 제안(`decisions.md` D-137).** 선생님이 "전역 단축키는?"이라고 물으셨다. 이 문서는 **지금의 단축키 전체**(v1.6과 현재 v2)를 조사한 결과와 **새 UI에서의 전역, 맥락, 화면 단축키** 설계, 결정할 것을 담는다. 구현하지 않았다. 브랜치 `ui-improvements`.

## 1. 지금의 단축키(v1.6 위키의 전수 조사표 + 현재 화면에서 직접 확인)

단축키는 **수정키 없는 한 글자**가 대부분이다. 입력란(`INPUT`, `TEXTAREA`)에 초점이 있으면 동작하지 않고, 한글 등 입력기로 조합 중인 키는 무시한다. 한글 자판에서도 같은 물리 키(`KeyH` 등)가 영문 키처럼 동작한다(`ShortcutKey.js`).

| 범위 | 키 | 동작 | 조건 | 현재 확인 |
|---|---|---|---|---|
| **전역** | `A` | 내 이슈(`/user/issues`) | 모든 화면 | 동작(홈, 프로젝트 화면에서 확인) |
| 전역 | `U` | 내 프로필 | 로그인 시 | 동작 |
| 전역 | `F`, `ㄹ` | 사용자 메뉴 패널을 열고 이름 필터에 초점 | **초점이 없을 때만**, `ShortcutKey`가 아니라 `keypress`(`Usermenu.js`) | 동작(패널 폭 360px, 필터에 초점) |
| 전역 | `ALT+S`(Mac은 `CTRL+ALT+S`) | 상단 검색 입력에 초점 | JS가 아니라 **HTML `accesskey="S"`**(브라우저가 처리) | 자동 시험으로는 확인하지 못했다(브라우저 기능이라 합성 키 입력으로는 안 된다) |
| 전역 | `CTRL+ENTER` | 입력란에서 가장 가까운 폼 제출 | 입력란에 초점 | 동작(이슈 댓글 입력란에서 댓글이 등록됨) |
| 프로젝트 맥락 | `H` 홈, `B` 게시판, `C` 코드, `I` 이슈(열림), `M` 마일스톤, `P` 코드 주고받기(Git만), `Q` 설정 | 이동 | 해당 메뉴가 **켜져 있을 때만**(`B`, `C`, `I`, `M`, `P`). `Q`는 설정 단축키가 켜진 경우 | `H`, `I`, `C` 동작. `B`는 이 프로젝트의 게시판 메뉴가 꺼져 있어 동작하지 않음(정상) |
| 화면 | `N` | 새 이슈(이슈 목록, 이슈 상세), 새 글(게시판), 새 마일스톤(마일스톤 목록) | 해당 메뉴가 켜져 있을 때 | `N`(이슈 목록) 동작: 새 이슈 화면으로 이동하고 제목에 초점 |
| 화면 | `L` 목록, `E` 수정 | 이슈 상세, 게시글 상세. `E`는 수정 권한이 있을 때 | | 동작(이슈 상세에서 `L`은 목록, `E`는 수정 화면) |
| 화면 | `←`, `→` | 이전, 다음 페이지 | 페이지 이동이 있는 모든 목록 | 동작(이슈 목록 pageNum 2와 1) |
| 화면 | `CTRL+A` | 이슈 목록의 일괄 변경 영역에서 전체 선택 | 입력란이 아닐 때 | 동작(체크됨 0개에서 17개로) |
| 화면 | `A`, `S` | **코드 이력에서 이전, 다음 페이지** | `A`는 전역 "내 이슈"를 **덮어쓴다**(같은 키를 나중에 등록한 쪽이 이긴다) | `S`(다음 페이지)는 동작. **`A`는 전역 "내 이슈"가 이긴다**: 본문 다음에 `common/scripts`를 불러 전역이 나중에 등록되기 때문이다. v1.6도 같은 순서라 같은 결함이며 R-147에 올렸다 |
| 화면 | `CTRL+SHIFT+ENTER` | 이슈 댓글 입력에서 댓글 단추 누르기 | v1.6 위키: 조합 정규화 결함 때문에 **동작하지 않을 가능성이 크다**. 도움말에는 적혀 있다 | 동작하지 않음(Playwright로 눌러 보았으나 댓글이 등록되지 않는다). v1.6 위키의 예측과 같아 v1.6 결함을 그대로 따른다(`CTRL+ENTER`는 정상) |

- **도움말**: 화면 안의 "단축키 안내"(`help/keymap`, 모달)가 현재 화면 범위의 키를 보여 준다(Mac이면 `⌘`와 `⌥`). 모달을 여는 단추가 화면 안에 있고 **여는 단축키는 없다**. 안내를 보이는 쪽(`isMac`)은 서버가 `User-Agent`로 판별한다(`LayoutModelAdvice`).
- **구현 구조**: 전역 객체 `yona.ShortcutKey`(`attach`, `detach`, `setKeymapLink`)에 화면마다 인라인 스크립트가 키와 주소를 등록한다. 키마다 핸들러는 하나이며 **같은 키를 다시 등록하면 마지막이 이긴다**(코드 이력의 `A`가 그 예). `F`만 이 체계 밖의 별도 코드이다.

## 2. 문제점

1. **범위가 암묵적이다.** 어떤 키가 어느 화면에서 되는지는 화면의 인라인 스크립트와 도움말 템플릿 두 곳에 따로 적혀 있어 어긋날 수 있다(예: 도움말에 있는데 동작하지 않을 수 있는 `CTRL+SHIFT+ENTER`).
2. **충돌이 조용히 일어난다.** 같은 키의 마지막 등록이 이긴다(코드 이력의 `A`와 전역 `A`).
3. **한 글자 단축키를 끌 방법이 없다.** WCAG 2.1.4(문자 키 단축키, 일반 지식으로 A 수준)는 문자 키만 쓰는 단축키를 끄거나 바꾸거나 초점이 있을 때만 켜도록 요구한다. 지금은 입력란 밖이면 항상 켜져 있다.
4. **입력 제외 범위가 좁다.** `INPUT`과 `TEXTAREA`만 제외하고 `SELECT`와 `contenteditable`(편집기)은 제외하지 않아, 그 위에서 글자를 누르면 단축키가 발동할 수 있다(v1.6 위키 기록).
5. **`F`가 별도 코드**이고 초점이 없을 때만 동작한다. 사용자 메뉴 패널이 새 UI에서 없어지므로(IA 4.2.2절) 의미를 정해야 한다.
6. **서버가 `User-Agent`로 Mac 여부를 판별**한다. 새 UI의 같은 주소 두 가지 응답(조각과 전체, `Vary: HX-Request`, htmx 설계 6절)에 `User-Agent` 의존이 끼면 캐시가 어려워진다.
7. 도움말을 열 키가 없고, 닫는 `Esc` 규칙이 화면마다 다를 수 있다.

## 3. 원칙

1. **v1.6 단축키는 전부 유지한다**(키, 효과, 범위, 조건). 새 UI가 바꾸는 것은 의미가 사라지는 `F` 하나뿐이다(4절).
2. **범위는 전역, 맥락, 화면 세 층**이고, 충돌하면 **화면, 맥락, 전역** 순으로 이긴다. 지금 "마지막 등록이 이긴다"는 암묵 규칙을 이 명시 규칙으로 바꾸되 결과는 같다(코드 이력의 `A`가 전역 `A`를 이긴다).
3. **선언형으로 한 곳에서 모은다**(6절). 도움말은 실제 등록된 키에서 자동으로 만들어 어긋나지 않게 한다.
4. **입력 중에는 동작하지 않는다.** 입력란, 선택 상자, 편집 가능 영역, 편집기, 입력기 조합 중에는 무시한다.
5. **한 글자 단축키는 끌 수 있다**(기본은 켜짐, v1.6 동작).
6. **배열 독립**: 한글 자판에서도 같은 물리 키로 동작한다(지금의 `KeyboardEvent.key`와 `code` 방식을 유지).

## 4. 새 UI의 단축키

### 4.1 전역(어느 화면에서나, 로그인 후)

| 키 | 동작 | 출처 |
|---|---|---|
| `A` | 내 이슈 | v1.6 유지 |
| `U` | 내 프로필 | v1.6 유지 |
| `F`, `ㄹ` | **전환기를 열고 이름 필터에 초점** | v1.6의 "사용자 메뉴 열기"가 새 UI에서 전환기로 바뀐 것(IA 4.2.1, 4.2.2절). 목록(즐겨찾기, 프로젝트, 최근 읽은 이슈)과 이름 필터가 전환기로 옮겨 가므로 사용자가 얻는 효과는 같다. 지금처럼 초점이 없을 때만 동작하게 하되 `ShortcutKey` 한 경로로 통합한다 |
| `ALT+S`(Mac `CTRL+ALT+S`) | 상단 검색에 초점 | v1.6 유지(`accesskey`) |
| `CTRL+ENTER` | 입력란에서 폼 제출 | v1.6 유지 |
| `?` | **단축키 안내 열기**(현재 화면의 전역, 맥락, 화면 키 표) | **새 동작**(8절 결정 3) |
| `/` | **검색에 초점**(`ALT+S`와 같은 효과) | **새 동작**(결정 3) |
| `Esc` | 열린 드롭다운, 서랍, 전환기, 안내 닫기, 초점을 연 곳으로 돌려줌 | **새 동작**(결정 3). 접근성의 표준 동작 |
| `[` | **사이드바 접기와 펼치기**(넓음은 고정과 레일, 좁음과 중간은 서랍과 레일 펼침) | **새 동작**(결정 3) |

### 4.2 맥락(프로젝트 안, 조직 안, 사이트 관리 안)

- **프로젝트**: `H`, `B`, `C`, `I`, `M`, `P`, `Q`를 **그대로 유지**한다. 이 키는 프로젝트 사이드바 항목과 같은 원본에서 나온다(6절). 항목이 메뉴 설정으로 꺼지면 키도 꺼진다(지금과 같다).
- **조직, 사이트 관리**: 새 키를 만들지 않는다(v1.6에 없다).

### 4.3 화면

`N`(새 이슈, 새 글, 새 마일스톤), `L`, `E`, `←`, `→`, `CTRL+A`(이슈 일괄 변경), `A`와 `S`(코드 이력 페이지)를 **그대로 유지**한다. `CTRL+SHIFT+ENTER`(이슈 댓글 제출)는 도움말에 적혀 있고 동작이 불확실하므로 결정 8로 둔다.

## 5. 접근성, 플랫폼, 기기

- **끄기 설정**: 사용자 설정에 "한 글자 단축키 사용"을 둔다(기본 켜짐). 끄면 한 글자 키(`A`, `U`, `F`, `H` 등)와 새 키 중 한 글자인 것(`/`, `?`, `[`)이 동작하지 않고, 수정키가 있는 키(`CTRL+ENTER`, `ALT+S`)와 `Esc`는 계속 동작한다. 저장은 IndexedDB의 `prefs`(`ui-client-storage.md`)이다. 단축키는 로드 뒤에 처리하므로 첫 그림용 동기 거울이 필요 없다.
- **입력 제외 범위 확대**: `INPUT`, `TEXTAREA`에 더해 `SELECT`, `contenteditable`, 편집기(`common/editor`의 텍스트 영역과 미리보기), 입력기 조합 중을 제외한다. 지금과 다른 동작이라 기록한다(결정 5).
- **스크린 리더**: 스크린 리더는 탐색 모드에서 `H`(제목), `B`(단추) 같은 글자 키를 먼저 처리해 페이지의 단축키와 겹칠 수 있다(일반 지식, 확인하지 못함). 끄기 설정이 그 사용자의 우회로이다.
- **Mac 표기**: `⌘`와 `⌥` 표기는 서버의 `User-Agent` 판별(`isMac`) 대신 **클라이언트에서** 판별해(`navigator.userAgentData?.platform`, 없으면 `navigator.platform`) 같은 주소의 응답이 `User-Agent`에 따라 달라지지 않게 한다.
- **폰, 폴드, 태블릿**: 키 입력은 기기와 상관없이 받는다(블루투스 키보드를 쓰는 폴드 펼침과 태블릿). 다만 안내의 키 표시와 `?` 안내 링크는 `pointer: fine`(마우스, 터치패드)인 환경에서만 노출한다.
- **htmx 이동**: 새 화면의 키는 `htmx:load`에서 수집하고 `htmx:beforeCleanupElement`에서 해제해, 본문을 바꿔도 등록이 쌓이지 않는다(htmx 설계 5절의 문서 수준 핸들러 규칙).

## 6. 구조

- **선언형 수집**: 키를 `data-shortcut="N"`(필요하면 `data-shortcut-label`) 속성으로 요소에 선언한다. 링크 요소면 그 `href`로 이동하고, 단추면 누른다. 한 곳의 작은 모듈(`esm/shell/`의 단축키 모듈, 가칭)이 문서에서 수집해 한 번만 문서 수준 핸들러를 달고 `htmx:load`마다 다시 수집한다.
- **맥락 키는 사이드바 데이터에서**: IA의 사이드바 목록(데이터)에 `shortcut` 필드를 두어 `H`, `B`, `C`, `I`, `M`, `P`, `Q`가 항목과 같은 원본에서 나온다. 메뉴 설정에 따라 항목이 사라지면 키도 사라진다(지금의 `setKeymapLink` 조건 대신).
- **우선순위**: 화면 > 맥락 > 전역. 같은 범위에서 같은 키를 두 번 선언하면 구조 시험이 실패한다(조용히 덮어쓰지 않는다).
- **안내(`?`)**: 수집된 키에서 **자동으로** 표를 만든다(전역, 이 맥락, 이 화면). 지금의 `help/keymap` 조각은 이 자동 표로 대체한다. 대화상자는 `role="dialog"`, 초점 가두기, `Esc`로 닫기, 닫으면 초점 복귀.
- **`F`**: 지금의 `Usermenu.js`의 별도 `keypress`를 없애고 같은 모듈에서 처리한다. `ㄹ`은 물리 키(`KeyF`)로 같이 처리한다.
- 기존 `ShortcutKey.js`는 화면을 새 모듈로 옮길 때까지 그대로 둔다(IA의 단계 계획을 따른다).

## 7. 시험(TDD, 구현 때)

- **키 동작(Playwright)**: 4절의 모든 키가 기대한 주소, 초점, 열림을 만든다. 한글 자판에서도 `H`, `F`(`ㄹ`)가 동작한다.
- **입력 제외**: 입력란, 텍스트 영역, 선택 상자, 편집 가능 영역, 편집기, 입력기 조합 중에는 키가 무시된다.
- **수정키**: `CTRL`, `ALT`, `⌘`와 함께 누른 한 글자 키는 단축키가 되지 않고 브라우저 기본 동작이 유지된다(`CTRL+F` 등).
- **끄기 설정**: 끄면 한 글자 키가 동작하지 않고 `CTRL+ENTER`와 `Esc`는 동작한다.
- **메뉴 설정**: 게시판 메뉴가 꺼진 프로젝트에서 `B`가 동작하지 않는다(지금과 같다).
- **우선순위와 중복**: 코드 이력에서 `A`는 이전 페이지이다. 같은 범위의 중복 선언은 구조 시험이 잡는다.
- **htmx**: 이동 뒤에도 키가 동작하고 한 번만 반응한다(핸들러 중복 없음). 이동 전 화면의 `N`이 새 화면에 남지 않는다.
- **안내**: `?` 대화상자의 표가 실제 등록된 키와 같다(자동 생성). `Esc`로 닫고 초점이 돌아온다. 좁은 화면에서는 키 표시가 숨는다.
- **여닫기**: `[`와 `Esc`가 구간별 사이드바(고정, 레일, 서랍)에서 의도한 대로 동작한다.
- **뷰포트**: 344, 390, 673, 768, 1024, 1280(IA 4.5절).

## 8. 결정이 필요한 것(`decisions.md` D-137, 권장안 포함)

1. **v1.6 단축키를 전부 유지한다.** 권장: **유지**(키, 효과, 조건 그대로).
2. **`F`의 의미**: 사용자 메뉴 열기 대신 **전환기 열기와 이름 필터 초점**. 권장: **그렇게 바꾼다.** 사용자 패널이 없어지고 그 안의 목록이 전환기로 가기 때문이며 사용자가 얻는 효과는 같다.
3. **새 키 허용**: `?`(안내), `/`(검색), `Esc`(닫기), `[`(사이드바). 권장: **넷 다 허용**. 전부 흔한 관례이고 v1.6의 키와 겹치지 않는다. v1.6에 없는 동작이라 `differences-from-v16.md`에 기록한다.
4. **한 글자 단축키 끄기 설정**(기본 켜짐). 권장: **도입**(WCAG 2.1.4).
5. **입력 제외 범위를 선택 상자, 편집 가능 영역, 편집기, 입력기 조합 중으로 넓힌다.** 권장: **넓힌다**(오동작 방지). v1.6과 다른 점으로 기록한다.
6. **선언형 `data-shortcut` + 맥락 키를 사이드바 데이터에서 파생 + 안내 자동 생성.** 권장: **그렇게 한다**(키와 도움말이 어긋나지 않음).
7. **범위 밖**: 두 키 조합(`G` 다음 `H` 같은 순서 입력)과 명령 팔레트(`CTRL+K`). 권장: **이번 범위 밖**.
8. **`CTRL+SHIFT+ENTER`(이슈 댓글 제출)**: v1.6에서 조합 정규화 결함으로 죽어 있었을 가능성이 크고 도움말에는 적혀 있다. (가) 동작하게 구현한다. (나) 도움말에서 지우고 두지 않는다. (다) 현재 v2 동작을 확인한 뒤 같게 둔다. 권장: **(다)**, 확인 뒤 동작하지 않는다면 도움말과 일치하도록 **동작하게 구현**한다(도움말이 약속한 동작이다).

## 9. IA, htmx, 저장소 설계와의 관계

- IA: `F`는 전환기(IA 4.2.1절), `[`와 `Esc`는 사이드바의 구간별 상태(4.5절), 맥락 키는 사이드바 데이터(4절).
- htmx: 키 등록은 `htmx:load` 수집으로 하고(5절) 안내 대화상자도 서버 조각이 아니라 클라이언트가 만든다.
- 저장소: 한 글자 단축키 끄기는 `prefs`에 둔다(`ui-client-storage.md`).

## 10. 확인 결과와 남은 한계

- **`ALT+S`**: `accesskey`는 브라우저가 직접 처리하므로 합성 키 입력으로는 확인할 수 없다(브라우저와 OS마다 조합이 다르다). `navbar.html`의 `accesskey="S"`와 v1.6 위키 기록으로 대조했다. 이것은 자동화로 풀 수 없는 한계이다.
- 2026-11-11에 v2에서 직접 눌러 확인했다: `L`, `E`, `←`, `→`, `CTRL+A`, `Q`, `S`(코드 이력), `CTRL+ENTER`는 동작하고, `CTRL+SHIFT+ENTER`는 v1.6처럼 동작하지 않으며, 코드 이력의 `A`는 전역에 덮인다(R-147).
- 스크린 리더와의 키 충돌, 한글 외 입력기, Mac의 `⌥` 조합은 실제 환경이 필요해 자동화로 확인할 수 없다(설계는 끄기 설정으로 우회로를 둔다).
