# 팀 기능 구현 계획 (X-44)

> **상태: 계획 작성 완료, 단계 0(상세 확인) 결과 반영(2026-11-03), 선생님 검토 대기.** 단계 0에서 GitHub 문서와 Yona 코드를 확인해 계획의 가정 일부가 틀렸음을 알았고 아래 "단계 0 결과"와 본문에 반영했다. 선생님이 범위를 "깃허브"로 정하셨고, 세부 질문 15개는 7절에 권장안과 함께 있다. 구현은 선생님이 계획을 확인하신 뒤 시작한다. 결정은 [decisions.md](../decisions.md) D-84, 로드맵은 [roadmap.md](../roadmap.md) X-44이다.

## 1. 목표와 결론

조직 구성원을 **팀**으로 묶고, 팀에 프로젝트 접근 권한을 한 번에 주며, 팀을 멘션하고 리뷰어로 지정할 수 있게 한다. 범위는 GitHub의 조직 팀 기능이다.

- 지금은 프로젝트마다 구성원을 한 사람씩 등록해야 한다. 같은 사람들에게 프로젝트 여러 개의 권한을 주려면 같은 작업을 프로젝트 수만큼 되풀이한다.
- 팀은 **v1.6에 없는 새 기능**이다. [D-28](../decisions.md)의 추가 개발 항목으로 다루고, 기존 테이블과 요청·응답 계약은 바꾸지 않는다.
- 팀이 하나도 없는 사이트에서는 모든 권한 판정이 지금과 같아야 한다. 이것이 가장 중요한 안전 조건이고, 기존 시험 전체가 그대로 통과하는 것으로 확인한다.
- 가장 위험한 부분은 접근 제어(`AccessControl`)에 "팀을 통한 권한"을 더하는 일이다. 권한 판정이 모든 화면과 API에 걸려 있기 때문에 단계 2와 3에서 동작별 시험을 먼저 쓴다.

## 2. 현재 구조 (2026-11-03 조사)

| 영역 | 현재 | 팀과의 관계 |
|---|---|---|
| 조직 구성원 역할 | `ORG_ADMIN`, `ORG_MEMBER` 두 가지(`RoleType`) | 팀은 조직 구성원만 담는다. 조직 관리자가 모든 팀을 관리한다 |
| 프로젝트 구성원 역할 | `MANAGER`, `MEMBER` 두 가지(`project_user`). 읽기만 하는 구성원은 없다 | 팀 권한 5단계 중 2단계(Write, Admin)는 이 두 역할과 같다. 나머지 3단계는 새로 정의한다 |
| 조직 구성원의 프로젝트 권한 | 조직의 **공개·보호** 프로젝트에서만 구성원과 같은 권한(`isAllowedIfGroupMember`). 비공개 프로젝트는 구성원 등록이 필요하다 | 비공개 프로젝트에 대한 일괄 부여가 팀의 가장 큰 이득이다 |
| 권한 판정 | `AccessControl.isAllowed`와 `isProjectResourceCreatable`이 `isProjectMember`, `isProjectManager`, `isOrganizationAdmin`을 조합한다. 이 두 함수의 호출은 19곳(2개 파일)이다 | 이 함수들에 팀 경로를 더하면 대부분 자동으로 따라온다 |
| 직접 조회 | `project_user`를 `AccessControl` 밖에서 직접 읽는 곳이 25개 안팎의 파일에 있다(`ProjectViewContext`, `SessionPermissions`, `PullRequestPageAssembler`, `NotificationReceivers`, `MentionService`, `IssueSharerService` 등) | "구성원 목록"을 뜻하는 곳과 "접근할 수 있는가"를 뜻하는 곳을 단계 0에서 나눈다 |
| 담당자·리뷰어 후보 | `IssueListService.assignableUsers`가 프로젝트 구성원과 조직 구성원을 합친다 | 팀으로 접근 권한을 받은 사람이 빠지면 안 된다 |
| 멘션 | `MentionService`가 `@아이디`, `@조직이름`(조직 구성원 모두), `@소유자/프로젝트`(프로젝트 구성원 모두)를 푼다. 정규식이 이미 `/`를 허용한다 | `@조직/팀`이 `@소유자/프로젝트`와 같은 모양이라 **이름 충돌**이 생긴다(7절 질문 5) |
| 리뷰 요청 | `PullRequestReviewRequestService`, REST `…/requestedreviewers` | 팀을 리뷰어로 요청하는 경로를 더한다 |
| 규칙 묶음 | `Ruleset`에는 `bypass_admins` 하나뿐이다. 바이패스 목록(구성원, 조직 관리자, 개별 사용자)은 [X-35](../roadmap.md)로 대기 중이다 | 팀을 바이패스·푸시 허용 대상으로 쓰려면 X-35의 "종류와 대상 번호" 구조가 먼저 필요하다 |
| 코드 소유자 | Yona에 `CODEOWNERS` 기능이 **없다** | GitHub에서 팀의 중요한 쓰임이지만 별도 기능이다(7절 질문 8) |

## 3. GitHub 기능과 Yona 대응

범위가 "깃허브"이므로 아래를 모두 포함한다. 세부 동작 중 확인하지 못한 것(중첩 깊이 한도, 부모 팀 멘션이 자식 팀 구성원에게 가는지)은 단계 0에서 GitHub 문서로 확인한다.

| GitHub 기능 | Yona에서 하는 일 | 단계 |
|---|---|---|
| 조직 안의 팀(이름, 설명) | 새 테이블 `team`. 팀 이름은 조직 안에서 대소문자 구분 없이 고유 | 1 |
| 팀 구성원과 팀 역할(Member, Maintainer) | `team_user`. Maintainer는 그 팀의 구성원과 설정을 관리한다 | 1 |
| 공개 팀과 비밀 팀 | 공개 팀은 조직 구성원이 모두 보고 멘션한다. 비밀 팀은 구성원과 조직 관리자만 본다. 비밀 팀은 중첩하지 않는다 | 1 |
| 중첩 팀(상위 팀과 하위 팀) | `team.parent_id`. 하위 팀은 상위 팀의 프로젝트 권한을 이어받는다. 깊이 한도와 순환 금지 | 1, 2 |
| 팀에 프로젝트 권한 부여 | `team_project`. 단계는 Read, Triage, Write, Maintain, Admin | 2, 3 |
| 조직 프로젝트에만 팀 권한 | 개인 계정의 프로젝트에는 팀이 없다 | 2 |
| 팀 멘션 `@조직/팀` | 팀 구성원(공개 팀의 하위 팀 구성원 포함)에게 알림 | 5 |
| 팀 알림 설정(켬/끔) | 끄면 **팀 멘션** 알림만 보내지 않는다. 리뷰 요청 알림은 이 설정과 상관없이 간다(GitHub 동작) | 5 |
| 팀을 리뷰어로 요청 | 팀 구성원 누구의 리뷰든 요청을 채운다 | 6 |
| 조직 설정: 누가 팀을 만들 수 있는가 | 조직 관리자만 또는 모든 구성원 | 1 |
| 규칙 묶음 바이패스·푸시 허용 대상에 팀 | X-35의 대상 구조와 함께 | 8 |
| REST, CLI, OpenAPI | `…/orgs/{org}/teams` 계열, `yona team` | 7 |
| 코드 소유자(CODEOWNERS)의 팀 | 별도 항목으로 분리 권장 | (X-45) |
| 팀 토론, 라운드 로빈 리뷰 배정, IdP 팀 동기화 | **이번 범위에서 뺀다**(질문 10, 11) | - |

## 4. 설계

### 4.1 데이터 (새 테이블 3개)

모두 `SchemaMetadata`의 `INTENDED_ADDITIONS`에 올리고, 내보내기·가져오기 표(`DataTables`, 지금 69개)에 더한다.

| 테이블 | 열 | 비고 |
|---|---|---|
| `team` | `id`, `organization_id`, `name`, `description`, `privacy`(`VISIBLE`/`SECRET`), `parent_id`(없을 수 있음), `notifications_enabled`, `created_date` | `(organization_id, lower(name))` 고유. 이름 규칙은 프로젝트 이름과 같은 글자 집합 |
| `team_user` | `id`, `team_id`, `user_id`, `role`(`MEMBER`/`MAINTAINER`), `created_date` | `(team_id, user_id)` 고유. 조직 구성원만 들어간다 |
| `team_project` | `id`, `team_id`, `project_id`, `permission`(`READ`/`TRIAGE`/`WRITE`/`MAINTAIN`/`ADMIN`), `created_date` | `(team_id, project_id)` 고유. 프로젝트의 조직이 팀의 조직과 같아야 한다 |

팀 리뷰 요청을 위해 단계 6에서 `pull_request_review_team_request`(`pull_request_id`, `team_id`, `requested_by`, `created_date`)를 더한다. 기존 리뷰 요청 테이블의 모양은 단계 0에서 확인한 뒤 맞춘다.

### 4.2 규칙

- **팀 만들기**: GitHub의 기본처럼 조직 구성원이 만들 수 있고, 조직 설정으로 조직 관리자만으로 제한할 수 있다(질문 3). 만든 사람은 그 팀의 Maintainer가 된다. 팀을 만든 것만으로는 프로젝트 권한이 생기지 않는다(프로젝트에 팀을 추가하려면 그 프로젝트의 관리자나 조직 관리자여야 한다).
- **팀 옮기기**: 조직 관리자는 어떤 팀이든, 팀 Maintainer는 자기가 Maintainer인 하위 팀을 자기가 Maintainer인 상위 팀 밑으로 옮긴다(GitHub 규칙).
- **중첩**: 깊이 한도는 Yona가 안전장치로 5단계를 둔다(GitHub 문서에는 한도가 적혀 있지 않다, 질문 2). 자기 자신이나 자기 하위 팀 밑으로 옮길 수 없다. 비밀 팀은 상위도 하위도 될 수 없고 비밀 팀 밑으로 옮길 수도 없다. 이미 상위가 있는 팀을 다른 상위 밑으로 옮기면 이전 상위에서 빠진다(상위는 하나뿐). 상위 팀을 지우면 하위 팀도 함께 지운다(GitHub가 그렇게 동작한다고 알려져 있다. 공식 문서에는 없어 확인 화면에서 하위 팀 목록을 보여 준다, 질문 13).
- **구성원 자격**: 조직 구성원만 팀에 들어간다. 조직에서 빠지면(탈퇴, 제거) 그 조직의 모든 팀에서 빠진다. 사용자를 지우면 팀 구성원 행도 지운다.
- **프로젝트 권한 부여**: 프로젝트가 팀과 **같은 조직의 것**일 때만 한다. 프로젝트를 다른 소유자로 이전하면 이전 조직 팀의 권한은 지운다(GitHub 동작, 질문 9). 포크는 팀 권한을 이어받지 않는다. 프로젝트를 지우면 부여를 지운다.
- **감사 기록**: `team.create`, `team.update`, `team.delete`, `team.member_add`, `team.member_remove`, `team.member_role`, `team.project_grant`, `team.project_revoke`, `team.project_permission`. 조직 감사 화면에 나타난다.

### 4.3 실효 권한 계산 (`TeamAccessService`)

사용자 U의 프로젝트 P에 대한 팀 권한은 다음과 같이 구한다.

1. U가 속한 팀 집합을 구한다(`team_user`).
2. 각 팀의 상위 팀을 깊이 한도까지 따라 올라가 집합에 더한다. 하위 팀 구성원이 상위 팀의 권한을 이어받는 방향이다.
3. 그 집합 중 P에 `team_project`가 있는 것의 **가장 높은 단계**가 팀 권한이다.

최종 권한은 **기존 규칙과 팀 권한 중 높은 쪽**이다(직접 구성원 역할, 조직 구성원 규칙, 조직 관리자, 사이트 관리자). 팀 권한은 권한을 올리기만 하고 내리지 않는다. 한 요청 안에서는 결과를 기억한다(`SessionPermissions`가 프로젝트 관리자 여부를 기억하는 방식과 같다).

### 4.4 권한 단계 (초안, 단계 0에서 동작별 표로 확정)

Yona 프로젝트 역할은 둘뿐이므로 GitHub의 5단계 중 2단계는 기존 역할과 같고 3단계는 새로 정의한다.

| 단계 | Yona에서의 뜻 |
|---|---|
| Read | 비공개 프로젝트를 읽는다. 이슈, 이슈 댓글, 풀 리퀘스트 댓글, 코드 댓글, 포크를 만든다(공개 프로젝트의 로그인 사용자가 할 수 있는 것과 같다). 남의 이슈를 고치거나 닫지 못하고 푸시와 병합을 하지 못한다 |
| Triage | Read에 더해 이슈와 풀 리퀘스트의 라벨, 담당자, 마일스톤 관리, 닫기와 다시 열기, 리뷰 요청을 한다. 푸시와 병합은 하지 못한다 |
| Write | **프로젝트 구성원(`MEMBER`)과 같다.** 푸시, 병합, 이슈 관리 |
| Maintain | Write에 더해 프로젝트 설정 중 위험하지 않은 것(라벨·마일스톤 관리, 규칙 묶음 보기, 웹훅 보기 등)을 한다. 삭제, 이전, 공개 범위 변경, 구성원 관리는 하지 못한다 |
| Admin | **프로젝트 관리자(`MANAGER`)와 같다** |

### 4.5 멘션과 알림

- `@조직/팀`은 그 팀 구성원에게, 팀에 하위 팀이 있으면 하위 팀 구성원에게도 알린다(상위 팀 멘션은 하위 팀 구성원에게 가고, 하위 팀 멘션은 그 팀 구성원에게만 간다. GitHub 문서로 확인). 알림을 끈 팀에는 보내지 않는다.
- 비밀 팀은 그 팀 구성원과 조직 관리자에게만 보인다. 다른 사람이 비밀 팀 이름을 쓰면 알림은 가지 않고 평범한 글자로 남는다(GitHub는 비밀 팀을 멘션하면 팀 이름이 글에 드러난다고 설명한다).
- **이름 충돌 방지(선생님 제안, 2026-11-03)**: 멘션의 `/` 형식은 지금 `@소유자/프로젝트` 하나뿐이고(`MentionService.projectMembers`), `@조직/팀`과 모양이 같다. 그래서 **같은 조직 안에서 팀 이름과 프로젝트 이름이 같지 않게 한다**(대소문자 무시). 팀 만들기·이름 바꾸기는 같은 조직의 프로젝트 이름과 같으면 거절하고, 프로젝트 이름을 정하는 경로(만들기, 가져오기, 포크, 이름 바꾸기, 이전 수락, REST 만들기)는 소유자가 조직이고 같은 이름의 팀이 있으면 거절한다. 팀이 하나도 없는 사이트에서는 새 검사가 아무 일도 하지 않으므로 v1.6 동작이 바뀌지 않는다. 사용자 아이디와는 모양이 달라(`@아이디`에는 `/`가 없다) 충돌이 없다. 팀 기능이 켜지기 전부터 있던 프로젝트와는 팀 만들기 쪽에서 막으므로 충돌이 생길 수 없다.
- 멘션 자동 완성(`MentionListController`)에 볼 수 있는 팀을 더한다.

### 4.6 화면

Bootstrap 5와 기존 조직 화면의 틀을 따른다. 메시지는 한국어와 영어 모두 만든다.

- **조직 화면에 "팀" 탭**: 팀 목록(트리 모양, 구성원 수, 프로젝트 수), 새 팀.
- **팀 화면**: 구성원(추가, 제거, 역할), 프로젝트(권한 부여, 단계 변경, 회수), 하위 팀, 설정(이름, 설명, 공개 범위, 상위 팀, 알림, 삭제).
- **프로젝트 설정에 "팀" 탭**: 조직 소유 프로젝트에서만 보이고 프로젝트 관리자(또는 조직 관리자)가 팀 접근을 추가하고 뺀다. 구성원 화면(`project_user`)은 그대로 두고 팀 접근은 별도 목록으로 보여 준다.
- 풀 리퀘스트 화면의 리뷰어 선택에 팀이 나온다.
- 화면 확인은 마지막 단계에서 Playwright로 한 번만 한다.

### 4.7 REST, CLI, 어댑터

- REST(토큰 전용, 범위는 조직 REST와 같은 `read:org`, `write:org`): `GET/POST /-_-api/v1/orgs/{org}/teams`, `GET/PATCH/DELETE …/teams/{team}`, `…/teams/{team}/members`(GET, PUT·DELETE `{login}`), `…/teams/{team}/projects`(GET, PUT·DELETE `{owner}/{project}`에 단계), `…/teams/{team}/teams`(하위 팀). 프로젝트 쪽에서 `GET /owners/{o}/projects/{p}/teams`(범위 `read:repo`). 모두 OpenAPI와 `ApiScopeRules`에 올리고 구조 시험이 빠지면 실패하게 한다.
- CLI(`yona-cli`): `yona team list|view|create|edit|delete`, `yona team member add|remove`, `yona team project add|remove`.
- Magpie 어댑터: `add_team_member(<조직>/<팀>, <login>)`이 지금은 조직 구성원 추가인데, 팀이 생기면 GitHub처럼 진짜 팀을 가리키게 바꾼다(질문 12).
- MCP는 읽기 전용이므로 이번에는 건드리지 않는다.

### (2) 권한 단계별 GitHub 동작과 Yona 대응 (단계 3의 시험 기준)

GitHub의 단계 표는 공식 문서에서 가져왔고, Yona의 현재 요구 권한은 `AccessControl`과 컨트롤러 어노테이션을 읽어 정리했다. "현재"는 지금 Yona에서 그 동작에 필요한 권한이다.

| Yona의 동작 | 현재 | Read | Triage | Write | Maintain | Admin |
|---|---|---|---|---|---|---|
| 비공개 프로젝트 읽기(코드, 이슈, 풀 리퀘스트, 위키, 게시판), 코드 받기 | 구성원 | O | O | O | O | O |
| 이슈, 게시글, 댓글, 풀 리퀘스트·코드 댓글 만들기, 리뷰 의견, 포크 | 공개는 로그인 사용자, 비공개는 구성원 | O | O | O | O | O |
| 자기 글 수정·삭제, 자기 이슈 닫기 | 작성자 | O | O | O | O | O |
| 남의 이슈를 닫기·다시 열기, 담당자·라벨 붙이기·마일스톤 지정, 풀 리퀘스트 닫기·다시 열기, 리뷰 요청 | 구성원 | - | O | O | O | O |
| 남의 이슈 제목·본문 수정 | 구성원 | - | - | O | O | O |
| 라벨·마일스톤 **만들기·수정·삭제** | 구성원 | - | - | O | O | O |
| 푸시, 풀 리퀘스트 병합, 브랜치·태그 삭제 | 구성원 | - | - | O | O | O |
| 필수 승인 수에 세어지는 승인 | 구성원이 아닌 사람의 승인도 세는지 **단계 3에서 확인** | - | - | O | O | O |
| 프로젝트 개요(README 영역) 편집, 라벨 분류 관리 | 프로젝트 관리자 | - | - | - | O | O |
| 기본 브랜치 변경, 이슈 삭제(작성자 아닌 경우) | 프로젝트 관리자 | - | - | - | - | O |
| 프로젝트 설정, 구성원 관리, 규칙 묶음, 웹훅, 배포 키, LFS, 저장소 종류 변경, 이전, 삭제 | 프로젝트 관리자 | - | - | - | - | O |

해설:
- **Write와 Admin**은 지금의 `MEMBER`, `MANAGER`와 같다.
- **Read**는 비공개 프로젝트에서 공개 프로젝트의 로그인 사용자와 같은 일을 하게 한다. GitHub의 Read(남의 글에 라벨을 못 붙이고 병합을 못 한다)와 맞는다.
- **Maintain**은 Yona에서 구분할 일이 적다. GitHub의 Maintain은 저장소 설명·위키·병합 방식을 다루는데, Yona의 설정은 한 화면(`ProjectSettingController`)에 이름, 공개 범위, 삭제가 섞여 있어 쪼개지 않으면 Admin과 구분되지 않는다. 그래서 Maintain을 **Write + 프로젝트 개요 편집 + 라벨 분류 관리**로 정의했다(질문 15). 규칙 묶음과 웹훅은 GitHub에서도 Admin 전용이라 같다.
- 표에 없는 동작은 가장 높은 요구 권한(Admin)으로 둔다(안전한 쪽).

### (3) `project_user` 직접 조회 분류

`AccessControl` 밖에서 `project_user`를 읽는 곳은 **약 40개소, 25개 파일**이었다. 줄 단위로 읽고 세 가지로 나눴다.

| 분류 | 곳 | 팀 처리 |
|---|---|---|
| **A. 접근 판정**(팀 권한을 반영해야 한다) | `AccessControl`(`isProjectMember`, `isProjectManager`), `SessionPermissions.projectManager`·`projectMember`, `ProjectService.hasMember`·`isGuest`, `ProjectViewContext.guest`·`projectMember`, `ApiUserNodes.isCandidate`, `BoardWriteController`(공지 권한, 파일 올리기), `PullRequestCreateController`(보내는 프로젝트 후보), `PullRequestPageAssembler`(충돌 도움말의 주소), `IssueService`(이슈 이동 때 라벨 옮기기), `OrganizationService.visibleProjects`, `NoheadViews`, `MigrationService.isAllowedToSettings`, `ProjectTransferService`(보내는 사람이 관리자인지) | 실효 권한 서비스(`TeamAccessService`)로 바꾼다. 단계 2의 주된 일이다 |

중요한 발견: v1.6의 **"게스트"**는 시스템 게스트 사용자가 아니라 "프로젝트에 역할 행이 없는 로그인 사용자"를 뜻하는 화면 개념이다(`ProjectService.isGuest`, `ProjectViewContext.guest`). 팀 접근자는 이 정의에서 게스트이지만 실제 권한은 구성원 이상이다. 그래서 화면 판정(게스트 여부)은 **"역할 행이 없거나 팀 권한도 없는 사용자"**로 바꿔야 하고, 이를 빠뜨리면 팀 구성원에게 게스트용 화면이 보인다. 단계 2의 화면별 시험 항목에 넣었다.

### (4) 리뷰 요청 저장 구조

- 대기 중인 요청은 연결 테이블 `pull_request_review_request`에 저장한다(`PullRequest.reviewRequests`, 사용자 집합). 이력은 타임라인 이벤트에 남는다.
- 요청 대상은 `IssueListService.assignableUsers`(프로젝트 구성원과 조직 구성원, 비공개 조직 프로젝트는 조직 관리자만)로 정한다. **이 함수가 팀 접근자를 포함해야** 팀 구성원에게 리뷰를 요청할 수 있다(단계 2).
- 팀 리뷰 요청은 새 테이블 `pull_request_review_team_request`가 필요하다. 팀 구성원 한 명이 리뷰를 제출하면 요청이 채워진 것으로 지운다. 요청한 팀 구성원 각각에게 알림을 보낸다(팀 알림 설정과 무관).
- 리뷰 판정(`pull_request_review`)과 승인 집계(`PullRequestReviewService`)는 사용자 단위라 바꾸지 않는다.

### (5) 삭제·정리 지점

- 조직 삭제(`OrganizationManagementService.delete`)는 네이티브 SQL로 연관 행을 지운다. 여기에 `team_project`, `team_user`, `team` 삭제를 더한다.
- 프로젝트 삭제(`ProjectDeletionService`)는 "v1.6 외래 키 그래프에서 닿는 테이블을 모두 처리"하는 구조 시험(`ProjectDeletionServiceTest`)이 있다. `team_project`를 더하면 이 시험이 기대하는 목록도 갱신한다.
- 새 테이블은 `SchemaMetadata`의 `INTENDED_ADDITIONS`와 `AddedTablesSchemaTest`, 내보내기 표(`DataTables`, 지금 69개)에 올린다.

## 6. 위험과 한계

- **접근 제어 회귀**: 가장 큰 위험이다. 팀 경로는 권한을 올리기만 하고, 팀이 없으면 새 질의를 하지 않도록(또는 결과가 같도록) 만든다. 단계 2에서 기존 시험이 모두 그대로 통과해야 다음으로 간다.
- **성능**: 권한 판정마다 팀 조회가 더해질 수 있다. 한 요청 안에서 기억하고, 사용자가 속한 팀이 없으면 곧바로 끝낸다. 상위 팀 따라 올라가기는 깊이 한도(5)로 묶는다.
- **새 권한 단계 3개**: Read, Triage, Maintain은 Yona에 없던 개념이라 모든 동작에서 허용 여부를 정해야 한다. 단계 0의 표가 빠진 동작이 있으면 안전한 쪽(거절)으로 둔다.
- **직접 조회 25개 파일**: "접근할 수 있는가"를 `project_user`로 직접 묻는 곳(4.8절 A, 약 15곳)이 빠지면 팀 구성원이 어떤 화면에서만 거절당하거나 게스트용 화면을 본다. 4.8절 목록과 단계 2의 화면별 시험으로 막는다.
- **이름 충돌 검사 누락**: 프로젝트 이름을 정하는 경로(6곳) 중 하나가 새 검사를 빠뜨리면 충돌이 생긴다. 단계 1의 시험으로 6개 경로를 모두 확인한다.
- **이번 범위에서 빠지는 것**: 팀 토론, 라운드 로빈 리뷰 배정, IdP 그룹 동기화, 코드 소유자.
