# Git LFS(X-8) 구현 계획

> **상태: 계획서 작성(2026-11-02). 결정 질문 D-79의 답변을 기다린다. 구현은 답변을 받은 뒤 시작한다.** 결정은 [decisions.md](../decisions.md) D-79에 있다.

## 1. 목적

큰 바이너리 파일(디자인 자산, 데이터 세트, 빌드 산출물)을 git 저장소 밖에 두고 저장소에는 **포인터 파일**만 두는 Git LFS를 Yona가 서버로서 받아 준다. v1.6에는 LFS 서버가 없어 `git lfs push`가 실패한다. 이 항목은 v1.6의 기존 동작과 계약을 바꾸지 않고 **새 경로만 더하는** 추가 항목이다(D-28).

## 1.1 현황(2026-11-02 조사)

- **이 저장소(`next2`)에는 LFS 컨트롤러가 없다.** 소스와 시험 어디에도 LFS 코드가 없고, 사이트 구성에도 LFS 항목이 없다.
- **v1.6에도 LFS 서버가 없다.** v1.6은 JGit의 `jgit.lfs` 의존성만 가지고 있을 뿐 LFS 라우트가 없다(`yona-v1.6-wiki`의 tech-stack, medium-severity-fix-status 기록).
- **이전 구현인 `next` 브랜치에는 시제품이 있다**: JGit의 LFS 서버 라이브러리(`org.eclipse.jgit.lfs.server`의 `LfsProtocolServlet`, `FileLfsRepository`)를 서블릿으로 등록하고(`/git-lfs/*`), 객체 전송용 `LfsStorageController`(`/git-lfs/{소유자}/{프로젝트}/objects/{oid}`)와 옛 프로젝트 이름 해석(`LfsLocation`)을 가졌다. 저장은 `yona.lfs.base-dir/<소유자>/<프로젝트>`이고 사용자가 `lfs.url`을 설정해 쓰는 방식이다. 이 시제품은 **인증이 없고**(경로만 알면 올리고 내려받는다), **올라온 내용의 해시와 크기를 확인하지 않으며**, 한도와 이어받기가 없다. 참고만 하고 그대로 옮기지 않는다. 옛 이름 해석은 `findByPreviousPlaceOf` 규칙(v1.6 GitApp)을 따라 이 계획에 넣는다(단계 2).

## 2. 프로토콜 요약(공식 규격 기준)

- 클라이언트는 저장소(remote) 주소에서 LFS 주소를 **자동으로 만든다**. 주소가 `.git`으로 끝나면 `/info/lfs`를 붙이고, **끝나지 않으면 `.git/info/lfs`를 붙인다**(공식 서버 탐색 규격). Yona의 저장소 주소는 v1.6부터 `https://host/{소유자}/{프로젝트}`(`.git` 없음)이므로 클라이언트가 실제로 부르는 주소는 `https://host/{소유자}/{프로젝트}.git/info/lfs`이다. **그래서 LFS 경로는 `{프로젝트}.git` 꼴을 받아야 하고, 지금의 git HTTP 경로(`.git` 없는 `info/refs`)와는 모양이 다르다.** 사용자가 `lfs.url`로 직접 지정하면 `.git` 없는 주소도 쓰므로 둘 다 받는다. (단계 0에서 실제 클라이언트로 확인한다.)
- **Batch API** `POST …/info/lfs/objects/batch`: 본문 `{"operation": "download"|"upload", "transfers": ["basic"], "objects": [{"oid", "size"}]}`. 응답은 객체마다 `actions`(`download`, `upload`, `verify`)의 `href`와 `header`를 준다. 이미 있는 객체의 업로드는 `actions`를 비운다. 미디어 타입은 `application/vnd.git-lfs+json`이다.
- **basic 전송**: 업로드는 `PUT …/objects/{oid}`, 내려받기는 `GET …/objects/{oid}`(`Range` 이어받기), 올린 뒤 선택적으로 `POST …/verify`.
- 객체 이름 `oid`는 내용의 **SHA-256 16진수 64자**이다. 서버는 올라온 내용의 해시와 크기가 맞는지 확인해야 한다.
- 인증은 git HTTP와 같은 Basic이다. 클라이언트가 git의 자격 증명 도우미를 그대로 쓴다.
- **SSH**는 `git-lfs-authenticate <경로> <download|upload>` 명령을 서버가 받아 `{"href", "header"}` JSON을 돌려주면 클라이언트가 그 HTTP 주소로 전송한다.
- **잠금 API**(`/info/lfs/locks`, `/locks/verify`, `/locks/{id}/unlock`)는 선택 기능이다. 서버가 404나 501을 주면 클라이언트는 잠금을 쓰지 않고 계속한다.

## 3. 설계

### 3.1 경로와 인증

| 경로 | 메서드 | 필요한 권한 |
|---|---|---|
| `/{소유자}/{프로젝트}[.git]/info/lfs/objects/batch` | POST | `operation`에 따라 읽기 또는 쓰기 |
| `/{소유자}/{프로젝트}[.git]/info/lfs/objects/{oid}` | GET, PUT | 읽기, 쓰기 |
| `/{소유자}/{프로젝트}[.git]/info/lfs/verify` | POST | 쓰기 |

- 권한 판단은 **git HTTP와 똑같이** 한다: `BasicAuthResolver`로 신원을 확인하고 `allowsRepository(identity, project, write)`로 토큰 범위를 보며(읽기 `repo`와 `read:repo`, 공개 프로젝트의 `public_repo`, 쓰기 `repo`), `AccessControl`로 프로젝트 권한을 본다. 쓰기는 푸시 권한과 같다.
- 개인용 토큰만 받고 OAuth 토큰은 받지 않는 현재 git HTTP 규칙(D-70)을 그대로 따른다. 그래서 조직의 OAuth 앱 정책(D-78)은 이 경로에 해당하지 않는다.
- 공개 프로젝트의 내려받기는 익명도 된다(git 복제와 같다). 인증 실패 제한(`TokenFailureLimiter`)과 지표(`VcsMetrics`, `vcs=git_lfs`)도 같이 쓴다.

- `[.git]`은 있어도 없어도 같은 프로젝트로 본다. 프로젝트 이름에 `.git` 접미사를 쓰는 경우는 v1.6 이름 규칙에서 따로 확인한다(단계 0). 이 경로 처리는 LFS 경로에만 두고 기존 git HTTP 경로(`info/refs`, `git-upload-pack`)는 바꾸지 않는다(v1.6 계약 유지).

### 3.2 저장

- 위치: `<데이터 디렉터리>/repo/lfs/<소유자>/<프로젝트>/objects/<oid 앞 2자>/<다음 2자>/<oid>`. 저장소(`repo/git/<소유자>/<이름>.git`) 바로 옆 구조이다. 현재 코드의 실제 배치(확인 2026-11-02)는 `<데이터 디렉터리>/repo/git/<소유자>/<이름>.git`(Git, `GitRepositories`), `…/<이름>.wiki.git`(위키, 같은 `repo/git` 아래), `<데이터 디렉터리>/repo/svn/<소유자>/<이름>`(Subversion, `SvnRepositories`)이고, 데이터 디렉터리는 `yona.data-dir`, 없으면 `-Dyona.data`, 그것도 없으면 작업 디렉터리 순이다(`DataDirectory`). `repo/lfs`는 이 `repo/<종류>/<소유자>/<이름>` 규칙을 따른 새 형제 디렉터리이다. 위키 저장소는 LFS를 지원하지 않는다.
- 올릴 때는 임시 파일에 받으면서 SHA-256과 길이를 센 뒤 **선언한 값과 맞을 때만** 제자리로 옮긴다(원자적 이동). 맞지 않으면 400이고 임시 파일을 지운다. 이미 있는 객체는 다시 쓰지 않는다.
- 프로젝트 지우기, 이름과 소유자 바꾸기, 프로젝트 이전은 저장소와 같이 LFS 디렉터리도 따라간다(`RepositoryService`의 같은 자리에서 처리).
- 데이터베이스 테이블은 첫 단계에는 필요 없다(객체는 파일 시스템, 용량은 디렉터리에서 센다). 잠금을 넣으면 `lfs_lock` 테이블이 하나 필요하다.

### 3.3 사이트 설정과 한도

- 사이트 관리자 설정: LFS 사용(켜짐/꺼짐), **객체 하나의 최대 크기**, 프로젝트별 **용량 한도**(선택). 꺼져 있으면 batch API가 404이다.
- 한도를 넘는 업로드는 batch 응답에서 객체별 오류(`error: {code: 413, message}`)로 알린다(규격의 방식).

### 3.4 화면

- 코드 보기에서 LFS 포인터 파일(`version https://git-lfs.github.com/spec/v1` 로 시작하는 작은 파일)을 열면 **원래 포인터 내용은 그대로 보이고**, 위에 "Git LFS로 저장된 파일(크기)" 줄과 내려받기 링크를 더한다. v1.6의 표시는 바꾸지 않는다.
- 프로젝트 설정에 LFS 사용량(객체 수, 용량)을 한 줄 보인다(관리자만).

### 3.5 SSH

- 내장 sshd와 Go 도우미(`yona-ssh`) 경로 모두에서 `git-lfs-authenticate`를 받는다. 응답은 HTTP 주소와 **짧은 수명의 서명 토큰**(사용자, 프로젝트, 동작에 묶인 약 10분 값)을 헤더로 준다. 이 토큰은 LFS 경로에서만 유효하다.

### 3.6 감사와 지표

- 객체 올리기와 내려받기는 양이 많아 감사 로그에 남기지 않고 지표(`VcsMetrics`: 요청 수, 바이트, 지연)로 남긴다. 잠금과 사이트 설정 변경은 감사 로그에 남긴다.

### 3.7 Mercurial(X-7)과의 관계

- Mercurial에는 **내장 `lfs` 확장**이 있고 **Git LFS와 같은 batch 규격**으로 서버와 말한다(포인터를 저장소에 어떻게 두는지만 다르다). 그래서 이 항목의 서버 쪽(batch, 객체 전송, 저장, 한도)은 **VCS에 묶이지 않게** 만들면 X-7 때 그대로 쓸 수 있다.
- 설계 규칙: (1) 저장 위치는 `repo/lfs/<소유자>/<프로젝트>/`로 `repo/git`과 무관하다. (2) 서비스 계층(`LfsService`)은 "프로젝트와 oid"만 안다. git에 대한 가정(포인터 파일, JGit)은 코드 보기와 포인터 판별 쪽에만 둔다. (3) 프로젝트가 LFS를 지원하는지는 한 군데(`LfsSupport.supports(project)`)에서 정하고 지금은 `GIT`만 허용한다. X-7의 선행 정리가 만드는 "지원하는 VCS 선언 방식"이 생기면 그것으로 바꾼다. Subversion은 지원하지 않는다.
- Mercurial 클라이언트가 LFS 주소를 어떻게 만드는지(git은 `.git/info/lfs`를 붙인다)와 주소 모양은 X-7을 할 때 실제 `hg`로 확인한다. 지금은 확인하지 못했다. 그때 경로를 더하는 일만 남도록 경로 처리를 한 곳에 모은다.

## 4. 단계(시험 먼저)

| 단계 | 내용 | 확인 |
|---|---|---|
| 0 | 조사: 실제 `git-lfs` 클라이언트(3.x)의 주소 탐색, 인증 헤더 전달, 오류 처리 확인 | 선생님 허락을 받아 `git-lfs` 바이너리를 내려받아 확인 |
| 1 | 저장소 계층, 사이트 설정, batch와 객체 전송(basic), 해시와 크기 검증, 한도 | 단위와 통합 시험, 규격의 오류 모양 |
| 2 | 프로젝트 지우기, 이름과 소유자 바꾸기, 이전, 포크에서의 동작 | 수명 주기 시험 |
| 3 | SSH `git-lfs-authenticate`(내장 sshd, Go 도우미) | 실제 OpenSSH 컨테이너로 확인 |
| 4 | 코드 보기의 포인터 안내, 설정의 사용량, 사이트 설정 화면 | Playwright 한 번 |
| 5 | 잠금 API(질문 2번에서 하기로 한 경우) | 잠금 시험, 실제 클라이언트 |
| 6 | 문서(이 문서를 `git-lfs.md`로 바꿈), 구성 키, 로드맵 갱신 | |

## 5. 위험과 주의

- **디스크**: 큰 파일이라 디스크가 가장 큰 위험이다. 한도와 사용량 표시를 처음부터 넣는다.
- **스트리밍**: 업로드와 다운로드는 메모리에 올리지 않고 흐르게 한다(수 GB까지). 서블릿 컨테이너의 요청 크기 제한과 Spring의 멀티파트 설정이 이 경로에 걸리지 않게 한다.
- **포크 원본 삭제**: 포크가 원본의 객체를 빌려 쓰게 하면(질문 4번 (나)) 원본을 지울 때 규칙이 필요하다.
- **백업**: 사이트 데이터 내보내기는 데이터베이스만 다룬다. LFS 디렉터리는 저장소와 같이 운영자가 파일 시스템에서 백업해야 한다(문서에 적는다).
- **실제 클라이언트 확인이 필수**: 규격이 세부(헤더, 상태 코드, 이어받기)에서 까다로워서 `git-lfs` 실물로 확인하기 전에는 끝났다고 하지 않는다.
