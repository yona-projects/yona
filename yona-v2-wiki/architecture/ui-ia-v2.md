# UI 정보 구조(IA) 재설계 v2

> **상태: 설계안, 선생님 확인 대기(`decisions.md` D-138, D-139).** 이 문서는 D-134(GitLab 방식 맥락별 사이드바, 승인)의 첫 설계안(v1)을 **대체**한다. 선생님이 "기존 골격에도 빠진 것이 있을 수 있으니 재설계하라"고 하셔서, v1의 맥락과 묶음을 전제로 두지 않고 **갱신된 UI 계약과 화면을 여는 주소 181개를 처음부터 다시 훑어** 도출했다(3절). v1에서 **그대로 지킨 승인 결정**은 0.2절에 있다. 구현은 하지 않았다.
> 새 전제: 새 UI는 **Bootstrap 5 네이티브 구성 요소**로, 스크립트는 **TypeScript**로 다시 만든다(D-139). D-135(IndexedDB), D-136(htmx), D-137(단축키)은 **지킨다**(5절).
> GitLab의 구조는 일반 지식이며 현재 GitLab 버전과 대조하지 않았다(9절).

## 0. 요약

### 0.1 무엇이 달라졌나 (v1 대비)
1. **골격을 다시 도출했다.** v1은 "지금의 메뉴를 사이드바로 옮기기"였고, 이번에는 **사용자의 작업(무엇을 하러 오는가)과 역할**에서 출발해 맥락과 묶음을 다시 만들었다(4절). 결과적으로 v1의 맥락 5개는 유지되지만 **빠져 있던 것**(보낸 풀 리퀘스트와 닫힌 풀 리퀘스트 탭, 사용자 공개 프로필, 검색 범위, 사이트의 데이터 가져오기와 내보내기, 프로젝트 수명 주기 화면, 조직 설정이 조직 셸 밖에 있던 것, 셸 밖 화면의 범위, 맥락 횡단 기능 등 22가지)이 자리를 얻었고 일부 묶음이 바뀌었다(3절, 4.3절). 반대로 **통계와 전역 내 리뷰는 만들지 않는다**(미완 화면, v1.6에 없음).
2. **Bootstrap 5 네이티브로 구성한다.** 셸의 모든 부품이 BS5 구성 요소에 대응한다(4.2절). 직접 만드는 CSS는 사실상 없다(레일과 묶음 접기를 없앴다, D-141). 이미 Sass로 BS를 빌드하고 있다(`build-tools/sass`, `app/assets/stylesheets/bootstrap.scss`).
3. **TypeScript로 재작성한다.** 셸, 저장소, 단축키, htmx 수명주기 같은 **새로 쓰는 코드는 처음부터 TS**이고, 화면별 옛 스크립트는 화면을 새 셸로 옮길 때 함께 TS로 옮긴다(6절, 7절). 규모와 순서는 `ui-ts-inventory.md`에 있다.
4. **서버가 사이드바를 그린다.** 항목과 보이는 조건(권한, 기능 켜짐, 저장소 종류)은 서버(Kotlin 데이터 + Thymeleaf)가 판정해 HTML로 내려 준다. TS는 그 위에서 접기, 전환기, 기억만 맡는다. 계약의 서버 규칙(메뉴를 끈 이슈 주소 404 등)과 화면의 항목이 **같은 데이터에서** 나오게 하기 위해서다(4.4절).

### 0.2 v1에서 그대로 지키는 승인 결정(D-134)
GitLab 방식 맥락별 왼쪽 사이드바, **메뉴 이름은 v1.6 용어 유지**(코드 주고받기, 리뷰, 게시판), **반응형**(D-141로 2단계로 단순화: 992 미만 서랍 기본 닫힘, 이상 고정. 폰과 폴드 접힘은 기억 제외), 맥락 단위 단계별 전환, 이슈 라벨을 계획 묶음으로, 홈을 "내 작업"과 "탐색"으로, **핀 사이드바(iframe)를 전환기로 흡수하고 iframe 제거**(기억 키 `shallWeOpenLeftNavigation`과 `/user/sidebar` 주소는 이어 씀), 아바타 메뉴는 짧은 드롭다운, 시험 뷰포트 6가지(344, 390, 673, 768, 1024, 1280). 이 결정들과 어긋나는 제안은 이 문서에 없다.

## 1. 목표와 제약

- **목표**: 화면 이동의 틀을 **맥락마다 사이드바 하나**로 모으고, 위에 경로와 페이지 머리를 둔다. 틀은 Bootstrap 5 구성 요소로 만들고, 동작은 TypeScript 모듈로 만든다.
- **지킬 것**
  1. **주소, 요청, 응답 계약, 기능은 바꾸지 않는다**(D-134). 바뀌는 것은 틀과 마크업, 스크립트 구현이다. 주소 불변은 시험으로 지킨다(7절).
  2. **갱신된 UI 계약이 새 UI의 명세이다**(`ui-contract/`). 새 UI가 그 계약대로만 동작하면 기능이 같아야 한다. 계약의 교차 규칙(`ui-contract/index.md`의 "수정으로 달라진 화면 계약")을 새 틀이 깨지 않는다: 컨텍스트 경로, 메뉴를 끈 기능의 404, 알림 이스케이프, 중복 제출 방지, 로그인 잠금, 비밀번호 정책 등.
  3. **마크업은 BS5 고유 모양**을 쓴다(호환 층 금지, D-56). 현대화는 BS2 모양 유지가 아니라 BS5 고유 모양이다.
  4. **서버 권한은 화면과 따로 있다**(A-459). 사이드바가 항목을 숨겨도 서버 검사는 그대로다. 화면이 보이게 하는 조건과 서버가 막는 조건이 어긋나지 않게 **한 곳의 데이터**에서 만든다(4.4절).
  5. Vue 컴포넌트와 2단 보기 개선은 이 작업의 범위가 아니다(나중 UI 개편). 이 IA는 그 개편이 올라탈 틀이다. 새 UI는 JSON API와 클라이언트 렌더링을 **늘리지 않는다**(D-136).
- **v1.6 동등성 원칙과의 관계**: 틀과 마크업, 스크립트 구현을 바꾸는 일이라 선생님 승인이 필요하다(D-134 승인, D-138, D-139 확인 대기). 응답 비교(`tools/v16-diff`)에는 영향이 없어야 하고 영향이 나오면 결함이다.

## 2. 입력: 갱신된 계약에서 뽑은 사실

- **화면을 여는 주소(GET)는 181개**이다(웹 컨트롤러, 외부 REST 제외). 프로젝트 안 84개, 사용자 24개, 사이트 19개, 조직 16개, 사용자 인증 6개, 이전 8개(JSON 조회 포함), 그 밖의 전역 화면(홈, 프로젝트 목록 `/projects`, 그룹 목록 `/orgs`, 전역 검색 `/search`, 알림 `/notifications`, 도움말 `/_help`, 프로젝트 만들기 `/projectform`, 가져오기 `/_import`, 비밀번호 찾기, 이메일 확인 등)이다.
- **템플릿 230개**(user 33, common 30, project 26, issue 22, organization 17, site 15, pullrequest 14, code 14, error 9, search 8, index 8, layout 7, wiki 6, board 6, milestone 5, help 3, welcome 2, reviewthread, oauth, oauth2, migration, audit 각 1)이고 템플릿별 대응은 `ui-screen-map.md`에 있다.
- **역할**(권한 행렬 기준): 비로그인, 로그인 사용자, 프로젝트 구성원, 프로젝트 관리자(소유자 포함), 조직 관리자, 사이트 관리자. 사이트 관리자는 읽기 권한을 우회하지만 **메뉴를 끈 이슈, 마일스톤 주소 404는 관리자도 막는다**(`admin-role.md` F24). 로그인 ID가 `admin`일 때만 뜨는 붉은 띠는 권한이 아니라 알림이다(`admin-role.md` F1).
- **서버가 이미 판정하는 화면 조건**(새 사이드바가 재사용): 프로젝트 기능 메뉴 켜짐(`menuSetting.issue`, `milestone`, `board`, `code`, `pullRequest`, `review`, `wiki`), 코드 접근(`codeAccessible`), 저장소 종류 능력(`VcsCapability`: BRANCHES, TAGS, PULL_REQUESTS, DEFAULT_BRANCH, LFS_SCREEN, DEPLOY_KEYS, PROTECTED_REFS, TAG_MANAGEMENT 등), 사이트 설정(익명 허용, 가입, SSO 전용, 업데이트 알림), 사용자 상태.
- **v1.6에 없던 추가 기능의 화면**: 2단계 인증과 보안 키, 사용자 토큰, GPG와 SSH 키, OAuth 앱과 정책, 연결된 계정, 보안 기록과 감사 화면(사이트, 조직, 사용자), 규칙 묶음(rulesets), 위키, 기기 인증, MCP, 사이트의 보안, SSO, 업데이트, 진단. 이들은 v1 골격이 대부분 담았지만 **사용자 감사와 조직 감사의 위치**, **데이터 가져오기와 내보내기**는 어색하거나 빠져 있었다.
- **새 계약이 요구하는 것**: 컨텍스트 경로(모든 주소가 접두어를 가진다), 알림 문구 이스케이프, `data-submit-once`, 메뉴 꺼짐 404, 단축키 안내와 실제 등록의 일치(D-137), 로그인 잠금과 비밀번호 정책 안내 토스트, 이전 화면의 서버 거절 표시.

## 3. 기존 골격에 빠졌거나 어색했던 것 (v1 점검 결과)

주소 181개와 템플릿 230개를 전수로 대 본 결과이다. 사실은 소스와 계약에서 확인했고 템플릿별 근거는 `ui-screen-map.md`("기존 골격에 빠졌거나 어색한 것" 절)에 있다. 골격 적합도는 템플릿 230개 중 **적합 200, 어색함 20, 자리 없음 10**이었다.

## 4. 재설계 IA

### 4.1 원칙

1. **맥락(scope)과 영역(area)의 두 층**: 맥락은 "어디에 있는가"(전역, 프로젝트, 조직, 사용자, 사이트), 영역은 "무엇을 하는가"(개요, 코드, 계획, 협업, 문서, 설정). 사이드바는 맥락마다 하나이고 영역이 묶음이다.
2. **기능은 한 곳에만 산다.** 같은 기능이 두 곳에서 열려도 **정식 위치는 하나**이고 다른 곳은 링크이다(예: 알림 목록은 내 작업, 알림 설정은 내 설정, 프로젝트 가져오기는 새로 만들기).
3. **보이는 것과 막히는 것이 같다.** 사이드바의 항목 가시성과 서버의 접근 검사가 **같은 데이터**를 쓴다. 숨긴 기능의 주소를 직접 열면 서버가 막는다(404 또는 403). 계약의 규칙을 그대로 따른다.
4. **이름은 v1.6 용어**(D-134 결정 2).
5. **맥락 횡단 기능은 같은 부품을 쓴다**: 검색, 알림, 감사, 목록(이슈, 게시판, 풀 리퀘스트)은 맥락만 달리해 같은 부품과 같은 단축키를 쓴다(4.5절).
6. **셸 밖은 최소로, 이유가 있을 때만.** 맥락이 없거나(로그인) 보안상 분리(동의, 기기 승인)하거나 별도 흐름(이전)인 화면만 셸 밖이다.

### 4.2 셸: Bootstrap 5 구성 요소 대응 (D-141로 단순화)

```
┌─────────────────────────────────────────────────────────────┐
│ ☰ Y  [전환 ▾]  [범위▾ 검색…]                   +   🔔  아바타▾ │  navbar
├────────────┬────────────────────────────────────────────────┤
│ 맥락 이름    │  breadcrumb                       [주요 단추]    │
│ 홈          │  ──────────────────────────────────────────────  │
│ 코드        │                                                │
│ 이슈        │               본 문 (htmx 교체 영역)             │
│ ...         │                                                │
└────────────┴────────────────────────────────────────────────┘
```

| 셸 부품 | Bootstrap 5 구성 요소 | 직접 만드는 것 | 책임 |
|---|---|---|---|
| 상단 바 | `navbar`(`sticky-top`), `navbar-brand`, `input-group`(검색), `dropdown`(전환, `+`, 아바타), `btn`, `badge` | 없음 | 전환기, 검색, 만들기, 알림, 관리자 진입 |
| 관리자 알림 띠 | `alert alert-danger`(로그인 ID가 `admin`일 때) | 없음 | 지금과 같은 알림(`admin-role.md` F1) |
| 사이드바(1024 이상 고정, 그 아래 서랍) | `offcanvas-lg` 하나 + `nav flex-column nav-pills`. 폭이 좁으면 `offcanvas`(포커스 가두기, Esc, 바깥 누르기 닫기를 BS가 제공) | 폭 256px 정도 | 맥락 메뉴(평평한 항목 목록) |
| 전환기 | 상단 바 `dropdown` 안의 `nav-tabs`(3탭), `list-group`, `input`(이름 필터), `spinner-border`, `placeholder` | 없음 | 즐겨찾기, 프로젝트(하위 4탭), 최근 읽은 이슈 |
| 경로 | `breadcrumb` | 없음 | 위치 표시(깊이가 2 이상일 때만) |
| 페이지 머리 | `d-flex`, `h1.h4`, `btn-toolbar`, `btn-group` | 없음 | 제목, 주요 단추 한 개 강조 |
| 목록 화면 | `table table-hover`(`table-responsive`), `list-group`, `pagination`, `form-select`, `input-group` | 없음 | 이슈, 글, 풀 리퀘스트, 사용자, 프로젝트 목록 |
| 폼 | `row g-3`, `form-floating`, `form-text`, `invalid-feedback`, `form-check`, `form-switch` | 없음 | 모든 폼, 서버 오류 422는 `is-invalid`로 |
| 알림(토스트) | **`toast`** + `toast-container` | 없음 | `$yona.notify`의 대체(3초 자동 닫힘) |
| 알림 창, 확인 창 | **`modal`**(`modal-dialog-centered`) | 없음 | `$yona.alert`와 `confirm`의 대체 |
| 탭(화면 안) | `nav-tabs`, `nav-pills`, `tab-pane` | 없음 | 열림, 닫힘, 코드의 파일, 커밋, 브랜치, 태그 같은 화면 안 구분 |
| 배지, 상태 | `badge`, `text-bg-*` | 없음 | 이슈 상태, 개수 |
| 도움말, 단축키 안내 | `modal`(`?` 키) | 없음 | D-137 |

- **테마색은 현재 요나와 같다**(D-58: Bootstrap 5 기본 팔레트 + 요나 고유 주황). 새 색을 만들지 않고 `_bs-variables.scss`와 `_variables.scss`의 값을 그대로 쓴다. 화면 틀과 아티팩트는 실제 앱에서 측정한 값을 썼다: 상단 바 `#1B1B1B`, 주황 `#FF7332`(활성 메뉴 글자 `#FC491E`), 성공 단추 `#198754`, 위험 `#DC3545`, 본문 글자 `#333`.
- **직접 만드는 CSS가 사실상 없다.** 아이콘 레일과 묶음 접기(`accordion`)를 없앴기 때문이다(D-141). 사이드바 폭과 `.shell-*` 접두어 몇 줄뿐이다. 옛 `yobi.css`와의 충돌(206px 고정 입력란 등)은 BS 유틸리티로 피한다.
- **사이드바 규칙**: 묶음 제목이 없고 하위 항목이 펼쳐지지 않는다. 항목은 항상 아이콘 + 글자이다(`yobicon`을 이어 쓴다). 설정이 있는 맥락(프로젝트, 조직)은 설정 항목을 누르면 사이드바가 **설정 전용 목록**으로 바뀌고 맨 위에 "← 프로젝트로"(또는 "← 조직으로")가 붙는다(4.3.2절).

### 4.3 맥락별 구조 (D-141: 모두 묶음 제목 없는 평평한 목록)

표의 "보이는 조건"은 서버가 판정한다(4.4절). 근거 줄 번호와 템플릿별 대응은 `ui-screen-map.md`와 해당 `ui-contract/<영역>.md`에 있다.

#### 4.3.1 전역(프로젝트 밖)

| 항목 | 주소 | 보이는 조건 |
|---|---|---|
| 프로젝트 | `/projects` | 모두(익명은 사이트 설정이 허용할 때) |
| 그룹 | `/orgs` | 모두(같은 조건) |
| 내 이슈 | `/user/issues` | 로그인 |
| 알림 | `/` | 로그인 |
| 내 파일 | `/user/files` | 로그인 |

- 홈(`/`)은 지금처럼 알림 화면이고 사이드바에서 "알림"이 강조된다("기본 페이지로 지정"으로 바꿀 수 있다).
- "새 프로젝트, 프로젝트 가져오기, 새 그룹"은 사이드바에 두지 않는다. 상단 바 `+`에 이미 있고, 프로젝트 가져오기는 프로젝트 만들기 화면의 단추로만 들어간다.
- **내 코드 주고받기**(사용자 페이지의 코드 주고받기 탭 `/{내 ID}?selected=pullRequests`)는 넣지 않는다(v1.6에 전용 화면이 없고 최근 기간 필터라서 GitLab의 Merge requests와 다르다). 필요하면 추가 개발 항목으로 올린다(선생님 확인 대기).
- 도움말: 단축키 안내(`?` 키, D-137)는 새 동작이다. `/_help` 링크를 아바타 메뉴에 더할지는 화면 모양이 바뀌므로 결정 8절 6번에서 묻는다.
- 사용자 공개 프로필(`/{user}`)은 이 맥락의 하위 화면이다. 사이드바는 그대로이고 페이지 안 `nav-tabs`로 프로필 구성(`user.md`)을 둔다. 내 설정(4.3.4절)과는 다른 화면이다.
- 비로그인 홈(소개, 로그인, 가입)은 항목이 프로젝트, 그룹뿐인 사이드바와 소개 블록을 둔다. 로그인 화면 자체는 셸 밖이다.

#### 4.3.2 프로젝트

**메인 사이드바**는 지금의 가로 메뉴와 같은 이름과 순서이고 항목은 9개이다(D-140, D-141).

| 순서 | 항목 | 주소 | 보이는 조건 |
|---|---|---|---|
| 1 | 홈 | `~` | 읽기 가능 |
| 2 | 코드 | `~/code` | `menuSetting.code`이고 코드 접근 가능 |
| 3 | 이슈 | `~/issues` | `menuSetting.issue`(꺼지면 항목도 주소도 404) |
| 4 | 코드 주고받기 | `~/pullRequests` | `menuSetting.pullRequest`, PULL_REQUESTS 능력, 코드 접근 |
| 5 | 리뷰 | `~/reviews` | `menuSetting.review`, 코드 접근 |
| 6 | 마일스톤 | `~/milestones` | `menuSetting.milestone`(꺼지면 항목도 주소도 404) |
| 7 | 게시판 | `~/posts` | `menuSetting.board`(꺼져도 주소는 열려 있음, 계약) |
| 8 | 위키 | `~/wiki` | `menuSetting.wiki` |
| 9 | 설정 | `~/settingform` | 프로젝트 관리자(서버가 `UPDATE`를 요구한다) |

- 코드의 **파일, 커밋, 브랜치(BRANCHES 능력), 태그(TAGS 능력)**와 코드 주고받기의 **열림, 닫힘(`~/closedPullRequests`), 보냄(`~/sentPullRequests`)**은 사이드바 하위 항목이 아니라 **화면 안 탭**이다(지금과 같다).
- **설정 전용 사이드바**: 설정을 누르면 사이드바가 다음 목록으로 바뀌고 맨 위에 "← 프로젝트로"가 붙는다.

| 항목 | 주소 | 보이는 조건 |
|---|---|---|
| 일반 | `~/settingform` | 프로젝트 관리자 |
| 구성원 | `~/members` | 프로젝트 관리자 |
| 규칙 | `~/setting/rulesets` | PROTECTED_REFS 능력 |
| 배포 키 | `~/setting/deploykeys` | DEPLOY_KEYS 능력 |
| Git LFS | `~/setting/lfs` | LFS_SCREEN 능력(Mercurial은 이름 LFS) |
| 웹훅 | `~/webhooks` | 프로젝트 관리자 |
| 라벨 | `~/issue/labelsform` | 이슈 메뉴를 꺼도 항상 보임(서버가 주소를 열어 둔다) |
| 위험 구역 | `~/changeVCS`, `~/transfer`, `~/deleteform` | 이전과 삭제 항상, 저장소 종류 변경은 `menuSetting.code` |

- 통계(`~/statistics`)는 미완 화면이라 항목을 만들지 않는다(3절 4번).
- **머리(페이지 안, 사이드바 아님)**: 지켜보기(수, 목록 `~/watchers`), 즐겨찾기, **포크**(`~/newFork`), **코드 주고받기 만들기**(`~/newPullRequestForm`), 프로젝트 안 검색(`~/search`)이 프로젝트 머리의 단추이다. 계약의 조건(로그인, 코드 접근, VCS 능력)을 그대로 따른다.
- 저장소 종류에 따른 차이는 서버가 항목을 걸러 낸다(Subversion: 코드 주고받기, 배포 키, LFS 없음. Mercurial: 기본 브랜치는 북마크 이름으로 기억한다, A-467).
- 사이드바 단축키 `H C I M P B Q`는 항목에서 파생한다(`ui-shortcuts.md`). 리뷰와 위키는 지금처럼 키가 없다.

```

· 사용자 토큰 · SSH 키 · GPG 키 · 2단계 인증 · 보안 기록 · OAuth 앱(사용 설정이 켜졌을 때만)
```

주소는 `/user/editform`, `/user/editform/{password, emails, linked-accounts, notifications, token, ssh, gpg, two-factor, audit, oauth-apps}`이다. 보안 기록은 **사용자 본인의 기록**이다(3절 13번). "OAuth 앱"은 사용자 앱 사용 설정이 꺼지면 숨긴다(서버가 `new`를 403으로 막는 것과 일치).

#### 4.3.6 셸 밖 화면(맥락이 없거나 분리해야 하는 것, 10개)

`user/login`, `login-two-factor`, `signup`, `verified`, `reset-password`, `site/lost-password`, **`oauth2/consent`**(보안상 분리), **`user/device`**(기기 승인, 동의 화면과 성격이 같다), `welcome/*`(최초 설정, 비밀 키와 재시작). 인증 상태가 바뀌는 흐름이라 전체 문서 이동이 안전하고 사이드바가 의미 없다. **이전(Migration)**은 별도 레이아웃(`migration-layout`)을 유지한다. 프로젝트 이전 확인(`/project/transfer/{id}/{key}`)도 셸 밖이다. **프로젝트나 조직 안의 오류**(404, 403 등)는 맥락을 알고 있으므로 **셸 안**에서 그려 돌아갈 길(사이드바)을 준다(3절 14번). 기본 오류는 사이드바 없는 상단 바만 두고, 500과 413은 셸이 못 그려질 때를 위한 최소 문서로 물러난다. 오류 화면은 항상 전체 HTML이라 htmx 교체 대상이 아니다.

### 4.4 사이드바는 서버가 그린다 (한 곳의 데이터)

- **서버가 항목 목록을 만든다.** Kotlin에 `ShellNav`(맥락, 묶음, 항목, 아이콘, 주소, 보이는 조건, 활성 판정)를 한 곳에 정의하고, 조건은 **서버가 이미 가진 판정**(`menuSetting`, `codeAccessible`, `VcsCapabilities`, 역할)을 그대로 쓴다. Thymeleaf 조각이 이 목록으로 사이드바 HTML을 그린다.
- **같은 데이터가 서버 검사와 화면에 쓰인다.** 예: 이슈 메뉴를 끄면 `ProjectCheckStage.checkMenuEnabled`와 사이드바의 이슈 항목이 **같은 설정**을 본다. 화면과 서버의 조건이 어긋나 생긴 결함(예: 단축키 도움말, Mercurial 단추)을 구조로 막는다.
- **TS는 서버가 준 HTML 위에서만 일한다**: 접기와 기억(D-135), 전환기 불러오기(htmx), 단축키 선언 읽기(D-137), 활성 표시 갱신(htmx 이동 뒤). 항목 판정을 클라이언트가 하지 않는다.
- **주소의 컨텍스트 경로**는 서버가 `@{}`로 붙인다. TS는 `config.ts`의 `url()`만 써서 만든다(6.3절).

### 4.6 전환기, 경로, 페이지 머리 (D-141)

- **전환기**(핀 사이드바의 흡수, D-134 결정 7): **상단 바의 "전환 ▾" 드롭다운 하나**이다(사이드바에서 뺐다). 즐겨찾기, 프로젝트(하위 4탭: 최근 방문, 내가 만든, 지켜보는, 참여 중), 최근 읽은 이슈 3탭, 이름 필터, 조직별 묶음, 새로고침. 데이터는 지금의 조각(`index/my-organization-list`, `my-project-list`, `my-recent-issue-list`)을 그대로 쓰고 **htmx로 탭 내용을 불러온다**(D-136). 불러온 목록은 **IndexedDB의 `switcher` 캐시**에 담아 먼저 보이고 뒤에 갱신한다(D-135). 키는 사용자 ID로 구역을 나누고 로그아웃 때 지운다. `F`(한글 `ㄹ`)가 전환기를 열고 이름 필터에 초점을 준다(D-137 결정 2).
- **경로**(BS `breadcrumb`): 깊이가 2 이상일 때만 보인다. `조직 또는 사용자 / 프로젝트 / 화면`. 마지막은 링크가 아니다. 서버가 만든다.
- **페이지 머리**: 제목, 주요 단추(오른쪽, 하나만 강조). 목록 화면의 검색과 필터는 머리 아래 한 줄이다. 화면마다 달랐던 제목 크기와 단추 위치를 맞춘다.
- **본문 폭**: 본문 영역이 여백을 책임져 옛 `.row` 10px 넘침을 없앤다. 오른쪽 빈 공간을 만들지 않는다.

### 4.7 반응형: 2단계 (D-141, D-134의 3구간을 대체)

| 폭 | 동작 |
|---|---|
| Bootstrap 기본 `lg`(992px) 이상 | 사이드바 고정(펼침이 기본). 숨기기와 다시 보이기가 가능하고 상태를 기억한다(`shellSidebarCollapsed`, 예전 키 `shallWeOpenLeftNavigation`은 한 번 이전) |
| 992px 미만(폰, 폴드 접힘과 펼침, 태블릿 세로) | 사이드바는 서랍(`offcanvas`). **기본 닫힘**, ☰로 열고 이동하면 닫히며 기억하지 않는다 |

- **구간표를 바꾸지 않는다.** Bootstrap 기본 `lg`를 그대로 쓰므로 Sass 변수 변경과 옛 화면 경계 이동의 영향이 없다(D-138 18번이 해소된다). 아이콘 레일을 없애 직접 만드는 CSS도 거의 없다. 폴드 펼침(약 673px)은 서랍으로 처리한다.
- 깜빡임 방지(`<head>`의 짧은 스크립트가 저장된 숨김 상태를 그리기 전에 읽음), 좁음에서 저장 제외, 폴드 대응(접고 펴도 입력과 스크롤 유지, `dvh`, 터치 대상 44px, 안전 영역), 시험 뷰포트 6가지는 v1의 4.5절 내용을 이어 쓴다(레일 관련 항목은 제외).
- 서랍은 열면 초점을 안으로 모으고 Esc와 바깥 누르기로 닫으며 닫으면 ☰로 초점을 돌려준다(BS `offcanvas`가 제공).

### 4.8 역할별로 보이는 것

`ui-screen-map.md`가 템플릿별 조건에서 뽑은 표를 가진다. 요약 규칙:

- **프로젝트 관리자**: 설정 묶음 전체와 위험 구역.

## 5. 상호작용 설계: D-135, D-136, D-137을 지킨다

### 5.1 htmx (D-136: 화면 단위 옵트인, 조각 응답, 수명주기)
- **교체 영역**: 셸의 본문 `<main id="shell-main">` 하나. 사이드바 링크는 `hx-get`, `hx-target="#shell-main"`, `hx-push-url`로 본문만 바꾼다. 사이드바와 상단 바는 유지된다(같은 문서이므로, iframe 없음).
- **옵트인 기준**: 화면이 **swap-safe**(모듈이 한 번만 실행되는 최상위 부작용 없음, 문서 수준 핸들러가 쌓이지 않음, 정리 가능)임을 판정한 뒤 `data-swap-safe`를 켠다. 아니면 일반 이동. **새 TS 화면은 처음부터 swap-safe로 만든다**(6.2절의 `Page` 수명주기).
- **서버 계약**: `HX-Request`가 오면 본문 조각만 내려 준다(`Vary: HX-Request` 필수, D-98). 사이드바 활성 표시는 응답 헤더 또는 조각에 실어 갱신한다. 오류와 표지 없는 응답은 일반 이동으로 대체한다.
- **쓰는 곳**: 셸 이동, 폼(검증 오류 422를 `is-invalid`로), 토글과 행 갱신, 지연 불러오기(전환기, 알림 더 보기), 입력 중 검색, 알림 배지 폴링(선택). JSON API와 클라이언트 렌더링은 늘리지 않는다.
- **주소와 뒤로 가기**: 주소는 그대로이고 뒤로 가기는 서버 재로드(`historyCacheSize=0`)를 유지한다(D-136 결정 3).

### 5.2 IndexedDB (D-135: 하이브리드)
- **원본은 IndexedDB**, 첫 그림에 필요한 작은 값(사이드바 접힘, 2단 보기)만 **localStorage 거울**(그리기 전에 동기로 읽어야 깜빡임이 없다).
- **저장소(store)**: `drafts`(초안: 이슈, 글, 댓글. 지금 localStorage의 임시 저장을 이전), `switcher`(전환기 목록 캐시), `prefs`(개인 설정: 소개 블록 접기, 단축키 켜짐, 2단 보기, 탭 기억), `recent`(최근 방문, 검색어), `meta`(버전). **세션, 토큰, 비밀 값, 이슈와 프로젝트 본문 캐시는 담지 않는다.** 키에 사용자 ID를 넣고 로그아웃 때 캐시를 지운다. 초안은 남기되 설정으로 지우기를 고르게 한다.
- **TS 구성**: 라이브러리 `idb`(타입 포함, D-135 결정 3)로 `DBSchema`를 타입으로 선언하고, 저장소마다 `Store<T>`를 하나씩 둔다. 거울은 `MirroredPref<T>`가 쓴다. 이전(localStorage 키 → IndexedDB)은 **처음 한 번만** 읽어 옮기고 예전 키를 지운다(넓음 폭에서만, v1 4.5절과 같은 규칙).

### 5.3 단축키 (D-137: v1.6 키 유지, 3층, 선언형)
- **선언형**: 요소에 `data-shortcut="n"`과 설명 키(`data-shortcut-label="메시지 키"`)를 둔다. TS의 `ShortcutRegistry`가 문서에서 선언을 수집하고, **맥락 키(`H B C I M P Q`)는 사이드바 데이터에서 파생**한다(서버가 그린 항목의 `data-shortcut`). 안내(`?`)는 등록된 키에서 **자동 생성**하므로 안내와 실제 등록이 어긋나지 않는다(shell-F5의 근본 해결).
- **세 층과 충돌 우선순위**: 화면 > 맥락 > 전역. 같은 키는 선언 위치로 명시한다.
- **입력 제외**: `INPUT`, `TEXTAREA`, `SELECT`, 편집 가능 영역, 편집기, 입력기 조합 중에는 동작하지 않는다. 한 글자 단축키 끄기 설정(기본 켜짐, `prefs`)을 둔다(WCAG 2.1.4).
- **새 키**: `?`(안내), `/`(검색), `Esc`(닫기), `[`(사이드바). `F`/`ㄹ`은 전환기. `CTRL+SHIFT+ENTER`는 이미 동작한다(shell-F4).

## 6. 구현 구조: Bootstrap 5와 TypeScript

### 6.1 구성 (스크립트 전환 조사 `ui-ts-inventory.md`에 따라 조정)

- **사실**: `esm/` 88개 모듈(18,636줄)은 **이미 ES 모듈**이고 import map으로 불러온다. 그래서 전환은 모듈 시스템 변경이 아니라 **타입 붙이기와 빌드 단계 추가**이다. Gradle에는 npm을 부르는 Sass 단계가 이미 있어(`build.gradle.kts:266-308`) TS 빌드는 같은 모양의 작업 하나를 더하는 일이다.
- **도구 체인(권장)**: **`tsc` 단독**. 입력과 출력이 1:1(`esm/X.ts` → `esm/X.js`)이라 import map, `th:src`, 모듈 이름 계약이 그대로이고 `register`의 모듈 단일성이 유지된다. `isolatedModules`와 `verbatimModuleSyntax`를 켜 두어 `tsc`가 느려지면 esbuild 변환 + `tsc --noEmit`으로 바꿀 길을 열어 둔다(저장소 밖 선례 `components/editor`가 esbuild를 쓴다). Vite 번들은 파일 구조와 `register` 단일성을 바꾸므로 쓰지 않는다. (이 문서 초안은 esbuild를 먼저 제안했으나 조사 결과 구조 보존이 더 중요해 `tsc` 단독으로 고쳤다.)
- **출력과 위치**: 산출물은 **빌드 때 만든다**(Gradle `installTs`와 `compileTs`, 입력이 바뀔 때만, `processResources`에 합침, 커밋하지 않음). TS 원본은 `static/` 밖(예: `src/main/frontend/ts/**`, 가칭)에 둔다. `static/` 안에 두면 `AssetFilter`가 `.ts` 원문을 그대로 서빙하기 때문이다. `package.json`은 선례대로 `build-tools/ts/`에 둔다. 한 모듈을 옮기는 커밋에서 `esm/<이름>.js`를 지운다.
- **추적되지 않는 `frontend/`**(`node_modules/@hotwired/turbo`뿐)는 TS와 무관하다. 정리할지는 선생님께 묻는다(D-139 7번).
- **디렉터리(새 모듈)**: `esm/` 안의 기존 구조를 이어 쓴다.
```
esm/shell/     Page.ts(수명주기), shortcuts.ts, sidebar.ts(접기, 구간, 기억), switcher.ts, toasts.ts, dialogs.ts
esm/store/     IndexedDB(`yona-ui`: drafts, switcher, prefs, visited, search-history, meta), 거울, 메모리 폴백
esm/core/      config.ts(컨텍스트 경로, url()), 메시지 키 타입(후속)
types/         yona-globals.d.ts($yona, Messages, yona, jQuery 플러그인 선언), server.d.ts(서버 값의 타입)
```
- **엄격함**: 새 모듈은 `strict`, `noUncheckedIndexedAccess`, jQuery 비의존(DOM 표준 API)이다. 옛 모듈을 옮길 때는 **동작을 바꾸지 않고 타입만** 붙인다(v1.6 동등성). **타입 옮기기와 수명주기(swap-safe) 고치기는 같은 변경에 섞지 않는다.**
- **옛 전역에 대한 계약 걸림돌 4가지**(조사 결과, 처음에 풀어야 한다): (1) 템플릿이 `yona.Mention({...})`처럼 `new` 없이 부르는 전역이 있어 `class`로 바꾸면 깨진다. (2) `yona.Common.js:21-23`이 `$yona = ...` 암묵 전역을 만들어 모듈로 옮길 수 없다(`.d.ts`로 선언하고 구현은 사용처가 안정된 뒤에 옮긴다). (3) `yona.Csrf.js`는 XHR와 `fetch`를 교체하는 클래식 스크립트로 요청보다 먼저 실행되어야 한다. (4) `loadModule`의 폴백 경로(`service/yona.X.js`)는 지금 죽은 경로이다(정리는 선생님 확인 후).

### 6.2 수명주기: 모든 화면 모듈은 `Page`이다
```ts
export interface Page { mount(root: HTMLElement, ctx: PageContext): Dispose | void }
```
`mount`는 **교체된 본문 루트**에서만 일하고(문서 수준 핸들러 금지, 위임은 루트에), 반환한 `Dispose`로 모든 것을 정리한다(`AbortController`로 이벤트와 요청을 한 번에 해제). htmx가 본문을 바꾸면 이전 `Page`를 `dispose`하고 새 `Page`를 `mount`한다. 이 규약이 있으면 **TS 화면은 처음부터 swap-safe**이다(D-136 결정 5).

### 6.3 서버가 박는 값과 주소
- **전달 방식(조사 권장)**: 전역 값(컨텍스트 경로)은 `<meta>`, 화면 값은 `data-*`, 객체나 배열은 `<script type="application/json">` 한 개이다. **화면을 옮길 때 함께 바꾸고**, 옮기기 전까지는 지금의 `th:inline` 인라인을 둔다. `data-*`는 요소와 함께 교체되어 htmx의 `Page.mount(root)` 모델에 바로 맞는다. 서버에 안전한 JSON 직렬화 도우미(`</script>`, `<!--` 탈출)가 필요하다. `window.yonaContextPath`는 옛 모듈용으로 유지하고 새 모듈은 `url()`만 쓴다.
- **주소는 반드시 `url('/x')`로 만든다.** 문자열 `"/"`로 시작하는 주소 리터럴은 린트(`no-restricted-syntax`)로 금지한다. 서버가 주는 주소(`data-href` 등)는 이미 접두어를 가진다. `ContextPathLinksTest`는 새 셸에도 적용한다(사이드바, 전환기 조각 포함).
- **메시지 키 타입**은 후속이다. 처음에는 지금의 `/messages.js`(전역 `Messages`)를 `declare function`으로 선언해 쓴다(조사 권장). 키 유니온 생성(`messages*.properties` 5개 언어와 동기 빌드)은 TS가 자리 잡은 뒤 별도 결정이다.
- **서버 응답 타입**: 화면이 쓰는 JSON 응답은 `types/server.d.ts`에 계약(`ui-contract`)대로 선언한다. (외부 REST의 OpenAPI에서 생성하는 안은 화면용 AJAX가 OpenAPI에 없어 이번 범위 밖.)

### 6.4 시험
- **현 체계**: JS 시험은 67개 파일, 약 650항목이고 Gradle 밖에서 수동 실행된다. 하네스는 소스 텍스트를 정규식으로 잘라 클래식 스크립트로 바꿔 돌린다(`classicFromEsm`)이라 TS 원문을 직접 읽지 못한다. Kotlin 시험 11개도 JS 원문을 읽는다.
- **권장**: (1) 시험 전에 TS를 빌드해 **산출 JS를 현행 하네스로** 시험한다(시험 650개가 거의 그대로 돈다, 수정은 하네스의 경로 한 곳과 Kotlin 원문 시험 11개). (2) **새 모듈은 모듈 방식 시험**(`esm.test.mjs` 방식, 실제 Chromium)으로 한다(IndexedDB, `BroadcastChannel`, `htmx:load`를 실제로 시험하기 위해). (3) `tsc --noEmit`을 시험의 첫 단계로 둔다. (4) 시험 코드를 TS로 바꾸는 일과 JS 시험을 Gradle에 연결하는 일은 이번에는 보류한다.
- **화면(Playwright)**: 뷰포트 6가지, 서랍 초점, 깜빡임 0, 폭을 바꿔도 입력 유지, htmx 이동 뒤 사이드바 유지와 `Page` 정리(핸들러 누적 0).
- **서버(Kotlin, 기존)**: `ContextPathLinksTest`, 메뉴 끈 기능 404 시험, 주소 불변 시험이 계속 지킨다. 새 시험: 사이드바 데이터가 서버 검사와 같은 조건을 쓰는지(항목이 보이는데 주소가 404이면 실패).

### 6.5 공존 규칙 (옛 모듈과 새 모듈)
- 한 화면은 **옛 방식이거나 새 방식**이다(섞지 않는다). 맥락 단위로 전환한다(D-134 결정 4).
- 새 셸이 켜진 맥락의 화면은 옛 모듈을 전역 선언(`yona-globals.d.ts`)으로만 부른다. 옮기지 않은 화면의 스크립트는 그대로 동작해야 하고, 새 셸은 그 화면을 **일반 이동**으로 연다(`data-swap-safe` 없음).
- 옛 전역(`yona.*`, `$yona`)은 새 코드가 **선언으로 읽기만** 하고 쓰지 않는다.

## 9. 확인하지 못한 것

- GitLab의 현재 화면과 용어는 대조하지 않았다(일반 지식).
- 폰과 폴드 기기의 실제 폭과 접힘 비율은 에뮬레이션 뷰포트로만 측정한다(v1의 9절과 같다). 터치와 서랍 제스처는 실제 기기 확인이 필요하다.
- 4.7절 A안의 **기존 화면 경계 이동의 영향**은 구현 전이라 측정하지 못했다(P0 시험에서 확인).
- 4.3절의 보이는 조건 중 일부는 계약의 권한 행렬을 요약한 것이다. 템플릿별 정확한 조건은 `ui-screen-map.md`가 근거 줄 번호와 함께 가진다.
- TS 빌드 시간, `checkJs`로 돌린 타입 오류 수, 시험 650개의 현재 통과 상태, 새 모듈의 실제 규모는 측정하지 않았다(조사는 읽기 전용이었다). `@types/*`의 존재는 일반 지식이다(`ui-ts-inventory.md` 8.4절).
- 화면 대응표의 Bootstrap 구성 요소 열은 계약과 옛 클래스 표지에 근거한 설계안이며 템플릿을 줄 단위로 대조하지는 않았다. swap-safe 판정은 예비 판정이다(`ui-screen-map.md` 끝).
